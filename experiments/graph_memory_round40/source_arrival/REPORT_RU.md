# Можно ли сохранить оптимальную выдачу при поступлении нового источника

Дополнили ранее проверенный отзыв операцией поступления свидетельств. Из 1 264 добавлений источника при исходной видимости 50% в **803 случаях (63,53%, 95% ДИ 55,25–70,41%)** одного сравнения оптимальных значений было достаточно, чтобы сохранить прежнюю выдачу. Полный пересчёт выявил 815 неизменившихся выдач. В 12 случаях консервативный алгоритм выполнил лишний пересчёт. Во всех 1 264 случаях конечный упорядоченный набор совпал. [Протокол](PROTOCOL_RU.md) · [Все исходы](results.json)

Пусть обязательный префикс после открытия источника остался прежним, C — токены на хвост, V(k) — максимум полезности прежних узлов при k токенах, A — кандидаты открытого источника. Лучшее решение с хотя бы одним новым узлом имеет значение max по непустым S⊆A при cost(S)≤C от выражения **u(S)+V(C−cost(S))**. Это следует из разложения любого допустимого набора на старую и новую части. Если максимум меньше V(C), прежняя выдача остаётся единственным ранее избранным победителем по фиксированному правилу разрешения ничьих. При равенстве выполняем пересчёт. При одном новом узле нужна одна операция поиска в массиве V. При нескольких узлах используем динамическую программу. Поэлементная проверка может ошибиться, когда два новых узла выгоднее брать вместе. Это воспроизведено на явном примере в тесте перебором. [Целочисленный оператор](admit.cpp) · [Независимый перебор, 30 576 сравнений](exhaustive.py)

На основном срезе медиана одного исполнения составила 19,9 мкс против 49,8 мкс. Сохранённый массив занимал 8 216–12 136 байт на запрос. Медиана первичного расчёта старого кэша 64,75 мкс, измерена отдельно. Обе ветви получают готовые массивы кандидатов, режимы чередуются. Распределение открытия источников смоделировано по хешу. У 40 запросов зафиксированы исходные ранги и полезности полной истории. Результат применим к обслуживанию одного такого снимка.
