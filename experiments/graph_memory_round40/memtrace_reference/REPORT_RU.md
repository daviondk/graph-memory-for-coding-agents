# Исходная инвалидация MemTrace после правок файлов

Реальный SemanticStore из открытого MemTrace после 2696 подтверждённых изменений сохранил весь прежний пакет в **6** событиях. При отдельном пересчёте по интервалам предыдущий порядок и состав сохранились в 691, из них **664** выдержали последующую проверку байтов изменённого пути. Одинаковые исходные блоки и действия использовались во всех условиях. На всех 2696 событиях фактическое множество закрытых строк в SQLite совпало с авторским предикатом и файловым правилом. Каждой закрытой строке соответствовало реальное ребро INVALIDATED_BY, запись и история остались в базе. В основной группе строже проверенная выдача дала 172 парных выигрышей и 0 проигрышей по повторному использованию целого пакета. Интервалы получены 10 000 перевыборками целых задач с возвращением; дополнительные траектории используют те же задачи. [Численные результаты](results.json) · [Код оценки](grade.py)

Исходный компонент обработал 10,805 вхождений старых блоков. Он закрыл 10,083 из них, или 2,365,732 из 2,529,528 байтов исходной выборки. В старой ревизии осталось 722 активных вхождений. Новый точный запрос со старыми ключами получил 0 попаданий. Суммы учитывают повторные чтения и не являются уникальными байтами проекта или физическим I/O. Две оригинальные проверки авторов выполнены без изменения кода. В отдельной SQLite с двумя символами одного файла, объектом самого файла и другим файлом указание одного изменённого символа закрыло один объект, указание целого файла закрыло три. [Авторские тесты и диагностика](fixtures.json) · [Нативный запуск](replay.py)

**Что именно проверяет сравнение.** Для каждого прежнего фрагмента создана запись CODE_OBSERVATION с идентификатором файла и отличимой семантической ролью. В SemanticStore.advance_workspace_revision передан один изменившийся файл. Интервальный алгоритм дополнительно использует границы замены из того же события. SDK распознаёт точные идентификаторы файлов, символов и тестов; для смещений произвольного блока в этой операции отдельного поля нет. Если известны надёжные события на уровне символа, фактическая гранулярность MemTrace может повыситься. Даже непогашенную запись со старой ревизией исходный ContextAssembler помечает при восстановлении на новой ревизии как историческую и требующую повторной проверки. Прежние метки активности SQLite и полная текущая выдача относятся к разным шагам. Первые 64 транзакции заранее фиксированы по хешу идентификаторов. При медиане 0,261 с на событие эксперимент продолжился на всей панели. Время обработки составило 12,9 мин, включая создание отдельного хранилища, страницы, SQL-проверки и освобождение файлов на каждом событии. Этот показатель относится к проверочной установке. [Условие продолжения](pilot-decision.json) · [Воспроизведение](REPRODUCE_RU.md)

**Как это соотносится с предыдущей работой.** R10 уже использовал нативный MemTrace для хранения и восстановления результатов тестов с разными ревизиями и реального повторного исполнения pytest. Там оценивалась достоверность 418 выводов о тестах, здесь — инвалидация чтений исходного текста при 2 696 подтверждённых действиях Handoff Debt. Числа интервального контроля были известны из R40/span_updates. Новое наблюдение подтверждает, что их файловый компаратор при заданных входах действительно реализуется реальным SQL-компонентом MemTrace. Доступны только участки затронутого файла; другие пути считаются фиксированными. Проверка не измеряет конечное качество действий LLM или обобщение на новые репозитории.
