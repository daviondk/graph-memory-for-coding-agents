# Где исполнять точный top-8 графовой памяти

Используем неизменяемый журнал совместных изменений файлов из R56. Обработчик SQLite и читатель располагают общей нумерацией путей. Клиент может менять вторичный порядок при равных частотах. Проверяем, достаточно ли передавать все положительные счётчики выше восьмого места и целиком группу равных на границе. Если положительных соседей меньше восьми, клиент самостоятельно дополняет ответ нулевыми из собственного списка. Для одинакового числа совпадений оба режима применяют один и тот же клиентский порядок.

**До измерения.** Основная выборка — три длинные истории R56, дополнительная — шесть историй B. Задания, границы истории, ID, порядок путей и независимый битовый оракул берём без изменений. Репозитории и запросы повторяются по отношению к R57. Сравниваем на каждом запросе реальный сериализованный размер запроса и ответа с однобайтовыми операциями, одной длиной сообщения varint и положительными/смещёнными ID, без заголовков транспортного протокола. Протокол без состояния между запросами. Первичная метрика — отношение суммарных байтов для границы против всех положительных частот, отдельно по панелям. Ценность выявляется при сохранении точных восьми ID, порядка и оценок во всех запросах. Также покажем размер полной выдачи, среднее, медиану, 95-й процентиль объёмов, число RPC и SQL-чтение внутри сервиса.

**Сильные контроли.** (1) Полные положительные счётчики, сгруппированные по баллу с разностным кодированием ID. (2) Ранжирование целиком на сервере при доступности того же порядка обоим концам. (3) Для частного клиентского порядка передаём серверу доступную компактную спецификацию — все ненулевые частоты за 32 изменения и длину каталога; при полном совпадении допустим только честный учёт обеих сторон обмена. (4) Небольшое дополнительное сообщение в первоначальном запросе — восемь известных клиенту лучших ID по вторичному порядку; если в граничной группе хватает таких путей, сервер может сократить эту группу до точного набора. В остальных случаях передаёт весь остаток, достаточный для произвольного продолжения порядка. Параметры, включая k=8, фиксированы. Полные тела для каждого запроса обслуживаются одной и той же SQLite filelist внутри сервиса, число вызовов и реальные BLOB регистрируются отдельно. Здесь проверяется граница между сервисом и клиентом. Её байты не суммируем с внутренними без явной маркировки.

**Проверка причинного объяснения.** Если группа с одинаковой c-й частотой пересекает границу k и клиент может задать любой порядок внутри неё, каждый участник может войти в ответ при некотором допустимом порядке. Разные порядки переберём исчерпывающе на малых графах. Для реальных историй проверим точный вывод и при исходном, и при заранее определённом ином порядке (обратный ID). Ранги без общих метаданных в такой проверке пересчитываются независимо от SQL. Только реальная сериализация, длина декодированных байтов, сырые построчные результаты и digest на панель. Размер ответа не свидетельствует о росте качества решения задач или меньшем числе внутренних обращений к архиву.
