# Какие события графовой памяти стоит сохранять перед перезапуском

На длинных Git-историях отбор по прошлой частоте участия файлов сократил суммарную передачу данных через SQLite с 106 186 до 82 907 байт относительно снимка последних событий при одинаковом лимите 1 КиБ на репозиторий (−21,9%). Холодный запуск потребовал 106 781 байт, отбор самых длинных тел — 88 562. Одни и те же ранжированные ответы получены во всех вариантах. Выигрыш относится к переданным байтам при запланированном перезапуске. На коротких историях наименьший трафик дал полный снимок без заполнения до лимита; по времени всей инструментированной нагрузки преимущество предлагаемого метода отсутствовало.

## Механизм и проверка

Единица памяти — ранее наблюдавшийся Git-коммит с упорядоченным списком файлов. Обращение по одному файлу возвращает восемь кандидатов по историческим совместным изменениям. База хранит все события. В процессе работы каждый файл удерживает восемь недавних событий; событие доступно через любого его участника, пока его удерживает хотя бы один файл. Граница планового перезапуска проходит после половины принятых событий проекта. Снимок сохраняет выбранные события из доступной на границе памяти. После перезапуска они закреплены в RAM до конца сессии. Новые события обслуживает тот же кеш, пропущенную историю загружаем из общего точного индекса. Лимит снимка ограничивает запись на диск, объём развернутого в Python кеша измеряем отдельно.

Для каждого события оцениваем экономию байт тела на один байт записи. Экономию предсказываем по длине тела, умноженной на сумму сглаженных частот его участников в предшествующих 128 событиях. Размер записи включает тело, номер события и длину. Более высокий счёт даёт приоритет при заполнении. Для сравнения применены те же упаковка, ранжирование, данные и лимиты к двум простым порядкам — по давности и по длине тела. Последующие запросы и составы коммитов при выборе недоступны. Правило пропускает подтверждённую полную историю только при сохранении доказательства полноты; списки и недостающие тела остаются доступны в полном индексе. [Заранее зафиксированный протокол](PROTOCOL_RU.md) · [Реализация](checkpoint.py)

Зафиксированы 6 049 исходных событий в девяти репозиториях, 880 вопросов короткой панели B и 196 вопросов длинной панели. После границы остаются соответственно 492 и 196 вопросов. Полная история служила эталоном для упорядоченных пар «файл, балл». Выполнено 216 прогонов SQLite (8 методов × 9 проектов × 3 блока), всего 25 824 проверки ответов, включая 16 512 после границы. Порядок методов внутри проекта случайный, seed 58041. Отдельная реализация восстановила из источника множества сохранённых событий, размеры тел, списки адресов, попадания и SQL-вызовы для всех 16 512 пострестартовых записей. Для четырёх состояний снимка дополнительно проверены 24 ранжирования: корректный снимок, повреждение контрольной суммы, устаревшая версия источника, отсутствие таблицы. [Независимая проверка](audit.py) · [Результаты проверки](audit.json)

## Стоимость передачи

В итог входят запись и загрузка снимка, 20 байт SHA на репозиторий для проверки привязки снимка к источнику, а также все BLOB списков и недостающих тел, возвращённые после рестарта. Холодный запуск обходит операции со снимком. Заголовок, контрольная сумма и padding входят в размеры. Общие всем вариантам исходные записи коммитов не входят в показатель. Физические WAL, размер БД, число вызовов и CPU приведены отдельно. В таблицах байты суммированы по уникальным репозиториям одного блока. Повторы не увеличивают объём выборки.

В основном сравнении на длинной панели экономия против отбора самых длинных тел составила 5 655 байт (6,4%), против холодного запуска — 23 874 байта (22,4%). Большая часть эффекта по сравнению с давностью уже достижима по одной длине. При 4 КиБ экономия относительно длины уменьшилась до 1 155 байт (1,8%). По сравнению с полным снимком при 4 КиБ передано на 7 935 байт меньше (11,4%), хотя последующие чтения при полном снимке были быстрее. Это расчёт логических байтов; время и физические страницы для такой модификации не измеряли.

Время — медиана трёх блочных сумм одной машины. Сумма измеренных операций включает запись исходных событий, запросы, обновление счётчиков, выбор/запись снимка, checkpoint после записи и открытие; общие служебные операции цикла и финальный checkpoint в неё не входят. Журнал измерен после одной отдельной FULL WAL-транзакции до checkpoint. На трёх длинных проектах запись суммарно 3 072 байт снимка породила WAL размером 24 816 байт. По этим данным нельзя переносить сокращение передаваемых приложению байтов на объём чтения диска или общую пропускную способность устройства.

На длинной панели при 1 КиБ частота сохранила 63 события, давность — 291, длина — 45. За первые десять вопросов каждого проекта частотный отбор передал 11 920 байт списков и тел, давность — 15 035, холодный — 16 176, полный — 2 795. За все последующие вопросы число SQL-вызовов для списков и тел составило 344 против 338 у давности: экономию дало уменьшение размеров запрошенных тел. Поддержание частот заняло 12,08 мс, выбор снимка — ещё 12,73 мс против 2,93 мс у давности. Сумма оценок Python-объектов закреплённого кеша сразу после открытия — 288 228 байт против 259 176 у давности и 1 604 072 у полного снимка. Дополнительно кольцо частот и счётчики непосредственно перед рестартом оценены в 140 906 байт. Это размеры достижимых объектов Python, а не RSS процесса. [Все метрики и повторы](results.json)

## Границы результата и воспроизведение

Проверены запланированная остановка в одной точке истории и один последующий сеанс. При аварийном завершении до создания снимка остаётся точный холодный индекс. Реконструкция истории Git моделирует адресный доступ к графовой памяти. Показатели качества работающего LLM-агента, ускорение пользовательских задач и преимущество перед внешними системами в данном опыте не измерялись. Три длинных проекта позволяют показать эффект на каждой отдельной истории; этого недостаточно для интервального вывода о проектах вообще.

Из этого каталога выполнить:

```console
python -B bench_restart.py --verify
python -B audit.py --verify
```

Первая команда повторяет агрегацию сырых измерений и сверяет контрольную сумму протокола и подписи эталонных ответов. Вторая независимо проверяет затраты и точность. Для нового прогона времени можно использовать отдельную копию checkout без существующих `runs.json.gz`, `results.json` и `audit.json`, затем выполнить `python -B bench_restart.py` и `python -B audit.py`. Измерения записаны по запросам с фазой, временем, количествами и объёмами обращений. [Сырые измерения](runs.json.gz) · [Драйвер](bench_restart.py)
