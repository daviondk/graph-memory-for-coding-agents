# Хранение повторяющегося текста под разными адресами в памяти агента

В R57 на 108 опубликованных сессиях SWE-agent группировка строк по файлам полностью воспроизвела результат графового кэша. Вместо очередной настройки сходства файлов проверяем другую гипотезу: при жёсткой ёмкости часть байтов стоит выделять под дополнительные адреса, сохраняя одинаковый текст один раз. Сравниваем также политику защиты строк, повторно запрошенных с тем же содержимым по тому же адресу. Используем **только** сохранённый обезличенный prefixes.json.gz R57. Никаких текстов кода, команд, патчей или новых загрузок. Идентификатор содержимого в сессии обозначает точное равенство байтов; присвоенная ему численная величина для ранжирования не используется.

**Первичная пара (16 КиБ).** Одинаковый порядок удержания: наиболее недавно прочитанный файл, затем более недавно прочитанные строки этого файла. Обычный вариант записывает полную строку под каждым удержанным адресом. Наш вариант при уже удержанной побайтно равной строке репрезентирует дополнительный адрес ссылкой. На запрос отвечаем по состоянию **до** его наблюдения. Совпасть обязаны путь, номер строки и всё содержание. При каждом барьере R57 все таблицы и содержимое очищаются. Две сессии одной задачи никогда не обмениваются данными. Мы оцениваем способность обслужить записанные действия; влияние на успех исправления этим replay не определяется.

**Равная вместимость.** Фиксируем простой полный формат контрольной точки. Заголовок — 8 байт (число файлов и строк). На активный файл — 4 байта длины и полное имя UTF‑8, локальный ID задаётся позицией в записи. На сохранённый адрес — 12 байт: индекс файла, номер строки и управляющее 32-битное слово с длиной литерала либо индексом уже перечисленного идентичного буфера. Флаг защищённого сегмента помещается в старшие биты управляющего слова. Ряды хранятся в порядке давности строк, файлы — в порядке давности файлов; восстановление обеих очередей возможно по порядку записи. У положения несжатого варианта такой же заголовок; длина нужна для восстановления произвольной строки. В основной паре разная только необходимость повторно передавать тело одинаковой строки. Учитываем размер активного словаря путей, всех адресов и самих хранимых байтов после каждого чтения. Индекс хеширования для быстрого поиска литералов не входит в сериализованное состояние; алгоритм может находить равенство линейным сравнением. Задержка и фактический RSS не являются показателями. Публичная проекция позволяет точно вычислить длину и класс идентичности каждого тела, но не содержит его оригинальных байтов. Дополнительно на синтетических буквальных строках проверяем настоящий encode/decode и сохранение порядка/ссылок.

**Контроли.** С тем же форматом и ёмкостью: обычный глобальный построчный LRU; его вариант с однократным хранением одинаковых строк; LRU по файлам с полными строками и со ссылками; защищённый двухсегментный LRU по строкам с обоими представлениями. Для двухсегментного варианта повторное совпадение того же резидентного адреса и содержимого на более позднем показе даёт приоритет. Половина ёмкости зарезервирована как максимум для защищённых строк по давности; лишние переходят в обычную очередь. Затем заполняем остаток в порядке давности, пропуская строки, которые уже не помещаются. Пропуск и последовательность решения совпадают для всех политик. Обновление содержимого сбрасывает защиту. При сравнении LRU по файлам с предыдущим источником дополнительно воспроизводим прежнюю модель расхода только на полезный текст. Целевая рабочая точка — 16 КиБ, чувствительность 4 и 64 КиБ. Заранее включаем контроль постоянной цены адреса 8/16 байт вместо 12 при 16 КиБ. Это моделирование, отдельное от первичного реально сериализуемого формата.

**Метрики до открытия новых результатов.** Главная — разность долей байтов показа, обслуживаемых точно совпадающими резидентными строками, в процентных пунктах, по всем действиям (ratio of sums). 95% парный percentile-bootstrap 20 000 раз по issue, с сохранением обеих моделей одного issue вместе; seed 58017. Вторичные — число повторно использованных байтов, полностью покрытых показов, остаточные несовпадения, пик сериализованного размера и число неудачных вытеснений/случаев ссылки. Отчёт по каждому репозиторию и исполнителю. Дополнительно делим репозитории пополам сортировкой SHA‑256 строки «58017/имя» по возрастанию, назначения не меняем после оценки; гиперпараметры одинаковы в обеих половинах. Это проверка чувствительности к составу проектов. Эти траектории уже использовались в R57 и не являются независимой поведенческой выборкой. Для каждого нового показа логируем рассчитанный на прошлом прогноз и измеренное совпадение до обновления состояния. Отдельно публикуем отрицательные и нулевые результаты.
