# Инкрементальное обновление точной границы top-k по запросу

Вопрос для агента с частным порядком разрешения ничьих: что оставить на стороне сервиса после чтения файла, чтобы при следующем обращении читать только новые события? Из заранее наблюдавшихся величин храним смещение списка событий в байтах, частоты всех положительных соседей вплоть до границы с равенствами и максимум u среди отброшенных. На запросе получаем добавленный суффикс журнала для этого файла. Для сохранённых кандидатов частоты обновляются точно. Для остальных верна оценка u + max прибавки любого кандидата вне сохранённого множества. Если эта оценка строго меньше восьмой известной частоты, то граница точна при любом порядке ничьих. При u=0 известны все прежние положительные соседи и можно напрямую объединить все новые частоты. Если данных недостаточно, читаем недостающий префикс, учитываем его полную цену и восстанавливаем точное состояние. Холодный запрос строит состояние обычным способом.

Фиксируем до сбора результатов. Сравниваем на тех же 196 длинных и 880 коротких реальных запросах пять вариантов. Полный пересчёт без кеша, LRU полных счётчиков с дочитыванием суффикса, кеш восьмой границы с простым сбросом при изменении, проверка верхней границы (кандидат), и та же проверка с хранением до 16 позиций с равенствами (буфер по аналогии с Yi et al.). Для всех вариантов с кешем одинаковый лимит 1 024 байта на проект, дополнительный 4 096. Одинаковая LRU-дисциплина, одно кодирование varint для адреса, смещения, максимума и групп. В лимите также 8 байтов на слот для связей LRU. Отличаем сериализованную ёмкость от накладных расходов объектов Python. Каждый ответ должен давать тот же канонический пакет восьмой границы и ровно те же итоговые баллы с разрешением ничьих на клиенте. Сравним реальный суммарный объём данных из SQLite, число SELECT, число проверок, успехов и возвратов к префиксу, число размещённых и вытесненных состояний. Основная пара — граница против полных счётчиков, 1 КиБ, длинные истории. Записываем цену неудачной проверки без двойного считывания суффикса. Не заявляем новизну общей идеи материализации top-k или границ. [Yi и соавт., ICDE](https://cse.hkust.edu.hk/~yike/topk/icde03.pdf).
