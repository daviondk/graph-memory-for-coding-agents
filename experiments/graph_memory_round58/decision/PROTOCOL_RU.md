# Решение о записи снимка до рестарта

Исходные сводные итоги R58/restart и R58/restart_transfer для фиксированных режимов уже известны. Этот протокол фиксируется до расчёта адаптивных правил, покейсных сожалений и кривых горизонта. Это вторичный анализ сохранённых запусков. Калибровка — исходные девять проектов, перенос — обе нагрузки на каждом из следующих двенадцати проектов. Все случаи включаются. Единица сравнения — проект с нагрузкой. Две нагрузки одного проекта образуют пару.

## Наблюдения и действия

В момент записи известны только спрос из прошлых запросов и состояние памяти. Первичная политика: если до рестарта был хотя бы один запрос, записать снимок по частоте спроса с верхним пределом 1 КиБ, иначе запуститься без снимка. Публикуем случаи, в которых при нулевой прошлой активности будущее всё же сделало снимок окупаемым. Признак политики принимает ровно один аргумент — число предшествующих запросов. Название нагрузки, проекта, длина продолжения, идентификаторы будущих вопросов и стоимости альтернатив недоступны.

Сравниваем с постоянными решениями cold, demand ≤1 КиБ, full и с единственным постоянным решением, минимизирующим сумму байтов на девяти исходных проектах. При равенстве стоимостей порядок cold, demand, full. На внешних проектах фиксируем этот выбор. Сравниваем также фиксированный софт-лимит с физически дополненным нулями 1 КиБ из исходного протокола. В основном подсчёте реальная длина полезного снимка из SQLite-трасс заменяет длину дополненного тела в обе стороны. Счётчики обращений, полезное содержимое и SHA-проверка совпадают; если есть независимая физическая проверка режима без заполнения, укажем её. Full уже имеет переменную длину.

Дополнительное условие при **заранее объявленном числе будущих запросов**: по исходным девяти проектам для трёх фиксированных решений минимизировать сумму байтов отдельно для горизонтов 0, 1–4, 5–16 и ≥17. Пустая группа использует общее лучшее фиксированное решение для соответствующего горизонта оценки данных калибровки в целом. Для строгой однозначности калибровочные примеры включают четыре обрезки каждого исходного потока (0, 1, 4, 16 запросов при наличии, а также весь поток; совпадающие длины одного потока считаем один раз). Общий fallback минимизирует сумму на этих уникальных примерах. Для обычного фиксированного решения используем лишь полные потоки. Это условное сравнение с дополнительной информацией планировщика; в обычной политике будущий размер отсутствует.

## Исходы

Стоимость = байты записи + загрузки + проверка источника + фактически возвращённые списки и тела пострестартовых чтений. Включаем оплату снимка при нулевом горизонте. Сравниваем суммы, разницы по проектам и число побед/равенств/проигрышей; сожаление = разница с минимумом трёх решений на конкретном продолжении. Для внешней панели публикуем сводки оригинальных полных потоков и срезы 0/1/4/16 доступных запросов (при нехватке — весь доступный поток), точное число одинаковых наблюдаемых признаков с разным оптимальным решением, наихудшие наблюдавшиеся случаи. Больше положительных дельт означает больше затрат. Анализ детерминированный, новые наблюдения о времени и решении задач не собираем.

Для аудита политики сравниваем предрестартовые счётчики между руками одного проекта, проверяем повторяемую плату за заголовок и независимое восстановление оригинального оплаченного итогового объёма из записанных исходов; приводим SHA входов. Публикуем покейсные данные, включая нулевые и неблагоприятные случаи. Статистическую независимость двух потоков одного проекта не предполагаем.
