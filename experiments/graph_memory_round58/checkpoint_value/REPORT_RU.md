# Что даёт каждое сохранённое событие: формула и офлайн-оптимум

На 196 запросах по трём длинным историям мы нашли **точный максимум** экономии запросных данных для фиксированного снимка размером 1 КиБ на репозиторий в изученном SQLite-читателе. Даже зная весь будущий журнал, можно сэкономить не более **33 439 байт** внутреннего чтения относительно пустой памяти. Каузальный отбор по прошлой активности сэкономил **30 078 байт**, или 89,95% этого максимума. Все 30 078 байт пришлись на повторное использование тел событий. После оплаты записи, загрузки и проверки трёх фиксированных снимков чистая экономия составила 23 874 байта. На других проектах вклад пропущенных списков бывает положительным. ## Точная формула

Пусть S — сохраняемое подмножество ещё доступных до рестарта событий, bⱼ — число байтов в теле j, qⱼ — число будущих запросов по участникам j. Множество E_f содержит все дорестартовые события пути f, включая те, которые могли быть к этому времени вытеснены. Длительность жизни новых событий после рестарта зависит только от последующих записей. Величина w_f — сумма длин исторических списков на втором и последующих запросах к f после рестарта, если в момент очередного запроса все его послерестартовые события ещё удерживаются. Берём только непустые E_f, которые принципиально можно сохранить целиком. При таких условиях экономия относительно пустого старта в байтах запросов равна

$$G(S)=\sum_{j\in S} b_j q_j+\sum_f w_f\,\mathbf{1}\{E_f\subseteq S\}.$$

Первый член получается суммированием по фактическим обращениям к каждому телу. Второй возникает из условия полноты индекса. Первый запрос проверяет полноту в SQLite. Последующие могут обходиться без чтения списка адресов лишь при условии, что ни одно необходимое событие не отсутствует. Файл без дорестартовой истории может избежать таких чтений и при холодном старте, поэтому его вклад в разность равен нулю. Для фиксированного будущего эта функция супермодулярна: если для некоторого пути осталось добавить последнее из нескольких необходимых событий, оно даёт также весь бонус списка. Добавление того же события к пустому набору может дать только его собственные байты. Модель предполагает неизменную историю до границы, закрепление снимка до конца сессии, один заданный поток запросов и именно эту проверку полноты.

## Проверяемые границы

Стоимость записи каждого события cⱼ включает ID, длину и тело. Для 1 КиБ остаётся 984 байта после заголовка. Для каждого группового бонуса распределим w_f целочисленно по участникам E_f. Полностью выбранная группа получает тот же бонус, а частично выбранная может преждевременно получить часть. Значит, максимизация этой аддитивной суммы при том же бюджете обычным целочисленным рюкзаком даёт верхнюю границу. Проверяем три распределения веса, пересчитываем реальные значения найденных наборов и берём сильнейшие нижнюю и верхнюю границы. Только их совпадение устанавливает оптимум. Состояние хранится при одинаковом лимите по каждому проекту, общая оценка складывается по проектам.

На 140 малых задачах проверили интервалы против полного перебора подмножеств и 20 460 дискретных неравенств супермодулярности. ## Если снимок необязателен и имеет естественный размер

Дополняем ценность каждого события расходом на две передачи его записи. При непустом снимке вычитаем ещё 100 байт (два заголовка по 40 байт и 20-байтовый SHA). Пустой старт даёт нулевую чистую экономию. Для исходной длинной панели точный офлайн-оптимум чистой экономии равен 27 239 байтам. На 12 внешних проектах при редком потоке каузальная политика потратила **на 1 579 байт больше** холодного старта. При известных будущих запросах оптимум чистой экономии находится между **7 768 и 7 798 байтами**. На восьми проектах найден реально допустимый выгодный набор, на четырёх доказана оптимальность холодного старта по этой метрике. Даже точный офлайн-оптимум относится к фиксированному набору допустимых событий и назначенному потоку; это диагностика возможной экономии. В полном checkout из этого каталога: `python -B decompose.py --verify` и `python -B natural.py --verify`. Нужны Python, NumPy и зафиксированные журналы соседних экспериментов.

Отдельный аудит физически материализовал оба набора-свидетеля на всех 33 сочетаниях проекта и режима: 66 запусков SQLite и 5 880 проверок ранжирования. Достижимая экономия совпала с нижней границей в каждом случае. Границы сошлись в 26/33 случаях для фиксированного размера и в 17/33 для естественного снимка с возможностью отказа. Ещё 108 произвольных подмножеств дали 21 780 физических проверок; в 250 малых задачах с положительными и отрицательными чистыми ценностями интервал всегда содержал полностью перебранный оптимум.
