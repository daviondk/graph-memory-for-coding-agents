# Разложение ценности набора событий и верхняя граница для оракула

После измерения суммарных затрат исследуем механизм. Для фиксированной будущей последовательности запросов и записей экономия чтения тела события j при его закреплении равна длине тела, умноженной на число последующих запросов по любому участнику. Дополнительно можно пропустить чтение списка адресов для файла f после первого запроса, если сохранены **все** прежние события этого файла и все более новые его события остаются в горячей памяти. Поэтому ожидаем неаддитивную добавку за полноту множества старых событий. Материализация фиксированных кадров оплачивается независимо от их состава.

Сверим разложение с фактической разностью тела и списка в SQLite для всех восьми исходных вариантов на девяти исходных проектах и 12 проектах переноса в двух режимах. Для снимка с лимитом 1 КиБ построим офлайн-границы только как диагностику потенциального запаса. Нижняя граница максимума — любой реализуемый набор, выбранный по известному будущему. Верхняя — решение целочисленного рюкзака, где каждый достижимый бонус за полную группу распределён по её участникам неотрицательными долями с сохранением суммы. На частичной группе эта релаксация может переоценить бонус. Проверим распределение поровну (целые с остатком по ID), целиком первому или последнему событию. Возьмём минимум трёх верхних и лучший фактический набор от четырёх рюкзаков (в том числе по одним телам), с включением фиксированных контролей. Размер записи каждого кандидата и 40-байтовый заголовок те же, что в SQLite. Фиксируем до вычисления разложения, границ и доли дополнения на этих данных. Покажем ширину интервала и сравним каузальный отбор по прошлой активности с верхней границей. По будущим запросам нельзя выбирать онлайн-снимок. Малые случаи проверим прямым перебором всех допустимых наборов.
