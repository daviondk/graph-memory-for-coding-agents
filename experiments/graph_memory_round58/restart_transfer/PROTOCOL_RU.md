# Внешний перенос снимка при перезапуске

Документ фиксируется до вычисления затрат для этих проектов. Входы — два целых ранее опубликованных архива R57, replication/events.json.gz и seed_pair/events.json.gz, по шесть других репозиториев. Сохраняем все проекты и все нулевые/отрицательные результаты. Проверяем ту же политику R58/restart с тем же кодом SQLite. Протокол предыдущего исследования, данные, SHA голов и происхождение: [исходный опыт](../restart/PROTOCOL_RU.md), [группа replication](../../graph_memory_round57/replication/PROTOCOL_RU.md), [группа seed_pair](../../graph_memory_round57/seed_pair/PROTOCOL_RU.md).

**Первичный вопрос** — меньше ли логическая передача после учёта обеих сторон снимка при отборе по прошлой частоте, чем по давности, при 1 024 фиксированных байтах на проект, на внешних репозиториях. Первичная нагрузка повторяет исходную разреженную длинную панель R56/R58. Вопрос в коммитах второй половины исходного архива при наличии 2–64 путей, если целое SHA даёт остаток 0 по модулю 11; номер якоря равен (SHA div 11) mod число путей. Дополнительно проверяем более частую нагрузку по неизменённому протоколу B R56/R58: все коммиты с 2–64 путями после первых 64, якорь SHA mod число путей; первичные показатели относятся лишь к пострестартовым запросам. Предварительно известная нагрузка на этих архивах использовалась в других постановках R57. В этом опыте политика заморожена на предыдущих девяти проектах.

Граница — после floor(n/2) принятых событий с 2–64 путями, раздельно по проектам. Политики без снимка, полный снимок, давность, наибольшее тело и прошлый спрос с неизменными восемью событиями на файл и окном 128 событий. Для трёх ограниченных политик используем 1 024 байта и вторичный лимит 4 096 байт, физически включая padding, полезную длину записываем отдельно. Запись, загрузка, 20 байт проверочного SHA источника, пострестартовые varint-списки и все недостающие тела входят в общий трафик. В архиве без единого принятого события рестарт и платный снимок не моделируются, проект по-прежнему включается с нулём запросов и байтов. Если префикс до границы пуст, для всех режимов используется холодный запуск. Для непустого префикса стоимость заряжается даже при нуле последующих вопросов. Развёрнутая БД хранит полный архив, полный ранг включает восемь ID с баллами, tie-break повторяет исходный контракт. Равные нулю разницы, число проектов с выигрышем и проигрышем, веса крупнейшей истории и результат обеих исходных групп показываем явно.

По одному реальному SQLite-прогону на сочетание проекта, нагрузки, метода. Цель — байты и точность, время не является исходом. Один активный временный файл. Каждое ранжирование сравниваем с битовым эталоном всей видимой истории. Дополнительный независимый пересчёт по исходным членствам проверяет отбор и расходы на уровне каждого запроса, включая головы, query ID, плату за снимок, числа и байты SQL-обращений. Сохраняем фактические SQL-счётчики, длины снимков, WAL и итоговый размер базы. Единственная первичная пара — частота против давности, 1 КиБ, разреженный поток. Контроль по длине закрывает простое объяснение. Cold и Full оценивают возможный проигрыш при ненужном восстановлении. Без повторного выбора порога, формулы, проектов или горизонта после изучения результата.
