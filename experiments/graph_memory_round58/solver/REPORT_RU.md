# Что возвращать из памяти после первой попытки решения

На 21 функции из boltons, more-itertools и toolz выбор первой **нарушенной** исторической проверки изменил запись для трёх функций и исполняемую реализацию для одной. Это изменение не отразилось ни на одном авторском тесте. Обе политики, статический BM25 и поиск по результату проверки, дали 7/21 полностью корректных реализаций и 46/85 успешных примеров. Скрытие статуса или пересмотр черновика без дополнительной записи дали по 8/21. На этой выборке оснований предпочесть сообщение о нарушении нет. ## Исполнение и контроль

Три проекта и авторский doctest совпадают с [предыдущим экспериментом](../../graph_memory_round56/solver/REPORT_RU.md). Все целевые **функции новые** относительно его 36 целей. Из остальных функций, прошедших первоначальный фильтр, для 22 нашлась как минимум одна историческая проверка с явным вызовом функции и самодостаточными аргументами. Оригинальная реализация `pairwise_iter` сама не прошла один из трёх примеров в закреплённой среде, поэтому по предварительному правилу осталась 21 функция (5/8/8). На каждой оригинал прошёл все примеры, заглушка провалила хотя бы один. Эта выборка отобрана по наличию проверяемой истории. [Калибровка](calibration.json.gz) · [Источники и SHA](selection-seal.json)

Qwen3-4B-Instruct-2507 Q4_K_M на локальной RTX 3090 получила контракт и один ранжированный по BM25 тест из более раннего Git-коммита, затем написала черновик. Инструмент попробовал выполнить на черновике до шести записанных исторических утверждений. На следующем независимом вызове модель получила тот же контракт, тот же черновик и ровно 240 токенов под одну запись, включая нейтральное заполнение. Пустой контроль сохранил тот же бюджет. Ветвям доступны только историческое ожидание и наблюдение над своим черновиком. Используется greedy-декодирование с пределом 640 токенов на ответ. Исходные авторские doctest применены отдельным процессом после фиксации ответов. Оценивается восстановление тела функции в исходном модуле, с исходной сигнатурой и доступом к уже существующим вспомогательным функциям. Основная пара дала 21 ничью. Внутри наблюдённых данных парный бутстрэп по функциям вырождается в [0, 0], точный sign-flip по трём репозиториям даёт p=1. При таком числе различных решений оценить эквивалентность методов в генеральной совокупности нельзя. Для `windowed_iter` статическое и адаптивное сообщение породили разный исполняемый код с одинаковым результатом. Разница между 7 и 8 полными решениями в контрольных ветвях целиком пришлась на `product_index` (два примера). У `reshape` все ветви пересмотра решили три из семи примеров, первый черновик — ноль. ## Что ограничило эффект

Из 70 запланированных сравнений инструмент вернул 58 индивидуальных результатов. Для трёх черновиков парсер не допустил исполнение, одна функция исчерпала предел времени. Для всех 70 позиций итоговые метки составили 38 PASS, 10 FAIL и 22 UNKNOWN. Последняя включает отсутствующий ответ и исполнение, для которого прежний проверяющий модуль не вернул канонизируемое значение при отрицательном результате. Явно нарушенные наблюдения нашлись на пяти функциях, у двух первый BM25-пример уже был нарушен. Осталось всего три различающихся контекста в основном сравнении. Ограничение одинаковых входов задавало максимум 3/21 по абсолютному изменению доли решений ещё до оценки. [Назначения примеров и их статусы](assignments.json.gz) · [Ответы измерительного инструмента](probe-execution.json.gz)

После оценки сопоставили аргументы вызовов из прежних источников с входами текущих авторских примеров. Точные совпадения обнаружены в первом извлечённом отрывке на четырёх функциях, среди шести прежних проверок тоже на четырёх, объединение — пять. На оставшихся 16 основная пара дала по 5/16 и 38/64, пустой контроль — 6/16 и 37/64, контроль со скрытым статусом — 6/16 и 40/64. Аудит покрывает буквальное совпадение вызовов, смысловое сходство и возможное предобучение на открытом исходном коде остаются возможными. [Аудит по функциям](overlap.json)

Фактическую стоимость составили 21 общий черновик (6 420 входных и 6 496 выходных токенов) и 66 различных пересмотров (45 705 входных и 18 243 выходных токена). Каждая из четырёх ветвей имела ровно 14 507 входных токенов пересмотра на всю выборку. 18 назначений пересмотра имели токенные последовательности, побайтно совпадавшие со статическим контролем; им присвоен один и тот же новый greedy-ответ. В Docker выполнено 28 различных пар «функция, синтаксически допустимое тело». Файл решений получен живой генерацией; все прогоны состоялись на одной модели, одном устройстве и с одним seed. Это локальный эксперимент от выбора записи до результата текущего решателя. Данных о решении задач SWE-bench или о превосходстве над публичным SOTA он не даёт. ## Повтор

Быстрая проверка корпуса, хешей, равенства входных бюджетов и метрик выполняется командой `python -B verify.py`. Для повторной генерации нужны файлы GGUF и llama-server из [конфигурации R52](../../graph_memory_round52/reranker/common.py), закреплённые ZIP трёх библиотек и `author-inputs.json` из [подготовки R56](../../graph_memory_round56/solver/prepare.py), Docker с закреплённым образом Python, requests и CUDA. В PowerShell для Docker Desktop в этом окружении до запуска использовали `$env:DOCKER_HOST='npipe:////./pipe/dockerDesktopLinuxEngine'`. В чистой копии этого каталога с исходниками и протоколом последовательность команд — `python -B solve.py`, `python -B visibility.py`, `python -B evaluate.py`, `python -B verify.py`. Существующий журнал используется для возобновления только совпавших по хешу входов и конфигурации. Оригинальные фрагменты тестов и контракты распространяются по [лицензиям исходных проектов](../../graph_memory_round56/solver/THIRD_PARTY_LICENSES.md).
