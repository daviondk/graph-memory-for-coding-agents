# Какую запись памяти возвращать решателю после первого черновика

Проверяем память о прошлых тестах на новом наборе функций. В рамках одной задачи решатель сначала получает контракт и самый релевантный по полному BM25 исторический тест, пишет функцию, затем может пересмотреть решение. Между двумя обращениями к модели общий проверяющий инструмент выполняет до шести исторических утверждений на этом черновике. Политики отличаются тем, какое из наблюдений вернуть в контекст пересмотра. Это проверка воздействия одной записи на следующий шаг решателя. Текущие авторские doctest скрыты до оценки сформированных реализаций.

**Выборка.** Из полного закреплённого корпуса R56 берём все функции, отсутствующие среди 36 прежних экспериментальных целей, с хотя бы одним самодостаточным историческим утверждением, которое прямо вызывает целевую функцию. До просмотра новых решений по одному только наличию источников обнаружено 22 таких функции (6/8/8 по проектам). Используем прежние фильтры безопасных утилит, прежние SHA и извлечение утверждений, не расширяем набор проектами. Эталонная функция должна пройти все собственные doctest, заглушка должна провалить хотя бы один при том же числе тестов. Эту калибровку делает отдельный оценщик, только флаг пригодности могут видеть политики. Данные знакомы модели или могут содержать похожие старые примеры. Отдельно после выбора оценим буквальное пересечение аргументов прошлых проверок с текущими примерами; отбор по этой мере запрещён.

**Проверки в процессе работы.** Используем BM25 прежней работы по замороженному корпусу тестовых отрывков, затем упорядочиваем совпавшие записи по давности и стабильному адресу; внутри записи идём в порядке исходного кода. Дедуплицируем пары «выражение, тип сравнения, ожидание» и берём первые шесть. Утверждения допускают только прежний ограниченный синтаксис, длина формулировки с адресом ограничена для контекста. В рабочей памяти запись состоит из исторического адреса, ожидаемого значения и результата проверки только на собственном черновике. При ошибке парсинга или отсутствии ответа инструмента статус неопределён. Все ветви получают один и тот же список чисел проверок и один результат первого шага.

**Основная пара.** Статический BM25 всегда показывает первый исторический пример и его измеренный статус. Адаптивный поиск показывает первую по тому же порядку нарушенную проверку; если нарушений нет, возвращается первый пример. Третий вариант показывает ту же адаптивно выбранную запись, но скрывает статус выполнения. Дополнительный контроль пересмотра показывает тот же черновик и приглашение пересмотреть его без исторической записи. До трёх исторических вариантов ограничены одинаковыми 240 входными токенами для записи с заполнением нейтральным пробелом; аналогично у пустого контроля. Для черновика и каждой попытки пересмотра — до 640 выходных токенов, отдельный контекст, greedy и одна и та же Qwen3-4B-Instruct-2507 Q4_K_M на RTX 3090. Одинаковые токенные запросы получают одну детерминированную генерацию. Решатель может оставить первую реализацию словом KEEP. При непарсируемой попытке пересмотра засчитывается неудача, кроме явного KEEP.

**Оценка.** До открытия исходов вторых ответов фиксируем все их токены, ответы и решения о KEEP. Первичная мера — функция прошла все исходные авторские doctest. Дополнительно число успешных примеров, равновесная по функциям доля успешных примеров, результаты по проектам и разности по каждой функции. Интервал по парам функций имеет условную интерпретацию, кластерный exact sign-flip по трём проектам обладает низким разрешением. Обязательно показываем число реально различавшихся выдач и ответов, верхний предел возможного инкремента и абсолютную стоимость обеих стадий. Это исследование исполнения кода для выбранного класса задач. Проверку преимущества над SOTA оно не заменяет.
