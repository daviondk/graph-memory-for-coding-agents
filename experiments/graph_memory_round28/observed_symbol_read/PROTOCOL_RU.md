# Переход по наблюдаемому вызову в памяти кодового агента

## Вопрос и выборка

Может ли префикс выдачи, открытый по ребру «увиденный вызов → определение», покрыть больше исходных строк будущего изменения, чем второй блок обычного BM25? Это проверка оператора чтения внутри уже выбранного исходного файла. «Видимый» означает буквально в выданном тексте, тело невидимой функции не участвует в предложении перехода. В отличие от R27 ни выбор задач, ни выбор первого файла не используют целевую правку.

До чтения патчей и метрик фиксируем две непересекающиеся панели. Основная — SWE-Explore Verified в новых для R27 репозиториях sphinx-doc/sphinx, pytest-dev/pytest, pylint-dev/pylint, mwaskom/seaborn и ограниченном подмножестве django/django (только описания, упоминающие форматирование, виджеты, даты, представление или визуализацию). Архивы, тематические отсечения и допустимые производственные Python-пути фиксируются в prepare.py. Для каждого прошедшего фильтры issue сначала выбираем один опубликованный путь траектории по SHA256(issue NUL trajectory), затем самый ранний шаг, на котором прочитан допустимый производственный файл; при нескольких файлах одного шага берём минимум SHA256(issue NUL path). Не смотрим на будущие шаги, modified/core-файлы или итог задачи. Факт успешной траектории и принадлежности к авторской выборке известен заранее. Первая выдача — общий для всех искусственный BM25-блок исходного снимка этой траектории, а не копия терминального вывода.

Перенос — официальный Loc-Bench, отдельный набор репозиториев численных/ML/языковых или графических библиотек, без пересечения с обеими панелями R27 и основной R28 по репозиториям. Берём только файл, прямо названный путём к .py в исходном пользовательском описании, с удалением префикса среды, проверкой допустимых префиксов пакета, до восьми вариантов URL на задачу в фиксированном порядке. Обязательное условие — файл существует в base_commit. Это отдельная прикладная выборка задач, где в issue есть подсказка исходного пути. Никакой рандомизации/тюнинга политик между панелями. До подписания прогнозов parquet читается только колонками repo, instance_id, base_commit и problem_statement. Все файлы — исключительно статический текст. Никакой проверки решения, запуска приложений или загрузки текста будущего исправления.

## Операторы и цена

Общий первый блок содержит 16 последовательных строк, выбирается BM25 по query среди всех 16-строчных неперекрывающихся блоков видимого файла (ставки R27, k1=1.2, b=.75). Начальная цена одинакова для всех политик. Второе чтение получает до 256 настоящих WordPiece, включая заголовок [0:offset]. Один диапазон вправо, начиная с выбранной строки, вплоть до EOF. Выдача сохраняет первый блок. Нулевая выдача при отсутствии второго кандидата. У всех политик один и тот же файл, запрос, токенизатор и бюджет. Сохраняем адреса и SHA токенных id.

1. Базовый repeat_bm25 — открыть второй непустой блок по полному исходному BM25-ранжированию. Right — открыть продолжение первого блока.
2. Графовая политика query_call — токенизацией Python ищем имена, за которыми в прочитанном блоке идёт открывающая скобка, исключая собственные объявления def/class и содержимое строк/комментариев. Ищем одноимённые определения def, async def, class только в этом файле. Ребро ранжируется числом общих частей snake/camel имени и текста issue (уникальные части длины от трёх, кроме фиксированного списка распространённых терминов), затем числом видимых вызовов, первым наблюдением и физическим расстоянием. При нескольких одноимённых определениях предпочитаем ближайшее по строке от видимого блока, затем меньший номер строки. Видимые определения исключены. Перейти к определению разрешено только при хотя бы одном совпавшем терме; иначе fallback к repeat_bm25. Политика работает и без графового движка, для одноразового запроса достаточно найти определения реально наблюдаемых имен.
3. Первый доступный видимый вызов → ближайшее определение (обычный go-to-definition). Первый вызов по лексическому условию query_call без фильтра положительной близости. Имена, включая обычные ссылки, разрешаются и той же query-политикой. Чисто лексический поиск — та же выбранная строка имени, но открываем ближайшее буквальное упоминание вне первого блока, не требуя объявления. Прямая соседняя выдача и repeat_bm25 выступают самостоятельными контролями.
4. Отрицательный контроль — ровно та же активация query_call, но вызванная функция подменена иной невидимой функцией в том же файле по фиксированному циклическому сдвигу отсортированного набора строк определений на половину массива (при единственном адресе одинаковое поведение учитывается отдельно). Также оцениваем точное имя в запросе без требования, что вызов виден в первом блоке, с полнотекстовым индексом имён определений.

Измеряем суммарный размер прочитанных исходников, стоимость BM25, построение статического указателя def/class, стоимость ленивого сканирования текста только для востребованных имён, стоимость обращения к построенному индексу, число реальных переходов и строк разрешённых имен, влияние повторной адресации. Для динамического Python связь по имени/расстоянию — гипотеза о том, куда перейти, а не гарантированная цель исполнения. Отрицательный контроль и сравнение с дешёвым строковым совпадением нужны для оценки структурного вклада.

## Эталон и выводы

Только после SHA прогноза открывается patch. Из исходной стороны diff берем все удаленные или заменённые непустые строки допустимых производственных Python-файлов, отдельно проверяем совпадение текста каждого положительного адреса выбранного файла с его base_commit. Первичный исход — доля всех таких строк issue, полностью доступных в объединении двух выдач, включая нулевые исходы при неверном выборе файла. Если таких строк в issue нет (например, чистая вставка), указываем число, исключаем из основного знаменателя и приводим вариант с нулями; при несовместимых строках явно исключаем задачу без замены. Вторично — доля найденных строк внутри выбранного файла при ненулевом числе его эталонов, any/all, новые покрытые строки, стоимость, разделение по наличию целевого файла и активной/неактивной связи. Первичный контраст query_call против repeat_bm25 при точно одинаковой реальной индивидуальной длине. Для этого первичный общий cap уменьшается до достижимой общей фактической цены. На полном потолке 256 приводим и альтернативные политики. Для обеих панелей отдельные paired percentile 95% интервалы (10000 повторов по issue, seed 28028), числа выигрышей/проигрышей/ничьих и per-repo/leave-one-repo-out. Дополнительно интервалы повторной выборки целых репозиториев с сохранением весов задач, ориентировочны при малом числе проектов. Публикуем широкие ДИ и неуспехи. Отсутствие переходов/голых changed lines ограничивает измеримость и фиксируется. С официальной метрикой решения или репозиторного ранжирования эти величины не смешиваем.
