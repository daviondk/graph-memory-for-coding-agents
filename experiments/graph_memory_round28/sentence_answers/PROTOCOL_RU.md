# Прямое сравнение двух способов двустороннего чтения по конечному F1

Один основной контраст — token-both из R26 минус boundary_window из R27 по официальному SQuAD v1.1 Answer F1 на всех известных 576 dev-вопросах, 12 из каждой из 48 статей. У аналогов одна исходная память, одна выбранная компонента и тот же ридер. Boundary_window вычитает уже показанные координаты, берёт до трёх новых предложений слева и справа и перераспределяет неиспользованную часть квоты. Первичный R27 на 5 304 вопросах train измерял доступность размеченного адреса, без запуска ридера. Ни тексты, ни метки train не используются здесь. Известен результат R26 относительно других сравнений на dev. Настоящий F1 именно этих двух операторов ранее не использовался; эта выборка не является новым слепым корпусом.

Применяем без изменения operators.Reader R27 на официальных uncased WordPiece. Оба оператора получают серверный лимит от 0 до 256, подсчитываем состав всей сериализации, включая реальные строки заголовков. Native-токенизатор ридера — DistilBERT cased. Будем искать максимальную общую длину добавки до 256 native WP по всем целым исходным квотам от 0 до 256. Если максимальная физически возможная общая длина 256 подтверждена обоими операторами, остальные квоты можно пропустить. При одинаковой native-длине выбираем вариант с наибольшей исходной квотой. Метод никогда не превышает 256 uncased или cased WP. Показываем реальную дополнительную стоимость обоих токенизаторов и число диапазонов. Это ретроспективное выравнивание затрат двух допустимых выдач. Онлайн-агент заранее не знает, сколько потратил бы альтернативный оператор.

На dev запускаем настоящий SentenceWindowNodeParser 0.14.26 с библиотечным пунктуатором R27, проверяем каждую исходную подстроку и текст нативного окна. Неизменные выбор R25, код операторов и параметры R26 переносятся по хешам. Полученные диапазоны образуют отдельные записи с адресами. DistilBERT-base-cased-distilled-SQuAD, те же квантованные веса, batch 1, CPU 2 потока, окна 384 с перекрытием 128, до 30 токенов ответа. Декодер может вернуть лишь один физически непрерывный показанный фрагмент исходного текста. По каждому вопросу точно совпадают нативная длина полной сериализации и логический объём всех вычислительных окон. Совпавшие с предыдущими входы можно использовать по полной контрольной сумме сериализации, одинаковым координатам всех сегментов, параметрам ридера и последовательности хешей всех входных ID каждого окна. Старые логиты по отдельным окнам не сохранялись. Для остальных выполняется реальный ONNX на CPU. Число доставленных, переиспользованных и пересчитанных окон указывается отдельно.

Выбор примеров зафиксирован R25 независимо от разметки. Сначала фиксируем входы и 1 152 предсказания, затем рассчитываем официальный max-over-references F1/EM, совпадение эталонных координат, наличие эталона в непрерывном фрагменте и долю новых символов. 95% парный percentile bootstrap из 20 000 выборок по 48 статьям (seed 280347), числа выигрышей и потерь. Результат на известном dev и одном читателе ограничен этой постановкой. Сравнение с адаптивным выбором стороны из R26 имеет другие условия и отдельный результат.
