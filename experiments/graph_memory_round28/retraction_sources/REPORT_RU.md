# На каких данных проверять исправление памяти и чтение по адресу

Для проверки ответа на изменившийся факт наиболее удобен **STALE**. Публичный набор содержит 400 сценариев с явными старой и новой формулировками, двумя адресами в истории и тремя вопросами к одному сценарию. Для проверки **отзыва источника и распространения исправления по зависимостям** ближе **Dependency-Guided Rollback Repair**. Авторы опубликовали неисправные и чистые состояния, помеченные зависимости, эталоны и контрольные методы. Два теста измеряют разные эффекты. В STALE новое сообщение изменяет знание о пользователе. В Rollback исходная неисправность может уже быть диагностирована, а нужно исправить последствия. [STALE](https://arxiv.org/abs/2605.06527), [Rollback Repair](https://arxiv.org/abs/2608.10502).

## Честная blind-проекция

Подготовлен локальный поток для всех 400 STALE-кейсов: 20 000 сессий, 237 358 реплик, 1200 отдельных вопросов. Вход одного вызова — один вопрос, нейтральные идентификаторы источников и реплик, последовательность, время, роль, исходный текст. Ни вариант вопроса, ни два других вопроса этого сценария, ни старый/новый эталон читателю не передаются. Значения M_old, M_new, объяснение, тип и ожидаемые адреса отделены в каталоге evaluator. Реальные исходные timestamps отсортированы во всех 400 историях, индекс прежнего факта всегда предшествует новому. В обоих типах M_old дословно, после сведения регистра и пробелов, входит в нужную сессию лишь в 129 из 200 случаев; M_new — в 194/200 и 193/200. Проверка ссылки на сессию и проверка точного текстового спана — разные метрики. [Лицензированная публикация данных STALE](https://huggingface.co/datasets/STALEproj/STALE/blob/617c51dc200b5ab09970834144c7e51c77959af0/README.md).

Официальный baseline применяет evidence-preserving truncation только для помеченных авторами настроек и превышения окна: функция trim читает gold-индексы и удаляет соседние/промежуточные сессии так, чтобы сохранить оба эталонных источника. Для сравнения с такой строкой авторской таблицы нужен отдельный запуск под тем же правилом. Строгий blind-поток сохраняет всю историю и учитывает только фактически выбранные агентом адреса. В опубликованной таблице CUP-Mem даёт 68,0% среднего по двум типам и трём измерениям; это авторское комплексное значение, без совпадения reader, judge, бюджета и протокола ввода переносить его на наш ретривер нельзя. [Исходник обрезки](https://github.com/icedreamc/STALE/blob/ea7d391103a151927cd29d2f01d87597a782bdcb/STALE/Evaluation/run_target_model.py), [авторская таблица](https://github.com/icedreamc/STALE/tree/ea7d391103a151927cd29d2f01d87597a782bdcb).

Для последующего испытания сравнить полный контекст (когда помещается), BM25, BM25 с сортировкой только найденных результатов по времени, выбор последнего утверждения об объекте, CUP-Mem, сохранение версионных связей плюс чтение исходного сообщения и случайную перестановку связей при совпадающем числе выданных токенов. Основной показатель — доля успешных **ответов** при одинаковых reader, judge и бюджете, отдельно три авторских измерения State Resolution, Premise Resistance, Implicit Policy Adaptation. Диагностика — наличие старого и нового источников, корректность ссылки и условная точность ответа после получения нового источника. Oracle с обоими эталонными сеансами нужен отдельной строкой. Три вопроса каждого сценария сильно зависимы; 33 группы дословных старых фактов повторяются между сценариями. Нужны парные интервалы по сценариям, дополнительная группировка по повторяющимся семействам и отдельное тестирование на новых темах. Исторический вопрос «как было раньше» требует собственной разметки: официальные три вопроса нацелены на текущее состояние. [Описание протокола](https://arxiv.org/abs/2605.06527).

## Ближайшие механизмы адресуемого чтения

* ReadAgent сохраняет краткие представления частей длинного документа и может запросить исходный эпизод при ответе. Это прямой предшественник «сводка плюс чтение по ссылке». На том же корпусе надо выяснять, что даёт выбор конкретного диапазона и его объем. [ReadAgent, ICML](https://proceedings.mlr.press/v235/lee24c.html).
* Folio ведёт несколько уровней детализации истории и оставляет в свернутом контексте адреса, по которым можно вернуть ограниченные страницы или вычислить ответ по полному файлу. Это близкий опубликованный контроль для самого интерфейса bounded read и переноса проверенных наблюдений в постоянную запись. [Folio](https://arxiv.org/abs/2611.16627).
* Recursive Language Models оставляют длинный вход во внешней среде и разрешают программе обращаться к нужным его частям. Здесь стоимость чтения зависит от всей цепочки вызовов и повторных обработок. Для сравнения с равным бюджетом нужно считать все запросы и результаты, включая субвызовы. [RLM](https://arxiv.org/abs/2512.24601), [код](https://github.com/alexzhang13/rlm).
* ISETrace привязывает эталоны к координатам истории выполнения и проверяет полноту набора доказательств при ограниченном бюджете. Для нового метода полезно сохранить внешний QA-показатель STALE и отдельно диагностировать реальное покрытие источников. [Работа](https://arxiv.org/abs/2609.25913), [официальный репозиторий](https://github.com/xiaoqi-7/GraphMemory).
* Zep хранит временные отношения в графе; устаревание ребра и доступность его исторической версии уже заложены в эту линию систем. Dependency-Guided Rollback Repair непосредственно связывает устранение ошибки с зависимостями последующих выводов и действий. В работе об устаревших фактах на MemoryAgentBench было отдельно измерено ухудшение ответов при увеличении объёма полученной информации. Поэтому само сохранение времени, добавление provenance или observation/retrieval split уже имеют близких предшественников. [Zep](https://arxiv.org/abs/2501.13956), [Rollback Repair](https://arxiv.org/abs/2608.10502), [Obsolete Facts](https://arxiv.org/abs/2610.36308).
* MemDelta меняет по одному компоненту и показывает зависимость результата от семейства модели и retrieval. LongMemEval-V2 проверяет применение опыта в новых задачах среды; номера и раскладку из LongMemEval-S на него переносить нельзя. Присланная работа Multi-Agent Memory Inconsistency измеряет передачу конфликтующих утверждений между отдельными контекстами работников и ведущего. Это дополнительный этап после чтения памяти, который можно оценить отдельно от качества обновления записи. [MemDelta](https://arxiv.org/abs/2606.29914), [LongMemEval-V2](https://arxiv.org/abs/2605.12493), [Multi-Agent Memory Inconsistency](https://arxiv.org/abs/2611.22245).

## Границы обзора

Это целевой обзор ближайших первичных работ, без претензии на исчерпывающий систематический поиск. В primary-sources.json сохранены проверенные названия, авторы, идентификаторы и регистрации DataCite четырнадцати работ. В discovery.json — запросы к OpenAlex и Crossref и ответы сервисов. Статьи и выпущенный код просмотрены по тематическим запросам и ссылкам авторов. Формат и числа проверены вычислением на закреплённых входах. Здесь не обучались модели, не запускались большие LLM или оценщик и не измерялось улучшение QA. Для HaluMem с лицензией CC BY-NC-ND сохранены метаданные и агрегаты аудита; новая публичная редакция корпуса не распространяется.
