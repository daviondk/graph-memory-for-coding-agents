# Эксперимент до чтения новых результатов

Отдельно проверяем публичный smoke и пересборку авторской таблицы DreamBench-SWE. Они характеризуют установку. Авторский smoke подмешивает expected_behavior в запрос, а успех ряда задач определяет по факту непустой выдачи; сравнение наших методов на его Pass@1 не проводится. Скрытые ответы DreamBench-SWE для работы не используются.

**Новая задача.** Агент ведёт несколько Python-проектов и после обновления версии должен ответить на четыре точных вопроса о распространяемом wheel: строка описания, поддерживаемые версии Python, множество встроенных extras и множество имён безусловных зависимостей (Requires-Dist без marker). Эталон — независимое чтение METADATA реально выпущенного wheel. Наблюдение прошлого результата — прежний wheel. Для дешёвой повторной проверки среда предоставляет только исходный pyproject.toml из опубликованного sdist (проект PEP 621). Это тест одного механизма памяти при синхронизации сведений о сборке, а не задачи исправления кода. Изменение одного символьного поля может сказываться на сборке, декларация PEP 621 и собранный артефакт не всегда обязаны совпадать; отдельно включаем практический контроль с PKG-INFO из sdist.

**Панель.** До извлечения меток фиксируем упаковки attrs, Babel, click, iniconfig, more-itertools, networkx, packaging, pluggy, pyparsing, python-dateutil, tqdm, wcwidth. На каждом из четырёх срезов 30 июня 2022, 2023, 2024 и 2025 выбираем последнюю опубликованную стабильную версию PEP 440, имеющую неотозванные универсальный wheel и sdist к концу дня UTC. При нескольких универсальных wheel предпочтение имени py3-none-any, затем лексикографическое. Без предположений об изменении меток пропускаем повтор той же версии на соседних срезах. Все оставшиеся обновления входят в панель. Наблюдения фиксируются в неизменяемых HTTP-файлах с SHA256, исходный проектный код не исполняем.

**Интерфейс.** Неизменённые MemoryStore и RetrievalGate авторского reference probe хранят по одной старой записи на каждый ранее измеренный facet, тип SEMANTIC_PROJECT, repo_scope равен проекту, symbol_scope равен facet, provenance с SHA источника и ссылкой на предыдущий артефакт. Запрос имеет project и facet, имя новой версии и нейтральное описание, без новой метки. Для чтения прошлой записи потребуем правильный идентификатор facet в реально возвращённом кандидате native gate. Пустой ответ — пропуск.

**Версия источника и выходная стоимость.** Дешёвое наблюдение представляет текст текущего pyproject и соответствующие четыре статические декларации, сформированные из него. Для extras и безусловных зависимостей отсутствующее поле в статическом [project] без записи в dynamic даёт пустое множество, при отсутствии [project] или пометке dynamic — неизвестно. Summary и Requires-Python считаем известными только при явном поле. Приводим имена к PEP 503, Python-ограничения к сортированному SpecifierSet, описание к строке с единичными разделителями пробелов. Никаких предсказаний по номеру релиза.

**Политики.** (1) Без памяти — только подтверждения. (2) Историческая квитанция от нативного gate без проверки. (3) Использование текущих явных деклараций без памяти. (4) Переиспользование только при побайтно неизменном полном pyproject, иначе пропуск. (5) Наше правило — при равенстве известных деклараций в старом и новом источниках вернуть прежний измеренный ответ; при изменении явной декларации разрешить новый ответ, только если преобразование прежней декларации совпало с измеренным прежним wheel, иначе пропуск. (6) Контроль без воздержания — верить известной новой декларации, при отсутствии переносить старую квитанцию. (7) Фактический текущий PKG-INFO, если присутствует, отдельный контроль с другим входом. Например, в checkout разработчика может отсутствовать готовый sdist. (8) Все wheel как положительный контроль.

В основной настройке агент получает B=floor(число изменившихся проектов/3) подтверждающих чтений **wheel** в каждой временной волне. Одно чтение сразу подтверждает *все четыре* поля пакета. Первоначально политика вычисляет прогноз/воздержание по каждому полю. Для любого ограниченного метода выбор B проектов начинается с наибольшего числа пропусков, затем SHA от имени проекта и новой версии. Дополнительно считаем B=0. Верность/ошибка/воздержание, ложное доверие к старому ответу, условная точность, байты, число архивов; главный контраст — процент всех запросов с правильным ответом у правила против полного хеша pyproject, парный 95% bootstrap по проектам 10000, seed 4920. Если варианты подтверждают разные проекты, сравнивалась политика вместе с планировщиком. Отдельно показываем все сильные контроли. Ни метрика новых полей, ни прочитанные release aggregates не обозначаются как официальный балл DreamBench-SWE.
