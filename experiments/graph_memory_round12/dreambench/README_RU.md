# DreamBench-SWE и проверка памяти о состоянии программного пакета

Выполнили 31 авторский тест, запустили публичный smoke DreamBench-SWE, восстановили опубликованную таблицу и проверили отдельно опубликованный пакет v2.1. На новом прикладном тесте с **12 проектами, 31 обновлением и 124 вопросами** наш осторожный способ перепроверки памяти оказался слабее прямого чтения доступного источника. При девяти разрешённых чтениях нового wheel он дал **82 правильных ответа**, прямое чтение деклараций текущего проекта — **104**, оба без ошибок. Готовая метаинформация из исходного дистрибутива дала **124/124** без чтения новых wheel. [Результаты нашего эксперимента](results.json) · [Протокол до оценки](PROTOCOL_RU.md)

## Что удалось проверить у авторов

Использован оригинальный публичный код DreamBench-SWE с SHA `d340bb2eaf3a81691820ef0683cd652753a9fa5a`. Данные отслеживаемого дерева относятся к авторскому пакету v2.0.5. Проверили три различных результата.

1. **Публичный smoke.** Неизменённая команда `python scripts/run_smoke.py` завершила 15 последовательностей по четыре задания, по 60 вызовов для каждого из двух детерминированных stub. Семь открытых тестовых модулей для схемы, хранилища, извлечения, консолидации, конфликтов, загрузчика и smoke — **31 passed** на pytest 8.4.2. В smoke запрос содержит ожидаемое поведение из публичной фикстуры, а stub для последующих сессий считает успехом наличие хотя бы одной извлечённой записи. Поэтому этот запуск подтверждает работоспособность кода, его TaskSuccess и Pass@1 нельзя использовать как оценку нового метода. [Исходный smoke](https://github.com/iroiro147/dreambench-swe/blob/d340bb2eaf3a81691820ef0683cd652753a9fa5a/scripts/run_smoke.py) · [Фактические выходы по 120 вызовам](author-smoke.gz) · [Журнал тестов](native-tests.log)
2. **Регенерация опубликованных чисел.** Штатный скрипт `generate_tables_v2.py` воспроизвёл таблицу из поставляемого авторами `v2_fold.json`. Текст совпадает полностью после приведения Windows CRLF и Unix LF. Например, исходные опубликованные строки дают 21/180 для No memory, 67/180 для Reflection-vector и 78/180 для Probe strict-hybrid. Мы повторили преобразование готового агрегата в таблицу. Авторский мануал прямо указывает, что сырой fold по ответам hosted-моделей и скрытые oracle/reference solutions исключены из публичного пакета. [Таблица](author-tables.tex) · [Публичный runbook](https://github.com/iroiro147/dreambench-swe/blob/d340bb2eaf3a81691820ef0683cd652753a9fa5a/artifact/README.md) · [Статья](https://arxiv.org/abs/2608.20664)
3. **Публичное дополнение v2.1.0.** Скачали отдельный официальный release-архив внешнего аудита, сверили хеш с отсоединённым реестром контрольных сумм и запустили авторский `source/verify_v21.py`. Он завершился с `STATUS PASS failures=0`. Верификатор проверил выпущенный пакет свидетельств. Официальный hidden-grade результат нашего решения получить этими операциями нельзя. [Авторский релиз](https://github.com/iroiro147/dreambench-swe/releases/tag/v2.1.0) · [Проверка файла](release-verification.json) · [Результат верификатора](successor.log)

## Наш тест на новых входах

Ситуация типична для агента, который возвращается к проекту. Он когда-то проверил артефакт сборки и запомнил четыре свойства. Версия изменилась. Какие старые наблюдения полезны, если можно открыть только часть новых артефактов? Здесь правильный ответ определяется содержимым опубликованного wheel, без LLM-судьи. Пакеты и четыре контрольных временных среза зафиксированы до чтения новых ответов. Для 12 проектов из разных областей взято 31 реально отличающееся соседнее обновление. Каждый вопрос относится к одному из четырёх полей — краткому описанию пакета, ограничению Requires-Python, множеству extras или именам безусловных зависимостей. Из 124 значений изменились 28, в том числе 19 ограничений Python, шесть наборов extras, два набора зависимостей и одно описание. [Список архивов, версий, URL и SHA256](releases.json) · [Все переходы](transitions.json)

Исторический факт записан в настоящий `MemoryStore` как `SEMANTIC_PROJECT` с привязкой к проекту, полю и хешу фактически прочитанной записи METADATA. Для каждого вопроса неизменённый `RetrievalGate.retrieve(k=1)` получил только название проекта, имя свойства, новую версию и обычные метаданные области применения. Все **124/124** прошлые записи корректно извлечены. Правило проверки актуальности реализовано нашим читателем поверх этого выхода. Если конкретное статическое поле pyproject не изменилось, он переносит прежнее измерение. Изменившуюся декларацию принимает, только если на прежнем релизе её значение совпадало с артефактом сборки. Когда основания нет, читатель запрашивает подтверждение или воздерживается. В store в этом тесте по одной актуальной на момент записи квитанции на поле. Задача измеряет перенос, сложного поиска среди конкурирующих версий здесь нет. [Реальный RetrievalGate](https://github.com/iroiro147/dreambench-swe/blob/d340bb2eaf3a81691820ef0683cd652753a9fa5a/src/dream_memory/retrieval.py) · [Авторские выходы для наших запросов](native.gz)

В трёх волнах обновились соответственно 10, 11 и 10 пакетов. В основной настройке в каждой разрешили три текущих wheel — всего девять. Одно подтверждение открывает сразу все четыре ответа. Методы сначала формируют прогнозы по доступным свидетельствам, затем выбирают проекты с наибольшим числом вопросов без ответа. Выбор сохранён до оценки. Отдельно провели сравнение вообще без текущих wheel. [Предсказания до раскрытия](predictions.gz) · [Выбранные проекты](reading-plans.json) · [Запись до оценки](plan-lock.json)

При девяти открытиях наше правило дало на 34,68 п. п. больше правильных ответов, чем полный хеш pyproject (95% percentile bootstrap по 12 проектам [+19,83; +51,61]). Однако прямое чтение статических полей дало на **22 правильных ответа больше**, при тех же нулевых наблюдаемых ошибках. Разность «наше правило минус текущая декларация» равна −17,74 п. п. [−30,88; −5,65]. В парном сравнении по запросам нет ни одного случая, когда наш читатель дал правильный ответ, а прямая декларация с её расписанием не дала. Поэтому преимущество над хешем полного файла не служит аргументом в пользу усложнения памяти на этой задаче. [Пары, интервалы и разбиение по проектам](results.json) · [Каждый ответ и основание](outcomes.gz)

Единственная ошибка контроля по полному хешу показывает, почему его условие недостаточно. У tqdm при переходе 4.64.0 → 4.65.0 файл pyproject остался прежним, а ограничение поддерживаемой версии Python в wheel сменилось с поддержки части старых версий на `>=3.7`. Прежнее наблюдение о сборке относится к более широкому набору входных файлов, чем один хеш pyproject. Политика по отдельному полю воздержалась. Когда доступен текущий PKG-INFO, он позволяет проверить именно сформированные метаданные поставки; в этой выборке все четыре поля в нём совпали с независимым wheel. ## Стоимость и границы

Все операции локальны после скачивания 86 публичных архивов, суммарно **107 376 521 байт**. Код содержащихся в них пакетов не исполнялся. Уникальный размер входных архивов характеризует получение исследовательского набора. В расчёте доступности свидетельств один новый wheel соответствует одному платному действию. Его фактическая цена по объёму неодинакова. В основной настройке выбранные нашим методом архивы заняли 10 707 261 байт (44 172 байта самого METADATA), у прямого чтения статической декларации — 12 827 265 байт (81 818 байт METADATA). Суммарно в 31 новом состоянии было 76 928 байт доступных pyproject и 414 025 байт PKG-INFO. Готовый PKG-INFO внутри загруженного sdist является сильным практическим контролем с другим входом, и может отсутствовать в рабочем checkout. Эти цифры описывают логический бюджет и объём наблюдений. Время конечного агента и сетевое ускорение не измерялись.

Панель включает библиотеки с универсальным wheel, одну декларативную систему и четыре поля. Старые записи берутся из фактического предыдущего артефакта каждого перехода; обновлённое состояние одной волны может закономерно выступать историей следующей. Единица оценки неопределённости — пакет, поэтому четыре поля и несколько версий не считаются независимыми проектами. Полученный результат помогает отсечь слабую гипотезу о пользе безусловной исторической калибровки. Следующий вопрос — выявление случаев, где текущая декларация доступна, но не совпадает с реально сформированным артефактом. Только на независимо зафиксированной панели таких проектов можно проверить, оправдана ли дополнительная память как средство снижения ошибок. ## Воспроизведение

В каталоге опыта сначала выполните `python -B fetch.py` и `python -B published_release.py` для двух публичных исходных пакетов. Шаги авторского smoke и табличного анализатора приведены в авторском runbook. Использована локальная копия pytest 8.4.2 без автозагрузки внешних плагинов; установку можно ограничить отдельным каталогом через `pip install --target ./pytest-deps pytest==8.4.2`. Для собственного опыта нужны Python 3.11+ и packaging (здесь Python 3.14.4, packaging 24.2). Сценарий `artifacts.py` повторно выберет архивы по опубликованной истории; для воспроизведения точной панели на более поздней дате используйте зафиксированные URL и SHA из releases.json. Все релизные документы скачиваются публичными GET. Платных API, решений скрытых заданий и отправок результатов не было.

Для точного повторения с уже сохранённым releases.json обеспечьте существование каталога downloads. Если кеш пуст, шаг forecast/score скачает именно зафиксированные URL через функцию cache. Затем выполните `python -B experiment.py forecast`, `python -B experiment.py score` и `python -B check.py`. Это перезапишет локальные квитанции, включая служебное время touch в оригинальном MemoryStore. Состав панели, планы и баллы воспроизводимы при сохранённых артефактах. [Получение артефактов](artifacts.py) · [Проверка каждого ответа по оригинальным wheel](check.py)
