# Когда стоит перепроверять пустой поиск кодового агента

В историях VibeMemBench найдено **96 воспроизводимых пустых поисков по исходникам в 62 задачах 14 репозиториев**, для которых известны исходный коммит, рабочий каталог и код завершения команды. После слияния изменений положительными стали 14 запросов в девяти задачах шести репозиториев. Простая проверка «изменился ли файл в области поиска» вызвала 55 повторов. Проверка точного литерала в добавленных строках вызвала 14 повторов и обнаружила все изменения. Штатный Git с `diff -G` получил те же 14 результатов. Это независимое воспроизведение механизма, для которого в R11 было три случая на 29 запросах без сохранённого численного кода выхода.

Главное практическое различие — цена обновления нескольких записей одновременно. При обработке записей реальными группами по версии репозитория один общий diff занял 1,687 с, совмещённый штатный `git diff -G` — 1,681 с, пакетный полный поиск — 2,479 с. При независимом выполнении каждого запроса с обязательным подтверждением совпадений полный поиск оказался быстрее проверки диффа. Из 96 наблюдений агент во время исходной траектории повторил тот же семантический поиск лишь в трёх случаях. Новая оценка измеряет стоимость обслуживания кэша результата инструмента, а влияние кэша на долю решённых агентом задач остаётся открытым. ## Почему проверка срабатывает

Пусть в фиксированной области старого дерева нет ни одной строки, содержащей литерал. Любая подходящая неизменённая строка нового дерева совпадала бы и в старом. Поэтому впервые положительный запрос требует подходящей добавленной строки. Обратное направление также верно для бинарного признака присутствия: обнаруженной подходящей добавленной строки достаточно, чтобы выдать положительный ответ.

Новое имя файла включено в предикат области. Переименование трактуется как удаление по старому адресу и добавление по новому адресу (`--no-renames`), поэтому вход существующего содержимого в область поиска учитывается. В данных имелась всего одна основная задача с обнаруженными Git-переименованиями. Её запрос остался отрицательным. Эмпирическая проверка нового положительного результата вследствие одного переименования здесь отсутствует.

При тех же условиях нативный `git diff -G` ищет изменения, содержащие подходящие добавленные или удалённые строки. При проверенном старом отсутствии удалённая строка в старой области не может содержать искомый литерал. Равенство результатов двух точных методов поэтому предсказуемо. Оно ограничено однострочным поиском по обычным отслеживаемым исходникам с одинаковой семантикой сопоставления. Многострочные регулярные выражения, отрицательные контекстные условия, конвейеры, декодирование пользовательских файлов, неотслеживаемые файлы сборки и смена пути разрешения имени требуют других правил. [Описание pickaxe и -G в Git](https://git-scm.com/docs/git-diff).

## Цена одного обращения

Измерения выполнены на Windows, Git 2.49.0.windows.1, без сети при оценке и на полностью загруженных объектах. У всех методов одинаковый доступ к двум SHA. Политика самостоятельно получает список изменений или diff, время этого процесса и анализ его вывода включены. Сравниваются суммы медиан трёх проходов по каждому из 96 запросов, порядок методов и запросов перемешан, ОС использует прогретый файловый кэш. Полной очистки системного кэша между запросами не производилось. Каждый вызов CLI создаёт отдельный процесс. Подтверждение положительного результата выполняется дополнительным нативным поиском.

| Политика | Повторных поисков | Полное время, с | Получено байт stdout от команды diff |
|---|---:|---:|---:|
| Прямой `git grep -q` | 96 | **2,772** | 0 |
| Изменение области + подтверждение | 55 | 4,216 | 2 813 |
| Добавленные строки + подтверждение | 14 | 3,117 | 172 585 |
| Нативный `git diff -G` + подтверждение | 14 | 3,105 | 955 |

Если каждый раз выполнять отдельную проверку, сокращение числа перечитываний **не привело к ускорению**. Для 76 явных файлов прямой поиск занял в сумме 2,149 с, точная проверка с подтверждением 2,209 с. На 20 областях прочих видов соответствующие значения составили 0,623 и 0,908 с. Расчётное правило «искать напрямую в явном файле, на остальных применять -G с подтверждением» даёт 3,045 с. В столбце stdout учтены байты, переданные процессом Git. Физический дисковый ввод-вывод отдельно не измерялся. [Все 1 152 одиночных измерения](timing_rows.json.gz) · [Сводка](timing.json).

## Цена обновления группы записей

Группа — реальная тройка (репозиторий, base SHA, merge SHA). Среди 77 прямых пар у 15 нет пригодных ключей, у 44 по одному, у девяти по два, у пяти по три, у трёх по четыре и у одной семь. 18 пар с несколькими ключами объединяют 52 из 96 запросов. Для пустых групп все методы немедленно возвращают пустой вектор. Первый нативный контроль объединяет несколько `git grep -F -e` только при одинаковых области и флагах. По выданным строкам проверяется, какие именно литералы встретились, включая перекрывающиеся. В точном варианте один `git diff -U0` строится для объединения областей, строки относятся обратно к каждому ключу по пути и литералу. У обоих методов выход — индивидуальный булев ответ на каждый запрос.

В первом измерении единый diff занял 1,726 с, пакетный полный grep 2,526 с, нативный -G с отдельной проверкой каждого уникального литерала/области — 2,593 с. **Сильнее оказался контроль, который тоже объединяет литералы внутри Git.** Для группы он передаёт `-G` их регулярное объединение и общий диапазон путей. Нативный Git заранее отбрасывает ненужные файлы. Выданные добавленные строки привязываются к каждому исходному ключу так же, как у общей проверки diff. Для одной записи достаточно `--name-only`. Этот контроль и остальные методы повторно измерены вместе в новом случайном порядке. [Первый групповой опыт](batch_summary.json) · [Уточнённый протокол](UNION_PROTOCOL_RU.md).

| Метод повторного группового измерения | Все 77 пар, с | 44 пары по одному ключу, с | 18 пар с несколькими ключами, с | Процессов Git | Байт stdout |
|---|---:|---:|---:|---:|---:|
| Пакетный полный git grep | 2,479 | 1,228 | 1,251 | 89 | 4 177 |
| Общий diff, бинарный ответ | 1,687 | 1,193 | 0,494 | 62 | 130 020 |
| Стандартный общий git diff -G, бинарный ответ | **1,681** | 1,185 | 0,496 | 62 | **39 937** |
| Общий diff + подтверждение положительных ответов | 2,035 | 1,334 | 0,701 | 74 | 134 197 |
| Общий git diff -G + подтверждение | 2,045 | 1,334 | 0,711 | 74 | 44 114 |

Бинарный ответ из общего diff оказался на 32,0% быстрее прямого пакетного grep в этом запуске. Стандартный общий -G дал практически такое же время и передал на 69% меньше байтов вывода, чем общий нефильтрованный diff. Преимущество группировки сосредоточено в естественных группах с несколькими ключами. При дополнительном подтверждении положительных результатов вариант с общим diff был быстрее прямого пакетного поиска на 17,9% по всей панели, а на 44 одиночных парах уступал ему. При последовательном исключении одного репозитория преимущество общего diff перед прямым поиском оставалось в диапазоне 29,2–33,4% для непосредственного булевого ответа. Измерения относятся к этому набору и этой реализации запуска процессов. ## Значение для статьи

Эксперимент подтверждает два разных требования к рабочей памяти агента. Перед записью отрицательного факта нужен проверяемый адрес источника. При обновлении репозитория сравнения имеет смысл группировать только для записей, действительно принадлежащих одной версии. **Для буквального поиска штатный Git уже выдерживает сильное сравнение.** Преимущества собственного алгоритма над ним или улучшения доли решённых задач здесь не обнаружено. Для обоснования нового метода остаются содержательные задачи — восстановление достоверности наблюдения при незакоммиченных изменениях, память о зависимостях между несколькими разнородными действиями или экономичная обработка действительно повторяющихся запросов агента.

При первоначальном агрегировании времени несколько запросов использовали один и тот же идентификатор более раннего наблюдения, которым подтверждалось местоположение репозитория. Это дало 88 ключей при 96 запросах. Идентификаторы исправлены на исходные tool_call_id внутри задачи, все временные прогоны для таблиц выполнены заново. Состав, прогноз и Git-исходы всех 147 зафиксированных запросов совпадают до и после исправления.
