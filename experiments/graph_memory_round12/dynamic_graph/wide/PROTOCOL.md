# Dynamic dependency memory under repeat test execution

Primary question: after a single test completes, what read accuracy, update work and peak storage does the service incur before the next lookup? Can updating local test stripes, with exact suppression of repeated observations, reduce write and replay bytes compared with rebuilding a complete static XOR table while retaining its quality? New external subject: NetworkX native Python unit tests, official releases 3.4.2 and 3.5 (wheels by PyPI hashes); this is a replay of successful observed function calls from two genuine revisions. No solver, language model or synthetic software fault. Pre-specified modules, whole benchmark population and limits in collect.py. Start with shortest-path unweighted and weighted, BFS/DFS, connected/strong components, DAG and min-cost flow. Within each test module select up to 8 node IDs present in both test collections by hash of identity. Exclude failing or skipped observations only when the pair has no complete successful trace. Log all candidates/exclusions. Statistical unit is module within a single repository, not a source project or salt.

At each module start empty, add the observed symbol set of one native test at a time in a hash-fixed order on the earlier release, then replace each test by its actual run on the later release in a second hash-fixed order. Stable keys are production-relative .py path and function qualname. Trace the call phase only (fixture setup, native/compiled calls and external packages out of scope). Publish number of added/removed/deleted edges, identical observations, all event streams and source locks. Query after EVERY operation on both warm-up and replacement phases; no method sees later rows when writing. Evaluate per-module closed universe of every actually observed symbol over both versions plus 32 pre-specified nonmembers. Calculate full false-negative edges, positive/test pairs spuriously nominated, stale pairs (previously owned by this test and now removed), true-negative denominator and directional per-group counts. Separately evaluate one-key queries restricted to genuinely changed production function definitions identified by normalized AST differences between releases. Keys/labels for the grade cannot influence fitting. Save states before evaluation in separate processes. Primary quality metric: per-module false-positive rate on all exact-negative pairs after replacements at 256 bytes/test. Primary write metric: logical replacement bytes emitted per event. Report 64 bytes/test as stress case, both phases, absolute costs and FP vs static global and direct-per-test baselines. Pair four salt seeds 0,7,19,31; cluster bootstrap of module-average effects; finite single-library semantics only.

Every resident approximate index is a fixed byte buffer of exactly n × budget bytes. A small common header, salts, active and dirty masks count within it. Policies: (a) global static R10 Bloomier/XOR map, rebuilt upon each test record, (b) independently replaceable per-test Bloom filter with cardinality-adaptive hash count, (c) deterministic pairs / groups of four tests with R10 XOR in the touched stripe, (d) global base XOR plus two fixed shadow slots with latest per-test Bloom filters; after two distinct outstanding tests, rebuild on arrival of the third, avoiding stale associations via shadowing, (e) conservative batch-of-four with stale tests marked dirty and therefore nominated for all keys until the fourth commit triggers rebuild, (f) full exact sorted-string CSR/inverted test-mask dictionary, including all key bytes; publish serialized cost, unconstrained quality and writes, fixed-budget feasibility. When exact encoding exceeds capacity, equal-budget variant can only announce all active tests until it fits again; flag every such case. Add a conventional exact dynamic per-test forward dictionary (sorted strings and compressed lists with independent update) if practicable. Compare full commit buffers vs dirty substructures, byte differences and dirty 64-byte/4KiB pages. Report persistent old and staging peak bytes, size of the immutable replay archive and any offset table separately. Compare exact-in-budget without attributing an infeasible structure a win. Raw event/test names remain external environment labels to all arms equally. Full replay required to recover old row after replacing one member of an XOR stripe is explicitly charged; words are never assumed recoverable from XOR. Per-test Bloom can update without any older run. Alternative change detector compares replacement against exact prior serialized event and skips identical updates (extra replay reads charged); compare with same policy without skip on every method. No-op shortcut may use no future lookup information.

For cost measurements replay input records are append-only, self-contained serialized row lists with byte lengths and stable positional access. Charge archive append bytes and off-index address table separately and give totals for both archive-present and archive-free applicable modes. Measure total bytes emitted by replacing full touched components (including unchanged internal bytes), not just Hamming changes. Include measured Python traced heap for representative builds if available, distinguish algorithmic resident/COW estimates from physical I/O, OS cache and RSS. Include baseline rank-fusion or solver only if directly relevant; this study measures updateable dependency storage. Primary claims must survive simple exact/batched comparators and costs of historical replay. Any post-hoc choices/additions will be labeled.
