# Исполняемая проверка на двух новых целях VibeMemBench

До просмотра задач и источников результата отбираем mpmath__mpmath-881 и adamchainz__flake8-comprehensions-553 по именам двух небольших научного и инструментального проектов. Обе отсутствуют в прежнем пилоте VibeMemBench. Набор не репрезентативен для 111 целей. Фиксируем официальный релиз датасета 11164976b4f920cdb0d0cd570ca572e49acea1e8, harness 7152cf96809b45343ccc1caf7115a7d3fa43f956, mini-swe-agent bc85a45654e6348dcc6e4c5a40ad146ed0bb144d. Обрабатываем обыкновенные задачи программирования. Все исходы и скрытые тесты остаются оценщику, входной parquet для решателя содержит только разрешённые поля. Не подменяем задачу на основании качества решения.

Единица сравнения — одна задача и один фиксированный seed. Целевая метрика — resolved из авторского исполняемого оценщика. Дополнительные — поставка патча, фактические шаги, токены, повторные поиски. Первичный доступ к задаче и инструменты одинаковы. Сравниваем отсутствие дополнительной памяти, историческую выдачу простого лексического поиска и ту же подходящую историю с явной последовательностью «поиск/просмотр → путь → последующая проверка». Внешняя память строится из предоставленной авторами допустимой истории репозитория до задачи. Не передаём модельные решения, патчи или корректные имена из target-оценщика. Сложный вариант и лексический контроль имеют одинаковый верхний бюджет памяти. Истории с малым общим объёмом отражаем отдельно. Записываем фактические доставленные тексты до запусков.

Модель локальная Qwen3.8-27B UD-Q4_K_M. Одинаковое и ограниченное число шагов в каждой руке, по возможности исходный этап run_instance и официальный оценщик. Решение проблемы инфраструктуры или отдельный адаптер должны записываться явно в журнал, эксперимент с отличающимся от статьи решателем даёт внутримодельный парный результат. Семантика связывания источников опирается на эмпирические выводы MemDev-Bench об утрате процессной информации при сжатии, точное преимущество графа остаётся проверяемой гипотезой.
