# Офлайн-оценщик двух задач VibeMemBench

Оцениваем четыре контроля и шесть заранее выбранных эпизодов, по три варианта памяти на задачу. Каждый результат имеет отдельный каталог, нативный машинный отчёт и необработанный вывод запуска тестов. Сводка указывает число уже оценённых случаев и список ожидающих. [Текущий статус](results.json) · [Окружение и два образа](environment.json)

**Первичный критерий** — `resolved` из оригинальной функции `run_eval.evaluate_seed`. Для каждого готового эпизода используем штатное извлечение `model_patch` из `preds.json`, при отсутствии — авторскую обработку `info.submission` и `exit_status` из траектории завершённого эпизода. Байты строки патча передаются как есть. Новый результат фиксируется только после появления `finished.json`. Возврат невалидной либо пустой правки не заменяется правкой с исправленным синтаксисом: нативный результат и причина учитываются отдельно. Статус `unresolved` при нулевом коде управляющего скрипта возможен, когда набор прошедших тестов не совпадает с эталоном. В каждой записи даны отдельные поля `unit_exit`, `passed_match`, выполненные FAIL_TO_PASS, потерянные PASS_TO_PASS и ошибка vendor. [Код отдельного процесса](grade.py) · [Проверка результатов](audit.py)

**Калибровка** — опубликованная эталонная правка и добавление пустого в функциональном смысле нового текстового файла `.vibe-calibration-marker`. Второй контроль должен сохранить исходный дефект. Оба использовали один и тот же официальный тестовый патч и тот же образ для соответствующей цели. У модели нет каталога с эталонами в контейнере. Временные JSON-входы оценщика, полные эталонные строки и файл с официальным тестовым патчем хранятся отдельно на диске D в x20-r12-evaluator-inputs. В каталогах controls и models публикуются выходы тестов. При работающем наблюдателе они пополняются независимо от решателя.

**Условия выполнения.** Оригинальные скрипты VibeMemBench `run_eval.py` и `vendor/eval.py`, оригинальный log_parser, штатные команды тестирования и уже загруженные Docker-образы SWE-rebench-V2. Исходный vendor запрашивает сеть host; локальный переходник Docker заменяет режим на none, ограничивает контейнер половиной CPU и запрещает загрузку образов. Одновременно работает один оценивающий контейнер. Оценщик не вызывает модель, API либо удалённый авточекер. Используемая WSL-система — CodexX20MSR. [Переходник WSL](bridge.py) · [Применяемые параметры Docker](bin/docker) · [Авторский релиз](https://github.com/AlibabaResearch/DAMO-ConvAI/tree/7152cf96809b45343ccc1caf7115a7d3fa43f956/VibeMemBench)

Из этого каталога в PowerShell воспользуйтесь заранее подготовленным Python с pyarrow:

```powershell
$graderPy = 'D:/CodexResearch/x20-official-vibe/solver-runtime/agent-venv/Scripts/python.exe'
& $graderPy -B grade.py controls
& $graderPy -B grade.py one --iid mpmath__mpmath-881 --method base
& $graderPy -B grade.py once
& $graderPy -B grade.py watch
& $graderPy -B audit.py
```

Режим `once` оценивает все готовые случаи и выходит; `watch` ещё ждёт недостающих. На одном наборе запускают один оценщик за раз. Готовые результаты повторно не запускаются. `audit.py` пересчитывает контрольные суммы, сверяет байты реально поданного model_patch с сохранённым результатом и проверяет соответствие завершённому эпизоду. Полный повтор с чистого состояния лучше проводить в новом каталоге. При прерывании с незавершённым состоянием `grade.py` сообщает его точный путь и сохраняет предыдущие данные.
