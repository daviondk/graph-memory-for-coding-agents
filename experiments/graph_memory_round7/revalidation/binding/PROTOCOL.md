# Повторная проверка при изменении привязок имён

После первичного анализа обнаружен один ошибочный ответ. В boltons/ecoutils.py между версиями 23.1.1 и 24.0.0 в файле появилось определение dumps. Вызов dumps уже присутствовал в get_profile_json, но раньше не создавал ребра в графе локальных функций. Старая сигнатура get_profile и тело вызывающей функции остались за пределами отмеченных изменений. Это наблюдение использовано для разработки метода.

Гипотеза: при изменении списка объявлений надо помнить также имена ранее виденных прямых вызовов, которые не разрешились в локальные объявления. Контроль G: помимо прежней проверки caller+headers сбрасывать запись при любом изменении строки определения на нулевом уровне отступов в файле. Кандидат S: сбрасывать при пересечении имён из таких строк с именем вызывающей функции или любым именем её прямого синтаксического вызова (включая неразрешённые). Абляция B: учитывать только наблюдавшиеся положительные рёбра и имя caller. Вариант H: прежние header-интервалы без списков имён. Имён из строк добавлений/удалений (регулярное выражение для def/async def) достаточно для реализации; тела новых функций и эталонные графы политика не видит. Все сравниваемые варианты получают одинаковый сигнал. Обрабатываются прямые именные вызовы свойств того же синтаксического графа, что в основном протоколе. В потоке обновлений требуется передать извлечённые имена; аудит признаков и их объём сохраняются.

На старой панели оценивается только устранение наблюдавшейся ошибки, это разработка. Для независимой проверки механизма фиксируем восемь других проектов toolz, pydot, mizani, tabulate, mpmath, patsy, markdown-it-py, pyparsing; те же шесть последних стабильных pure-wheel релизов до фиксированной отсечки 2025-01-01, без отбора по результату. Если доступны менее шести универсальных релизов, берем все, число проектов с подходящими запросами указываем явно. Это новые проекты для данной серии валидации. Никакой подстройки порогов после просмотра. Предсказания и контроли блокируются до оценки, агрегаты обеих панелей выводятся отдельно.

Первичное сравнение S против G на новых проектах: среднее по проектам изменение доли корректного переиспользования. Априорный критерий поддержки — положительная нижняя граница описательного 95% bootstrap (10000 выборок по проектам, seed 70632), без дополнительных ошибочных ответов. Отдельно проверяется, снизил ли S хотя бы одну ошибку относительно B/H на новой панели; если обе политики не ошиблись, защита от устаревания не подтверждена независимо. Стоимость — холодные перечитывания, количество разных файлов при пакетном обслуживании, число имён из дельты; не измеряет вызовы модели. Закреплённые сравнения не доказывают общего отсутствия ошибок, логирование меток времени и прошлые источники фиксируются в машинных артефактах.
