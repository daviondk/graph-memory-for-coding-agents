# Протокол проверки актуальности сведений о вызовах

Гипотеза: после обновления файла можно повторно использовать часть памяти, хранящей для функции список её вызовов локальных функций и статические сигнатуры вызываемых функций. Изменение только тела вызываемой функции часто не меняет ответ. В отличие от проверки строк R6 здесь входными сигналами служат координаты изменений версий, а целевой ответ задаёт статический синтаксический граф.

Объекты: more-itertools, boltons, fonttools, pint, svgwrite, plotnine, humanize, wcwidth. Для каждого выбираем шесть последних обычных стабильных релизов (без pre/dev/post/local) с доступным неотозванным универсальным wheel до 2025-01-01 UTC. Список проектов, отсечка, порядок и формула фиксируются до получения результатов. Получение метаданных, URL, SHA-256 и байты архивов фиксируются отдельно. Сторонний код не исполняется. Если программный интерфейс источника недоступен, отмечаем это явно.

Единица — один запрос к ранее наблюдавшейся функции в изменённом или удалённом исходном Python-файле между соседними релизами. Берём все доступные уникальные функции верхнего уровня с хотя бы одним прямым именным вызовом другой уникальной функции верхнего уровня того же модуля. Саморекурсия, вложенные области, тестовые и вендорные каталоги исключаются. Запрос просит вернуть набор пар «имя вызываемой функции, её объявленная сигнатура»; цель синтаксическая, без динамического разрешения имён. Исходный модуль должен успешно разбираться. Если новый файл отсутствует или не разбирается, ранее сохранённый непустой ответ считается непригодным (ошибки разбора отдельно). Если в новой версии caller пропал или изменился состав вызовов, это учитывается. Выбор запросов никогда не зависит от того, изменился ли ответ.

У всех политик одна старая версия файла и один сигнал обновления: идентификатор файла, удаление и старые координаты изменённых строк/границы вставок. Тексты новых строк скрыты во время решения. Для построения сигнала внешняя система сравнивает две версии; стоимость этого общего этапа не входит в число перечитываний. Границу вставки считаем пересечением и на краю интервала. Политики: перечитать при каждом изменении файла; вслепую переиспользовать; проверять только тело caller; проверять caller и полные определения всех известных callees; проверять caller и только заголовки известных callees. Удаление файла вызывает перепроверку во всех условных политиках. Вызовы и сигнатуры могут меняться по причинам вне отслеживаемых диапазонов, поэтому считаем ошибки и сравниваем с полным пересчётом.

Первичное сравнение: доля запросов, где корректное перечитывание удалось избежать (ответ побайтово/структурно соответствует свежему разбору), у «caller + заголовки» минус «caller + полные определения». Предсказание: положительное среднее по проектам и отсутствие дополнительных ошибочных ответов на панели. Отдельный риск — число выданных устаревших ответов на все запросы и на переиспользования. Показываем парные показатели по каждому пакету и общие счётчики; для среднего разницы по проектам — 95% непараметрический bootstrap по 8 пакетам, 10000 выборок, seed 70631. Интервал описательный для выбранных пакетов. Вторичная проверка стоимости — число различных файлов, которые пришлось открыть хотя бы раз при одновременной обработке всех запросов по одному переходу. Это верхняя граница объединения обращений. Сырые события сохраняются. Даты версий относятся к экспериментальным данным. Ни автономное решение задач, ни экономия времени агента из этого стенда не следуют.
