# Графовая память при выборе следующего чтения кода

Вопрос обзора — какие работы позволяют отдельно оценить выбор файла, локализацию строк внутри него и пользу повторного чтения после изменения кода. Семь первичных работ отобраны целевым поиском по названиям систем и сочетаниям `coding agent memory repository state reread`, `software issue localization file function line recall` и `gold context coding agents`. Проверены полные тексты авторских версий arXiv и публикация ICLR на OpenReview. Выборка предназначена для проектирования сравнения. Результаты ниже получены авторами соответствующих работ.

## Что уже проверено

| Работа | Результат и значение для эксперимента |
|---|---|
| MemTrace, Xu и соавт., arXiv v3 | Система сохраняет неизменяемые наблюдения, связывает их с файлами и символами и проверяет применимость к текущей версии перед восстановлением. На полном DeepSWE с Codex CLI были решены 64/113 задач против 40/113 у штатного агента. Это сравнение двух полных систем. Для оценки отдельной политики чтения требуется тот же набор записей на входе. [Метод, таблицы 2 и 5](https://arxiv.org/html/2610.04838v3) |
| CoReMem, Li и соавт., arXiv v1 | Между последовательными задачами обучают агента оценивать перспективную ценность памяти. В авторской таблице для Qwen3.5-9B постобученный вариант достиг 17,7% решений при 79,9 тыс. токенов за сеанс, включая запись памяти и учёт кеширования. Базовый агент дал 14,0% при 98,3 тыс. токенов. Вариант с памятью без постобучения потребовал 111,7 тыс. при 15,5% решений. Это обосновывает отдельный учёт накладных расходов записи и вкладов обучения и памяти. [Таблица 1](https://arxiv.org/html/2611.17316v1) |
| MemDev-Bench, Chen и соавт., arXiv v1 | На специально отобранных 68 задачах, проваленных во всех трёх новых прогонах без памяти, лишь 2 из 18 условий с памятью превысили исходную полноту файлов, а 13 из 18 — исходную полноту строк. Авторы вычисляли эти величины по **финальным патчам**. Нужны отдельные измерения прочитанного входа и сгенерированного результата. [Раздел 4.2 и приложение H](https://arxiv.org/html/2610.27524v1) |
| Agentless, Xia и соавт., arXiv v2 | Последовательная локализация по файлам, элементам кода и местам правки. После каждой стадии авторы измеряют сохранность эталонного адреса и объём оставшегося кода. Этап выбора файлов по отдельности дал 78,7% для запроса к модели и 67,7% для эмбеддингов, их комбинация — 81,7%. Такая декомпозиция даёт контроль для выявления стадии, на которой потерян нужный код. [Разделы 3.1 и 5.2.1](https://arxiv.org/html/2407.01489v2) |
| ARISE, Seddik и соавт., arXiv v2 | Статический граф содержит связи определения и использования переменных. На SWE-bench Lite с одной моделью и каркасом SWE-agent первый ответ совпал с эталоном на уровне файла в 0,67 против 0,57 случаев, строки — в 0,41 против 0,26. Доля решённых задач выросла с 17,3% до 22,0%. Локализация и генерация патча выполнялись в отдельных запусках. Покрытие при бюджете 8 тыс. токенов авторы измеряли только для вариантов ARISE. [Таблицы 1 и 2](https://arxiv.org/html/2605.03117v2) |
| SweRank, Gangi Reddy и соавт., ICLR | Сильный обученный контроль для поиска функций по описанию issue. После извлечения биэнкодером применяется переранжирование. В SWE-bench Lite оставлены 274/300 задач, где эталон меняет существующую функцию. Их Acc@k требует нахождения **всех** эталонных сущностей. При сравнении с Hit@k достаточно одного совпадения, поэтому значения из разных протоколов нельзя подставлять в одну колонку. Для локального контроля авторы выпустили SweRankEmbed-Small (137 млн параметров) и скрипт оценки на своей выборке. [Публикация ICLR](https://openreview.net/pdf/77e9c362444de0bfb28202e5dd535d368f8cb235.pdf) · [Код и данные SweRank](https://github.com/SalesforceAIResearch/SweRank) |
| ContextBench, Li и соавт., arXiv v3 | Для 1136 задач в 66 репозиториях на восьми языках размечен компактный достаточный контекст. Оценщик различает просмотренный и использованный контекст. Разметка покрывает свидетельства за пределами строк эталонного патча, что полезно при проверке чтения зависимостей и тестов. [Раздел 2 и приложение D](https://arxiv.org/html/2602.05892v3) |

## Проверяемое отличие и пределы выводов

**Гипотеза для текущей программы** — сигналы уже наблюдавшихся чтений и подтверждённых правок позволяют распределить фиксированный бюджет следующего чтения между файлами и участками внутри файла. Это более узкая задача, чем выбор архитектуры памяти или построение полного графа репозитория. Происхождение записей, проверка версии и двухэтапная локализация уже описаны в работах выше. Обоснование возможного вклада потребует абляции конкретного правила выбора и независимого переноса.

1. Для событий, где ищется хотя бы одна эталонная строка, обозначим через F наличие файла с такой строкой в выбранных K файлах, через L — включение эталонной строки в итоговый бюджет B. Если все итоговые строки берутся из K файлов, L влечёт F, и P(L) = P(F) · P(L | F). Отчёт должен содержать числители и знаменатели для F, L и L при F. Условные доли разных политик могут относиться к разным задачам. Изолировать выбор строк позволяет общий фиксированный список файлов либо парное сравнение на пересечении успешных событий.
2. Для оперативной памяти воспроизводится порядок «наблюдение → обновление памяти → выбор чтения → следующая команда». Запись и предвыборка включаются в бюджет. Отдельные контроли — LRU при тех же записях, простая частота переходов и перераспределение тех же чтений без графового сигнала. Повторение уже исполненного запроса наблюдателем измеряет потенциальное попадание кеша. Влияние изменённого контекста на действия потребует отдельного запуска агента.
3. Для функциональной проверки фиксируются задачи, версия репозитория, решатель, число попыток, права доступа и лимиты. Главные исходы — выполнение целевых и регрессионных тестов, полные затраты на задачу и парные выигрыши/потери. Контекст вокруг эталонной правки используется отдельно как привилегированный диагностический контроль.
