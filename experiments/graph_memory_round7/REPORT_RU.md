# Как кодовому агенту выбрать следующее чтение и проверить сохранённый код

Седьмая графовая серия проверяет два решения во время работы агента. Первое — по наблюдениям выбрать, к какому файлу и месту обратиться. Второе — после изменения кода решить, нужно ли перечитывать прежнее свидетельство. Использованы хронологическое воспроизведение реальных действий, поиск файлов и строк на SWE-bench Verified, 16 локальных генераций Qwen с проверкой pytest и отдельный стенд на версиях открытых Python-библиотек. Единого суммарного знаменателя у этих опытов нет. [Постановка относительно семи опубликованных работ](literature.md)

## 1. Адрес будущего чтения

| Одношаговый прогноз | Kimi, 210 чтений | Claude, 348 чтений | Другая панель Kimi, 225 чтений |
| --- | ---: | ---: | ---: |
| Последняя прочитанная или изменённая строка | 10 | 18 | 21 |
| Строка из вывода поиска, срок два шага | 33 | 32 | 34 |
| Строка из вывода поиска до следующего чтения или правки | 43 | 32 | 51 |

Попадание означает, что единственная предсказанная строка вошла в диапазон, который агент затем действительно прочитал. Прогноз делается до появления аргументов следующего вызова. Внешняя Kimi-панель не пересекается с двумя первыми по идентификаторам задач. У версии со сроком два шага эффект относительно давности составил соответственно +10,95, +4,02 и +5,78 п.п. Простое удержание последнего поискового адреса оказалось сильнее ограничения по сроку. На первой панели 13 из 23 парных выигрышей краткоживущего адреса пришлись на одну задачу. В отдельном опыте без терминального поиска учёт типа прошлого действия дал 26 попаданий в нужную страницу из 947 против 28 у выбора по давности.

Запомнить ссылку и заранее прочитать область кода — разные действия. Если после каждого поискового сигнала заранее оплачивать 16 строк, в наиболее удачном из простых режимов это полностью покрыло последующее обращение **7 раз при 57 предзагрузках, 0 при 42 и 0 при 63**. Частичное пересечение может экономить строки. Фактическую экономию инструментальных вызовов в работающем агенте этот опыт не измеряет. [Протоколы, поштучные результаты и модель затрат](online/README_RU.md)

## 2. На каком этапе теряются нужные строки

При лимите до восьми файлов и 1800 токенов сравнили поиск BM25 по фрагментам с дополнительным ранжированием по связи «документация функции → её исполняемое тело». Среди 30 ранее использованных задач SymPy только для 17 нашёлся нужный файл. Среди 24 новых для этой проверки задач Sphinx — для 9. Даже идеальный выбор строки внутри заданных файлов ограничен этим числом.

| В пакет попала хотя бы одна строка эталонного изменения | SymPy, 30 задач | Sphinx, 24 задачи |
| --- | ---: | ---: |
| BM25 | 12 | 8 |
| Связь документации с телом функции | 6 | 5 |
| Перемешанные связи | 6 | 3 |

Парная разность графового метода и BM25 составила −20 п.п. на SymPy (95% ДИ [−36,67; −6,67], точный p=0,03125) и −12,5 п.п. на Sphinx (ДИ [−29,17; +4,17], p=0,375). При постфактум разборе граф чаще сосредотачивал контекст в меньшем числе функций. Эта ассоциация не устанавливает причину. Исходный некорректный прогон оценщика для Sphinx изолирован, ошибка проверки базового Git-каталога зафиксирована, неизменность предсказаний при повторной оценке проверена.

Ещё на **20 непересекающихся задачах Sphinx** сравнили способы выбора ровно восьми файлов. Исходная политика включила требуемый файл в 10/20 случаях, учёт объявлений в пакетных инициализаторах — в 12/20, плюс вес редких имён — в 13/20, добавление соседей по импортам — в 12/20. Для сравнения 13 против 10 было три приобретения без потерь, p=0,25. Итоговое число задач с целевой строкой в контексте составило соответственно 9, 10, 10 и 10. ## 3. Функциональный результат на SymPy

Для восьми заранее выбранных позиций в прежней выборке SymPy впервые выполнили генерацию в этой панели. Одинаковые issue, базовые ревизии, допустимые файлы, лимит памяти и одна попытка у каждой политики. Инференс локальный, **Qwen3.8-27B UD-Q4_K_M на RTX 3090**. Проведены 16 реальных вызовов и независимые проверки базовых, эталонных и предложенных изменений.

| Исход, задач из 8 | BM25 | Связь документации с кодом |
| --- | ---: | ---: |
| Эталонная строка есть в переданном коде | 3 | 2 |
| Правку удалось применить | 6 | 4 |
| Прошли целевые тесты и сохранены ранее проходившие регрессионные тесты из контрольной выборки | **2** | **0** |

Две парные потери без приобретений, точный двусторонний p=0,50. На одной задаче граф вытеснил нужную строку, на другой обе подсказки содержали её, оба изменения применились, а тест прошёл только с BM25. Отсутствие выигрыша согласуется с результатами локализации. Выборка из одного проекта недостаточна для общего вывода о качестве исправлений. [Модель, бюджеты, проверки и поштучный разбор](reader/REPORT_RU.md)

## 4. Когда сохранённое утверждение устарело

В графе сохраняется проверяемое утверждение о прямых вызовах в функции и объявленных сигнатурах вызываемых функций. При изменении файла можно перепроверять весь граф или только записи, чьи зависимости затронуты. Источники — 265 зафиксированных дистрибутивов PyPI; исходный код пакетов анализировался статически.

На первой панели (707 запросов) проверка только заголовков вызываемых функций потребовала **146 перечитываний вместо 203** при отслеживании их полных тел, но пропустила появление новой локальной функции с уже встречавшимся именем. Дополнение памяти ранее не разрешёнными именами устранило этот случай. На **717 запросах из восьми других проектов** выборочная проверка потребовала **244 перечитывания**, контроль по полным определениям — **298**, сброс при любом изменении объявления в модуле — **321**. Устаревших ответов на этой панели не обнаружено. При пакетной работе это соответственно **84, 96 и 88** различных открытий файла на пару версий. Более простой вариант по заголовкам совпал с выборочным на всех 717 запросах. Ещё на 2404 запросах из других переходов версий учёт неразрешённых имён потребовал одного лишнего чтения и не предотвратил ни одной дополнительной ошибки.

В семи повторах на панели из 717 запросов медиана времени полного пересчёта составила 0,587 с, выборочного с готовой дельтой — 0,372 с, с построением дельты внутри таймера — 0,530 с. Все ответы совпали. Это реальное время обработки всего пакета запросов CPU-реализацией на прогретых данных в оперативной памяти. Инференс, инициализация старой памяти и дисковый ввод-вывод в таймер не входили. [Три протокола, метрики и границы применимости](revalidation/README_RU.md)

## Вывод для следующего эксперимента

Наиболее перспективно **сохранять точный адрес, который агент уже увидел при поиске, и читать исходный код по запросу с проверкой его актуальности**. В рабочем агенте нужно сравнить три варианта на одних задачах и с одним решателем: обычный поиск, поиск с доступным указателем, поиск с указателем и проверкой зависимостей. Для каждой задачи фиксировать использованные указатели, повторные открытия, токены записи и чтения, полную задержку и прохождение тестов. Отдельный кандидат для проверки на других репозиториях — отбор файлов по объявлениям в пакетных инициализаторах и редким идентификаторам. Данных в пользу постоянной предзагрузки, добавления соседей по импортам или дополнительного веса docstring при выбранных бюджетах не получено. Превосходство над SOTA по функциональной корректности не установлено.
