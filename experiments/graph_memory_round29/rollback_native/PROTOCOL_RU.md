# Оригинальный no_repair и контроль удаления с повторным выводом зависимостей

Фиксируем исходную ревизию авторов 713724491b9bbc6e55f0f9d8723da0eb0766ced7. У no_repair нет модельных вызовов: точный upstream Python-оператор сохраняет исходные неисправные шаги и память. Запускаем штатный Python CLI сначала на одном детерминированно выбранном случае, затем на полном controlled registry и полном adapted registry, с неизменённым official oracle, если поддерживается для раздела. Используем только статические JSON-снимки, сетевые модельные вызовы и команды из данных не требуются. Публикуем все сбои/исключения отдельно. Проверяем структурный invariant всех выходов (совпадают с исходным неисправным trace и памятью) и фактическую стоимость. Метод получает перечисленные в registry faulty_memory_ids, поскольку диагностика исходной неисправности дана в постановке. Эталоны expected_output, affected_steps, source/derived_faulty и метки oracle_role могут использоваться только оценщиком.

В отдельной серии восстанавливаем только вероятное множество затронутых утверждений, без симуляции исправленного ответа. После отделения gold читаем только именованные адреса диагностики, id записей памяти и публичные связи derived_from, шаги с их типом, used_ids и generated_memory_ids. Имена остаются непрозрачными ключами, строковые префиксы faulty ids, чистый снимок, текст target answer, сам домен и семантические признаки не используются. Наборы прогнозов для всех случаев замораживаем до подсчета. Базовые контроли:

* No-op ничего не инвалидирует.
* Source-only исключает только указанные источники; варианты direct-claims и reach-any дополнительно отмечают непосредственное и транзитивное использование подозрительного родителя (объединение зависимости).
* Delete-and-rederive пересчитывает наличие альтернативной опоры после удаления диагностированных источников: наблюдаемая вершина с явными входами становится неподдержанной, только когда все её непосредственные источники уже неподдержаны. Независимые корни и внешние известные ссылки сохраняются. Считаем отдельно самый прямой физический алгоритм (повторные сканы до неподвижной точки) и очередь с обратными связями/счётчиками. Они обязаны дать идентичные ответы. Сопоставляем с вариантом «любая испорченная предпосылка портит результат». Эти полярные трактовки проверяются как приближения по опубликованной разметке; коллекция used_ids не декларирует логическое И/ИЛИ, поэтому один порядок правил не гарантирован семантически.
* Независимая дополнительная репликация извлекает те же метрики из исходных авторских оценок. Primary для детерминированной серии — micro-F1 на подмножестве реально затронутых claim шагов по исходной авторской реализации метрики, с интервалом paired case bootstrap по registry task. Для памяти вторично — удаление исходного fault, удаление derived_fault и сохранение benign при непустых соответствующих знаменателях. Два набора не объединяем, указываем число сравнений и число меток, заведомо раскрытых диагностикой. Пересчёт support не является LLM-replay, конечный oracle ответ новых правил не оценивается. Сравнение с опубликованными затратными LLM методами требует совпадения модели/эмбеддера, официальных runtime и judge; при отсутствии публичных pred и доступных сервисов фиксируем границу.
