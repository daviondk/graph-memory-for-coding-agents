# Отзыв диагностированного источника на официальных данных Rollback Repair

Штатный детерминированный baseline **no_repair** воспроизведён на всех 150 контролируемых задачах и 50 адаптированных задачах LongMemEval-V2. При сохранении неисправного состояния официальный oracle дал 0/150 и 0/50 успешных восстановлений, совпадая с таблицами 2 и 4 публикации. Авторский протокол специально отбирает случаи, в которых введённая ошибка изменила конечный ответ и дала последствия. Учёт источника ошибки уже входит во входные условия. [Статья и таблицы](https://arxiv.org/html/2608.10502), [зафиксированный код](https://github.com/xiaoqi-7/memory-rollback/tree/713724491b9bbc6e55f0f9d8723da0eb0766ced7).

В отдельном испытании оценили, какие claims теряют опору после отзыва выданных источников. Простое правило «пометить все транзитивные зависимые утверждения» достигло **0,672 micro-F1 на 50 адаптированных задачах** при полном обнаружении 126 размеченных зависимых claims. Цена — ещё 123 ложных срабатывания. На 150 контролируемых задачах выгоднее ограничиться непосредственной ссылкой (0,497 против 0,471). Обратное правило «любая оставшаяся ссылка служит достаточной независимой опорой» привело к пропуску почти всех действительно затронутых claims. Так проявилось ограничение структуры used_ids: наличие у утверждения второй ссылки само по себе не устанавливает, можно ли вывести утверждение из неё отдельно.

## Нативное воспроизведение

Проверены git blob ID всех 133 выпущенных файлов; оригинальный Python CLI сборки, записи результата, доменного oracle и метрик не изменялся. На полной закреплённой версии установлены оригинальные зависимости. Сначала выполнено по одному случаю каждой панели, затем оба реестра целиком. no_repair имеет ноль LLM и tool-вызовов. В 200 случаях выходные списки шагов и памяти точно совпали с соответствующими исходными неисправными списками. Официальные метрики дали нулевые recovery, faulty removal и claim F1, полное сохранение benign памяти; повторное возникновение ошибки не определено при нуле успешных восстановлений. На контролируемой панели 53 задачи customer support, 48 shopping и 49 travel. Адаптированная панель содержит 50 задач в одном домене. [Исходный метод](https://github.com/xiaoqi-7/memory-rollback/blob/713724491b9bbc6e55f0f9d8723da0eb0766ced7/baselines/no_repair/baseline.py), [oracle](https://github.com/xiaoqi-7/memory-rollback/blob/713724491b9bbc6e55f0f9d8723da0eb0766ced7/eval/run_oracle.py), [метрики](https://github.com/xiaoqi-7/memory-rollback/blob/713724491b9bbc6e55f0f9d8723da0eb0766ced7/eval/metrics.py).

Всем авторским методам выданы diagnosed faulty memory identifiers. Во всех 200 случаях реестр перечисляет ровно истинные source_faulty_memories — 177 из 177 на controlled и 137 из 137 на adapted, без дополнительных адресов или заранее раскрытых derived_faulty. Поэтому «удалено 100% исходных ошибок» у правила удаления выданных адресов является следствием постановки. Для сравнения структурных методов информативнее полнота и точность на следующих уровнях. [Реестр задач](https://github.com/xiaoqi-7/memory-rollback/blob/713724491b9bbc6e55f0f9d8723da0eb0766ced7/data/controlled_benchmark/registry.jsonl).

## Дополнительное сравнение на одинаковых источниках

После замены источников на непрозрачные идентификаторы методы получают только ссылки used_ids, generated_memory_ids и derived_from, идентификаторы/типы шагов и выданное множество отозванных источников. Ни oracle_role и fault_type, ни истинный финальный ответ или список затронутых шагов не нужны. Эти скрытые поля в исходной записи существуют. Проекция с явным списком полей предохраняет новый метод от их случайного использования. После фиксации двух прогнозов результаты сверены с авторским определением affected_claim_ids и F1. Для 1000 экспериментов «кейс × политика» применили соответствующие отметки к отдельной SQLite-проекции копий и проверили их чтением; предыдущие записи оставлены доступными для аудита. Исторические исходники не изменялись.

| Правило деактивации claim | Controlled TP / FP / FN | Controlled F1 [95% ДИ] | Adapted TP / FP / FN | Adapted F1 [95% ДИ] |
|---|---:|---:|---:|---:|
| Ничего не менять | 0 / 0 / 148 | 0 | 0 / 0 / 126 | 0 |
| Исключить только исходную память | 0 / 0 / 148 | 0 | 0 / 0 / 126 | 0 |
| Только claim с прямой ссылкой на отозванный источник | 133 / 254 / 15 | 0,497 [0,457; 0,539] | 103 / 112 / 23 | 0,604 [0,526; 0,681] |
| Транзитивно, если отозван хотя бы один источник | 144 / 319 / 4 | 0,471 [0,435; 0,510] | 126 / 123 / 0 | 0,672 [0,586; 0,752] |
| Удалить и пересчитать поддержку, если потеряны все родители | 11 / 0 / 137 | 0,138 [0,065; 0,214] | 0 / 0 / 126 | 0 |

Парный 95% bootstrap по целым задачам, 10 000 повторов; на каждом повторе заново считается micro-F1. Непосредственный минус транзитивный вариант дал +0,026 [0,006; 0,046] на controlled и −0,068 [−0,117; −0,022] на adapted. Точный пересчёт выживающих оснований двумя независимыми физическими алгоритмами (полные сканирования и очередь с обратными связями) дал одинаковое множество отключённых записей во всех случаях. При единственной реализации исходные формулы сами по себе могли бы скрыть ошибку обхода; независимый аудит также проверил цифры авторского oracle и интервалы.

Для памяти транзитивное правило обнаружило 17/17 производных faulty записей в 12 controlled задачах и сохранило 1334/1492 размеченных benign (89,41%). Прямой и консервативный варианты сохранили все 1492, но не отозвали ни одной из 17 производных. На adapted нет положительной разметки производных записей, поэтому значение их cleanup recall не определено. Транзитивное правило сохранило 239/292 benign, прямое — 292/292, пересчёт всех родителей — 291/292. Это сопоставление решений деактивации с размеченными ID. В нём нет проверки, какой новый конечный ответ был бы получен после повтора действий.

## Сопоставление с опубликованным методом

На adapted в таблице 4 указаны claim F1 0,669 у полной системы и 0,603 у AgentTrace-style при 68% и 54% конечного восстановления. У простого обхода 0,672 с ДИ от 0,586 до 0,752; разность с округлённым результатом полной системы 0,003. В публичном дереве этой ревизии и в GitHub Releases нет готовых предсказаний полной системы уровня отдельных задач для парного ДИ. Более того, обход самостоятельно не пересчитывал ответ пользователя. Данных о статистическом или сквозном превосходстве этого оператора здесь нет. На controlled наиболее высокий опубликованный claim F1 — 0,946 у LLM-judge repair, у полной системы 0,566. Все испытанные структурные правила на этой панели слабее обеих точечных отметок. В статье генеративные методы запускаются с конкретными backbone/API, общей исполняющей средой и отдельным эмбеддером; перенос на альтернативную локальную модель изменил бы сравнение. [Таблицы 2 и 4](https://arxiv.org/html/2608.10502), [требования оригинального запуска](https://github.com/xiaoqi-7/memory-rollback/blob/713724491b9bbc6e55f0f9d8723da0eb0766ced7/README.md).

Практический вывод для дальнейшего метода: любой сложный графовый алгоритм здесь должен сравниваться и с прямым цитированием, и с транзитивным обходом. На адаптированном бенчмарке последний уже полностью покрывает пострадавшие claims. Возможный выигрыш должен прийти от устранения ложных срабатываний с сохранением причинно важных связей. Нужны сведения о том, какое именно подутверждение поддерживает каждая ссылка, и отдельная проверка конечного ответа после обновления. Вариант «сохранять claim всегда, пока осталась хотя бы одна ссылка» экспериментально оказал обратный эффект.
