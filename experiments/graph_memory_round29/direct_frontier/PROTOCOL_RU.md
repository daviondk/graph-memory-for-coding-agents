# Прямое построение точной памяти по исходным логитам

Для двух списков смен допустимого ответа нужны только победители каждого конца и начала. Если конец j фиксирован, допустимые начала лежат в [j−K+1,j] внутри его сегмента. Максимальную float32-сумму определяет наибольший начальный логит в этом диапазоне. Из нескольких начал с той же округлённой суммой выбирается самое раннее. Для фиксированного начала правило симметрично. Это сокращает число оценок, передаваемых в сводку по координатам, до двух на токен. Пара исходных координат и ord из перекрывающихся окон различаются и участвуют в проверке.

На прежних 96 вопросах сравним четыре реализации построения одной и той же структуры памяти. (1) Векторизованная материализация кандидатов с глобальной сортировкой в стиле R28/evaluate_views.py, (2) сильный потоковый NumPy-контроль без глобальной сортировки, который сворачивает кандидатные ключи в максимумы по координатам, (3) непосредственно 2 локальных победителя на токен через векторизованные окна длины K, (4) прямой метод через таблицу максимумов 2^j и поиск самого раннего равного округлённого значения в O(log K) на токен. K=30 соответствует исходному читателю. Контроль 2 и оба прямых метода используют одинаковые локальные словари координат, бинарный полный ключ score/tie и построение смен. Для порядка слияния при совпадениях входные +0 и −0 считаются равными; при выдаче восстанавливаются точные исходные биты выбранного победителя.

Первичная проверка — полное байтовое совпадение каждой сохранённой записи всех методов с фактическим R28 SQLite, обе стороны, все 96 вопросов. Время построения исключает чтение BLOB и проверку ответа. Публикуем расходы подгрузки отдельно. Измеряем 3 повтора каждого метода в новых Python-процессах по всем 96 вопросам, порядок методов чередуем случайно. Сравниваем прежде всего прямой метод O(log K) с сильным потоковым без сортировки. Дополнительно показываем самый быстрый точный метод, полную материализацию, p50/p95 по вопросам. 95% интервалы парных разниц и отношений медиан получаем бутстрэпом 48 статей. Пиковый RSS и его приращение относительно состояния после импорта и подготовки соединения измеряются монотонным счётчиком Windows PeakWorkingSetSize в каждом отдельном процессе; это процессный максимум за 96 вопросов, включая временную упаковку результата и исходный BLOB одного вопроса, а не точная разметка по отдельным массивам.

До измерения проводим искусственные проверки ничьих, отрицательных оценок, ширины K=1, коротких сегментов и отсутствия кандидатов, включая ситуацию, когда меньший логит при сложении float32 округляется до максимальной оценки. Для объяснения масштабирования дополнительно измерим K=8 и 120 на фиксированных по SHA восьми вопросах. Эти ширины меняют пространство допустимых ответов и служат только инженерной диагностикой; основной результат относится к K=30. Формат текущей постановки — неизменные логиты и один запрещённый полуоткрытый интервал.
