# Предварительный план проверки индекса версий следующего чтения

Исследуем оператор БД, который сохраняет источник следующего чтения при поступлении упоминаний и возвращает выбор для уже раскрытого префикса. Исходные признаки и оценки R51 известны. Протокол фиксирует новый серверный контраст прежде измерения времени или просмотра распределения его исходов. Все четыре панели R51, всего 3 840 вопросов, включаем в проверку правильности.

Для вопроса берём фактический текст первого фрагмента, нормализованное название каждой оставшейся статьи и точную позицию окончания первого соответствующего вхождения. Префикс продвигается по 16 нормализованным словам, включая последний неполный отрезок. Указатель активации относится к концу раскрытого отрезка. Текст и все совпадения подлинные, нарезка и обращения к истории смоделированы. Косинус и лексические ранги фиксируем при значениях полного фрагмента; состояние представляет последовательную проверку флага связи на уже закешированной проекции. На промежуточных шагах не оценивается собственно качество гипотетического QA-агента. Оптимизация относится к выбору второго документа, стоимость поиска в тексте и вычисление исходных признаков не входят в замер.

**Аргумент.** Скоринг имеет вид b_i + beta * e_i с положительной beta, уникальным стабильным вторичным ключом и одной необратимой активацией каждой связи. Если новые строки получили бонус, на следующий максимум претендует прежний лидер или одна из этих строк. При повторном чтении старого префикса достаточно ближайшей слева сохранённой версии лидерства. Пишем версию при улучшении пары «балл, приоритет», даже если ID не изменился. Все активации одного раскрытия имеют одну позицию и атомарно дают одну финальную версию.

**Базы.** Все системы работают с кандидатами, ценой до добавления признака, рангом ничьей, позицией первого подтверждённого упоминания и курсором. Плоский обход сортирует по фактической версии флага при чтении. Обычный покрывающий expression index ускоряет текущий выбор, исторический пересчитывается. Более сильный частичный покрывающий индекс хранит активированных кандидатов в порядке их баллов с бонусом; верхний допущенный временем кандидат сравнивается со статическим лидером. Проверяем дополнительно его вариант, материализующий только кандидатов, которые могут обойти статического лидера, если это можно исполнить корректно. Новый план ведёт SQLite-журнал повышений лидера, включающий начальную запись. Известные ответы читателя и метки во время обслуживания не используются.

**Основной режим.** Заранее заданные четыре группы источников, по 256 первых вопросов после сортировки SHA256('r52-witness-io-v1|'+панель+'|'+id) из каждой панели, всего 1 024 вопроса. Запросов на каждый этап раскрытия 1 или 8; каждая чётная позиция с нуля запрашивает последнюю версию при одном чтении и исторический ранее доступный срез при восьми чтениях; общий порядок сформулирован в коде и публикуется до первого замера. Дополнительно режим без чтений для цены записи. Основной контраст — суммарная задержка при 8 чтениях смешанных версий с включённой стоимостью строительства против частичного покрывающего индекса по всем активированным кандидатам. Источники репликации — вопросы, сгруппированные в общие блоки по 32 (8 от каждой панели), и повторы измерений. Внутри повтора независимая рандомизированная очерёдность физических планов. Проводим четыре повтора; публикуем сырые времена блока, порядок, контрольную сумму выбранных документов, стоимость настройки индекса, число записей и диск для каждого плана. Для процентов экономии/ускорения — парный bootstrap по блокам и повторам, 10 000 повторных выборок. Остальные режимы и сравнения описательные. Не сообщаем о качестве ответов по этим значениям.

**Граница обслуживания.** Все планы используют одинаковый файловый SQLite, один клиент, WAL и synchronous=NORMAL. Для каждого раскрытия фиксируется курсор и его новые активации в одной транзакции. После commit выполняется запрошенное число обращений на том же соединении в общей транзакции чтения. Очерёдность синтетических обращений и проверяемое значение ответа совпадают по всем планам. Продолжительность транзакции включает SQLite, его Python-вызовы и выдачу целочисленного адреса. Подготовка общей сырой таблицы, построение корпуса и финальная контрольная сверка выполняются вне замера. Стоимость дополнительных индексных/табличных построений включаем в основное сравнение на панели, числа на прогретом исполнении приводим отдельно. У планов есть одинаковые журнальные/чекпоинт-параметры. Результаты не являются измерением сетевой службы или синхронной записи на физический диск после каждого обновления.

**Проверки.** До таймингов сверяем все версии четырёх датасетов с перебором исходных кандидатов. Для каждого промежуточного шага исторические ответы не могут содержать ещё не полученную связь. После последней активации должны совпасть все выбранные адреса из R51. Отдельный тест проверяет ничьи, одновременные активации и повтор записи. Перезапуск соединения должен сохранить граф и версии. Упорядоченное поступление привязано к одному снимку неизменных базовых оценок. Редактирование текста задним числом, снижение балла и удаление ребра требуют отдельного алгоритма.
