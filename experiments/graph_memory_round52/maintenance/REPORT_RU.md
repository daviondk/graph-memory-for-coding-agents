# Отчёт. Обслуживание графовой памяти при поэтапном подтверждении рёбер

В исследовании R52 проверен физический оператор SQLite для выбора второго документа из графовой памяти. При неизменных исходных оценках кандидатов он восстанавливает точный результат для любой уже полученной версии. На первой группе из 1 024 вопросов при восьми обращениях на обновление время сократилось на 10,7% относительно частичного покрывающего индекса. Повторная проверка на других 1 024 вопросах дала 2,2% экономии с интервалом, включающим нулевую экономию. Корректность подтверждена значительно надёжнее, чем преимущество по времени.

## Что меняется в памяти

Когда фактически встречается название другой статьи, кандидат получает один постоянный положительный бонус. Из 3 840 реальных первых фрагментов панелей R51 восстановлены 2 472 первых совпадения в 34 417 кандидатах. Каждое совпадение сверено с меткой ребра исходной SQLite-базы. Нарезка по 16 нормализованным словам дала 18 006 раскрытий и 2 362 непустые группы обновлений. Исходные косинус и ранги вычислены ранее на полном фрагменте. Тексты и позиции настоящие, моменты верификации рёбер и запросы к старым версиям воспроизводятся синтетически. Цена получения представлений, генерация ответа и полнотекстовый поиск лежат вне измеряемой операции.

Для кандидата i и версии t ключ K_i(t) равен (b_i + β·1[s_i ≤ t], −r_i, −id_i), где β > 0, s_i — время первого подтверждения, b_i и приоритет r_i в эпизоде фиксированы. Пусть W(t) — наибольший ключ. При переходе t−1 → t достаточно сравнить W(t−1) с новыми усиленными ключами. Все прочие ключи сохраняют прежние значения и логически ограничены W(t−1). Журнал хранит начального победителя и версии, в которых W улучшился. Чтение ищет последнюю запись с версией ≤ t. При нескольких улучшениях за транзакцию остаётся один победитель. Это сохраняет идентификатор и при равных оценках. Если тот же победитель получил бонус, его новое значение необходимо для верного сравнения на будущих шагах.

При Q эпизодах и M непустых группах обновлений история содержит не более Q+M записей. Здесь верхняя граница равна 6 202, фактически записано 5 822, в том числе 3 840 начальных. Адрес победителя менялся 752 раза. Остальные 1 230 новых записей фиксируют рост ключа у того же победителя. На всех четырёх панелях выполнили 80 314 запросов ко всем доступным прошлым срезам после каждого обновления для каждого из пяти планов. Расхождений с прямым вычислением и исходными финальными адресами не обнаружено. Один клиент, обновления приходят по порядку, редактирование уже принятого текста и отзыв связей требуют другого оператора.

## Сравнение физических планов

Первичная выборка содержит 9 161 кандидата, 633 подтверждения рёбер, 4 931 транзакцию обновления и 39 448 чтений при отношении 8:1. Для каждого получения префикса фиксируем курсор и все обнаруженные рёбра в одной транзакции записи. Следом проводится одна транзакция чтения. Из восьми обращений четыре относятся к текущей версии, четыре — к случайным уже доступным версиям. Все планы идут по одному расписанию. Уровень сохранности, настройки WAL и ограничение кеша одинаковы. В полном времени учтены построение специфичного индекса на подготовленной базе, обработка всех операций и финальный checkpoint. «Прогретое» время учитывает только операции. Сборка общей исходной таблицы исключена у всех планов. Репликация использует то же определение.

Планы `partial` и `eligible` заслуживают особого внимания. Оба фиксируют лучший исходный адрес и ищут подтверждённого кандидата, способного его превысить. Первый проверяет это условие при чтении, второй заранее материализует признак допуска и хранит в частичном индексе только подходящих кандидатов. SQLite действительно использовал покрывающие индексы, что зафиксировано через EXPLAIN QUERY PLAN. Журнал реализует поиск предшественника по составному первичному ключу (эпизод, версия).

|---|---:|---:|---|---:|---|
| Основная, 1 024 вопроса | 163,72 | 183,42 | 1,120 [1,022; 1,260] | 174,51 | 1,066 [1,010; 1,122] |
| Повторная, другие 1 024 вопроса | 163,34 | 166,94 | 1,022 [0,964; 1,073] | 173,03 | 1,059 [0,997; 1,122] |

Ускорение равно среднему полному времени базы / среднему полному времени журнала. Время журнала оказалось меньше времени обычного частичного индекса в 4/4 первичных и в 6/8 повторных измерений. Парный bootstrap, 10 000 выборок по 32 общим блокам вопросов и повторам запуска. Сопоставление с усиленным индексом вторично и не корректировалось на множественность. У повторной группы 4 668 раскрытий и 654 подтверждённых ребра. Хеши вопросов и первых фрагментов групп не пересекаются. Обе группы происходят из тех же четырёх панелей, а правильность оператора проверялась на них до отдельного замера времени.

На первой выборке направление точечной разницы меняется между двумя и четырьмя чтениями. Различаются шум измерения между режимами и разброс checkpoint. Для четырёх, шестнадцати и тридцати двух чтений интервалы допускают паритет. Устойчивая универсальная граница окупаемости пока не установлена. Дальнейшая независимая проверка требует естественной частоты исторических запросов из трасс агентов, нескольких размеров адресного пула, большей продолжительности прогона и конкурирующих клиентов. Параметры и базы зафиксированы до соответствующих измерений.

## Связь с работами по БД и воспроизводимость

Поддержка материализованного временного агрегата и поиск на момент времени давно исследованы. Классический SB-tree обсуждает обновления, способные менять значительные части истории, а Timeline Index поддерживает запросы на срезе и агрегацию. Специализацию здесь даёт однократное положительное подтверждение ребра в ранжировании следующего чтения. Результат обосновывает проверяемый механизм для демонстрации. Утверждения о фундаментально новом типе индекса, росте качества QA и превосходстве над опубликованной SOTA потребовали бы иных сравнений. [Incremental computation and maintenance of temporal aggregates](https://scholars.duke.edu/publication/807145), [Timeline Index](https://doi.org/10.1145/2463676.2465293), [SQLite partial indexes](https://www.sqlite.org/partialindex.html), [SQLite indexes on expressions](https://www.sqlite.org/expridx.html).

Сценарии записаны в PROTOCOL_RU.md, FRONTIER_PROTOCOL_RU.md и REPLICATION_PROTOCOL_RU.md. Первоначальный запуск остановился до первого блока времени, поскольку системная сборка SQLite не экспортирует виртуальную таблицу dbstat. Для идентичного измерения размера у всех планов используются PRAGMA page_count и page_size. run-seal.json фиксирует исправленный таймер. Метки платформы и версий лежат в environment.json. Все фазы воспроизводятся локально из каталога эксперимента. Замеры выполнялись на одной рабочей станции. Величина выигрыша между системами, устройствами и режимами фиксации может различаться.

~~~text
python source.py
python study.py
python study.py --frontier
python stats.py
python replicate.py
python verify.py
python demo/test_console.py
~~~

Для просмотра без пересчёта откройте results.json, replication.json и correctness.json. Блоковые затраты, порядок, планы и хеш итоговых состояний лежат в timings.json.gz, frontier-timings.json.gz и replication-timings.json.gz. source.py восстанавливает набор из базы R51, а исследование и демонстрация работают с приложенными проекциями. Повторный замер перезапишет соответствующие файлы таймингов. Изолированное копирование каталога сохраняет архивный результат. Консоль посетителя запускается командой `python demo/serve.py`.
