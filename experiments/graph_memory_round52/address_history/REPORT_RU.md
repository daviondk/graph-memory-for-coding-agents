# История адресов с точным восстановлением оценки

Зачем хранить новую строку, когда выросла оценка прочитанного документа, но сам выбор не изменился? В SQLite реализованы два журнала. Первый сохраняет каждое изменение ключа победителя. Второй записывает его адрес только при смене победителя на границе транзакции. Историческую оценку второго оператора даёт одна адресная выборка по кандидату и версии подтверждения его связи.

На **3 840 вопросах, 18 006 атомарных раскрытиях и 80 314 исторических запросах** все шесть реализаций выдали одинаковые ID и битовые представления оценок binary64. Каждый план проверен повторным открытием базы. Базовый источник — сохранённые оценки графового читателя и фактические позиции совпадений слов; границы раскрытия смоделированы. Сокращение относительно исходного журнала составляет **21,13% строк истории** и **5,79% размера всей базы после checkpoint**. Из 77 824 сэкономленных байт 61 440 приходятся на удаление столбцов, ещё 16 384 — на укрупнение интервалов при одинаковом наборе столбцов. В реплике с VACUUM направления обоих эффектов сохранились. База с полным пересчётом остаётся самой маленькой.

Для восстановления адреса поиском предыдущей записи нужно хотя бы одно начало интервала на вопрос и хотя бы одно на каждое изменение ID. В нагрузке это 3 840 + 752 = 4 592, что в точности достигнуто. Это нижняя граница для представления последовательности интервалами и predecessor lookup. Проверен также случай, когда лидер изменился и вернулся в течение одной транзакции. Повторное применение обновления и откат не создают ложных границ. [Оператор](address_store.py) · [Проверка точности](compare.py)

**Цена реконструкции.** Для каждого из восьми случайно упорядоченных повторов выполнено 21 846 прогретых запросов на один контракт и план. Когда нужен только ID, минимальный и исходный журналы заняли 2,59 и 2,60 мкс на запрос, отношение времени исходного к минимальному 1,001 [0,989; 1,012]. Когда требуются ID и оценка, минимальный журнал занял 3,08 мкс, исходный — 2,71 мкс. Частичный индекс с предварительным отбором занял 3,23 мкс. Стоимость записи и построения в это измерение чтения не входит. [План измерения](LATENCY_PROTOCOL_RU.md) · [Оценки](latency.json) · [Сырые времена каждого блока](read-timings.json.gz)

Из этого каталога `python -B compare.py` повторяет все шесть состояний с нуля, `python -B latency.py` измеряет чтения (NumPy), `python -B test_extension.py` проверяет реальный HTTP. Для последней проверки и живой демонстрации доступны три сохранённых вопроса с полными маленькими таблицами. Команда `python -B extension.py --port 0` выводит локальный адрес. По ссылке **Compact version history** пример Jay Craven показывает две строки журнала оценок и одну строку истории адреса при совпадающих битах исторической оценки.
