# Два чтения из полного справочника заголовков 2Wiki

Исходный вопрос — даёт ли настоящее исходящее ребро дополнительную информацию относительно материализации буквальных упоминаний, когда агент сам должен найти оба источника среди всех записей корпуса? Участие отвлекающих документов организатора в прежних опытах сужало пространство поиска и могло скрыть как полезные переходы, так и ложные совпадения. До вычисления результатов фиксируем все 12 576 вопросов публичной dev-части 2WikiMultiHopQA и полный авторский снимок para_with_hyperlink.jsonl. Числа предыдущих экспериментов на частично пересекающихся вопросах известны. Новый режим поиска на этих данных ранее в этой работе не измерялся.

**Доступ.** Каталог адресов состоит из всех записей снимка; используются заголовки и их числовые ID. Для одинаковых нормализованных заголовков проверяем поведение явно. Полные тела не участвуют в общем инвертированном индексе. Первое чтение выбирает один заголовок по словам вопроса. Доступен только префикс первых 192 токенов E5 выбранного первого абзаца. Метаданные даже существующих гиперссылок видны только при полном расположении текста анкера в этом префиксе. Второй адрес выбирается в полном каталоге без предоставленных benchmark distractors, ответов и опор. Размеченные заголовки и тип вопроса открываются после фиксации обоих адресов. Модель ответов не запускается; оценивается доступность свидетельств после двух чтений.

**Лексическое основание.** Для заголовков — BM25 с k1=1,2 и b=0,75, положительным IDF, без учёта повторов слова запроса. Токены — буквенно-цифровые, строчные. Заранее фиксируем список английских служебных и типовых вопросительных слов. Первый источник — максимальный BM25 на вопросе с приоритетом полного явного названия в вопросе среди положительно оценённых заголовков; далее счёт BM25, затем меньший числовой ID. Единственный порядок для всех вторых адресов: буквальное полное название в вопросе, затем BM25 на вопросе плюс 0,25 BM25 по видимому первому префиксу, затем меньший ID. Непустая точная фраза содержит хотя бы три буквенно-цифровых символа и хотя бы один неслужебный токен. Адрес первого заголовка исключается. Сохраняем также обычный BM25 вопроса без приоритета упоминаний как вспомогательный контроль. При отсутствии положительного лексического совпадения используем устойчивый ID.

**Сравнение.** В контроле text выбираем лучший по общему порядку буквально названный в первом видимом абзаце заголовок, при пустом множестве используем общую выдачу. В href выбираем в том же порядке среди направлений наблюдаемых гиперссылок первого абзаца, с таким же fallback. Чтобы единственное различие касалось вида ребра, в обоих вариантах явный оставшийся заголовок из вопроса имеет приоритет над любыми остальными кандидатами: при наличии таких заголовков сначала ищем ребро среди них, а при отсутствии пересечения берём лучшего из этой группы. Отдельно сохраняем unrestricted, объединение и контроль, который рассматривает только написанные заголовки без отмеченного приоритета самого вопроса. Разбираем расхождения, включая переход по анкеру с другим написанием, считаем долю достижимых опор после первого чтения. Число ребер-подсказок не выравнивается в основном функциональном сравнении, указываем их размеры.

**Единственный первичный показатель** — разность по доле вопросов, для которых оба чтения совместно покрыли все различные эталонные заголовки, href минус text, знаменатель — все вопросы dev, в том числе с более чем двумя опорами. 95% доверительный интервал — парный bootstrap групп одинакового первого адреса (10 000 выборок, seed 520117, веса сохраняют частоты вопросов). Дополнительно Hit первого чтения, доля найденных опор, условная точность при достижимой второй опоре, результаты по типу вопроса и числу опор. Для гипотезы о происхождении эффекта различаем совпадения текста анкера с адресом и прочие, без утверждений о причинном эффекте на этих выбранных подгруппах. Это сравнение по поиску заголовков в авторском снимке; публикации с индексом всех текстов, читателем и ответной метрикой будут описаны как отдельный режим. Никакие параметры по итогам dev не пересматриваются.
