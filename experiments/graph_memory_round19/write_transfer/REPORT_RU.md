# Перенос ограниченной записи памяти на development split ISETrace

Сохранение начала каждого события подтвердило преимущество над FIFO на всех 580 новых вопросах. Дополнительный приоритет начал результатов вызовов дал 255 полных комплектов свидетельств после чтения BM25 против 242 при одинаковом приоритете начал аргументов и результатов. Связать приоритеты двух сторон одним идентификатором вызова оказалось недостаточно для дополнительного выигрыша. Все правила использованы в версии, зафиксированной до получения этой выборки.

В колонках хранения измеряется, остались ли в памяти все эталонные символы по правильным адресам. Чтение BM25 по сохранённым данным ограничено 2 048 E5-токенами. У ограниченных методов ёмкость записи равна 8 192 токенам, служебные адреса в этот лимит не входят. Стоимость текста в UTF-8 и число блоков для каждой траектории доступны в [журнале хранения](storage.json.gz). Полное хранение соответствует другим затратам, поэтому служит точкой отсчёта по доступности данных. Метрика чтения характеризует найденные координаты доказательств.

**Какая часть эффекта переносится.** В более ранней тестовой выборке приоритет начала результатов после BM25 дал 873/2 000 против 831/2 000 при полном хранении. На dev порядок изменился: 255/580 против 258/580. Экономия хранения сохранилась (в среднем 7 868 против 36 582 токенов на траекторию). Превосходство над неограниченным хранением по качеству чтения не воспроизводится. [Парные сравнения в обеих выборках](pair-counts.json)

**Происхождение и независимость.** Публикационный профиль DenseFT использует 500 вопросов на 331 траектории для выбора чекпойнта. Ещё 80 вопросов принадлежат 74 траекториям. Между этими двумя срезами есть общие траектории. Все 352 траектории dev и все 580 запросов не пересекаются ни с 1 207 траекториями / 2 000 вопросами test, ни с train. Исходные агрегаты test были известны, а метод был разработан до нового dev-прогона. Это проверка переноса внутри одного корпуса. Ни один из восьми вариантов не обучается по dev-меткам.
