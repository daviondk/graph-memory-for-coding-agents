# Механизм выигрыша BM25 при обученной записи

После того как стали известны исходы полного BM25 (A) и обученной записи с последующим новым BM25 (C), вводим единственное дополнительное условие B. Для всех 2 000 test и 580 dev запросов берём точно ту же маску записи Full при 8 192 токенах, ту же плитку около 64 токенов и тот же лимит чтения в 2 048. A читает из исходной полной истории в порядке её BM25. B читает только сохранённые блоки, но оставляет каждому из них его прежний порядок в рейтинге полной истории. C читает только сохранённые блоки и строит BM25 на этом остатке. Пусть M — метрика запроса. Тогда M(C)−M(A) = [M(B)−M(A)] + [M(C)−M(B)] по каждому вопросу. B−A измеряет эффект изменения допустимых кандидатов при фиксированных исходных рангах и доборе в бюджет. C−B измеряет дополнительное влияние перестройки корпуса BM25, включая IDF и нормировку длины; по одному контрасту их разделить нельзя.

Новых гиперпараметров или нового обучения нет. Оба итоговых набора вопросов и исходы A/C уже известны; это диагностическая проверка, порядок шагов фиксирован. Для B используются тот же pack, стабильное упорядочивание по исходному номеру блока и лексический токенизатор, что в поштучном анализе исходной серии. До оценки B хешируются все поштучные предсказания; входы имеют свои ранее закрытые SHA. Повторное вычисление A и C должно совпасть с ранее опубликованными списками индексов, иначе оценивание останавливается. Метрики — Full Support (полное покрытие всех размеченных символов), символьное Coverage, фактический объём чтения, парные эффекты в п.п. и 95% интервалы бутстрепа 10 000 раз по целым траекториям. Декомпозиция выполняется отдельно на test и dev. У B есть офлайн-доступ к корпусу для получения прежних рангов; B предназначен для интерпретации. Расчёт не меняет базовые пакеты.
