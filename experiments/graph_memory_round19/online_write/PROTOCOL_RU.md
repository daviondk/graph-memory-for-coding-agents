# Запись инструментальных наблюдений при жёстком ограничении памяти

Можно ли при появлении результата инструмента решить, какие исходные фрагменты оставить для ещё неизвестных вопросов? На официальном тесте ISETrace сохраняем хронологию сообщений и координаты символов. Проигрываем только поступление аргументов и результатов инструментов. Вопрос, эталон и ранг источника недоступны селектору записи. Репликация известных агрегатов R18 уже открыла общие характеристики этой выборки, поэтому это новая гипотеза на знакомом бенчмарке. Никакие вызовы из архива не исполняются.

Текст каждого события после его получения разделяем на неперекрывающиеся блоки не более 64 исходных WordPiece-позиций. Отдельно считаем стоимость каждого фактически передаваемого фрагмента, повторно токенизируя его отдельный текст. Модель токенизации та же, что у авторов. Для исправления разреза внутри слова таким образом учитывается реальная стоимость отдельного фрагмента. Границы сохраняются в координатах исходного поля. В потоковом симуляторе при переполнении удаляем наименее приоритетные блоки до восстановления лимита. Удалённый фрагмент впоследствии вернуть нельзя. Для воспроизводимости за пределами памяти агента сохраняем координаты решений. Если несколько блоков имеют одинаковую полезность, используем стабильный хеш события для межсобытийного порядка.

Предварительно фиксируем пять политик. FIFO сохраняет последние наблюдения. Hash хранит блоки с наименьшим псевдослучайным ключом. Head сохраняет первые блоки каждого события, затем вторые и т.д. Ends для каждого события поочерёдно приоритизирует первый, последний, второй, предпоследний блок. Output-head оставляет все события в том же общем сравнении, но отдаёт результатам более частые позиции по глубине: первому блоку аргумента присваиваем глубину 0, второму 2 и так далее, а результатам обычные последовательные глубины. Это проверка относительной ценности двух ролей при записи. Ни одно правило ничего не записывает сверх бюджета текста. Очерёдность между событиями восстанавливаем по message_index и sub_index из нативных кандидатов, для полного совпадения ключей фиксируем порядок по роли и ID. Объём и затраты адресной метаинформации отчитаем отдельно.

Основное сравнение — Head против FIFO. Первичный исход — полностью ли сохранились все эталонные позиции в долговременной памяти с бюджетом 8 192 токена до извлечения. Это измеряет потерю информации на записи. Второй исход — Full Support при чтении из этой памяти одним и тем же BM25 и добором по рангу в 2 048 токенов. Поиск видит только оставшиеся тексты. Иные политики и бюджеты записи 4 096 и 16 384 токена — дополнительные. На неограниченном хранилище тех же 64-токенных блоков вычисляем опорное значение для BM25. Хранимые данные/разметку учитываем отдельно от доступных ранжировщику; оценки не участвуют в отборе. База сравнения исходной публикации привязана к другой единице чтения, поэтому для проверки эффекта самой записи основной контроль — одно и то же представление мелких блоков.

До оценки запечатываем список входов, код записи и чтения, решение по хранению и выбор читателя. Для каждого запроса считаем полноту комплекта, покрытие официальных координат и затраты. Ошибки реализации отделяем от исходов. Парная разница по 2 000 запросам с 95% кластерным bootstrap (10 000 выборок, seed 13, единица ресемплирования — траектория). Отдельно приводим описательную чувствительность к бюджету и дополнительное сравнение с хеш-контролем, которое отделяет специальный приоритет начала события от простого охвата истории.
