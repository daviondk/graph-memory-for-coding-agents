# Независимый аудит восстановления функции после изменения Git

Проверены входной oracle, локальные Git-снимки, модули prepare, predict, score, route, описание эксперимента, основные агрегаты и построчные результаты. Код и данные первоначального эксперимента не изменялись. Дополнительные сравнения в этом документе выполнены после публикации его локальных агрегатов, поэтому носят поисковый характер.

**Существенная поправка к выводу.** По простой проекции номера строки Git получает 118–133 из 157 в зависимости от порядка разрешения неоднозначности. Если учитывать весь диапазон исходной функции, согласование с неизменёнными строками Git даёт **140/157**. Восемь редких лексических отпечатков дают **147/157**. Парная разница +4,46 п. п., 13 выигрышей и 6 поражений. 95% интервал при bootstrap по коммитам от −1,71 до +11,27 п. п. На этой панели преимущество отпечатков над лучшим проверенным здесь Git-контролем остаётся неопределённым.

## Входы, доступ к разметке и знаменатель

- Хеш фактического файла внешней разметки совпал с source-lock. Проверены все хеши внешних данных и скриптов, перечисленные в source-lock и prediction-lock. Архив аннотаций содержит 203 записи изменений. Среди выбранных типов есть 140 TP переименований, 23 TP перемещений, 9 TP перемещений с переименованием и ещё 2 CTP переименования вне критерия. Из 172 TP синтаксический разбор пропустил одну запись со словом “to” вместо “renamed to”. Эту потерю можно исправить при следующем независимом прогоне. Из 171 запросов не идентифицированы 14 старых объектов (11 без совпадения, 3 с двумя).
- Для оставшихся **157** запросов в **66** коммитах нет повторов основного ключа (проект, коммит, старое определение). Два случая засчитаны как промах всем методам по протоколу, в одном неоднозначна новая разметка и во втором определение отсутствует среди кандидатов. Выбор исходного подтверждённого рефакторинга и его старого имени дан экспериментатору oracle. Данных о частоте спонтанного возникновения такого запроса в агентных траекториях этот эксперимент не даёт.
- В записях oracle присутствуют описание, пометка валидации, инструмент обнаружения и валидатор. Точных AST-координат для двух сторон там нет. Предлагаемая метрика требует локально сопоставить имя и суффикс области с AST. 171 из 172 TP изначально обнаружил RefactoringMiner, один — PyRef. Такой набор подходит для сопоставления ранжирования преемников на заданных примерах. Он селективен относительно обнаруживаемых типовых изменений и не позволяет оценить полноту обнаружения рефакторингов в репозитории.
- Предиктор импортирует код подготовки без выполнения main, загружает только queries.json и изменённые Git blobs. Нового имени/области из labels.json в признаки не попадает. Идентификатор case рассчитан в подготовке с участием целевой разметки, но используется для соединения таблиц, не для ранжирования, разрешения ничьей или отбора по новому имени. Проверка разделения основана на прочитанном коде. Хеши контролируют целостность, но не являются независимым опубликованным штампом времени.
- На 155 разрешимых эталонах у **84** старой и новой функций совпало полное множество лексических 5-грамм нормализованного исходника. Для 80 из них функция была единственным кандидатом с таким набором. Редкие отпечатки дали 82/84 в этой страте и 65/71 при изменившемся наборе. Отпечатки не моделируют произвольную глубокую перепись функции. Идентичность множств 5-грамм не равносильна побайтовому равенству тел.
- В реализации старый и новый пул образуются только из затронутых Python-файлов. При агрегации по всем пулам 7 старых и 4 новых входа-файла не удалось разобрать в AST (по парам версий, без глобальной дедупликации блобов). Изменённые файлы с отсутствующими кандидатами всё равно учтены в модели затрат. В этой панели Git сопоставил старый путь во всех 157 оцениваемых запросах и прежний путь доступен в текущей дельте для всех 157. Проверка обещания протокола о доступности прежнего пути, если тот существует вне дельты, требует другой панели.
- Файлы Python извлекаются локально через git cat-file и AST, проектный код не исполняется. Для воспроизведения необходимы либо старые и новые Git-объекты перечисленных SHA, либо повторное клонирование публичных проектов. Скрипт воспроизводит закешированный локальный oracle; исторический sha256 записан в source-lock. Сохранять этот lock отдельно от перезаписывающей его функции prepare полезно для внешнего воспроизведения.

## Сравнение способов проекции по Git

Все следующие варианты получают одну карту zero-context diff и тот же текущий пул функций, что и селектор по отпечаткам. Интервал исходной функции входит в объявленный старый адрес. Прежний и нынешний диапазоны для проверки восстанавливались AST-разбором тех же Git-блобов.

| Способ выбора по Git | Верных / 157 | Только rarelex | Только Git |
|---|---:|---:|---:|
| Равенство старого имени, затем путь и позиция | 121 | 31 | 5 |
| Путь, затем расстояние до начала функции | 118 | 35 | 6 |
| Точное совпадение заголовка с проекцией, затем порядок по имени | 133 | 19 | 5 |
| Число сохранившихся строк в диапазоне кандидата, затем точная проекция заголовка, затем порядок по имени | 140 | 13 | 6 |
| Точная проекция заголовка, затем число сохранившихся строк, затем порядок по имени | 136 | 17 | 6 |

Для варианта с голосованием берём каждую строку старой функции вне старых интервалов изменений Git. Для неизменённой строки отображение определяется суммой предшествующих вставок и удалений. Один голос получает каждое текущее определение, в которое попала такая строка сопоставленного файла. Выбирается максимум голосов. При равенстве используется точное совпадение проекции строки объявления, затем совпадение имени, файла и владельца, позиция и детерминированный идентификатор. Нужны полный diff и старый диапазон. Цена diff и AST-кандидатов в сравнении качества не измерялась. Пять синтетических сценариев (вставка в начало, вставка после строки, удаление, замена, два hunk) дали верный результат на 17 вручную заданных проверках границ, в том числе на строке непосредственно слева от вставки. Для полностью удалённой строки у переноса нет единственного текстового истинного соответствия. Голосование исключает такие строки.

## Статистика и проверка маршрутизации

- 66 кластеров по коммитам для 157 запросов. В трёх самых больших кластерах 15, 11 и 8 примеров. Первичный bootstrap по коммитам учитывает повторение запросов одного изменения. Невозможно распространять его интервал на новые проекты без внешнего теста, поскольку три проекта представлены фиксированной селективной панелью.
- Приведённые в score/routing числа top-1 и числа парных расхождений воспроизводятся. Rеальный выбор первого идентификатора при локальной остановке нигде не разошёлся с полным глобальным ранжированием на этой панели; отчётный интервал [0,0] для разности точностей следует из отсутствия расхождений в исходной выборке. Это не свидетельство доказанной эквивалентности или оценки вероятности промаха на новых изменениях. Среди 116 локальных остановок 114 попали в gold, две были ошибочными так же, как и полный поиск.
- Оценка затрат моделирует ленивое чтение. Реальная программа уже посчитала глобальные признаки и отфильтровала существующие результаты. Ранжирование и доверие локальным кандидатам определяются только прежним файлом и локальными счётчиками совпадений. Теоретически воспроизвести решение с ленивой загрузкой можно. Заявлять наблюдавшуюся экономию времени, вызовов или токенов модели по этому прогону нельзя.
- При холодном кеше на каждый запрос полная стратегия читала бы 7 231 263 байта, локальная с расширением — 3 834 575 (46,97% сокращения). **Если внутри одного коммита кешировать каждый открытый путь**, полная стратегия запросила бы 2 738 067 байтов (306 различных пар коммит–путь), локальная — 1 767 766 (165), сокращение **35,44%**, 95% интервал по коммитам от 23,51 до 48,06%. В 24 из 66 коммитов хотя бы один запрос потребовал полного расширения. Эта чувствительность рассчитана объединением списков нужных путей в коммите и также является моделью стоимости. При кешировании Git-блобов между коммитами результат потребует отдельного расчёта.
- Ложное доверие после удаления настоящего преемника — искусственная абляция. В общем случае удаление функции из Git затронет также фронтир, карту hunks и пул отрицательных примеров. Для оценки принятия устаревших адресов необходимы естественные удаления и разделения функций. Разность «8 редких лексических vs 4+4» отрицательна на один случай, редкость также не доказала преимуществ перед minlex по top-1 (оба 147). Этот материал поддерживает исследование памяти малых адресных записей и стоимости их повторного чтения.

## Совместное использование отпечатков и Git

Независимо восстановлен выбор трёх опубликованных в этом раунде контролей из полных Git-снимков. Для прежних Git name-first, Git position-first и для варианта «сначала восемь лексических отпечатков, затем близость к спроецированному началу определения» правильность по каждому из 157 идентификаторов совпала с identity-cases. Затем тот же комбинированный метод сравнивался с самым сильным из дополнительно проверенных здесь Git-контролей по всему диапазону.

| Страта | Запросов / коммитов | Git, голоса старого диапазона | Отпечатки + Git-позиция | Только гибрид / только Git | Δ, п. п. [95% ДИ] |
|---|---:|---:|---:|---:|---|
| Все | 157 / 66 | 140 | 151 | 13 / 2 | +7,01 [1,83; 13,25] |
| Полные множества лексических 5-грамм различаются | 71 / 34 | 59 | 68 | 11 / 2 | +12,68 [1,56; 25,00] |
| Полные множества лексических 5-грамм совпадают | 84 / 45 | 81 | 83 | 2 / 0 | +2,38 [0,00; 6,25] |

Две последние группы используют имя и область эталона только на этапе анализа исхода и не включают две неразрешимые цели. Коммиты могут содержать оба типа случаев. При замене позиционного разрешения ничьей в гибриде на голосование диапазонов получилась та же правильность по каждому ID. Это оценка post hoc, включая выбор Git-контроля и анализ по изменению тела. На результатах этих же трёх проектов нельзя подтвердить устойчивость эффекта или новизну сочетания отпечатков с Git.

**Различие доступных данных.** Обе стороны получают общий список изменённых Python-файлов, тот же текущий AST-пул и карту Git diff с прежней и текущей версий. Все 157 старых путей сопоставлены картой. В сохранённом tag старой функции фактически есть путь, имя, начальная строка. Контроль по диапазону дополнительно получает end_lineno из AST прежнего блоба. Это соответствует объявленному в протоколе полному диапазону, но даёт контролю больше координат относительно минимального реально сохранённого tag. Конец можно было бы сохранять вместе с началом при первоначальном наблюдении или прочитать из Git позднее. Без тегов и служебных полей кодирование разности end_lineno−lineno через unsigned LEB128 потребовало бы 1 дополнительный байт для 156 записей и 2 для одной. Голосование также знает границы current AST-кандидата и Git patch; выводы об экономии времени, общего хранилища или вычислений из этого сравнения не следуют.
