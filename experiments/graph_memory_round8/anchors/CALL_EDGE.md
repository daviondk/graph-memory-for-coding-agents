# Проверка типа ребра после встраивания

Дополнительная разведочная гипотеза возникла после выявления шести ошибок на Inline Method. Повторная проверка этих шести — разработка механизма, она не образует независимую проверку качества. Общая задача — решить, обозначает ли найденный фрагмент по-прежнему самостоятельное определение исходного символа. Текст исходной функции мог перейти в тело её прежнего вызывающего метода. В этом случае семантика связи меняется с «тот же символ» на «возможное место использования прежнего кода».

Правило использует прежний и текущий снимки фрагмента. Применяем к уверенному лидеру смешанной политики после проверки неизменившегося постороннего определения. Если (1) старый символ исчез по исходному квалифицированному адресу, (2) лидер — другой адрес и уже имел единственное определение в прежнем снимке, (3) прежний код этого определения содержал явный вызов с именем исходной функции, а в текущем этот вызов отсутствует, вместо восстановления исходного адреса возвращаем метку возможного встраивания и указатель на кандидата. Если любой признак отсутствует, дополнительных ограничений не вводим. В Python это синтаксическое сопоставление basename для Name и Attribute, без разрешения перегрузок, импортов и динамической диспетчеризации. Вложенные функции и классы в набор вызовов внешней функции не входят.

Сравнить с одной проверкой прежнего определения, число отброшенных правильных переходов и число оставшихся ложных на 157 положительных основной панели, 11 наследованиях, 6 встроенных методах. Отдельно посчитать, совпадает ли адрес получателя кода с внешней аннотацией Inline Method. Отчёт содержит все случаи и доступ к прежнему Git-снимку как явное условие. Проверка правила на заранее невиденных встраиваниях остаётся необходимой.
