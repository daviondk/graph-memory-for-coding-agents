# Как устроена сравниваемая графовая память

Здесь память — статический снимок истории действий, к которому после работы агента поступает вопрос. Единица извлечения — фрагмент аргументов инструмента или его результата. Крупное поле режется примерно по 504 WordPiece с перекрытием 64. Дополнительные узлы представляют вызовы и объекты. Они участвуют в обмене сообщениями. В текстовый бюджет читателя могут попасть лишь кандидаты с исходными координатами. Структуру формирует опубликованный код GraphMemory из наблюдаемого порядка исполнения. [Публикация](https://arxiv.org/abs/2609.25913) · [Исходный граф](https://github.com/xiaoqi-7/GraphMemory/tree/df29287116fa1565b3fd6b485022cd6090dc0b27/graph_memory/graphs/provenance)

Пусть $e_i$ и $e_q$ — нормированные векторы фиксированного PU Dense-FT для текста узла и вопроса. Каждый текст кодируется с соответствующим префиксом. Нативный поставщик графовых признаков заносит в тензор FP32 значения $s_i=e_i^Te_q$, для временного узла вопроса численный признак равен нулю. Общая память содержит весь нативный набор узлов и связей. Временный узел вопроса содержит его вектор и собственные преобразования. Публичный код строит только физические сообщения, которые проходят по семи видам связей в обоих направлениях. [Тензоризация](https://github.com/xiaoqi-7/GraphMemory/blob/df29287116fa1565b3fd6b485022cd6090dc0b27/graph_memory/models/graph_retriever/provenance.py)

Для каждого из трёх графовых слоёв и каждого типа ребра $r$ поступающие в узел $i$ сообщения имеют типоспецифичное линейное преобразование и коэффициент $1/d_{i,r}$, где $d_{i,r}$ — входящая степень для этого типа. Сумма таких средних добавляется к собственному линейному преобразованию $h_i$, далее ReLU и LayerNorm. Это вводит явную зависимость представления кандидата от наблюдавшихся узлов на расстоянии до трёх рёбер. Нормировка ограничивает суммарный вес соседей одного типа при росте их числа. Сама по себе формула не устанавливает улучшения конкретной метрики. [Графовые слои](https://github.com/xiaoqi-7/GraphMemory/blob/df29287116fa1565b3fd6b485022cd6090dc0b27/graph_memory/models/graph_retriever/internals/neural.py)

Итоговый логит $z_i=s_i+u_\theta(h_i,h_q,h_i\odot h_q,s_i)$. У последнего линейного слоя $u_\theta$ изначально нулевые веса и смещение. При таком состоянии $z_i=s_i$ для каждого кандидата. Это позволяет реализовать строго согласованный контроль на идентичных тензорах запроса и узлов. После обучения порядок двух кандидатов $i,j$ изменится, если разность $u_j-u_i$ пересилит исходный разрыв $s_i-s_j$. Возврат бюджетного списка остаётся отдельной дискретной операцией. Из роста релевантности на отдельных узлах не следует, что в окно войдут одновременно все эталонные символы. [Модель чтения](https://github.com/xiaoqi-7/GraphMemory/blob/df29287116fa1565b3fd6b485022cd6090dc0b27/graph_memory/models/graph_retriever/internals/neural.py)

Обучение использует BCE по выбранным размеченным кандидатам. Вес положительного примера равен отношению числа отрицательных примеров к положительным по всей train-выборке. По одному положительному запрашиваются 2 случайных, 2 лексически трудных, 1 семантически трудный и 1 графический сосед; фактически доступные количества отражены в pair-inventory.json. Само построение отрицательных использует исходный E5. Закреплённый E5 уже после PU-дообучения даёт признаки и начальные оценки для R-GCN. Усреднение loss по фактически отобранным примерам текущего пакета, ограничение нормы градиента 1, AdamW, выбор сохранённой эпохи по node-level recall@5 на 500 dev — нативная процедура. На test оценивается точное покрытие символьных интервалов разных событий при ограничении контекста. Это две разные задачи оценки.
