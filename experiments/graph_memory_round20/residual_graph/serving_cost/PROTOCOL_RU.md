# Парная задержка обслуживания одной графовой памяти

Сравниваем две реально исполняемые процедуры на одном CPU и для одного запроса одновременно. Входы общие — один уже разобранный нативный граф, те же FP32 E5-признаки и одна и та же величина cosine для каждого PU. Один вариант добавляет scalar prior восьми типизированных степеней к линейной функции семантического ранга. Другой выполняет обученный авторский трёхслойный residual R-GCN. Выход обоих путей — упорядоченный список тех же идентификаторов кандидатов и последовательный prefix исходных длин до 2 048 токенов. Семантический энкодер, общий архив и диск исключены из измерения теплого пути.

Панель зафиксирована хешем ID до измерений: ровно те же 96 из 2 000 test-запросов, что в ранее зарегистрированном runtime probe. Протокол времен не использует test gold и не отбирает запросы по сходству рангов. Результаты выдачи сверяются с независимыми исходными запечатанными порядками; отмечаются возможные перестановки почти равных FP32-оценок. Для каждого запроса оба пути стартуют с одинакового семантического вектора. У двух путей разные служебные структуры, и для обоих они материализованы до измерения. Для R-GCN дополнительно показываем время сборки батча 1 отдельно. Для структурного индекса выделяем разовый обход каждой уникальной траектории. Замер состоит из 8 парных блоков с чередованием очередности двух методов по вопросу и блоку. Сначала каждый результат прогревается и проверяется. Точные времена поштучно публикуются. Сравниваем медиану парных отношений, p50/p95, отношение средних и 95% кластерный bootstrap этого отношения по траекториям. Это локальный CPU microbenchmark при многозадачной нагрузке, а не end-to-end latency.

Учитываем отдельно размер исходных графов в сжатых файлах (в них есть исходная проекция), общие плотные векторы, надбавку к пайплайну от 14-реляционного обученного checkpoint, реальные размеры массивов восьми целочисленных степеней и скомпилированного скалярного prior. Последние два — альтернативные представления. Дедуплицируем структурные массивы по траектории. Временную сборку числовых признаков R-GCN для каждого запроса и привязку семантического ранга к позиции ID отражаем явно. Не суммируем общие данные, сериализацию файловой системы и числовые payload как единую стоимость. Все варианты используют один поток PyTorch и BLAS, допустимые фоновые нагрузки и точный состав интерпретатора записываются. Проводим отдельно на hash64, затем на полном обученном checkpoint. GPU в тесте времени не используется.
