# Перенос замороженной политики записи на выбор повторного теста в QuixBugs

До запуска модулей и чтения их исходов. Контролируемая задача передачи работы между шагами кодового агента. Для каждого эпизода агент наблюдает реальные обращения к исходникам, тестовым данным и stdout pytest, завершает запись и получает один фиксированный вопрос. Требуется выбрать один ранее упавший точный параметризованный pytest nodeid для повторного запуска или воздержаться, когда падений не было. Правильность положительного ответа подтверждается повторным выполнением выбранного теста на том же варианте программы. Исторические дефекты и тесты взяты из QuixBugs; сценарий работы и порядок инструментов построены для этого эксперимента.

Из закреплённого публичного коммита 4257f44b0ff1181dedaedee6a447e133219fcebf допускаем Python-программы, для которых есть две авторские реализации, одноимённый pytest-модуль и штатный JSON с тестовыми случаями. Исключаем девять имён из R9/agentvalue и R11/multiset_quix. Первые 18 допустимых в порядке SHA-256 от строки `R20 code transfer target|<name>` станут целевыми программами. По каждому имени образуем пару эпизодов с дефектной и с исправленной реализацией. В оба добавляем 12 исправленных других программ по SHA-256 `R20 context|<target>|<other>`. Все 13 программ в одном и том же порядке SHA-256 `R20 order|<target>|<member>`. Отбор и порядок не зависят от кодов возврата. Никакая программа не заменяется по исходу. Общие безопасные открытые проекты — единственные исполняемые данные. Полные сырые журналы хранятся вне публикуемого каталога на D.

В каждом шаге реально читаются текст реализации, авторский тестовый файл, JSON входов, затем предъявляется действительный stdout запуска всего pytest-модуля. Кэш разрешён только для бит-в-бит тех же артефактов и варианта исполнения; раскрываем число уникальных запусков. Аргументы, обращённые к модели, имеют одинаковый вид для обеих версий. Приватные fixture paths, длительность, имя хоста и выбор `--correct` скрываются. Набор данных и флаги версии не передаются в read query. Идентификаторы событий получаем из позиции вызова; соседние независимые эпизоды не обмениваются памятью.

Основные политики — точные R19 full, output_head и FIFO при записи 8 192 и BM25-чтении 2 048 токенов. Тот же токенизатор, 64-токеновые блоки, константы выбора, веса, порядок разрешения ничьих. Добавим позиционную абляцию R19, полную историю с тем же читателем и компактный специализированный контроль, сохраняющий один лексикографически минимальный наблюдавшийся nodeid со строкой FAILED, или пустое состояние. Текст читатель восстанавливает только из соседних прочитанных диапазонов одного события. Любой предлагаемый идентификатор принимается только после точного совпадения с допустимым локальным pytest ID. Эталонному журналу доступен независимый машинный pytest-хук. После фиксации всех предложений исполнитель повторяет каждый различный предложенный nodeid в соответствующем варианте. Учитываем размер специализированного состояния; служебные метаданные универсальных вариантов оцениваются отдельно от бюджета исходных токенов.

Первичный контраст — full минус output_head по доле корректных решений на всех 36 эпизодах. Вторичные — FIFO, позиционная абляция, полный BM25 и специализированный контроль. Покажем положительные/отрицательные решения, неизвестные состояния, долю занятого бюджета и времена выполнения. Timeout 8 секунд на отдельный pytest-процесс, максимум три конкурентных. Неполная проверка одного из модулей даёт неизвестный исход эпизода и нулевой вклад в число подтверждённых успешных действий всех методов. Исключать такие эпизоды из основного знаменателя запрещено. Дополнительно укажем знаменатель полностью проверенных. ДИ разности — парный кластерный бутстреп по 18 целевым алгоритмам, 10 000 повторов, seed 20. Исполнитель и текстовый парсер фиксированы; генеративная модель не участвует. Часть контекстных программ повторяется между эпизодами, поэтому интервал условен относительно этого набора задач.
