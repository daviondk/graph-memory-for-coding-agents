# Воспроизведение панели QuixBugs

Для независимой проверки файлов и исходов достаточно `python -B verify.py`. Она проверяет манифест, хеши фиксаций, состав хеш-выборки, ограничения бюджета, собирает точный набор увиденных и допустимых тестов, пересчитывает исходы из квитанций первоначальных запусков и последующих запусков одного теста. Численные прогнозы и исходы находятся в архиве, исходники берутся из авторского MIT-репозитория. [QuixBugs](https://github.com/jkoppel/QuixBugs) · [Фиксация наблюдений](observation-lock.json) · [Фиксация прогнозов](forecast-seal.json)

Для повтора требуются Git с закреплённым коммитом QuixBugs, Python с pytest 8.4.2, Python-окружение исполняемой R19 с NumPy, tokenizers, rank_bm25 и исходной GraphMemory, а также `graph_memory_round19/online_write` и `graph_memory_round19/write_learned` в соседнем каталоге. Код записывает материалы этого опыта в собственный каталог, сырые временные файлы — в отдельный каталог на D. Переменные `QUIX_REFERENCE`, `QUIX_PRIVATE` и `QUIX_PYTHON` задают репозиторий QuixBugs, новый каталог сырых материалов и отдельный интерпретатор pytest; путь к токенизатору R19 задаётся через `X20_DATA`. Для нового измерения используйте пустой каталог сырых наблюдений и рабочую копию материалов. Время и хеши сырых stdout могут зависеть от платформы.

Выполните последовательно `study.py plan`, `study.py observe`, `study.py predict`, `study.py grade`, затем `stream_index.py` и `stage_loss.py`. Каждому имени скрипта предшествует вызов Python с `-B -X utf8`. Для независимой точечной проверки подойдёт нативный pytest nodeid из `native-receipts.json.gz`. При новом запуске `verify.py --write-manifest` обновляет собственный манифест рабочей копии. Проверьте `verify.py` ещё раз без параметров. Приватные файлы stdout и служебных наблюдений содержат фактические данные исполнения; среди публикуемых файлов остаются их SHA-256, точные селекторы тестов, статусы и численные прогнозы.

Нативный pytest-плагин записывает список коллекции и все фазы, раздельно от stdout. В опубликованной квитанции содержатся список собранных тестов, наблюдавшиеся падения, статус полноты и код процесса. Только совпадение одного заданного nodeid с одним реально собранным и упавшим тестом засчитывает положительное точечное действие. Кэши повторно используются по варианту и точному аргументу процесса; число логических выборов методов может превышать число уникальных процессов. Вторичный контроль потокового индекса отдельно проверяет все промежуточные состояния, включая размер одного служебного байта. [Протокол](PROTOCOL_RU.md)
