# Воспроизведение упаковки и подсчёта

Для каждой проверяемой панели дополнительный вызов `clean_sensitivity.py <panel>` после строгого оценивания воспроизводит анализ по двум подгруппам из R19. Он использует только поштучные результаты и проверяет SHA ранее опубликованных флагов дословного совпадения. `run_cpu.ps1 -Panel availability` и `run_cpu.ps1 -Panel hash64` проводят полную последовательность для двух сокращённых CPU-ранжировщиков.

Проверка уже запечатанных данных доступна через `python -B verify.py --require-both`. Она сверяет контрольные суммы, идентификаторы всех вопросов и траекторий, вложенность множеств координат, стоимость для каждого запроса и агрегаты. При наличии только одной полностью готовой панели флаг `--require-both` снимается. Исходные вопросы, веса и буквальные ответы в данный пакет не входят.

В чистой рабочей копии используйте структуру R17/R18/R19/R20 и внешние данные из исходных исследований. Нужны полные официальные поля test ISETrace в проверенной проекции из `graph_memory_round18/isetrace_e5/inventory.json`, эталонные символьные диапазоны R18, нативный GraphMemory, E5 tokenizer, NumPy и tokenizers. Если корень данных отличается от D:/CodexResearch, передайте `X20_DATA`.

1. Разово запустите `pack.py design`. Затем `pack.py plan dense` и `pack.py predict dense`. Это проверяет upstream SHA и фиксирует U/W/F без доступа к gold.
2. Запустите `overlap_control.py plan dense`, затем `overlap_control.py predict dense`. По окончании `score.py dense` независимо сверяет нативный расчёт с отдельной реализацией объединения и пересечения интервалов и сохраняет поштучные исходы.
3. Строгая ветвь была добавлена после результатов Dense-FT и до тестовых рангов R-GCN. Сначала `strict_render.py plan`, затем `strict_render.py predict dense` и `strict_render.py score dense`. Хеш исходного известного Dense-FT результата входит в `strict-plan.json`.
4. После готовности полного upstream `residual_graph/forecast-seal.json` повторите шаги выбора и подсчёта с аргументом `rgcn`. Общие design и strict-plan не перезаписываются. Модель R-GCN получает те же правила и тот же допустимый объём, что Dense-FT.
5. Для независимого восстановления всего входного текста используется `render_audit.py dense` и, соответственно, `render_audit.py rgcn`. Нужен Python с transformers, локальный каталог токенизатора E5 и исходные строки. Этот этап работает на CPU. Затем `report.py`, `verify.py --write-manifest --require-both` и `verify.py --require-both`. Для всех вызовов Python предпочтительны ключи `-B -X utf8`.

Каждый файл прогнозов содержит массивы `[event_id, json_pointer, char_start, char_end, token_count]`. Конец интервала исключён. Пересечения удаляются только внутри одинакового поля одного события. Идентификатор вопроса и траектории входит в каждую запись. Хеш итогового текста в контрольной сводке вычисляется из упорядоченного списка «ID вопроса, метод, SHA-256 UTF-8 представления, количество токенов, количество байтов». Расход строгой выдачи проверяется токенизацией реальной строки целиком с одним переводом строки между цитатами, без усечения, padding и спецтокенов. Отдельный словарь адресов и токены пользовательского вопроса не тарифицируются, как и метаданные provenance unit в основном исходном сравнении.
