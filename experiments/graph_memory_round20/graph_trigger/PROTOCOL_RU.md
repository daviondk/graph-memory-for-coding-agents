# Нужен ли графовый ранжировщик на текущем запросе

На ISETrace оцениваем условное использование обученного residual R-GCN. Для каждого вопроса сначала доступен полный порядок standalone PU Dense-FT, полные исходные координаты кандидатов, текст вопроса и цены PU. Граф вызывается только в выбранных случаях. У обеих моделей одинаковые кандидаты и упаковка skip до 2 048 токенов. Различие фактических рангов standalone Dense-FT и графового seed допустимо и проверяется владельцем ранжировщиков отдельно.

До меток графа фиксируем признаки: длина вопроса WordPiece, число союзов/временных связок из списка and/or/both/between/before/after/then, логарифм количества PU, первые косинусные score и разницы первого со вторым и пятым PU, стандартное отклонение первых десяти score, доля разных полей среди первых пяти, максимальная доля одного поля среди первых десяти, доля выходных полей среди первых пяти, нормированная цена пяти первых, число уникальных полей и свободная доля бюджета нативного skip. Общая цена ранжирования и статистики кандидатов не принимается за ноль. Предиктор не читает R-GCN score/ранг, эталонные цитаты, идентификатор репозитория или ID вопроса как признак. Значения ID используются только для воспроизводимого разрешения ничьих.

На авторских 500 dev-запросах оцениваем парную дельту Full Support(graph) минус Full Support(dense); эмпирически проверяем тех же кандидатов и точные символьные координаты. Одна Ridge-регрессия с alpha=25, стандартизацией по dev, невзвешенными запросами и свободным intercept. Фиксированных 500 наблюдений используем для обучения и калибровки квантилей, поэтому performance на данных подгонки не служит оценкой качества. Базовый Dense-FT ранее выбирался по той же dev, целевая оценка выполняется на 2 000 test с непересекающимися ID и траекториями. Когорта ранее изучалась в других задачах; этот предиктор до фиксации решений не обращается к меткам test.

Для бюджетов 25/50/75% выбираем порог упорядочения dev по убыванию предсказанной дельты с отдельным SHA-256 для разрешения ничьей. Тот же полностью фиксированный порог применяется к отдельному test-вопросу без знания состава других test. Аналогично калибруем бюджетный контроль «вызвать при малой разнице двух лучших Dense-FT score». Второй контроль выбирает ровно фактическое количество вызовов основного метода в каждом бюджете среди test по независимому SHA-256. Этот контроль использует известное число запросов панели и служит аналитическому сравнению. Приводим также всегда dense, всегда graph и описательный достижимый при знании ответов oracle: сначала вызываем граф на запросах, где только он имеет полный support, затем на ничьих и последними — на запросах, где выигрывает dense. Результат oracle вычисляется только после запечатывания прогнозов и решений.

Первичное заранее установленное условие для 50%-режима: фактически вызвать граф на ≤60% test и получить нижнюю границу двустороннего 95% ДИ для ΔFS относительно always-graph строго выше −1,00 п.п. Интервалы парные, percentile bootstrap с возвращением по целым траекториям, 10 000 повторов, seed 20. Вторичные — FS и Coverage, плотность и читаемые токены, парные выигрыши/проигрыши, разница с matched random и margin; доля обращений на тесте не тождественна ускорению. Укажем время feature extraction, обучения и решения отдельно от стоимости обеих моделей; реальные GPU-вызовы по одной заявке в этой симуляции не измеряются. Все графовые test score используются для оценки заранее выбранных маршрутов из двух имеющихся рангов. Отдельно покажем обе стороны разногласий и достижимый резерв. Цитаты и метки test разрешены только после фиксации весов, порогов и всех test решений.
