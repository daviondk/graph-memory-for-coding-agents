# Запись о следующем использовании объявления в памяти контекста кода

Протокол от 18 ноября 2026, до обучения и раскрытия тестовых меток. Работа R3-R. Используем официальный Python RepoBench-R v0 с четырьмя полными test_easy/test_hard для cross_file_first и cross_file_random. Запрос содержит только поле code. Система получает только список фрагментов context, последний префикс до 120 физических строк и его варианты меньшей длины. Никаких import_statement, next_line, repo_name, file_path, номера gold, режима CFF/CFR или позиции кандидата в обучаемых признаках. Список доступного контекста дан авторами. Будущая строка физически не читается ни при одном вызове. Файлы с исходным кодом не импортируются и не исполняются. Отдельный только-метаданные шаг удаляет из обучения все тестовые проекты. Из двух первых train_hard Parquet (один CFF, один CFR) выбираем до 3000 обучающих записей каждого по хешу, ≤25 записей на один проект в каждой части. Разбиение между train и test авторское, дополнительно разделяем по полному имени репозитория.

Гипотеза — если в предыдущей работе был переход от похожего кода к вызову объявления, стоит поднять соответствующий фрагмент в выдаче. Для каждой объявленной функции или класса в кандидатной памяти извлекается её основное имя и имена объявленных методов. В видимом префиксе сохраняются косвенная связь переменной с классом после присваивания и завершённые случаи употребления: к имени объявления и его использованию присоединяется контекст предыдущих строк. При чтении используются сходство нынешнего префикса с тем, что наблюдалось перед прежним использованием, уникальность связи и давность. Выгоден повтор схемы действий, первое использование с новой лексикой может не выиграть. Математическая интерпретация — взвешенное эмпирическое условное ожидание использования конкретного объявления при похожем предшественнике. Подтверждение в прямом сравнении с теми же записями без присоединённого предшественника и с плацебо заменённых связей. Это модель чтения памяти о сегменте исходного кода, а не наблюдение полноценного цикла решения issue.

Целевая метрика — micro Acc@1 по всем тестовым строкам официальных четырёх частей, первичное сравнение обучаемого полного графа с вариантом владельцы+давность без контекстных переходов. Покажем отдельно каждую часть, Acc@3, Acc@5, MRR, среднее число просмотренных фрагментов до корректного, долю/объём контекста топ-1, результаты по репозиториям. Сравним официальный Jaccard на токенах Salesforce CodeGen на последних 3 строках и на последних 120, классический BM25 по идентификаторам, одинаково обучаемую плоскую модель, чтение владельца+давности, полный и плацебо (контексты предшественников циклически сдвинуты в пределах того же префикса). Плацебо обучается и оценивается с тем же преобразованием. Дополнительно оцениваем обучаемую плоскую модель и правила ролей при тех же 3 строках что у авторов, чтобы отделить рост доступного входа от качества ранжирования. Все обучения — одна предзаданная HistGradientBoostingClassifier, s=261118, max_iter=75, max_leaf_nodes=15, min_samples_leaf=28, L2=1, learning_rate=0.10. Один положительный на задачу и суммарный вес отрицательных такой же, каждая задача имеет одинаковый вес. Признаки только числовые. Код детерминирован, равные баллы — исходный порядок, как в репозитории авторов. Длина символов, время локальной CPU обработки и число записей сохраняются; генерация LLM и расходы токенов генерации отсутствуют.

Публикуются все методы независимо от направления эффекта и все четыре страты. Для основных парных разностей выдаём 95% интервал bootstrap репозиториев, 10000 повторов с фиксированным seed, число выигрышей и проигрышей, macro разность и разницу при устранении повторных пар идентичных запросов. Evidence без угадывания новых коэффициентов по тесту. Проверяется совпадение реализации официального Jaccard с таблицей исходной статьи с учётом округления, иначе заранее различаем версии данных/подсчёта. Сравнение с внешними лидерами ограничено совпадением задач, выдачи и длины. При недоступных поштучных прогнозах не строим парные интервалы по чужому среднему и не заявляем SOTA по результатам одной исходной статьи. Допускается постфактум диагностика зарегистрированного результата с явной маркировкой.
