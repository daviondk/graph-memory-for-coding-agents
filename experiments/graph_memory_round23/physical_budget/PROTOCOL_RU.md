# Обновление ограниченной токенами выдачи после изменений в памяти

Рассматриваем физическое исполнение уже вычисленных p/c-баллов для мелких интервалов. Исходными данными служат нативные ранги полной R-GCN без content.next, модель fine_train и ранее запечатанная строгая выдача. Контрольный источник альтернативных баллов — обычная нативная R-GCN с теми же Dense-весами и той же моделью чтения. Тексты в переносимую фикстуру не включаются. Вычисления LLM и признаков не входят в стоимость SQL-оператора.

Из 1 207 тестовых историй детерминированно берём первые 192 по SHA256 строки `pack-update/trajectory/` + id, затем один вопрос из каждой истории по хешу `pack-update/query/` + id. Исходы и скоростные результаты при выборе не используются. Фиксированные бюджеты 1 024, 1 536, 2 048 и 3 072. В каждом случае защищаем первые две реальные PU основного ранжировщика. Кандидаты идут по убыванию p/c со стабильным приоритетом индекса исходного блока при равенстве. В число допустимых входят только принадлежащие PU блоки. Из совпадающих по месту выбираются неперекрывающиеся. На 2 048 сравним каждую исходную упорядоченную последовательность с ранее запечатанной; при остальных бюджетах эталон — полный независимый проход.

Подготовленная запись содержит id вопроса и блока, два реальных вычисленных балла, стоимость и интервал. SQLite хранит основную таблицу и, в одном из условий, покрывающий B-tree по порядку чтения. Для статического чтения сравним поиск по вопросу с нативной сортировкой SQLite, поток по покрывающему индексу и готовый материализованный ответ. Для холодного режима переоткрываем соединение и явно называем его холодным лишь на уровне SQLite; файловый кеш ОС не сбрасываем. Для тёплого режима переиспользуем соединение. Указываем число возвращённых строк, размер таблиц и индексов, число и цену обновлений. Строки Python и чтения с накопителя различаем.

Основной динамический сценарий — корректировка балла одного равномерно выбранного по воспроизводимому хешу блока на его значение в альтернативном ранжировании, когда остальные баллы и два защищённых PU сохраняются. Контроли чувствительности — обновление выбранного в старый ответ блока, пакет 8/32 баллов, полная замена всех отличающихся баллов и появление ранее скрытого блока. Реальные баллы вносятся при моделируемом расписании обновлений. Регистрируем число реально изменившихся выдач. Для пакетных сценариев число изменений ограничено доступными различающимися блоками.

Сравниваем обычную инвалидизацию с полной пересборкой по покрывающему индексу и точное обновление прежнего ответа. Последнее проверяет, способны ли изменённые элементы нарушить прежний выбор, сохраняет гарантированно неизменный префикс до первой затронутой позиции и при необходимости заново исполняет жадный выбор по новому суффиксу индекса. Для сравнения храним один и тот же материализованный результат до изменения. Обновление позиции одного элемента означает, что порядок всех прочих ключей сохраняется. Если затрагиваются защищённые PU или множество доступных интервалов неизвестно, требуется полная инвалидизация. Сравнение скоростей допустимо только после полного равенства выбранных блоков и их порядка. Положительный эффект на данном фиксированном операторе не экстраполируем на стоимость генерации ответа или всего агента.

Первичное сравнение времени — парная медиана разностей и отношение медиан для одного случайного изменения при бюджете 2 048, вместе с доверительным интервалом пересэмплирования вопросов/траекторий. Остальные бюджеты и интенсивности дают кривую затрат. Замеры ориентированы на эту машину и совместную фоновую нагрузку; укажем порядок прогонов и повторы. Отдельно измеряем вставку и изменение строк базы, цену хранения/построения индексированного и готового ответа и устойчивую запись с COMMIT. Не включаем генерацию фикстуры в таймер запросов и показываем стоимость формирования материала отдельно.
