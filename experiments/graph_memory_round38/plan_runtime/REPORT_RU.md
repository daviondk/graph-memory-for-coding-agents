# Можно ли устранить стоимость выбора плана, сохранив предыдущее чтение в процессе?

**Лишние SQL-чтения удалось убрать полностью при попадании в кэш. Преимущество по времени полного цикла перед постоянным отложенным планом L подтвердить не удалось.** В основной реализации на одну правку со всеми обращениями понадобилось 90,56 мкс у селектора H, 87,85 мкс у L и 94,18 мкс у постоянной адресной таблицы A. После упаковки служебных данных полный цикл H занял 91,70 мкс против 89,81 мкс у L на новом парном прогоне, отношение **1,021 [0,977; 1,111]**. При промахах кэша H был на 20,4% медленнее L. ## Какой режим моделировали

В Handoff Debt редактор вернул агенту пронумерованный фрагмент файла. Обработчик уже получил номера строк и хеши содержания. Если тот же рабочий процесс хранит снимок активного файла до следующей правки, он может повторно использовать эти данные при записи. В R37 диспетчер каждый раз запрашивал сохранённый список номеров из SQLite и отдельно определял маршрут при каждом чтении; среднее время H составляло 64,82 мкс против 57,11 у постоянной L, исключая первоначальную запись снимка. В R38 вход образуется только из ранее видимых строк, типов ранее выполненных операций с этим путём, текущей замены и её квитанции. Все 128 решений H совпали с замороженными внешними моделями R37. Переобучения на том же наборе не было. [Предыдущий эксперимент](../../graph_memory_round37/plan_choice/REPORT_RU.md) · [Первоисточник данных](https://aclanthology.org/2026.emnlp-main.738/)

**A** сохраняет готовые адреса после правки. При попадании в кэш ей не нужен SQL-запрос для чтения прежних пар; результат уже есть в памяти после вычисления. **L** сохраняет интервал замены и квитанцию. Первый запрос собирает новый ответ из прежнего снимка, следующие возвращают тот же кэшированный ответ. **H** применяет прежнее правило выбора A/L, используя количества адресов, их пересечение с квитанцией и изменяемой областью, давность и историю просмотров и замен. Предыдущие номера упорядочены, поэтому размер области определяется двумя бинарными поисками. Числовые вклады признаков для небольших целых значений табулированы; для значений выше 256 используется исходная формула. Всем схемам разрешено сохранять первый полный ответ, а постоянные контролы не оплачивают прогноз.

Начальное формирование словаря из входных хешей и его транзакционная запись входят в замер. H дополнительно оплачивает индекс номеров, обработку цепочки видимых типов действий текущего пути, собственный заголовок и прогноз. Экспорт исходного корпуса и общая подготовка схемы БД находятся вне измерений. Использованы 128 эпизодов из 25 задач пяти репозиториев, 76 подтверждённых нулей, 52 окна с чтениями, 122 обращения. Новая нагрузка повторяет наблюдённую частоту строгих просмотров из R37; один такой просмотр моделируется полным запросом памяти. Доля попаданий кэша в реальном агенте неизвестна, поэтому раздельно измерены два предельных режима.

В режиме промахов состояние файла в процессе отбрасывается перед обработкой правки и снова перед первым чтением изменённой версии. H вынуждена восстановить прежние координаты для выбора, тогда как L может сразу записать интервал и квитанцию. Идентичность результата и восстановление маршрута проверены также при двух настоящих закрытиях и повторных открытиях SQLite-соединения на всех 128 файлах, включая окна с нулевым спросом. Время открытия нового процесса или холодного дискового ввода в эти числа не входит.

## За счёт чего изменились затраты

В основном прогоне после того, как прежний снимок сохранён, обработка правки и запросов заняла 38,98 мкс у H против 40,62 у L и 46,19 у A. Среднее H/L для этой части — 0,959 [0,910; 1,086]. Готовый снимок устранил прежние 128 обращений к таблице метаданных при записи; кэш первого ответа устранил SQL-запросы при тёплых повторах. Стоимость первоначального помещения снимка в SQLite составила 51,58 мкс у H, 47,23 у L и 47,99 у A. При учёте обеих стадий преимущество H перед L исчезает. По сравнению с ценой «выбранная фиксированная схема без диспетчера» стоимость H после первоначального помещения снимка в память выросла на 4,35 мкс. В R37 разница в том измерительном режиме составляла 13,95 мкс; в R38 улучшены и контролы, поэтому два числа не образуют изолированной абляции одного изменения.

В первичном варианте H добавляет служебную запись на каждый исходный снимок. После получения результата зарегистрирована дополнительная проверка, в которой три 32-битных числа H (позиция, количество предыдущих просмотров, количество предшествующих замен) добавляются к первому уже сохраняемому 32-байтовому хешу. При обращении API возвращает только первые 32 байта значения. Резервное представление пустого снимка проверено отдельно. При промахе до правки один SQL-запрос возвращает исходные факты и метаданные. После правки объединённый запрос получает постоянную запись о маршруте, базовые пары и квитанцию за одно обращение к SQLite. Общий объём операций накопителя здесь не измерялся.

## Стартовая стоимость и границы

Основные результаты относятся к долгоживущему процессу с готовыми таблицами коэффициентов. Их первоначальное вычисление для пяти внешних моделей добавляет в основном резидентном прогоне **9,28 мкс на эпизод**, если распределить всю работу ровно на 128 окон; полный H/L тогда равен 1,136 [1,088; 1,238]. Во вторичном опыте заранее создан один бинарный файл размером 102 800 байт; его разовое построение с записью заняло 1,00 мс. Чтение и распаковка при старте процесса добавляют 3,60 мкс на эпизод на той же панели; H/L с этим расходом = 1,061 [1,016; 1,149]. При другой продолжительности процесса и числе одновременно используемых моделей амортизация изменится. [Аудит выдачи и восстановления](independent.json)

Оптимизированный селектор можно применять корректно, не выполняя SQL для выбора у резидентного активного файла. На измеренной панели эта экономия сократила накладные расходы, но при равных возможностях кэширования **не установлено преимущество H над постоянной L по полному циклу**. При вытесненном снимке L выиграла по времени, поскольку для записи ей не требуются прежние строки. Эффекты проверены для одного изменения файла и прежней нагрузки. Хранение нескольких версий, частота реальных вытеснений и задержка многофайлового сервиса требуют отдельных измерений.
