# Цена выбора при резидентном снимке и восстановлении после промаха

Фиксируем прежние 128 окон, модели и 128 решений H из R37/plan_choice. Новые примеры или подбор параметров не используются. Проверяются те же статические A (материализовать перенос при записи) и L (сохранить интервал и квитанцию). Цель — измерить инженерную экономию, когда прежний просмотр этого файла доступен в работающем процессе, и цену восстановления, когда он вытеснен. Прошлые числовые результаты известны.

У всех планов одинаковая оптимизация чтения: предыдущий видимый снимок может оставаться в памяти между просмотром и успешным редактированием. Для A готовый словарь новых адресов доступен сразу после транзакции. L хранит ранее виденные строки и квитанцию до первого запроса. Всем разрешено кэшировать первый упорядоченный ответ одной неизменной версии для остальных её обращений. Постоянные планы используют свой заранее известный маршрут и не оплачивают признаки селектора. H повторяет подписанное аффинное решение R37. Его десять числовых вкладов заранее вычисляются для небольших целых значений; для больших значений используется та же формула. Адреса упорядочены при исходном просмотре; пересечение с областью правки определяется бинарным поиском. Новый селектор обязан воспроизвести все прежние решения побитно как метки A/L.

Первичный сценарий — один процесс сохраняет предыдущее явное чтение активного файла, затем обрабатывает правку и R реальных обращений к версии. Измерение жизненного цикла включает формирование состояния из входных хешей, запись начального снимка с коммитом, подготовку требуемых исключительно H счётчиков и индекса, обработку правки с коммитом, первую выдачу и последующие обращения. Предшествующие события того же пути передаются как уже распознанные типы view/edit; H оплачивает построение накопленных количеств из этих типов. Глобальный парсинг корпуса во время опытов не нужен ни одному варианту. Для H счётчики и координата предыдущего просмотра сохраняются компактной служебной записью в той же B-tree, без отдельной таблицы. Стоимость создания таблиц функций для H измеряем и отдельно прибавляем амортизированную цену первоначальной загрузки на 128 запросов. Сами коэффициенты уже обучены в R37.

Во втором сценарии между начальным просмотром и правкой, а затем перед первым чтением теряется состояние процесса для соответствующего файла; страницы SQLite и ОС остаются прогретыми. H восстанавливает все исходные числа из одной таблицы. Если план L указан записью интервала в БД, комбинированная SQL-выдача позволяет восстановить маршрут. Статическая L сохраняет возможность ничего не читать при правке. Результат первого чтения после промаха вновь может кэшироваться всеми реализациями. Отдельное реальное закрытие и повторное открытие SQLite-соединений на этапе проверки контролирует восстановление всех 128 выходов вне таймера.

Три алгоритма получают одни и те же доступные при записях данные. Прогноз H и операции записи не видят будущего количества запросов. Кратность R использует внешний драйвер только после записи. Основные сравнения — тепловые отношения H/A и H/L по времени от исходного просмотра до последнего зарегистрированного обращения, вторичные — сценарий промахов, время после записи исходного снимка, сумма циклов и SQL-операции. Используем локальный диск D, WAL и synchronous=NORMAL, один поток, разогрев и шесть сбалансированных перестановок планов для каждого окна. Парный bootstrap по пяти репозиториям и 25 задачам, 10 000 повторов, seed=380451. Результат для одного пути в одном обновлении не переносится автоматически на пропускную способность многофайлового сервиса. Собственные нулевые и отрицательные эффекты сохраняем.
