# Цену повторного чтения можно оценить до сжатия памяти

Внутренний протокол от 16 ноября 2026 года, до исполнения симуляции. Версия механизма 1. Время локальной фиксации и SHA-256 протокола, генератора, стратегий и расчётов находятся в frozen.json. Эта отметка документирует порядок работы и не является внешней регистрацией.

## Вопрос и единица анализа

Во время сжатия агент видит снимок из 32 неизменных значений и прошлые запросы. Какая политика лучше выбирает восемь записей при последующих составных запросах, если один вызов источника способен вернуть несколько полей? Предположение о преимуществе относится к числу необходимых чтений для полного ответа. Оно может исчезнуть при независимом чтении полей или когда популярные источники лучше хранить целиком. Более низкая средняя цена не обязывает долю ответов за два чтения расти.

Единица воспроизведения и статистического анализа — мир. 64 независимых генератора миров, семена от 916001 до 916064 включительно, общий вес каждого мира одинаков. Мир задаёт веса скрытого ранга (зипфовский показатель в интервале 0,7–1,5), перестановки физического источника для четырёх ролей, вероятности ролей и таблицу из 32 значений unsigned int32. Роли можно понимать как четыре разных атрибута задания. Они запрашиваются без повторений. Число ролей 2, 3 или 4 имеет вероятности 0,33, 0,45 и 0,22.

На уровне запроса с вероятностью ρ из множества {0, 0,5, 1} роли получают общий скрытый ранг, иначе ранги выбираются независимо. Перестановка для каждой роли переводит ранг в один из восьми источников. Роль имеет одинаковое маргинальное распределение источников при всех ρ. В одном запросе общий ранг иногда ведёт в разные физические источники. Во всех ρ одного мира используются общие случайные числа для сравнимых заданий. Описательно измерим долю пар полей, действительно оказавшихся в одном источнике.

## Наблюдение, компактирование и проверка

Семя каждого потока равно 100 × семя мира + номер этапа. Этап 0 задаёт мир, 1 — 96 запросов fit, 2 — 48 validation, 3 — 128 test. Последние 128 запросов генерируются независимо от первых двух потоков при фиксированных параметрах мира. Алгоритмы не получают скрытых рангов, истинных весов, будущих запросов или тестового ранжирования. Они знают идентификаторы ранее запрошенных полей и открытую карту «поле → источник». В момент сжатия доступен общий полный снимок, включая поля, которые ни разу не запросили. Его приобретение стоит восемь вызовов источника или 32 одиночных вызова (32 возвращённых значения в обоих случаях). На этапе проверки сохранённый снимок не обновляется, кэш между тестовыми запросами не пополняется, значения во времени не меняются.

Во всех вариантах хранится ровно 8 различных записей. В эталонной двоичной сериализации запись занимает один байт ключа и четыре байта значения, итого 40 байт, 8 первоначальных записей и 0 новых записей за 128 проверочных заданий. Логические байты не измеряют объем Python-процесса или токены LLM. История ключей (144 маски по 32 бита дают 576 байт без учёта порядка ролей внутри запроса), RAM обучения, пространство DP, исходный снимок, обучающий журнал, внешний источник и временный рабочий ответ не оплачиваются этим лимитом. Сам снимок как список пар занимает 160 байт. Архив диагностики не доступен политикам во время теста. При оценке занимаемой памяти результат касается сохраняемых между запросами фактов. Порядок ролей для recent доступен в исходном журнале.

Сравним два контракта инструмента на идентичных заданиях. В блочном режиме вызов возвращает все четыре поля источника. При равных чтениях сначала читается источник с большим числом недостающих запрошенных полей, затем источник с меньшим номером. В поштучном режиме вызов возвращает одно поле, сначала с меньшим номером. Доступны не более двух чтений на запрос. После двух чтений вычисляется точное равенство всех запрошенных значений данным снимка. Если часть значений потеряна, ответ неверен. Также вычисляется точное общее число вызовов, необходимых для полного ответа из этого кэша без лимита. Это функция наблюдаемого запроса и состава кэша. Симулятор не исполняет сверхлимитные вызовы. В первичном показателе учитывается требуемая работа, в дополнительном — реально выполненная.

## Политики

1. **joint**. По наблюдавшимся задачам считаем частоты подмножеств ролей по каждому физическому источнику. Сохранение подмаски предотвращает одно блочное чтение, когда она целиком включает локальную потребность запроса. По каждому источнику перебираем 16 вариантов подмаски. Динамическое программирование распределяет восемь слотов между источниками, максимизируя предотвращённые чтения на обучающей истории. При поштучном чтении выгода подмаски равна сумме частот её полей. DP исполняется и в этом случае, и совпадение масок joint и marginal проверяется утверждением. Таблица содержит до девяти состояний по числу использованных слотов для каждого префикса источников. Тестовой оптимизации нет.
2. **marginal**. Восемь наиболее частых индивидуальных полей. Этот метод точно оптимизирует эмпирическую цену при поштучном чтении.
3. **whole_block**. Два полных источника, обеспечивающие наибольшую эмпирическую экономию, с учётом выбранного контракта. Это оптимальный обученный кэш среди политик, хранящих источники целиком.
4. **recent**. Последние восемь различных ключей по истории запросов.
5. **validation_choice**. Выбирает один из marginal, whole_block и recent по минимальной цене полного ответа на последовательности validation, предсказывая на основе fit. При равенстве действует указанный порядок. Выбранный метод и все другие методы заново компилируются по fit + validation. Это основной соперник, доступный практически. Для каждой фиксированной политики tie-break по меньшему ID. При равных суммарных выгодах DP берёт наименьшую целую битовую маску.

## Оценки и неопределённость

Основной контраст — сэкономленные joint необходимые чтения на запрос против validation_choice в блочном режиме, при равных весах трёх ρ. На каждом семени вычисляем разность средних на одних и тех же запросах. Положительная разность означает снижение цены. Для доли заданий, полностью выполненных за два чтения, положительная разность означает повышение доли. Публикуем среднюю парную разность и двусторонний 95% t-интервал по 64 мирам. Проверка чувствительности для первичного исхода — перцентильный bootstrap целых миров, 10 000 выборок, seed 833171. Публикуем число положительных пар, равенств, медиану и границы разброса. Наблюдения не исключаются, досрочной остановки нет. Номинальные интервалы характеризуют только случайность заданного генератора.

Вторично — сравнения со всеми соперниками отдельно, по каждому ρ и контракту, включая число реальных чтений, число перенесённых значений и долю верных ответов при лимите. Градиент эффекта между ρ=1 и ρ=0 оценивается внутри мира. Для блочной цены вычисляем также одновременные интервалы по Бонферрони для 16 сочетаний (четыре соперника × три ρ и их среднее). «Сильнейший» фиксируется описательно по минимальной тестовой средней цене. Эту оценку не передаём алгоритму. Остальные вторичные интервалы точечные. По умолчанию не делаем выводов на основе p-value.

Анализ ошибки берёт первое по порядку семя, условие и задание с каждым из трёх исходов блочного сравнения с validation_choice: отвечает только joint, только соперник или никто. В журнале останутся идентификаторы, маски и вызовы для обоих вариантов.

Это опыт на механизме выбора хранимых фактов. Нет языковой модели, динамического репозитория, естественного языка, ошибок распознавания схемы, времени отклика или наблюдений расходов реального API. Все вычисления локальные. Границы применимости результаты будут описывать наряду со случаями выигрыша.
