# Досрочное завершение чтения точной одноякорной выдачи

Задача — сохранить точный порядок восьми соседних файлов при обычном числе голосов 1/(m−1) из максимум восьми сохранённых событий одного известного файла. Оцениваем **все** ранее зафиксированные запросы новой панели R57/replication и длинной панели R56/shared_evidence. Параметры этого контроля фиксируем до подсчёта новых показателей; сами панели, выбор fill6 и их Recall@8 изучались ранее. В R57 используем SHA mod m на всех допустимых запросах второй половины; R56 long наследует SHA mod 11 и выбор (SHA div 11) mod m. Берём новейшие события с m≤6, затем до восьми дополняем новейшими свыше порога. Составы читаем в порядке возрастания m (убывания веса), при ничьей начиная с новейшего. Все варианты обязаны точно воспроизвести прежний top‑8; дополнительно сверяем оценки всех победителей с прямым суммированием рациональных чисел.

После каждого дочитанного события каждый файл имеет нижний балл по уже известным составам и верхний, добавляющий веса тех оставшихся событий, которым он может принадлежать. Все ранее встреченные кандидаты, в том числе нулевые, разрешение ничьих исходное. Сертификат упорядоченных ID сравнивает нижний ключ каждого победителя с верхними ключами всех оставшихся. Для точных оценок дополнительно требуем нулевую ширину интервалов победителей. Состояние проверяем и до первого чтения. Без дополнительных метаданных неизвестный файл потенциально входит в любое оставшееся событие.

Варианты — обычное полное чтение одной пачкой; только известные размеры; отдельные Bloom-фильтры по 32 либо 64 бита на каждое выбранное событие; точные составы коротких эпизодов с тем же потолком служебных байтов 4 и 8 на событие. Bloom содержит всех участников, включая якорь, две позиции из фиксированного хеша ID; положительный ответ даёт лишь верхнюю границу. Для точного короткого состава в один из 4 или 8 байтов пишем длину или нулевой признак отсутствия, в остальные — весь delta-ULEB128 отсортированных ID, если он помещается. Передаваемая длина переменная. Встроенные составы дают точные вклады с начала запроса. Остальные читаются в прежнем порядке. Общие для политик данные селектора — ID эпизодов, их размеры и хронологический порядок, идентификаторы кандидатов, разрешение ничьих. Итоговый размер каждого закодированного состава, индивидуальные членства и будущие целевые пути селектору не раскрываются.

Каждый полный состав кодируем дельтами отсортированных ID в ULEB128, число путей уже известно. Для каждого независимо сохранённого запроса фиксируем байты метаданных, фактически дочитанные байты, количество обращений за составами, число случаев экономии, равенства и перерасхода к одной полной пачке. Дополнительно сравниваем вариант с явным условным протоколом запросов: одна байтовая команда на всю пачку (при наличии выбранных событий); при последовательном чтении — один байтовый индекс на каждый запрос к эпизоду. Это нижняя оценка расходов на команды; сеть и задержка СУБД не измеряются. Для режима «только ID» и «ID+баллы» сообщаем отдельно. Тестируем гипотезу о меньшем числе байтов за счёт ранней остановки после **полной оплаты выдачи метаданных**. Построение метаданных требует просмотра событий на записи, отдельно укажем расход на один физический эпизод и число обновлений. Публикуем отрицательные результаты и цены всех вариантов без выбора параметров по меткам.
