# Дополнительный дешёвый запрос только к последнему фильтру

После первичной оценки известно, что покупка Bloom-фильтров сразу для всех событий увеличила суммарный трафик. Проверяем простое условие выбора последнего фильтра до расчёта его показателей. Первую часть списка читаем одной пачкой. Рассматриваем Bloom-метаданные только самого последнего по прежнему порядку события. Если его размер m не больше ширины фильтра в байтах, читаем сразу все события одной пачкой. Иначе, когда после точного префикса ответ не гарантирован общим ограничением, читаем только один фильтр за 4 или 8 байт. При отсутствии сертификата дочитываем последний состав. Для выдачи IDs и для IDs с точными баллами отдельно считаем запросы: одна пачка за непустым префиксом, один запрос за фильтром и один за последним составом при необходимости. В выборке без событий — ноль запросов. Одна операция запроса условно стоит один байт; сеть не моделируется. Вторичная схема использует прежний сохранённый фильтр каждого физического события, так что разовая стоимость построения по всем физическим событиям не меняется. Дополнительно для понимания предела считаем с подсмотренной разметкой **оракульную** маршрутизацию, покупающую один последний фильтр, только если точно известно, что она сэкономит трафик; это исключительно верхняя оценка достижимой экономии в данной двухходовой схеме.
