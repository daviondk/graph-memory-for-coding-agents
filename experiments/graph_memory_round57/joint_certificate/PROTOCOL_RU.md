# Можно ли восстановить точный результат совместного свидетельства по агрегатам

Воспроизводим все запросы уже оценённой политики joint из R57/seed_pair, с теми же SHA и объединением до восьми ранее выбранных событий каждого из двух якорей A и B. Целевой результат — точный упорядоченный top‑8 идентификаторов и численные баллы p+q у этих файлов. Новая метрика — достаточность данных для точного ответа и цена при необходимости дочитать архив. Это ретроспективная проверка на прежних панелях; Recall@8 фиксирован требованиями точного восстановления.

**Контракт.** На запросе даны по каждой размерной страте m числа выбранных эпизодов только A, только B и обоих (A₀,B₀,J), а также разреженные счётчики uₓ и vₓ — сколько эпизодов страты с x содержат соответствующий якорь. Включаем каталог ID совместных событий по страте для навигации в архиве. Даны исторические частоты путей и обычный порядок ничьих. Дополнительное поле tₓ — число эпизодов, содержащих оба якоря и x; его нет в этих сводках. Предполагается, что агрегаты доступны именно для объединения отобранных событий. Ни принадлежность путей отдельному эпизоду, ни будущая разметка для сертификации недоступны.

**Границы.** Для каждой страты начинаем с max(0,uₓ−A₀,vₓ−B₀) ≤ tₓ ≤ min(uₓ,vₓ,J) и с tₓ=0 при m=2. Используем закон Σₓtₓ=J(m−2), исключив оба якоря. Сужаем границы через суммы верхних и нижних пределов остальных x до неподвижной точки. Попарная часть p известна точно, q ограничена суммой взвешенных нижних и верхних пределов tₓ/(m−2). Ранжирование с исходными ничьими. Для упорядоченного top‑8 сравниваем нижний ключ каждого победителя с верхними ключами последующих конкурентов. Для сертификата численных баллов дополнительно требуем совпадения их нижней и верхней границы. Это достаточный критерий; неудача вычисления сертификата сама по себе не доказывает, что точный ответ информационно невозможен.

Пока сертификат не получен, выбираем размерную страту с ненулевой шириной у претендента на top‑8. Претенденты — первые восемь по нижним ключам и прочие, верхний ключ которых может превысить нижний ключ на восьмом месте. Предпочитаем наибольшее суммарное уменьшение верхней оценки неопределённости этих претендентов в пересчёте на читаемое членство. Раскрываем составы **лишь совместных** событий этой страты и решаем задачу снова. Выбор страты не использует скрытые составы. Отдельно фиксируем, сколько чтений нужно было для определения порядка и для определения порядка с баллами. Все прогнозы сверяем с исходными top‑8 и независимым прямым суммированием p+q с рациональными числами на исходных событиях.

**Стоимость.** Публикуем число запрошенных страт, прочитанные события/составы против чтения всех совместных событий с m>2 и против всего объединения. Считаем также клетки (стратные заголовки и ненулевые u/v), фактически сериализуем и прочитываем компактный пакет сводок: 1 байт на число страт; 8 байт заголовка на страту (m,A₀,B₀,J uint8; число кандидатов uint32); 6 байт на тройку (ID uint32,u uint8,v uint8); 4 байта на указатель на каждый совместный эпизод при m>2. Сравниваем объём пакет+дочитывание и полное чтение составов (4 байта на ID). Метаданные, общие обеим схемам, исключаем. Отдельно считаем стоимость построения пакета с нуля по тем же входным событиям. Не предполагаем его бесплатной предматериализации под каждый запрос. Не делаем вывода о latency по логическим счётчикам.
