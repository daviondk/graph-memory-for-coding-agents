# Когда маргинальных счётчиков достаточно для точного top‑8 по совместным эпизодам

На **1 153** запросах с двумя известными файлами условные попарные счётчики позволили восстановить **1 120 точных ранжирований с численными баллами без обращения к архиву** (97,1%). Это включает 639 из 672 запросов, у которых совместные изменения действительно давали голос третьему файлу. Для 33 остальных запросов понадобилось прочитать **43 из 1 676** эпизодов с обоими якорями и хотя бы одним партнёром. На всех запросах итог совпал с прямым вычислением по полным событиям. Однако передача самих счётчиков оказалась дорогой: 535 143 байта вместе с дочитыванием против 392 416 байт для составов всех исходных событий. Результат важен, когда счётчики уже доступны рядом с механизмом поиска и нужно решить, обращаться ли за исходными эпизодами. Экономии общего трафика в наших реализациях не получилось. [Протокол](PROTOCOL_RU.md) · [Агрегаты и результаты по проектам](results.json).

**Что задано до чтения архива.** Для каждой размерной группы событий m известны числа отобранных изменений только первого якоря A, только второго B и обоих — Nₐ, Nᵦ, J. Для каждого кандидата x есть два счётчика u и v его совместного появления с A и B. Все агрегаты относятся к тому же ограниченному набору событий, что использует исходный метод. Сводка по всей репозиторной истории не обязательно даст такие же числа. Предполагаются известными время принятия решения, список выбранных событий, недавние частоты и ID кандидатов. Номера и состав событий специально привязаны к этому запросу. [Исходные ранжирования и нормировка p+q](../seed_pair/joint.py).

Число t совместных прошлых появлений A, B и x в страте ограничено снизу величиной max(0,u−Nₐ,v−Nᵦ), сверху — min(u,v,J). При m=2 третьего участника нет. Каждый совместный эпизод даёт m−2 таких участников, поэтому сумма t по всем кандидатам строго равна J(m−2). Например, если все возможные голоса кроме одного кандидата уже учтены, остаток задаёт точное число его свидетельств. Из этих границ получаем интервал для q(x), суммируя с весом 1/(m−2). Попарная нормированная часть p(x) известна точно. Нижний ключ победителя должен быть больше верхнего ключа каждого кандидата, идущего за ним; ничьи по основному баллу разрешаются исходной попарной суммой, недавней частотой и ID. Для точного балла дополнительно требуется нулевая ширина его интервала. Это достаточные условия, их полнота в общем случае не установлена.

Если границы пересекаются, алгоритм рассматривает только страты с неопределённостью у кандидатов, ещё способных войти в top‑8 или поменять порядок лидеров. Выбирает страту по ширине их интервалов на читаемое членство, декодирует совместные эпизоды выбранного размера и повторяет проверку. На этой выборке для каждого из 33 запросов с уточнением хватило одной страты. [Реализация сертификата, сериализация и доступ к архиву](certificate.py).

Уточнение по сумме сделало точными численные баллы ещё в **60 запросах**. Равенство двух показателей после уточнения — эмпирическое свойство панели. В исчерпывающей проверке малых историй порядок и точные значения ведут себя по-разному.

Четыре байта на ID пути, шесть байт на разреженную клетку (ID, u, v). Стратные заголовки и каталог указателей на совместные эпизоды входят в фактически сериализованный пакет. Для сведения, пересылка всех совместных составов при уже имеющихся попарных счётчиках заняла бы 118 512 байт против 652 байт выборочного уточнения. Если счётчики строить заново при каждом запросе, построение потребовало прохода через все 98 104 исходных членства и 110 542 обновлений попарных счётчиков, с учётом того что кандидат в совместном эпизоде обновляет оба. Полученный по запросу пакет вместе с уточнением меньше прямого чтения только в 111 из 1 153 случаев. Хранение общих счётчиков для всех возможных пар и реальная задержка БД в этом эксперименте не измерялись.

После первичной проверки сделали дополнительный контроль формата: сортировка и дельта-кодирование ID, ULEB128 с компактной парой счётчиков для сводок и такое же дельта-кодирование составов для архива. В порядке «прямое чтение / пакет с уточнением» получилось 60 144 / 106 350 байт на новых проектах, 42 157 / 69 452 на репликации, 11 491 / 19 382 на длинных. После одинакового zlib для каждого запроса — 52 213 / 69 881, 30 174 / 39 913 и 10 911 / 13 886. Использованы сравнимые кодеки с проверкой декодирования. Оптимальность форматов не утверждается. [Условия проверки кодека](CODEC_RU.md) · [Результаты](codec-results.json).

### Проверка правильности

Для каждого запроса первичный алгоритм получил только байты пакета, общие ключи ничьих и проверяемую операцию чтения по ID события. Полный проход независимо вычислил исходные рациональные p и q, отсортировал все доступные кандидаты и сравнил их с сертификатом. Все упорядоченные ID и все дробные баллы совпали. Также совпали ID с ранее сохранённым top‑8 каждого запроса seed_pair. В протоколе каждого запроса содержатся SHA текущей ревизии, SHA‑256 сводки, ID и точные числители/знаменатели, размеры и SHA фактически дочитанных событий. [Сценарий и независимое вычисление](run.py) · [Журнал запросов](queries.json.gz).

Дополнительно перебраны 4 750 историй фиксированных малых типов с пятью возможными третьими участниками и расширенным пулом кандидатов. Истории распались на 3 265 групп с побайтно одинаковой сводкой. У 785 таких групп при одинаковой сводке менялись точные результаты, у 665 менялся даже порядок файлов. Сертификат не подтвердил ни одного неоднозначного ответа. В этом ограниченном переборе он распознал все 2 600 однозначных порядков и все 2 480 однозначных ответов с баллами. Полная проверка для конкретных размеров дополняет общие достаточные условия. [Код перебора](check_small.py) · [Итог](exhaustive-small.json).

Воспроизведение: `python -B run.py --verify`, `python -B check_small.py` и `python -B codec.py`. Достаточны Python и сохранённые проекции соседних каталогов. Для статьи вывод касается точного порядка доступа к архиву при заранее доступных условных агрегатах, а также стоимости, которую добавляет попытка передавать такие агрегаты для каждого запроса.
