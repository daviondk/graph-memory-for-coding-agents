
# Уточнение представления списков при запечатывании

В первых двух полностью записанных блоках первичного эксперимента с масками появился сильный простой контроль. На длинной панели одна строка SQLite с упакованными ID на файл заняла 323 584 байта, индекс запечатанных масок — 479 232 байта. Это мотивирует разведочное продолжение после просмотра этой части исходов. Исходный протокол, счётчики и все пять его повторов остаются отдельным сравнением.

Проверяем, каким станет компромисс, если сохранить первоначальную границу запечатывания 64 события, но заменить маски упакованными адресами. Сравниваем в новых случайных блоках: (1) непосредственный полный список на файл, (2) запечатанные маски, (3) **запечатанный список на файл** с добавлением всех адресов этого блока одним SQL append, (4) **запечатанный список с полосой 1 024 событий**: в ключе путь и номер полосы, в значении переменно кодированные смещения событий в полосе. У последней схемы для одного файла в строке до 1 024 указателей, а число append для неё не превосходит 16 даже у самого частого файла. Простая модель (3) не имеет верхней границы размера строки в длинной истории. Все четыре режима используют один и тот же формат основного журнала и явный незапечатанный хвост там, где индекс отложен. Отложенные варианты полностью записывают исходный коммит до подтверждения транзакции; за пределами хвоста хранят все ID для аудита.

Пять новых блоков режимов, фиксированный seed 57062. Те же 880+196 запросов, те же точные результаты и режим WAL. Первичный технический исход уточнения — размер standalone по сравнению с полным списком. Вывод о практической выгоде сопровождаем логическими записями и полной/хвостовой задержкой. Тот же тест аварии при запечатывании, восстановление до 63 событий. Это разведочное изменение представления после сравнения с сильным контролем, а не воспроизведение первичной гипотезы.
