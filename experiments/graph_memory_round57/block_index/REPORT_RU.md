
# Точный индекс истории Git с отложенной записью

При поиске сопутствующего файла по истории Git все проверенные планы выдают один и тот же упорядоченный список и точные числа совместных изменений. Практический результат — сильный простой контроль: на трёх длинных историях хранение одного упакованного списка номеров событий на файл заняло **323 584 байта**, исходный двухуровневый индекс R56 — **512 000 байт**. Двухуровневый индекс быстрее отвечал и передавал меньше данных. На шести более коротких историях новый план с отложенной записью упакованных списков занял **118 784 байта** против **122 880** у непосредственной записи списка. На длинных историях размеры этих двух списочных планов совпали. Поэтому полезность хранения последних событий зависит от того, что дороже на конкретной нагрузке: чтение, восстановление или дисковое пространство. [Первичный протокол](PROTOCOL_RU.md) · [Исходные измерения](runs.json.gz)

## Что хранит база

Каждый принятый многопутевой коммит имеет номер, SHA-1 и состав в исходном порядке. Журнал сохраняет их до подтверждения отдельной транзакции в SQLite WAL с synchronous=FULL. Во всех вариантах бюджет чтения составляет восемь путей. Частоты для разрешения ничьих, набор известных путей и один открытый путь заданы одинаково. Вне таймера битовый оракул восстанавливает точные ответы по всему наблюдаемому прошлому. Для новой записи не нужно предварительно индексировать дерево исходников. Полная история продолжает занимать место на диске.

В основном эксперименте граница блока равна 64 многопутевым событиям. При немедленной записи у каждого файла и блока в таблице лежит целая 64-битная маска. При отложенной записи до границы события уже сохранены в долговременном журнале, а их обратные ссылки находятся в RAM. При заполнении блока каждая встречавшаяся ссылка на файл представляется одной строкой с маской, атомарно с последним событием. При перезапуске число записанных событий определяет границу последнего завершённого блока, поэтому нужно прочесть максимум 63 состава для каждого репозитория. Эталонный ответ восстанавливается как сумма частот на непересекающихся запечатанном префиксе и незапечатанном хвосте. Изменённые пути могут быть редкими или впервые появиться уже после перезапуска. На запрос план всё же проверяет индекс файла даже при отсутствии архивных попаданий. Отдельный каталог файлов с холодной историей отсутствует. [Реализация](block_store.py)

Сопоставление с R56 включает смену кодека. В исходной схеме ревизия занимает 40 символов, а один ID — четыре байта. В новых схемах SHA занимает 20 байт, ID имеют переменную длину. Честный контроль эффекта обратного индекса — полный SQL JOIN при **том же новом кодеке**. Ранжированию не доступны SHA будущих событий, метки эталонных путей или будущие версии файла.

Блочная упаковка адресов имеет промышленные аналоги. Например, Lucene 10.1 разбивает длинные обратные списки по терму на блоки из 128 целых и кодирует остаток переменной длиной. У нас обратный ключ — путь, а общая граница отсчитывается по хронологии всех наблюдений, поэтому можно вывести состояние незапечатанного хвоста из журнала после аварии. Прямой прогон Lucene на этой рабочей нагрузке не проводился. Семантика dbstat важна для измерений: свободные страницы SQLite учитываются отдельно от внутреннего неиспользованного пространства уже выделенных страниц дерева. [Первичная документация Lucene](https://lucene.apache.org/core/10_1_0/core/org/apache/lucene/codecs/lucene101/Lucene101PostingsFormat.html) · [Описание dbstat SQLite](https://www.sqlite.org/dbstat.html)

При равных кодеке и ширине отложенные маски уменьшают суммарный размер на B на 12 288 байт, но увеличивают его на длинной панели на 4 096 байт. Число изменений строк SQLite (все таблицы, включая источник) уменьшается с 5 615 до 2 548 и с 32 122 до 19 075. Перезапуск на длинной панели требует 74 события суммарно из трёх независимых хвостов, 405 байт их полезной нагрузки и 4,88 мс. Для R56 с общим горячим уровнем — 3 920 строк, 87 780 байт полезной нагрузки и 15,28 мс. При этом R56 читает из SQLite 27 716 байт составов за все 196 решений, отложенные маски — 132 211 байт и дополнительно дескрипторы масок. На длинной панели p99 записи возрастает с 693 мкс при немедленной маске до 803 мкс при отложенной; для записей на границе блока p99 равен 613 и 1 834 мкс. Снижение числа изменений строк не гарантирует снижение этой задержки.

## Замена масок списками

После первых двух блоков основной серии в отдельном протоколе зафиксировали переход на упакованные адреса событий. Запечатывание добавляет последовательность адресов файла за блок одним SQL append. Альтернативная реализация хранит отдельные строки в полосах по 1 024 события, что ограничивает каждую строку 1 024 адресами и 16 обновлениями. На длинной панели это увеличило размер до 339 968 байт относительно 323 584 для единого списка. [Регистрация уточнения](EXTENSION_RU.md) · [Результаты](extra-results.json) · [Поштучные задержки](extra-runs.json.gz)

На B отложенный список с одной строкой на файл сократил суммарное чтение с 53,51 до 44,85 мс и смешанную медиану с 484,59 до 473,23 мс. Знак смешанного различия сохранился во всех пяти блоках на этой машине. На длинной панели смешанное время составило 2 404,53 мс при немедленной и 2 406,92 мс при отложенной записи. Знак разности менялся между повторами. Количество модифицированных строк сократилось на 40,6%, а p99 записи вырос с 626 до 770 мкс. Измерение после перезапуска исключает ленивое восстановление пользовательского кеша R56 own при последующих операциях. Для отложенного полного списка хвост восстановлен целиком к окончанию измерения.

## Блочное хранение самих исходных событий

В разведочном сравнении 2×2 меняли независимо хранение исходных событий и момент записи обратного списка. Первый вариант хранит каждое событие строкой. Во втором до 64 событий лежат в одной строке с раздельными областями SHA, концевых смещений и данных. Последняя строка растёт после каждого коммита, запрос получает широкие области смещений и данных и выбирает нужные события. Две области для одного возвращённого блока считаются двумя BLOB. [Отдельный протокол 2×2](SLAB_RU.md) · [Поштучные замеры](slab-runs.json.gz) · [Агрегаты](slab-results.json) · [Код](slab_store.py)

На длинной панели при немедленном обратном списке новый формат увеличил footprint с 323 584 до 356 352 байт и BLOB-трафик источника с 135 845 до 1 585 423 байт. Количество BLOB при этом уменьшилось с 7 034 до 4 010, занимающих 2 005 строк. На B объём переданных данных вырос с 58 326 до 697 459 байт. Широкий физический блок позволяет вернуть много неиспользованных участников. Эти цифры учитывают действительно переданные из SQLite данные обоих полей, исключая отдельно опубликованный трафик обратного списка. Они не являются показаниями блочного устройства.

В следующем протоколе проверили однократную материализацию неизменяемых групп. Незавершённые события остаются долговременными строками. При заполнении группа атомарно переезжает в две области — SHA фиксированного размера и последовательность составов с префиксами длины. Для каждой ширины сравнили исходный поток байтов с zlib level 1, применяемым при сокращении представления. Во всех условиях тот же сильный непосредственный обратный список. На B та же ширина увеличила базу на 24 576 байт, или 20%. У сжатых и несжатых восьмёрок суммарные размеры совпали из-за размещения в SQLite-страницах. Обнаруженный эффект ширины требует проверки на новых проектах с иными размерами событий и долей исторических запросов.

## Что меняет реальное уплотнение страниц

Независимый диагностический прогон заново построил 72 базы и подтвердил все опубликованные размеры без уплотнения. Затем для каждой закрытой базы измерили таблицы SQLite dbstat и выполнили VACUUM с checkpoint. На B у непосредственного списка была одна свободная 4-КиБ страница. После уплотнения отложенный и непосредственный списки занимают **ровно 118 784 байта каждый**. Разница в цифрах при обычном закрытии характеризует размещение страниц, а не устойчивое сокращение минимального физического размера этих двух форматов. На длинной панели при одинаковом полном списке индекса восемь неизменяемых событий на группу дают **299 008** байт после уплотнения против **319 488** у событий по одному в строке. Выигрыш по размеру 6,41% сохранился. Для растущего группового блока с полным списком — 352 256 байт даже после уплотнения. До него dbstat насчитал 112 547 неиспользованных байт внутри выделенных страниц против 56 129 для плоского источника. Времена отдельных VACUUM опубликованы отдельно от операционного времени. [Все страницы, полезная нагрузка и размеры для 72 баз](vacuum.json) · [Диагностика](page_cost.py)

## Независимая проверка и воспроизведение

В четырёх сериях 900 запусков на свежих временных SQLite-базах и 107 600 сравнений ответов с одним и тем же оракулом по девяти закреплённым хронологиям. Полные ID и целочисленные баллы совпали. Генератор и SHA-256 последовательностей входных запросов общие с R56. Повторные измерения на тех же событиях служат контролем времени и не образуют 107 600 независимых задач. Ограничения — локальная машина, одна установка SQLite, один писатель, 9 исходных проектов. Холодный уровень обозначает логически вытесненные события; перезапуски проходят при тёплом файловом кеше ОС. Стоимость модели-решателя здесь не измерена.

У всех 12 новых физических форматов проверили разрыв процесса при исполнении SQL-триггера ровно на границе запечатывания. После повторного открытия незавершённая операция отсутствовала, повторное добавление прошло, проверка SQLite integrity_check и 62 независимых рейтинга после сбоя совпали. Для каждого формата отдельно проверили 593 рейтинга в синтетическом SQL-оракуле, пять полных снимков при откате, 196 идемпотентных повторов, 392 конфликта и 196 пропусков номеров. После перезапуска посредине реальной истории проверено ещё 688 ответов из 1 076 по каждому формату, включая появление новых путей. Сохранённые SHA и исходный порядок участников каждого из 6 049 реальных событий сверены непосредственно через читатель журнала. [Проверки индекса](correctness.json) · [Проверки источника](source-correctness.json) · [Воспроизводимый сценарий](correctness.py)

Для воспроизведения нужен полный checkout и Python 3.10+ со стандартной библиотекой. Из этой папки для сверки опубликованных журналов запустите последовательно:

```sh
python -B bench.py --verify
python -B extension.py --verify
python -B slab_bench.py --verify
python -B frame_bench.py --verify
python -B correctness.py --verify
python -B correctness.py --storage --verify
python -B page_cost.py --verify
```

Для нового замера создайте отдельную копию каталога с теми же соседними источниками, освободите в копии файлы результатов соответствующей серии и запустите её без флага проверки. Все времена отдельных операций уже сохранены в сжатых JSON. Диагностика размещения страниц в отдельном прогоне использует `python -B page_cost.py --stats-python PATH`, где PATH — Python с поддержкой SQLite dbstat. Статистический процесс открывает уже закрытый checkpointed-файл в режиме чтения, а VACUUM выполняет тот же интерпретатор, которым сделан основной замер.
