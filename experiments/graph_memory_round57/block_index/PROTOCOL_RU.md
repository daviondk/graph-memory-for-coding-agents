
# До измерений. Индекс по запечатанным блокам событий

Проверяем точную долговременную выдачу для известного файла по всем наблюдаемым многопутевым событиям. Идея состоит в отсрочке материализации обратного индекса до заполнения блока из **64 событий**. Каждый новый SHA и полный состав записывается в основной журнал в отдельной транзакции SQLite WAL synchronous=FULL. До запечатывания блок доступен через незавершённый хвост в оперативной памяти. На границе одним атомарным завершением события строятся строки только для встреченных файлов, каждая с номером блока и 64-битной маской его событий. После аварийного перезапуска число событий журнала однозначно задаёт границу, поэтому читаются лишь последние 0–63 события. Справочник файлов с холодными строками полностью устраняется. Путь никогда не нужно включать в оперативную память для всех прошлых коммитов. Оцениваем эту конкретную реализацию. Индексация по блокам, битовые маски и отсроченная материализация имеют известные аналоги, а научная гипотеза касается точки компромисса на журнале агентской памяти.

**Основная пара.** Сравнение отложенного запечатывания с немедленными масками при том же размере блока, том же общем кодеке, той же базе свежего состояния и тех же результатах. Размер транзакции и форма индекса в опубликованном прошлом совпадают. Незавершённый хвост может дать выигрыш на чтении самых недавних событий и в числе записей индексных строк. На границе возможен рост задержки отдельной записи. Дополнительные сильные сопоставления — упакованный неограниченный список ID на файл, полный компактный парный индекс (файл,событие) с SQL JOIN, неизменённые R56 full, own и split. У R56 исходный формат SHA-текста и uint32. В компактных вариантах все SHA храним 20 байтами и кодируем идентификаторы путей переменной длиной в исходном порядке. Эффект кодека показываем отдельно через полный компактный JOIN.

**Нагрузка.** Все 880 запросов панели B и 196 длинной панели, девять историй. Публичный генератор R56 подаёт те же хронологические запросы, события, частоты за 32 предыдущих коммита и порядок разрешения ничьих. Сравниваем восемь ID и соответствующие баллы с независимым битовым оракулом перед записью будущего события. Снимки на отдельных файлах БД. В пределах каждого проекта и повтора случайно переставляем семь стратегий фиксированным seed 57061. Пять полных блоков повторов при одном чтении на наблюдаемом решении. Все методы получают одинаковые запросы на одном компьютере. Времена описательные. Не считаем повторы независимыми репозиториями. Основной показатель работы — суммарное время записи плюс чтения после создания схемы до контрольной точки, медиана пяти сумм по проектам. По отдельности показываем холодный логический и публичный трафик (из SQLite в ранкер), число запрошенных SQL строк/вызовов, байты standalone DB после checkpoint/TRUNCATE, точное чтение при перезапуске, задержки записи по событиям (p50, p95, p99 и на границе), дополнительные ресурсы RAM, число манипуляций индекса. Анализ размера не смешиваем с изменением кодека и не приравниваем трафик приложения к физическому I/O.

**Проверки.** Независимое совпадение ранжирований после обновления, в том числе после перезапуска до/на/после запечатывания, повтор SHA/состава, коллизия, пропуск ID, исключение до commit; идентичность известных и новых после восстановления файлов. Все контрольные базы создаются локально на D и удаляются после штатного закрытия. По возможности дополнительно проверяем сбой процесса с незавершённой транзакцией в отдельном процессе. Закреплённая область — один писатель, Git SHA-1, конечные файлы с историей как наблюдаемым состоянием; общий каталог путей и входные привязки одинаковы для всех читателей. Если упакованный полный индекс или R56 быстрее/меньше, оформляем это как результат.
