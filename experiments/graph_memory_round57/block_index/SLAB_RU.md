
# Проверка упаковки источника и индекса в факторной постановке

Предшествующие замеры показали, что отдельная SQLite-строка на файл с полным списком адресов компактнее индекса масок. Отложенная запись того же полного списка привела к совпадению физического размера двух баз на длинной панели. До запуска новых вариантов фиксируем факторный эксперимент 2×2. Фактор источника — по одной строке на событие либо по одной строке на 64 хронологических события. Фактор обратного индекса — немедленное добавление адресов в список файла либо отложенное запечатывание списков на границах 64. У всех одинаковы SHA, IDs путей, точность и момент подтверждения записи.

Новый физический формат разделяет один блок на три поля: последовательность SHA по 20 байт, таблицу конечных смещений полезных нагрузок (4 байта на событие), непрерывные байты идентификаторов участников. Даже незаполненный блок хранится в SQLite и расширяется внутри обычной FULL WAL-транзакции на каждом событии. SHA отделены от состава; чтение рангов не требует SHA. При решении запроса архивные ID группируются по блоку. SQLite отдаёт смещения и данные каждого нужного блока целиком, в том числе возможные посторонние события; далее выбираются точные участники. Учитываем все переданные байты обоих полей, выбранные байты и число пересланных BLOB, в дополнение к числу фактически затребованных событий. Разницу в фактической передаче используем для оценки дополнительных расходов чтения, даже если время улучшается. Режим запечатывания на холодном старте восстанавливает незавершённый блок, до 63 событий. У непосредственного индекса достаточно концевого номера и длины последнего блока. Для удалённого запроса, повтора или аварийного перезапуска сохраняется исходный SHA и упорядоченный состав события.

Первичный показатель этой дополнительной проверки — размер базы после штатного checkpoint/TRUNCATE у упакованного источника в паре с тем же способом записи обратного индекса на длинной панели. Докладываем все четыре условия на обеих панелях, суммарную задержку read+write, запросы/байты/BLOB, перезапуск и p99 записи. Пять блоков × девять проектов × четыре режима со случайным порядком seed 57063. Сопоставления по трём наборам заводим отдельно от предыдущих прогонов. Один писатель, тёплый файловый кэш, FULL WAL, один контрольный вывод в момент настоящего запроса, предварительные и подтверждённые данные R56. Нагрузка на переписывание последнего блока по мере заполнения и чрезмерное чтение целых блоков — основные конкурирующие объяснения. Если выигрыш по размеру слаб или отсутствует, покажем это вместе с расходами. Чтобы не смешивать возможности SQLite с представлением источника, сохраняется реализованный в прошлой серии сильный полный плоский список со строками событий.
