# Перенос правила выбора эпизодов на шесть новых репозиториев

На 932 запросах в шести новых проектах правило с приоритетом изменений до шести файлов прочитало **на 33,1% меньше данных** при том же числе событий, чем выбор последних восьми. Средний по проектам Recall@8 составил **58,72% против 58,39%**, разность **+0,33 п.п.** Парный 95% bootstrap-интервал по проектам от −0,57 до +1,43 п.п. включает ноль. Подтверждено снижение объёма чтения в этой панели. Данных недостаточно для вывода о преимуществе в полноте. [Зафиксированный до оценки протокол](PROTOCOL_RU.md) · [Все метрики](results.json).

**Постановка.** По одному файлу будущего коммита нужно найти до восьми других файлов, которые изменятся вместе с ним. Агент видит только предыдущую историю. Хранилище удерживает восемь последних ссылок на многофайловые события для каждого пути; событие доступно, пока его помнит хотя бы один участник. Контроль читает восемь последних событий якоря. Проверяемое правило сначала выбирает до восьми событий размером не более шести путей, начиная с новейших; остаток заполняет новейшими событиями большего размера. Обе схемы присваивают каждому партнёру голос 1/(m−1) за событие с m файлами. Этот вес происходит из взвешенной проекции двудольных графов, а пороги по размеру ранее проверялись в change recommendation. [Newman, 2001](https://public.websites.umich.edu/~mejn/papers/016132.pdf) · [Moonen и соавт., ASE 2016](https://www.cs.loyola.edu/~binkley/papers/ase16-mining-guidelines.pdf).

**Данные.** Для каждого проекта взяты последние 1 024 перехода Git по первому родителю либо все имеющиеся. На первой половине истории память заполнялась. Все коммиты второй половины с 2–64 изменёнными Python-путями вошли в оценку. Всего обработано 4 238 переходов, в том числе 496 слияний. 195 из 3 277 целевых путей впервые встретились в оцениваемом коммите и остались в знаменателе. Шесть имён заранее проверены по составам прошлых выборок R55–R56. Все отсечки, направление первичного сравнения, метрики и интервалы зафиксированы до оценки коммитом ceb87c37. Средние по всем запросам составили 62,58% против 61,76% (+0,82 п.п.), Hit@8 — 751/932 против 741/932. По Recall@8 у приоритета малых событий 44 выигрыша, 54 проигрыша и 834 равенства. Положительная средняя при большем числе проигрышей возможна, поскольку размер изменений и величина эффекта различаются между запросами. Из 932 запросов набор прочитанных событий изменился в 453; итоговый порядок файлов — в 442. Точный парный sign-flip по шести проектным разностям дал p=0,625. Большое число ничьих и всего два запроса в trove-classifiers ограничивают точность вывода.

**Цена чтения.** Основные политики декодировали одинаковые 5 953 события; суммарные объёмы составили 187 864 и 280 888 байт при четырёх байтах на ID участника. При одинаковом индивидуальном потолке байт у двух методов Recall@8 составил 58,72% и 57,87% (по проектам), Δ +0,85 п.п., 95% интервал [−0,81; +2,84], p=0,50. Из-за неделимости эпизодов базовый метод фактически потратил 181 288 байт и декодировал 4 847 событий. Первоначально приоритет малых всегда расходует не больше байт, поскольку заменяет только событие более шести файлов на событие с меньшим составом. Таким образом общий лимит ограничивает прежде всего базовый метод. Эти цифры учитывают прочитанный состав событий. Метаданные выбора, физические операции БД и генерация ответа LLM в них не входят.

**Воспроизводимость.** В комплект входят проекции только имён путей и ревизий. Временный Git-репозиторий занимал максимум 1 327 472 байта. Извлечение командой git log независимо сверено с рекурсивным сравнением необработанных деревьев Git, проверкой SHA объектов и первого родителя на всех 4 238 переходах. Отдельная реализация эталона пересобрала живые события из полной доступной истории и повторила ранжирование с точными дробями.
