# Когда память исходных событий полезнее графа попарных связей

В этой серии проверили две гипотезы о памяти кодового агента. Достаточно ли короткой локальной истории, чтобы выбрать следующий файл при известном первом пути? Если агент уже знает два файла, помогает ли информация о том, что они менялись **в одном и том же** коммите? Для хранения и чтения проверили отдельные точные SQLite-реализации. Для наблюдаемого поведения агента воспроизвели сессии двух исполнителей. [Предыдущий отчёт](../graph_memory_round56/REPORT_RU.md)

## Тот же файл БД, другой способ читать граф

В составном варианте полный упакованный список номеров событий каждого пути остаётся долговременным индексом. Оперативный читатель использует тело любой совместной правки, пока хотя бы один из её участников удерживает его в своём окне. Если данных не хватает, запрос дочитывает отсутствующие события. После перезапуска кеш может начать пустым без сканирования репозитория. Полная точная выдача сохраняется.

На 196 запросах при непрерывной работе три базы занимали суммарно **323 584 байта**. Между клиентом и SQLite передано 149 294 байта при обычном чтении, 123 058 при чтении собственных удержанных событий, 21 142 при совместном использовании и 91 732 у кеша готовых счётчиков по запрошенному файлу. В основной контролируемой паре одинаковы физические базы, состав слоёв в RAM и события записи. Медианное суммарное время чтения 38,36 и 28,50 мс; полное время записи и чтения — 2 412,05 и 2 399,50 мс. На 880 запросах другой панели расход уменьшился с 25 727 до 6 349 байт. При перезапуске на середине длинной истории общему варианту понадобилось уже 106 781 байт. В независимом контроле кеш результатов по запрошенному файлу без ограничения на число записей передал 91 732 байта в обоих режимах. При пустом кеше он оказался экономнее общего. Более крупная сохраняемая раскладка R56 восстановила свой горячий слой и обслужила чтения с меньшей задержкой. Байты здесь обозначают данные списков и тел, доставленные из SQLite в процесс, а не объём чтения с SSD. [Составное сравнение с учётом RAM, перезапуска и LRU](composed/REPORT_RU.md)

## Математическое различие и его цена для БД

В построенном семействе из 16 историй частоты всех 768 пар файлов одинаковы. При заданных двух исходных файлах в каждой истории требуется разный третий. При равновероятном выборе истории любой метод, знающий только эти попарные частоты, может покрыть восемью ответами не более половины исходов. Достаточно сохранить составы событий, чтобы восстановить все 4 096 заданий. Этот модельный пример устанавливает предел представления. В реальных правках сила такого эффекта зависит от распределения запросов. [Конструкция](seed_pair/ambiguity.py) · [Пройти два реальных и синтетический пример в браузере](seed_pair/demo.html)

На 1 153 двухъякорных запросах ограничили неизвестное число троек попарными счётчиками по размеру события и точным суммарным числом третьих участников. Если условные счётчики уже доступны, 1 120 выдач со всеми баллами определяются без архива. Для остальных потребовалось 43 из 1 676 совместных эпизодов. При полной доставке суммарный объём возрос с 392 416 до 535 143 байт. Поэтому для системы важны как число обращений к архиву, так и место построения и стоимость передачи сводок. В отдельном контроле коротких окон учтена даже цена маленьких членских фильтров. [Алгоритм и стоимость](joint_certificate/REPORT_RU.md) · [Раннее завершение чтения](read_stop/REPORT_RU.md)

**Физический размер базы.** Для длинной панели R56 точный полный упакованный инвертированный список на файл занял 323 584 байта против 512 000 у прежнего разделяемого хранилища. В первом блоковом сравнении чтение заняло 41,03 и 19,46 мс соответственно. В отдельном факторном эксперименте упаковка самих неизменяемых событий группами по восемь уменьшила 323 584 до 303 104 байт на длинных историях, но увеличила время чтения относительно соответствующего контроля с 41,44 до 50,16 мс. На коротких историях размер вырос на 20%. Полные истории, порядок участников, SHA и режим атомарной записи сверены. [900 прогонов, проверки перезапуска, VACUUM и стоимости](block_index/REPORT_RU.md)

Для статьи наиболее содержательное разделение проходит между достаточностью памяти для точного ответа, выигрышем на будущей задаче и ценой физической доставки сведений. На [двух действительных изменениях Dask и Xarray](seed_pair/REPORT_RU.md) посетитель может сменить правило, раскрыть исходные свидетельства и проверить достижимое число попаданий. Критерий успеха для следующей агентной проверки — выигрыш при одинаковой доступной информации и бюджете у независимого исполняемого решателя. В этой серии новый решатель не запускался. Данные относятся к воспроизведению действий, рекомендациям файлов и работе SQLite.
