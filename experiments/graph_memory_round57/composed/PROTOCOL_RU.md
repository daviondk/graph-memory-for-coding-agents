# Один долговременный индекс и разные способы чтения памяти

Сохраняем одну и ту же базу filelist: полный SHA-1, составы коммитов в исходном порядке, по одному упакованному списку IDs событий на путь. Все продолжающие работу процессы имеют доступ к тому же журналу. Работа одного писателя в SQLite WAL synchronous=FULL, отдельный commit для каждого наблюдаемого изменения.

**Первичная пара.** Сравним чтение всех событий якоря, ещё удерживаемых хотя бы одним участником, и его собственных последних восьми событий. В обоих случаях одинаковы владельцы, заранее доступные события в памяти и обратная карта членства; возможная разница должна объясняться использованием уже удержанного материала. Каждый участник хранит восемь последних ссылок, событие освобождается при уходе последнего владельца. При недостающей информации читается компактный долговременный список IDs якоря, затем из SQLite выбираются через IN только отсутствующие составы. В own-режиме события, удерживаемые только другими файлами, остаются за рамками допустимого чтения. Все обновления RAM происходят после успешного commit. Основной результат — число переданных байтов состава и время чтения за всю длинную панель при непрерывной работе. Различие сравнивается с ценой списка, общей работы и RAM.

**Обязательные контроли.** (1) Идентичная база без оперативного кеша: полный список и все указанные составы. (2) Сильный read-through LRU, кеширующий *полный словарь точных совместных частот для запрошенного якоря*. Новое событие повышает частоты всех затронутых закешированных якорей; остальные остаются точными. Порядок при ничьей и заполнение нулевых мест всегда вычисляются заново по текущим общим входам. Miss читает тот же полный список и тела. Допуск и вытеснение ограничиваем одинаковым с горячим состоянием логическим бюджетом, заданным по предыдущему потоку, без будущего: 8 байт на горячее событие, 8 на записанное в нём членство (ID пути и обратная ссылка), 4 на ссылку владения, 4 на файл с потерянным наблюдением. Кеш LRU получает 8 байт на якорь и 8 на каждую отличающуюся пару (ID, счёт). Расчёт допуска учитывает последнее уже принятое событие и исключает самосвязи. Ограничение номинальное; Python-объекты имеют собственные измеряемые расходы. Отдельно приводим результаты живого запуска R56 split с малым холодным индексом на тех же входах. У него другая долговременная схема; в эту группу не входит проверка равенства размера файла. Сравниваем абсолютные величины при одинаковом контракте.

**Перезапуск.** Вторая серия закрывает базу после первой половины принятых многопутевых событий каждого проекта, очищает RAM и открывает её заново. Ни одна из четырёх стратегий filelist не читает историю для восстановления, кроме концевого номера журнала. Собственное и общее чтение после рестарта считают предыдущее покрытие пути неизвестным. Его можно установить только при первом запросе по индексу. Каждый промах дочитывает отсутствующие тела; прежний кеш целиком до прогрева не загружается. Досрочный рост RAM от вмешательства эталона запрещён. Дополнительные показатели — первые десять и все прочие пострестартовые решения на репозиторий, время открытия, стационарное/прерывистое число SQL-вызовов и переданных байтов. Для R56 split фиксируем его фактическое восстановление горячего уровня. Повтор проверяется на известном и новом после перезапуска файле.

**Выборка и метрики.** Те же 880 запросов B и 196 длинной панели, 6 049 событий и девять зафиксированных R56 оракулов. Правило выбора целей и число путей неизменны, новый ответ сверяем с независимым оракулом на уровне восьми ID и их точных баллов. В каждом из пяти блоков на проект в случайном порядке (seed 57118) запускаем все 5 планов в каждом из двух расписаний рестарта. Отдельные новые базы, размеры и SHA-256 файла после WAL checkpoint проверяются попарно для четырёх способов обслуживания filelist. Указываем SQL round-trips, число BLOB и байты обратных списков и тел по раздельности; это граница SQLite/приложение, не дисковый I/O. Раздельно измеряем общее время чтения, записи и обновления кеша, их сумму, новые durable bytes и рестарт. Вычисление эталонов и независимого номинального бюджета LRU вынесено из таймера. Дополнительно фиксируем состояние RAM в логических единицах и выборочные размеры Python-объектов через getsizeof с дедупликацией. Семплирование вне таймера. Наблюдения об относительном времени ограничены машиной и данной частотой запросов. Оба ранее оценённых подхода, исходные сроки и метрики фиксируем до составного сравнения; положительный прирост не гарантирован.
