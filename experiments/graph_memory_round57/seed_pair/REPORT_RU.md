# Два известных пути и третий участник общей правки

На отложенной панели 621 многофайловую правку из шести проектов использовали как запросы. Для каждой раскрыли два пути и спросили, какие файлы стоит открыть следующими. Все политики читали ровно один и тот же набор из не более чем 16 прошлых эпизодов. В сумме это 6 008 чтений составов и 52 007 участий файлов. Ещё 494 повторных чтения удалось убрать при объединении двух списков до декодирования. Результаты оценивают предсказание следующего затронутого файла по ретроспективной истории Git. ## Что можно вывести из памяти

Попарный контроль складывает голоса связей каждого якоря с каждым кандидатом. Вариант с общими событиями добавляет голос, только когда оба известных файла и кандидат встретились в одном прошлом эпизоде. Вес такого свидетельства распределяется поровну между прочими участниками. Чтобы отделить пользу самого совпадения от более высокого веса двухсторонней поддержки, дополнительный контроль распределяет **тот же суммарный бонус** по гармоническому среднему двух попарных оценок. Ему доступно общее число совместных эпизодов двух якорей. Все методы исключают оба известных пути из выдачи. [Скоринг](joint.py)

При ограниченном числе проектов эти интервалы служат описанию неопределённости. Результаты на старых панелях разнонаправлены. ## Где попарные связи принципиально теряют информацию

Рассмотрим три группы путей A, B и C по 16 элементов. В истории с номером s записаны все 256 эпизодов (Aᵢ, Bⱼ, `C[(i+j+s) mod 16]`). У любой пары из разных групп частота ровно один при любом s. Частоты всех вершин и все 768 положительных попарных весов тоже совпадают. Если s равновероятен, то для заданных Aᵢ и Bⱼ каждый C может оказаться целевым с вероятностью 1/16. Любой алгоритм с доступом только к этим агрегатам может включить не больше восьми из 16 равновероятных целей. При наличии исходных эпизодов единственный подходящий третий файл находится напрямую. Это доказательство относится к попарным частотам. Хранение номера события на каждом ребре возвращает часть утраченной информации.

Все 4 096 сочетаний истории и пары проверены. Откалиброванная попарная выдача покрыла 2 048 из них и достигла своей верхней границы. Память исходных событий восстановила 4 096 из 4 096. Реальная панель в таблице выше показывает, почему эта математическая конструкция не даёт автоматического преимущества в предсказании будущей изменённой программы. Связь задачи с симплициальным замыканием описана у Benson и соавторов. ## Демонстрация и воспроизведение

Скачайте [автономную HTML-страницу](demo.html) и откройте её в браузере. В примере Dask попарная сумма нашла 0 из 3 скрытых файлов, свидетельства троек — 2, а контроль равного бонуса — все 3. В примере Xarray попарная сумма нашла 1 из 2, остальные два метода — 0. Примеры подобраны для демонстрации разных исходов. Можно скрыть эталоны, увидеть прошлые коммиты и состав каждого, затем переключить одну из 16 синтетических историй. Число совместных наблюдений каждой пары остаётся постоянным при изменении целевого третьего файла.

Локальный SQL-режим запускается командой `python -B demo.py serve`; ссылка печатается в терминале. В нём рейтинги вычисляются при запросе к SQLite, метки скрытого коммита читаются после вычисления. В [готовой базе](replay.sqlite) видны исходные эпизоды, строки участников и отдельная таблица оценивания. Проверка `python -B demo.py verify` сравнивает SQL с предсказаниями и восстанавливает автономную страницу. `python -B browser_check.py` проверяет обе версии в Chromium с широким и узким экраном. Для полного эксперимента используются `python -B run_pair.py --verify` и `python -B ambiguity.py --verify`.
