# Помогают ли признаки поведения предыдущих попыток выбрать работающую программу

На 48 новых задачах первый кандидат решает 39, первый после открытого теста решает 40. Лучший возможный выбор из всех трёх кандидатов тоже решает 40. Никакая стратегия, которая только читает результаты этих попыток и выбирает одну, не могла улучшить показатель относительно лучшего простого контроля на этом наборе.

| Полный усиленный тест MBPP+ | Новые, 48 | Архивные, 83 |
|---|---:|---:|
| Исходная программа | 39 | 62 |
| Первый прошедший публичный тест | 40 | 64 |
| Консенсус программ на пробах (вариант MBR-exec) | 40 | 62 |
| Статический вес классов поведения | 40 | 63 |
| Прямая оценка кода моделью | 40 | 64 |
| Кратчайший различающий вход | 40 | 64 |
| Наибольший ожидаемый выигрыш решения | 40 | 64 |
| Плацебо с перепутанным соответствием | 40 | 63 |
| Потолок при известном результате всех трёх | 40 | 65 |

Новая политика строит двудольный граф между решениями и пробами. Рассогласование между несколькими решениями сужает выбор входа, который можно показать читателю. Базовые принципы исследования поведения программ уже есть у [CodeT](https://arxiv.org/abs/2207.10397) и [S*](https://aclanthology.org/2025.findings-emnlp.865/). Наше проверяемое отличие — правило одного чтения по точной ожидаемой вероятности правильного выбора при заданной модели шума. Константы модели шума в этом запуске зафиксированы вручную. При двух различных классах каждая различающая проба задаёт одно и то же разбиение. Её шумный канал — симметричный бинарный канал, и более шумное наблюдение получается дополнительной рандомизацией менее шумного. Ожидаемая точность оптимального решения поэтому не убывает при повышении надёжности. Поскольку заданная надёжность монотонно убывает с объёмом входа и вариантов ответа, правило во многих ситуациях выбирает ту же пробу, что и контроль длины. В старой панели иной вход был выбран один раз, итоговый номер программы никогда не отличался от контроля длины.

Из 131 задачи одна свежая и десять архивных допускают различающую пробу после фильтра исходной проверки. Градация выполнена по усиленным тестам [EvalPlus](https://github.com/evalplus/evalplus); собственные ограничения на интерфейсы и количество попыток делают эту выборку адаптированным протоколом. Все 131 эталонные реализации прошли, 131 заглушка завершилась неуспехом. На 48 свежих R2-C и контроль кратчайшей пробы равны по каждой задаче, 0 выигрышей / 0 проигрышей. Вырожденный bootstrap при идентичных ответах описывает только эти наблюдения и не доказывает эквивалентность методов в иной популяции.

Генерация проводилась локально на RTX 3090, Qwen3.8-27B-UD-Q4_K_M, через llama.cpp. Сохранены 144 вызова генерации новых программ, 19 физических вызовов для оценки поведенческой пробы (общие запросы кэшированы между методами), 11 прямых сравнений программ, всего 174. По журналу сервера 22 222 входных и 14 532 выходных токена. Выбор прямой оценкой на старых задачах совпал с предлагаемым по факту прохождения всех тестов. Контекст новых задач ранее не использовался в этой серии; возможное присутствие задач в предобучении модели неизвестно.

### Воспроизведение

В живом рабочем каталоге D используются исходные данные и изолированный исполнитель из work/memory_session6/repair. Подготавливающий скрипт сохраняет происхождение данных. Последовательность в отдельной копии: prepare.py, generate.py (для повторной генерации нужен локальный сервер), observe.py и policy.py через finish.py, score.py, strong.py, audit.py. Для перепроверки уже сохранённых исходов достаточно python audit.py и сравнения audit.json. Ответы LLM с настройками, наблюдения проб, программы и поштучные receipts доступны в архиве. Полные команды подготовки и характеристики находятся в PROTOCOL.md, STRONG_CONTROLS.md и исходных скриптах.
