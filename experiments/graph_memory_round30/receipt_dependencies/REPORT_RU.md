# Память по ID наблюдений и граница применимости на SQuAD

Проверили, даст ли переход от символьных интервалов к ID отзываемых наблюдений дополнительную экономию. На этапе записи памяти фиксируются все наблюдения, присутствовавшие при выводе модели. Сигнатура кандидата — множество их идентификаторов, отзыв которых запрещает его цитату. Если Dⱼ ⊆ Dᵢ и j выше в фиксированном ранге, i не может стать победителем при проверке Dᵢ ∩ R = ∅. Можно удалить i при подготовке памяти. Более простой контроль хранит один лучший кандидат для каждого **равного** D; ещё проще — один лучший кандидат от каждой записи-производителя. Измерение сразу включило оба контроля.

**Основной результат — точное совпадение трёх правил.** В 96 вопросах с 1 722 полными исходными записями попарных физических пересечений внутри вопроса ровно ноль. Все наблюдаемые сигнатуры содержат один ID. У каждого вопроса от 4 до 26 записей, медиана 18. Поэтому на этом наборе лучший кандидат производителя, дедупликация равных сигнатур и удаление надмножеств выбирают одинаковые записи. Эффект здесь объясняется единицей изменений. Дополнительного выигрыша от частичного порядка зависимостей данные не дают.

Основные события включают 570 непустых и 6 явно доказанных пустых ответов. Среди новых случайных комбинаций известных ID было 47 пустых ответов. При K≤8 у всех трёх политик по ID 482/576 и 5 908/6 144 полностью доказанных случаев. Для K≤64 у всех трёх политики записи физически стоят 73 728 байт каждая, общий реестр идентификаторов и координат 69 632 байта, общий резерв 3 751 936 байт. Суммарное состояние 3 895 296 байт против 4 034 560 у raw с тем же реестром и 4 038 656 у геометрического Pareto. При обслуживании строго только известных полных ID этим трём правилам достаточно 143 360 байт вместе с реестром. Модель, исходные тексты и последующий fallback в таком узком варианте не включены.

Классификация 6,68 млн кандидатов по их пересечению с имеющимися ID заняла 0,226 с; выбор уникальных сигнатур и проверка доминирования — ещё 0,204 с. Сопоставление по исходному производителю из BLOB окон и их сегментов заняло 0,636 с. Эти тайминги измерены один раз при уже загруженных кандидатных score/координатах. Прогретые p50/p95 при K≤64 для одного кандидата на производителя 5,35/12,77 мкс, группировки сигнатур 5,43/11,77, удаления надмножеств 5,33/11,82, геометрического Pareto 6,38/2 631,99. Равнозначные методы по ID отличаются здесь только техническим шумом.

Для неизвестной координатной правки правила по ID использовали точный резерв, получив 1 152/1 152 правильных ответов. Хотя предварительную проверку потребовал каждый запрос, локальные верхние границы позволили обойтись 43 фактическими пересчётами окон и 185 295 байтами BLOB. Ложное игнорирование неизвестного интервала дало один ошибочный результат у K≤64. Частичные интервалы сформированы заранее по хешу и редко попадают в исходного победителя, поэтому одна ошибка не оценивает прикладной риск направленной правки. В сумме выполнены **94 464** строгих сравнения с перебором по исходным символьным координатам — 12 политик/размеров и 7 872 событий. Библиотека решений сравнивалась с одинаковым резервом и дополнительным благоприятным сертификатом полноты по реестру.

**Следствие для статьи.** Этот корпус выявляет простой точный контроль для полного отзыва записей и задаёт условия, в которых графовая структура окупиться не может. Для проверки множественных зависимостей нужны источники с перекрывающимися наблюдениями одного неизменного содержимого. Кроме того, отзыв канонических байтов и потеря одной из нескольких независимых доставок требуют разных правил допустимости.

Для воспроизведения выполнить `python inputs.py`, `python build.py`, `python evaluate.py`, `python summary_stats.py`, `python verify.py --private`. Сохранены вопросы и идентификаторы событий, переданные физические интервалы, индивидуальные результаты, затраты и физические SQLite БД, их хеши входят в build-seal.json.
