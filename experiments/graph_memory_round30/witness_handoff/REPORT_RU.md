# Может ли память восстановить цитату после потери одного сообщения

В 125 задачах SWE-Explore с будущим адресованным чтением запасная ссылка от другого исполнителя повысила вероятность восстановить обе крайние строки будущего чтения после потери одного исполнителя с 34,71% до 36,33% при равных 8 байтах на строку. Разность 1,62 п.п. [0,49; 3,11], 7 задач улучшились, 118 дали одинаковый результат. На ISETrace с проверенными байтами вывода хранение двух разных квитанций вместо одной дало 1,31 п.п. [0,37; 2,25] после потери одного сообщения. На этих коротких префиксах полная битовая карта истории сохраняет все свидетельства и занимает гораздо меньше двух 32-битных адресов.

## Откуда взялись первичные наблюдения

В SWE-Explore несколько независимых успешных агентов решали один и тот же реальный issue открытого репозитория. В 161 подходящей задаче научных Python-репозиториев найдено 8 228 опубликованных записей чтения и 3 313 различных ограниченных обращений. У 148 задач есть хотя бы одно такое обращение, у 138 есть пересечение разных шагов одного запуска, у 106 пересекались чтения разных запусков. Для эксперимента синхронизировали **первые три** ограниченных шага каждого исполнителя. Их относительный порядок между исполнителями задан исследователем. Подлинность координат проверена по исходникам на base_commit, взяты 255 файлов без пропусков. Журнал не даёт stdout каждого шага или точного промежуточного состояния рабочей копии. Это моделирование командного обмена на настоящих адресах независимых прогонов. [SWE-Explore](https://arxiv.org/abs/2606.07297), [авторские данные](https://huggingface.co/datasets/SWE-Explore-Bench/SWE-Explore-Bench).

В ISETrace есть реальные возвращённые строки исполнения и исходный JSON аргументов. Из 23 132 записей 11 519 прошли ограничение по тематике. У 2 341 из них было подходящее чтение текстового файла из workspace, у 779 было не меньше двух, у 120 найдена повторная квитанция из другого сообщения на ту же строку с совпадающими координатами и байтами. Из 181 660 разных ключей 3 812 имели больше одного первичного наблюдения. Успешная оболочка sessions_send встретилась лишь 9 раз в 7 сессиях, и только 0 содержали полный буквальный текст подходящей более ранней строки. Парафразы и короткие цитаты здесь не учитываются, успешный статус оболочки сам по себе не доказывает доставку. В основном тесте ISETrace участвуют первые два фактических чтения одного владельца истории и первое последующее подходящее чтение. Расширенная панель принимает четыре имени аргумента пути. В первоначальной панели только с path/file_path было 238 будущих чтений, эффект 1,05 п.п. [0,21; 2,10]. Дополнительные имена обнаружила независимая проверка авторской схемы. Обе оценки сохранены. [Данные и лицензия](https://huggingface.co/datasets/valiere/ISETrace), [ISE, статья об исполнении](https://arxiv.org/abs/2606.11520), [зафиксированное дополнение](ISE_SCHEMA_ADDENDUM_RU.md).

## Что должен восстановить оператор

Цель — нужные адреса первой и последней информативных строк следующего реально записанного чтения. В физический запрос уже переданы ключи этих двух строк. При заполнении памяти агент их ещё не знал. Выбор строк требует длины 32–320 байт и минимум четырёх различных буквенных последовательностей. Пара может принадлежать одному документу и не обязана выражать конфликт. В каждом префиксе доступны только уже состоявшиеся чтения. Условие совпадения адреса содержит путь, номер строки и SHA-256 её UTF-8 содержимого без разделителя строк. Переберём равновероятную потерю ровно одного из сообщений либо всех сообщений ровно одного исполнителя. Политика одного свидетеля, первые два сообщения, первое с последним, резерв у другого исполнителя и список всех наблюдений сравниваются на одних и тех же отказах. Вопросы и новые ответы LLM не генерируются. [Протокол](PROTOCOL_RU.md).

Каждая задача имеет один вес, внутри задачи одинаково взвешены будущие диапазоны и возможные отказы. Большинство будущих целей ISETrace не было полностью в префиксе. Среди первоначально доступных целей SWE (78 задач, 115 пар строк) резерв у другого исполнителя дал 3,53 п.п. [1,18; 6,30] относительно первых двух сообщений. Для ISETrace среди 34 таких пар дополнительное сообщение дало 10,29 п.п. [4,41; 17,65]. Основное сравнение включает обращения к новым строкам с нулём. Из-за зависимости задач одного репозитория bootstrap по задачам описывает результат этой панели. Снижение частоты ошибок в реальных командах, причинная значимость выбранных строк и частота подлинных сбоев здесь не измерены. [SWE, все контрасты](swe-results.json), [ISETrace, все контрасты](ise4-results.json).

## Почему двух адресов достаточно в указанной модели

Пусть у цитаты несколько истинных наблюдений из множества исполнителей. Если исполнитель один, его потеря уничтожит все исторические пути. Если их хотя бы два, два адреса с разными владельцами сохраняют хотя бы одно наблюдение при исчезновении любого одного владельца. Поскольку сообщение целиком принадлежит одному исполнителю, та же пара переносит и потерю одного сообщения. Если исполнитель один, берём два разных его сообщения для второго режима отказа. Свойство выполняется отдельно для каждой цитаты. Чтобы вернуть обе, требуются обе сохранившиеся опоры. Если недействителен сам источник, все его доставки отзываются одновременно. Это частный случай альтернативных дериваций и совместного требования к нескольким свидетельствам. Здесь эмпирически измерена частота такого случая, его практическая цена и предел при фиксированном бюджете. [Green, Karvounarakis и Tannen, Provenance Semirings](https://doi.org/10.1145/1265530.1265535).

У результата есть ещё один сильный контроль. Если после потери сообщения всё равно можно запросить привязанный к коммиту исходный файл и уже известны его координаты, при исправном файле обе строки восстанавливаются во всех допустимых SWE-пробах. Каждый такой адрес проверен чтением содержимого. Тогда сохранять повторное наблюдение для физического доступа к тексту необязательно. Его применение — журнал со строгим требованием подтвердить, кто ранее действительно видел эту цитату, или ситуация без доступа к прежней версии origin. Исторический каталог ISETrace предоставляет ранее записанные сообщения и не обеспечивает доступ к неизменному оригиналу после потери рабочего окружения.

## Физическая цена

У пары 32-битных адресов одна и та же схема для всех вариантов. В коротких префиксах SWE максимум 9 сообщений, в ISETrace 2. Сильнее всего по объёму сработала битовая карта **всех** событий на цитату. В ней сохраняются также ответы при нескольких отказах. Для независимой семантической проверки обход всех оставшихся сообщений реализован отдельно.

| Постоянное представление резервов | SWE, байт | ISETrace, байт |
|---|---:|---:|
| Одна компактная 32-bit ссылка | 64 156 | 231 868 |
| Две ссылки | 128 312 | 463 736 |
| Все ссылки с 32-bit смещением переменного списка | 219 908 | 705 600 |
| Полная битовая карта событий | 19 997 | 57 967 |
| Общие ключи пути/координат/хеша | 1 090 652 | 3 941 756 |

Пара с резервом у другого исполнителя и битовая карта дали точные ответы во всех 563 SWE и 534 ISETrace физически выполненных проверках отказа относительно сканирования истории. Медианное прогретое время на пару в микросекундах (SWE / ISETrace) составило 1.81 / 0.93 у сканирования исходных событий с хеш-таблицами, 1.60 / 0.75 у полного списка, 0.83 / 0.63 у двух разнодоменных квитанций и 0.97 / 0.64 у битовой карты. Каждая цифра — медиана 33 чередующихся серий после прогрева. Исходное декодирование журнала общее. Построение всех вариантов сразу заняло 35.4 / 121.5 мс. Измерены резидентные mmap, Python lookup и обработка адресов, без нейросетевой задержки и сброса кэша ОС. Каталоги и исходные проекции значительнее самих резервов, используются всеми вариантами. Холодный диск и конечный размер интерпретатора не измеряли. [SWE, время и байты](swe-physical.json), [ISETrace, время и байты](ise4-physical.json).

Проверка опирается на 186 618 отдельных физических строк в исходных ISETrace-ответах. Для SWE независимо сверены 2 354 проверок байтов по закреплённым исходникам. Во всех подвыборках перебор каждого возможного отказа дал те же значения, что формула для общего доступа к обеим цитатам. Для статьи о делегировании более сильным следующим тестом будет проверка восстановления именно двух конфликтующих фактов в естественных worker-to-lead сообщениях с контролями прямого доступа к документам и полного журнала. [Схема проверки ISETrace](ise4-byte-audit.json), [проверка SWE](swe-audit.json), [Zhang и соавт.](https://arxiv.org/abs/2611.22245).
