# Проверка выборочного чтения памяти Java
18.11.2026. Решения по поиску объявления в панелях A/B уже известны. Данные о качестве генерации Java не использовались для выбора правила. Оставляем три те же строки, те же объявления и исходный промпт. Если в последних трёх строках встречается имя типа или метода из выбранного графом фрагмента, передаём его модели. Иначе передаём пустой контекст. Имя выделяет небольшой детерминированный парсер Java, код parser/правила хранится в selective.py. Это проверка применимости подсказки в момент чтения. Оба ранга и короткие имена доступны заранее, экономию считаем только на этапе передачи контекста в LLM. Знание того, к какой категории авторы отнесли следующий вызов, при принятии решения не требуется.
Сравниваем с постоянной выдачей графа, постоянной выдачей Semlith, пустым контекстом и выдачей графа у такого же числа задач псевдослучайной выборки в каждой страте. Первичное сравнение на B — разница точных строк между выборочным и равным по количеству случайным чтением. Для сопоставления расходов отдельно сравним реальные токены и Edit Similarity с постоянной выдачей графа. На A результат разведочный. Для каждой пары 10 000 репозиторных bootstrap-повторов, без использования этой панели для подбора порога. Сохраняем все промпты и фактические ответы в том числе при пустом контексте. Режим полного отказа от внешнего фрагмента доступен на всех 320 примерах B. Субстроки внутри других имён совпадениями не считаются.
