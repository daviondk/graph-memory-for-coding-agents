# R4. Память редактора с изменяемой границей

Дата 18.11.2026. Используем только опубликованные входы/выходы редактора SWE-agent 1.0 с Claude Sonnet 4, сохранённые авторами для SWE-bench Verified. Фиксируем 4 096 байт на весь сжатый буфер одной сессии после каждого перехода. На входе очередного перехода доступны только этот буфер, текущее событие, неизменяемое условие и общие константы/веса для всех репозиториев. Никаких запросов к модели, выполнения программ из корпусов или полного индекса репозитория. Исходная третья серия установила 31/34 чистых выигрышей алгоритма совместного хранения над точечной моделью на правках через границу; также известно, что простой LRU почти не уступает графовой политике.

Проверяем две причины потерь при ограничении размера. Первая — отбрасывание всей очередной страницы сбрасывает в том числе допустимые строки. Алгоритм временно рассматривает отсечённый фрагмент и пытается вернуть прилегающий к резидентному соседу конец с точным учётом размера. Альтернатива — одно и то же заполнение с выбором по центру последнего просмотра. Вторая — повторяющиеся формы строк Python можно сжимать общим словарём, обученным на других SWE-smith-проектах. Это общеизвестный инженерный контроль. Сравнение с той же кодировкой, индивидуально зафиксированными контрольными строками LRU и mixed и сопоставлением с числом сохранённых байтов обязательно. Разрешён отдельный вариант калибровки риска правки блока на исторических A посредством признаков, доступных до перехода, если его точность на прежней B обоснует выбор. Границы, выбор типа/кодека и исходы открытой разработки логируются полностью.

A и B из предыдущего раунда уже открыты. Для разработки разрешены их архивы и SWE-smith. Перед запросом оценок C выполняется freeze со списком методов, SHA протоколов/кода/весов/словаря и контрольных корпусов. Единственный основной кандидат выбираем по максимуму полных попаданий на открытой B, затем разрешаем ничью по A и вычислительным затратам. Перечень дополнительных методов раскрываем. Первичное сравнение — кандидат против R3 mixed и LRU, а также против лучшего из двух их вариантов с тем же кодеком по B. При сравнении новизны важен этот контроль на той же кодировке. Основное событие и знаменатель целиком совпадают с R3. Каждые четыре фактических события сохраняем снимок состояния. Если первая непустая попытка str_replace среди следующих четырёх реально подтверждена, оцениваем полное точное наличие требуемых строк, долю верных строк и наличие первой строки. Неоднозначно или совсем не локализованные цели получают ноль у всех. По возможности независимо сверяем новую версию по возвращённому редактором тексту.

Тест C — все оставшиеся официальные задачи из тех же 500, исключаем объединение 165+129 всех прежних selection IDs и sympy__sympy-11618 (пример разбора), сохраняем исходные критерии предметного отбора, верхний предел файла 48 МиБ и критерии проверки проекции из R3. Отбор не использует патчи или результат решения. Публикуем состав по проектам, причины потерь, единицу переноса. Эффекты парные, логируются все случаи. Для основного эффекта — средняя по действиям, средняя по задачам и по репозиториям; 10 000 bootstrap по задачам внутри наблюдаемых проектов, альтернативный кластерный bootstrap по проектам и точные знаковые перестановки по суммам проектов (при симметрии). Из-за малочисленности оставшихся проектов чётко отделяем вывод об этих задачах от межрепозиторного обобщения. Каноническое восстановление байтов, максимальный и средний размер буфера, latency и общие ресурсы вне сессии также измеряются. На новой C повторного подбора по результатам не проводим. Тест измеряет сохранность наблюдений для следующей операции, а не официальную долю исправленных задач.
