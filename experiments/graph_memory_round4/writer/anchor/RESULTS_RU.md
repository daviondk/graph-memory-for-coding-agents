# Перенос ранее известных строк по подтверждению редактора

После успешной операции str_replace один и тот же файл имеет две системы координат, до и после замены. Если старый полный литерал отсутствовал в памяти, консервативный алгоритм R3 забывал старое содержимое этого файла и принимал обратно только строки, показанные редактором. Новый вариант обращается ко второму источнику — новому тексту в подтверждении. Если new_str непустой и имеет единственное вхождение в непрерывном пронумерованном блоке подтверждения, его положение указывает строку начала замены. Пусть это строка s, а Δ — количество переводов строки в new_str минус количество переводов в old_str. Старые строки перед s сохраняют адрес. Строка после конца старого диапазона переходит из n в n+Δ. Старые строки внутри замены удаляются. Если полученные известные строки конфликтуют хотя бы в одном месте с действительным новым выводом редактора, перенос отменяется. Все эти операции используют только уже совершённое действие.

Результат проверяем через последующую принятую замену. Из её уже нового отображения восстанавливаем старые полные строки заменой new_str на old_str, сохраняя префикс/суффикс крайних строк. Запечатанная память должна содержать все строки старого фрагмента по номерам и с исходным точным текстом. Учет неизвестных позиций изменился по сравнению с предыдущей проверкой, поэтому числители и знаменатели двух ветвей нельзя сравнивать напрямую.

| Панель, число обратимых правок | LRU | LRU с переносом | Обычный журнал без лимита | Журнал с переносом без лимита |
|---|---:|---:|---:|---:|
| Claude A, 637 | 363 | 379 | 411 | 416 |
| Claude B, 534 | 295 | 308 | 317 | 327 |
| Claude C, 831 | 406 | 412 | 461 | 467 |
| CodeSweep + Kimi, 218 | 92 | 96 | 94 | 97 |

A и B были открытыми панелями. Критерии переноса на C зафиксированы отдельно после завершения гипотезы о вытеснении. Для политики привязки целевые результаты C на тот момент оставались закрыты. У контролей с LRU на A прибавка +2,51 п.п. [1,36; 3,83] по проектам, 17 улучшений и 1 потеря. На B — +2,43 п.п. [0,13; 5,43], 13 улучшений и 0 потерь. На C остаётся +0,72 п.п., 9 улучшений и 3 потери. Стратифицированный по задачам двух известных проектов интервал [−0,13; 1,70] пересекает ноль. Все шесть чистых дополнительных попаданий пришлись на Django. У Kimi другой агент совершал совершенно другие действия в прежних issues. Из 101 траектории 93 дали обратимые цели. Прирост +1,83 п.п. [0,46; 3,41] по проектам, 4 улучшения, 0 потерь. Каждая из четырёх правок приходится на отдельный проект. У остальных восьми проектов чистая разность нулевая, точная двусторонняя перестановка знаков по проектам даёт p = 0,125. Это подчёркивает неопределённость интервала при малом числе различий. История одного метода при переполнении может потеснить другой полезный код, что объясняет возможность потерь даже при безошибочном переносе строк.

## Независимый контроль правильности

Для полных исходных строк, которые можно было установить из двух сторон редактирования, на A совпали 411 прямых и обратных эталонов, на B 317 совпали и один различался. На C согласуются все 461, на Kimi все 94. В единственном расхождении двух эталонов у Sphinx номер строки был один и тот же, но строка импорта изменилась внешней операцией. В публичном журнале на шаге 66 содержится восстановление источников средствами Git, между срезом памяти на шаге 64 и редактированием на шаге 67. Такие действия не дают писателю текстового наблюдения в нашем протоколе. Исключение этого случая сохраняет все 13 дополнительных попаданий B. Верификационная квитанция source_check.json содержит номер шага, классификацию и SHA источника. [Исходный публичный журнал](https://swe-bench-submissions.s3.amazonaws.com/verified/20250522_sweagent_claude-4-sonnet-20250514/trajs/sphinx-doc__sphinx-8475/sphinx-doc__sphinx-8475.traj)

В ограниченных буферах отдельно сверены строки, которые перенос предсказал, а базовый метод в тот же момент не содержал в таком виде. Когда настоящий агент повторно показывал строку в просмотре файла, сравнивали байты. Три панели Claude дали 204 из 204 совпадений в 6 задачах, 47 из 47 в 4 и 69 из 69 в 7 соответственно. Ноль зарегистрированных противоречий относится к этим 320 повторно увиденным строкам. Для Kimi таких просмотров дополнительных строк не было. Проверенные строки не дают оценки частоты ошибок среди всего не наблюдавшегося позже текста.

## Совместимость способа записи и способа вытеснения

Обе части были заморожены до этой проверки. После открытия результатов отдельных компонентов провели разведочный факторный опыт с единым обратным эталоном и неизменными 4096 байтами. Пара методов с калиброванным вытеснением использует словарь, обе разновидности LRU — исходный кодек. Сравнения обновления внутри типа вытеснения выравнивают формат.

| Память | Claude C, из 831 | Kimi, из 218 |
|---|---:|---:|
| LRU и прежнее обновление | 406 | 92 |
| LRU и привязка по новому тексту | 412 | 96 |
| Калибровка и прежнее обновление | 423 | 93 |
| Калибровка и привязка по новому тексту | 431 | 96 |

На C оба компонента вместе добавили 25 полных совпадений против исходного LRU, +3,01 п.п. [1,29; 4,89] по задачам внутри наблюдаемых проектов, 32 выигрыша и 7 потерь. Этот интервал характеризует выборку задач при фиксированных Django и SymPy. Кластерный интервал всего по двум проектам [−2,30; 3,63] крайне нестабилен. Добавление привязки к тому же калиброванному вытеснению даёт 8 улучшений без потерь. Приращение привязки у LRU составило 6, описательная разность разностей равна 2. На Kimi обе записи с привязкой достигли 96/218, при сравнении друг с другом у них по одному выигрышу. Общий полезный механизм на этих действиях — корректное обновление адресов при известных данных. Функциональное качество патчей новыми вызовами агента в данном опыте не измерялось.
