# Графовая память прочитанных фрагментов кода. RepoBench-R, серия 4

Здесь измерено, как по последним строкам кода выбрать объявление из доступных фрагментов. Значения относятся к поиску. Эксперимент с генерацией следующей строки описывает отдельная ветвь общего отчёта. RepoBench предоставляет готовый набор кандидатов. В реальной работе агенту ещё предстоит его сформировать. В данной постановке исследована память внутри доступного контекста, а перенос между задачами обеспечивается фиксированными весами. Временные последовательности настоящих действий агента в данных отсутствуют.

## Что записывается и как читается

Один узел соответствует предоставленному объявлению. Когда тело фрагмента *s* упоминает имя другого объявления *t*, создаём направленное ребро *s → t*. Рядом сохраняем слова из двух строк перед упоминанием. Учитываем неоднозначность имени с весом 1/m, где m — число кандидатов с этим именем. Кандидаты узнаются по эвристикам заголовков и имён, поэтому омонимия и неполный синтаксический разбор вносят ошибки. Входной граф строится только по показанным кандидатам. Для дорогих по длине объявлений сохраняются первые 120 и последние 40 непустых строк для разбора связей, суммарные словари строятся по целому тексту.

Для фиксированного запроса q вычисляем сходство с сохранённым предшествующим контекстом A. Пусть a(s,q) — наибольшее сходство q с сигнатурой, именем или локальным окном соседа. Тогда один из сигналов для t — max по входящим рёбрам от s величины cos(q,A) × a(s,q) / m. Это перенос свидетельства от соседа, который уже подходит к запросу. Ещё учитываем входящую и исходящую степень, количество упоминаний и усреднённую активацию. Смена степени узла может объяснять часть эффекта. Данные ниже проверяют это сравнением с отдельным контролем.

Ранжировщик — HistGradientBoostingClassifier, 80 итераций, 15 листьев на дерево, без ранней остановки. Для сравнения пять вариантов имели одинаковые 5 000 размеченных Java-задач, 84 161 пару «пример–кандидат» и 1 977 проектов. Контроль flat использует 23 признака отдельного фрагмента, local — 31 с локальными окнами, owner — 35 с предыдущими упоминаниями внутри запроса, граф — 43 со связями между кандидатами. В placebo структурные признаки сдвигаются по кандидатам. В признаках отсутствуют имя проекта, путь, тип задачи, будущая строка и индекс правильного кандидата. На 42 задачах отдельный тест подтвердил инвариантность вероятностей относительно перестановки кандидатов; стабильная сортировка разрешает совпавшие баллы исходным порядком.

## Две публичные панели Semlith

Оценка опубликована для Semlith 0.36.0. В каждой из четырёх страт first/repeat × easy/hard по 500 задач. Параметр «три строки» задаёт длину входного запроса. Параметр «512 токенов» относится только к дополнительной задаче упаковки целых кандидатов в выходной бюджет, максимум три объявления с разделителями. Acc@k означает долю задач, в которых искомый индекс попал в первые k позиций. MRR — среднее обратное место первого правильного кандидата. Недопустимый индекс считается промахом. ## Запись графа при поступлении фрагмента

В дополнительном проверочном опыте по мере поступления очередного фрагмента он добавлялся в граф. Новый фрагмент связывается с уже известными именами. Когда появляется новое имя, «обратные» упоминания ищутся в сохранённых множествах слов прошлых объявлений. При чтении множитель неоднозначности пересчитывается по актуальному числу владельцев имени. Память хранит уже разобранные документы, направления связей и короткие контексты. Этот вариант не требует отдельного обратного словаря по всем словам.
Заранее выбраны 240 архивных эпизодов из 79 репозиториев. После каждого из 2811 поступлений проверили точное равенство множеств рёбер с контекстом и весом, исходящих соседей и частот текста. Во всех 240 эпизодах совпали вероятности и конечные ранги замороженной модели. Тест использует первые не более 20 фрагментов в фиксированном перемешанном порядке. В четырёх эпизодах были объявления с совпадающим корневым именем.
В повторном измерении полный пересчёт для каждого промежуточного состояния занял 5.27 с CPU, сохранение и дополнение графа 4.64 с. Ускорение 1.13×, кластерный 95%-интервал [1.01; 1.23]. Разовое построение только финального графа заняло 4.23 с CPU. Для первого замера на тех же данных отношение составило 1.16×. Перед каждым вариантом в начале эпизода очищается кэш разбора текста. В elapsed входят парсинг и материализация снимка, отдельно от извлечения 43 признаков, обращения к LLM и работы IDE. Об имитации порядка поступления фрагментов следует сообщать при сопоставлении с реальными агентами. Отдельный опыт координатора с 320 примерами использует другую методику измерения и собственные файлы.

## Интерпретация и воспроизводимость

Граф выбирает из уже предоставленных объявлений. Проверенный источник добавочной ценности — сравнение с одинаково обученным ранжировщиком в условиях одинакового видимого кода и входных кандидатов. Разница с внешней системой объединяет действие графа, параметры ранжировщика и целевую супервизию. Влияние отдельно контекста, степени и ложных рёбер проверялось с абляциями. Изменения порядка в первой тройке, упаковки в 512 токенов или совпадения следующей строки являются разными целевыми величинами. На одной лишь лучшей позиции нельзя основывать вывод об улучшении работы агента.

Ближайшие графовые работы оценивают другие режимы доступа к коду. GraphCoder строит граф зависимостей между операторами и извлекает похожие фрагменты из репозитория. RANGER в Table 2 использует Python RepoBench v1.1, 430 проектов, собственный этап отбора контекста, Cypher и отдельные rerankers. У этих чисел другой пул кандидатов, входной контекст и язык. Об их превосходстве или отставании от нашего метода данный эксперимент не свидетельствует. [GraphCoder, ASE 2024](https://arxiv.org/abs/2406.07003) · [RANGER, раздел 4.2](https://arxiv.org/html/2509.25257v1#S4.SS2).

Следующая проверяемая гипотеза вытекает из потерь вроде budgetapp. Когда имена в запросе почти однозначно указывают на кандидата, большой входящий degree может отодвинуть верный фрагмент. Можно разрешать влияние соседей только при наличии совпадения предшествующего контекста и оценивать отдельно случаи сильной и слабой прямой подсказки. Порог следует зафиксировать на других проектах до оценки. Для агентной памяти за пределами заполнения строки стоит проверить повторяемую последовательность правок, журнал фактических чтений файлов, одинаковый бюджет инструментов и целевая метрика прохождения тестов. Только такой эксперимент позволит оценить, помогают ли дополнительные рёбра при реальной работе с репозиторием.

Воспроизведение описано в REPRODUCE.md. Протоколы фиксируются файлами *_PROTOCOL*.md, веса и исходники — SHA-256 в *_lock.json. Предсказания запечатаны до присоединения gold. Во время подготовки полного HF-прогона первый старт завершился из-за отсутствующего импорта pyarrow.parquet до первого сценария, затем скрипт исправили и перезапустили с новой фиксацией. Изолированный нативный клиент использовал публичные веса и не изменял конфигурацию пользовательского клиента.
