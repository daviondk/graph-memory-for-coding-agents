# Инкрементальная запись графа при новых наблюдениях
До замера фиксируем 240 архивных Java-задач по 60 из четырёх страт, sha256('incremental|{panel}|{id}'), порядок получения предоставленных фрагментов перемешивается детерминированно по задаче. Измеряем первые не более 20 поступлений, чтобы длинные эпизоды не доминировали в процессорном времени. Корпуса репозиториев заранее не индексируются. Наблюдения моделируют поступление кодовых фрагментов. Порядок не является настоящей траекторией работающего агента.
Сравниваются одинаковые финальные и промежуточные графы. Контроль после каждого обнаружения заново вызывает encode на всех ранее виденных кандидатах с его стандартным кэшем разбора. Инкрементальный метод разбирает новый кандидат, проверяет его ссылки на известные корневые имена и обращается к уже увиденным текстам только при появлении в них очередного имени. Вес неоднозначного имени вычисляется при чтении, чтобы новый кандидат мог изменить число известных владельцев имени. При замерах обеим реализациям одинаково очищается текстовый кэш перед эпизодом. Порядок замеров чередуется детерминированно по наблюдению. Основное время — CPU процесса perf_counter/process_time, отдельно сохранить wall clock и число событий. Измеряется построение графа со срезом, а не время генерации, полного ранжирования, сети, ведения постоянной БД или поиска исходных файлов.
До интерпретации подтвердить равенство множств направленных событий с их кратностями и весами, исходящих связей и DF при каждом поступлении. На финале сравнить все 43 признака, при равенстве также ранги графа frozen model. Зафиксировать случаи неоднозначных имён, размеры, время, среднее/медиану парного ускорения, интервал отношения суммарного CPU по целым проектам. Никакие параметры модели не меняются. Для одного разового чтения со всеми готовыми кандидатами инкрементальный алгоритм может быть менее эффективен. Отдельно измерить единственную batch-конструкцию, чтобы эту цену было видно.
