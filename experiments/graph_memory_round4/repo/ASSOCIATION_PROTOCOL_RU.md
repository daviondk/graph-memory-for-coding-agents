# Как хранить полезные пары после завершения обращения

Дополнительная гипотеза сформулирована до открытия оценок текущих R4-моделей. В репозитории периодически требуется импорт, чьё имя ещё не было упомянуто текущим вызовом. После прошлой успешно размеченной операции можно связать идентификаторы в видимом перед её выполнением коде с частями имени использованного внешнего объявления. Каждое такое событие обновляет ребра «наблюдаемый признак → потребовавшаяся роль/тип». Это вариант статистической модели переводов терминов / ассоциативной памяти. Потенциальный вклад — дешёвая запись контрастного сигнала и проверка при честном ограничении длины запроса. Требуются завершённые размеченные обращения. Из тестовой разметки ничего в память не записывается.

Используем только те же ранее отобранные Java train-задачи. Для каждой формируем нормированную массу на именах правильного объявления и нормированную среднюю массу на кандидатах текущей задачи. Две разреженные таблицы запоминают совместную массу query–name для наблюдённого и фонового выбора, отдельно фоновые массы имён. Для положительной связи нужен избыток совместной массы относительно ожидаемой. Такой сигнал не сводится к сходству совпадающих токенов. Модель выбора остаётся тем же HistGradientBoosting, к уже вычисленным признакам полной модели добавляются интенсивности и отношения шансов. Контроль с теми же признаками, циклически сдвинутыми между кандидатами внутри запроса. Все зачисляемые кандидату сведения должны быть доступны до gold. При оценке обучающих объектов используем 5-кратное перекрёстное формирование признаков с разделением по проекту, чтобы обучающий ответ не присутствовал в своей таблице. В тесте используем все завершённые исторические обучающие задачи и замороженный ранжировщик. Числовые гиперпараметры фиксируются в коде до открытия оценок.

Первичная метрика этой дополнительной ветви — парное Acc@1 новой памяти против ранее заданной полной модели при keep=3 на том же закрытом Java-срезе. Сравнение с предыдущей гипотезой образует семейство из двух проверок; вместе приводим парный random-sign test по проектам и коррекцию Holm. Для оценки защиты от подбора под публикуемую подвыборку позднее фиксируем ещё 250*4 ранее не использованных Java-задач, непосредственно на тех же Java test-shards и ни одного совпадающего ID с 2000 основных. Если подвыборка не исключает целые репозитории основной панели, учитываем их пересечение и оговариваем только перенос на новые запросы. Для полной сопоставимости фиксированные Java-веса применим также к тем же 2000 Python случаев без дополнительного обучения на Python.
