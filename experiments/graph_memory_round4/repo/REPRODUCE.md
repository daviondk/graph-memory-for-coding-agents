# Воспроизведение серии R4 на RepoBench-R

Основные программы запускались на CPU в Windows. Python 3.12 из work/graph_memory_round2/multihop/dev_env с NumPy, scikit-learn и PyArrow; токенизатор CodeGen и исходные Python Parquet закреплены в graph_memory_round3/repo. Для исходной рабочей раскладки требуются оба раунда. Источники и SHA Java-данных записаны в sources.json, бинарника — native/release.json. Все использованные входные таблицы и производные записи находятся на диске D. Для сравнений с Semlith на диске D были созданы отдельные локальные копии опубликованных фрагментов; код этих примеров не исполнялся. Каждый вызов нативного семантического индекса использовал CPU. Системная регистрация клиента, автозагрузка и вход в аккаунт не использовались.

1. В окружении R3 запустить fetch_java.py, затем data_io.py. Первым скачивается авторская parquet-конверсия pinned revision c9daeba525cb28cfb9fbe17886f32b8ea34fc870, затем строятся списки и проверка непересечения проектов.
2. Получить publisher_repobench.py, publisher_common.py, publisher_arms.py (они находятся в комплекте). Оригиналы — github.com/semlith/semlith, commit 4a0be44a76e2bc90e44d131c16c49ff5eb61a668, bench/scorecard/{repobench,common,arms}. Запустить published_baseline.py. Скрипт использует оригинальный код bm25_rank и terms. Затем experiment.py фиксирует метод, получает признаки без test labels, обучает, сохраняет модели и запечатывает ранжирования.
3. Для собственного запуска Semlith 0.36.0 — get_tool.py (проверяет vendor SHA256SUMS) и native_run.py. Измерения 96 задач сохранены отдельно. Приложение загружает модель granite-embedding-small-english-r2-ONNX под native/models. Нужно существующее сетевое соединение во время первого запуска. Сейчас исходные ранжирования уже есть и повторная загрузка для их сравнения не нужна. score.py сверяет все 32 опубликованные числовые ячейки лексического контроля, затем считает исходы основного эксперимента.
4. association.py обучает разреженную контрастную память из 5 000 исторических размеченных решений. Веса и списки пятерного разбиения детерминированы именами репозиториев; бинарная модель и потоки записи на D. Этот скрипт также запечатывает исходы 1 000 дополнительных новых ID. Пошаговая диагностика в association*_*.json*, assoc.pred.jsonl.gz, assoc_prediction_lock.json. Режим валидации по 1 000 новым ID и следующая панель из 1 000 задач на 172 новых репозиториях пересекаются на 850 задачах, суммировать их как независимые нельзя.
5. Для следующей панели — strict_select.py, strict_predict.py, strict_binary.py. Генерируются 1 000 задач на исключённых репозиториях, затем отдельно словарь пар, SHA-256 моделей и 320 поштучных рангов реального Semlith. structure.py сравнивает степень, соседей и связь с контекстом, secondary_score.py оценивает все sealed длительности и исходы. order_diagnostic.py, затем order_score.py проводят позиционную проверку на тех же фиксированных индексах, отчёт строит report.py. verify.py отдельно проверяет данные, отсутствие совпадающих проектов/стимулов и инвариантность модели к перестановке кандидатов. Предсказания в *.pred.jsonl.gz, подсчёты по задачам в *.scores.jsonl.gz, агрегаты в results, native_results, structure_results, association_results, holdout_results и order_results.json.
6. Исходные рёбра эпизодической памяти теста восстанавливаются из соответствующих кандидатов и правил memory.py; копия данных включает авторские ограничения. Малый архив для проверки может исключать большие inputs, cache, strict_cache, индексы native, native_holdout и загружаемые веса. Все такие пути в оригинальном рабочем каталоге на D доступны. Каталоги corpus содержат файлы исключительно для индексации. Для инспекции достаточно агрегатов, понаблюдательных прогнозов, исходов, скриптов, протоколов и ссылок на исходные версии. Для тренировки требуется установка указанных библиотек. Сравнение выполнялось на полном исходном наборе кандидатов для каждой выбранной строки.

### Полные публичные корпуса и дополнительные проверки

Для полной оценки HF Java с официальным crop и Jaccard запустить full_java.py, затем full_score.py. Размер 24 000, деление easy/hard поровну. Методический и поштучный протокол в FULL_PROTOCOL_RU.md. Кроме файла full_results.json сохраняются полные порядки кандидатов и исходы в full.pred.jsonl.gz, full.scores.jsonl.gz. Загрузка авторского конференционного исходного архива независима от HF-конвертации. Путь — Download Data via Google Drive в зафиксированном upstream README. archive_probe.py проверяет Range, читает центральный каталог ZIP, загружает и проверяет CRC только двух Java retrieval членов. archive_convert.py cff и archive_convert.py cfr преобразуют исходные файлы последовательно через restricted unpickler, который разрешает только примитивы Python. Затем archive_java.py, full_score.py archive и archive_audit.py. Последний проверяет совпадение полных текстов, репозиториев и всех упорядоченных кандидатов. Токенизатор Salesforce/codegen-350M-multi независимо сверен с ревизией b25de779e2044ed5e7707505dea0e5a9bb08556a. Опубликованные веса/скореры из семантических строк Table 2 не включены в архив наблюдений.

Для контроля без train запустить zero_ppr.py. Для проверки обновления при поступлении отдельных объявлений — archive_streaming.py. Оба скрипта сначала фиксируют протокол и идентификаторы. report.py включает завершённые проверки в RESULTS_RU.md. Артефакты archive.pred.jsonl.gz, archive.scores.jsonl.gz и full.pred.jsonl.gz/full.scores.jsonl.gz уже содержат все сводные поштучные решения; папки archive_full и full дублируют прогнозы по шардам. Для компактного комплекта допустимо исключить сами исходные общедоступные 36k/24k архивы, распакованные корпуса, onnx-модели, исполняемый Semlith и индексы, сохраняя их идентификаторы, хеши и скрипты восстановления. Обязательная сигнатура исходного 36k test находится в archive_audit.json. Путь train-run сохранён в method_lock.json и fit.json.
В этой папке лежат также отдельные замеры координатора на 320 примерах. Файлы incremental.py, incremental_precise.py, lean_graph.py, incremental_lock.json, INCREMENTAL_RU.md, INCREMENTAL_TIMER_RU.md и cycle_* относятся к его протоколу. Архивная проверка на 240 примерах из настоящего ICLR test использует строго команду archive_streaming.py. Её собственные файлы — ARCHIVE_STREAMING_PROTOCOL_RU.md, archive_streaming_lock.json, archive_streaming_results.json, archive_streaming.jsonl.gz. В начале эпизода кэш разбора очищается; измерено суммарное CPU на разбор, запись и построение снимка графа. Контроль ведёт стандартный кэш разбора внутри эпизода. В первом техническом запуске имена для архивного скрипта совпали с тремя файлами соседней проверки. Координатор восстановил свои оригиналы по независимым SHA, затем архивную проверку повторили под уникальными именами с теми же задачами, алгоритмом и исходами. Первоначальные результаты сохранены отдельно с префиксом archive_streaming_initial*. Для запуска использовать только archive_streaming.py, а не сохранённую для проверки историческую копию archive_streaming_frozen.py. Время округления process_time() на Windows ограничивает поэпизодные отношения. Отчёт содержит обе повторности и статистику по сумме CPU, wall-clock и разовой инициализации. Заметка по архивной ICLR-таблице строится archive_page.py и использует только archive_results.json.
