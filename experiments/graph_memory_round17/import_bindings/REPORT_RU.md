# Обновление памяти о тестах, зависящих от импорта Python

Тест может использовать значение, вычисленное до начала его собственного исполнения. В Colorama объекты Fore, Back и Style уже содержат строки цветов, когда авторский тест обращается к атрибуту. Правка функции, собравшей эти строки, делает прошлый pass устаревшим. Граф вызовов только за время теста теряет эту зависимость. Сохранение цепочки «функция при импорте → созданное значение → потребитель» позволило найти все четыре провала на трёх контролируемых правках настоящей библиотеки. [Исходник Colorama](https://github.com/tartley/colorama/blob/3de9f013df4b470069d03d250224062e8cf15c49/colorama/ansi.py) · [Протокол](COLORAMA_PROTOCOL_RU.md)

|---|---:|---:|---:|
| Полный запуск pytest | 78 | 4 | 0 |

| Сброс по вызову изменённого блока при импорте для всех тестов | 52 | 4 | 0 |
| Граф привязок имён и вызовов при импорте | 22 | 4 | 0 |
| pytest-testmon 2.3.0 и 2.3.1, каждый | 0 | 0 | 4 |
| pytest-filemon 0.1.0 | 78 | 4 | 0 |
| pytest-mortadelo 0.1.0 | 26 | 1 | 3 |

В знаменателе 26 разных положительных тестов, каждый оценивали после трёх отдельных изменений. Граф отправил на исполнение 4 теста после изменения code_to_chars, 18 после изменения атрибута AnsiFore.RED и 0 после изменения clear_screen. Полный pytest обнаружил соответственно 3, 1 и 0 провалов. Во всех случаях выбранные графом nodeid действительно исполнены. Изменения внесены экспериментально. Данные о частоте данного механизма в обычных коммитах требуют отдельного исследования. [Фактические запуски](colorama-runs.gz) · [Сводка](colorama-results.json)

**Проверка конкурирующих методов.** Оба testmon независимо проверены штатным CLI без нашего наблюдателя. Для каждого изменения и каждой версии использовали новую базу зависимостей, положительный прогрев на всех 26 тестах, неизменённый контроль с нулём выбранных тестов и полный запуск после правки. Для filemon и mortadelo использованы отдельные чистые Git-клоны и штатные точки входа. Все четыре установки проверены по нативному JUnit XML. На этой панели filemon покрывает все четыре провала и исполняет все 78 проверок. Граф исполняет на 56 проверок меньше при том же обнаружении. Полный набор сравнений нужен по двум разным причинам: одна политика тратит лишние проверки, другая пропускает действительное изменение. [JUnit штатного testmon](cli-checks.gz) · [JUnit filemon и mortadelo](other-controls.gz) · [Реализация filemon](https://pypi.org/project/pytest-filemon/0.1.0/)

**Проверка механизма.** На специально написанном модуле провели девять отдельных изменений с десятью тестами. При полном повторе получились восемь провалов. Граф связей при импорте обнаружил 8/8 при 24/90 повторах, консервативный сброс по импорту — 8/8 при 81/90. Граф только по вызовам и testmon 2.3.0 — по 1/8 при одном повторе. Набор включает значение по умолчанию, атрибут класса, цепочку присваиваний, регистрацию через побочный эффект, непрозрачный доступ через globals и неиспользуемое значение. Для непрозрачных операций политика намеренно расширяет область перепроверки. [Исходные правила](PROTOCOL_RU.md) · [Граф микронабора](import-graph.json) · [Поштучные исходы](runs.gz)

**Почему исходный граф даёт ложный пропуск.** Пусть функция f выполняется при загрузке модуля и возвращает значение x, а тест t позднее читает x. Даже при неизменной функции теста результат может зависеть от f. В графе, ограниченном динамическим стеком теста, пути t → f нет. В расширенном графе появляются рёбра t → x и x → f. Если изменение пересекает множество достижимых источников, прежняя положительная запись подлежит повторной проверке. Гарантия такой схемы требует полноты всех влияющих зависимостей, фиксированных внешних входов и детерминированного исполнения. Наш наблюдатель аппроксимирует чтения из co_names и использует идентичность импортированных объектов. Он не решает общую задачу алиасов, изменения состояния сторонней библиотекой, рефлексии, параллелизма или произвольных побочных эффектов. Предположение о безопасности по графу вызовов опровергается уже микропримером.

**Цена записи.** На неизменённой Colorama провели дополнительно пять пар запусков, чередуя порядок. Медиана полного pytest с обычным наблюдателем составила 0,900 с, с профильным сбором связей — 1,180 с. Медианная парная надбавка — 0,236 с, компактное JSON-представление связей заняло 3 833 байта. Работа велась на общей машине. Число пропущенных тестов само по себе не определяет выигрыш времени во всём процессе. [Пары измерений](costs.json)

**Место в литературе.** В Ekstazi уже учитываются инициализаторы и обращения к статическим полям. NameRTS строит граф имён и элементов Python и прямо описывает потерю точности при функциях, выполненных во время импорта. Возможный вклад для агентной памяти — сохранить происхождение конкретного наблюдавшегося значения и использовать его для проверки актуальности утверждения «тест пройден». Положение относительно NameRTS требует сравнения на уровне файлов и по их определениям affected/safe. Приведённые 78 пар оценивают отдельные nodeid и фактические падения после контролируемых изменений. [NameRTS](https://arxiv.org/abs/2605.25356) · [Ekstazi](https://users.ece.utexas.edu/~gligoric/papers/GligoricETAL15Ekstazi.pdf) · [Отдельная проверка NameRTS](../namer_ts/REPORT_RU.md)


## Автоматический поиск экспортов и источника изменения

Первоначальный адаптер явно перечислял четыре публичных объекта Colorama и получал имя изменённого блока из описания интервенции. В дополнительном контроле известен только путь редактируемого модуля. На первом исполнении 26 тестов наблюдатель сам перечислил 16 имён пространства модуля, исключив служебные имена с двойным подчёркиванием. В проектных кадрах Python он сопоставлял значения глобальных имён по идентичности объектов и сохранял все совпавшие псевдонимы. Предиктор получил наблюдения исходной версии и байты модуля до и после правки. Идентификатором варианта служил SHA-256 его содержимого. [Предварительная фиксация дополнительного контроля](AUTOMATIC_PROTOCOL_RU.md) · [Наблюдатель](auto_observer.py) · [Анализ AST](auto_predict.py)

Для правок тел функций сопоставление AST нашло определения code_to_chars (строки 12–13) и clear_screen (18–19). Для присваивания внутри класса найден точный узел AnsiFore.RED (строка 51). Граф исполнения хранит информацию на уровне класса, поэтому при принятии решения источник расширили до AnsiFore. Во всех трёх случаях набор тестов побайтно совпал после канонической сортировки nodeid с первоначальным планом. Для code_to_chars фактически выполнили 4 теста и нашли 3 падения, для AnsiFore.RED выполнили 18 и нашли одно падение, для clear_screen вызов дополнительных тестов не понадобился. Три полных запуска независимо проверили 78 исходов, в том числе отсутствие падения после изменения clear_screen. Все 22 выбранных теста реально выполнены, исходы подтверждены XML JUnit. [Запечатанные прогнозы](auto-forecasts.json) · [Поштучное сравнение](auto-results.json) · [JUnit и stdout](auto-runs.gz)

Этот контроль устраняет ручной список экспортов и подачу имени производителя в предиктор на данной панели. Проект, изменённый файл, три интервенции и семейство наблюдаемых зависимостей были известны при разработке. Неизвестные конструкции AST вызывают консервативный сброс. Импортные ссылки, полученные через внешние библиотеки, динамические атрибуты и чтения скалярных объектов с совпадающей идентичностью требуют проверки на других проектах. Дополнительная серия выполнена после исходной оценки и не является независимой репликацией по задачам.
