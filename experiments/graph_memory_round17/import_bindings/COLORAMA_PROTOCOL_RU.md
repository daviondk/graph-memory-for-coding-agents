# Проверка зависимостей инициализации на пользовательской библиотеке

После контролируемой проверки механизма выбрана Colorama 0.4.6, где реальные объекты Fore, Back и Style создаются при импорте. Состояние закреплено на commit 3de9f013df4b470069d03d250224062e8cf15c49. Это целевой выбор проекта с необходимым механизмом. Используем целиком два авторских файла тестов colorama/tests/ansi_test.py и colorama/tests/ansitowin32_test.py. При первом запуске учитываем только действительно завершённые положительные тесты, отмечаем все исключения и отсутствие результатов. Одна строка меняется в каждой из трёх независимых копий. (1) Заменяем суффикс m на x в code_to_chars. (2) Меняем цвет RED с 31 на 32 внутри класса AnsiFore. (3) Меняем J на H в clear_screen. Это контролируемые внесённые изменения, тесты библиотеки оставляем без изменений.

Правила полного повтора, графа функций, привязок имён и широкого сброса при импорте зафиксированы в предыдущем протоколе. Для настоящих клиентских тестов нужны два расширения наблюдателя: он включается до импорта pytest, а в исполненной функции теста или библиотечного клиента видимое значение глобального имени сопоставляется с текущими объектами модуля ansi по идентичности объектов. Ограничиваем соответствие экземплярами классов/объектами функций и имена берём из co_names исполнившегося кода. Это консервативное приближение среди возможных ссылок. Относительно модуля ansi регистрируем исполнение связанного класса по его корневому имени. Время изменения искусственно сдвигаем минимум на 5 секунд, байткод-кеш отключён. Хеш источника и фактический импорт проверяем. Сравним с новым прогревом, проверкой неизменённого дерева и реальным исполнением pytest-testmon 2.3.0, а также с полным запуском на каждой изменённой копии. После выбора отдельно исполним проверки, предложенные графом. Новый пример проверяет применимость механизма на настоящем проекте, его выбор и мутации ограничивают внешнюю валидность.
