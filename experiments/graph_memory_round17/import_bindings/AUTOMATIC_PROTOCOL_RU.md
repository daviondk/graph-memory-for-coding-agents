# Автоматическое получение экспортов и источника изменения

Результаты первоначального контроля уже известны. Задаём дополнительную проверку чувствительности на тех же трёх изменениях Colorama и всех прежних 26 положительных nodeid. Исходный вариант и его запечатанные прогнозы остаются самостоятельным экспериментом.

В новом предикторе путь редактируемого файла известен из события изменения, как у исходного варианта. Конкретные имена объектов и изменённых производителей не предоставляются. При первом запуске наблюдатель берёт все недвойные имена из пространства имён этого модуля. По каждому коду теста и наблюдаемого проектного вызова в co_names он ищет ссылки на объект модуля через идентичность в globals. Сохраняются все совпавшие имена при нескольких псевдонимах. Такая аппроксимация может расширять набор чтений, в особенности при интернированных простых объектах или неисполненных ветвях. Остальной механизм построения связей повторяет исходную серию.

Вход анализа изменения — только байты старого и нового модуля, наблюдения исходной версии и неизменная форма дерева тестов. Сравниваются AST именованных верхнеуровневых определений без номеров строк. Для изменения функции берётся её имя. Когда в прежнем и новом неизменившемся каркасе класса меняется простое именованное поле, располагаем изменением вида класс.поле. Поскольку в этом наблюдателе связи импорта привязаны к вызванному классу, консервативно расширяем его до всего класса. При неопределимой структуре модуля или добавлении/удалении имени, неизвестном результате разбора либо неоднозначном соответствии планируем полный набор повторов. Политика применяется одинаково к каждому модулю, полученному под анонимным ключом SHA-256. Имена интервенций используются только исполнителем и для присоединения к исходному контролю после сохранения прогнозов.

Фиксируем исходные хеши, полный список экспортов и совпавших ссылок, каждый распознанный узел AST, возможное расширение и выбранные тесты. Сохраняем прогнозы до выполнения нового повтора. Для каждой непустой выдачи запускаем все выбранные nodeid в отдельном процессе pytest, считываем исходы из JUnit и проверяем относительно полного нового запуска и исходной замороженной панели. Оцениваем число повторов, обнаруженных отказов и изменившихся решений по отношению к прежнему адаптеру. Это дополнительная проверка на ранее изученных данных.
