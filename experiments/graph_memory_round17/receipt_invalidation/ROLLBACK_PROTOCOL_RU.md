# Контроль на реальных изменениях производственного кода

В архивных повторах команды с непрозрачными эффектами сделали интервалы непригодными для разделения консервативных политик. Для отдельной панели задаём точную наблюдаемую интервенцию. Публичный more-itertools используется как небольшой изолированный CPU-репозиторий обработки последовательностей, с собственными Python-тестами. Источник в прежних сериях встречался на других релизах. Для этой панели берём новые коммиты строго между v10.6.0 и v10.8.0. Смотрим обычные коммиты с первой родительской базой, изменением одного из двух основных .py модулей и хотя бы одного Python-теста. Исключаем сообщения о безопасности и графы с неразрешёнными исходными файлами. Для основной проверки берём до восьми коммитов по фиксированному SHA-256 от commit ID, среди коммитов затрагивающих реализацию уже существующей верхнеуровневой функции или класса. Пропускаем изменение импортов, добавление/удаление публичной функции либо глобальной конфигурации при невозможности выделить единый исполняемый модуль. Выбор ведётся до запуска тестов.

Исходная версия — после коммита. Для каждого коммита запускаем оригинальные тестовые методы с этой версией, далее откатываем только байты изменённого производственного модуля к первому родителю. Тестовые методы, остальное дерево и интерпретатор сохраняются. Включаем до четырёх добавленных либо изменённых методов нативных тестов и до восьми неизменённых по хешу ID на коммит. Рассматриваем в основной оценке исходно проходящие тесты. Для двух сред делаем по два независимых запуска в отдельных процессах. Фиксируем нестабильность и технические отказы отдельно от настоящих падений теста.

До доступа к результату отката фиксируем прогнозы, используя только первую положительную квитанцию, исходные тестовые наблюдения и известный diff. Сравниваем полный повтор, безусловный пропуск, сброс по изменению любого ранее исполненного файла и сброс по изменённым исполнявшимся функциям. Для связи теста с функцией используем событийный Python-профиль в фазе setup/call/teardown самого теста. До- и послесессионные побочные эффекты не входят в граф. Для каждого блока файла используем корневую функцию или класс и синтаксический AST без строковых позиций, учитывая class-body изменения консервативно. В отдельной абляции недорогая статическая политика отслеживает лексические идентификаторы изменённых функций в тексте самого тестового метода. Границы наилучшей наблюдаемой политики ограничены выбранными коммитами и открытым тестовым набором. Изменения подобраны по факту изменения авторских тестов, поэтому частоту провалов в общей истории из этой панели не оцениваем. [Авторский проект](https://github.com/more-itertools/more-itertools)
