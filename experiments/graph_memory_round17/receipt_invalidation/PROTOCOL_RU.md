# Актуальность положительного свидетельства pytest между изменениями рабочего дерева

Проверяем применимость ранее показанного агенту успешного результата при следующем **реальном** вызове той же тестовой команды. Публичная панель R15 фиксирует 24 репозитория и все допустимые вызовы pytest. Берём все последовательные в рамках задачи вызовы с **байтово одинаковой** командой, одним буквальным относительным Python-селектором файла или nodeid, явным окружением рабочего каталога /testbed и без смены каталога кроме cd /testbed. Регистрируем число пар с прежним явным pass и нулевым rc, включая неизвестный результат второго запуска. В сравнениях используем один набор пар, разбивку по исходным двум панелям и уровню селектора. Повтор номера файла скрывает возможность смены состава тестов, поэтому отдельно учитываем nodeid и смену количества успешных тестов. Тесты могли иметь скрытые побочные эффекты. События упорядочены по исходным сообщениям, интервалы с параллельными вызовами отмечаются неопределёнными.

Источник исхода — уже зафиксированный парсер финальной строки pytest, который читает вывод инструмента, отдельно от статуса последней команды конвейера. Валидный повторный PASS требует также нулевого shell-кода. Сначала сохраняем прогнозы без доступа к итогам вторых запусков при принятии решений. После этого отдельно присоединяем метки и публикуем исходы всех пар.

Политики записывают действие USE или RECHECK. (1) всегда перепроверять и (2) всегда принимать прежнюю запись задают крайние границы. (3) разрешать прежнюю запись лишь если все промежуточные наблюдаемые команды явно читающие либо их нет. Любая потенциальная запись, непрозрачная команда и наблюдающееся параллельное исполнение вызывают сброс. (4) если все операции разобраны, сохранять прошлый результат, пока не изменены файл селектора, conftest, базовая конфигурация, а также код, имя которого совпадает с именем тестового модуля без test_/ _test. (5) более консервативная политика разрешает повтор после известных изменений только для изменений других тестовых Python-файлов или текстовой документации. Изменения производственного кода приводят к повтору. Каждая неизвестная операция принуждает варианты (3–5) к повторной проверке. Все проверки эвристические, поскольку запуск программы также может менять внешнее состояние.

Для каждого варианта публикуем число возможных пропусков повторного запуска, реальные последующие fail среди таких пропусков, неизвестное состояние и подтверждённые pass, попарную разницу действий. Сопоставляем их с повторным запуском всех команд в наблюдаемых исторических событиях. Для долей даём описательные интервалы по независимым блокам задач. При нуле ошибок также отмечаем ограниченность размера выборки. Ожидаем, что часть повторных проверок действительно происходит после явно локальных действий, но перенесённые положительные результаты могут оказаться ложными при изменении импортируемого кода. Запрос агента на пропуск, рабочая копия на точной ревизии, скрытые побочные эффекты и причинная экономия wall time в этих историях неизвестны. Внутризадачные сравнения одинакового селектора между интервалами без возможных записей и с изменениями публикуем, только если такая группа наблюдается. Никакие исторические команды не исполняются.
