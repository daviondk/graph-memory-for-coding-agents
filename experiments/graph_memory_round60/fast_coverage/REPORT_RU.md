# Стоимость точной графовой памяти с учётом уведомлений о вытеснении

На 12 репозиториях и 1 206 запросах после перезапуска компактный кеш, хранящий исключения относительно **обеих** резидентных копий события, прочитал **26 122 байта** из SQLite. Оптимизированный полный индекс — **33 837 байт**. При лимите 1 КиБ разница составила 22,8%. В одной и той же серии из пяти блоков медианное время обновлений графа и запросов составило 91,43 и 94,60 мс. Более простой вариант, который учитывает только горячий граф B8, оказался быстрее обоих (84,77 мс) и прочитал больше данных (38 402 байта). При 4 КиБ эти три реализации прочитали по 10 233 байта, а B8-only сохранил преимущество по времени. [Основной протокол](PROTOCOL.md) · [Протокол полного контроля](CONTROL_PROTOCOL.md) · [Протокол оптимизации чтения](HIT_PROTOCOL.md)

## Что хранится и почему ответ точен

Для файла f обозначим через A все события текущего зафиксированного префикса, содержащие f. Горячий граф B8 удерживает последние восемь событий каждого владельца. Событие доступно горячему графу, пока на него ссылается хотя бы один владелец. Второй кеш LRU может независимо хранить его тело. Пусть R — доступные в одном из этих двух мест события из A. Новый метод хранит для f список исключений E и поддерживает инвариант **A = R ∪ E**. После чтения E равно множеству отсутствующих тел. После повторного появления тела в LRU список вправе содержать лишнюю ссылку на это уже доступное событие. Все ID внутри E остаются элементами A.

- Новое событие с f сразу появляется в B8. Оно включается в A и R одновременно. Если кеш хранит только исключения, ни одну запись по затронутому файлу обновлять на этой операции не требуется.
- При потере последней локальной копии ID переходит из R в E для каждого файла, который действительно содержался в теле. При совпадении ключа обновляется только резидентная запись этого файла. Если сами исключения вытеснены, следующее чтение обращается к полному списку SQLite. Если LRU-пакет повторно вытесняется, проверка канонического varint исключает дубликат ID.
- Метод получает событие об утрате B8 прямо в месте удаления тела последним владельцем. Расход на B8, формирование уведомлений и обработку последующих вытеснений LRU включён во время обновления или вызвавшего их чтения. При запросе семантическая принадлежность файла определяется по закодированным ID внутри резидентных тел. Дополнительной таблицы «файл → все кешированные тела» нет.
- Если каждое исключение уже имеет доступное тело, весь ответ можно собрать из горячего графа и LRU. Прямой путь суммирует эти тела, восстанавливает хронологический порядок повышения в LRU и сохраняет пустой остаток. На 1 КиБ он использован в 148 из 485 и 211 из 721 запросов. После каждого запроса отдельный повтор сравнивал **все ключи, тело каждого пакета, их порядок и множество локально известных файлов**, получено 4 824 совпадения полных состояний при двух лимитах. [Реализация](residual.py) · [Прямое чтение](resident_hit.py) · [Аудит состояний](stream-audit.json)

## Основной эксперимент

Использованы все шесть репозиториев R60 и все шесть R59, плотное расписание B. Подтверждения записей предшествуют изменениям в памяти. Каждый метод обслуживает отдельный B8 и LRU того же размера. Методы читают одну и ту же прогретую физическую SQLite на одинаковых префиксах. Порядок методов для каждой операции и порядок проектов рандомизированы. Пять блоков измеряют изменчивость времени. Разные запросы одного репозитория статистически зависимы. Следующие значения относятся к двум новым реализациям и ранее опубликованному коду в этом репозитории. Столбцы — независимые медианы по пяти суммам времени. Медиана суммы может отличаться от суммы двух медиан. У основного метода на R60 три победы по трафику и три равенства с полным списком. На шести R59 такая же разбивка, затраты 16 935 против 22 186 байт. На R60 произошло 782 вставки ID исключений при 1 КиБ, для обработки уходящих тел LRU декодировано 2 190 байт. При входе в обработку уведомлений LRU наибольшая наблюдавшаяся очередь — 43 ссылки; B8 выдал до трёх тел за одну операцию. Это временные ссылки на объекты, ждущие обслуживания. Постоянный лимит 1 или 4 КиБ относится к сериализованным записям LRU, сверх существующего B8. Размер объектов Python и полный RSS приложения — отдельные величины. [Исходные измерения](runs.json.gz)

## Более сильные контроли

Первая дополнительная серия показала, что при таком улучшении контроль обгоняет вариант «только исключения» по времени: на R60 это 37,84 против 40,45 мс. На шести R60 выбранное прямое чтение при 1 КиБ заняло 38,16 против 38,75 мс у компактного полного кеша (9 187 и 11 646 байт). На шести R59 — 53,27 против 55,89 мс (16 935 и 22 191 байт). Во всех пяти блоках по 12 проектам прямая реализация сократила измеренное время относительно компактного полного кеша, разность от −3,97 до −1,95 мс. Одновременно B8-only быстрее, а время абсолютного полного списка сопоставимо. Реализация B8-only в этой таблице накапливает абсолютные ID для всех негорячих событий. Родственный эксперимент с дополнительным выбором сжатого представления B8-only даёт 10 863 байта на R60 и 20 705 на R59, тоже выше 9 187 и 16 935. Абсолютные времена разных стендов между этими исследованиями сравнивать нельзя. Вывод ограничен расходами чтения SQLite и локальным временем на данном компьютере. ## Граница корректности

Отказ от числа |A| требует синхронной, гарантированной и полной доставки уведомлений об утрате последней локальной копии тела. Известный пропуск последовательности коммитов, ошибка в обработчике, перезапуск процесса или известная утрата доставки требуют инвалидировать всю изменяемую память. После сброса первая выдача опирается на зафиксированную SQLite. Вариант с числом способен обнаружить неполное покрытие по мощности объединения.

В отдельном контроле скрытое удаление одного тела с подавлением уведомления **действительно испортило ранжирование** без числа и без сигнала об утрате. Для варианта с числом оно привело к точному чтению полного списка. Явная инвалидация полностью восстановила выдачу. Аудит также проверил 14 618 записей против прямого перечня всех событий, 3 267 ответов, четыре отката записи, четыре повтора, два физических открытия и 27 замеченных пропущенных уведомлений о коммитах по комбинациям режимов. Исключения обработчика в чтении и после подтверждённой записи отдельно вызвали сброс и точное восстановление. По всем трём временным сериям выполнены 229 140 сверок рангов на 1 206 уникальных пострестартовых запросах. Реальные задачи агента разработки, ретриверы других систем и end-to-end SOTA этими измерениями не оценивались. [Исходный код проверок](audit.py) · [Фактические итоги](audit.json)

## Воспроизведение

Достаточно стандартного Python и уже включённых в репозиторий зафиксированных историй. Команды запускаются из этой папки.

```sh
python -B bench.py --verify
python -B control_fast.py --verify
python -B resident_hit.py --verify
python -B audit.py --verify
python -B check_streams.py --verify
```

Для нового измерения выполните три первых команды без `--verify` в указанном порядке. Байт и ранги воспроизводятся детерминированно. Время нового измерения зависит от компьютера и фоновой нагрузки. В первичных файлах `runs.json.gz`, `control-runs.json.gz`, `hit-runs.json.gz` сохранены время каждого блока по проектам, per-query трафик, число SQL-вызовов и хеши эталонных рангов; одинаковые детерминированные ряды за последующие блоки сохранены один раз.
