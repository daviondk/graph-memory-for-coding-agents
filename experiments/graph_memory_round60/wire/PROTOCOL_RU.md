# Исключения в графовой памяти при настоящей передаче по TCP

До измерения зафиксированы шесть новых источников R60/panel (SHA архива 0e0590566b60acc4b15007c45550c42ee6f6287068c9693609196426555d16fa). Используем плотный график R58, 485 пострестартовых запросов. 3 парных блока, seed 60079, случайный порядок проектов и режимов в каждом блоке. Прежний двухоперационный TCP-протокол R59 для списков и тел выполняется на IPv4 loopback, TCP_NODELAY, с задержкой ответа 0 или 2 мс, с отдельной физической копией одного SQLite-префикса для каждой ветви. Сравнение exact (сжатый полный список), XOR и R60 notify при 1 и 4 КиБ поверх общей B8. Первичная метрика — сумма реально отправленных и принятых TCP application frames, включая заголовки двух направлений, при 1 КиБ. Сверяем число RTT, хеши потоков на двух концах, точность пар ID/балл и исходные SQL BLOB для каждого запроса с локальным опытом. Время чтений и обслуживания кеша после каждой подтверждённой записи, время поиска возможных вытеснений из B8 и всего смешанного прохода сохраняем отдельно; общие исходные записи проходят локально у писателя как и в R59. Установка соединения измеряется отдельно. Тайминги одной машины иллюстративны.

Дополнительный интерфейс закрывает полный top-8 на стороне сервиса за один RTT. Приоритет равных баллов использует все видимые файлы и частоты в последних 32 исходных коммитах, включая однофайловые; полный исходный приоритет в архиве допустимых многопутевых событий отсутствует. В запросе передаём численность каталога (ID являются плотными) и более короткий из полного разреженного описания ненулевых частот и дельты предыдущего состояния данного соединения, оба с явными длинами/ID/значениями. Сервер хранит подтверждённый последний вектор приоритета, к клиентскому кешу 1/4 КиБ этот интерфейс не привязан. Он сам обращается к SQLite и считает ранжирование, возвращает только настоящие пары ID/балл. Все фактические запросы и ответы учитываются. Дополнительно рассчитываем нижнюю оценку длины такого же обмена при заранее разделяемом каталоге и точном текущем приоритете у сервера (только номер якоря + те же результаты); эта оценка не имеет цены предварительной синхронизации и не считается сравнимой технологией при исходном контракте. Если у сервера уже есть полный входной поток, интерпретируем результат отдельно. Варианты порядка, бюджетов и формата остаются фиксированными. Независимый пересчёт заголовков и SQL результатов, сохранение отрицательных исходов обязательны.
