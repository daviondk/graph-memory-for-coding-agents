# Сравнение с сильными представлениями списков событий

Для применения в статье недостаточно сравнить графовое дополнение только с полными списками в формате varint. Сопоставим его с нативным форматом Roaring Bitmap и точной компактной записью монотонных списков. Испытаем опубликованную библиотеку PyRoaring 1.2.0 с run_optimize() и канонической сериализацией, базовое кодирование Elias–Fano и двоичное интерполяционное кодирование. Быстродействие авторских поисковых индексов этим опытом не воспроизводится: SQLite и сроки жизни записей оставляем одинаковыми. Эталон включает сильную политику, которая по каждому полному списку сравнивает фактические байты всех трёх новых форм и прежнего лучшего из абсолютных ID, разностей и битовой карты, сохраняя кратчайшую форму. При каждом append разрешаем перекодировать список. Таким образом контроль получает доступ ко всем этим представлениям. Используем те же кодеки внутри графовых исключений в отдельной ветви, чтобы не сравнивать новый формат только с более слабым компрессором. Размеры управляющих тегов, границ и самих записей полностью включаем в лимит LRU. Зафиксируем размеры отдельных кодировок при фактических обращениях, раздельные байты списков/тел и точность рангов.

Панели — прежние шесть R59 и новые шесть R60, плотное и разреженное расписание, 1/4 КиБ. Первичное сравнение — суммарные байты SQLite «кратчайший полный формат» против «кратчайший полный формат или явно поддерживаемые исключения с теми же кодеками» на плотной панели R60 при 1 КиБ. Исходы этих двух условий ещё не измерены, но сама панель уже изучалась. Отдельно сопоставим оригинальный R60 callback с его версией с усиленным кодеком. Во всех вариантах один writer, равные реальные байты слотов и общее горячее состояние B8. Положительная разница означает преимущество по работе этого конкретного читателя, перенос на более крупные графы и целые движки требует отдельного эксперимента.
