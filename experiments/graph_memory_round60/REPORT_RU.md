# Графовая память с учётом вытеснений

В R59 выяснилось, что по числу событий и XOR их идентификаторов можно дёшево восстановить один недостающий ID. В новой серии исследовали произвольное число пропусков. Для каждого файла сохраняем доступные в горячем индексе и общем кеше события и короткую запись об отсутствующих. Когда последняя локальная копия события вытесняется, его ID добавляется в записи участвующих файлов. Полный сжатый список остаётся альтернативой, если он короче. Агент получает тот же список наиболее часто изменявшихся вместе файлов с теми же баллами. Само представление множества через дополнение имеет известные аналоги в БД. Измеряемое предложение — обновлять запись о связях при утрате последней локальной копии и выбирать между представлениями при фиксированном бюджете. [Механизм и проверки](coverage/REPORT_RU.md) · [Ближайшие исследования](PRIOR_ART_RU.md)

## Основной результат

При дополнительном кеше 1 КиБ на репозиторий динамические исключения сократили байты чтения из SQLite относительно двух исходных способов хранения. Результат сохранился после усиления кодеков и замены политики вытеснения. Полная история Git и горячий индекс последних восьми событий участника были доступны всем методам. Байтовый бюджет относится к сериализованным дополнительным слотам. В таблице плотный поток, где очередной файл запрашивается до записи соответствующего нового события. Расписания построены по реальным Git-историям, обращения боевого агента рассмотрены отдельно.

| Панель | Запросов | Полный сжатый список | Число + XOR | Динамические исключения |
|---|---:|---:|---:|---:|
| 12 ранее использованных проектов | 2 063 | 123 019 | 115 945 | **109 005** |
| 6 проектов зарезервированной панели R59 | 721 | 21 957 | 20 055 | **17 177** |
| 6 новых проектов | 485 | 11 531 | 10 465 | **9 213** |

На новых проектах выигрыш относительно полного списка составил 20,1%. Три проекта дали экономию, ещё три — равенство. Из 2 318 байт общего преимущества 1 505 пришлись на TOML Kit. При 4 КиБ полный список и исключения передали по 4 322 байта. На тех же шести проектах при 45 редких запросах — по 2 525 байт при обоих бюджетах. Разметка графа и ранги сверены независимо. Для панели зафиксированы и дважды проверены 3 566 переходов Git без загрузки текстов файлов. [Паспорт шести проектов](panel/REPORT_RU.md) · [Поштучные данные 48 расписаний](coverage/runs.json.gz)

## Вывод для статьи

Самый устойчивый результат — точное обслуживание запроса к графу при малом кеше и длинной истории, где много событий повторно встречаются у разных файлов. Полезное различие между методами можно увидеть непосредственно в SQLite. В примере Tablib кеш уже содержит 38 из 40 требуемых событий. Благодаря двум сохранённым адресам агент получает оба недостающих тела за 8 байт. Если события были вытеснены без обновления записи, точный резервный путь читает ещё 49 байт. Оба варианта возвращают одни и те же восемь файлов. [Рабочая рукопись, 4 страницы](manuscript/paper.pdf) · [Интерактивный пакет с реальным запросом](release/README.md) · [Видео](walkthrough/walkthrough.mp4)

Сокращение байт графового хранилища воспроизвелось на нескольких панелях и сильных контролях. Выигрыш по времени зависит от реализации и режима. На коротких редакторских сессиях основной эффект не воспроизвёлся. Маршрутизация дорогого читателя экономит обращения на полном Lite, но превосходство по качеству решения задач над опубликованной SOTA пока не доказано. Для дальнейшего выбора важны нагрузки с длинными **реально наблюдавшимися** возвращениями к репозиторию и стоимость доставки изменений для нескольких одновременно открытых клиентов.
