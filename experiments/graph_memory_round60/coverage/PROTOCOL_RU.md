# Явные исключения для точного списка событий файла

Фиксация до измерения результата. Из предыдущих R59 известны результаты полных списков и XOR на 12 внешних и шести недавних репозиториях. Проверяем альтернативу: в общем LRU записать число всех событий якоря и сжатый список E тех номеров, которые нельзя получить из резидентных тел. Общий индекс SQLite неизменяемых событий остаётся точным. Во время запроса для файла f известное множество R_f получается из его адресов в B8 и проходом по действительно резидентным телам LRU с проверкой участника. Исключения всегда принадлежат этому файлу. Если |E ∪ R_f| совпадает с сохранённым числом событий, объединение даёт точный полный список; иначе читаем список SQLite. Запись выбирает меньшее из этого пакета и полного списка, при равенстве выбираем полный. Формат исключений платит один байт типа, varint числа, затем, для непустого E, лучший из полных форматов R59 (abs/gap/bitmap и его тег). Ключ, длина и запись в общем LRU оплачены по правилам R59. При формировании E ещё удерживаемое в B8 или дополнительном кеше тело можно пропустить. Если собственная вставка записи вытеснит тело, это вытеснение тоже подлежит обработке.

Основной вариант поддерживает E при утрате последней копии тела из B8 или LRU. Краткоживущий список вытесненных ID/тел получает информацию прямо из изменяемого кеша. Если копия не осталась в обоих уровнях, декодируем именно вытесненное тело и для каждого его участника с резидентным пакетом добавляем ID в E. Вставка/расширение исключений может вытеснить новые тела или сам пакет. Обрабатываем каскад до пустой очереди, без постоянного дополнительного обратного индекса. Если тело вновь подгрузилось, старое исключение можно сохранить до следующего запроса, поскольку запрос использует объединение. Новое принятое событие увеличивает счётчик каждого резидентного пакета его участников; тело уже находится в B8. При повторной доставке/откате модификация пакета не выполняется, при потерянном процессе кеш сбрасывается. Простой абляционный вариант не обрабатывает вытеснения, но проверяет мощность объединения при каждом чтении и при необходимости безопасно возвращается к SQLite. Контроли в том же проходе: полный сжатый список и R59 count+XOR с тем же пулом B8 и бюджетом.

Основная нагрузка: заданные R57/R58 12 внешних проектов, прежний плотный режим, 1 024 байта. Конкретное предсказание — динамические исключения уменьшают сумму реально полученных из SQLite байтов полных списков и тел по сравнению с XOR. Контроль относительно сильного полного сжатия и поражения по проектам обязательны. Далее без изменения правил измеряем все шесть R59 holdout и всю группу из R60/panel/events.json.gz, когда подготовка источника завершится. Дополнительно исходный разреженный режим и 4 096 байт. Граница по половине принятых событий R58, запрос до добавления его коммита, равные топ-8 ID/баллы относительно битового эталона. Измеряем actual SQL запросы, BLOB, резидентную packed-RAM, объём сканирования тел при проверке, количество и работу обновлений на вытеснениях, пиковую временную очередь. Один технический проход по всем методам для детерминированных метрик; время иллюстративно, сравнительного вывода о latency не делаем. Отдельно проверяем ошибку после вытеснения из двух уровней, откаты, повторную доставку и каскад при ограничении памяти. Сохраняем неудачные исходы наравне с выигрышами.
