# Выбор представления по ожидаемому вытеснению

Проверяем, можно ли выбрать представление списка событий по текущему содержимому кеша, не подбирая лимит переключения на новой панели. Используем неизменяемые тела событий SQLite, общий горячий слой B8, упакованный полный список и число + XOR из R59. Единственное изменение — правило выбора формы каждой записи в кеше непосредственно после очередного чтения. При добавлении нового события продолжает действовать правило обновления R59. Архив и все восемь файлов с баллами остаются точными. Никакие будущие запросы или разметка не доступны читателю.

Для каждого из двух форматов моделируем помещение записи как самой недавно использованной. Последующий поток новых различных объектов до следующего чтения представим случайным объёмом Z с равными весами для целых значений 0,…,C−1, где C — байтовый лимит. Это простая модель давления на кеш, а не измеренное распределение. Если объекты между двумя чтениями больше не затрагиваются, то запись, для которой суммарный размер всех более свежих записей вместе с ней равен W, переживёт ровно L=max(0,min(C,C−W+1)) значений Z. Самый свежий кандидат получает W, равное его полному сериализованному размеру. Старое представление того же ключа при расчёте удаляется. Если новый слот превышает весь лимит, его время жизни равно нулю, а остальные записи сохраняют исходный относительный порядок.

Полный список избавляет от чтения адресов в течение собственного L. Для сводки нужны все адреса, кроме максимум одного. Считаем L=C для горячих тел и L=0 для отсутствующих. Второе снизу значение L среди событий запрошенного файла даёт длину интервала, где декодирование возможно. Берём минимум этого числа и срока жизни сводки. Для списков длины 0 или 1 покрытие равно C. Ценность метаданных — срок успешного ответа, умноженный на длину соответствующего BLOB адресов в SQLite. Ценность тел — сумма произведений фактических размеров кэшированных BLOB на срок их выживания. Тела в общем горячем слое уже доступны и получают нулевую дополнительную ценность. По основному правилу все прочие тела считаются потенциально полезными по одному разу. Специальный контроль включает только тела данного файла. Выбираем больший суммарный балл. Ничья остаётся за полным списком. В модель не входят будущие записи и повторные касания, стоимость других списков и вычислений. Реальная точность ответов обеспечивается независимым дочитыванием SQLite. Дополнительная память правила состоит из временных вычислений внутри запроса, постоянного обученного состояния нет.

До первого расчёта исходов зафиксированы старые 12+6 проектов для разработки и отчётности, а также шесть ранее не использованных историй, которые отдельно фиксирует [панель](../panel/PROTOCOL_RU.md). У каждого репозитория два расписания R59, плотное и редкое. Основной показатель — сумма байт BLOB из SQLite на новом плотном потоке, включая оба предписанных бюджета 1 и 4 КиБ с равным весом одного исполнения каждого запроса при каждом бюджете. Основной соперник выбирает XOR на 1 КиБ и полный список на 4 КиБ. Это сильный заранее фиксированный соперник по итогам R59. Покажем обе части отдельно, число выигранных и проигранных репозиториев, обычные всегда-полный, всегда-XOR, R59-правило немедленной восстановимости, совместный обычный LRU, а также вариант расчёта только по телам данного файла. Проверим чувствительность на 512 байтах и 2 КиБ. Для этих вторичных двух лимитов правило по размеру использует XOR до 1 КиБ включительно. Время всего чтения, количество SQL, байты тел и адресов и распределение решений будут описательными. Сохраним данные каждых запросов и проверим неизменность всех ответов и размеры упакованных записей. Положительный результат относительно одного слабого режима ещё не означает выигрыш относительно лучшей фиксированной политики.
