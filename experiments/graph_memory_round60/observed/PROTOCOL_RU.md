# Восстановление графа на наблюдавшихся чтениях SWE-agent

Источник — обезличенные 108 ранее опубликованных сессий R57, два агента на одних 54 безопасных задачах SWE-bench Verified. Анализируются только проекция пути и показанные номера строк; размеры и идентификаторы содержимого строк удаляются до анализа. Данные этих сессий уже использовались в других опытах. Данный результат проверяет перенос способа представления posting lists на другое происхождение графа; выборка не является новой независимой выборкой поведения агентов.

**Наблюдение и смоделированная операция.** В каждом непустом окне редактора агент реально увидел определённые строки одного файла. Разбиваем файл на блоки по 16 строк начиная со строки 1. Узел — (путь, номер блока); событие — множество блоков, действительно показанных вместе в одном окне. До записи текущего окна в граф выполняем один смоделированный запрос для блока первой показанной строки (численно минимальный номер показанной строки). Эта координата берётся из фактического ответа редактора, она не предсказывается и не приписывается агенту как ранее выполненный SQL-запрос. Запрос возвращает до восьми других известных блоков, ранжированных по числу прежних совместных показов. Разрешение равенств — частота присутствия в последних 32 окнах и стабильный локальный ID. Новые узлы регистрируются только после запроса. Даже одноблочное окно генерирует запрос, запись события требует 2–64 разных блоков. Все показанные блоки обновляют частоту, включая одноэлементные окна. Пропускаем пустые показы, сколько их было — укажем. Обычные записи истории совместного показа остаются истинными после правки; они не свидетельствуют о современном содержании этих координат. Вторая, заранее заданная разбивка по четыре строки проверяет чувствительность к подробности адреса.

Ни одна сессия не видит историю другой. После floor(W/2) непустых окон закрываем базу, открываем её заново с пустой оперативной памятью; при нечётной длине во вторую часть входит ещё одно окно. Для каждого следующего показа общая SQLite-база и точный ответ одинаковы у всех политик. Применяем читатели R59 без изменения алгоритмов: обычный joint LRU списков и тел, полные сжатые postings (exact) и компактное число+XOR с fallback к точному posting, а также count-only и bodies-only как контроли. Общий недавно записанный хвост B8 для каждого участника поддерживается в процессе. Каждый отдельный LRU подсчитывает свои служебные поля и тела. Лимиты 1 и 4 КиБ; 256 байт — вторичный стресс. Виртуальная цена запросов/страниц диска, холодный старт ОС и исправление задачи не измеряются.

**До вычисления** первичный показатель — разность суммы возвращённых SQLite BLOB между XOR и exact при 1 КиБ на блоках 16 строк за все продолжения. Публикуем отдельные суммы байтов полных posting и тел, фоновую работу и попадания, число точных случаев одного отсутствующего ID, парные результаты по сессиям, issue и проектам. Показываем, сколько якорей ранее наблюдалось, сколько использовалось как якорь до и после перезапуска, какой размер posting для них существовал непосредственно перед запросом. Считаем долю исходов с расхождением, включая нули. 95% эмпирический парный bootstrap средней разности байтов на issue с 20 000 повторов, seed 60031, два исполнителя одного issue едины. Проверяем каждый ранжированный ID и балл прямым перебором всех более ранних гиперрёбер. Для условной диагностики заранее выделяем вопросы с предшествующим обращением того же якоря в текущем процессе, а также с ≥4 действительными прошлыми совместными показами якоря. Масштаб распределения и нулевой прирост сообщаем независимо от знака. Для интерпретации используются коррелированные трассы действий и виртуальная задача чтения графа, а не новые запуски LLM.
