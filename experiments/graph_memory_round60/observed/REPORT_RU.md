# Графовая память на адресах, которые действительно читал SWE-agent

На 108 сохранённых сессиях SWE-agent политика «число + XOR», полные сжатые списки и обычный joint LRU прочитали **по 1 668 байт** из SQLite при лимите 1 КиБ. Для первичного варианта графа с 16 строками в блоке стоимость XOR и полных списков совпала в каждом из 436 пострестартовых запросов. Все ранги и баллы у всех методов совпали с прямым подсчётом на историческом префиксе. [Протокол, зафиксированный до расчёта](PROTOCOL_RU.md) · [Полные результаты](results.json)

**Как построен запрос.** Восстановлены восемь проектов, 54 задачи и два исторических исполнителя на каждую задачу. В 102 сессиях были непустые показы, всего 822 окна. Шесть сессий без показов оставили в анализе; окна есть у 53 задач. Медиана составила пять окон на сессию, максимум — 46. Из пути и показанных номеров строк строим событие совместного просмотра блоков одного файла. После половины окон закрываем и вновь открываем SQLite. Для каждого следующего фактического показа блок его первой строки становится якорем моделируемого вопроса: какие прежние блоки наблюдались вместе с ним? Вопрос вычисляется перед добавлением текущего показа. Эти SQL-запросы созданы исследователями по наблюдаемым адресам; исходные агенты их не выполняли. Узлы относятся к координатам файла, а само ребро описывает исторический показ и не служит свидетельством неизменности содержимого после правки.

Плата в таблице — байты списков и тел событий, возвращённые SQLite. Лимит относится к дополнительному сериализуемому LRU. Общий для политик индекс последних восьми записей и вспомогательные структуры Python не входят в эту квоту. Исходные тексты файлов и идентификаторы содержимого строк не использовались.

**Были ли повторные обращения?** Для блока 16 строк на момент запроса 299 якорей уже встречались как узлы; 224 ранее использовались как якорь хотя бы в одной части сессии. После перезапуска 117 запросов повторяли якорь текущего процесса; они приходились на 37 сессий. Только 59 запросов имели хотя бы четыре прошлых совместных показа, а у 149 не было ни одного. На повторных якорях exact и XOR потребовали по 22 байта, в группе с не менее чем четырьмя предшествовавшими событиями — по 305 байт. Для проверки числа и XOR читатель 30 раз установил, что уже имеет полный набор, и проверил 2 797 байт резидентных тел, не сократив трафик относительно сжатых списков. Зато сам факт хранения posting в памяти сэкономил 344 байта против хранения одних тел (317 против 661 байта списков, тела в обоих случаях 1 351). [Исходы каждого запроса](queries.json.gz)

**Эффект стресса локализован.** При блоке по четыре строки и квоте 256 Б XOR прочитал на 148 байт меньше, чем полный список (1,90%). Тела сократились с 7 369 до 7 216 байт, списки выросли с 429 до 434. Из 436 запросов только семь различились по цене. Две сессии с ненулевым итогом принадлежат одному проекту и одному исполнителю. В sympy-15809 получено −153 байта, в sympy-13647 — +5 байт. Парная средняя разность на задачу −2,74 байта, 95% эмпирический bootstrap-интервал [−8,50; +0,28]. Первичное сравнение на 16 строках имеет 54 нулевые разности на задачу, поэтому его эмпирический интервал [0; 0] описывает лишь эту выборку. Данные объясняют, почему наблюдавшиеся для длинных плотных Git-историй преимущества не проявились в коротких редакторских сессиях при обычной квоте.

Для воспроизведения из каталога: `python -B replay.py --verify`. Выполняются реальное переоткрытие SQLite, проверка точного Top‑8 перед каждым добавлением, контроль вместимости, расчёт статистик, повторное сравнение с сырыми строками и сводкой. Исходные действия агентов и их патчи не исполняются. Воспроизводится работа подсистемы памяти на фиксированных действиях; влияние на решение задач и время работающего агента здесь неизвестно.
