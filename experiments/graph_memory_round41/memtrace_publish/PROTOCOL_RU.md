# Материализация проверенного фрагмента в MemTrace на новой ревизии

Цель — проверить узкий стык между адаптером обновления памяти и исходным API MemTrace на Git SHA 5508f8be81025d8aa90726b1e06aef4ea484e577. Программа на полностью синтетических последовательностях ASCII сохраняет прежнее наблюдение CODE_OBSERVATION, исполняет нативное обновление ревизии, затем просит точный текущий фрагмент через RecallService.fault. Проверяем, вернул ли API содержимое запрошенного ключа внутри нативного RecoveredContextBlock, его источники, состояние покрытия, надпись о ревизии, стоимость чтения. Прогона языковой модели здесь нет.

Связанные предпосылки. Из доверенной обёртки старого чтения доступны путь, номер ревизии, хеш версии, смещения, хеш точных сохранённых байтов. Из доверенного процесса записи доступны путь, старая и новая ревизии и хеши, старый интервал замены, длина вставки и длины версий. Для изоляции требований целостности тестовый производитель ставит HMAC с постоянным открытым тестовым ключом. Полные версии доступны только создателю события и независимой сверке. При запросе адаптер получает старое наблюдение и две квитанции; повторно файл он не читает. Квитанция описывает точно одну непрерывную замену, атомарно породившую назначенную новую версию. При одновременных правках, скрытых преобразованиях или недостоверных событиях гарантии требуют другого контракта.

Предопределены пять ситуаций переноса. Замена после фрагмента, замена до него с ростом длины, замена до него с уменьшением длины, вставка точно в левую границу фрагмента и вставка точно в правую границу. Предопределены отказы при изменении с пересечением, при пересечении с теми же байтами, повреждённом старом содержимом, несовпадении пути старого наблюдения, несовпадении хеша старой версии, неверной предшествующей ревизии, неверной целевой ревизии, ином пути правки, нарушении подписи записи и при отсутствующей квитанции записи. Каждая ситуация повторяется на фрагментах 48 и 128 байтов, всего 30. Порядок лексикографический. Первичный исход — точная доставка старых байтов на новой ревизии только в десяти предусмотренных положительных случаях. Фиксируем и необоснованную выдачу в каждом из двадцати отказов. Отдельно проверяем лемму переноса на всех непустых интервалах строк длины от 1 до 12 и всех однократных заменах, включая граничные вставки и удаления.

Все три режима получают одинаковые синтетические варианты. В первом исходному хранилищу передаются только исходные данные и событие изменения файла. Во втором адаптер проверяет квитанции и при успехе дописывает через PageStore новое EvidenceDraft с Authority.DERIVED, подтверждениями события прежнего чтения и записи, координатами и содержимым. В третьем старое содержимое безусловно материализуется на новой ревизии. Третий режим показывает, способна ли проверка источника хранилища самостоятельно отклонить непроверенный перенос. Сравниваем также отдельно факт совпадения возвращённых байтов с текущим текстом и достаточность сертификата. Это функциональные случаи, целенаправленно покрывающие границы алгоритма; интервалы статистической точности популяционного эффекта для них не определены.

Принимаем доставку только при COMPLETE, наличии одного факта с ожидаемым ключом и текущей ревизией и сверке возвращённого содержимого. Повторные запросы после повторного открытия прогоняем в каждом режиме. Для каждой строки сохраняем хеш исходного результата, наблюдаемую стоимость чтения, причину допуска или отказа и независимую оценку. Сравнение разграничивает исходные способности MemTrace и наш внешний адаптер, который сам производит доказательство переноса.
