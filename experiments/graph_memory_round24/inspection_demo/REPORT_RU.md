# Интерактивный разбор одного чтения памяти

[Открыть автономный демонстратор](inspection.html) · [Снимок экрана](inspection.png)

Посетитель выбирает один из 19 обезличенных вопросов ISETrace, способ передачи памяти и правило одного следующего чтения. Для каждого сочетания показаны координаты эталонных доказательств, уже покрытые интервалы, точный вклад нового чтения и оставшиеся пробелы. Рядом доступны адрес, физический размер передачи, стоимость в WordPiece и параметризованный SQL-запрос к снимку записи. Все шесть вариантов для вопроса доступны одновременно в сравнительной таблице.

### Что видно на первом примере

В памяти для вопроса Q-0792AA4E уже находились 116 из 207 эталонных символов поля 88. Слияние у отправителя и выбор первого лексически подходящего окна с ожидаемым приростом вызвали чтение диапазона [0, 553). Из возвращённых 553 символов 292 ранее отсутствовали в памяти. Среди них были все 91 недостающих эталонных символов [132, 223). Получилось полное покрытие при расходе 2 048 WP на исходную память и 256 WP на возвращённый фрагмент. Такое же правило для раздельных исходных записей добавило 80 эталонных символов. Чтение по обычному BM25 на этом вопросе добавило 0 при суммарном расходе 2 114 WP.

### Состав снимка

| Объединение у получателя, receiver | 19 записей R23 | 19 дополнительных проверок R24 |
| Объединение до передачи, sender | 19 записей R23 | 19 записей R23 |

После выбора вопроса источник и ранжирование фиксированы. В режиме receiver получатель объединяет только уже доставленные части. В режиме sender объединение предшествует токенизации и оплате контекста, поэтому при том же лимите могут попасть иные символы. Система показывает отдельно входящую передачу, контекст внутри получателя и стоимость возвращённого чтения. Использование варианта first_positive может приводить к пропуску обращения. В этом случае расход на чтение равен нулю и интерфейс явно указывает, что SQL-запрос отсутствует.

Панель сформировали для иллюстрации поведения. В ней 12 примеров по хешу из оставшегося набора, три примера дополнительного полного покрытия, два пропуска чтения и два случая повторного получения уже известного текста. Выбор демонстрационных случаев учитывал завершённые результаты R23. Доли в панели не оценивают качество на всём бенчмарке. Для 38 новых сочетаний политика выбора использует только видимый текст, длины полей и исходный вопрос. Выбор и оплаченные результаты зафиксированы до вычисления покомпонентного покрытия в R24. ### Проверка результата

- Независимый пересчёт построил множества исходных символов для всех 114 вариантов. Для каждого проверены добавленные и отсутствующие эталонные диапазоны, повторно доставленные символы, величина физического чтения и стоимость заголовка. Отдельный путь расчёта заново выбрал адреса для 38 дополнительно проверенных сочетаний. Открытия BM25 сопоставлены с исходными пообъектными отчётами во всех 57 его вариантах. Для 38 sender-режимов проверены метрики расширения памяти по архиву R23. [Машинная проверка](verification.json)
- Chromium проверил все 114 состояний в локальном интерфейсе SQLite и все 114 в автономном файле. Сверены числовые показатели, каждое отрисованное поле и символьный интервал, SQL, переключение вопроса и режима. Для экрана шириной 390 px проверено отсутствие горизонтального переполнения страницы; автономная версия не запрашивает сеть. [Протокол браузерной проверки](browser-receipt.json)

### Запуск и воспроизведение

Для автономного просмотра достаточно файла [inspection.html](inspection.html). Он содержит зафиксированные ответы для всех 114 действий. Запуск `python serve.py` в этом каталоге поднимает версию SQLite по локальному адресу `http://127.0.0.1:8774/`. Стандартной библиотеки Python достаточно. База открывается в режиме `mode=ro&immutable=1` с `PRAGMA query_only=ON`, API принимает только GET для фиксированных маршрутов и заранее известных способов чтения. Произвольный SQL не принимается. В автономном файле отображается SQL, который для этого адреса был выполнен при его экспорте. В сетевом варианте этот же SELECT выполняется при загрузке сохранённых состояний вопроса.

Снимок SQLite занимает **90 112 байт** и содержит только обезличенный идентификатор вопроса, его категорию, ID полей, числовые полуинтервалы и метаданные расхода. В интерфейсе и базе отсутствуют исходный текст вопроса, содержимое трасс, команды, пути и тело возврата. Опубликованный идентификатор даёт возможность переключать способ чтения, удерживая тот же вопрос. Интерактивность ограничена фактически записанными действиями.

Сборка из локальных исходов использует окружение Python с пакетом tokenizers и исходные данные R23 на диске D. Последовательно выполняются `build.py generate`, `build.py build`, `export_offline.py` и `verify.py`. Для браузерного теста запускается `node browser_check.mjs` с доступным Chromium и Python. Переменные CHROME_PATH и PYTHON задают исполняемые файлы при необходимости. [Исходный сервер](serve.py) · [Проверка в браузере](browser_check.mjs)
