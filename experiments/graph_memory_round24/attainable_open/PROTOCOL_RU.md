# Какую долю пропусков вообще можно исправить за одно чтение

На ISETrace и MultiDoc2Dial уже измерены реальные правила выбора следующего адреса. На известных исходах проводим диагностическое исследование достижимого результата. В обоих корпусах используем прежний выбор смешанного масштаба, объединённые координаты, не более 2 048 входных токенов и один ответ до 256 токенов. Считаем вопросы, исходно не покрытые полностью, и четыре разных ограничения.

1. При неограниченной длине чтения достаточно ли одного поля в базе, чтобы покрыть всё оставшееся?
2. Встречается ли это поле в исходном контексте? Эти два условия дают теоретические верхние границы для одноисточниковой операции.
3. Может ли хотя бы одно из реально допустимых 128-токенных видимых окон дать полный набор за фактические 256 токенов вместе с адресом? Перебираем все допустимые адреса только для диагностики. Это точный потолок для селектора с этим меню и данным API.
4. Стало бы полное покрытие возможным при адресе непосредственно на первом недостающем символе и том же ограничении ответа? Отдельно считаем уже видимое и любое поле. Этот вариант требует эталона; он иллюстрирует потенциал позиционного индекса. Из-за особенностей токенизации не объявляем его строгим потолком для всех произвольных начальных позиций.

Для каждого корпуса записываем число доступных исправлений, достигнутые доли для уже замороженных политик и классификацию пробелов. Эталон участвует в этом анализе намеренно. Ни одна рассчитанная здесь навигационная подсказка не используется как прогноз модели. Первичные результаты не содержат текста документов или журналов. Ниже термин «исправление» обозначает дополнение недостающего доказательства в выдаче.
