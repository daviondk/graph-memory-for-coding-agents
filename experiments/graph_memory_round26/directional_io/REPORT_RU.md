# Реальная цена двустороннего чтения в SQLite

Когда границы двух текстовых диапазонов уже известны, их выдача одним SELECT по первичному ключу занимала 11,15 мкс против 15,70 мкс при двух отдельных SELECT. На парных измерениях отношение времён составило 0,738 [0,724; 0,751]. Когда сервис сам определяет конец каждого диапазона по токенному бюджету и проверяет итоговую строку, пакет из двух выборок и два последовательных SQL-запроса дали 2,720 и 2,713 мс; отношение 0,993 [0,974; 1,011]. Локальная выборка с тем же токенизатором сократила передаваемый объём в 5,09 раза относительно загрузки поля целиком. Измеримой экономии полного времени в строго согласованном контроле она не дала.

### Стенд

Использованы реальные операции R25, по 96 вопросов ISETrace, MultiDoc2Dial и SQuAD с двумя непустыми адресными диапазонами. В SQLite сохранены только 215 выбранных источников, включая 124 с символами вне ASCII. Начальных текстов 2 694 158 байт в UTF-8, база заняла 3 014 656 байт. На страницах таблицы текстов занято 2 854 912 байт, на таблице из 10 574 контрольных символьных смещений — 155 648 байт. Медианное поле на запрос — 8 706 байт. Пользовательский диапазон определён в кодовых точках Unicode. Перевод в байтовые смещения требуется для низкоуровневого BLOB-доступа.

Каждый оператор получал тот же ключ и адреса. Число диапазонов у правого и двустороннего чтения различается: в первом случае это один исходный фрагмент до 256 токенов, во втором — два фрагмента до 128, каждое со своим заголовком. Для самосравнения вариантов двустороннего чтения проверены идентичность выданных байтов, границы UTF-8 и совместная строка. По плану SQLite обе SQL-формы выполняют обращение по INTEGER PRIMARY KEY. Прогон выполнялся локально на Windows, Python 3.12.13, SQLite 3.50.4, mmap выключен, cache_size 8 MiB, без сетевого транспорта. Система выполняла параллельные исследовательские задачи.

Для каждой строки — медиана индивидуальных медиан, 21 повтор на тёплом соединении, 3 первых запроса на заново открытом соединении. Интервалы для отношений получены из 5 000 парных бутстрэпов по 215 полям. Относительно одного полного правого диапазона пакет двух стоил на 22,3% больше запросного времени, парное отношение 1,223 [1,199; 1,246]. Экономия пакетной SQL-команды относительно двух отдельных воспроизводилась во всех трёх корпусах: отношения 0,763, 0,749 и 0,702. С прогревом кэша ОС, но на новом SQLite-соединении, отношение 0,859 [0,839; 0,879]. С включёнными открытием и закрытием — 0,967 [0,954; 0,980].

Одно BLOB-открытие ускоряет два чтения при готовых байтовых адресах. Оплата Unicode-перевода с помощью разреженного индекса увеличила число обращений к нему в среднем до 3,87 и дала отношение времени к пакетному TEXT-запросу 1,48 [1,33; 1,64]. Адресное пространство интерфейса важно для честного сравнения.

### Сервис знает только начальные точки и токенный лимит

Во втором опыте сервис получил ID поля, две границы **видимого** фрагмента и размер поля. Конечную точку допустимого ответа определял настоящий WordPiece-токенизатор. Локальный оператор начинал с 2 048 символов около каждой нужной границы. В этой выборке расширять окно дополнительно ему не потребовалось. Время включает выборку, преобразование UTF-8, определение границ под лимит, сборку строки с двумя заголовками и проверку её полной токенной цены. Отбор источника и генерация ответа агента остаются за пределами этих чисел.

| Полный оператор | Тёплый запрос, мс | Первый запрос нового соединения, мс | Байт от SQLite |
|---|---:|---:|---:|
| Двусторонний, локальные окна одной SQL-командой | 2,720 | 3,180 | 3 268 |
| Двусторонний, локальные окна двумя командами | 2,713 | 3,113 | 3 268 |
| Двусторонний, всё поле и исходный алгоритм токенизации | 3,412 | 4,228 | 16 630 |
| Только вправо, локальное окно | 1,928 | 2,247 | 1 630 |
| Только вправо, всё поле и исходный алгоритм токенизации | 2,492 | 2,887 | 16 630 |

На парном измерении локальный двусторонний сервис занимал в 1,585 раза больше времени правого [1,504; 1,678]. В эксперименте с загрузкой всей строки исходная функция обработки начинает с окна другой длины. Поэтому отдельно повторили сравнение с **строго одинаковым** токенизатором, логикой границ и внутренними окнами 2 048 символов: один SELECT ограничивает строку в SQLite, второй возвращает всё поле и выполняет те же срезы в клиенте. Время — 2,816 против 2,804 мс, отношение 1,010 [0,997; 1,023], объём из SQLite — 3 268 против 16 630 байт. Выигрыш в переданных байтах сохраняется при одинаковых результатах и обработке. Общего ускорения token-budgeted выдачи на тёплом локальном SQLite этот контроль не обнаружил.

Проверено 62 208 обычных SQL/BLOB-операций, 8 640 обслуживаний с онлайн-определением границ и ещё 5 184 обслуживаний при согласованном токенизаторе. Холодный накопитель, тариф сети, реальный сетевой RTT и физические байты на диске не измерялись. Метрика байтов соответствует границе SQLite и клиентского Python. Это локальный профиль конкретного распределения адресов, а не прогноз времени облачной БД или LLM.
