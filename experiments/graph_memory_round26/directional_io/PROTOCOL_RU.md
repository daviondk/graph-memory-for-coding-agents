# Физическая стоимость двух адресных диапазонов

Данные — зафиксированные реальные операции R25. Отбираем первые 96 по SHA-256(`direction-io-v1/` + query ID) запросов каждого из ISETrace, MultiDoc2Dial и SQuAD, для которых в ответе both были две непустые стороны. Источник — только фактически выбранное поле для каждого из 288 примеров. В материализованную SQLite-таблицу попадут полные версии только этих полей, по одной записи на уникальную пару «источник, поле». Тексты и база остаются в приватном кэше на D, в каталоге отчёта сохраняем хеши и размеры. Бинарные результаты качества R25 при отборе не используются.

**Основное сравнение.** Для двух одинаковых диапазонов поля сравниваем один SQL SELECT по INTEGER PRIMARY KEY с двумя substr и два отдельных SELECT с одним substr каждый в одной локальной SQLite connection. Сильный технический вариант — получить всю TEXT-запись один раз по тому же ключу и нарезать ответ в клиенте. Отдельные ориентиры — один правый диапазон из настоящего правила right при бюджете 256 и одна правая половина от правила both. Для одного чтения в сторону и пакета двух параметрические запросы работают с теми же символьными координатами и общим исходным источником. Клиентские результаты проверяем побайтно как UTF-8 и с настоящими заголовками исходного чтения.

**Доступ по байтам.** Измеряем один и два реально открываемых дескриптора sqlite3_blob / blobopen и прямое позиционирование по байтам. Отдельно учитываем цену трансляции из исходных координат Unicode по разреженному индексу (каждые 256 кодовых точек) с обращением к БД. Без стоимости трансляции результаты относятся только к заранее известным байтовым адресам. Считаем байты, переданные библиотекой к клиенту: результат SQL, целое поле или диапазоны плюс чтение для границ. Физические обращения ОС к накопителю, сетевой RPC, токенизация, построение запроса и исполнение решателя не входят в измерение. Обоим вариантам переданы уже определённые адреса правого и левого пределов. На работающем сервере для поиска фактической границы токенного бюджета может потребоваться больше чтений.

**Нагрузка.** 21 повтор тёплой connection и 3 повтора первого обращения после открытия новой connection без shared cache и без mmap, OS file cache остаётся тёплым. Заранее детерминированное псевдослучайное перемешивание запросов и методов по каждому проходу. Для свежей connection показываем время запроса с подготовкой statement и отдельно открытие+запрос+закрытие. Для каждой пары задач вычисляем отношения медиан повторов, сообщаем геометрическое среднее парных отношений и 95% интервалы по кластерам уникальных полей с 5 000 bootstrap. Средние байты интерфейса, страницы базы и индекса, размеры полей и медианы латентности показываем отдельно. Логируем процессор, SQLite, Python, файл базы, план запроса и проверки выходов. Этот микроэксперимент не делает выводов о latency LLM или холодном диске.
