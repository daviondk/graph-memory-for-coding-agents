# Что происходит с памятью при переходе контекста к другому исполнителю

Четыре независимых процесса Python получили по 132 запроса к одним и тем же уже прочитанным эпизодам. На 528 вопросах по 48 статьям исполнители каждый раз возвращали тот же исходный адрес, что полный BM25. Когда каждому из них закрепили по две активные статьи и позволили хранить четыре эпизода, сырой журнал потребовалось загрузить **48 раз**. Когда на каждом следующем вопросе менялся исполнитель, понадобилось **528 загрузок**. На каждом раунде нагрузка всех четырёх процессов была одинаковой. Действительное число пересечений границы между процессами в трёх повторах и 14 конфигурациях составило 22 176 RPC поиска.

| Способ чтения, ёмкость 4 на процесс | Распределение | Байт SQLite → процесс на запрос | Загрузка сырых окон | Медиана запроса с IPC, мкс | p95, мкс |
|---|---|---:|---:|---:|---:|
| Полный разбор эпизода в локальном кэше | Закрепление | 851 | 48 | 103 | 758 |
| Тот же локальный кэш | Ротация | 9 359 | 528 | 869 | 991 |
| Общий индекс, получить только списки слов | Закрепление | 366 | 0 | 177 | 212 |
| Общий индекс, получить только списки слов | Ротация | 366 | 0 | 182 | 226 |
| Общий индекс и локальный кэш уже запрошенных слов | Закрепление | 87 | 0 | 142 | 204 |
| Общий индекс и локальный кэш уже запрошенных слов | Ротация | 366 | 0 | 187 | 233 |

В первом способе медиана и хвост ведут себя по-разному. Большинство закреплённых запросов обслуживаются из RAM. Однако в начале каждой статьи процесс должен разобрать все окна, поэтому p95 существенно выше, чем при чтении из общего B-tree. При ёмкости один эпизод обе политики маршрутизации вытесняли нужную статью к следующему запросу и дали 528 промахов. При ёмкости восемь ротация вызвала 192 промаха, по одному на каждую пару «статья, процесс». Автономный скрипт `reuse_distance.py` воспроизвёл каждый промах по расписанию до чтения времён и результатов. Это проверяемое следствие установленного размера рабочего набора. Для текущего расписания формула LRU точна: попадание происходит, если число **различных** других статей с прошлого обращения того же процесса меньше его ёмкости. Показан конкретный механизм роста затрат по мере смены исполнителей.

Во всех вариантах первоисточник и число RPC сохранены. У маршрутизатора один запрос в полёте. Локальный SQLite работает с прогретым кешем ОС; диск, внешний сетевой RTT и стоимость предварительной индексации сюда не входят. Кэш измерен в числе эпизодов. Разный объём эпизодов в байтах исследован в сопутствующей [проверке записи](../write_cost/REPORT_RU.md). Эксперимент проверяет реальное разделение оперативной памяти исполнителей. Для оценки способности агентов делать вывод по фактам нужен отдельный генеративный тест. В среде с подготовленными `query-views.sqlite` и `terms.sqlite` серии 25 выполните `python -B workers.py`, затем `python -B analyse.py` в копии каталога. Второй скрипт автономно перепроверяет поштучные исходы, идентичность адресов, хеш, равную загрузку четырёх исполнителей и времена технических повторов.
