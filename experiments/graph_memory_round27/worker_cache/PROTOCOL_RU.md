# Передача следующего вопроса между реальными процессами

Прошлая проверка моделировала сброс кэша при смене исполнителя. Здесь четыре независимых процесса с разными PID, отдельными Python-объектами и независимыми read-only соединениями SQLite. Запросы по тем же 48 статьям идут группами по восемь одновременно активных статей, внутри группы 11 раундов по одному вопросу каждой статье. Фиксированный хеш задаёт порядок статей и вопросов. При закреплении каждый процесс получает по две статьи из восьми. При ротации следующий вопрос каждой статьи переходит другому процессу. Каждый процесс и в том и в другом случае получает одинаковое число запросов в каждой группе и каждом раунде. Один RPC находится в полёте, чтобы изолировать локальность и исключить разницу в длине очереди.

Исполнители выполняют один и тот же точный поиск. Первый вариант читает сырой журнал и сохраняет полный разбор эпизода в локальном LRU-кэше, второй всегда читает только нужные списки из общего SQLite-индекса. Третий читает те же списки из общего индекса, сохраняя в локальном кэше также результаты для отсутствующих слов. Размер кэша на работника — 1, 4, 8 эпизодов. При запуске сверяем каждое решение с замороженным BM25. Три перемешанных повтора, единица для результатов — запрос или статья, технические повторы сворачиваются внутри запроса. Основное сравнение — объём сырых данных при закреплении и ротации с ёмкостью четыре. Для общей БД считаем все логические байты строк, включая заголовки и строки терминов. Дополнительные величины — доля промахов кэша, медиана и p95 времени запроса по часам координатора с IPC, время обработчика на стороне работника. Инициализация процессов и построение общего индекса находятся вне этого теста; последнее отдельно измерено в write_cost. Сравнение касается сервисной памяти наблюдений. Это реальное разделение адресных пространств, выводы о способности языковых моделей распознавать конфликт из него не следуют.
