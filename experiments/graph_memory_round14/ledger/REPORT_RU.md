# Проверка актуальности сохранённого чтения файла

**Основной результат.** Привязка к состоянию файла может экономить повторные чтения без изменения переданных агенту данных. В опыте на четырёх парах публичных выпусков три простых проверки дали правильное содержимое во всех 56 случаях. Экономию обеспечили 49 действительно неизменных файлов. Преимущество дополнительного поля NTFS ChangeTime проявилось только в контролируемом сценарии записи с сохранением размера и времени. Уменьшение ошибочных действий агента и качество решения программных задач здесь не измерялись.

## Какой оригинал доступен

В статье Wang и соавторов Ledger ведёт журнал виденных файлов, изменений и действий. Перед решением inform добавляет состояние в запрос к модели, а перед исполнением govern может вернуть предыдущее наблюдение. Авторы оценивали весь агентный цикл на 500 задачах SWE-bench Verified. Мы проверили публикацию, запись о работе на странице первого автора, его публичные репозитории, метаданные Hugging Face и поиск GitHub по точному названию и идентификатору. Ссылки на идентифицируемую реализацию Ledger в этих источниках не нашли. В прежних локальных сериях обнаружены обзор публикации и упоминание различий с собственным reader. Подтверждаемых локальных запусков авторских govern или inform не обнаружено. [Статья](https://arxiv.org/html/2608.00808v1) · [Страница автора](https://zehaowang00.github.io/) · [Сохранённые ответы поисков](ledger_audit.json)

Для исполнимой проверки взяли **OctoFS 0.25.2**, открытый MCP-инструмент чтения кода. Стандартный whole-file view сохраняет ранее переданный текст в рамках сессии, снова читает файл с диска, затем выдаёт изменения или короткое сообщение о совпадении. Для этой функции клиент должен объявить поколение контекста. Пин репозитория — 40b3f80516720b24ec00ba9575389d943aae0520. Исполнен официальный бинарный выпуск Windows с проверкой SHA-256 опубликованного архива. Через MCP повторён приведённый разработчиками пример с первым чтением, повтором, чтением диапазона, внешним изменением и принудительным полным чтением. Независимо от этого на том же коммите в публичном CI успешно завершились Rust-тесты, включая Windows. При локальном запуске использовался релизный бинарник. Перекомпиляция полного набора Rust-тестов локально не проводилась. OctoFS реализует часть жизненного цикла наблюдения. В данное сравнение не входят политика inform, выбор команд и собственный решатель Ledger. ## 96 контролируемых пар

Взяли 12 файлов из исходников Click, attrs, Hypothesis и PyYAML. Для каждого выполнили повтор без изменений, касание временной метки, правку соседнего файла, замену строки, такую же замену с сохранением mtime, атомарную замену с сохранением размера и mtime, добавление строки в конец и вставку в начало. Метаданные каждой пары, старые и новые хеши и границы чтения сохранены. Писателем был отдельный процесс. После его завершения все варианты получили одно состояние на томе NTFS. Для каждого варианта с MCP использовалась отдельная сессия, одинаковое первое чтение и случайный порядок запросов внутри пары. Эталоном служили актуальные байты после завершения записи. Изменение восстанавливал отдельный декодер, до сравнения с эталоном. При совпадении метаданных наша надстройка отдаёт тот же короткий маркер OctoFS и использует предыдущее чтение в доступном контексте. В остальных случаях она вызывает настоящий view. Во всех 96 случаях расширенный вариант передал столько же текста, сколько нативный механизм. Для нативного процесса засчитан логический минимум в один полный размер запрошенного содержимого согласно опубликованному пути чтения. Python-контроли выполняли реальные чтения. Счётчик дисковых секторов, page-cache misses и энергозатраты не собирались. Стоимость первого полного чтения общая и составляет ещё 281 928 байт на вариант. С её учётом для всей пары нативный минимум — 564 408 байт, у расширенного валидатора — 493 926 байт. Среднее время запроса составляло 1009 против 856 мкс, хотя медиана была лучше у нативного инструмента. Прямые Python-вызовы обходятся без IPC и форматирования идентификаторов строк. Из 24 ошибок простого сравнения 12 пришлись на атомарную замену. Идентификатор файла исправил все 12. Остальные 12 возникли при записи в тот же файл с восстановлением mtime. Добавление ChangeTime распознало эту группу, включая случаи с идентичным размером. Поле отражает изменение метаданных NTFS. Оно может меняться и при сохранении прежнего содержимого, что вызывает лишнюю перепроверку. Так, касание вызвало 12 полных перепроверок при неизменном тексте. При локальной проверке без объявления context epoch и в новой сессии OctoFS заново передал весь текст. [Определение поля в Windows](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_basic_info) · [Контроли сессии](context_control.json)

**Стоимость восьмистрочного наблюдения** отличается от стоимости полного файла. По старому смещению прочитано 26 192 байта, правильны 85/96 результатов. Вставка перед выбранным диапазоном изменила координаты, 11 из 12 таких случаев вернули другое содержимое. Чтение от начала с отсчётом строк блоками по 512 байт дало 96/96 при 174 726 байтах. Штатный ranged view тоже дал 96/96, логический нижний предел 282 480 байт. Диапазонное чтение нельзя считать полной проверкой прежнего файла.

## 56 естественных переходов путей

После контролируемого опыта зафиксировали четыре перехода между выпусками и взяли все 56 подходящих исходных файлов. На следующих версиях 7 из них изменились и 49 сохранили побайтно прежнее содержимое. Удалённых файлов в этой панели не было. При обычном развёртывании отдельный процесс переписывал только файл, чьи опубликованные байты изменились. Поддержание каталога выпуска и поиск изменившихся файлов происходили со стороны стенда. Валидатору список изменений не передавался. Режим копирования каталогов целиком может давать другую стоимость. **Что объясняет результат.** Пусть файл имеет размер B, проверка метаданных обозначается V, а повторное чтение стоит R. Если V совпал, предыдущий ответ сохраняется. Ожидаемый выигрыш в чтении содержимого равен E[B · 1{V совпал}], а ожидаемый выигрыш в затраченном времени зависит от E[R · 1{V совпал}] за вычетом цены проверки V на каждом запросе. Риск устаревшего наблюдения — совместная вероятность совпадения V и изменения содержимого. На первом стенде расширение V устранило наблюдавшиеся ошибки ценой дополнительных перепроверок. На втором полезную экономию уже даёт простой V. Доли сценариев заданы дизайном, независимость 96 повторов не предполагается. Опыты не устанавливают верхней границы риска для других файловых систем, разрыва доступности контекста или записи, конкурентной самому чтению. Для статьи эти данные задают проверяемый механизм контроля актуальности и сильный базовый вариант. Перенос на агентный бенчмарк требует натуральной частоты таких событий и вмешательства в реальные действия модели.
