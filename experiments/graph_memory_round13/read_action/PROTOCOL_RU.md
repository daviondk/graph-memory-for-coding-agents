# Выбор первого чтения после пустого поиска

Проверяем, превращается ли изменение первого файла в выдаче памяти в изменение выполненного действия. До составления индивидуальных входов исследователям известны суммарные результаты ранжирования в основной и внешней панелях. Первичная внешняя панель содержит пять задач с расхождением первого файла по входным данным. Правило отбора едино для обеих панелей. Берём самый ранний пустой запрос на задачу, в котором заранее запертые ранжирования strong и graph расходятся в top-1, есть хотя бы два пути и оба первых доступны в списке. Сохраняем все такие задачи и число всех исходных запросов для знаменателя. Исключаем задания по атакам или эксплуатации уязвимостей по тексту условия до вызова модели. Исходы отдельных задач не используются для выбора, порядок методов и порядок пунктов меню задаёт хеш. Авторы формируют вход только из опубликованной постановки и уже видимой агенту части истории. [Правило ранжирования](../reformulation/PROTOCOL_RU.md)

На каждом входе один и тот же локальный Qwen3.8-27B UD-Q4_K_M с одинаковым seed и параметрами получает оригинальное описание задачи (до 3000 символов), литерал и область текущего пустого запроса, список из максимум восьми уже адресованных путей. Оба конкурирующих кандидата обязательно включены, оставшиеся — по недавнему наблюдению. У каждого пути одинаково доступны давность и короткий префикс ранее увиденного вывода. В трёх условиях меняется одна строка интерфейса — нет предложенного пути, первый файл strong либо первый файл graph. Одинаковый интерфейс с единственным инструментом чтения и одинаковый порядок файлов. Кандидат выбирается посредством настоящего tool call, один вызов модели, до 128 выходных токенов, greedy, without thinking. Выбранный путь реально открываем в исходной Git-версии задачи в отдельной фазе до чтения оценки. Другие инструменты отсутствуют. Это контролируемая задача следующего действия с замкнутым меню.

Первичные метрики — доля разных выбранных путей при замене подсказки и доля фактически открытых путей, вошедших в production Python-файлы последующего изменения, на строгих Git-парах. Вторичные — доля принятых подсказок, фактическая доступность пути, токены входа/выхода, парные выигрыши/потери, совпадение с ближайшим естественным чтением в пределах пяти действий. Сохраняем случаи вне строгой подвыборки и ошибки вызовов. При разной доступности исходной ревизии знаменатель показываем явно. Основная и внешняя панели считаются отдельно. Отбор расхождений оценивает механизм на трудных случаях, поэтому результат нельзя экстраполировать на каждое чтение или долю решённых задач. Для передачи дискретного решения Replay допустим только при неизменённом контексте до действия. Последующие изменения траектории после иной подсказки этим методом не наблюдаются.
