# Когда агенту можно повторно использовать пустой результат поиска

**На 147 опубликованных наблюдениях Git нашёл совпадение в 29 случаях, хотя поиск агента ранее вернул код 1 и пустой вывод.** Мы проверили, можно ли заранее отсеять такие записи, используя только данные, доступные до запроса. Самый дешёвый содержательный сигнал — искомый литерал уже встречался в ранее показанной строке файла из нужной области. Правило отправило на повторный поиск 6 наблюдений и обнаружило 5 опасных. Сверка тех строк с прежней версией Git сузила множество до 5 из 5. При этом **24 из 29 расхождений остались незамеченными**. Сигнал полезен для отбраковки конкретной записи. Он плохо подходит как условие, разрешающее все остальные записи. [Результаты по каждой политике](results.json) · [Прогнозы и метки](graded.json.gz)

## Что именно проверялось

Панель состоит из 147 отдельных ключей пустого поиска, 96 задач и 17 репозиториев из уже исследованной истории VibeMemBench. Событие ошибки определено узко: в зафиксированной целевой базовой Git-версии существует отслеживаемый текстовый файл с совпадением для тех же литерала и области. Агент работал в своей рабочей копии; источник расхождения по таким логам установить нельзя. Все 147 областей оказались сопоставимыми. Эталон каждого случая проверен нативным git grep и прежним независимым побайтовым проходом по Git-объектам. Новый трёхкратный запуск прямого поиска дал те же значения. Набор условий, признаки и порядок оценки закреплены до открытия меток новой серии. Исходный корпус уже применялся в R12. [Протокол](PROTOCOL.md) · [Квитанции прямых поисков](direct_receipts.json) · [Описание VibeMemBench](https://arxiv.org/abs/2609.23570)

Решение «переиспользовать» означает довериться старому пустому ответу. «Воздержаться» означает оплатить новый поиск в целевой версии. Coverage — доля сохранённых ответов, selective risk — доля опасных среди сохранённых. Если сохранений нет, риск не определён. Сравнивались как правила с естественной долей сохранений, так и ранжирования с одинаковым числом сохранений. Неопределённость оценивалась кластерным bootstrap по задачам, двумя связанными записями одной задачи нельзя искусственно увеличить размер выборки. [Постановка risk–coverage](https://arxiv.org/abs/1705.08500)

Свежесть — число ранее завершённых вызовов инструментов. Сравнение строк требует совпадения относительного пути и нормализованного текста с blob целевой ревизии. Условие «файл в области» для запроса к одному файлу требует тот же файл, а для каталога допускает подходящий вложенный файл и фильтры по имени. Наличие трёх длинных строк в области улучшило абсолютное число ошибок относительно широкого признака свежести, но подняло **долю ошибок среди сохранённых**, поскольку дополнительно выбросило много правильных записей. ## Сколько качества добавляют именно признаки

Предзаданное ранжирование учитывает прямое противоречие, несовпадение содержимого, тип и давность свидетельства. При сохранении ровно 110 записей (74,8%) оно пропустило 4 опасные, фиксированный порядок по SHA — 23. У более сильного описательного контроля, который сначала принимает именованный каталог и синтаксически похожую на файл область, — 7. Площадь под эмпирической кривой риска составила соответственно 0,0421, 0,1887 и 0,0796; меньшая величина лучше. При первых 37 сохранениях у ранжирования было 0 ошибок. Для решений о развёртывании этот конечный ноль недостаточен. [Кривые](results.json) · [Контроль типа пути](scope_diagnostic.json)

Состав группы заметно влияет на эффект. У 66 из 96 задач всего одно наблюдение. При случайном выборе **того же числа** записей внутри каждой задачи для 110 сохранений ожидаются 5,83 ошибки вместо наблюдаемых 4; интервал условной перестановки 4–7, одностороннее p=0,054. Для сохранения по свежим строкам риск 4,50% с кластерным 95% интервалом 0,81–9,80%. При той же coverage по задачам ожидаются 6,17 ошибок против фактических 5, p=0,168. Принимая решения по названию каталога или одному графу, легко приписать методу различия между задачами. Среди множества сравнённых правил значения p носят исследовательский характер.

Отдельный разбор после просмотра меток выявил техническую особенность: **все 20** наблюдений, сопоставленных с общим корнем /testbed, были поисками **по каталогу** и попали в группу опасных. Это 17 задач и девять репозиториев. Среди 127 наблюдений из именованных путей опасными были 9: четыре из 29 поисков по каталогу и пять из 98 запросов к конкретному файлу. Признак сопоставленного корня и реально наблюдавшийся вывод pwd — разные вещи. Пять ошибок, найденных по ранее увиденному литералу, и двадцать ошибок у общего корня не пересекались. Постфактум их объединение дало **26 платных поисков, 121 сохранение и 4 оставшиеся ошибки** (3,31%). Проверка такого правила на новых данных ещё нужна. Удобное имя каталога само по себе происхождение репозитория не устанавливает. [Разбор по корням](alias_sensitivity.json)

## Цена проверки

На этом компьютере сумма медиан трёх прямых запросов git grep на 147 наблюдениях составила **4,49 с**. Для правила свежих совпадений повторные поиски стоили 1,32 с. Однако поиск и загрузка необходимых деревьев и blob для подтверждения увиденных строк прибавили около 6,62 с, даже с повторным использованием объектов внутри задачи. У ранжирования при 110 сохранениях аналогичная сумма только на Git-операции признаков и повторный поиск достигла 16,15 с. Это оценка по реально измеренным операциям и зафиксированному порядку доступа, а не сквозной замер сервиса с постоянным индексом файлов. Общие для нескольких политик проверки не оплачиваются заново внутри одной задачи. Раннее прекращение сверки на первом подходящем свидетельстве R12 отдельно учтено. [Операции чтения Git](operations.json)

Признак уже показанного литерала обходится без доступа к Git. Его отдельная реализация, работающая по уже разобранным логам, затратила **0,26 с** на все записи. Шесть последующих прямых поисков заняли 0,18 с. Если журнал надо загрузить заново с диска, чтение и разбор исходных 66,6 МБ добавляют 1,44 с. Метод экономит работу, только если допускается оставить 24 опасных записи. При требовании нуля ошибок на этой панели прямой поиск дал полный ответ. Фактические байты, которые git grep прочёл с устройства, не измерялись: объём подходящих blob в квитанции — верхний ориентир полного обхода, а поиск с ранней остановкой и кеш ОС могут читать существенно меньше. ## Проверки переноса и предела информации

Для отдельной чувствительности использованы все 31 выделенные ранее текстовые команды из историй Kimi-transfer, Kimi-writer и Claude, пять других репозиториев. В этих данных пустота имеет слабое подтверждение; отдельного численного кода 1 нет. Нативная проверка обнаружила 28 сопоставимых областей в 16 задачах, в них **0 из 28** базовых версий содержали искомый текст. Три отсутствующие области вынесены отдельно. Совпадающие строки найдены для 11 из 28, свежие — для семи. В этой панели нельзя оценить способность поймать опасное сохранение, не зарегистрировано ни одного такого события. Она не подтверждает и не опровергает чувствительность на основном корпусе. [Внешняя оценка](external/results.json) · [Внешние сырые решения](external/graded.json.gz)

Проверены также 36 пар контролируемых текстовых деревьев. В 24 парах список имён каталога и ранее увиденные длинные строки совпадали в точности, а ответ прямого поиска различался. Искомый текст был в непросмотренном соседнем файле либо в непросмотренном фрагменте того же файла. В 12 положительных контролях показанная строка содержала литерал и сигнал сработал. Эти пары демонстрируют ограничение доступной информации; частоты в реальных репозиториях по ним не оцениваются. [Состояния, хеши, возвраты Git и время](controlled_results.json)

**Вывод для статьи.** Положительное свидетельство может дать локальную причину перепроверить сохранённое отрицание. Сходство нескольких фрагментов плохо обосновывает отсутствие чего-либо в большой области, а его проверка иногда дороже полного поиска. На следующем независимом корпусе имеет смысл фиксировать физически проверяемую идентичность снимка или полный охват конкретного файла, отдельно измеряя долю обнаруженных ошибочных отрицаний и стоимость запроса. Доказательств нового SOTA или улучшения успешности работы решателя в этой серии нет.
