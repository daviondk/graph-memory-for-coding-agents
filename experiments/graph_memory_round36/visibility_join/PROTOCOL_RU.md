# Цена отображения видимой связи между группами фрагментов

Панель до оценки — 128 из всех 1207 test-историй по наименьшему SHA-256 строки «r36-visibility-sql/v1/» и ID. Четыре исходных среза 25/50/75/100%, включая пустые множества и совпадающие срезы. Дополнительно используем 12 исходных историй нативной сверки R36 для проверки идентичности множества. Они не входят в физические измерения, за исключением случайного совпадения с основной панелью.

Сравним способы хранения одного и того же отображения M. Плоская таблица хранит каждую впервые видимую пару PU вместе с моментом её первого появления. Факторизованная таблица хранит пару выходов вызовов и момент первого перекрытия интервала её поддержки с видимостью обоих выходов. Отдельная таблица указывает принадлежность PU к выходу. Интервал активности [birth,end) не включает событие end. При нескольких свидетельствах достаточно одного живого. Механизм пригоден, если все PU одного выхода появляются вместе и их идентичности стабильны. На каждом срезе читаем лексикографически упорядоченные направленные пары и раздельно ненулевые входящие/исходящие степени. Проверяем оба ответа физического SQL против независимой событийной материализации и графов R36. Дополнительно проверим, воспроизводятся ли зафиксированные порядки возвращённых кандидатов R36 из степеней физического запроса, при наличии всех входов.

Контроли хранения: плоская таблица без membership (минимальная схема); плоская с общей таблицей membership, когда эта таблица нужна существующему графу; компактная с полностью учтённой membership. Все схемы поддерживают один и тот же первичный интерфейс чтения. Одни и те же 128 историй делят одну физическую БД, устраняя округление к странице на каждую маленькую историю. Индексы — только составные первичные ключи WITHOUT ROWID с префиксом истории, стратегия сканирования по истории и отбор по времени одинаковы. Первично — размер завершённой базы в байтах, медиана и p95 тёплого SQL+fetchall для пар и степеней, полное время построения статического снимка на готовых числовых входах (создание схемы, подготовка/materialization производных строк, вставка, COMMIT и закрытие). Кэш векторов, извлечение интервалов из исходных инструментальных данных и получение нормализованных числовых строк учитываем отдельно от СУБД. Для всех схем одинаковые page size=4096, synchronous=FULL, journal_mode=DELETE, CPU и диск. Пять физических построений каждой схемы; порядок определяется независимым хешем. Одно прогревочное обращение по каждому запросу, затем 9 повторов для каждой из 512 пар история–срез, методов и двух форм результата, с детерминированной перестановкой схем и запросов. Результаты материализуем на стороне Python. Задержка не включает ранжирование LLM. Точечные времена агрегируем сначала по повторениям того же запроса. Интервалы разности или отношения времени чтения, если представлены, получаем парной перевыборкой историй. Опубликуем объём без общей таблицы и с общей таблицей, оценку издержек JOIN и ограничения области валидности.
