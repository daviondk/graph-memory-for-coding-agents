# Дополнение после просмотра планов SQLite

Исходный запрос для раскрытия пар обошёл обе таблицы принадлежности по ключу истории до обращения к таблице отношений. Проверим, насколько это зависит от порядка JOIN. По той же панели, на тех же 512 состояниях, запланированы пять конфигураций: исходные flat без принадлежности и grouped с автоматически выбранным порядком, grouped с принудительным порядком «активная связь → левая группа → правая группа» через CROSS JOIN, flat и grouped с автоматически выбранным планом после штатной команды ANALYZE. Отдельный физический вариант записывает в каждую групповую связь две мощности выходов, известные при её создании. Для исходящих/входящих степеней он суммирует соответствующую мощность и только затем выдаёт степень каждому PU группы. У него тот же порядок раскрытия пар. Таблица принадлежности также полностью учитывается в размере. Фиксируем результаты и планы для всех вариантов. Проверяем совпадение всех результатов с теми же эталонными хешами. Повторяем исходный порядок прогрева, 9 измерений и 10 000 парных перевыборок траекторий. Пять построений дополнительной схемы. Это диагностика реализации на известной панели, причинный вывод о применимости к другой нагрузке потребует отдельного корпуса.
