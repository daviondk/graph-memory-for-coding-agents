# Отложенное сопоставление аргументов при построении графовой памяти

В ISETrace можно точно восстановить все исторически наблюдавшиеся связи между результатами инструментов, даже если при самом вызове ещё не искать источники его аргументов. На 1207 траекториях ранний и отложенный операторы выдали одно и то же множество пар после каждого из 72 186 событий. Выигрыш от пропуска сопоставлений оказался мал. На этом корпусе чтение по ссылке не показало ускорения, а чтение из SQLite в оперативной памяти увеличило затраты CPU.

## Что хранит оператор

Источником связи FEEDS служит типизированное значение из результата инструмента, встретившееся в аргументах последующего вызова. В нативной схеме ISETrace столкновение с другим производителем делает значение необратимо неоднозначным. Историческая связь фиксируется, если после обработки хотя бы одного завершённого события оба результата представлены видимыми единицами происхождения (PU, фрагменты вывода), а у связи остался хотя бы один уникальный свидетель. Коды вызовов однозначны. Сравнение велось с уже проверенным [потоковым оператором, отбирающим свидетелей при вызове](../streaming_witnesses/REPORT_RU.md).

Новый оператор при вызове запоминает позицию события и ссылку на неизменные аргументы. При появлении результата он сначала применяет все новые определения и коллизии. Если у результата есть видимый фрагмент, он перебирает ещё уникальные значения, произведённые видимым источником строго до исходного вызова. При первой подходящей записи один раз получает аргументы по ссылке и проверяет их штатным предикатом. Новые связи добавляет к историческому множеству.

## Почему множества совпадают

Пусть вызов находится в позиции c, а результат появляется в позиции o. Отсчёт ведётся по паре (номер сообщения, позиция внутри сообщения). Ранний оператор признаёт значение v свидетелем, когда оно имело уникального производителя p до c, аргументы вызова содержат v и этот же p остаётся уникальным после o. Применяются также общие условия видимости источника и результата. Из поглощающей неоднозначности следует обратное утверждение. Если после o значение имеет уникального p, первая позиция p строго меньше c и поток идёт в порядке позиций, то p уже был уникален в момент c. Неизменность аргументов даёт одинаковый ответ при обеих проверках. Равенство для каждого значения даёт равенство объединений по всем свидетелям; исторические множества после очередного события совпадают по индукции. Вызовы без завершившегося результата сами новых пар не публикуют.

Проверка позиции c существенна при параллельных вызовах. Производитель, который впервые появился между c и o, не мог сообщить значение исходному вызову. Коллизия на самом o уже исключает значение. На синтетических примерах подтверждены восемь штатных случаев и два контрпримера. Изменение аргументов после вызова удалило одну связь только в отложенном варианте. Искусственное возвращение уникальности породило в нём одну лишнюю связь. [Граничные случаи](fixture_results.json)

## Полный повтор потока

Оба оператора получили один и тот же неизменный поток из 36 093 вызовов и 36 093 результатов. У 795 из 1207 траекторий одновременно ожидали результата как минимум два вызова. Проверялись реальные идентичности производителей, открытых вызовов и исторических пар. На четырёх фиксированных префиксах каждой траектории дополнительно совпали число исторических пар и размер их PU-проекции с ранее проверенным материализатором, всего 4828 сравнений. Переобучение не требовалось. Равенство графа позволяет прежнему детерминированному читателю сохранить ранги и качество, дополнительное качество ответов в этом опыте не измерялось. Отсрочка сократила вызовы предиката на 21 030, или 0,751% (парный 95% интервал экономии 0,623–0,895%). Из них 21 010 исключила коллизия, ещё 20 пришлись на результаты без видимых фрагментов. При этом словарь за время ожидания вырос. Общее число просмотренных записей увеличилось на 5,33% [4,69%; 5,98%]. Совокупное число обращений к архиву составило 92,77% от числа исходных вызовов. Полные аргументы занимают в двух представлениях 45 838 504 байта исходного текста и 45 763 417 байт компактного JSON для востребованных вызовов. Это объём возвращаемой логической нагрузки при хранении двух представлений. Если объекты доступны по указателю в оперативной памяти, полное копирование не требуется.

В раннем варианте кроме записей на открытый вызов хранятся списки совпавших значений. В отложенном каждая из 11 потенциально открытых записей несёт позицию и ссылку. За весь поток суммы по состояниям составили 25 178 ссылок на совпадения и 49 725 ссылок на аргументы соответственно. Эти величины описывают разные объекты; разница в резидентных байтах зависит от размещения архива и устройства контейнера. [Полные числовые показатели](summary.json)

## Измерения времени

96 траекторий отобраны минимальным SHA-256 до измерения. Один разогрев, затем по четыре парных повтора с чередованием порядка. Ни подготовка существующего архива, ни загрузка трасс, ни построение карты видимых фрагментов не входят во время. Отношения рассчитаны по сумме средних времён траекторий. В скобках приведены 95% перцентильные интервалы по 10 000 парных перевыборок траекторий. Один программный поток, Python 3.12.13 на Windows, SQLite 3.50.4.

Основной таймер GetProcessTimes выдавал положительные приращения от 15,625 мс. Среди 384 повторов каждой реализации он дал нулевое время для 243, 241 и 231 коротких прогонов соответственно. Поэтому его интервал для ссылки широк. Циклы потока и время по монотонным часам тоже совместимы с отсутствием эффекта ссылки. Вариант SQLite возвращал обе формы аргументов по целочисленному первичному ключу и восстанавливал структурированный JSON. За один нетаймируемый контрольный проход панели учтено ровно 2444 таких чтения на 3 324 242 + 3 318 810 байт. Относительно отложенного доступа по ссылке SQLite потребовал на 4,31% больше циклов [2,41%; 6,30%]. Измерение включает CPU-последствия SQL и десериализации, обращения к физическому носителю не измерялись. **Вывод для системы.** Отложенное сопоставление даёт другую точную реализацию того же оператора и ограничивает число ожидающих записей числом незавершённых вызовов. На реальных трассах он редко избегал проверки значений, требовал почти всегда вновь получать аргументы и не показал ускорения относительно лёгкого потокового контроля. В системе с уже резидентным журналом выбор допустимо основывать на интерфейсе хранения. Для этого корпуса отдельное чтение через SQL в целях сокращения CPU экспериментом не поддерживается.
