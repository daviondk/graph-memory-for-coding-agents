# G3-Free. Заранее зарегистрированное чтение на новой группе C

18.11.2026. Зафиксировано после результата G3-L A/B и до любого просмотра отдельных результатов, исходов, числа альтернатив или чисел G3 по группе C этой реализацией. Членство в C и подготовку зеркал определяет внешний стенд transfer. Заранее потребляем только пары, не исходы.

Выбрать до 24 пар (old,new,s,t) на каждый из восьми репозиториев C. Сортировка SHA256 от полей G3-Free-C, repo, old, new, s, t с разделителем |. При нехватке берём все. Не расширять после наблюдения. Новые вопросы C с положительной старой достижимостью задаются общим стендом. Методы — внутри одного и того же вопроса и холодного состояния. Первичный исход — суммарно прочитанные с нового коммита исходные Git-объекты (новая фаза и обе фазы); сравнение free3 против one-path. Дополнительно paired wins/losses/ties по вопросам и репозиториям, покрытие и парные интервалы регионального переноса с блокировкой по репозиторию, метаданные, реальные байты сертификата, результат в точности равен независимому полному сверенному оракулу.

1. На old ровно один раз делается прямой BFS в той же семантике, который останавливается после первого найденного пути (max 4 рёбра). Для него суммировать actual reads. Полученный первый путь p* обязателен в каждой доказательной стратегии. На основании только уже раскрытой смежности провайдеров строим ориентированный подграф: ребро u→v допустимо, если код u уже разобран и v разрешён в кэше named-tree. Дополнительные решения не могут вызывать Git при записи, стоимость конструкции в CPU и байты записи явно измеряются. Слепой контроль экономит всё на новом чтении, просто копируя старый ответ. Считать отдельно ложные ответы. Прямой поиск без памяти даёт независимый контроль цены и правильности.

2. Для free3 собрать первые 16 простых путей (детерминированный BFS, до 4 рёбер, общий лимит 10 000 префиксов) в ограниченном подграфе, вернуть первый плюс жадно до двух дополнительных по максимуму разнообразия зависимостей согласно равновероятной модели одиночной изменившейся вершины. При равенстве ранее встреченный путь. Если на старом BFS доступен второй/третий путь, соответствующие частоты протоколируются; никаких последующих дочитываний для поиска пути.

3. Контроль памяти того же бюджета на каждую задачу: сохранить то же первое доказательство и, по порядку раскрытия обычного BFS и лексическому порядку соседей, положить дополнительные единичные наблюдения u→v в каждый случай, когда сериализованная запись вместе с необходимыми манифестами не превышает число байт соответствующего free3. Если следующий элемент не вмещается, продолжить просматривать уже прочитанные элементы. Дополнительные рёбра могут дать пути через вершины, присутствующие в кэше; при recall найти из сохранённых рёбер простые пути до 4 и проверить сначала первое свидетельство, далее готовые пути. Если неполный кэш не доказывает цель, fallback использует проверенные кэшированные положительные рёбра без выдачи отрицательного ответа до полного поиска, насколько позволяет алгоритм. Формат конкретизируется до скоринга: общие source,target,old, упорядоченный манифест [модуль,путь,blob SHA], целочисленные идентификаторы вершин, пути в виде упорядоченного списка индексов модулей. Кодирование дополнительных рёбер — пара ID. Равенство является верхней границей байт со сведениями; фактический размер фиксируется для каждого варианта. Дополнительный диагностический контроль free-short3 — первые три найденных в том же наблюдаемом подграфе, включая первый.

4. Проверять истины и быстрые ответы на новой версии тем же Git-reader, а не отдельной моделью. Полный oracle хранится в внешнем публичном для исследователя шарде. Использовать данные oracle только после построения ответов. Все вкладчики публикуются независимо от направления. Работа с уже увиденным пространством, оценка показа памяти кодовому агенту и перенос на программы, прошедшие тесты, принадлежат разным этапам. Эта проверка измеряет повтор статического запроса. Оценка wall time условна из-за OS-кэшей и параллельности.
