# G3-Free. Стоит ли сохранять дополнительные пути, если агент уже увидел их во время обычного поиска?

**Предварительно зарегистрированная гипотеза не подтвердилась.** В 51 из 168 запросов прямой поиск уже прочитал всё необходимое для альтернативных свидетельств; такие случаи встретились в шести репозиториях. Сохранение до трёх путей из уже доступных данных избавило от дополнительных чтений при записи, но дало **0 выигрышей, 0 проигрышей и 168 ничьих** по сравнению с одним путём по числу новых исходников, открытых после изменения версии. Один проверяемый путь оказался достаточно хорош для этой выборки.

## Данные и метод

Восемь новых проектов C были зафиксированы предыдущим стендом. Для каждого выбирали до 24 ранее положительных вопросов по хешу его входных данных. У pypa/build таких вопросов не было, поэтому получилось семь проектов с 24 вопросами каждый. Вопрос одинаков для всех условий: есть ли путь длиной до четырёх в статическом графе импортов Python между двумя заданными модулями? Проверка выполнялась до и после перехода на 12 коммитов. После изменения четыре запроса стали отрицательными. Все варианты получили один и тот же изначальный BFS вплоть до всех переданных Git blob и дерева; подбор дополнительных доказательств больше не вызывает Git. Программы репозиториев не выполнялись.

На исходной версии записывался один путь, до трёх первых увиденных путей либо до трёх путей с разными зависимостями. Первое свидетельство всегда сохранялось. Добавлен контроль из того же первого свидетельства и отдельных рёбер в естественном порядке BFS. Полные манифесты, SHA исходников и номера вершин включались в общий лимит. Для каждого случая байты контроля не превышали фактическое число байт варианта с разнообразием. При отрицательной проверке незакрытые части графа исследуются ленивым прямым поиском. Даже при смене старой цепочки известный прежний суффикс может доказать достижимость, когда прямой поиск приходит к его началу и суффикс умещается в лимит глубины. Слепой кэш использует только старый ответ.

Здесь «байт на диске» — длина компактной сериализации UTF-8 без накладных расходов файловой системы и БД. Манифест хранит точный путь и Git blob, имена модулей закодированы локальными целыми идентификаторами для рёбер. Чтения исходников независимо сверены по идентификаторам Git-объектов в построчных логах. У прямого контроля на повторе 14 245 107 байт содержимого, у любого из проверяемых вариантов 4 408 291. Первоначальный поиск для всех потребовал 14 767 221 байт исходников и 559 475 байт дерева и коммита. Во время записи дополнительных свидетельств счётчики и наборы ранее прочитанных деревьев и blob проверялись на точное равенство исходному BFS. Метрики времени остаются диагностическими из-за кэшей Git и файловой системы.

Варианты с памятью дали по 51 быстрому положительному ответу с опорой на неизменившиеся Git-объекты и по 164 верифицированных положительных ответа до fallback. Все сравнения проверяемой памяти с полным эталонным графом совпали. При выборе одного пути вместо нового поиска было 150 пар с меньшим числом чтений, одна с большим и 17 с тем же. На уровне всех семи проектов затрат по числу объектов стало меньше. Среднее по проектам уменьшение составило 5,36 исходного объекта на повтор, описательный 95% репозиторный bootstrap для разницы «один путь минус прямой поиск» [−10,18; −2,37]. Суммарно это −84,7% чтений на повторе и −41,2% за два запроса. Против отдельных рёбер того же бюджета прибавка нового метода также точно нулевая. Валидированными исправлениями программ эти числа не являются.

## Почему дополнительных выигрышей не оказалось

После блокировки первичных результатов проверили неизменность общих зависимостей на тех же вопросах, без расширения выборки и дополнительного чтения исходных blob. Из 51 случая с альтернативами в 38 набор провайдеров первого пути был подмножеством набора каждого другого **выбранного** пути. Такой дополнительный обход не обходит ни одной зависимости первого. У 15 из 51 исходный путь уже допускал быстрый ответ. Во всех остальных 36 случаях обнаружен изменившийся или отсутствующий провайдер, общий для всех выбранных путей; в 25 случаях из 36 изменился сам исходный модуль. Поэтому проверка «путь подтвердился по метаданным» не может сработать ни для одной из альтернатив в этих 36 случаях. Отдельно, во всей выборке первое свидетельство после чтения изменившихся поставщиков подтверждает все 164 сохранившихся положительных ответа. Дополнительные пути могли бы экономить чтения, даже если первое свидетельство конечный вывод не меняет; на фактических трассах ни в одном вопросе такой экономии не возникло.

**Следствие для исследования.** Полезнее оценивать долю поломок, которые действительно можно обойти независимым свидетельством, чем просто увеличивать число путей. Две разные цепочки с общим изменившимся провайдером дают одно и то же требование перепроверки. Это наблюдение относится к статическим путям в выбранных версиях Python-проектов и к однократному повтору. Оно ограничивает объяснение предложенной эвристики. Экстраполяция на реальные запросы LLM-агентов, другие языки или часто меняющиеся зависимости требует отдельного стенда.
