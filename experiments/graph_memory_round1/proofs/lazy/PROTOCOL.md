# G3-L. Операционный аудит ленивого чтения Git

Заморожено до нового измерения затрат. Исходы G3 A/B известны. Эта фаза проверяет точное воспроизведение опубликованных внутри проекта записей и стоимость реализации. Новая популяция задач и подтверждение DL/LLM-эффекта здесь не заявляются.

**Выборка.** Для каждого непустого репозитория G3 берём до 10 пар среди всех его временных окон. Сортировка — шестнадцатеричный SHA256 от соединённых вертикальной чертой полей G3-L-20261118, repo, before, after, s, t. Все отобранные пары остаются в знаменателе. Тексты файлов, число альтернатив, признак изменения и исход не участвуют. Выборка компактна, так как каждый вариант холодный и выполняется через реальные операции Git.

**Внешний вход.** Путь к bare или рабочему Git, old commit, new commit, исходный и целевой модуль. Начальная выборка G3 заранее содержит положительные запросы на старом состоянии, длина кратчайшего пути от двух до четырех. В новом состоянии есть отрицательные случаи. Глобальное построение графа, ls-tree -r и импорт/исполнение исходников запрещены в измеряемом коде. Оракул — предыдущие шардированные результаты из полной AST-проекции, уже независимо рассчитанные для этой пары. Для метода с историей разрешена история имён изменений до old. Входные пары специально берутся из замороженного стенда, практически готовый вопрос на входе является условием измерения.

**Фазы.** Первый вызов direct ищет достижимость на old, отдельный такой же вызов на new даёт контроль без памяти. one/short3/diverse/historical при первом ответе ищут соответственно 1, 3, 16, 16 путей либо доходят до исчерпания/исходного лимита в 10 000 развернутых путей. Последние две стратегии сохраняют максимум 3 свидетельства. На new для каждой независимо проверяем присутствие/путь/идентичность содержимого провайдера, при необходимости парсим изменившихся провайдеров, затем без исчерпывающего индекса запускаем прямой поиск. Сравниваем фактические пути, новую истину, fast и validated со шардом. Любое расхождение приводится и исследуется до принятия выводов. Общий кэш операционной системы может быть тёплым. На каждой фазе и стратегии заново начинаем с пустым кэшем открытых объектов, поэтому метаданные и исходники поступают через реальный Git-процесс, без общего прикладного кэша. Допускается совместный подсчёт одинаковых детерминированных префиксов запросов данных с явным обозначением.

**Измерения.** Число и байты переданных из Git исходных blob, отдельно число и байты полученных объектов дерева/коммита, попытки разрешения имён, логические разборы поставщиков, время и чтение старой Git-истории (команды diff, имена/байты). Затраты разбиты по записи и следующему обращению. Все агрегаты — валовые фактические числа на выборке, отдельно по группам или репозиториям. Прорыв по SOTA, качество патчей, выигрыш по wall-clock на другой машине и обобщение с положительных запросов не оцениваются.
