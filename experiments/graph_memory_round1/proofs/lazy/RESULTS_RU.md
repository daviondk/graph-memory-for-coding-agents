# G3-L. Цена записи и повторного чтения из настоящих объектов Git

На **156 положительных исходных запросах в 16 репозиториях** один сохранённый путь потребовал **1211 чтений исходных Git-объектов** за начальный запрос и один повтор через 12 коммитов. Поиск с нуля в обоих снимках потребовал 1994 (экономия 39,3%, меньше чтений во всех 16 проектах). При активном поиске нескольких путей начальная запись обходилась дороже. Следующий запрос читал меньше файлов, однако в сумме за однократное переиспользование все три стратегии проиграли одному пути и прямому поиску.

Это специальный вопрос **«есть ли статическая цепочка импортов длиной до четырёх от известного модуля s к известному модулю t?»**. Python выполняет только статический синтаксический разбор. Код из репозитория и нейросети не запускались. Исходная выборка G3 специально требовала положительный начальный ответ длиной от двух шагов. После смены версии 154 ответа остались положительными и два стали отрицательными. Качество выбора программистом нужного вопроса и частота его повтора в настоящей сессии здесь неизвестны.

## Прямые измерения

Единица — один Git blob исходного файла, действительно переданный процессом Git после запуска фазы. Два файла с идентичным содержимым внутри одного запроса могут использовать один объект, который повторно не запрашивается. По новому коммиту используются только манифест и сохранённые пути. Старые исходники, списки смежности и дерево памяти очищены. Скрытого глобального индекса нет. Во всех 624 парных проверках метода воспроизведены все выбранные полным алгоритмом пути, все быстрые/валидированные ответы и истина независимого исчерпывающего оракула. Один удалённый или отсутствующий в новом состоянии конец пути может дать корректный отрицательный ответ вообще без чтения исходника.

Сумма байт сериализованных записей четырёх стратегий соответственно 80 700, 120 725, 121 640 и 121 927. Это формат CLI, включающий исходный коммит, пару модулей, пути и точные Git blob SHA провайдеров. Сумма прочитанных байт метаданных дерева и коммита на запись / повтор составила 507 518 / 503 956 для прямого поиска, 507 518 / 458 342 для одного пути и 529 721 / 445 045 для варианта с историей. Имена файлов истории учтены отдельно от исходного содержимого. За 156 записей историческая стратегия вызвала 156 rev-list, 3493 diff и получила 29 583 имени пути (1 649 750 байт ответа diff). Прямой контроль выполняется первым, остальные методы также запускаются в фиксированном порядке; библиотеки Git и файловая система могут быть прогреты. Относительную скорость по времени из этого порядка выводить нельзя.

Для первых трёх путей вместо одного получено 50 дополнительных сэкономленных чтений на повторе ценой 1266 дополнительных чтений в начале. Если *гипотетически* одна запись имела бы ту же среднюю экономию на каждом следующем использовании, окупаемость потребовала бы как минимум 26 таких повторов. Фактически измерен один новый снимок на запрос. Поздние изменения могут сделать сохранённые пути бесполезными раньше. На B выбор с историей использовал при повторе 36 чтений против 41 для первых трёх путей, при 1380 против 1037 начальных.

## Рабочая реализация и контроль

Каталоги Git раскрываются по необходимым сегментам пути. Для обнаруженного имени модуля исследуются обычные файлы и пакеты в корне, src и lib; двусмысленные имена и нерегулярные файлы отсекаются. Содержимое каталога, однажды прочитанное через git cat-file --batch, содержит имена и ссылки его непосредственных детей — стоимость раскрытия каталога фиксируется целиком. Blob читается исключительно для достигнутого провайдера, когда требуется его AST. Содержимое целевого конечного файла для самого факта существования пути может не понадобиться. Если ни один сертификат не подтвердился, выполняется ограниченный прямой поиск, включая корректные отрицательные ответы.

JSONL в logs содержат файлы и SHA каждого фактически загруженного исходника, OID каталогов, счётчики кэша, выбранные свидетельства и результаты сверки.

Команды для повторения из этой директории:

    python run_audit.py
    python analyze.py

Три раздельных процесса для собственного запроса, где OLD и NEW — ревизии данного репозитория, а cache.json — новый файл для записи:

    python query.py record REPO OLD source.module target.module cache.json --method one
    python query.py recall REPO NEW cache.json
    python query.py direct REPO NEW source.module target.module
