# Графовая память кодового агента в меняющемся репозитории

**Аналитический обзор.** Вопрос проекта — как на незнакомом репозитории инициализировать память по мере работы, обновлять её при изменениях в Git и давать агенту проверяемую информацию к следующему действию. Ниже отдельно обозначены результаты авторов, следствия выбранной математической модели и гипотезы для проверки. Приводимые результаты статей в этом обзоре повторно не измерялись.

## Ответ в четырёх тезисах

1. В графовой памяти инженер решает, что считать вершиной, откуда берётся ребро, что делает запись применимой и какой **исходный материал** увидит агент. Этот выбор может изменить даже знак эффекта. Набор связей без хороших исходных записей и ранжирования способен проиграть простому поиску. [Контролируемое сравнение Hu и др., ACL 2026, табл. 4–7](https://aclanthology.org/2026.acl-long.1232.pdf)
2. Существуют прямые предшественники общей постановки проекта. RepoMem подключает историю коммитов к агенту локализации. Chronos строит типизированный граф прошлых PR и отбирает опыт с учётом времени. CoSIL строит и исследует граф по запросу. Эти механизмы задают высокий порог для утверждения о новизне. [RepoMem, ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/hash/b4c06f095368497f3ac19422efef8133-Abstract-Conference.html) · [Chronos](https://arxiv.org/html/2610.11578v1) · [CoSIL](https://arxiv.org/abs/2503.22424)
3. Наибольшая неопределённость для прикладной работы возникает **после поиска**. Один и тот же предыдущий опыт может помочь слабому в этой задаче решателю и помешать сильному. Прослойка преобразования опыта в длинную подсказку сама создаёт ошибки. [VibeMemBench, §4–6](https://arxiv.org/html/2609.23570v1) · [MemDev-Bench](https://arxiv.org/abs/2610.27524)
4. Конкретный открытый вопрос для нашей программы — по каким **наблюдаемым до решения признакам** агент может выбрать режим чтения: открыть прошлый опыт, сверить с текущей версией, искать в исходниках или пропустить. Наиболее убедителен результат, показывающий, где такая политика сохраняет пользу и предотвращает перенос устаревшего опыта при равной стоимости. Публикационную новизну и прирост нужно проверять отдельно для выбранной реализации.

## 1. Из каких операций складывается память

Пусть в момент t доступны версия репозитория r, описание задачи q и префикс наблюдённой истории H. Узел события хранит команду либо факт изменения, версию, источник, краткий результат и ссылку на исходную запись. Одному событию могут соответствовать несколько файлов. Ребро задаёт конкретное отношение, например «вывод получен командой», «команда читала файл», «две сущности изменились в одном коммите». Положение в Git DAG, время доступности и записанное автором время коммита дают разные ограничения. Даже если сообщение PR датировано вчера, сегодняшняя правка его текста могла быть недоступна вчера. Дата слияния — приближение доступности законченного решения для другой задачи. При работе с ветвями проверка достижимости снимка от конкретной базы дополняет дату. Chronos отсекает по датам создания и слияния PR до даты создания целевого PR и применяет ограничение на обеих стадиях поиска. [Chronos, §2.2](https://arxiv.org/html/2610.11578v1)

**Запись.** Для узлов полезна разная степень точности. Имена символов, Git blob, путь и вывод команды допускают повторную проверку. Естественно-языковое объяснение причины — производное утверждение. Сохранение указателя с проверяемым источником делает возможным короткую подсказку и последующее чтение исходного контекста. В ряде систем исходник можно восстановить, даже если извлечение сущностей ошиблось. Это важно для повторных команд и деталей патча, где один идентификатор меняет смысл. [WikiTrace](https://arxiv.org/abs/2611.14320) · [MIRIX‑2.0, §2.2–2.3](https://arxiv.org/html/2611.12068v1)

**Поиск и чтение.** Типичная схема начинает с совпадения текста или вектора запроса, проходит по небольшому числу рёбер, переоценивает кандидатов, укладывает выбранные фрагменты в лимит и только потом передаёт их решателю. В HippoRAG вероятностный обход связывает совпавшие сущности с более удалёнными фрагментами. MAGMA переключает виды связей в зависимости от запроса. В Chronos переход по графу может открыть карточку за пределами исходной семантической выдачи. Эффект обусловлен как привлечением новых кандидатов, так и вытеснением старых при неизменном размере выдачи. [HippoRAG, NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/hash/6ddc001d07ca4f319af96a3024f6dbd1-Abstract-Conference.html) · [MAGMA, ACL 2026](https://aclanthology.org/2026.acl-long.1709/) · [Chronos, §2.2](https://arxiv.org/html/2610.11578v1)

**Обновление.** Свежая запись может дополнять старую, исправлять её, менять срок её применимости или раскрывать второе имя той же сущности. Эти операции имеют разные последствия. В Zep старые факты и их временные отношения доступны для последующего запроса. В MIRIX фоновая процедура объединяет идентификаторы при сохранении исходных свидетельств. В IMCA отдельно задаются момент истинности факта и граница доступного агенту знания. Для утверждения «эта функция прошла тест» одного совпадения имени функции недостаточно. Зависимости теста могут измениться при неизменившемся файле, а иногда изменившийся файл не влияет на проверяемый вывод. [Zep](https://arxiv.org/abs/2501.13956) · [MIRIX‑2.0](https://arxiv.org/abs/2611.12068) · [Описание артефакта IMCA](https://github.com/nicl-nno/IMCA#readme)

**Движок хранения.** Представление графа требует узлов, типизированных связей, версий и операций запроса. Его можно реализовать таблицами SQLite, списками смежности в памяти, графовой СУБД, поисковым индексом с таблицей происхождения. Смена движка влияет на задержку, расход диска и стоимость обновления. Чтобы приписать прирост качеству структуры, нужно сохранить одинаковые исходные наблюдения, лимиты чтения и решатель. CodexGraph — пример явного интерфейса графовой БД по коду, IMCA — реализации графовых запросов к данным с журналом SQLite. [CodexGraph, NAACL 2025](https://aclanthology.org/2025.naacl-long.7/) · [IMCA](https://github.com/nicl-nno/IMCA#readme)

## 4. Когда граф способен выиграть математически

**Окрестность даёт новых кандидатов.** При фиксированных множестве правильных целей R, бюджете k и двух выдачах A и B точная разность Recall@k равна (|R ∩ (B без A)| − |R ∩ (A без B)|) / |R|. Число найденных новых целей должно превышать число вытесненных. Вывод объясняет, почему хорошая доля достижимых целей и множество рёбер могут сочетаться с отрицательной прибавкой. Для эмпирической проверки можно логировать каждую добавленную и вытесненную цель, разбить случаи по доказательству ребра, степени узла и давности. Это алгебраическая декомпозиция метрики, не причинное доказательство качества системы.

**Повторяемость связи может давать дополнительную информацию.** Если X — якорь и его текст, G — наблюдаемая до ответа графовая характеристика, а Y — верный следующий файл, то улучшение *оптимального* среднего log-loss при переходе от X к (X,G) равно условной взаимной информации I(Y;G | X). Это тождество для корректного распределения и Bayes-предсказателя. На конечной выборке оценивание редких связей и смена версии могут перекрыть пользу. Для Recall@k тождество не обещает даже строгого улучшения: возможно более точное распределение с тем же порядком первых k вариантов. Простейший устойчивый контроль — предсказание по пути, популярности и недавности, затем добавление только графового сигнала. Если G полностью вычисляется из уже доступного входа X с неограниченным оптимальным решателем, дополнительная информация нулевая; практический выигрыш тогда возникает из ограничения времени или модели. Утверждать, что детерминированный граф создаёт новые данные, было бы ошибкой.

**Слишком крупная транзакция делает слабую связь популярной.** При проекции коммита с m файлами каждая вершина получает m−1 соседей. Если всем дать единицу, массовый рефакторинг создаёт за один раз сумму m−1 из данного файла. При весе 1/(m−1) сумма равна единице. Тем самым выбирается новая статистическая цель — каждое историческое событие имеет одинаковое влияние на якорь. Массовые правки могут быть информативны, поэтому улучшение Recall — гипотеза. Такая дробная проекция уже применялась Ньюманом к большим группам соавторов. Принцип ассоциативных правил для программных изменений известен десятилетия, чувствительность к максимальному размеру исторического коммита также исследована. [Newman, 2001](https://doi.org/10.1103/PhysRevE.64.016132) · [ROSE](https://doi.org/10.1109/ICSE.2004.1317478) · [Practical Guidelines for Change Recommendation](https://www.cs.loyola.edu/~binkley/papers/ase16-mining-guidelines.pdf)

**Читать можно по ожидаемой ценности.** Для двух действий, с подсказкой и без неё, пусть p+ и p− — вероятности парных выигрыша и проигрыша в данной ситуации, V и L — их полезность и ущерб, c — дополнительная стоимость обращения. Ожидаемый выигрыш чтения равен p+V − p−L − c. Отсюда следует условие сравнительного выбора. В отдельном запуске виден только один исход, и обе вероятности нельзя извлечь из результата единственной траектории. Нужны воспроизводимые парные запуски с тем же предшествующим состоянием, отдельная выборка для выбора порога и контроль калибровки. Работающий решатель может отступить от выданной подсказки; score найденного узла не заменяет p+ или p−. [Эмпирические случаи смены знака на VibeMemBench](https://arxiv.org/html/2609.23570v1) · [MemDev-Bench](https://arxiv.org/abs/2610.27524)

## 5. Что остаётся кандидатами на вклад

| Кандидат и ближайшие подходы | Механизм под проверкой | Решающий контроль и возможное опровержение |
|---|---|---|
| Избирательно накапливать связи из уже увиденных агентом операций; подбирать между путём, предыдущими совместными правками и недавностью. Близки ROSE, Newman, RepoMem, адаптивные смеси экспертов | Граф начинает с пустого состояния. Сигнал семантики пути доступен сразу, статистика связей устойчивее после нескольких наблюдений; доверие к ним может меняться | Сравнить с частотой и недавностью, сильным путевым априори, графом со сглаживанием, статической смесью при тех же кандидатах. Развернуть метрику по возрасту памяти и наблюдаемой степени. Популярные неизменные закономерности могут сделать простую смесь сильнее адаптации. Схема fixed-share и её общий механизм давно известны. [ROSE](https://doi.org/10.1109/ICSE.2004.1317478) · [Herbster и Warmuth](https://doi.org/10.1023/A:1007424614876) |
| Хранить область применимости наблюдения — выполненная операция, затронутые артефакты и версии. Близки IMCA, WikiTrace, Stratum и инкрементальные сборки | После изменения вызывается дешёвая проверка только тех сведений, чей источник затронут; при недостатке доказательств запрашивается новый вывод | Сравнить со строгим хешем, простой проверкой пути, TTL и полным повтором, тем же набором наблюдаемых зависимостей. Если проверка дороже повторов либо выход зависит от окружения вне графа, гипотеза отпадает. Поиск нового файла через glob и смена окружения — необходимые отрицательные случаи. [Build Systems à la Carte](https://www.microsoft.com/en-us/research/wp-content/uploads/2018/03/build-systems-5ab0f42d0f937.pdf) · [IMCA](https://github.com/nicl-nno/IMCA#readme) · [WikiTrace](https://arxiv.org/abs/2611.14320) |
| Оценивать применение записи по ожидаемой потере на текущем шаге и разрешать отказ от подсказки. Близки REM, Git-bound routing, VibeMemBench | Измеримый кандидат на выигрыш — меньше задач, испорченных устаревшим опытом, при сохранении числа задач, решённых благодаря релевантному опыту | Сопоставить одинаковые записи и лимит вызовов с REM-подобным условием затруднения, always-read, never-read, случайным отбором той же частоты. При равной стоимости совершенные исправления важнее выбранного порога. Если попарные потери сконцентрированы в уже различимых простым правилом случаях, добавочный механизм не оправдывает себя. [REM](https://arxiv.org/abs/2610.27377) · [VibeMemBench](https://arxiv.org/html/2609.23570v1) · [Git-bound memory](https://arxiv.org/abs/2607.14390) |

Эти направления совместимы, но проверка их общей комбинации до изолированных абляций почти ничего не скажет о причине изменения результата. Наиболее содержательный уровень новизны — конкретное правило записи или допуска к чтению, у которого заданы наблюдаемый сигнал, стоимость, пределы применимости и условия проигрыша. Сочетание Git, графа, SQLite, следов источника или нормировки само по себе уже имеет предшественников.

## 6. Как честно сопоставлять с работами

- Для **локализации из описания issue** повторить официальный набор, правила расчёта и сравнение LocAgent/RepoMem на том же снимке, с одинаковым решателем и инструментами. Прогон, где уже дан изменённый файл, отвечает на более лёгкий и иной вопрос. При сравнении с RepoMem добавить плоскую базу тех же PR и сводок. [RepoMem и таблица 1](https://arxiv.org/html/2510.01003v2)
- Для **поиска ранее решённой задачи** подходит SWE‑ContextBench, где известна связь между задачами. Отдельно считать официальный статический режим и онлайн-режим с доступными до задачи источниками. Убедиться, что записи у методов успешно построены на одних и тех же историях. Match@1, стоимость записи и чтения, а затем executable resolve — разные результаты. [SWE‑ContextBench](https://arxiv.org/abs/2602.08316) · [REM](https://arxiv.org/abs/2610.27377)
- Для **исполняемых исправлений** MemDev‑Bench связывает 555 базовых задач с 4869 историческими задачами и даёт управляемую релевантность. VibeMemBench включает 111 задач из 90 репозиториев и 3634 прошлых траектории. Во втором наборе цели намеренно отобраны по положительному эффекту предъявления истории на одном решателе. Проверка переноса на другие решатели сильнее, чем оценка на отборочном, но доля таких задач в свободной разработке здесь неизвестна. И методы поиска, и пустой контроль должны иметь одинаковые разрешённые источники для тестового запроса. [MemDev‑Bench](https://arxiv.org/abs/2610.27524) · [VibeMemBench, ограничения](https://arxiv.org/html/2609.23570v1)
- Записывать версию решателя и извлекателя, исходный коммит, порядок PR, параметры индекса, обращения всех агентов и цены offline/online отдельно. При наличии исходных записей сравнивать единый формат ответа, отдельно варьируя связь и операцию чтения. Полезный плацебо-контроль — перемешать концы рёбер внутри репозитория с сохранением типовых степеней, временной доступности и числа узлов, которые помещаются в контекст. Даже если граф улучшил hit, проверять, смог ли агент воспользоваться найденным фрагментом.
- Развести разведочный и окончательный этапы. Публиковать общее качество, выигранные и потерянные относительно контроля задачи, парные интервалы и стоимость обновления. При многократных запусках той же задачи кластеризовать по задаче, а перенос между проектами оценивать по репозиториям. Несколько формулировок, нескольких читателей и многократные выборки одного PR нельзя считать независимыми репозиториями.
- Исследовать потолок для холодного старта: долю задач, для которых правильная цель вообще существует в памяти к моменту поиска. Стратегии «хранить только увиденное» нужен выход в поиск по исходникам. Преимущество в стоимости индекса требует измерения инициализации, памяти, чтений файлов, инкрементальных записей и полного числа шагов.
