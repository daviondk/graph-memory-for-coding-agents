# Точное обслуживание отзыва источника в графовой памяти

Проверяем новую идею для живой БД на уже фиксированной панели provenance_packet_demo. При отзыве исходного поля из доступного представления текущего вопроса отсекаются все ссылающиеся на него узлы. Базовые ранги, стоимости и функции полезности оставшихся узлов зафиксированы. Каждый запрос what-if независимо начинается из того же полного снимка. При переобучении баллов, изменении запроса, бюджета, рангов или добавлении узлов требуется отдельная логика обслуживания. Измеряем реальные операции с целыми источниками исходных траекторий и полный список идентификаторов, включая порядок, которые вернул бы новый расчёт.

Метод хранит множество исходных полей, связанных либо с выбранным узлом, либо с первым узлом, который не поместился в защищённый префикс. Если отзываемое поле отсутствует в этом множестве, возвращаем сохранённый пакет. В противном случае выполняем полный выбор. Удаление незатронутого поля сохраняет и префикс, и ёмкость остатка. Допустимые решения остаточной задачи сужаются, ранее оптимальный пакет остаётся допустимым. Детерминированный выбор при равенстве устойчив к удалению проигравших вариантов, поскольку сохраняется относительный порядок оставшихся кандидатов. Это достаточное, потенциально консервативное условие. Свидетель границы нужен даже когда сам узел не вошёл в результат. Дополнительно проверяем опасное упрощение, которое следит только за уже отобранными, и минимальный числовой контрпример.

До оценки фиксируем B=2048, все 40 запросов/траекторий исходной панели, каждый имеющий свидетельство источник по отдельности. Основная проверка точности — полное совпадение списков с полным новым вычислением на каждой операции. Быстрый и полный используют одну и ту же реализацию точного C++-рюкзака и одинаковую SQLite-базу метаданных. Кэш хранит идентификаторы результата и отдельный индекс зависимостей по (запрос, источник). Для схемы, использующей лишь выбранные узлы, отдельно укажем реальные ложные подтверждения и числовой контрпример. Для производительности используем три чередующихся повтора на каждом запросе с группировкой по траектории, медиану и p95, число настоящих пересчётов, добавочную цену создания кэша и число запросов до амортизации. Множество проверок шире часто используемого сценария «удалить самый частый источник». Поэтому дадим и равновзвешенный по запросам результат, и долю среди всех удалений. Для честного контроля измерим также кэш только выбранных записей с перепроверкой границы в SQL и сравним эквивалентные реализации при необходимости. Ускорение будет относиться к локальному обслуживанию запроса после подготовки проекции. Полная сборка эмбеддингов или качество последующего ответа здесь не измеряются.
