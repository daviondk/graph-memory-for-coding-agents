# Сколько выводов о тестах агент может перенести между версиями кода

При 126 разрешённых подтверждениях на 418 запросов компактная память зависимостей дала **264 правильных ответа**. Из них 126 подтверждены новым запуском, 138 — прогнозы для новой версии по наблюдениям на прежней. При том же числе подтверждений и том же размере буфера плоский фильтр с четырьмя хешами дал 218 правильных ответов. Более сильный плоский фильтр с адаптивным числом хешей дал **248**. Свежие прогоны pytest совпали с прогнозом во всех случаях, где эти три политики решились ответить. При использовании фактической маски выбора тестов специализированного pytest-testmon тот же читатель даёт **312** правильных ответов, у этого ориентира существенно больший объём исходного состояния. ## Как поставлен вопрос

У нас есть история с настоящими исходами pytest и наблюдавшимися зависимостями тестов. Код меняется. Для каждого ранее выполненного теста агент получает запрос о его исходе в **новой** версии. Он может найти историческую квитанцию, запросить фактическое выполнение, выдать помеченный прогноз или воздержаться. Для честного сравнения все политики получают тот же набор тестов и изменений. Положительный ответ «тест прошёл» и отрицательный ответ «тест упал» требуют одинакового ключа. Идентификатор теста берётся из предшествующего запуска. Поиск по правильному ответу отсутствует. [Протокол до основного запуска](PROTOCOL_RU.md) · [Запертый план](plan-lock.json)

Включены 18 уже известных из R9 задач SymPy и 209 пар «задача, тест». Рассмотрены оба направления изменения, с отдельным хранилищем в каждом. Получились 36 пакетных сценариев и 418 запросов. В 38 запросах исход сменился, в том числе в 19 случаях успешный тест стал падающим. В data loader используются имена полей `base` и `gold` из набора SWE-bench. В текущей версии доступны только сам код и список изменённых определений. Номер версии стенда однозначно связан с исходным коммитом, патчем тестов, состоянием исправления и версией среды. Прежние результаты R9 уже были известны до этой работы. Повторное выполнение служит независимой проверкой измерения на этих же примерах. ## Что действительно реализовано в MemTrace

Использовали неизменённые авторские `PageStore`, `SemanticStore`, `PlanRegistry` и `RecallService` из коммита `5508f8be81025d8aa90726b1e06aef4ea484e577`. Наш адаптер переводит фактическую фазу pytest отдельного теста в типизированный `TEST_RESULT`. На страницу записываются nodeid, булевый исход, версия и контрольная сумма конкретного свидетельства. Внешний каталог сопоставляет nodeid и идентификатор страницы, выданный хранилищем. Исторический запрос передаёт этот адрес и соответствующий MemoryRef. Таким образом, мы измеряем возврат свидетельства по известному адресу внутри публичного API. Свободный поиск, естественно-языковой вывод модели и штатное преобразование произвольного вывода терминала этим испытанием не охвачены. [Реализация адаптера](SMOKE.py) · [Оригинальная статья](https://arxiv.org/abs/2610.04838) · [Исходный код](https://github.com/Homy-Xu/MemTrace/tree/5508f8be81025d8aa90726b1e06aef4ea484e577)

В авторской реализации факты `TEST_RESULT` и `TEST_FAILURE` зависят от текущей версии целиком. При её смене компонент пересматривает валидность этой категории. Исторический запрос позволяет прочитать старую страницу с явной отметкой о времени наблюдения. Новый исход становится доступен через точный запрос после поступления свидетельства о текущем выполнении. Наша зависимость «тест → наблюдавшееся определение» и правило переноса прогнозов находятся **снаружи** авторской политики. Для передачи дополнительного свидетельства используется публичный тип `CODE_OBSERVATION`. [Типы фактов](https://github.com/Homy-Xu/MemTrace/blob/5508f8be81025d8aa90726b1e06aef4ea484e577/src/memtrace/contracts.py#L173) · [Обновление версии](https://github.com/Homy-Xu/MemTrace/blob/5508f8be81025d8aa90726b1e06aef4ea484e577/src/memtrace/semantic_memory/store.py#L857) · [Формирование временной метки ответа](https://github.com/Homy-Xu/MemTrace/blob/5508f8be81025d8aa90726b1e06aef4ea484e577/src/memtrace/recall/assembler.py#L78)

## Почему может помочь отдельная запись зависимостей

Для каждого теста собирается множество определений Python, которые наблюдались при прежнем выполнении. Несколько тестов часто используют один и тот же код инициализации. Если положить всё в отдельный фильтр Блума на тест, одни и те же определения будут многократно занимать фиксированный объём. Второй вариант сохраняет пересечение множеств один раз и кодирует остаток для каждого теста. До следующего изменения выбирается размещение с меньшей ожидаемой частотой ложного совпадения среди схем «раздельно с настройкой числа хешей» и «общая часть + остатки». Запрос проверяет пересечение с изменёнными определениями. Пустое совпадение разрешает выдать прогноз по старому исходу. Обнаруженное совпадение повышает приоритет повторного запуска и в отсутствие бюджета вызывает воздержание. Более точное кодирование способно уменьшить неопределённость, внесённую фильтрами. Граф фактически наблюдавшихся зависимостей сам по себе может пропустить влияние изменения. [Алгоритм и модель ложных совпадений](../../graph_memory_round9/budget/sketch.py) · [Чтение настоящего буфера из памяти](native_reads.py)

## Результаты при фиксированных подтверждениях

Для каждого сценария разрешено ⌊n/3⌋ подтверждений, всего 126. Свежий ответ возвращается через тот же нативный API. Для проверки альтернативных расписаний заново исполнили **36 полных пакетных прогонов с 418 результатами**. Оценщик видел их все, политика могла использовать только выбранные до исполнения 126 ответов. Эта схема измеряет бюджет доступных подтверждений. Замер ускорения CI потребовал бы физических прогонов каждого расписания по отдельности. |---|---:|---:|---:|---:|---:|---:|
| Без памяти, порядок по SHA | 126 | 0 | 292 | 126 | 0 | 0 |

| Переносить любой неподтверждённый исход | 126 | 292 | 0 | **404** | **14** | **12** |

**Основное сравнение.** Фиксированный плоский фильтр даёт правильный ответ на 52,15% всех запросов, выбор с общей частью — на 63,16%. Парная разница +11,00 п. п., 95% percentile bootstrap по 18 задачам [+0,55; +22,75]. У четырёх задач есть выигрыш, у остальных 14 ничья. Два направления одной правки объединены в один блок. В панели из 10 задач результат вырос со 100 до 134 из 212 (+16,04 п. п., интервал [0; +35,72]); в панели из восьми других задач — со 118 до 130 из 206 (+5,83 п. п., [0; +17,48]). Эти панели входят в общую оценку. [Первичная конечная точка и выигрыши по issue](results.json)

**Более сильный контроль.** После получения основного результата через такую же нативную страницу отдельно прогнали адаптивный плоский фильтр. После настройки числа хешей разница сократилась до 16 ответов, +3,83 п. п., 95% интервал [0; +10,29]. В первой панели у обоих 134/212. Во второй — 114→130/206. Все 16 улучшений приходятся на две задачи. Этого недостаточно для уверенного вывода о переносимости эффекта выделения общей части. [Вторичный протокол](POSTHOC.md) · [Квитанции](adaptive-native.gz) · [Результаты](adaptive-results.json)

**Сколько стоит ошибка.** Если у каждого верного ответа ценность +1, у воздержания 0, а у ошибки −λ, основной вариант получает 264, безусловный перенос с подтверждениями — 404−14λ. На этой панели они равны при λ=10. Когда ошибка относительно дешева, по этому критерию выгоднее безусловный перенос. Ошибки двух типов могут иметь разную цену. В таком случае надо отдельно учитывать 12 ложных pass и 2 ложных fail. При оценке, требующей установленного текущего выполнения, все ограниченные политики возвращают ровно 126 подтверждений.

**Системные ориентиры.** В дополнительном ретроспективном расчёте тот же читатель с тем же числом подтверждений получает 264/418 от несжатого графа зависимостей. На двух запросах различается основание даваемого ответа (подтверждение или прогноз), однако итог и покрытие совпадают. При замене сигнала на маску фактически исполненных тестов из независимого прогона официального pytest-testmon 2.3.1 он получает 312/418, из них 126 подтверждений и 186 верных прогнозов. Источник признака здесь — лишь принадлежность теста к набору запущенных; исходы выбранных тестов из журнала testmon в прогноз не подставляются. Это ссылка на наблюдавшуюся селекцию R9 с другим объёмом состояния (медиана исходной БД 110 592 байта на сценарий) и другим способом сбора зависимостей. Первичная серия сравнивает два наших способа записи через один нативный компонент MemTrace. Маска testmon служит вторичным техническим ориентиром. Результаты относятся к переносу исходов тестов. Сравнение опубликованного end-to-end показателя решения SWE-задач потребует отдельного эксперимента. ## Затраты и границы результата

По 256 байт на тест дают по 107 008 байт сериализованных буферов на формат или по 142 760 байт Base64. Это одинаковый бюджет научно сравниваемой нагрузки. Общая таблица адресов тестов в компактном JSON занимает 41 582 байта на все 36 сценариев. Дополнительные адреса буферов заняли 2 376 байт в фиксированном и 2 484 в структурном варианте из-за длины имён. С учётом всех чтений обоим читателям понадобилось по 580 запросов к памяти, включая 418 исторических страниц, 36 буферов и 126 текущих подтверждений. Нативные счётчики прочитанных байтов страниц — 966 621 против 967 283; оценка токенов возвращённых нативных блоков — 638 780 против 639 119. В этих числах нет платного LLM-инференса. Суммарный логический размер совместных архивных баз после закрытия — 48 924 778 байт, в ZIP — 4 762 920. В этих физических архивах присутствуют две альтернативные версии буфера, сам SQL-индекс и служебные страницы. Отдельные расходы постоянной памяти процесса и CPU на построение графа не оценивались. [Подробные счётчики](costs.json) · [Адреса настоящих возвращённых страниц](addresses.gz)

Все запросы относятся к одному проекту. Набор тестов — задачно-ориентированная панель, состоящая из ранее изученных исправлений и выбранных контрольных тестов. Удвоение направлений помогает наблюдать переходы в обе стороны на тех же тестах и не удваивает число независимо выбранных правок. Основная соль фиксирована; проверка нескольких солей в R9 измеряла поведение кодирования, но не выполняла эту политику подтверждений. Отсутствие ошибки в 138 прогнозах не гарантирует безопасность переноса статуса в других проектах и средах. Для статьи диагностически ценнее всего случаи, где специализированный инструмент нашёл больше переносимых исходов, и отдельная оценка при изменении конфигурации или внешних зависимостей. Для end-to-end вывода нужны новые проекты, независимый от прежних опытов набор правок и реальные расписания исполнения. [Первичные наблюдения](outcomes.gz) · [Сравнение с R9](verification.json)

## Воспроизведение на данном стенде

Все команды запускаются из этого каталога. Для обращения к модулю MemTrace используется существующий дистрибутив WSL CodexX20MSR с Python 3.12 и зависимостями R6. Сборка тестов — отдельная venv Windows на Python 3.11.15, pytest 7.4.4, py 1.11.0 и mpmath 1.2.1. CPU, без модели-решателя. Проверить имеющиеся результаты можно командами `python -B score.py`, `python -B adaptive.py score` и `python -B systems_reference.py`.

Для полного воспроизведения используйте отдельную копию рабочего дерева с теми же относительными путями панелей, т. к. шаги генерации будут перезаписывать собственные артефакты. Последовательность команд в PowerShell:

```powershell
$linuxDir = '/mnt/d/CodexResearch/x20-bench-workspace/work/graph_memory_round10/provenance'
python -B common.py
wsl.exe -d CodexX20MSR --exec python3 -B "$linuxDir/native_reads.py" first
python -B plan.py
& 'D:/CodexResearch/x20-round9-test311-runtime/venv/Scripts/python.exe' -B confirm.py
wsl.exe -d CodexX20MSR --exec python3 -B "$linuxDir/native_reads.py" current
python -B score.py
wsl.exe -d CodexX20MSR --exec python3 -B "$linuxDir/adaptive.py" forecast
python -B adaptive.py score
python -B systems_reference.py
```

При повторном запуске длительности тестов, хеши исходных квитанций, архивные метки времени и физические служебные расходы могут измениться. Проверяемые свойства — состав панели, воспроизводимость исходов, нативная маркировка, порядок выбранных подтверждений, объёмы сырых буферов и метрики.
