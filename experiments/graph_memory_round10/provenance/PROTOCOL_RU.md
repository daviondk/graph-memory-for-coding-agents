# Проверка происхождения ответа о тесте после смены версии

Протокол зафиксирован до запуска нативного MemTrace на экспериментальных данных. Ранее результаты тестов, графов и способов хранения измерялись на этих панелях в R9. Это дополнительный интерфейсный эксперимент на известных данных, без нового закрытого бенчмарка. Предварительный технический пример SMOKE.py использует вымышленные тест и ревизии только для проверки API.

**Задача** — вернуть исход конкретного теста в новой версии, показать, где был фактически получен каждый результат, и разделить текущий запуск, прогноз по наблюдавшимся зависимостям и воздержание. Сравниваем компонент MemTrace и варианты одного внешнего читателя; состав системы и исключение родного LLM-решателя сообщаются явно.

## Наблюдения и бюджет

Берём все подходящие пары из R9/testmemory_compat (10 задач из R8) и R9/testmemory_holdout (8 непересекающихся задач из R7). Направления base→gold и gold→base считаем раздельно в независимых экземплярах базы, для интервалов объединяем в блок одной задачи. Нет отбора запросов по исходу, изменившейся ветке, результатам методов или уверенности. Запрос формируется из заранее наблюдавшегося nodeid и номера версии. Порядок для разрешения ничьих определяется SHA256 от заранее заданных task, direction, node. Исходим из нейтральной записи TEST_RESULT с булевым success; одно и то же имя ключа работает для passed и failed. Источником статуса являются отчёты pytest, а не имя группы FAIL_TO_PASS. Вывод отдельного node из пакетного запуска не является утверждением, что команда для одного node исполнялась отдельно.

Используются неизменённые PageStore, SemanticStore.advance_workspace_revision, PlanRegistry и RecallService авторской реализации MemTrace, commit 5508f8be81025d8aa90726b1e06aef4ea484e577. Публичный typed Event/EvidenceDraft адаптирует реальные отчёты pytest на уровне отдельных тестов к native TEST_RESULT. Адаптер присваивает стабильный ключ и сохраняет возвращённый PageStore handle. Он не является реализацией provider-normalizer и не эмулирует селекцию всей системы. Запечатываем по одной странице факта на тест, запускаем настоящий нативный переход версии. В семантическое хранилище передаются адреса изменённых файлов. Следы будут наблюдаемы по ключу теста и по историческому адресу, любая политика получает одинаковые наблюдения, одинаковый интерфейс и одну страницу на запрос, до 8192 нативных токенов ответа и 128 КиБ чтения страниц и blob на один fault.

**Нативные конечные точки.** Проверяем полноту ответа по точному ключу прежней версии до изменения, по точному ключу текущей версии после изменения до нового запуска, по нативному MemoryRef исторической страницы при запросе из новой версии и по точному ключу текущей версии после записи нового фактического результата. Учитываем coverage state, реальные источники/версию, страницы и байты, соответствие возвращённому nodeid и исходу. Старый witness допустим как исторический. Исторический результат не помечается как прошедший в текущем снимке.

**Добавляемое свидетельство.** Исторический пакет наблюдавшихся зависимостей записывается отдельным CODE_OBSERVATION и возвращается нативным recall. Группа может один раз считать эту страницу целиком; последующие запросы используют декодированный публичный payload. Изменённые символы текущей правки подаёт среда отдельно всем ветвям. Сравниваем обычное плоское размещение и формат со структурой, выбранной правилами R9/sketch.py между адаптивным плоским и общей частью с остатками. Фиксируем seed=0, ровно 256 байтов на тест суммарно на пакет, включая заголовки. У вариантов один отсортированный список тестов, равные байты пакетов; список nodeid, служебные ключи и физические расходы архива учитываются отдельно. Название CODE_OBSERVATION служит транспортом наблюдения о прежнем выполнении. Запись в текущий TEST_RESULT по одному сходству запрещена. Ключи и временные метки тестовой версии — идентификаторы стенда, журнал содержит реальные исходные файлы и их хеши.

## Общая downstream процедура

На задачу и направление разрешено B=floor(n/3) подтверждений. У всех ограниченных политик точно B ответов с текущим выполнением при доступном корректном результате. Запросы на оставшиеся факты не получают текущих ответов из базы. Сравниваем (1) отсутствие памяти, подтверждать по SHA, остальные запросы пропустить; (2) строгий MemTrace, используя исторический результат для приоритета прошлых падений, остальные без свежего доказательства пропустить; (3) небезопасный контроль прежнего статуса, те же приоритеты и B, остальные выдать как предположение; (4) плоская и (5) структурная память. Для последних в первую очередь подтверждаем тесты с положительной проверкой пересечения, внутри групп — сначала ранее падавшие, затем SHA. Читатель может выдать прогноз по историческому исходу только при отрицательной проверке в **фактически восстановленном** пакете; неоднозначный неподтверждённый запрос приводит к воздержанию. Сама политика обоснования и размер бюджета у двух представлений одинаковы. Позитивный контроль confirm-all вне B и контроль «повтори весь прошлый статус без единого подтверждения» отдельно показывают границы.

Планы и подтверждения читаются отдельно от будущих исходов. После хеша плана заново исполняем одинаковые тесты на обеих текущих версиях в отдельной тестовой среде R9 Python 3.11, далее записываем реальные TEST_RESULT в MemTrace и считываем по точному ключу. При вычислении решений открываются только результаты разрешённых подтверждений, остальные доступны оценщику. Связь с независимым R9 контролем по каждому node проверяется. В повторном запуске исполняем целиком одинаковый набор тестов на задачу; B измеряется числом доступных ответов, а не числом физических вызовов и временем CI. Сбой подтверждения/разногласие сохраняется.

Первичен парный контраст числа правильных ответов (подтверждения + явно помеченные прогнозы) / всех запросов у структурной и плоской записи. По каждой политике выдаём количество подтверждений, прогнозов, воздержаний, верных/ложных ответов, ложных pass, достаточность нативных доказательств, число байтов, долю принятых запросов и условную точность. Считаем 95% percentile bootstrap по задачам с обоими направлениями вместе, 10000 выборок, seed 1019; также даём результаты обеих панелей. Нулевая эмпирическая ошибка не является гарантией сохранения статуса после изменения. Сравнение не воспроизводит DeepSWE, pass@1 опубликованного решателя или глобальный SOTA.
