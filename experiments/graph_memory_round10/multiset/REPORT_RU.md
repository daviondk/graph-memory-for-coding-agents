# Какие зависимости запусков тестов стоит хранить вместе

На 18 уже исследованных задачах SymPy мы проверили, можно ли сжать граф наблюдаемых зависимостей «символ → тесты» так, чтобы агент после изменения кода реже повторял уже выполненные проверки. При 256 байтах на тест статический XOR-словарь дал ровно набор тестов исходного графа на всех 36 запросах и всех 32 солях. Важная проверка новизны — обычный компактный словарь отсортированных отпечатков практически достиг того же результата. Выигрыш по отношению к предыдущей системе R9 невелик. Для статьи остаётся открытым вопрос о стоимости обновлений при изменении связей и о переносе на незнакомые репозитории.

## Что представляла собой память

Из старого запуска каждого теста берётся множество наблюдавшихся символов программы, включая зависимости общего этапа запуска. После изменения кода запрос передаёт список затронутых символов. Эталон хранит множества полностью и выбирает тест, если пересечение с запросом непусто. Компактное состояние возвращает битовую маску выбранных тестов. В основу всех сравнений положены одни и те же трассы, тесты, запросы и границы двух ревизий. У одной задачи две стороны перехода. Каждая сторона независимо получает собственное состояние. В исследовании нет модели-решателя или сравнения качества ответов LLM.

Проверены 10 задач из первой панели R9 и 8 задач, отложенных в R9. В R10 обе панели уже известны. Всего оценены 418 пар «тест × направление», 244 получает точный граф и в 38 действительно меняется результат pytest. Все 38 изменений входят в точный граф на этом наборе. Упаковка каждого варианта занимала ровно число тестов × 64 или 256 байт, с учётом заголовков, соли, таблиц и заполнения. Граф и словарь имён символов декодер не получает. Позиции тестов имеют общий для всех методов контракт. Таблица превращения позиции в строку pytest вне сравниваемого состояния; её внешнее JSON-представление имеет разброс 126–850 байт, медиана 744,5 байта на снимок. Данные и учёт длины доступны в [протоколе](PROTOCOL.md) и [квитанции проверки](verification.json).

## Что объясняет результат

У зависимостей одного символа может быть один и тот же набор тестов с зависимостями многих других символов. Значением в словаре служит номер класса равных битовых масок. Для встречавшегося ключа XOR трёх ячеек, с добавлением привязанного к ключу отпечатка, восстанавливает назначенный номер. Недостающие при узком бюджете маски заменяются ближайшей доступной надмаской. Это даёт одностороннюю ошибку для любого записанного ключа. При равномерном независимом w-битовом номере для незнакомого ключа ожидаемое количество ошибочно выбранных тестов равно сумме мощностей сохранённых масок, делённой на 2^w. Это предположение о хеше, поэтому ниже приведена отдельная эмпирическая проверка.

При 256 байтах все 1152 состояния системы XOR используют таблицу XOR. При 64 байтах в 128 из 1152 состояний минимальная таблица не поместилась и применился обычный OR бакетов. Для оставшихся состояний укрупнение классов допускает ложные положительные даже по записанным ключам. Выбор по прогнозу риска по старому графу совпал с результатом XOR на измеренных запросах. В четырёх снимках при 64 байтах селектор мог использовать другое представление. В реализации словаря сжатых бакетов риск включает как коллизии известных ключей, так и среднюю заполненность бакетов на неизвестных ключах с весами 1:1. В исходном протоколе краткое описание этой строки упоминает только второй компонент. Конкретная функция была зафиксирована вместе с кодом до декодирования.

Flat-Bloofi воспроизводит логику транспонированного индекса с поправкой на малое число фильтров: позиции битов соседних тестов упакованы плотно, а число хешей выбирается из 1–8 по старым мощностям множеств. Использованы исходная идея и собственная реализация Python/NumPy. Для сравнения XOR заимствованы известные статические отображения и трёхадресное построение с удалением рёбер. Сохранение классов тестов, их укрупнение по бюджету и формат записи реализованы в опыте. Дополнительный словарь сохраняет монотонную последовательность усечённых отпечатков методом Elias–Fano, объединяет коллизии через OR и оплачивает маски и коды их классов. Выбирается самая большая поместившаяся ширина среди 4–24 бит по старому снимку. Затраты на хеширование и пересборку измерены отдельно. [Flat-Bloofi](https://arxiv.org/abs/1501.01941) · [Оригинальный код Flat-Bloofi](https://github.com/lemire/bloofi/blob/f08504ad83a9bcf1b849e70f933259ec9d7b30fb/src/mvm/provenance/FlatBloomFilterIndex.java) · [Статические отображения и Bloomier filters](https://arxiv.org/abs/0807.0928) · [XOR filters](https://doi.org/10.1145/3376122) · [Elias–Fano в индексах](https://arxiv.org/abs/1206.4300)

## Незнакомые запросы и проверка на всём старом графе

В первых 36 запросах было всего 54 появления изменённых символов; 50 из них уже наблюдались в прежних зависимостях. В 32 из 36 обновлений все ключи были известны. Поэтому ноль дополнительных наблюдаемых запусков оставляет значительную неопределённость относительно запросов другого вида. Дополнительные проверки зафиксированы после обнаружения этой особенности. Они характеризуют механизм чтения и не измеряют поведение программы после искусственного изменения. [Протокол](ROBUSTNESS_PROTOCOL.md) · [Результаты](challenge_results.json)

На каждом из 36 снимков проверены 256 гарантированно отсутствующих ключей, всего 107 008 решений «ключ × тест» на соль. Между задачами переносились настоящие списки изменённых символов из остальных 17 задач в том же направлении. Получены 612 пар снимок–запрос и 7106 решений на соль. Из 918 перенесённых вхождений символов 283 знакомы принимающему графу. Исчерпывающая отдельная проверка всех 47 406 записанных ключей по снимкам при соли 0 обнаружила у XOR **1729 лишних битов** при 256 байтах и 69 248 при 64, при полном сохранении истинных битов. Следовательно, совпадение результатов на 36 естественных запросах не означает безошибочную реконструкцию всей памяти.

## Интерпретация для следующего исследования

На этой небольшой выборке хранение общих классов зависимостей эффективнее большинства фильтров при умеренном бюджете. Уже известный метод сжатия отсортированных ключей почти воспроизводит результат. Для разграничения причин полезен новый репозиторий с реальным потоком вставки и удаления связей, заранее зафиксированный порядок запросов и диапазон доли новых символов. Там можно измерять число изменённых байтов на добавление связей, задержку до следующего корректного чтения и суммарную стоимость повторного запуска тестов. Полная статическая пересборка XOR и компактного словаря служат практическими точками сравнения для такой задачи. Текущая работа опирается на статические снимки и наблюдённые зависимости. Подтверждение эффекта для качества решения задач агентом потребует отдельных запусков агента.
