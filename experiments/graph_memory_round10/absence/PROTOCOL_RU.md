# Память неуспешных поисков после появления модуля или ресурса

Вопрос — следует ли работающему агенту сохранять, какие конкретные модули или ресурсы он искал безуспешно при выполнении операции, чтобы решить, когда переиспользовать прошлый результат? Две границы проверки: настоящие опубликованные пары релизов tzdata и контролируемые установки официальных опциональных зависимостей в четырёх существующих проектах. Наблюдения в этих группах оцениваются отдельно. Исследователь выбирал случаи по документации о появлении зон и наличии опциональных функций, выборка обогащена механизмом. Синтетический механизм из R9 не входит.

**История релизов.** Берём полные наборы TZif из пакетов tzdata 2022.1→2022.2, 2022.6→2022.7, 2025.1→2025.2, обратные переходы отдельно. Выполним действительную стандартную библиотеку zoneinfo на выделенном TZPATH с ресурсами этих релизов и без venv-пакета tzdata. Известные целевые идентификаторы Europe/Kyiv, America/Ciudad_Juarez, America/Coyhaique. На каждом переходе проверяем их все, плюс стабильные UTC, Europe/London и America/New_York. Возвращаем доступность зоны и числовые UTC-смещения в середине января и июля фиксированного года 2025. Включаем любой реально изменившийся ответ, даже если он вызван обновлением содержимого старого TZif. Все шесть запросов, включая ещё отсутствующие целевые зоны, присутствуют в каждом блоке. Это история выпусков данных; не обозначаем её как исправления Python-кода. Данные одной серии релизов образуют один проект.

**Контролируемые установки.** tabulate (CJK и wcwidth), markdown-it-py (автоссылки и linkify-it-py), NetworkX (экспорт графа в pydot), fsspec (LZ4 и локальное сжатие). Для каждого проекта заранее фиксируем две осмысленные операции в его публичном API — целевую и простую контрольную, плюс вычисление стандартной библиотеки. Выполняем A→B, B→A для реального опционального пакета и A→P, P→A для постороннего пакета six в том же каталоге. Для NetworkX ставится основная зависимость pyparsing, для Markdown mdurl и uc-micro-py; компоненты, нужные в обоих вариантах/для работоспособности опционального модуля, присутствуют в обеих версиях. Актуальные совместимые с Python 3.11 колёса будут зафиксированы по версии, URL и хешу. Не меняем код библиотек. Систему, локальную установку пакетов и существующее окружение R9 не изменяем. Версии с одинаковой рабочей папкой и расположением vendor сравниваются в новых процессах. Проверяем отсутствие неявных установок опционального модуля в состоянии A.

**Метод.** В каждой операции получаем независимый процесс. Исполнитель прослеживает успешные обращения к локальным модулям/файлам и неуспешные поиски модулей (в конце meta_path) и файлов (фактический отрицательный isfile внутри TZPATH). Для каждого запроса записываем его имя и корень поиска. Конкурируют сохранение без проверки, только положительные наблюдения в изменённых файлах, переоценка на изменениях в наблюдавшемся каталоге при любом таком промахе, переоценка только при появлении соответствующего ключа плюс положительные наблюдения, и безусловное повторное выполнение. Проверяем и настоящий pytest-testmon 2.3.1 со штатным отслеживанием среды и с действительными метаданными установленных wheel. Ключи записываются из старого выполнения, предсказания фиксируются хешем до открытия новых записанных исходов. Решение о выборе не видит новых ответов; доступен только обычный список добавленных, изменённых и удалённых файлов. Производственный импорт и чтение проходят через оригинальные реализации; инструментация только наблюдает. Регистрация контекста и глобальное инспектирование файлов в измерительных целях не являются рабочей памятью метода.

Основной исход — изменилось ли каноническое значение прикладной операции (в т.ч. нормализованная наблюдаемая недоступность функции). Дополнительно фиксируем обычный двоичный исход интеграционного pytest с заранее заданным контрактом для полноценной функциональности. Установочные и обратные переходы указываем раздельно, placebo отдельной строкой. Считаем размер выдачи, пропущенные изменения, лишние проверки при неизменном значении, а также маргинальный размер отрицательной и полной памяти в сериализованном виде. Оригинальный testmon оптимизирует pytest и может штатно повторять ранее падающие тесты и реагировать на состав колёс. Интеграционные тесты для наших workload явно отделяются от исходных тестов самих проектов; где официальный тест доступен, дополнительно фиксируем его исход/skip. Результат на нескольких выбранных парах не устанавливает общее преимущество и не сравнивается с лидербордом памяти агентов.
