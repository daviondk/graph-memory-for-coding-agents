# Сколько читает БД, когда агент запрашивает несколько строк после правки

На **1 282** переходах Handoff Debt обратное отображение диапазона сократило число строк, переданных из SQLite ленивому читателю, с **36 441 до 11 787 (−67,65%)**. На всех переходах клиент получил ровно тот же набор наблюдений. На тёплом соединении среднее время запроса на заранее выбранных 128 переходах уменьшилось с **30,89 до 20,91 мкс**. Отношение времени **0,677 [0,533; 0,781]**. Более сильный контроль заранее материализовал текущие номера строк в индексе. Его диапазонный запрос занял **4,47 мкс** и вернул ровно **5 775** нужных строк. Отложенный перенос оказался в **4,67 раза [3,02; 6,66]** медленнее готового индекса на чтении. [Результаты](results.json) · [Условия до замера](PROTOCOL_RU.md)

## Как выполняется запрос

Входные данные содержат старые наблюдения, интервал правки [a,b], смещение δ и свежие наблюдения из ответа редактора. Пусть клиент запросил [l,r]. На участке выше правки БД ищет старые строки в [l, min(r,a−1)], а на участке ниже — в [max(b+1,l−δ), r−δ]. Третий диапазон извлекает свежие свидетельства по их текущим адресам. При совпадении адресов применяются свежие записи. Если место правки неизвестно, доступны только эти свежие записи. SQLite использовал ограничение по обоим концам диапазона составного первичного ключа для каждого из трёх поисков. [SQL-запрос](query.py) · [План SQLite](seal.json)

Вместимость памяти создаёт условие корректности. Если оставшиеся кандидаты конкурируют за общий лимит, отдельный локальный диапазон может содержать факты, вытесненные более приоритетными строками за его пределами. На записи сохраняется консервативный признак возможного переполнения: число старых и новых наблюдений до их объединения превышает 128 и правка локализована. В **37 случаях** запрос вычислил точный глобальный отбор. Для них объём остался **5 297 строк** в обоих вариантах. На остальных 1 245 переходах он снизился с **31 144 до 6 490**. Этот флаг требует одного дополнительного значения в заголовке перехода. [Числовые префиксы и результаты по запросам](forecasts.json.gz)

| Способ исполнения | Строк получено от SQLite, 1 282 запроса | Среднее время тёплого запроса, мкс |
|---|---:|---:|
| Полностью вычислить отложенное состояние, затем отобрать диапазон | 36 441 | 30,89 |
| Протолкнуть диапазон через отображение правки | 11 787 | 20,91 |
| Прочитать все материализованные строки, затем отобрать диапазон | 28 391 | 11,40 |
| Прочитать диапазон по готовому первичному ключу | 5 775 | 4,47 |

В 522 из 1 282 окон память содержала хотя бы одну запрошенную строку. Каждое окно задавалось первой и последней строками следующего видимого просмотра. Такой интервал позволяет проверить ретроспективную нагрузку. До запроса его границы при записи памяти не использовались. Все четыре схемы проверены дополнительно на **2 240 синтетических диапазонах** с пустыми окнами, удалениями, ростом и сокращением участка, повторяющимися адресами и переполнением. Результаты совпадали и с отдельным оракулом. [Независимая проверка](verify.py)

Время измерено на одном компьютере на 128 переходах из 31 задачи, для каждой задачи хранения использовались все 24 перестановки порядка вызовов. Для эпизода брали медианное время блоков, затем считали среднее по эпизодам и парный интервал по задачам. SQLite-строка в этой таблице — запись, доставленная Python из запроса. Физические чтения диска и просмотренные записи внутренней виртуальной машины — другие измерения. Данный опыт измеряет только фазу чтения после подготовки обеих БД. Связанный опыт содержит отдельные измерения записи и полных чтений. [Устройство файлового хранения](../code_store/REPORT_RU.md) · [Время всех блоков](timings.json.gz)

Воспроизведение из этой папки: `python study.py`, затем `python verify.py`. Нужны NumPy, штатная SQLite в Python, соседние подписанные каталоги `code_store` и `code_visibility` и доступ к диску D для временных физических баз. Запускать в рабочей копии. Повторное измерение времени создаёт новые файлы исходов в этой копии.
