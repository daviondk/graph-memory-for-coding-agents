# Как хранить номера строк после правки файла в SQLite

Отложенная запись смещения и квитанции редактора сократила время самой записи почти вдвое относительно таблицы с переносимыми слотами. При первом полном чтении этот выигрыш сохранился против слотов, а сравнение с простой таблицей по адресу дало **82,85 против 80,62 мкс** на переход, отношение **1,028 [0,939; 1,116]**. На четырёх чтениях простая таблица оказалась быстрее: **114,87 против 181,18 мкс**. Все три реализации сохранили точную выдачу в **1282 из 1282** реальных эпизодов Handoff Debt. [Метрики](results.json) · [Протокол](PROTOCOL_RU.md)

## Задача хранения

В исходном опыте агент видел несколько строк рабочего Python-файла, сделал локальную замену и получил пронумерованную квитанцию редактора. Старые наблюдения выше затронутого диапазона сохраняют номера, нижние сдвигаются на разность числа переводов строк. Квитанция имеет приоритет. Ёмкость логической памяти — 128 фактов «путь, номер, SHA-256 текста». Ранее проверено покрытие следующего наблюдаемого просмотра файла. Здесь все схемы выдают фиксированный ответ той же политики T. Вход SQLite-оператора образован только из первого просмотра и подтверждённого изменения. Будущие координаты чтения ему неизвестны. [Эксперимент с реальными строками](../code_visibility/REPORT_RU.md) · [Handoff Debt, EMNLP](https://aclanthology.org/2026.emnlp-main.738/)

- **A, таблица по адресу.** Ключ SQLite — пара «эпизод, номер строки». После получения квитанции реализация читает текущее состояние и меняет только различающиеся ключи или хеши. Читатель получает сразу упорядоченные готовые пары.
- **M, таблица слотов.** Внутренний rowid стабилен, для адресного чтения служит вторичный индекс. Совпадающие пары остаются на месте. Остальные слоты используются повторно, в первую очередь для перемещения того же хеша. Если осталось d лишних пар и нужно a новых, число изменяемых строк не меньше max(d,a), поскольку одна операция может убрать и создать максимум по одной паре. Переиспользование min(d,a) слотов достигает этой границы. Порядок слотов для потребителя не наблюдаем. Обновления совершаются одной транзакцией; уникальность номеров проверена во всех конечных ответах.
- **L, отложенный перенос.** Исходный снимок остаётся в таблице. Транзакция записывает строку границ и видимые факты квитанции. Чтение одним запросом UNION ALL получает нужные строки и применяет перенос и общую квоту в клиенте. Восстановление выполняется при каждом полном чтении.

Проверка использует 1282 независимых перехода из 37 задач. Для каждого эпизода заново подготовлен исходный снимок. Несколько эпизодов одной задачи могут повторять схожую ситуацию; статистическая повторная выборка сохраняет их в одном кластере. Это микробенчмарк одной правки при наличии предыдущих наблюдений. Для цепочек правок потребовались бы композиция интервалов и отдельные решения о материализации. [Префиксные входы](prefix_inputs.json.gz) · [Реализации](storage.py)

A и M выполняли по одному SELECT при записи и при чтении, по 1282 каждого вида. L выполняла только 1282 SELECT при чтении, а во внутренних ветвях запроса обращалась к нескольким таблицам. Счётчик прочитанных строк описывает передачу строк из SQLite клиенту. Прочитанные с устройства страницы в эксперименте не измерялись.

L изменила на 4,75% меньше строк относительно M; кластерный 95% интервал отношения **[0,796; 1,197]** допускает обратный порядок на других задачах. В 242 эпизодах L изменила меньше строк, в 24 — столько же, в 1016 — больше. Агрегированный выигрыш сосредоточен в дорогих переходах. На 102 строгих эпизодах основной группы направление действительно поменялось: L — 923 записи, M — 667, A — 787. В самой большой дополнительной группе из 659 эпизодов L — 7494, M — 9059, A — 11 671. [Счётчики каждого перехода](full_counts.json.gz)

Изменённая строка таблицы и кадр журнала относятся к разным единицам. Один и тот же кадр сохраняет целую страницу, а вторичный индекс и раздельные таблицы меняют набор затронутых страниц. В полном прогоне L записала в WAL **на 7,98% больше кадров, чем M**, и **на 61,65% больше, чем A**. Физический размер журнала измерялся на диске D после каждой транзакции с отключённым автоматическим checkpoint. Число кадров независимо восстановлено по 32-байтовому заголовку WAL и расходу 24 + 4096 байт на кадр. Это объём журнала SQLite в данном порядке эпизодов; системное кэширование и внутренняя запись накопителем могут изменить физический трафик. [Спецификация формата SQLite](https://www.sqlite.org/fileformat2.html#walformat)

## Запись и повторное чтение

128 эпизодов из 31 задачи выбраны по заранее зафиксированному SHA-256. В их числе 13 основных строгих эпизодов. Выполнены разогрев и шесть блоков, дающих все шесть порядков реализаций у каждого эпизода. Измерение включает подтверждение транзакции и восстановление полного ответа. Файлы расположены на диске D, SQLite 3.50.4 с WAL и synchronous=NORMAL, Python 3.12.13, один процесс, тёплые данные. Загрузка исходного корпуса и подготовка таблиц исключены. Дополнительные три чтения в последней строке — контролируемые повторные запросы к одной версии без кэша готового ответа в приложении; корпус не задаёт эту частоту.

| Запись + одно чтение | 80,62 мкс | 101,48 мкс | 82,85 мкс | **0,816 [0,762; 0,875]** | **1,028 [0,939; 1,116]** |

Интервалы получены 10 000 парными перевыборками задач после усреднения шести повторов каждого эпизода. По циклам потока вывод для одного чтения тот же: отношение L/M **0,807 [0,752; 0,867]**, L/A **1,031 [0,937; 1,129]**. Отложенный перенос ускорил запись через SQLite; в этой реализации восстановление переложило часть работы на читателя. Простая таблица готовых адресов сочетает меньший WAL с быстрым повторным чтением и сопоставимым общим временем уже при первом обращении. Для персистентной памяти потребуются отдельные измерения холодного кэша, адресных запросов к части файла, повторного использования полных ответов и нескольких последовательных правок.
