# SQLite для адресов наблюдений после одной правки

Повторяем по одному переходу на каждом из 1282 подписанных эпизодов R37/code_visibility. Вход оператора включает только предшествующее фактическое чтение, новую квитанцию и границы замены, уже вычисленные из видимых событий. Тексты и наблюдения будущего просмотра при построении исключены. База содержит до 128 старых пар (номер строки, SHA содержимого). Готовый ответ — все до 128 пар политики T, включая приоритет квитанции. При превышении ёмкости используется тот же фиксированный порядок по хешу пути и номера. Измеряются независимые одношаговые переходы с заранее подготовленным состоянием; состояние соседних эпизодов не переносится. Не экстраполируем эти измерения на длинную цепь редактирования.

Сравним три схемы. A материализует текущие ответы SQLite c первичным ключом (эпизод,номер) и записывает только различия по ключам. M — сильный контроль с физическими слотами и вторичным индексом по номеру. После исключения неизменившихся пар он назначает оставшиеся слоты новым парам, предпочитая перенос одинакового хеша, и использует минимальное возможное число insert/update/delete, если произвольное обновление слота стоит одну операцию. L оставляет исходное чтение неизменным и при записи сохраняет одну строку границ изменения плюс факты квитанции; первое и последующие чтения применяют перенос к записям исходного снимка. Реализации обязаны дать тот же полный набор ответа для каждого из 1282 переходов, включая случаи новых и удалённых строк, частично видимой квитанции и ограничения ёмкости. Объём исходного заполнения и накладные расходы разных индексов будут обозначены отдельно.

Главный инженерный вопрос — экономит ли L реальные записи и дефицитное время «запись + первое полное чтение» относительно M; дополнительно сравниваем с A по обеим метрикам. Основной счётчик записей — SQLite total_changes в подтверждённой транзакции; он считает строки таблиц, физическую запись страниц оценим отдельно по приращению журнального файла WAL при отключённой автоматической контрольной точке. Отдельно считаем вызовы SELECT и возвращённые строки при подготовке записи и каждом полном чтении; размеры основного файла и WAL не трактуются как суммарные операции физического носителя. Записываем время записи с коммитом, первого полного чтения и четырёх чтений (первое + ещё три); операции выполняются на локальном диске D с WAL и synchronous=NORMAL, один процесс, тёплый кэш. Хранится одна логическая запись на реальный эпизод в общей таблице каждой схемы.

Полная сверка COUNT, WAL и выдачи идёт по всем 1282 переходам. Для физических таймингов фиксируем 128 эпизодов с минимальным SHA-256 от строки R37-code-store|episode_id. Один разогрев и шесть измерительных блоков; в каждом блоке используются независимые подготовленные таблицы и все реализации получают идентичные состояния. По каждому эпизоду используются все шесть порядков реализаций за шесть повторов. Первичная оценка — отношение суммарного времени монотонных часов после усреднения повторов каждого эпизода; парные 95% интервалы — 10 000 кластерных перевыборок исходных issue, seed=371542. Циклы потока — вторичные. Описываем возможное ухудшение и число кластеров. Файлы временных БД содержат только координаты и хеши.
