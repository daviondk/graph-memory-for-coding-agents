# Спрос на память после реальной правки, включая отсутствие повторного обращения

До определения исходов фиксируем единицу анализа: успешная подтверждённая замена str_replace рабочего Python-файла в Handoff Debt, имеющая связанное предыдущее явное чтение того же пути с хотя бы одной информативной строкой по фильтру R37/code_visibility. Между этим чтением и ответом редактора не должно быть иной успешной записи или попытки записи по этому пути, действие и квитанция целевой замены должны совпасть по идентификаторам. При подсчёте знаменателя не используем наличие следующего чтения. Строгое исходное состояние дополнительно требует отсутствие между предыдущим чтением и записью непрозрачных действий (в том числе терминальных) или разрыва потока; исходные состояния с такой неопределённостью регистрируются отдельно. Отдельно отчитаемся за исходные и основные запуски и за дополнительные прогоны тех же задач. Повторяющиеся записи одной задачи объединяются в один статистический кластер.

После успешной квитанции считаем каждое строгое чтение того же пути — успешный типизированный view с хотя бы одной информативной строкой. Отдельно считаем физически наблюдаемые успешные view и те, где есть любая пронумерованная строка. Квитанция своей правки не является повторным чтением. Следующая подтверждённая файловая мутация закрывает версию; если в интервале от действия до успешной квитанции было чтение этого пути или непрозрачность, такой интервал считаем неопределённым с начала попытки. Неуспешная или неподтверждённая попытка записи того же пути консервативно прерывает наблюдение. Первый непрозрачный инструмент или разрыв публикации даёт цензуру, даже если версия формально могла остаться прежней. Чтение другого пути само по себе не закрывает окно.

Завершение всего запуска признаём при явном успешном FinishObservation, связанном с предшествующим FinishAction, отсутствии более поздней команды агента/квитанции и отсутствии зарегистрированной ошибки запуска. Неявный конец публичного журнала, ошибка или неполная пара Finish — правая цензура. Отдельно запишем индексы и пропуски исходного событийного журнала. При R=0 и границе «подтверждённая следующая мутация» или «подтверждённый конец» получаем наблюдаемый ноль для этого наблюдаемого интерфейса. При границе непрозрачности/обрыва R=0 — отсутствие зарегистрированного чтения до границы; делить эти случаи с завершёнными нулями запрещает постановка. R≥1 гарантирует хотя бы один явный возврат в наблюдаемом интервале. Покажем идентификационные границы частоты нулевого спроса без допущения о независимой цензуре и распределение R по видам границы. Отдельно подсчитаем зарегистрированные возвраты после непрозрачного шага до следующей явной мутации, сохраняя неопределённость версии.

Сопоставим с предыдущей R37/code_store, где попадание в 1282 эпизода требовало следующего чтения. Если есть полностью наблюдаемые окна, выполним новый физический replay замороженных A/M/L из R37/code_store для 128 завершённых чистых исходных состояний с минимальным SHA-256 от R37-natural-demand|episode_id (всех, если их меньше), включая нули, без отбора по R. Одна запись с подтверждением + R полных SQLite-чтений, один разогрев, шесть перестановок реализаций на эпизод. Считаем полный выход детерминированной политики и сверяем при каждом фактическом запросе. Поскольку подлинный агент вызывал редактор файлов, один полный запрос памяти на каждый строгий view — явное модельное соответствие. Новые замеры используют истинные кратности обращений внутри выбранных окон, из записей не следует, что авторские агенты вызывали SQLite. Тёплый кэш, диски D, WAL+NORMAL, методы не получают будущую кратность. Главный системный контраст L/A по времени операции записи плюс все обращения, вторично L/M; разрезы нулевых/положительных окон описательные. Для интервалов по корпусу и таймингам 10 000 парных перевыборок issue, seed=371802. Архивирует только числовую информацию, хеши и метаданные состояний.
