# Можно ли дёшево исключить глобальный отбор по вместимости

При штатной ёмкости 128 записей дешёвая исходная проверка потребовала полного отбора в 37 из 1 282 переходов. В 34 из них он действительно необходим по числу допустимых строк. Четыре сводных блока по старым адресам сохранили все **37** срабатываний и то же число прочитанных строк SQLite — **11 787**. Даже проверка по полному множеству старых адресов могла сократить только три полных отбора и доводила расход до **11 403 строк**. Основная гипотеза об экономии с четырьмя блоками при ёмкости 128 не подтвердилась. [Наблюдения](results.json) · [Протокол](PROTOCOL_RU.md)

Эта задача возникает перед диапазонным чтением отложенной графовой памяти. При переполнении приоритеты всех уцелевших фактов определяют, какие локальные строки доступны клиенту. Если вместимости заведомо достаточно, можно прочитать только локальный диапазон. Для каждого упорядоченного блока старых адресов храним минимум, максимум и число записей n. Внутри диапазона блока осталось не более u возможных позиций после исключения заменённого интервала и старых адресов, на которые легла новая квитанция. Тогда число живых строк ограничено сверху величиной min(n,u). Блоки не пересекаются. К сумме оценок прибавляем число уникальных строк квитанции. Если полученная граница помещается в память, проталкивание клиентского диапазона сохраняет точный результат. [Вывод интервалов и алгоритм](guard.py) · [Базовая реализация диапазонного чтения](../range_read/REPORT_RU.md)

| Ёмкость памяти | Простая сумма | Один блок | Четыре блока | Восемь блоков | Точная проверка всех адресов |
|---|---:|---:|---:|---:|---:|
| 16 | 758 | 633 | 582 | 562 | 522 |
| 32 | 320 | 269 | 244 | 231 | 212 |
| 64 | 83 | 77 | 74 | 72 | 67 |
| 128 | 37 | 37 | 37 | 37 | 34 |

В таблице дано число записей, для которых требуется полное вычисление по соответствующему правилу. В дополнительном режиме 16 записей четыре блока снимали **176 из 236 ложных срабатываний**. За это нужно хранить в среднем 13,51 байта на краткое описание старого чтения в заданном кодировании без накладных расходов БД. Для режима 16 измерялись решения предохранителя. Физические запросы SQLite исполнялись только при 128. Все пять вариантов совпали с готовым индексом на всех 1 282 запросах, суммарно вернули 5 775 требуемых пар. Проверка вложенности верхних границ и сравнение с точным счётом выполнены также на пяти тысячах синтетических конфигураций. [Прогнозы выбора плана до чтения эталона](decisions.json.gz) · [Поштучные физические результаты](measured.json.gz)

Для этого корпуса при 128 записях дополнительная метаинформация не окупилась по первичной метрике. При тесной ёмкости изменение числа срабатываний заслуживает отдельного измерения затрат на поддержку и чтение. Для воспроизведения в рабочей копии выполните `python guard.py` из этой папки. Нужны соседние папки `code_store` и `range_read`, штатный sqlite3 Python и диск D для временных БД.
