# Достаточно ли нескольких границ для точного диапазонного чтения

В опыте range_read из 1 282 переходов 37 отправлены на полный глобальный отбор, потому что сумма старых строк и размера квитанции выше вместимости 128. Эта агрегированная частота и объём полных просмотров уже известны. До вычисления более точных границ фиксируем основной вариант из четырёх равномощных последовательных блоков старых адресов. Контроли — исходная сумма, один или восемь блоков, точная проверка числа живых адресов по полному множеству старых ключей. Тестовая панель повторно используется для диагностики оператора.

Для блока храним его первый и последний адрес и число наблюдений. По правке и адресам квитанции вычисляем количество возможных позиций, которые могут выжить в этом диапазоне. Суммируем по блокам минимум этого количества и числа элементов блока. Добавляем все адреса квитанции. Если верхняя граница не превосходит 128, глобальный отбор не может вытеснить возвращаемую строку. Иначе используем прежний точный путь с вычислением всех кандидатов. Метод не приближает сам ответ.

Первичные показатели — количество переходов, избежавших глобальной операции относительно исходного предохранителя, суммарные строки SQLite→клиент и полное совпадение пар адрес/хеш с материализованным эталоном. Дополнительные — сколько раз только точный контроль мог бы избежать операции; нагрузка на параметризованный контроль при ёмкости 16, 32, 64, 128, подсчёт размеров сериализованного синопсиса. Для всех ёмкостей обе политики одинаково заново обрезают исходную память и квитанцию до выбранного лимита. Вторичные бюджеты служат проверкой чувствительности числа решений; физическое исполнение запросов измеряем при штатных 128. План не обещает ускорения времени работы. Сериализованные границы — накладные расходы при хранении старого чтения, в основном режиме синопсис нужен на записи правки.
