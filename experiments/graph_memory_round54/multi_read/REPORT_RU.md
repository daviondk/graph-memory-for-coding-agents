# Исторический top-k после добавления и отзыва свидетельств

На естественных знаковых правках рёбер из 40 трасс ISETrace самый простой из проверенных вариантов — упакованный снимок top-8 при изменении результата — дал наименьшее среднее время при восьми чтениях на транзакцию. Для хранения интервалов членства с баллом понадобилось **218,11 мс против 175,42 мс** за весь прогон. Отношение времён **1,24** (парный 95% ДИ от 1,11 до 1,40); интервальная схема медленнее в 7 из 7 повторов. Результат характеризует небольшие k и данную нагрузку. Он уточняет, когда имеет смысл поддерживать источник по отдельности. [Регистрация](PROTOCOL_RU.md) · [Результаты](results.json)

## Запись и чтение

Вход — 1 072 атомарных коммита, 1 264 рождения источников, 464 суммарные ненулевые операции над рёбрами, включая 118 отрицательных. Целочисленный балл производителя равен сумме активных исходящих весов. При одинаковом балле выигрывает меньший ID, источник с нулевым баллом остаётся доступным. Для всех k используется одна версия top-8. Из неё запрос забирает первые 2, 4 или 8 пар (ID, балл), а при меньшем числе доступных источников — весь список. Предыдущие системы раунда сохраняли только одного победителя.

Пусть V(t) — упорядоченный список допустимых пар на версии t, Q(t) — множество тех же пар. Для исходного снимка требуется одна новая запись тогда и только тогда, когда V(t) отличается от V(t−1). Для рангового блока достаточно сравнить только отрезки V(t) и V(t−1) в этом блоке. Результат чтения равен конкатенации последних сохранённых блоков. Для истории членства открываем интервалы ровно для Q(t) ∖ Q(t−1), закрываем для Q(t−1) ∖ Q(t). Пока (ID, балл) непрерывно входит в Q, смена ранга внутри top-8 не требует записи. Сортировка всех живых пар по общему порядку затем точно восстанавливает V(t). Это устанавливает число необходимых границ именно для представления непрерывными интервалами одной пары, независимо от величины и направления изменения веса.

У интервального представления 717 открытий и 398 закрытий. В 952 случаях пара сменила ранг внутри top-8 с сохранением ID и балла: каждое такое перемещение можно было пропустить именно при поддержке членства. При чтении всё равно нужно проверить границы пригодности версий. План запроса использовал покрывающий индекс, упорядоченный по баллу и ID. Снимку нужен один поиск последней версии по индексу, у блоков максимум три, у ранговых позиций до восьми. Блоки уменьшили полезную нагрузку с 6 784 до 4 244 байт (−37,4%), но дополнительные ключи и фиксированный размер страниц SQLite сохранили полный размер БД равным 180 КиБ. Отношение времени блоков к снимкам при восьми запросах — 1,024 [0,974, 1,086].

Операционная нагрузка с восемью чтениями содержит 8 576 обращений после коммитов, половина — к текущей версии, половина — к случайной более ранней. Для одного чтения выбирается более ранняя версия. Значение k циклически изменяется для всех планов одинаково. Время полного прогона — затраты на создание схемы, обновления, обработку запросов и финальный checkpoint. Обработка включает границу транзакции и валидацию запрошенной версии. Прогретое чтение измерялось отдельно 512 историческими запросами на каждое k после 64 прогревочных запросов. При k=8 чтение схемы членства было в 1,78 раза медленнее снимков [1,72, 1,83]. Это измерение включает SQLite, Python и декодирование ответа.

## Проверка и границы

После удаления рабочего кэша и повторного открытия SQLite независимый оракул восстановил баллы из всех накопленных весов рёбер и отсортировал их заново. Пять планов вернули те же целые ID и баллы на 1 112 версиях с учётом пустых исходных состояний, для всех трёх k — 16 680 проверок публичного API и столько же исторического пути, включая последнюю версию каждого эпизода. Проверены откат после записи изменившейся истории, повтор транзакции, конфликтующая квитанция, запрос будущего состояния и последовательная смена двух соединений-писателей. Измерение использовало семь перемешанных блоков, всего 105 созданий и прогонов БД. Каждая серия выполнялась последовательно одним локальным процессом; фоновые процессы ОС, нагрузка других программ и состояние системного кэша могут влиять на время. Интервалы повторов описывают локальную воспроизводимость. Параллельная нагрузка, более крупные k и влияние на качество решения задачи не измерялись.
