# Версионное чтение нескольких источников при отзыве свидетельств

До измерения фиксируем один общий максимум M=8 и запросы k∈{2,4,8}. На каждом коммите наблюдаемые транзакции R53 q01–q40 задают рождение источников и знаковые изменения весов рёбер. У доступного источника балл равен сумме активных исходящих весов; нулевые баллы остаются допустимыми. Возвращаем до k пар (ID, точный балл), сортировка по баллу убывающе, затем по целому ID возрастающе. Версия 0 пуста. Исторические результаты должны совпадать побитно по целым значениям с независимым полным пересчётом.

Пять заранее выбранных схем поверх одинаковых атомарных таблиц и текущего упорядоченного индекса: (1) упакованный снимок всего top-8 только при изменении хотя бы одной пары; (2) история каждой ранговой позиции, запись при изменении её пары; (3) три общих для запросов блока рангов [1,2], [3,4], [5,8], запись изменившихся блоков; (4) интервалы членства в top-8 по ID и баллу, без записи при изменении только позиции; (5) интервалы всех кандидатов при рождении или изменении балла с покрывающим индексом в порядке результата. В (1)–(3) используем компактное целочисленное кодирование без потерь. Для позиций и блоков каждый нужный блок ищется по последней версии одним индексным проходом; запросы группируются в один SQL statement. В (4) и (5) интервалы проверяются под общим покрывающим score-индексом. Для текущей версии всем доступен одинаковый текущий индекс. План (4) — проверяемая идея: ранговые перестановки внутри множества не требуют записи, однако предикат версии повышает стоимость чтения.

В каждой транзакции в (1)–(4) оцениваем действительный текущий top-8 после подписанных правок с помощью SQLite индекса. Общий кэш последнего максимального вектора валиден только при совпадении номера версии, после рестарта допускается восстановление по БД. Ширина единого представления и исходный поток совпадают для всех k. Сравниваем (4) с (1) по полному времени при 8 чтениях на коммит как основное операционное сравнение. Отдельно будем сообщать результаты всех пяти схем и нулевого и одного чтения. Используем повторяемые исторические/текущие запросы R53, циклический k со стартом, зависящим от коммита. Семь полных повторов, порядок планов и нагрузок случайно перемешан внутри повтора фиксированным seed 540263, один рабочий процесс. Время от создания схемы до завершения checkpoint, отдельно запись, чтение, checkpoint. Замеры warm history-only для каждого k — отдельный короткий набор (512 запросов на k и повтор, одинаковые ревизии для всех планов, прогрев). Эффекты в зависимости от распределения задержек/данных и от конкретной конфигурации SQLite локальной машины, 95% percentile bootstrap повторов для отношения средних. Публикуем выводы и при отсутствии выигрыша. Другие задачи на машине и состояние дискового кэша не контролируем полностью.

Проверяем запуск с пустого состояния, все сохранённые версии и k, атомарный откат, точный повтор транзакции и отказ при несовпадающей квитанции, запрос будущего состояния, смену лидера при отзыве источника, план SQL, размер основной БД после checkpoint, число записей истории и размер полезной нагрузки. Отдельные логические границы смены рангов не считаются независимыми экземплярами. Без новых LLM-вызовов и метрик QA.
