# Точный top‑8 по изменяющимся импортам Python

На 714 последовательных переходах Git в шести проектах резерв из 12 кандидатов позволил всем четырём проверенным алгоритмам обойтись без повторного запроса рейтинга при прогретом кеше. При ёмкости 8 собственная граница для объектов за пределами кеша сэкономила **один запрос и одну строку** относительно сильного контроля по Yi et al. Все шесть запросов холодного запуска выполнялись на непустых базах. С учётом этих запросов ёмкость 8 потребовала 48 строк, ёмкость 12 — 72 строки. Между политиками не было ни одного расхождения в результате top‑8.

## Как построена нагрузка

В каждом проекте заранее зафиксировали 120 снимков по цепочке первых родителей. На каждом снимке AST всех отслеживаемых обычных Python-файлов, включая тесты, определяет статические локальные импорты. Балл файла равен числу **разных** файлов, которые его импортируют. Одновременные импорты одной и той же цели из одного файла дают голос один раз. В SQLite передаются только рождения ID и пакет знаковых изменений рёбер между двумя коммитами. Для верификации отдельно по каждому полному снимку построены хеши всех рёбер, ранжирование всех баллов и эталонный top‑8. Синтаксических ошибок при разборе в этой выборке не встретилось. ## Результаты SQLite

Все политики используют один индекс по репозиторию, убывающему баллу и ID. Метод cutoff запоминает последние 8 результатов. Eager поддерживает точность всего резерва. Lazy хранит известные пары и верхнюю границу для остальных. Partial использует тот же сертификат и при его отказе дочитывает суффикс. Classic — реализация точного префикса переменной длины с индексным заполнением недостающего суффикса, адаптированная к пакетным обновлениям и устойчивому порядку при одинаковых баллах. Это воспроизведение алгоритмической идеи §3, реализованное в общей SQLite-системе. Все ёмкости фиксированы. Автоматический выбор ёмкости из статьи в данный эксперимент не входит. [Yi et al., *Efficient Maintenance of Materialized Top-k Views*](https://cse.hkust.edu.hk/~yike/topk/icde03.pdf) · [Дополнительная регистрация partial до измерений](EXTENSION_RU.md)

Таблица считает строки, возвращённые SQL-клиенту, а не посещённые страницы B-tree. В обоих режимах единственное тёплое расхождение пришлось на переход с изменившимся графом. Среди 56 таких переходов была одна обязательная непустая холодная загрузка в непрерывном режиме. Во всей рабочей последовательности lazy‑8 выполнил 5 154 SQL-операции, из них 1 572 SELECT, 1 327 возвращённых SELECT-строк и ещё 191 строка UPDATE … RETURNING. Classic‑8 добавил один SELECT и одну возвращённую строку. Преимущество по времени и по качеству ответа LLM эти измерения не устанавливают. [Счётчики основного сравнения](results.json) · [Сравнение при равных ёмкостях](extension-results.json)

**Почему отличается один коммит.** В tox при изменении 39 положительных и 62 отрицательных рёбер восьмой файл `src/tox/config/cli/parser.py` снизился с 30 импортёров до 29, ID = 11. У классического префикса прежний порог был (30, −11). Он запросил одну строку для заполнения восьмой позиции. В истории lazy уже была записана более узкая верхняя граница (29, −11) для отсутствующих в кеше файлов. Новый ключ восьмого файла совпал с этой границей, поэтому рейтинг однозначно определялся имеющимися сведениями. На остальных пяти проектах выигрыш равен нулю. [Коммит tox](https://github.com/tox-dev/tox/commit/62bd8cf9bfd5e8e5f3e8426b04645e6aa4ba5f0e)

**Холодная загрузка и хранение.** До первого рабочего перехода извлекли 518 уникальных Git-блобов объёмом 5 579 147 байт для 551 пути и вставили 1 648 рёбер. Общее начальное наполнение потребовало 5 773 SQL-операции, включая 6 запросов к ещё пустым индексам и 2 217 INSERT. На этом шаге для всех политик базы заняли 286 720 байт в сумме. Затем соединение каждого проекта было закрыто и создано заново. Отдельные непустые холодные чтения шести баз включены в таблицу. В режиме периодических рестартов дополнительно закрывали соединение перед 26-м, 51-м, 76-м и 101-м рабочим переходом каждого проекта. Для построения последующих эталонных снимков AST прочитано ещё 1 620 ранее не встречавшихся блобов, 41 417 885 байт. Это стоимость генератора и проверки, не стоимость обслуживания верхней границы. Во всех режимах после checkpoint итоговые SQLite-файлы заняли 364 544 байта в сумме. Материализованные ответы заняли 42 строки с суммарно 678 байтами полезной нагрузки.

**Граница вывода.** Эти шесть историй подобраны по наличию локального зеркала и нужной глубине. Проекты различаются по размеру и интенсивности изменения импортов, у Requests найден только один результативный переход. Статистический вывод по сотням зависимых коммитов завысил бы объём независимых данных. Здесь можно заявлять точность и объяснить один наблюдаемый выигрыш при L=8. Для большинства переходов и всех методов при L=12 обнаружен эффект насыщения. Дополнительных бенчмарков или вариантов параметров после открытия результатов этого теста не добавляли.

## Воспроизведение

`python -B verify.py` проигрывает опубликованные числовые потоки по восьми политикам и двум режимам. Генерация новых репозиториев или вызов модели для этого не требуется. Для проверки исходных графов выполните `python -B verify.py --git --mirror-map mirrors.json`, где JSON сопоставляет шесть ключей репозиториев из registration.json путям к локальным Git-зеркалам с зафиксированными объектами. В текущей среде пути на D доступны генератору по умолчанию. Снимки получаются командами чтения Git, файлы проекта не исполняются. Корень исследования должен содержать реализации из соседних каталогов reserve, cutoff, multi_read и R53/churn. `verification.json` фиксирует проверенные хеши и stdout.
