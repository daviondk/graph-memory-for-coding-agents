# Оптимальный пакет при двух одновременных изменениях веса

Ранее построенный одномерный индекс возвращал полный пакет для одной поправки к источнику. Теперь двум источникам можно присвоить разные поправки одновременно. Материализуем лучший пакет для каждого сочетания чисел выбранных фрагментов этих источников. Новая выдача сравнивает несколько аффинных оценок непосредственно в SQLite. Проверили полное совпадение с прямой C++-оптимизацией в **106 134 испытаниях** на 40 проекциях ISETrace, в том числе когда выбранный контекст меняется. Ещё **8 820** сравнений с независимым полным перебором прошли на малых пулах с нулевой ценой, равенствами и пересекающимися источниками. [По случаям](pairs.json.gz) · [Код алгоритма](bank.py)

| Случай двух новых весов, среднее время на пакет, мкс | 1 280 пар, случайная выборка | 600 пар источников с наибольшим числом элементов |
|---|---:|---:|
| Полная динамическая оптимизация C++ | 54,84 | 53,78 |
| Осевая выпуклая оболочка, затем при необходимости C++ | 37,50 | 37,71 |
| Материализованные оценки в SQLite | 3,90 | 4,55 |
| Те же оценки в оперативной памяти | 0,74 | 1,19 |

На случайной панели отношение времени C++ к SQLite составило **14,08 [12,10; 16,18]**, на нагруженной панели — **11,82 [10,17; 13,54]**. Интервалы парные по целым траекториям. Ускорение относится к локальному чтению с уже подготовленными кандидатами и известной парой источников. При повторении восьми одинаковых вариантов параметров прогретый кэш точного ответа на случайной панели тратил **0,47 мкс** против **4,26** у SQLite. При новых весах в этом кэше не было попаданий. [Все времена, интервалы и контроли](results.json)

**Почему достаточно нескольких оценок.** Для каждого допустимого пакета числа отобранных необязательных фрагментов двух источников задают коэффициенты i,j. Общая для всех пакетов прибавка обязательного префикса не меняет выбор. При фиксированных i,j любая поправка (x,y) добавляет одно и то же ix+jy, поэтому достаточно лучшего исходного пакета этого класса. Среди равных по полезности пакетов выбирается меньшая битовая маска по исходным позициям. Этот порядок сохраняется после добавления неизменного префикса. Реализация один раз решает задачу на незатронутых наблюдениях, группирует варианты затронутых по численностям и стоимости и соединяет их с лучшим допустимым дополнением. В SQLite хранятся (i,j), исходное значение, приоритет при равенстве и ссылка на полный список ID. Параметрическая оптимизация известна. Здесь проверяются физическая реализация и экономия для записей графовой памяти с общим бюджетом. [Протокол и предшествующие работы](PROTOCOL_RU.md) · [Физический индекс](planes.sqlite)

Две панели пересеклись на 18 парах. Для **1 862 различных пар** потребовалось **10 927** строк оценок и **5 192** различных последовательности ID. Размер SQLite-базы **1 224 КиБ**, измеренное время построения строк и записи индекса **0,378 с**. Кандидаты, связи с источниками и рабочие массивы уже доступны в памяти до этих замеров. На случайной панели на пару приходилось в среднем 4,71 строки (максимум 13), на нагруженной — 8,44. В этих проекциях имеется 97 676 потенциальных пар. Материализованы только зарегистрированные пары, поэтому цифры по памяти нельзя переносить на все пары без отдельного измерения. На реальных выбранных парах источники не пересекались по допустимым фрагментам. Корректность пересечений дополнительно проверена перебором. Изменения весов синтетические; частота реального совместного применения определяется отдельной нагрузкой. Этот тест оценивает точность и стоимость сохранённого оптимизатора, не качество ответа LLM.
