# Когда кодовому агенту стоит повторить ранее пройденные тесты

На шести новых изменениях Loguru сохранённые сведения о вызовах не сократили число повторных проверок. Из 120 решений «изменение × тестовый файл» новое и прежнее правила графа выбрали все 120. Опубликованный NameRTS выбрал 50 и сохранил те же 36 из 36 размеченных файлов. При этом удалось локализовать узкий случай, в котором граф полезен. Если новая вложенная функция находится внутри ранее наблюдавшейся функции, можно использовать сохранённый вход во внешнюю функцию как свидетельство зависимости. На одной дополнительной ревизии при полном переборе 48 файлов это сократило выбор с 48 до 3 при сохранении обоих размеченных файлов. NameRTS выбрал 2. ## Что хранит агент и как принимает решение

Для каждой успешной проверки на исходной версии сохраняются узел тестового файла, SHA, входы в функции и номера исполненных строк Python. Память растёт по мере исполнения тестов. При новой правке сопоставляются две AST изменённого модуля. Прежняя политика либо находит устойчивое имя функции, либо повторяет проверки всех файлов, загрузивших модуль. Новая политика при добавлении вложенной функции поднимается от неё до ближайшей охватывающей функции, чьё квалифицированное имя существовало на исходном SHA. Для базовых тестов, которые уже входили в неё, назначается повтор. Несопоставимые верхнеуровневые правки сохраняют сброс по модулю. Изменение общего тестового помощника, конфигурации или неподдерживаемого файла пакета вызывает повтор всей панели. При отсутствии чистого исходного pass агент не может повторно использовать результат. Граф строится для нужных изменённых модулей из фактических наблюдений, для эксперимента с историческими SHA соответствующие тесты специально воспроизведены на настоящем родителе. [Правило соответствия](owners.py) · [Отбор и исполнение](forecast.py)

Формально при замене сброса по модулю m на фильтр по историческому владельцу f множество выбираемых файлов с валидным наблюдением сужается с импортировавших m до входивших в f, с учётом остальных затронутых сущностей и обязательных повторов. Монотонность относится к количеству выбранных файлов. Полнота требует, чтобы любое влияние нового тела на файл проходило через наблюдаемый прежний вход. Рефлексия, инициализация определений, внешние потоки, процессы, плагины и изменения условий исполнения ограничивают это предположение. Исполнитель наблюдает события только текущего потока Python. Эти ограничения важны для переноса метода в рабочий агент. [Трассировщик](worker.py)

## Перенос на заранее выбранные ревизии

Из 50 официальных target-пар 9 имели хотя бы один SHA, общий с R17 (включая прямого и истинного родителя), и 41 осталась кандидатом. Первые шесть в закреплённом хеш-порядке имеют шесть различных истинных родителей. Для каждой зафиксированы 20 из 48 файлов по отдельному хешу. Все 120 исходных запусков прошли, всего 4 545 результатов pytest item pass, включая одинаковые nodeid на разных SHA. Вмешательства не используют модель, обращения к новому SHA ограничены чтением диффа. Это тест конкретного компонента памяти агента. Результат конечного агента-решателя не измерялся. Источник разметки и предсказаний сравниваемых систем — архив авторов на фиксированной ревизии. Всеми локальными вариантами, включая выбор по модулю и по исполненной строке, найдено 36/36 (micro precision 36/120 = 30%). NameRTS нашёл 36/36 (36/50 = 72%). BabelRTS нашёл 35/36 (35/106 = 33,0%) и упустил один файл в b2a5f732. EkstaP выбрал 120 и нашёл 36. На пяти из шести ревизий нашему графу потребовалось больше повторов, чем NameRTS, одна закончилась равенством. Разность числа повторов по ревизиям составляет +6, +20, +13, +11, 0 и +20. Двусторонний точный sign-test по пяти ненулевым разностям даёт p=0,0625. В шести ревизиях недостаточно информации для точной оценки переноса на другие проекты. [Индивидуальные результаты](paired.json) · [Условные метрики и интервалы по коммитам](results.json)

Причина широкого выбора измерима. В пяти ревизиях сработал предусмотренный общий сброс для изменений pyproject.toml, тестовой инфраструктуры или файла типов пакета. В шестой все 20 файлов были выбраны и действительно размечены affected. Для этой панели дальнейший прирост требует различать зависимости от конфигурации, типов и тестовых фикстур. Проверить это можно отдельной проспективной серией, в которой захват доступа к ресурсам начинается до импорта. [Все пути и причины сброса](plan.json)

## Частота механизма и дополнительная ревизия

Слепой поиск по диффам 41 допустимой пары обнаружил два изменения, где новое правило могло снять сброс отдельного модуля. В a486a6c0 остались изменения файла типов и вспомогательных Python-файлов тестов с обязательным общим повтором. Единственной подходящей ревизией стала f64b9e37, где добавлены `Logger.catch.Catcher.__aenter__` и `__aexit__`. У обеих ранее существующий владелец `Logger.catch`. Текущая версия этой дополнительной пары отличается от всех первичных. Её истинный родитель совпадает с текущей версией одной из шести первичных пар (7748b6cd). Такая связь важна при статистическом обобщении. [Все 41 диагностированных случая](mechanism-frequency.json) · [План диагностического отбора](FREQUENCY_PROTOCOL_RU.md)

В обоих нужных файлах (`test_add_option_serialize.py` и `test_exceptions_catch.py`) граф поставил повтор. Третий файл `test_add_option_colorize.py` попал в очередь из-за исходного падения проверки автоматического цвета TTY на данной Windows-среде. Для 47 чистых файлов наш и авторский наборы выбранных совпали. Сэкономлены 45 из 48 назначений по отношению к прежнему графу. Обобщать эту величину на все 41 ревизию нельзя. ## Сопоставление с фактическим исходом и стоимость

Для первых трёх файлов каждой из шести ревизий выполнен отдельный нативный запуск на новом SHA. Среди 18 файлов пять были размечены affected. На обеих сторонах совпали все 754 nodeid, включая пропущенные pytest элементы. Все 730 исходных pass повторились. Не обнаружено ни одного перехода pass→fail или изменения статуса по фазам. Таким образом, 36/36 в основном опыте измеряет сохранение авторских зависимостей от изменившихся сущностей. Информации для оценки вероятности пропустить новое падение в этих 18 проверках нет. [Поштучная сверка](current-diagnostic.json) · [Исходы и журнал исполнения на новых версиях](current-actual.gz)

Первичная панель затратила суммарно 422,3 с времени процессов с трассировкой на 120 исходных запусков, диагностика всех 48 файлов дополнительной пары — 123,6 с (включая 51,2 с первых 20). На 18 физических запусков новых SHA пришлось 90,7 с. Эти суммы включают старт Python и работу pytest, исключают подготовку git-архивов и распаковку перед запуском. Пять процессов могли работать одновременно. Списки NameRTS, BabelRTS и EkstaP взяты из воспроизводимого авторского пакета, их время исполнения здесь не измеряли. Экономию следующих запусков допустимо выражать количеством файлов, но перевод в ускорение потребует одинаковых сквозных запусков.
