# Почему комплектование пары аргумент–результат меняет полноту

После получения общей разницы 1 083 против 1 055 полных комплектов из 2 000 запросов ISETrace проверяем предполагаемый механизм. Мы уже видели состав и небольшие подгруппы R17. Эти правила фиксируем до вычисления новых подгрупп на всём тесте. Оцениваются замороженные предсказания без дальнейшего выбора параметров.

Версия механизма: чтение противоположной стороны вызова особенно полезно, когда для ответа нужны одновременно аргумент и результат этого же вызова. Для каждого запроса по его официальным координатам определяем множество пар (ID вызова, сторона). Разделяем запросы на четыре взаимоисключающие группы: обе стороны единственного вызова, несколько вызовов с хотя бы одной полной парой, несколько вызовов без такой пары и один источник. В диагностике используем также бинарное условие существования хотя бы одной обязательной пары. Эти метки недоступны при выборе памяти. Считаем по каждому слою число запросов, число полных комплектов, выигрыши/потери/ничьи, разность полноты и покрытия, средние токены. Парный 95% bootstrap ресемплирует траектории целиком. Для бинарных групп укажем разность эффектов с общим ресемплированием траекторий. При отсутствии представителей слоя явно отмечаем отсутствие наблюдений.

Отдельная проверка затрат — классификация запросов по фактической разности числа выбранных токенов. Публикуем выигрыши и потери при равном расходе, при меньшем расходе графа и при большем. Это условные наблюдения после реализации обеих политик. Одинаковый средний бюджет не гарантирует равного числа токенов на каждом запросе, а связь между попаданием и расходом в этих слоях не доказывает причинную роль стоимости. Ни подгруппу, ни для неё подходящую стратегию после этой проверки на том же тесте не выбираем.
