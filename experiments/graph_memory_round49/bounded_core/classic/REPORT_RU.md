# Независимый статический контроль на исходных Q32-полезностях

В официальном Google OR-Tools 9.15.6755 использовали два специализированных нативных решателя бинарного рюкзака — branch-and-bound и динамическое программирование. Оба принимают 64-битные целочисленные полезности. На сайте автора minknap при подготовке прогона истекло время ожидания TLS. Вариант с OR-Tools соответствует предварительно заявленной замене. Распространяются только код обвязки и числовые результаты. [Google OR-Tools, документация knapsack](https://developers.google.com/optimization/pack/knapsack) · [Исходник OR-Tools v9.15](https://github.com/google/or-tools/blob/v9.15/ortools/algorithms/knapsack_solver.cc)

Панель из seed 13 заранее определена по хешу вопроса. Получены 128 вопросов, 125 траекторий и 512 снимков. Во всех вариантах идентичны обязательный префикс до 1 024 токенов, общий бюджет 2 048 и исходная Q32-полезность каждого фрагмента. Оба внешних решателя и обе реализации проекта нашли одинаковое значение на 512/512 снимках. У branch-and-bound выбранный упорядоченный пакет совпал с каноническим на 490/512, у OR-Tools DP и у собственной редукции к ядру — на 512/512. Различия в 22 результатах относятся к альтернативным оптимумам. Максимальное значение вместе с обязательным префиксом составило 13 564 735 622, на 498 снимках итог превышает максимум знакового int32. При каждом сравнении проверены стоимость, точные идентификаторы и порядок. [Протокол](PROTOCOL_RU.md) · [Все исходы](ledger.json.gz)

Результаты показывают важность выбора при равенствах для материализованного представления. Совпадение OR-Tools DP на этой панели эмпирическое. Его правила не заявлены как универсальная спецификация нашего контракта. Отдельный проверяющий скрипт перепроводит полноразмерное целочисленное DP с исходным правилом строгого улучшения и независимо проверяет все альтернативные пакеты. [Проверка](verify.py)

**Стоимость публичных интерфейсов.** Три перемешанных повтора после прогрева, каждый охватывает 512 состояний. Медиана времени вызовов через Python составила 45,50 мс для OR-Tools B&B и 77,48 мс для OR-Tools DP. Для собственного кода соответствующие времена составили 19,48 мс у полного DP и 5,65 мс у редукции с предыдущим пакетом. Внешний интерфейс принимает Python-списки, подготавливает четыре отдельные задачи и восстанавливает членство покандидатными вызовами. Собственный интерфейс получает предвыделенные массивы и обрабатывает четыре состояния одним вызовом C++. Данные достаточны для сравнения результатов решателей. Вывод о сравнительной скорости их нативных ядер требует единого C++-интерфейса и согласованного контракта выбора при равенствах. [Все времена](timings.json.gz) · [Сводка и SHA нативного расширения](results.json)

Для воспроизведения из этого каталога выполните `python -B verify.py` при доступном соседнем исследовании learned_stream. Чтобы повторить внешние решения и замеры, установите `ortools==9.15.6755` в отдельное окружение Python 3.12 с доступным `g++` и запустите `python -B replay.py`. Повторная запись результатов сохранит новые измерения времени, поэтому для сравнения используйте рабочую копию.
