# Физическая проверка ограниченной памяти на более длинных траекториях

**Основной вопрос.** Снизит ли зафиксированная политика cost×frequency абсолютное время до полной ранжированной выдачи при том же бюджете 524 288 байт относительно наиболее сильного прежнего простого контроля — hot-LRU, который в равной группе сохраняет более дорогие входы? Второе заранее заданное сравнение — пакетный GDSF с часами старения. Предшествующее исследование обнаружило малые положительные разности по токенам на другой панели. В настоящем опыте первичны секунды до готовности ранга. Для заявления о превосходстве по времени над обеими альтернативами требуем положительные нижние границы парных интервалов для обеих разностей. Формулы, веса и размер 31 слот неизменны. По токенам результат основной гипотезы не гарантирует сокращения времени.

**Панель до измерений.** Единственный допущенный пул — 179 состояний бывшей train-части R34. Они применялись для других задач, включая обучение ролевой регрессии R47. В R48 по 305 состояниям они не участвовали ни в выборе чисел токенной экономии, ни в восьми парах по времени. По метаданным обнаружены 25 пригодных максимальных строгих цепочек из 23 репозиториев. Цепочка принадлежит одному repo/issue/commit/run_id. Всё содержание более раннего журнала должно быть строгим префиксом следующего; из одинаковых историй берём представителя по хешу. Конечная точка максимальна по включению префикса. Длина — не меньше трёх фактически доступных в Cal500 состояний. Из всех пригодных цепочек берём первые восемь различных репозиториев по SHA-256 от последовательности state_id с солью r49-long-hardware. Сохраняем в порядке префиксов все пригодные состояния от первого до последнего. Ни токены, ни повторяемость документов, ни длительности, ни качество не участвуют в выборе. 8 репозиториев дают маломощный тест и исключают точную оценку небольшого эффекта.

**Режимы.** Qwen3-Embedding-8B Q4_K_M, RTX 3090, тот же токенизатор/исполняемый файл/четыре слота. Свежий некешированный режим — проверка качества. Три ограниченных режима сначала находят все текущие попадания, затем кодируют каждое отсутствующее значение, после чего обновляют кеш по прежним алгоритмам. Запрос всегда кодируется заново. Варианты начинают каждую цепочку с пустой пользовательской памяти. Между состояниями одного режима живут только его 31 реальный float32-вектор и ограниченные метаданные, общий для всех рабочий буфер текущего пакета освобождается. Для прежней сопоставимости при разрешении равенств используем точный SHA-ключ и конфигурацию R48. Сквозные помощники измерительного стенда видят числовые прогнозы только после завершения запроса. Модель прогревается до измерений. Четыре режима исполняются полностью по цепочке в сбалансированном Williams-порядке ABCD из четырёх строк, с двумя полными циклами по восьми репозиториям. A=fresh, B=proposed, C=cost-hot-LRU, D=batch GDSF. Повторы выбранных из-за плохого результата трасс не допускаются.

**Время и точность.** Основной end-to-end wall с момента передачи исходных строк состояния до готового полного порядка включает сборку пути/фрагмента и запроса, токенизацию, расчёт ключа, поиск и физическое чтение векторов, запросы к локальному кодировщику и сортировку. Дополнительно публикуем wall до окончания записи выбранных векторов, число/длину кодированных единиц и вызовов, сумму wall-time только RPC эмбеддинга. Раздельно измеряем занятость вычислительных GPU-движков процесса llama-server по Windows WDDM GPU Engine Running Time с шагом 100 нс; суммирование нескольких перекрывающихся движков даёт engine-seconds. При отсутствии счётчика раскрываем это явно. Он отличается от RPC wall и от времени отдельного CUDA kernel. Сверяем полный порядок, top‑5/8, косинусы, побитовые SHA векторов с независимым fresh-запуском на каждом состоянии и официальные Complete-MSS@5/8. На конечной выборке возможны расхождения формы CUDA-пакета.

**Анализ.** Основная точка — суммарное абсолютное wall до ранга. Положительная экономия определяется как 1−Σwall(proposed)/Σwall(control), отдельно даём секунды и парный баланс по каждой полной цепочке. 95%-е номинальные интервалы из 20 000 перевыборок целых репозиториев, seed 490731. Никаких выводов о статистической мощности по числу документов. Нулевой результат, выигрыш в токенах без ускорения и дрейф рангов раскрываем.
