# Перенос пакетного ансамбля на 580 вопросов ISETrace

На полной официальной development-выборке точный отбор по голосам пяти ридеров уступил точному отбору по их средней числовой полезности на 6 вопросов из 580 при архивном порядке второго чекпойнта и на 7 при первом. Оба парных 95%-ных интервала включают ноль. Выбор по расстоянию Хэмминга сократил выходной контекст в среднем на 88–90 токенов. При предоставлении контролю такого же индивидуального лимита уверенный выигрыш в полноте также отсутствует. Наблюдения дополняют первоначальные 2 000 test-вопросов. [Предыдущий тест](../packet_consensus/REPORT_RU.md) · [Протокол](PROTOCOL_RU.md) · [Все контрасты](paired.json)

ISETrace оценивает, попали ли в контекст все исходные участки трассы, нужные для ответа. Читатель возвращает подмножество целых фрагментов с общей стоимостью до 2 048 токенов. Full Support — доля запросов, где покрыт каждый символ всех эталонных участков. Для частичного покрытия рассчитана доля покрытых символов на вопрос, затем среднее по вопросам. Каждый из пяти ридеров получает свой E5-ранг и свой no-adjacency R-GCN; один общий градиентный бустинг оценивает фрагменты на пяти различных числовых проекциях. В ансамбле защищается нативный префикс до 1 024 токенов после RRF. Голос — число одиночных DP-пакетов, включающих фрагмент. Для варианта Хэмминга полезность равна `2 × число голосов − 5`. [Исходный код агрегатора](../packet_consensus/run.py) · [Подпись прогнозов](forecast-seal.json)

В основном сравнении голосование против средней полезности в точном оптимизаторе дало −1,21 п.п. [−2,72; +0,18] при первом порядке: 7 выигранных и 14 потерянных вопросов. При втором разность −1,03 п.п. [−2,62; +0,52], 8 выигранных и 14 потерянных. Жадное голосование относительно жадного отбора по средним полезностям дало соответственно +0,69 п.п. Хэмминг относительно точной средней полезности сократил контекст на 87,51 токена [75,03; 100,47] при первом порядке и на 90,12 [77,68; 103,31] при втором. Разности полного покрытия равны −0,69 и −0,34 п.п. При предоставлении контролю на каждом вопросе фактического лимита Хэмминга и уменьшении префикса до половины нового лимита разности стали 0,00 п.п. [−1,21; +1,20] и +0,34 п.п. [−0,86; +1,54]. При сохранении прежней верхней границы префикса получено 0,00 и +0,17 п.п. Предварительно заданной границы неухудшения нет. ## Границы воспроизведения

По идентификаторам вопросы и траектории development отделены от официальных train (3 894 / 2 410) и test (2 000 / 1 207). Общий HGB использовал только train. Ранговые калибраторы каждой проекции использовали по 101 train-вопросу. Бустинг выдаёт ровно те же binary64-полезности при независимом прохождении исходных Python-деревьев R39, всего 363 120 сравнений на 72 624 парах вопрос–кандидат. Разработческая разметка исторически использовалась для выбора чекпойнтов и порогов. Нынешние ансамбли применены после фиксации правил, однако перенос на другой корпус и конечная точность ответов агента требуют самостоятельной проверки. [Связь с исходным обучением](input-seal.json) · [Проверка чисел HGB](tree-crosscheck.json)

E5 Recall@5 совпал с прежними метриками на каждом запросе всех пяти семян. Для CPU-восстановления оригинальных R22-весов средний нативный Recall@5 совпал с сохранённой метрикой обучения до округления binary64 во всех пяти случаях. Точный исторический полный порядок R22 на каждом запросе не сохранён. Для R34 доступна проверка по каждому ID: повтор той же модели на CPU изменил 174 из 2 900 полных ранжирований, в том числе 8 упорядоченных top-5. Изменились составы 2 из 2 900 индивидуальных пакетов и по 1 из 580 у `votes_dp` и `mean_dp`. Изменение порядка хотя бы одного индивидуального либо ансамблевого пакета обнаружено на 11 разных вопросах. В этом перекрёстном контроле обе метрики покрытия сохранились на каждом вопросе для всех 12 вариантов. Основная таблица для R34 использует исходные GPU-порядки.
