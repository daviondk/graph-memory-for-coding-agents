# Проверка переводов строк в текстовом контроле

При сверке входов десяти прежних пилотных состояний обнаружена особенность Windows. Токенизация через стандартный ввод нормализовала CRLF. В трёх запросах получились соответственно 490, 1 384 и 506 токенов вместо 492, 1 387 и 509 зафиксированных квитанциями Qwen. Первоначальные типы модели, сетка параметров и наборы полей оставлены прежними. До оценки качества на 204 состояниях повторяем все этапы подготовки и обучения вспомогательного лексического контроля с двоичным файлом входа (`llama-tokenize -bf`). В точечных проверках на четырёх пилотных запросах, содержавших CRLF, все длины через двоичный файл совпали с Qwen. Сохраняем первичную гипотезу, маску, бюджеты и то же эмбеддинговое вычисление на всех 214 состояниях. Временные файлы входного текста существуют только на локальном диске D и закрываются после токенизации. Для окончательной сверки сохраняем отпечаток и численные итоги по всем кандидатам и запросам. [Протокол контроля](MATCHED_INPUT_RU.md)

При проверке двух документов одного состояния обнаружен второй источник различия. Пакетная обработка через специальный разделитель дала длины на один токен меньше одиночной обработки, хотя в этих двух строках не было CRLF. Для окончательных результатов все 25 901 уникальные строки отдельно отправлены точно в тот же локальный HTTP-обработчик llama.cpp с теми же настройками tokenizer. CPU-экземпляр сервера использовал те же веса и не вычислял эмбеддинги. Два отличавшихся массива токенов исправлены до объединения локальных рангов с отложенной разметкой. Данные об этих проверках сохранены в [фиксации токенов](matched-token-seal.json).
