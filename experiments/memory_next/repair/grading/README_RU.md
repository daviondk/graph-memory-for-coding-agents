# Официальная проверка исправлений SWE-ContextBench Lite

На четырёх заранее выбранных идентификаторах используются неизменённый модуль swebench_memory.harness.run_evaluation и образы jiayuanz3/swecontextbench. Код всех 16 модулей проверен против Git blob из зафиксированного дерева. В отдельной сборке CodexX20MSR сверены digest образа, HEAD и дерево Git с закреплённой версией исходников. Артефакты и образы находятся на диске D. [Исходный код оценщика](https://github.com/jiayuanz3/SWEContextBench/blob/12ad6ab14e18e9378e1e293c9edbc3f7ce43d27b/swebench_memory/harness/run_evaluation.py)

## Устройство проверки

Все 12 назначений на локальной Qwen3.8-27B израсходовали лимит 24 обращений и вернули пустой diff. Официальные результаты составляют 0/4 в каждом условии, 0/3 при равном весе целевых PR, по четыре ничьи в каждом парном сравнении. Оценщик зарегистрировал No patch до исполнения тестов на всех 12 отправках. Тесты действительно выполнялись в положительном и инертном контролях каждого образа. Наличие чтения в протоколе не подтверждает, что прочитанное помогло агенту. Преимущество одной из трёх политик в исправлении кода здесь измерить не удалось.

| Условие | Обращения модели | Входные токены | Выходные токены | Запись доступна | Детали фактически показаны | Запросы чтения | Решено |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| brief | 96 | 572 861 | 6 860 | 3/4 | 0/4 | 1 | 0/4 |
| eager | 96 | 503 927 | 5 834 | 3/4 | 3/4 | 1 | 0/4 |
| on_demand | 96 | 547 050 | 7 616 | 3/4 | 3/4 | 3 | 0/4 |

Сумма по 288 последовательным обращениям составляет 1 623 838 входных и 20 310 выходных токенов, включая повторяемую историю. Время работы циклов решателя суммарно 1 918,3 с. В двух условиях счётчик запросов включает попытки прочитать недоступные или уже показанные детали. Указанные расходы относятся к фактическому локальному запуску.

Оценщик применяет официальный тестовый патч и получает статусы необходимых тестов перед исправлением. Затем применяет предсказанный патч и получает их повторные статусы. Результат берётся из опубликованной функции расчёта resolved. У разных языков и репозиториев есть авторские особенности запуска и парсинга. В одном из четырёх случаев исходная реализация запускает каждый из 102 тестов в собственном контейнере до и после применения патча. Точный пакет сравнения — FAIL_TO_PASS и PASS_TO_PASS из конкретной записи.

Для каждой ячейки создаётся уникальный run_id, собственные временные образы и свежие контейнеры. Используется штатный флаг --no-remove-instance-image для сохранения исходного образа на повторные запуски. Остальные параметры выставляет сам опубликованный оценщик. Сохранены его консоль, поштучные статусы до и после, отчёты и коды возврата. Официальный лог test_output.txt хранит распознанные им статусы. Это уровень детализации оригинального инструмента. Для пустого патча инструмент возвращает No patch до исполнения тестов. Такой исход учитывается как непринятое решение.

В положительном контроле на каждом целевом коммите подан эталонный патч. Во втором контроле подан патч, добавляющий только нейтральный текстовый файл вне кода и тестов. Третий контроль отдельно использует пустую заявку. Эталон принят в 4/4 случаях, инертный патч после реального исполнения тестов отклонён в 4/4 случаях. Пустой патч также отклонён для всех четырёх целевых задач. Результат на четырёх формулировках приводится вместе с тремя уникальными целевыми PR: две формулировки одного репозитория имеют одинаковые исходный коммит и эталонные патчи.

Решатель работает в другой копии контейнера. Ему передаются только разрешённые входы, а метки и проверочные патчи остаются на стороне оценщика. Для оценки программа принимает только candidate.patch из завершённой ячейки и сверяет его размер и SHA-256 с complete.json решателя. Каждая полученная заявка оценивается один раз. Сохранённый отчёт используется повторно только после проверки хеша. Эксперимент не заменяет 99-задачный end-to-end бенчмарк.

## Проверка материалов

- upstream_pin.json и image_manifest.json подтверждают версии оценщика, среду, фиксацию входных записей и базовые коммиты.
- per_trial.csv содержит один результат на заявку или контроль, время, имя независимого запуска, размер и хеш входного патча.
- summary.json и calibration_and_graded.json показывают охват, диагностические и основные исходы и парные разности по задачам. Окончательная выборка должна содержать 12 контролей и ещё 12 назначений решателю.
- official_execution.zip содержит отчёты, журналы и индивидуальные receipts. Полный эталонный патч можно загрузить из закреплённой публичной записи; дополнительные копии патчей и prediction.json исключены из этого вложенного архива.
- seal.json фиксирует SHA-256 проверяемых файлов. При пересборке из оригинального каталога seal.py проверяет каждую запись тестов и консоли по её индивидуальному receipt, суммирует официально распознанные статусы и упаковывает результаты.

Для воспроизведения укажите SWE_CONTEXT_DATA с подкаталогом case_metadata. Поместите модули в соседнюю repair/upstream, загрузите четыре исходных образа по тегам и проверьте контрольные суммы. Команды выполняются внутри Linux / WSL с доступом к тому же Docker Engine.

```bash
python3 grading/grade.py manifest
python3 grading/grade.py calibrate
python3 grading/grade.py ready
python3 grading/audit_test_paths.py
python3 grading/seal.py
```

Для проверки архива на обычном компьютере служит `python verify_archive.py`. Живой watch.py нужен только во время генерации патчей, чтобы ставить в очередь новые подтверждённые результаты. Модель в оценщике не используется.

Контроль доставки исправлений через штатные workspace.shell и workspace.patch выполняется в новом одноразовом контейнере. После изменения искусственной tracked-строки и создания нового файла следующая оболочка прочла оба изменения, а два последовательных извлечения дали один diff в 334 байта. Квитанция patch_transport.json привязывает проверку к версии функций, исходному образу и контрольной сумме diff.

После заполнения 12 ячеек audit_test_paths.py проверяет совпадения между путями из каждой отправленной правки и файлами из закрытого для решателя тестового патча. В открытой сводке выводятся количества совпадений. Имена скрытых тестов и файлов остаются на стороне оценщика. Совпадение файла считается основанием отдельно проверить принятую правку с флагом оценщика --ensure-patch.

Файл matched_groups.json соединяет квитанцию решателя с официальным исходом по хешу отправленного исправления. Доля решённых задач считается двумя способами. При первом каждая из четырёх формулировок имеет одинаковый вес. При втором сначала усредняются результаты формулировок для одного целевого pull request, затем три полученных значения имеют равный вес. Дубликаты сверены по репозиторию, номеру PR, коммиту и двум контрольным суммам эталонных правок. Учитываются суммарные обращения к модели, входные и выходные токены, случаи доступности записи памяти, фактического показа деталей, запросы на чтение и реальное исполнение тестов по заявкам.
