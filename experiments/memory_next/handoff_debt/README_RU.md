# Перенос состояния между агентами на Handoff Debt

Проведён отдельный повторный анализ реальных запусков из авторского набора на 75 задачах SWE-bench Verified. Для каждой пары «точка остановки — получатель» авторы провели все четыре способа передачи, что позволило оценить правила выбора по фактическому исходу соответствующего прогона. Нового запуска Qwen в этом разделе не было. Для сравнения, в соседней папке continuation находятся собственные интерактивные продолжения. Общих целевых задач и PR у этих двух опытов нет. Единственный общий репозиторий — psf/requests. Здесь это PR 2931, 6028, в локальном наборе — 2344, 3574 и Flask 4045.

## Опыт на основных исполнениях

Все 6 120 r01 запусков первичного и расширенного разделов. Три семейства предшественников, три семейства получателей, 510 checkpoint, 1 530 полностью сопоставимых квартетов. В основной конфигурации статьи использован предшественник Qwen с 181 checkpoint и 543 квартетами; ещё 987 квартетов приходятся на другие семейства предшественников. У авторов Qwen3.6-27B, Gemma 4 31B IT и Devstral-Small-2-24B-2512 работали в локальном OpenHands-окружении, лимит 500 шагов. В собственном пилоте Qwen3.8-27B Q4_K_M работает с другим лимитом и инструментами. Форма «raw» передаёт последовательность событий предшественника, «structured» использует фиксированные поля и итог работы модели, «summary» содержит свободную модельную записку. Условия и ресурсы оригинального стенда описаны в [методике Handoff Debt](https://arxiv.org/html/2606.02875v2).

До открытия индивидуальных оценок зафиксировано правило: передавать сырой след после первой правки, которая последовала за ошибкой проверки; на более ранних стадиях передавать структурированную записку. В 255/1 530 точек выбрана полная история. Для подсчёта используем явное official_resolved при backend swebench_official. При неопределённом статусе показываем консервативный расчёт, в котором неподтверждённые решения дают ноль, и отдельный расчёт по парам с известными обоими статусами. Из 6 120 строк 5 882 имеют явный официальный исход, у 200 есть отрицательный validation_passed без явного resolved, у 38 отсутствует validation. В четырёх строках official_resolved=True и validation_passed=False. Альтернативный подсчёт по последнему флагу оставляет основную парную разницу +3. Не требуется считать отсутствие статуса состоявшимся провалом агента.

Правило против постоянной структурированной записки: 13 выигрышей, 10 потерь, +0,20 п.п., 95% кластерный bootstrap по 75 задачам −0,53…+0,89 п.п., описательный p=0,678. При равном весе задач +0,196 п.п. Полные статусы в обеих ветвях известны у 1 469 пар, 12/9, +0,20 п.п. (−0,54…+0,89). Средний входной расход возрос на 52 058 токенов на 1 521 паре с обеими измеренными стоимостями, число событий сократилось на 3,90. Против постоянного полного журнала правило решило на 25 случаев меньше (−1,63 п.п., интервал −3,39…+0,07). Постоянный полный журнал был заранее зафиксирован вторичным компаратором. Внутри 255 изменённых назначений — 102 против 99, 53 разные исходные задачи. Ошибка валидации сама по себе не установлена как причина отсылать весь след.

## Тест на ещё не вскрытых r02/r03

После отрицательного r01 разработана новая гипотеза об условном выборе формы. Из 75 исходных задач всех 22, встречавшихся в повторных запусках, полностью исключили из обучения. Обучение — 1 056 конфигураций r01 на 53 других задачах. Тест — 40 фиксированных авторами точек с двумя отдельными попытками Qwen→Qwen, 80 квартетов и 320 реальных запусков. Население повторов было отобрано авторами, обобщение на все несвязанные задачи требует нового набора. Команда знала общие r01 числа, включая исходные задачи, по которым затем проверялись новые попытки, и опубликованные примеры. При фитировании ни одна такая задача не использована, ответы r02/r03 были скрыты до записи heldout_predictions_lock.json.

Два кандидата фиксировали до вскрытия повторов. В первом усреднили частоту успехов для модели-получателя и стадии со средним этой модели, эквивалентным 16 наблюдениям. Во втором последовательно сгладили оценки по модели-получателю, паре предшественника/получателя и стадии, по 20 псевдонаблюдений от уровня выше. Политики не видят исход текущей задачи. На этих исходных данных обе процедуры выбирают свободную записку после первого изменения и полный журнал после первой проверки. После правки вслед за ошибкой первая выбирает свободную записку, вторая — полный журнал. Первичное сравнение для первой — лучшая постоянная форма из обучения, для второй — всегда raw. Решение только по модели, включая дополнительный receiver-only контроль с 20 псевдонаблюдениями, во всех 80 случаях даёт свободную записку.

Оба выигрыша к свободной записке относятся к одной задаче pydata__xarray-3993 и одной точке post_first_validation_result в попытках r02 и r03. По отдельности в этих повторах обученные политики решили по 19/40, raw 20/40 и 18/40, свободные записки 18/40 и 18/40. Против свободной записки у обеих обученных политик 2 выигрыша, 0 потерь, +2,50 п.п., точный p=0,50, кластерный интервал 0…+8,11 п.п. Против raw по 3 выигрыша и 3 потери, 0 п.п., интервал −3,49…+3,75 п.п. Там, где явны оценки обеих форм, по 2 выигрыша и 2 потери в 78 попытках. В среднем на 79 полных парах первая политика потребовала на 473 538 входных токенов меньше, чем raw (−27,28%), вторая — на 227 762 меньше (−13,12%). Низкая медиана парных эффектов связана в том числе с тождественным выбором той же формы. Для первой политики дешевле/дороже/равно в 35/14/30 парах, для второй 19/10/50. Диагностические 95% интервалы средней абсолютной разницы, bootstrap по 22 исходным задачам, составили −863 390…−142 383 и −464 999…−29 874. По сравнению с самой дешёвой свободной запиской обе политики дороже: +156 022 (+14,1%) и +398 726 (+36,1%) на всех 80 парах. Относительно структурированной записки — +42 118 (+3,46%) и +284 822 (+23,4%).

Авторы исключают генерацию записки из показателей следующего агента. У них установлен лимит 1 600 выходных токенов на генерацию при температуре 0, однако фактическое полное потребление на генерацию для каждого handoff в таблице run summaries не приведено. Дополнительно проверены все 14 файлов авторской таблицы handoffs (6 665 строк). У handoff_json только ключи checkpoint_id, prompt, task_id и view; полей стоимости или промпт-токенов генератора нет. Аудит структуры и хеши находятся в note_generation_fields.json. Нельзя приписать суммарной системе выявленную экономию преемника. Для воспроизводимой гипотезы о компромиссе стоимости и качества нужен новый тест с заранее допустимой потерей качества, тестированием нескольких моделей и полным учётом расходов на запись. Равенство точечных долей решённых задач само по себе не доказывает эквивалентность.

## Воспроизведение

Без сети: `python verify.py`. Проверяются хеши и все выбранные действия, исходы, парные количества, стоимости и численные пределы bootstrap. Для восстановления проекции из исходных публичных данных нужны pyarrow и requests. Последовательность на отдельной копии: download.py → assign.py → project_scores.py → score.py → holdout_assign.py → heldout_project.py → heldout_score.py → heldout_diagnostics.py → cost_controls.py. Первые четыре авторских parquet скачиваются в D:/CodexResearch/x20-handoff-debt. Полный хеш каждого файла хранится в source.json, индивидуальные хеши авторских JSON summary сохранены в arm_outcomes.csv и heldout_outcomes.csv. По ID можно заново соединить строки релиза. Оригинальные траектории, записки и необработанные JSON с данными сессий в пакете не распространяются.
