# Индексирование наблюдавшихся правок

Локальная регистрация дополнительного анализа до вычисления новых прогнозов и оценок. Исходные агрегаты прошлого эксперимента известны. Репозитории и вопросы уже использовались. Новая независимая выборка здесь отсутствует.

**Вопрос.** Даёт ли отдельный поисковый ключ из наблюдавшихся инструментальных попыток правки прирост при фиксированных представлениях прежних симптомов и заключительной заметки? Предположение — правильно привязанные к истории правки увеличат Hit@5 в сравнении с удалением поля и с назначением того же содержимого другой истории. Проверка фальсифицируема по обеим контрольным разностям.

**Единица** — один запрос к библиотеке из 300 ранее завершённых историй, все варианты получают одинаковый запрос. Входы — уже зафиксированные и маскированные на предыдущем этапе cards.json и queries.json. Использовать всю выборку Lite (99) и отдельно все 258 дополнительных запросов к неизменной библиотеке. Отдельно сообщить диагностический исход на запросах расширения, у которых есть размеченная история в этой библиотеке. Бюджет выдачи — пять. Ни один вариант не читает репозиторий текущей задачи.

**Дизайн 2 × 3.** Для лексического и гибридного поиска применить три режима третьего поля. Во всех режимах есть два ключа BM25 (symptom с весом 2 и closure с весом 1). В гибридном поиске также две фиксированные косинусные выдачи Contriever с теми же весами. Третий лексический ключ с весом 1: (A) отсутствует, (B) исходный edits, (C) edits детерминированно назначено другой карточке. Константа reciprocal rank = 12, стабильный порядок ничьих исходной реализации. Порядок вычисления арифметики сохранить. В варианте A нет вклада от пустого ранжирования, порядок карточек не добавляет искусственного сигнала. Для C упорядочить карточки по количеству слов в edits, затем по SHA-256 от фиксированной соли и ключа карточки; попарно обменять edits соседних карточек. Для 300 записей полное взаимно-однозначное перемещение без неподвижных точек сохраняет набор полей, лексический словарь и общий текстовый объём, минимизирует разность длин внутри пар. Поскольку это перестановка целых документов лексического поля, можно переставить столбцы исходных BM25 scores перед стабильной сортировкой. Вариант B с гибридным поиском должен в точности воспроизвести исходные top-10 на всех 357 запросах; вариант B с лексическим — исходные sparse_fields top-10. При расхождении остановить оценивание и проверить причину.

**Заморозка.** До моделирования зафиксировать протокол, генератор, предыдущие слепые входы, исходный rank.py, исходные top-10, веса Contriever в манифесте SHA-256. Зафиксировать все новые 6 × 357 × 300 позиций до присоединения эталонов. Критерии и параметры после присоединения меток не меняются.

**Метрики.** Основная — Hit@5, соответствующий используемому в работах «ground-truth in top 5» / recall of at least one related experience. Дополнительно Match@1, MRR по всем 300 позициям с нулём при недоступном эталоне и обычный macro Recall@5 как доля всех известных релевантных историй. Оценка по той же таблице опубликованных связей, что в прошлой проверке, у задачи может быть несколько допустимых историй. Для каждой метрики парная разность «реальное поле минус контроль» с bootstrap по целым репозиториям (10 000 повторов, seed 20261116), на популяции каждого среза. Для бинарных исходов два направления расхождений и двусторонний точный тест Мак-Немара. Для основной пары проверок (гибридный real−absent, real−shuffle на Lite для Hit@5) корректировка Холма. Все остальные p описательные. Также оценить взаимодействие факторов по Hit@5: (real−absent в гибридном) минус (real−absent в лексическом); это специально заданное вторичное сравнение. Время, ядра, память процесса и размеры полей/поисковых ключей зафиксировать; расчёт текущих затрат CPU отличать от затрат фактической работы агента. При повторе использовать только CPU, один процесс, фиксированные локальные веса. Никаких новых обращений к LLM; этот механизм характеризует поиск до чтения памяти моделью.
