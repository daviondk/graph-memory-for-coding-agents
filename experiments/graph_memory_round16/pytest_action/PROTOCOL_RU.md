# R16. Как агент записывает факт прохождения теста

До извлечения исходов, создания конкретных входов и обращения к решателю. Два репозитория R12 и все 24 репозитория R15/test_receipts исключены. Берём все 165 доступных публичных трасс из четырёх дополнительных репозиториев замороженного VibeMemBench: aio-libs/aiohttp, HTTP-APIs/hydrus, systemd/mkosi и vyperlang/vyper. Их имена и числа директорий проверены до чтения результатов. Исполняются только локальная LLM и механизм записи решений. Исходные команды, программный код проектов и внешние тесты не запускаются. Фильтр по тематике задания, команде и путям исключает задания безопасности. Допускаем только вызовы прежней замороженной грамматики R15 с единственным явно заданным локальным тестовым файлом или nodeid, без -k/-m, и простыми флагами pytest, не меняющими выбор тестов. Все запросы относятся к тому же моменту наблюдения в журнале. Это область применимости на одном снимке, изменения исходников не моделируются.

**Следующее действие.** Агент получает запрос записать прохождение указанного тестового файла или узла для текущего рабочего снимка и одну связанную с ним команду. Он выбирает один вызов локального инструмента: записать положительное ребро либо отправить указанный селектор в очередь на повторную проверку. Маршрутизатор действительно записывает соответствующее действие для каждого ответа. Исполнителю доступен одинаковый контракт: хотя бы один тест успешно завершён, ошибок и провалов нет, область запуска покрывает запрос. Скрытые тесты и официальный статус решения задач не используются.

**Стратифицированная панель.** До запуска модели отбираем по стабильному SHA, без подбора по её ответам, до восьми различных задач в каждую из четырёх страт. Страты: положительный итог с совпадающим селектором, отрицательный с совпадающим, отсутствие достоверного положительного или отрицательного итога с совпадающим, положительный запуск при запросе другого тестового файла. Несовпадающий файл — настоящий селектор из той же задачи либо, при его отсутствии, из того же репозитория, с другим путём к тестовому файлу. Разные страты не делят задач. Нормализуем только начальный ./ и отделяем синтаксис nodeid. Исходная запись ранжируется SHA-256 от фиксированного salt, идентификаторов и потенциальной страты. Раунд-робин по четырём стратам до лимита. В случае дефицита публикуем действительные знаменатели. Выбор по заранее определённым типам свидетельства полезен для сопоставления, распространённость ошибочных записей в общей популяции такая панель не оценивает. Поскольку замороженный стандартный парсер формирует страты, ручная независимая разметка должна проверить и совпадение источника с запросом, и легитимность успеха без доступа к прогнозам, страте или рассчитанной метке. Публикуем расхождения. Автоматические и прошедшие аудит результаты различаем.

**Четыре условия.** Общая часть одинакова: непрозрачный идентификатор наблюдения, селектор запрошенного теста, исходный селектор, вид запуска и shell rc. Переменная запись имеет общий потолок 768 байт UTF-8. (1) Только код оболочки. (2) Конец показанного агенту исходного stdout, до 768 байт. (3) Последняя распознанная итоговая строка штатного текстового парсера R15, иначе пустая запись. (4) Структурированное свидетельство на том же исходном выводе: числовые счётчики pytest, факт распознавания конца сеанса, сокращённый хеш кандидатной строки и идентификатор исходного наблюдения. Оно не содержит готового решения записать или перепроверить, а хеш служит только адресом источника. Без внешнего JUnit или ранее неизвестного кода процесса. Если видимое сообщение длиннее бюджета, всегда отрезаем с начала. Фактические байты, входные/выходные токены и задержки сообщаем отдельно. Дополнительно без LLM: обычное правило rc=0 при совпадении селектора и правило явного положительного итога при совпадении селектора. Результат парсера частично встроен в стратификацию; его сравнение проходит отдельный аудит.

**Модель и подведение итогов.** Местный llama.cpp, модель Qwen3.8‑27B UD-Q4_K_M, температура 0, top_k=1, seed=13016, без reasoning и кэша prompts, изолированный запрос на пару задача × условие. Два инструмента с пустыми параметрами, обязательный единичный выбор. Для невалидного ответа повтор только при сетевом/серверном исключении, неверный ответ учитывается отдельно. Порядок пар перемешиваем фиксированным SHA. Сохраняем ответы и журналы до оценки. Первичные величины — число ошибочных положительных записей среди непригодных и число правильных положительных записей среди пригодных. Дополнительно указать общую точность действия и число повторных проверок. Для сравнений используем пары одних и тех же задач, точный двусторонний тест Макнемара между структурированной записью и исходным выводом, с точностью действия и отдельно по каждой исходной страте. Оцениваем новый механизм на одном шаге принятия решения. При малой панели и одном решателе нельзя выводить преимущество над системами памяти в целом или переносить частоты на все задачи. Исходные 40 ячеек R15 используются только как предыстория.
