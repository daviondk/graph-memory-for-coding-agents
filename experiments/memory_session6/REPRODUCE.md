## Офлайн-проверка

После распаковки выполнить `python -B verify_bundle.py` в корне архива. Проверяются SHA-256 всех файлов и регенерируются основные таблицы. В исследовательской среде использованы CPython 3.14.4, NumPy 2.4.4 и requests 2.33.1 (импортируется также одним из офлайн-оценщиков). Некоторые анализы рассчитывают интервалы с помощью фиксированного генератора NumPy; отличия в численных библиотеках могут изменить младшие разряды результатов. Для проверки только целостности есть `--hash-only`. Внешняя команда `python -B verify_bundle.py ПУТЬ_К_ZIP --receipt ПУТЬ_К_JSON` проверяет свежераспакованную копию. Тексты результатов и коды публикаций доступны без аккаунта.

Для генерации новых ответов нужен тот же GGUF (хеш и закреплённая ссылка в repair/runtime/model_receipt.json), сборка llama.cpp и параметры сервера из repair/runtime. Настройки вызовов и prompt-cache указаны в протоколах. Сервер имеет один вычислительный слот; очереди в этом выпуске делили его. Серверные счётчики, логические токены каждой политики и физические уникальные запросы учитываются раздельно. Повторное исполнение фиксированных программ описано в repair/REPRODUCE.md. Сравнение политик памяти на одном решателе и под одним оценщиком отличается от сравнения опубликованных чисел между решателями.

Версии внешних источников, поправки после первых попыток, диагностические прогоны и ограничения указаны в PROTOCOL.md, SOURCE.md, исходных манифестах и summary_ru.md соответствующей папки. Для полного воспроизведения Concord из сырого источника применялось отдельное окружение Python 3.12 с версиями из concord/dependencies.txt. В архиве сохранена используемая часть дерева авторов, для запуска штатной проверки git rev-parse требуется их git checkout на ревизии из concord/SOURCE.md. Тексты из датасетов интерпретируются как данные.
