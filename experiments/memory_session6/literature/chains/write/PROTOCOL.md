Which file pointers should a coding agent keep after a completed repository edit? A new prospective diagnostic on the official ChainSWE unique release, after inspecting only IDs and counts in the overlap audit. Feature extractor uses developer patch headers as an observed previous successful edit proxy. Whitelist production .py paths, exclude tests, generated vendor files and sensitive/security-related episodes. Do not inspect or publish source lines, executable content or task text; a deny-list classifier uses the task title/text solely to exclude episodes, never as a predictor. Store opaque per-repository path and directory hashes. Each actor starts empty, observes only prior edits of its chain. At every step *before* seeing the upcoming edit or issue description predict all retained pointers; then update from the just observed file set. Same maximum # file-pointer records (1,3,8); auxiliary frequency integers/dir tags declared, estimates are capacity in records, not physical bytes. Four candidate methods: newest seen files, breaking ties in deterministic path hash order (recency); newest with a bonus for already-resident paths to break ties (confirmation); diversity: from the confirmation ordering select at most one path per directory first then fill; protect one corroborated resident file with count >=2 then fill with confirmation. Include strong resident count first with recency tie-break. Scope is writing/retention with no issue-aware retrieval or repo indexing. Primary contrast at 3 slots is protect vs confirmation on Hit (any retained file among files actually changed at the next task); secondary micro per-target recall and proportion of target ever seen even at unlimited history; report all algorithms and capacities even if null. To prevent repeated prefixes inflating independent sample, choose exactly one prefix per repo/target across eligible positions via lowest SHA of its sequence/step ID, independent of the files and outcomes. Primary positions have two or more prior observed tasks, all tasks in the prefix incl target have a nonempty allowed production-file set, no repeat target ID within a prefix. Publish counts of all admissions and later reads, write churn at same budget, original repos as clusters for 10k bootstrap paired intervals on primary contrast plus win/loss counts. Mark as exploratory outcome-prediction proxy, not official ChainSWE resolved or live model improvement. All eligibility, tie breaks and contrasts are fixed before the first data projection.
