# Как сохранить результат поиска после правки

**Основной результат.** Для полного множества файлов Python, содержащих идентификатор, простое кодирование знака изменения полезнее четырёхбитных счётчиков при одинаковом бюджете на сообщение. На 7 995 повторных запросах с именами из реальных трасс неподписанный фильтр по изменению числа вхождений потребовал 982 перечитывания, подписанный 895, предложенные счётчики 3 592. Все три восстановили верный ответ в каждом случае. При парной кластеризации по проекту разница «счётчики минус неподписанный фильтр» составила +0,3265 файла на запрос, 95%-й интервал [+0,0232; +0,7055]. Полное повторное чтение изменённых файлов потребовало 16 536 обращений. Игнорирование правок вернуло устаревший ответ в 39 случаях. На 8 783 контролируемых запросах счётчики также проиграли простому фильтру, 4 442 против 1 436 чтений. Основной бюджет 512 байт на сводку изменения. В results.json есть также 128 и 2 048 байт и все контрольные варианты. Данные содержат 492 перехода из 12 репозиториев. Естественные имена удалось сопоставить с девятью.

**Запись по подписке.** На независимом, более раннем отрезке Git для девяти репозиториев клиент хранит прежнее число вхождений в каждом файле. Одна регистрация до 24 имён и пересылка только соответствующих целочисленных изменений стоили суммарно 4 585 байт для 378 переходов. Из них 2 648 — регистрация имён и 1 937 — обновления. Для пересылки только фактов появления или исчезновения файла понадобилось 7 418 байт, из них 6 510 — регистрация, 908 — обновления. Первая схема оказалась дешевле в восьми из девяти репозиториев. Редкий, обычный и плотный режимы используют одни и те же изменения и соответственно 90, 378 и 3 024 запроса. Обе схемы восстановили все ответы без последующих чтений файлов. При обычном режиме pull потребовал 8 342 байта и 378 обменов. Писатель получил 5 873 312 байт diff, прежний результат поиска уже имелся у клиента. Общая таблица путей при необходимости первичной передачи добавляет 18 662 байта. В суммах полезных нагрузок опущены транспортные заголовки, подготовка Git diff и время CPU. Метод относится к инкрементальному поддержанию представлений. [Gupta, Mumick, Subrahmanian](https://doi.org/10.1145/170036.170066)

**Как часто агенту это нужно.** Из 54 463 фактических команд shell в 4 310 траекториях допущенный парсер нашёл 5 867 вызовов с буквальным поиском. На последующем вызове такое же имя встречалось 1 113 раз. В 152 вызовах после предыдущего обращения к имени произошла подтверждённая правка. Отдельный счётчик нашёл 31 повтор полной строки команды после правки в 28 задачах. Пересечение этих двух множеств вызовов равно 28: между двумя одинаковыми командами агент иногда запрашивал то же имя другими способами. Совпадение команд и имён даёт кандидатов для кэширования, пути и флаги способны менять смысл результата. Система оценивает инкрементальную поддержку поиска; влияние на долю решённых задач остаётся открытым.
