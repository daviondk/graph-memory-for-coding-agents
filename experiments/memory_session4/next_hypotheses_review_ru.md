# Три проверяемые гипотезы для следующего исследования

17 ноября 2026. Независимая критическая оценка результатов этого раунда. Авторский обзор ниже формулирует кандидатов для выбора. Все три гипотезы пока эмпирически не подтверждены. Ближайшие первичные статьи открыты и проверены в текущей сессии.

## Что ограничивает дальнейшие утверждения

Compact показал, что причинное обновление виденных строк может помогать при неизменном reader. Сильнейший содержательный контроль сократил разность до +0,64 п.п. с интервалом [−0,13; 1,41], а при 256 токенах обновление ухудшило результат. В action простая типизированная FTRL дала 492 восстановления против 488 у эпизодической памяти. В WebLINX текущая короткая история воспроизвела и немного превысила эффект persistent focus. Эти результаты совместимы с объяснением через достаточность простого доступного состояния. Выигрыш новой памяти должен проявиться поверх такого контроля. Текущий handoff-эксперимент ещё ожидает итоговой интерпретации.

Независимый provenance-аудит обнаружил две разные полноценные подписи патча среди 923 пригодных пар. Он обосновывает проверку связи опыта с артефактом. Из него пока не следует улучшение решателя от такой проверки.

## 1. Сохранять совместно необходимые свидетельства для операции

**Гипотеза.** Ограниченная память помогает продолжению работы, когда сохраняет полный набор сведений, требуемый одной допустимой операцией. Независимый отбор отдельных похожих фрагментов может расходовать тот же бюджет на набор, из которого выполнить операцию невозможно.

**Реализация.** После успешного literal edit writer строит кандидата из подтверждённого post-edit текста, пути и минимального наблюдённого контекста, различающего повторяющиеся совпадения. По уже завершённым операциям на train он оценивает, какие комбинации этих полей достаточны для однозначного edit или проверяемого read. Контроллер выбирает целые комбинации под общий лимит. Допустимые кандидаты происходят только из уже прочитанных байтов и исполненных изменений. Новые вызовы решателя после разрыва получают обычный editor и одинаковый доступ к повторному чтению. Будущая историческая команда доступна только оценщику.

**Ближайший prior.** CoReMem уже использует расположения кода, исполняемые проверки и prospective valuation. Предлагаемая проверка касается совместной достаточности маленьких байтовых фрагментов под жёстким бюджетом. Первенство такого сочетания требует отдельной сверки реализации prior. [CoReMem](https://arxiv.org/html/2611.17316v1)

**Различающий исход.** При одном reader, одинаковом бюджете и равном числе дополнительных вызовов выше доля действительно исполненных свежих операций без восстановительного read, при сохранении task resolution. Основные контроли — recent-tail и recent-center с тем же exact update, затем обычный summary и location/check anchors. Обязателен контроль выбора отдельных полей с тем же ранжированием. Он проверяет пользу совместного хранения.

**Опровержение.** Эффект исчезает после целого неделимого recent-span baseline, возникает только при доступе writer к будущему old_str или оплачивается ухудшением тестового решения. Нулевое различие между комбинациями и независимыми полями опровергает предполагаемый механизм.

**Минимальная проверка.** 60 новых исходных задач из ещё не разобранной части SWE-smith, по одному заранее назначенному разрыву и три запуска свежего reader. Три бюджета 256/512/1024, четыре замороженных arm. Сначала проверить реализуемость, далее определить размер подтверждающего опыта по наблюдаемой частоте discordant pairs. Учесть неуспешные editor calls и восстановительные чтения. Интервал кластеризовать по исходной задаче. Этот pilot проверяет перенос на новые задачи, перенос на новые репозитории потребует отдельного корпуса. Его мощность для итогового resolved заранее не установлена.

## 2. Извлекать опыт, различающий причины и меняющий следующий тест

**Гипотеза.** Отрицательный опыт полезен преимущественно в ситуациях, когда он позволяет выбрать между двумя диагностическими действиями с разными ожидаемыми исходами. Общая вероятность успеха повтора может быть хорошо оценена простым статистическим методом.

**Реализация.** После фактической ошибки actor формирует две рабочие причины, вариант unknown и два возможных следующих действия. В короткой записи остаются наблюдённый симптом, выполненная проверка, её исход и явно наблюдаемые условия. При повторном затруднении контроллер ищет одну прошлую проверку, исход которой разделяет текущие причины. Сначала сравнивается выбор действия без этой записи и с ней. Инъекция производится только при изменении выбора, прошедшем простую проверку допустимости. При несовпадении наблюдаемого состояния предлагается воспроизвести саму проверку. Семантическая причина сохраняется гипотезой, фактический tool result остаётся свидетельством.

**Ближайший prior.** REM уже открывает подробный опыт при затруднении. AdMem связывает процедурные записи с ожидаемым и фактическим результатом. Предлагаемая добавка ограничена выбором различающего свидетельства и измерением изменения решения. [REM](https://arxiv.org/html/2610.27377v1), [AdMem](https://arxiv.org/html/2611.20605v1)

**Различающий исход.** При равном полном бюджете уменьшается число повторных неинформативных проверок и повышается task resolution либо снижаются затраты при заранее заданной границе допустимого изменения resolution. Контроли включают typed FTRL, последний результат проверки, summary плюс один check, REM-style gate и тот же actor с дополнительным вызовом без памяти. FTRL обучается на отдельной калибровочной части этих же инструментальных задач с теми же доступными признаками. Последний контроль отделяет эффект свидетельства от дополнительного вычисления.

**Опровержение.** Выбор теста почти не меняется, информационный выигрыш объясняется дополнительным actor call или обычным typed FTRL. Снижение Brier без прироста action utility не подтверждает эту гипотезу.

**Минимальная проверка.** На 40 новых официальных SWE-ContextBench Lite задачах сохранить реальные состояния первых ошибок одинакового frozen actor. Дальше разветвить один checkout и разрешить каждой политике четыре диагностических действия, затем одинаковый остаточный budget до конечного патча. Три повтора, одинаковый renderer памяти. Все ошибки и отсутствие двух различимых причин входят в знаменатель. Ограниченный branching сначала даёт метрику диагностической полезности, финальный патч оценивается официальными тестами. Для межзадачного опыта требуется отдельный split по experience group.

## 3. Писать память с учётом того, что уже знает получатель

**Гипотеза.** Существенная часть пользы памяти исчезает, когда её содержание уже восстановимо из текущего наблюдения и короткой истории. Writer может сохранять информацию эффективнее, оценивая дополнительный вклад записи для конкретного состояния получателя.

**Реализация.** До сжатия доступны свежий snapshot среды и короткая история, которые reader гарантированно получит. Для каждого небольшого кандидата writer сравнивает действия frozen proxy-reader на этом общем входе с записью и с её маскированием. По train оценивается, когда разница сопровождается допустимой операцией. Кандидат получает место в ограниченной памяти только при ожидаемой дополнительной полезности. В runtime writer видит только текущие данные и уже поставленную задачу. Ни будущий вопрос, ни reference action, ни hidden tests ему не доступны. Обычное удаление совпадающих строк служит дешёвым контролем.

**Ближайший prior.** Task-Conditioned Utility уже сравнивает память на matched reader inputs и требует blind writer. CoReMem оценивает последующую пользу сегментов. Здесь нужно проверить перенос такой условной оценки в доступный онлайн-выбор записи, учитывая стоимость proxy calls. [Task-Conditioned Utility](https://arxiv.org/html/2611.03930v1), [CoReMem](https://arxiv.org/html/2611.17316v1)

**Различающий исход.** При фиксированном общем контексте новый writer сохраняет больше сведений, полезных после реального разрыва, и повышает фактическое завершение задачи. Контроли — recent history, обычный writer того же размера, удаление видимых дубликатов и compute-matched writer. Дополнительный тест случайно задаёт доступность прежней истории независимо от метода, сохраняя одинаковую доступность между arm внутри пары.

**Опровержение.** Простое устранение видимых дубликатов воспроизводит выигрыш, поведение proxy не переносится на фактический reader, либо расходы на оценку записи превышают экономию. Выигрыш только при специально удалённом полезном фрагменте имеет ограниченную применимость и требует отчёта отдельно от естественных разрывов.

**Минимальная проверка.** 50 новых длинных задач, два заранее назначенных состояния доступности recent-history, по три повтора. Сохранять финальный success, восстановительные чтения, полный ledger writer/proxy/reader и долю записей, действительно изменивших выполненное действие. Bootstrap по задаче. Следующий этап потребует второго reader, поскольку переносимость proxy является частью гипотезы.

## Правило выбора

Для всех вариантов сначала замораживаются corpus, writer, reader, budgets и primary contrast. Решатель и модель остаются одинаковыми между arm, опубликованные методы запускаются в том же harness. Положительный replay служит основанием для live pilot. Вывод о превосходстве требует независимого набора и end-to-end исхода при полном учёте затрат. Текущий поиск задаёт ближайшие сравнения, оценка новизны остаётся открытой.
