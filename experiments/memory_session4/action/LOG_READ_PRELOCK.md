# Reading a typed diagnosis from the preceding failed operation
Before opening any job outcomes or individual reason labels freeze a second, paired job-level study using the first 64 MiB of the authors' 2.16 GB compressed restarted_logs.bson.gz and every complete BSON document in that byte prefix. Match those original job IDs to the full MD5-verified restarted_jobs dump. Adopt same temporal evaluation, 20% retry eligibility and project clusters as for builds. This is a file-order prefix, selected without labels, not a representative random sample. Primary incremental question: do source-typed failure categories improve a repository+status memory (same matched jobs) and is reading only under uncertainty sufficient? A project's historical repo+status empirical rate (with 8 pseudo-observations from global-state) is prior. For the typed model use up to eight most recent exact (repo, reason) completed examples and a cross-project prior of the first attempt's reason code, as specified in model.py before scoring. Code token length, old status, first author-provided reason set only. Compare globally shared signatures, #1 last matched vs pooled, numbers of exact matches, a leave-unknown fallback. When base predictive uncertainty is high (0.35<=p<=0.65), read the type; otherwise keep base. Read costs measured as number of fetched diagnosis values and UTF-8 bytes of canonical reason lists; do not infer wall time or tokens saved. First reason list is the log parser's output on only oldLog, verified from tdurieux/Travis-Listener commit 0e3d2c45b55570688e9454ffa84314ab35a2a4be logparser/server.js and plugins/restartedbuilds/jobs/analyzeLogs.js. The archive's top-level raw log is the *new* output and must NEVER enter features; also exclude diff, logDiff, analysis.restarted. Keep projection readable and source checksum of the fixed prefix; no storage of raw private values in user-facing docs. Primary and secondary cohorts can overlap in origin, do not pool jobs with builds or treat this as a separate provider.
