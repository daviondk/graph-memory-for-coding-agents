# Когда проверка блока исходного кода способна изменить пакет памяти

На 1 071 правке из 13 задач объединение двух способов подтверждения сохранило исходный пакет в **341 случае**. Пространственные интервалы давали 302, поиск каждого блока по содержимому полного файла — 287. При равном весе задач преимущество объединения составило **+2,97 п.п. [0,94; 5,74]** над интервалами и **+4,52 п.п. [2,13; 7,41]** над поиском. Это разведочное сравнение на знакомой панели. Бюджет, исходное ранжирование, способ разрешения равенств и доступные блоки до правки во всех трёх условиях совпадали. [Протокол](PROTOCOL_RU.md) · [Результаты](results.json)

Блок вне интервала изменения наследует адрес из квитанции редактора. Для пересекающегося блока система может запросить подтверждение по содержимому. Старый наблюдавшийся текст должен совпасть по исходному адресу и иметь единственное точное совпадение в новой версии. Пакет собирается заново из всех подтверждённых блоков. Это правило сохраняет прослеживаемость повторяющегося текста вне изменения и может восстановить содержимое внутри заменённого участка. Если два одинаковых фрагмента сделали историческое происхождение неопределённым, уникальная привязка определяет текущее содержимое. Утверждение о семантической эквивалентности программы из равенства строк не следует.

## Достаточно ли уже известных блоков

Пусть в наиболее полном допустимом пуле оптимизатор выбрал упорядоченный пакет P. Часть доступности ещё неизвестна. Пакет одинаков для **любого** завершения проверок в точности при двух условиях.

1. Для каждого выбранного блока доступность уже подтверждена.
2. Для каждого невыбранного блока j сумма его собственной стоимости и стоимостей **подтверждённых** предшественников больше порога защищённого префикса.

Если выбранный блок не проверен, возможен исход с его удалением. Минимальная стоимость пути по порядку до j при сохранении самого j достигается удалением всех неизвестных предшественников. Если она помещается в префикс, j может стать обязательным и изменить P. Иначе в любом завершении новый префикс содержится в P, P сохраняет допустимость, а множество остальных допустимых решений только уменьшается. Детерминированный порядок разрешения равенств сохраняет прежний оптимум. Вывод предполагает, что любое подмножество непроверенных блоков формально возможно, стоимости неотрицательны, полезности и ранги фиксированы. При корреляции доступностей правило остаётся достаточным, а необходимость может исчезнуть. Критерий сэкономил 4,11% логических проверок [2,15%; 7,50%] и 3,39% обращений к парам версий [1,75%; 5,89%]. Более простая проверка границы запросила всего один дополнительный блок. Стоимость повторной упаковки поглотила экономию на этой смеси операций. При буквальном поиске в прогретых строках, трёх чередующихся повторах и медиане на событие отношение суммарных времён полного и ленивого планов равно **0,984× [0,960; 1,002]**. Прогретый замер исключает чтение Parquet, сеть и время дискового ввода. Байты в таблице — объём пары при первом обращении за событие. В стендовом replay обе версии поданы источником данных. [Сырые тайминги](physical-timings.json.gz) · [Верификация](physical-check.json)

На всех 2 696 правках объединение сохранило 795 пакетов против 699 и 680 у компонент. Полный и оба ленивых плана дали одинаковые ID и адреса во всех 2 696 случаях. Повторный запуск по оригинальным строкам проверил 53 783 выбранные строки изменённых файлов и 7 713 блоков без расхождений. Независимый перебор проверил критерий на 8 928 конфигурациях непроверенных блоков и 117 612 завершениях, включая равные полезности и нулевые стоимости. 1 293 конфигурации позволяли раннюю остановку. [Перебор](theorem-check.json)

Классический пороговый алгоритм исследует цены доступа при монотонной агрегации рангов. Работа по top-k в неопределённых базах использует вероятности возможных миров. Здесь условие описывает инвариантность одного детерминированного бюджетного пакета при всех допустимых исходах проверок. Оптимальность числа обращений не установлена. [Fagin, Lotem и Naor](https://doi.org/10.1016/S0022-0000(03)00026-6) · [Soliman, Ilyas и Chang](https://cs.uwaterloo.ca/~ilyas/papers/SolimanICDE2007.pdf)

Численные ID и источник каждого прогноза сохранены в [поштучном журнале](forecasts.json.gz). Производительность решателя и полезность для будущих решений оцениваются отдельно.
