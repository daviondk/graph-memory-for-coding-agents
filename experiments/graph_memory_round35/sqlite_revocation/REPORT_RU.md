# Измерение SQLite на одном локальном диске

На 64 заранее выбранных историях отложенное до чтения удаление снизило среднее время обработки истории с **7,07 до 6,47 мс** с учётом принудительной контрольной точки WAL. Парная разность **0,59 мс [0,38; 0,85]**. По каждой истории и политике взята медиана четырёх повторов, затем среднее по историям. Расчёты выполнены на одном компьютере, а интервал получен повторной выборкой историй. [Все физические замеры](runs.json.gz) · [Результаты](results.json)

| Показатель | Сразу при изменении | Непосредственно перед чтением |
|---|---:|---:|
| Время на историю с финальным checkpoint, мс | 7,066 | 6,474 |
| До финального checkpoint, мс | 6,412 | 5,809 |
| Непустые транзакции на 64 истории | 901 | 809 |
| Вставленные / удалённые пары за 64 истории | 861 / 390 | 861 / 390 |
| Средний объём WAL перед заключительным checkpoint, байт | 58 034 | 52 111 |

Состав таблицы совпал с непосредственным воспроизведением упорядоченного потока событий при каждом чтении и по окончании истории. Всего проверено 2 560 фактически прочитанных состояний в 512 независимых файлах SQLite (64 истории × две политики × четыре повтора × пять проверок). В 34 историях уменьшилось число транзакций, в остальных 30 оно сохранилось. Среднее отношение времени исходной политики к новой 1,091 [1,061; 1,125], или примерно на 8,4% меньше времени у отложенного режима.

Замер охватывает таблицу одного отношения в SQLite WAL с synchronous=FULL и финальную принудительную контрольную точку. Он использует уже записанные события и заранее подготовленные списки SQL-операций. Подготовка графовых признаков, выдача модели, создание базы и сохранение самого журнала действий агента в замер не входят. В этой реализации pending-список между чтениями находится в оперативной памяти. Сокращение числа *пачек удалений* по всем 1 207 историям в отдельном опыте отличается от сокращения всех транзакций в SQLite, поскольку транзакции могут содержать вставки. [Полный журнал логических изменений](../deferred_revocation/REPORT_RU.md)

Для повторения выполнить `python benchmark.py` с Python и NumPy на Windows с доступом к исходным шардам и временному каталогу на D. Скрипт создаёт отдельный временный файл для каждого замера и по окончании удаляет только собственные временные каталоги. [Конфигурация](plan.json) · [Протокол](PROTOCOL_RU.md)
