# Обновление живого графа ISETrace

[Открыть локальную интерактивную демонстрацию](index.html). Выберите одну из трёх историй и долю завершённых групп вызовов (25%, 50%, 75%, 100%). На каждом срезе обе политики имеют одинаковые видимые фрагменты и один весовой вектор. Страница вычисляет, какие адреса в каком порядке войдут в строгий префикс из 2 048 токенов. Выбор фрагмента показывает его цену, позицию у каждого читателя и пересечение с эталонным текстом. Таблица связей раскрывает актуальные изменения и сохранённые старые привязки. Открытие одного HTML с диска достаточно для показа.

## Три примера на одном и том же срезе 50%

| Исход обновления | Текущая политика | Политика накопления | Что изменилось |
|---|---:|---:|---|
| Выигрыш | 409/409 эталонных символов, 2 029 токенов | 176/409, 1 868 токенов | Только актуальный граф доставил U016 ценой 338 токенов. Фрагмент дал недостающие 233 символа. При накоплении он стоял следующим за токенной границей, где оставалось 180 токенов. |
| Потеря | 0/69, 2 040 токенов | 69/69, 1 667 токенов | U010 ценой 66 токенов, содержащий весь эталон, оказался в префиксе накопительного графа. В текущем графе при другой последовательности чтения осталось восемь токенов. |
| Равная полнота | 93/93, 1 843 токена | 93/93, 1 872 токена | Накопительный граф добавил U017 ценой 29 токенов, сохранив полноту, и изменил порядок нескольких адресов. |

Эти вопросы целевым образом отобраны на публичном тесте. Из 901 непилотного запроса с доступным эталоном на середине истории изменение фактически отданного **множества** затронуло 449. В этой группе 43 выигрыша, 16 потерь и 390 случаев равной полноты при различном наборе адресов. В каждом классе показан первый вопрос при сортировке по заранее зафиксированному хешу и с отдельной историей. На всей панели R34 текущий граф дал FS 752/901 против 725/901 у накопления, +3,00 п.п. [1,33; 4,70]. Метрика измеряет получение всех исходных интервалов. Доказательство переноса на качество действий агента потребовало бы отдельного end-to-end опыта. ## Что именно было отозвано

Уровни связывания имеют разные единицы. Приход события может устранить ранее единственное соответствие между вызовами. После этого текущая проекция перестаёт повышать приоритет связанных фрагментов. В варианте накопления историческая привязка продолжает действовать и для фрагментов, появившихся позже. Страница отдельно показывает (а) разность соседних снимков всех четырёх типов рёбер, (б) каждое фактическое появление и отзыв видимой связи передачи данных с номером события и (в) все лишние рёбра накопления в текущем срезе.

В случае потери у накопителя на середине было 1 453 лишних ребра. Из них только шесть когда-либо соединяли одновременно видимые фрагменты. Для выигрыша это четыре из шести, для случая равной полноты — двенадцать из тринадцати. Эти три примера позволяют сформулировать следующий контроль: сравнить накопление только когда-либо материализованных рёбер с накоплением привязок вызовов, которые могут проецироваться на новые адреса. Примеры показывают состав текущего графа; вклад каждого из его рёбер в изменение FS потребует отдельной интервенции.

## Проверка

С эталонными R34-прогнозами и нативной функцией покрытия сверены доставленные адреса, токены и символьные интервалы для трёх вопросов × четырёх срезов × двух политик. Нативный построитель графа заново вызван на всех 12 снимках. Для проверки динамики проводилось отдельное восстановление после каждого поступления результата инструмента. При наличии незавершённых параллельных вызовов оно сохраняет все события уже завершённых вызовов и исходные позиции. Проверены 161 такой префикс, хронология событий для видимых рёбер, явные списки изменений на каждом из 12 снимков и их раскрытие в браузере. Проверка Chrome включает мобильный и настольный размер, управление срезами и клики по фактическим адресам. Приложение не отправляет сетевых запросов. Тексты событий, аргументы и содержимое результатов в демонстрацию не входят. [Нативный тест](oracle-receipt.json) · [Проверка событий](event-oracle.json) · [Проверка браузера](browser-receipt.json)

Для полной сборки в окружении R34: выполнить по порядку `python -B build.py`, `python -B oracle.py`, `python -B event_oracle.py`, `node browser_check.mjs`. Нативные данные и модель нужны только при пересборке. Для проверки переносимой копии достаточно стандартного Python и `python -B verify.py`. [Контрольные суммы](manifest.json)
