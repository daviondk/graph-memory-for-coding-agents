# Восстановление графовой памяти из журнала после аварийного выхода

На **64 историях ISETrace** завершали процесс SQLite непосредственно перед чтением графа. В **54 из 128** точек простое открытие сохранённой таблицы возвращало устаревшие связи. Повторное применение журнала после последнего долговечного барьера устранило все 54 расхождения. С эталоном совпали **382 из 382** последующих чтений и все **128** конечных состояний. Для этого потребовалось перечитать медианно **6 событий**, 95-й перцентиль — **18**, максимум — **42**. Эти показатели зависят от расстояния между чтениями и условий выбранного сбоя. [Поштучные результаты](cases.json.gz) · [Агрегаты](results.json)

## Что именно теряется

В графовой памяти поддерживается связь «источник результата → потребитель». При появлении свидетельства пара сразу записывается в SQLite. При отзыве последнего свидетельства пару помещают в очередь до следующего чтения. Это позволяет объединить несколько удалений. Если процесс завершается раньше чтения, SQLite сохраняет завершённые вставки, а содержимое очереди исчезает. Например, у таблицы с одной парой могут быть две различные предыстории. В первой поддержка пары сохраняется, во второй поддержка уже отозвана и удаление ещё ждёт чтения. Состояние таблицы в этих случаях одинаково. Чтобы различить их при восстановлении, нужен ещё один долговечный источник информации. [Эксперимент с отложенными удалениями](../deferred_revocation/REPORT_RU.md)

В проверенном варианте каждый барьер чтения одной транзакцией применяет очередь и сохраняет номер обработанной записи. Между барьерами достаточно знать исходное состояние на барьере и последовательность изменений для каждой пары. Если последним изменением был отзыв, пара войдёт в новую очередь удаления. Если последним было добавление, пара остаётся активной. Повторное добавление уже записанной пары сохраняет таблицу благодаря первичному ключу и INSERT OR IGNORE. При неизменном источнике и единственном последовательном писателе повторное чтение с первого события после барьера восстанавливает нужные изменения. Все 378 повторно посланных в основных испытаниях вставок встретили уже существующую строку. [Реализация](worker.py)

## Физический тест

До измерений из 1 207 историй по хешу ID зафиксировали 64, в том числе истории с пустой очередью на точке сбоя. Опыт воспроизводит восемь подписанных шардов с реальными изменениями отношений. Один экземпляр истории содержит только целочисленные номера операций, локальные номера пар и отметки исходных чтений. Для 64 историй записан отдельный долговечный SQLite-журнал из **2 243 событий**, в том числе события завершения группы без изменений отношений. Файл занимает **53 248 байт** с составным первичным ключом по истории и номеру события. На журнал приходится 1 325 отдельных добавлений и отзывов. Его подготовили одной транзакцией до измерений, затем открывали с mode=ro. [Журнал](source.sqlite3) · [Заранее заданная панель](plan.json)

Для каждой точки один локальный дочерний процесс содержал две самостоятельные одинаковые физические базы в режиме WAL с synchronous=FULL. После завершения префикса он вышел через os._exit(73) с открытыми соединениями. Другой дочерний процесс открыл обе базы, проверил integrity_check и последний завершённый барьер. Таблица и номер барьера на старте в обоих режимах совпали с независимо рассчитанным состоянием. Первый режим продолжал со следующей записи, предполагая пустую очередь. Второй перечитывал интервал после барьера, затем продолжал по тому же хвосту. Родитель проверял возвращённые множества на каждом чтении и в конце напрямую по исходным файлам операций, без обращения к подготовленному журналу. Случаи относятся к 64 историям с двумя детерминированными точками. [Протокол](PROTOCOL_RU.md) · [Проверка независимого эталона](run.py)

| Основные точки вместе | 64 / 128 | **54 / 0** | **160 / 0 из 382** | **54 / 0** | **1 013** |
| Дополнительно, во время открытой транзакции первого барьера | 16 / 16 | 5 / 0 | 20 / 0 из 64 | 5 / 0 | 111 |

В основной серии при простом продолжении хотя бы одно первое чтение оказалось ошибочным в **41 из 64** историй. В сумме на следующих чтениях сохранились 173 лишние пары, пропущенных пар не было. Во всех 54 случаях до сбоя очередь была непуста. Режим replay сделал 128 индексированных запросов диапазона. 124 вернули хотя бы одну запись, в общей сложности обработаны 378 логических добавлений и 173 отзыва. Это логические строки на границе SQLite. Размер страниц, фактический трафик устройства и задержка восстановления здесь отдельно не замерялись. Файлы WAL обеих баз имели ненулевую длину во всех 144 испытаниях. Максимальная длина одного WAL перед аварийным выходом в основной серии — 185 432 байта. [Результаты и версии](results.json)

В дополнительной серии до аварии уже были выполнены SQL-команды открытой транзакции барьера и новый watermark стал виден самому писателю. COMMIT ещё не вызывался. Во всех 16 повторах следующий процесс увидел прежний watermark и прежнее материализованное состояние. После replay совпали все 64 последующих чтения. Простое продолжение ошиблось на пяти историях с накопленными удалениями. При повторном открытии SQLite исключила незавершённую транзакцию из видимого состояния. Опыт контролировал границы до и после вызова COMMIT. Сбой питания устройства или сбой во время системного вызова записи не моделировался.

## Граница результата

Проверен контракт с заранее имеющимся источником, где история неизменна, упорядочена, сохраняет прежние записи и позволяет повторно читать стабильные номера. Закоммиченные изменения графа и его барьер живут в одной локальной транзакции. Источник был заранее заполнен целиком, при восстановлении считан только разрешённый префикс. В испытании «последняя принятая запись» задаётся точкой сбоя. В рабочем потребителе доступный диапазон задаёт внешний журнал, а его хвост должен безопасно допускать повторную доставку. Эксперимент проверяет чтение готовых изменений связей. Если есть лишь сырые вызовы инструментов, потребуется также детерминированно восстановить операции и их адреса; стоимость такого преобразования не входит в 53 248 байт. Отдельно потребуются меры для разрывов журнала, изменения схемы, параллельных писателей и согласования разных хранилищ. Отсутствие ошибок на выбранных точках характеризует восстановление графа, а не результат решения агентом исходной задачи. [Инструкции и контракт](REPRODUCE_RU.md)
