# Восстановление очереди отзывов при аварийном выходе

Панель — 64 траектории с наименьшим SHA-256 от «recover-r35/v1/» и исходного ID среди 1 207 фактических историй ISETrace. Выбор до оценки, без фильтра по наличию отзывов. Две точки парного испытания — непосредственно перед событиями первого и третьего *различных по времени* чтений. Если чтений меньше трёх, берём последнее. Повтор одной и той же точки учитываем отдельно в реестре и сообщаем число уникальных точек. Префикс до сбоя включает все события строго до целевого чтения, в том числе ранее завершённые барьеры. Дополнительный контроль на первых 16 историях по тому же хешу открывает транзакцию первого целевого чтения, изменяет таблицу и watermark и завершает процесс без COMMIT. Это проверка незаконченной транзакции, а не сбой оборудования во время физической записи COMMIT.

Уже существует долговечный, упорядоченный и полностью перечислимый журнал изменений отношений с устойчивым номером записи для каждой истории. Для опыта подготовим отдельный реально записанный SQLite-журнал; он содержит только номера событий, бит чтения и целочисленные ID пар. Идентификатор пары локален истории. Журнал представляет изменения, заранее выведенные из исходных событий R35; стоимость повторного построения отношений из сырого журнала не измеряем. Объём файла, число событий, число перечитанных записей и число семантических операций (up/down) публикуем отдельно. Данные после точки сбоя читаются по мере продолжения истории. Первоначальное сохранение источника и его репликация требуют ресурсов за пределами производной таблицы.

Две независимые одинаковые физические базы получают одинаковые изменения. Добавления сразу записываются с INSERT OR IGNORE. Отзывы накапливаются в оперативной памяти; повторное появление отменяет ожидающий отзыв. Барьер чтения в одной транзакции фиксирует удаления, добавления текущего события и его номер. Запускающий родитель остаётся жив, дочерний процесс использует os._exit(73) с открытыми соединениями WAL и synchronous=FULL. Условие после COMMIT означает, что все требовавшиеся SQL-приложения уже вернулись; сами отзывы живут в Python. Перезапуск происходит в другом дочернем процессе. При повторном соединении сверяем integrity_check, номер последнего долговечного барьера и полный материализованный набор с независимым ожиданием до сбоя. Режим только из таблицы начинает со следующей входящей записи и пустой очереди. Режим replay повторяет строго интервал между барьером и последней принятой до сбоя записью, затем обрабатывает тот же хвост. Оба режима получают одинаковый источник и все последующие барьеры. Успех — точное равенство *множества* рёбер инкрементальному эталону на следующем чтении и в конце. Сопоставим также все последующие публичные чтения. Разность множеств проверяется независимо вне дочернего процесса из подписанных operations, а не из подготовленной SQLite. Число строк и вызовов SELECT контролируем относительно разности порядковых номеров; при наличии ранее добавленных строк проверим фактические идемпотентные конфликты вставки. Вторично считаем лишние/пропущенные пары, количество историй и долю восстановлений с непустой последовательностью replay. Подгонки по исходам и заявлений об ускорении не предусматриваем.
