# Разделяемые события графовой памяти

Если пути A и B встречались в одной правке, событие записывается один раз. Из восьми последних записей A оно может исчезнуть раньше, чем из последних восьми B. При следующем обращении к A система может открыть эту запись через ссылку B. Это расширяет доступный контекст на уже сохранённом наборе событий. При полном истечении всех ссылок событие можно отправить в архив. [План сравнения](PROTOCOL_RU.md) · [Реализация](retain.py)

## Поиск файлов без обращения в архив

Раскрываем один путь будущей многофайловой правки и запрашиваем восемь других. Recall@8 — средняя по правкам доля остальных затронутых путей, попавших в первые восемь. Учитываются и пути, ранее не встречавшиеся. Порядок определяется общей частотой прошлых правок, затем частотой пути в последних 32 коммитах и идентификатором. Все варианты для одной строки используют один и тот же прошлый префикс.

| История | Запросы | Собственные последние 8 | Все сохранившиеся для любого участника | Восемь наименьших из сохранившихся | Полная история |
|---|---:|---:|---:|---:|---:|
| A | 1 075 | 58,44% | 58,24% | 59,71% | 58,84% |
| B | 880 | 48,13% | 48,49% | 48,94% | 48,83% |
| C | 1 216 | 50,45% | 51,99% | 51,71% | 52,20% |
| Три длинные истории | 196 | 41,97% | 43,53% | 45,88% | 46,33% |

Первичный контраст на длинной панели составил +1,56 п.п., с равным весом проектов +1,63 п.п. Выигрыш на 15 правках, ухудшение на 12 и равенство на 169. По matplotlib +4,63 п.п., networkx −0,17 и sphinx +0,42. Три проекта дают слабое основание для обобщения. Выбор восьми наименьших правок ограничивает число декодирований, но требует просмотра номеров и размеров всех подходящих записей. Разведочный выигрыш над собственным окном на длинной панели +3,90 п.п. Меньшая правка может содержать более специфическую совместную связь. В [последующем контроле по размеру](../size_control/REPORT_RU.md) простые пороги и нормировка по числу участников тоже улучшили поиск. Для оценки механизма нужен независимый контроль возраста. [Парные исходы](paired.json) · [Анализ](analyze.py) · [Все бюджеты и расходы чтения](results.json)

Отдельная политика даёт каждому файлу собственную равномерную выборку событий через bottom-B по воспроизводимому хешу. Вероятность включения в их объединение при независимых ключах равна 1 − ∏(1 − min(1,B/nᶠ)). Обратные вероятности дают несмещённую оценку парных частот в идеализированной случайной схеме. Ранг зависит от многих оценок нелинейно. На длинной панели один фиксированный seed дал 41,93%, 44,56% и 46,03% для чтения собственных записей, объединения и взвешенного объединения соответственно. На B взвешивание изменило 48,57% до 48,37%. Точная проверка ожидания на 274 состояниях маленькой модели дополняет наблюдаемые результаты реальной хеш-схемы. [Проверка ожидания](unbiased.py) · [Horvitz и Thompson](https://doi.org/10.1080/01621459.1952.10483446)

## Точный ответ с архивом

Состав видимых правок известен. По количеству полностью вытесненных эпизодов и потерянных участий двух файлов можно ограничить неизвестную часть пересечения. При достаточных границах верхние восемь путей с точными баллами определяются целиком. На B это выполнялось для 740/880 запросов, хотя только у 708 якорей сохранились все инцидентные события. На длинной панели все 81 сертифицированные выдачи относятся к якорям с полной историей. Это аналитическая политика. Отдельный измеренный физический план проще и запрашивает холодную часть при любой недостающей истории якоря.

Для каждого запроса независимо проверены восемь ID и их точные баллы. Время — медиана пяти сумм по всем запросам панели. Байты составов измеряются на границе SQLite и вызывающего кода, их нельзя пересчитать в физический дисковый ввод-вывод. Обе политики читают один и тот же поток запросов, а новая политика обслуживает больше данных из общего горячего состояния. В таблицу вошло только время чтения. Отдельный эксперимент учитывает долговременную запись и восстановление.
