# Повторное использование события, удержанного другим файлом

Проверяем сохраняемость и пригодность фактов для следующего чтения. У каждого файла есть лимит B=8 многофайловых эпизодов (B=2,4 и 16 — чувствительность). Эпизод остаётся в общем хранилище, пока хотя бы один его участник ещё сохраняет адрес. При обычном чтении доступны последние B событий известного файла. При расширенном чтении видны все сохранённые эпизоды с этим файлом, включая удержанные другими участниками. Пара сравнивается на одних и тех же **байтах исторических эпизодов**, с одним индексом «файл → сохранённые события» и одним архивом. Расширенное чтение может просмотреть больше эпизодов, поэтому учитываем их число и суммарное число членов. Сравниваем также равные B декодирований при выборе B маленьких транзакций из доступного множества (размер и номер доступны в метаданных); это включает дополнительное чтение метаданных.

**Основной контраст** — Recall@8 по одному раскрытому файлу, все уцелевшие эпизоды против только своих последних восьми на ранее не рассмотренной для этой политики длинной панели networkx/matplotlib/sphinx. Панели, фильтры, SHA подсказок и отложенные задачи те же, что в event_intersection; оценка прошлого компонента на этих задачах уже известна. Для ранжирования используем сырые числа совместных правок, затем частоту файла за 32 предыдущих коммита, затем меньший ID появления. Ненаблюдавшиеся пути остаются в знаменателе. Дополнительные метрики — Hit@8, полное совпадение ID и баллов с доступной до этого момента полной историей, доля полностью доступных эпизодов якоря, размер общего архива в событиях, фактическое число просмотренных событий и их членов. Сообщаем отрицательные результаты, разности по каждому проекту и перенос на A/B/C. В длинной панели всего три кластера, неопределённость оцениваем описательно.

**Проверка механизма.** Контроллер знает общее число прошлых инцидентных событий n_a и число оставшихся r_a. Для числа совместных прошлых правок двух файлов к видимому счёту можно добавить от max(0, d_a+d_b−D) до min(d_a,d_b), где d_a=n_a−r_a, а D — число полностью удалённых событий. Границы следуют из теории множеств на общей удалённой части архива. Совпадение нижней и верхней оценок даёт точный балл. Проверяем, сколько запросов top‑8 с баллами целиком определяется этими интервалами без доступа к архиву, и сколько раз нужен архив для остальных случаев. Для контролируемой проверки есть скрытый полный журнал, он используется только для оценки или явно отмеченного точного восстановления.

**Контроли при записи.** Кроме последних B используем независимый для каждого файла равномерный bottom-B по хешу (репозиторий, файл, SHA). Сравниваем чтение своих событий, чтение объединения и взвешивание сохранённого наблюдения по обратной вероятности включения. В идеализированной схеме независимых непрерывных случайных ключей вероятность попадания события e в объединение равна 1−∏(1−min(1,B/n_f)) по его участникам. Величины n_f фиксируются в момент запроса; при этом сумма обратных вероятностей по сохранённым успешным наблюдениям является несмещённой оценкой накопленного балла для фиксированной пары. Это утверждение об оценке, не о точности рейтинга. Удержание по давности детерминировано и эта формула к нему не применяется. Для проверки вероятностной части фиксируем seed независимого хеша, дополнительно симулируем распределение включений на малом примере. [Horvitz и Thompson](https://doi.org/10.1080/01621459.1952.10483446) · [Cohen и Kaplan](https://www.cs.tau.ac.il/~haimk/papers/p225-cohen.pdf).

Холодный архив, размер индексов, накладные расходы БД, пропускная способность и качество рекомендаций — разные затраты. Связанное физическое исследование независимо измеряет хранение общих событий в SQLite. Эта проверка добавляет исследование контракта чтения из уже сохранённого набора.
