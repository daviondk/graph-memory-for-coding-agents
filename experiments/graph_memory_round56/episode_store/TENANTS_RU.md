# Уплотнение нескольких проектов в одном файле

В отдельных файлах для шести проектов сборка мусора сократила число событий, но на второй панели не изменила суммарный размер базы после VACUUM. Возможная причина — минимальные страницы и отдельные корни таблиц SQLite для каждого проекта. Измеряем тот же финальный набор состояний в одном файле на шесть независимых пространств имён (первичный ключ начинается с числового ID проекта). Объединяем физические таблицы, сохраняя отдельные каталоги путей, частоты и события. Первичный размер страницы SQLite 4096; проверки чувствительности 1024 и 8192. Сравниваем сканирование полного и очищенного журнала, блочные варианты, индивидуальные копии восьми событий и упакованные ссылки на общие события. Все последние восьмёрки должны совпасть по номерам исторических коммитов и полному составу. Это опыт по размещению конечного состояния и холодному/тёплому чтению. Периоды накопления, задержки конкурентных транзакций и реальное распределение нагрузки в межпроектной службе здесь не измеряются.

Для итогового файла используем фактические таблицы работавшего локального хранилища, повторно выполняя тот же поток из Git. До VACUUM вставляем строки в хронологическом порядке или по порядку ключей исходных таблиц. Общая схема для каждого плана имеет составной ключ (проект, локальный ID). Пишем суммарный размер файлов и сумму размеров кодированных значений отдельно. При каждом размере страниц проверим все когда-либо существовавшие якорные файлы и все их предъявляемые свидетельства после повторного открытия базы.
