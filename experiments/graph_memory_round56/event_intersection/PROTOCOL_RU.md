# Когда краткая история двух файлов определяет точный вес ребра

Это продолжение эксперимента со Space-Saving, где двусторонние границы уменьшили число точных пересечений, но за один запрос приходилось проверять много пар. В новой сводке сохраняем события каждого файла, а не соседей. Каждый многопутевой коммит получает общий возрастающий номер, одно и то же значение у всех его участников. Для каждого файла сохраняем его общее число таких событий и B последних номеров. При записи одного коммита размером m достаточно обновить m файлов. Для явного обновления всех ориентированных связей требуется m(m−1) добавлений частоты.

Пусть c — более поздняя из двух границ сохранённых суффиксов; если вся история файла поместилась, её граница равна 0. Обе истории на [c,T) известны точно, пусть точное пересечение там равно z. Вычисляем r_a и r_b — количества событий файлов до c по полным количествам и известным суффиксам. В префиксе c возможных номеров. Тогда полное пересечение находится в [z+max(0,r_a+r_b−c), z+min(r_a,r_b)]. Проверяем достижимость обеих границ полным перебором множеств на малой вселенной. Совпадение границ позволяет вернуть точный счёт. В иных случаях ранжирование верхних границ выбирает пары, для которых требуется запрос только к префиксу [0,c). Результат включает ID и точный балл всех восьми файлов. Когда неизвестен сам якорь, все его совместные частоты равны нулю.

**Сравнение при одинаковых входах.** Основные B=8 и B=25. Последний соответствует фиксированной полезной ёмкости 104 байта на файл: 25 номеров и одно количество по 4 байта, против 8 трёхсловных счётчиков Space-Saving, границы вытеснения и количества событий. Упаковка имеет переменную длину для редко встречавшихся файлов; выделенный потолок, фактические сериализованные байты и память интерпретатора — разные величины. Сравниваем точные ответы по событиям, по Space-Saving и по полному материальному представлению. Контроли границ: только количества, нижняя граница по общим сохранённым событиям и глобальный остаток без согласования времён, двусторонний общий суффикс. Для каждого варианта отмечаем число точных запросов, позиции в меньшем списке для адресной проверки, долю запросов с целиком сертифицированной выдачей. Для точных методов Recall совпадает по построению. Логическая цена памяти включает регистрацию событий, равенство ID, поддержку порядка и приведённые ограничения. Физическая проверка включает сопоставление с прямым чтением инцидентных эпизодов и точными битовыми векторами.

Используем панели A/B/C из соседнего опыта без перестройки выборки. Для длинного внешнего прогона до загрузки фиксируем три проекта networkx/networkx, matplotlib/matplotlib, sphinx-doc/sphinx. Берём до 4 096 последовательных переходов от публичной вершины по первому родителю. Храним только SHA и отсортированные пути Python для коммитов до 64 путей, включая удаления. Идентичность — путь. Среди многофайловых коммитов второй половины выбираем детерминированную подвыборку по SHA modulo 11 равно 0; одну известную подсказку выбирают остальные разряды SHA. Все методы используют один и тот же будущий эталон и одинаковое число файлов. Вне новой выборки проверяем все прежние случаи. Сообщаем результаты по всем трём проектам и описательную совокупную оценку, без вывода о генеральной совокупности по трём проектам. Режим доступа к опубликованному прошлому Git отличается от эпизодов, которые агент лично наблюдал.

Общий порядок ID событий родствен согласованным bottom-k сводкам Cohen и Kaplan. Здесь порядок хронологический, выход требует точных оценок, границы проверяются против произвольного допустимого дополнения. Оптимальность границы формулируется для двух индивидуальных сводок; прочие данные могут дополнительно сузить её.
