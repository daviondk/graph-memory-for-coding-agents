# Точная графовая память в долговременном хранилище SQLite

Восемь последних совместных изменений каждого файла можно использовать при поиске истории любого участника тех же изменений. Мы реализовали эту схему в SQLite с атомарной записью новых событий и восстановлением после перезапуска. Все три варианта хранения вернули одинаковые восемь соседей с одинаковыми баллами на **1 076 исторических запросах** в девяти проектах. На длинной панели размер базы сократился с **664 до 500 КиБ** (−24,7%), на короткой вырос со **196 до 200 КиБ**. На обычной нагрузке суммарное время операций на короткой панели выросло на 1,6%, на длинной сократилось на 2,1% относительно полного индекса. Это результат для точного индекса эпизодов совместного изменения в Git. Качество ответов языковой модели здесь не измерялось. [Протокол](PROTOCOL_RU.md) · [Агрегаты](results.json) · [Все 162 прогона](runs.json.gz).

## Механизм и сравнение

* **Полный индекс.** Основной журнал хранит номер эпизода, SHA коммита и список идентификаторов изменённых путей. Вторичный индекс содержит пару «файл, событие» для каждого членства. По нему запрос находит исходные эпизоды для выбранного файла.
* **Собственный кэш.** Та же физическая база. Для каждого файла клиент сохраняет восемь последних эпизодов, в которые входил именно этот файл, и читает из БД более старые эпизоды при необходимости.
* **Общий горячий слой.** Каждый файл владеет восемью последними ссылками. Эпизод остаётся горячим, пока у него есть хотя бы один владелец. По каждому участнику запроса доступны все его горячие эпизоды, в том числе сохранённые благодаря другим файлам. После потери последнего владельца система в той же транзакции переносит членства старого эпизода в дисковый индекс. Основная запись события и его SHA доступны во всех схемах. [Реализация](store.py).

Для выбранного файла любой исторический эпизод находится ровно в одной из двух групп — горячей или вытесненной. Число совместных изменений двух файлов равно сумме по этим непересекающимся группам. Поэтому их раздельный учёт сохраняет точные баллы, порядок с фиксированным разрешением ничьих и заполнение оставшихся мест. При восстановлении каждый из восьми последних эпизодов любого пути по определению находится в объединении горячих событий. Этого объединения и каталога холодных путей достаточно для восстановления владельцев. Словарь путей и последние частоты, которые используются для разрешения ничьих, являются общим входом всех схем. Их хранение и восстановление в измерения не включены.

## Нагрузка и измерения

Панель B содержит 3 456 ревизий шести проектов, 983 принятых многопутевых эпизода и 880 запросов. Длинная панель содержит 12 288 ревизий трёх проектов, 5 066 эпизодов и 196 запросов. В запросе виден один файл текущего изменения. Система ранжирует файлы по событиям до этого изменения. Однофайловые коммиты участвуют в расчёте частоты для разрешения ничьих, в журнал совместных изменений попадают события с 2–64 путями. Бюджет равен восьми ссылкам на файл. Предварительная подготовка потока и его эталонных результатов исключена из таймера. [Состав панелей и выбор запросов](../event_intersection/evaluate.py) · [Журнал эксперимента](benchmark.py).

Каждая схема использовала свежую базу на диске D, WAL, synchronous=FULL и отдельную транзакцию на каждый принятый эпизод. Измерены две нагрузки — одно чтение в исходной точке решения и восемь повторных чтений того же запроса до следующей записи. Внутри блока «проект × повтор» порядок шести вариантов перемешан, seed 56045. Всего 9 × 3 схемы × 2 нагрузки × 3 повтора = **162 запуска**. Повторы нужны для оценки изменчивости времени на одном компьютере. Python 3.14.4, SQLite 3.50.4, Windows 10. Записи результата запроса в кэш в трёх реализациях нет. Добавление такого кэша позволяло бы обслуживать семь одинаковых запросов из восьми без повторного вычисления и требует отдельного сравнения на реалистичной последовательности разных запросов.

### Полное время операций

Числа в таблице — миллисекунды, медиана трёх сумм по проектам панели. Каждая сумма включает выполнение и фиксацию всех транзакций записи и вычисление всех запросов. Создание и закрытие БД, отдельный финальный checkpoint, измерение размера и контрольное восстановление вынесены за границы этой метрики. В исходных данных отдельно указаны время инициализации и финального checkpoint.

При нагрузке 1× на панели B собственно чтение для трёх схем заняло 35,8 / 27,5 / 23,9 мс, на длинной панели — 25,4 / 23,8 / 19,7 мс. Доминирует запись. На панели B при 1× медианы времени записи составили 429,8 / 444,3 / 448,9 мс. При таком соотношении чтений и записей экономия на поиске не окупила обслуживание горячего слоя.

В оперативной памяти общий слой поддерживал 3 338 ссылок владельцев и 4 274 членства горячих событий на панели B. На длинной — 11 752 и 21 945 соответственно. Это логические счётчики. ### Восстановление и независимая проверка

После закрытия и открытия конечных баз медиана суммарного времени старта общего слоя составила 12,0 мс на B и 15,4 мс на длинной панели при 1×. Восстановление прочло 943 и 3 920 строк каталогов и 17 096 и 87 780 байт составов соответственно. Полный индекс открылся за 9,5 и 4,9 мс. Собственный кэш первоначально пуст, догружает истории при последующем обращении к файлу. Отдельная проверка с перезапуском **на середине** всех исходных историй показала 1 572 и 5 936 строк такой отложенной догрузки у собственного кэша.

Для каждого layout контрольный скрипт пересчитал итоговые списки и баллы отдельным SQL-запросом с self-join таблицы членств и собственным SQL-учётом текущих частот. Совпали 1 076/1 076 запросов у каждой реализации. Из них 698 прошли после закрытия и нового подключения. Дополнительно сверено членство каждого исходного эпизода. Вторая реализация эталона в замерах использует пересечение битовых масок. [SQL-проверка](correctness.py) · [Результаты](correctness.json).

Для каждой схемы выполнены 14 повторных записей, 28 конфликтных повторов (изменена ревизия или содержимое), 14 пропусков номера и три отката после изменений внутри транзакции. По 187 раз проверен вывод при синтетических переходах, включая потерю последнего владельца. Наконец, шесть дочерних процессов аварийно завершили через os._exit внутри SQL-триггера или сразу после commit. После повторного открытия SQLite успешно прошла integrity_check, незавершённый эпизод отсутствовал, зафиксированный сохранился, а повтор привёл к одному и тому же журналу из девяти событий без дубликатов. Эти проверки моделируют прекращение процесса при работающей ОС. Для отказов накопителя и конкурирующих писателей нужны отдельные испытания. [Сценарии аварийного выхода](crash.py) · [Результаты](crash-results.json).

### Вывод для статьи

Общий горячий слой уменьшил объём исторических составов, прочитанных из SQLite, на **96,0%** на B и **92,3%** на длинной панели относительно полного индекса. На длинной истории этот выигрыш сочетался с меньшим размером БД. На короткой накладные расходы SQLite и более дорогая запись ограничили выигрыш. Реплики в 8× моделируют повышенную частоту обращений, причём повторяют один и тот же запрос при тёплом кэше страниц. Для распространения вывода на другие нагрузки нужны более длинные потоки прикладных запросов к разным якорям, сравнение с кэшем готовых ответов и измерение фактического потребления оперативной памяти. Числа в таблицах характеризуют этот механизм хранения и эти панели.

Для проверки сохранённых агрегатов запустить `python -B benchmark.py --verify`. Команды `python -B correctness.py` и `python -B crash.py` повторяют проверки целостности. Воспроизводимый полный замер выполняется командой `python -B benchmark.py` в свежей копии каталога без файлов runs.json.gz и results.json, при сохранении соседних каталогов с входными данными. Скрипт сохраняет результат каждого проекта и варианта и при прерывании начинает с первого отсутствующего запуска.
