# Точный долговременный журнал с горячими событиями и индексом вытесненных событий

Каждый принятый многопутевой эпизод атомарно записывает номер, SHA ревизии и упакованный список ID путей в SQLite. У каждого файла — восемь последних ссылок. Пока у события остаётся хотя бы один владелец, в оперативной памяти можно использовать весь его состав по любому участнику. После последней потери владельца его членства перемещаются в индекс холодного слоя. Чтение объединяет непересекающиеся множества горячих и холодных событий и возвращает полный точный top‑8 с баллами, включая устойчивое правило ничьих. В горячем списке SQL хранится по одному ID события; сам состав всегда уже записан в основной журнал. В таблице наличия холодной истории по одному ID на файл с вытесненными событиями. Восстановление читает этот каталог и горячие записи в хронологическом порядке. Оно восстанавливает владельцев, поскольку все последние восемь событий каждого пути входят в объединение. Повторное построение индексов по всему репозиторию для старта не требуется.

Сравниваем три схемы: полный индекс всех членств с одним запросом за эпизодами, та же БД с кешем собственных последних восьми эпизодов и чтением более старого префикса, новая раздельная схема. Всем доступны одни входные (ID, SHA, состав), те же вторичные ключи при запросе и полные исходные эпизоды для аудита. Все 880 запросов панели B, все 196 длинной панели, в реальном историческом порядке. При каждом принятом событии отдельная SQL-транзакция в локальном WAL, synchronous=FULL. Основная нагрузка — один запрос на наблюдаемом решении, дополнительная — восемь чтений на каждое такое решение. Учитываем полностью время записи и чтения, размер standalone БД после checkpoint/truncate, число строк обоих индексов и горячего слоя, время восстановления, входные записи, число прочитанных из БД байтов составов. Время создания эталонных ответов вне измерения. Разные организации БД запускаются на новых файлах в перемешанном порядке, три повтора на проект, seed 56045. Логические счётчики проверяем по каждому запуску. Небольшое число повторов и один компьютер ограничивают интерпретацию задержек.

Отдельно проверяем повтор того же события, коллизию повтора, пропуск номера, откат транзакции при имитации сбоя и повторное открытие на промежуточной ревизии. Проверка готовности одной операции на одном соединении не доказывает многопользовательской масштабируемости. Бюджет B ограничивает ссылки **на каждый файл**; объём объединения, прочих индексов и полных исходных событий учитываем отдельно. Это точное долговременное хранилище и неограниченный архив. План следует после измерения стоимости только чтения в [предыдущем сравнении](../shared_evidence/PHYSICAL_RU.md).
