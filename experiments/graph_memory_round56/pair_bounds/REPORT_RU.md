# Когда стоит проверять частоту связи с другой стороны

У каждой пары файлов есть две ограниченные сводки Space-Saving. В сводке популярного файла редкий сосед может оказаться плохо определён, хотя у соседа сохранилась точная запись о той же совместной правке. В протоколе заранее задан порядок разрешения ничьих. На всех трёх панелях и при всех трёх ёмкостях восемь идентификаторов и их баллы сверялись с полным журналом. [Протокол](PROTOCOL_RU.md) · [Реализация](bounds.py)

| Политика на контрольной панели, 880 запросов, восемь счётчиков на файл | Запросы к обратной сводке | Точные пересечения | Позиции в меньших списках | Выдачи целиком из сводки |
|---|---:|---:|---:|---:|
| Только сводка открытого файла | 0 | 44 788 | 183 411 | 244 |
| Обе стороны сразу | 95 159 | 34 155 | 150 092 | 248 |
| Обратная сторона по границе top-8 | 44 788 | 34 155 | 150 092 | 248 |

Отложенная проверка убрала в среднем 12,08 точных пересечений на запрос относительно одностороннего контроля. Описательный 95% интервал при повторной выборке шести репозиториев составляет [4,21; 17,63], среднее с равным весом проектов — 9,23. Один прямой проход по инцидентным эпизодам затронул всего 51 022 позиции участников. Счёт сокращённых пересечений поэтому недостаточен для выбора физического плана. Такой отбор полезно рассматривать при наличии дорогого адресного доступа и дешёвых обратных сводок. [Полные результаты и анализ чувствительности](results.json) · [Измерение физических планов](../shared_evidence/physical-wal-summary.json)

Базовые интервалы происходят из опубликованного алгоритма Space-Saving. Вклад этого опыта — проверка двустороннего уточнения для точной выдачи в графе совместных изменений, включая стоимость повторного чтения. Команда воспроизведения приведена в `run.py`.
