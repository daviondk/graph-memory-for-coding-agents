# Точное чтение из двух ограниченных сводок одной исторической связи

Измеряем, сколько точных подсчётов пересечения историй файлов можно исключить, если соседства обоих файлов уже сохранены ограниченными сводками Space-Saving. Для ребра (a,b) число совместных правок одинаково с обеих сторон. Сводки различаются, поскольку у файлов разные соседи и разная нагрузка. Проверяем пересечение двух интервалов возможных частот вместо использования только интервала со стороны уже открытого файла.

**Постановка.** Первая и вторая панели Git из R55/cochange, по шесть проектов, те же коммиты и SHA-выбор одного открытого пути. По первым родителям в хронологическом порядке принимаются изменения до 64 Python-путей, включая удаления согласно проекции R55. Первые 64 коммита служат прогревом. В каждом последующем коммите с двумя и более путями, увидев один из них, возвращаем top‑8 остальных известных в прошлом файлов с их точными накопленными баллами. Порядок задают число совместных правок, частота файла в последних 32 коммитах и меньший ID первого появления. Отдельно проверяем перенос на десять других проектов репликации R55/partner_clock: объединяем добавленные/изменённые и удалённые Python-пути, правила идентичны. Эти публичные данные ранее использовались для других вопросов; все три панели для нового алгоритма повторные. Параметры не обучаются.

**Память при записи.** Для каждого файла поддерживаем до H счётчиков Space-Saving, рост количества при повторе, замена наименьшего счётчика при промахе, при равенстве вытесняем больший ID. Храним ID соседа, оценку и ошибку; H=8 основной, H=16 и 32 чувствительность. Отдельно храним число допустимых многофайловых коммитов с каждым файлом и флаг, была ли сводка переполнена. Для всех вариантов верхняя граница частоты ограничена меньшим из чисел событий на двух концах. Баллы никогда не отрицательны. Индекс эпизодов для точной проверки общий. Рекомендации не используют содержимое текущего коммита, кроме предоставленного якоря и самого факта запроса.

**Контроли чтения.** (1) Полное воспроизведение совместных правок из эпизодов, (2) точное ранжирование по односторонней сводке и адресным проверкам неоднозначных кандидатов, (3) те же исходные сводки с учётом верхней границы отсутствующего соседа на другом конце для всех подходящих файлов, затем полной информацией обратной сводки, (4) двустороннее уточнение только для кандидатов, способных изменить результат. Абляции отделяют ограничение частотой и роль наблюдавшегося обратного счётчика. Нельзя сравнивать только число проверок: у третьего и четвёртого методов есть цена обращения к другим сводкам. Учитываем просмотренные адреса, обратные обращения, истинные пересечения и число просмотренных позиций списков. Отдельно считаем, как часто можно полностью отдать точный результат из памяти. Для низкой частоты якоря дополнительно сравниваем с дешёвым одним проходом по всем связанным эпизодам. Нулевая частота, равенство и неизвестный якорь входят в оценку.

**Анализ.** Все политики обязаны вернуть тот же порядок и баллы, что восстановлены из событий. Основной контраст на второй панели, H=8 — парное уменьшение числа точных подсчётов на запрос относительно сильного одностороннего контроля, 95% описательный bootstrap по целым проектам (20 000 повторов, seed 56015). Сообщаем обе панели и перенос независимо, равный вес каждого запроса и вторичное среднее по проектам. Показатель Recall@8 относится к задачам поиска файлов; все точные политики должны иметь идентичное качество. По каждому случаю сохраняем достаточные данные для проверки. Вопрос о суммарной задержке измеряется реальным исполнением, где применимо. Изменение числа подсчётов само по себе не даёт оснований для заявления о скорости.

Метод использует интервалы опубликованного алгоритма частых элементов. Проверяем конкретное следствие симметрии пар коммита для запроса агента.
