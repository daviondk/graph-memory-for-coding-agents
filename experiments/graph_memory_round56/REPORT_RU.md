# Совместные правки как разделяемая графовая память

После проверки отдельных окон памяти в предыдущей серии исследовали, можно ли повторно использовать уже сохранённое свидетельство о совместной правке, сколько это стоит базе и помогает ли модельному решателю. В хронологическом тесте мы открываем один затронутый путь, затем по доступному к этому моменту прошлому предлагаем восемь связанных файлов. Это измерение следующего чтения. Для проверки влияния на код выполнен отдельный эксперимент со скрытыми авторскими примерами. [Предыдущий отчёт](../graph_memory_round55/REPORT_RU.md)

## Результат для системы

Одно событие может входить в последние восемь изменений сразу нескольких файлов. Храним его состав один раз. Пока хотя бы один файл удерживает ссылку, любой участник может использовать событие при чтении. Для точного ответа добавляем из архива только полностью вытесненные эпизоды, затем объединяем частоты и возвращаем восемь файлов с баллами. Исходный коммит остаётся доступен для аудита. Отдельно проверено условие, при котором весь результат уже определяется усечёнными данными. [Разделяемая память и формулы](shared_evidence/REPORT_RU.md) · [SQLite](durable/store.py)

## Дополнительные сравнения и проверки

- Для сводок Space-Saving использование симметричной оценки со стороны соседа уменьшило число точных пересечений с 44 788 до 34 155 на 880 запросах. Прямой проход по событиям выгоднее по числу просмотренных позиций. [Двусторонние границы](pair_bounds/REPORT_RU.md)
- Если сохранять последние 25 идентификаторов событий на путь, выравнивание двух суффиксов по времени уменьшило число точных пересечений с 1 698 до 1 012 на тех же запросах. Получена достижимая верхняя и нижняя границы неизвестной частоты. Проверка охватила 262 143 сочетания множеств и бюджета на малой вселенной. В физическом тесте один SQL-запрос за упакованными событиями оказался быстрее адресных уточнений. [Границы и стоимость](event_intersection/REPORT_RU.md)
- Проверили и более простой контракт, при котором файл читает только собственные последние восемь событий. На шести контрольных проектах обратный проход для удаления устаревших событий уменьшил размер SQLite с 126 976 до 122 880 байт при страницах 4 КиБ. При 8 КиБ разницы в размере не было. При фиксированном бюджете 64 байта на путь сжатие повторов дало +0,01 п.п. Recall@8 относительно сильного простого контроля. Это отдельная схема хранения со своим контрактом. Проверка публичного бенчмарка воспроизвела 9 660 ранжирований. В полном воспроизведении экспериментов с генерацией требуются указанные веса модели и окружение. ## Сравнение с опубликованными правилами отбора

Ранние работы по рекомендации связанных изменений уже проверяли фильтры размера коммита. В ретроспективном контроле перенесли их на ту же совокупность разделяемых событий и одинаковый предел восьми декодирований на запрос. На 196 запросах ограничение правками до восьми файлов дало 47,32% Recall@8, выбор восьми наименьших — 45,88%. Взвешивание каждого участника как 1/(m−1) на тех же восьми наименьших событиях дало 47,61%, на собственных восьми — 46,12%. Сочетание приоритета правок до шести файлов, заполнения свободных мест и той же нормировки дало 48,90% в дополнительном факторном сравнении. Для него декодировано 9 496 участий файлов против 7 698 при взвешенном отборе наименьших правок. Строгий порог 6 со взвешиванием дал 47,96% при 3 323 прочитанных участиях. У всех вариантов общая доступная история и один предел числа прочитанных правок. Выборка уже использовалась при разработке. Измеримая выгода разделяемого физического хранения служит более прочным результатом для статьи. [Сравнение правил и числа чтений](size_control/REPORT_RU.md) · [Предшествующие работы](RELATED_RU.md)

**Следующая гипотеза для статьи.** Полезность повторно доступной записи зависит от числа её участников. Большие коммиты дают много слабых связей. В новом отложенном наборе стоит заранее зафиксировать основные варианты — статический порог и отбор со взвешиванием по размеру. На новых проектах нужны единый предел чтений, учёт байтов и контроль возраста свидетельств. Критерии успеха — улучшение поиска на замороженном методе и подтверждённая экономия базы при том же точном ответе. Проверенные улучшения стоимости хранения и чтения можно уже показать в демонстрации. Заявление о новом SOTA по качеству решения задач имеющимися результатами не обосновано.
