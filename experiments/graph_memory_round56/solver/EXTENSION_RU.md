# Дополнительная проверка механизма до раскрытия исполняемых результатов

Пока основная генерация ещё выполняется, фиксируем две проверки на тех же 36 задачах. В обоих случаях сравниваем сохранённую реализацию с независимо исполняемыми авторскими doctest.

1. При равном числе локальных коммитов сравним последние восемь с восемью случайно выбранными из всей доступной истории данного пути. Выборка без возвращения сортируется по SHA-256 от имени проекта, пути и SHA коммита. Она фиксирована по пути и не использует целевую функцию. Правило BM25 остаётся прежним.
2. Проверим, стоит ли читать только наблюдения, где тест прямо вызывает нужную функцию. Локальная политика сначала ищет непосредственный вызов в последних восьми связанных коммитах, затем во всех коммитах с данным путём и затем во всех исторических тестах. На первом непустом этапе выбирает один результат BM25. Если прямого вызова нигде нет, возвращает исходный полный BM25. Старший контроль использует такой же непосредственный вызов сразу по всей доступной истории и тот же fallback. Распознаём имена и атрибуты в видимом исходном коде исторического теста, без статического разрешения импортов; проверяем наблюдаемость вызова после токенизации отдельно. Рассчитываем источник и глубину каждого срабатывания. Прямой вызов в прошлом может оказаться нерелевантен раздельным требованиям будущего контракта.

Фиксированные руки: local8, случайные восемь, поэтапный поиск подтверждённого вызова, полный подтверждённый поиск, полный BM25. Длина отрывков в каждом вопросе общая для всех пяти, включая контроль; если кандидат короче предыдущего минимума, пересчитываем также обе базовые руки в этой задаче. Для неизменившегося полного входа используем уже полученную greedy-генерацию. Параметры, тесты, архитектура и семя совпадают с основной постановкой. Основные сравнения расширения — поэтапный поиск против полного BM25 и полного поиска по вызовам. При отборе усиливаемых свидетельств к выходам скрытых примеров не обращаемся.
