# Что сохранять после пакетного чтения фрагментов

Исходный опыт на 305 состояниях SERBench показал, что потоковое последовательное чтение/вытеснение в маленьком LRU почти не использует межсостояниевые совпадения. Перед сравнением новых политик фиксируем более сильный режим. Список кандидатных ключей поступает целиком. Читатель сначала определяет **все** попадания по состоянию кеша на начало запроса. Затем возвращает найденные векторы и кодирует каждый оставшийся уникальный вход ровно один раз. Только после выдачи начинается изменение постоянного кеша. Все варианты видят одинаковые текущие ключи, их стоимость и результаты предыдущих чтений. Акции агента и будущие запросы недоступны. Временный буфер текущего запроса общий, в постоянную ёмкость не входит. Сравнение с потоковым R48 оставляем диагностическим.

**Основной контраст.** При ограничении постоянного состояния в 512 КиБ сравниваем предлагаемый отбор по произведению стоимости кодирования и сглаженной прежней частоты с усиленным пакетным LRU. Оставшееся место сравниваем в точности в байтах: 256 байт заголовка, 1 024 байта эскиза для всех, затем слоты по 16 384 байта на действительный float32-вектор из 4 096 координат и 64 байта на его 32-байтный ключ и операционные метаданные. При 512 КиБ размещается 31 слот. Также исследуем 128 КиБ и 2 МиБ. Отдельно даём число векторов при том же лимите у LRU, если он отдаёт под векторы неиспользуемые 1 024 байта. В Python служебные объекты измерительного стенда не образуют исследуемый формат хранения. Проверка сериализованного постоянного представления учитывает заголовок, эскиз, записи и место под каждый вектор.

**Кандидат.** Счётчик Count–Min состоит из четырёх строк по 256 byte-счётчиков. Последовательные байты криптографического ключа дают индексы разных строк, счётчик насыщается при 255. Каждые 1 024 различных обращений, считаемых внутри потока один раз на уникальный ключ текущего запроса, делим все счётчики пополам. После наблюдения пакета оставляем среди нынешних кандидатов и прежних резидентов наибольшие значения tokens·(1+min счётчиков). При равенстве побеждает стабильный хеш. Эта целевая функция служит эвристикой потенциально сэкономленных токенов. Контроль без частоты сохраняет самые дорогие единицы, контроль без стоимости использует только оценённую частоту. Добавляем равновероятное стабильное хеширование.

**Сильные контроли.** (1) пакетный LRU по входному порядку, (2) основной усиленный batch LRU, который в пределах последнего пакета отдаёт преимущество уже оказавшимся полезными резидентам, обрабатывая новые ключи раньше повторных, (3) SLRU с защищённой долей около 80%, куда переходят повторно затребованные пробные ключи, (4) TinyLFU-подобное сравнение частоты претендента с частотой LRU-жертвы, использует тот же эскиз без doorkeeper, равенства в пользу резидента. Дополнительно показываем верхнюю границу на каждый запрос: оракул может идеально выбрать из всех действительно наблюдавшихся ранее ключей до C самых дорогих, нужных на текущем запросе. Эта граница допускает знание следующего запроса и ослабляет ограничения последовательного вытеснения. [TinyLFU](https://arxiv.org/abs/1512.00727)

**Статистика.** Каузальные строгие префиксы, общая 305 и раздельные 101/204 панели прежнего опыта. Первичная метрика — дополнительно сэкономленные токены между запросами после устранения внутрипакетных повторов, делённые на полную стоимость обработки запросов и документов без кеша; основной эффект — разность этих долей относительно усиленного batch LRU при 512 КиБ. Парные 95%-е интервалы по 20 000 перевыборкам целых репозиториев, seed 480532. Улучшение зафиксируем, если нижняя граница положительна. Если частотный вариант проиграет, фиксируем результат. Результаты предназначены для повторного обслуживания поискового пула в ходе известной траектории. [Исходное исследование](../embedding_reuse/PROTOCOL_RU.md)
