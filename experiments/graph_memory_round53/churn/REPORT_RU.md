# Журнал победителей на потоке с отзывом свидетельств

Графовая память получает свидетельства связей между инструментами. Для каждой ревизии нужно вернуть адрес наиболее подтверждённого источника и его точную оценку, включая состояния до последующих отзывов. В 40 записанных траекториях ISETrace при восьми чтениях на ревизию журнал победителей затратил **113,27 мс** на весь поток, версия оценки каждого кандидата с покрывающим индексом — **151,43 мс**, пересчёт по интервалам рёбер — **133,93 мс**. Когда чтений не было, один интервал рёбер обрабатывался быстрее журнала. Все три варианта вернули одинаковые пары «адрес, оценка» для 1 112 состояний, включая пустое состояние каждой траектории.

## Данные и задача

События взяты из подписанной числовой проекции R44, привязанной к оригинальным сообщениям и границам R48. Во входе 1 072 группы инструментальных сообщений, 1 264 наблюдаемых производителя, 831 элементарное изменение связи. После свёртки одновременных событий получено 464 ненулевых изменения пар; 118 уменьшают вес, в 112 случаях положительное ребро исчезает. На уровне исходящих степеней 72 уменьшения среди 405 ненулевых изменений. Это реальные переходы в восстановленном отношении FEEDS на записанных синтетических траекториях OS-агентов. Источник не измеряет пользовательские исправления текста или реальные откаты Git. Среди данных нет повторно активированного ребра после полного обнуления, поэтому правильность такого случая отдельно проверена регрессионным тестом.

Кандидат становится видимым в группе, где наблюдается его результат инструмента. Оценка равна сумме текущих весов исходящих связей, ничьи разрешает меньший ID инструмента. В 93 случаях изменился адрес, ещё в 94 сохранился адрес и поменялось число подтверждений. Отрицательная поправка пришлась на прежнего победителя в 28 группах, из них 18 завершились сменой адреса.

**Пример из данных.** В траектории q11, ревизия 16, у источника 14 два подтверждения, у источника 3 одно. Единственная поправка ребра в ревизии 17 уменьшила вес FEEDS(14,19) на единицу. Оба источника получили оценку 1; вернулся ранее доступный адрес 3. Два впервые появившихся результата 21 и 22 имели нулевую оценку. R48 независимо зафиксировал переход счётчика источника 14 с 2 до 1 в границе сообщения 49. ## Три плана SQLite

Во всех вариантах одинаковы интервалы активности направленного ребра, текущие оценки с покрывающим индексом, номер подтверждённой ревизии и реестр идентификаторов транзакций для повторов. Текущий максимум читается из одного индекса. Предполагается атомарное применение всех изменений группы.

| При запросе к прошлому | Дополнительное состояние | Строк |
|---|---|---:|
| Суммирование всех действовавших на ревизии связей по источникам | Исходная таблица интервалов рёбер | 352 периода ненулевых весов |
| Лучший кандидат среди действовавших интервалов оценки | История оценок с индексом по оценке, ID и границам | 1 669 версий кандидатов |
| Запись о последней смене пары «победитель, оценка» до нужной ревизии | Журнал с ключом (траектория, ревизия) | 227 изменений |

Журнал хранит начального победителя в каждой из 40 траекторий и 187 последующих изменений пары. Для сохранения состояния после отзыва достаточно применить всю группу, прочитать максимум из текущего индекса и сравнить его с последней сохранённой парой. Если пара прежняя, дополнительная строка не пишется. По индукции этот алгоритм даёт точный ответ для любой обработанной версии: значение между двумя соседними записями журнала постоянно, на границе оно совпадает с максимумом после обработки события. При одинаковом адресе и новой оценке алгоритм сохраняет новую строку. Корректность требует, чтобы изменение текущей таблицы, интервалов, ревизии и журнала подтверждалось одной транзакцией. Чтение номера текущей ревизии и значения также проводилось в едином snapshot, включая случай конкурентного коммита между этими запросами.

## Результаты на диске D

| Чтений после ревизии | Пересчёт по рёбрам, мс | История оценок, мс | Журнал, мс | Отношение времени истории оценок к журналу, 95% ДИ |
|---:|---:|---:|---:|---|
| 0 | 60,87 | 118,89 | 72,03 | 1,651 [1,195; 2,482] |
| 1, равномерное обращение в прошлое | 80,92 | 104,91 | 74,97 | 1,399 [1,225; 1,554] |
| 8, поровну текущих и исторических | 133,93 | 151,43 | **113,27** | **1,337 [1,292; 1,389]** |

В первичном режиме 8 576 чтений. При сравнении с пересчётом исходных интервалов отношение времени составило 1,182 [1,150; 1,231], журнал быстрее в 6/6 повторов для обеих баз. При нулевом числе чтений интервал/журнал равен 0,845 [0,759; 0,919], что соответствует меньшим расходам записи у плана без дополнительной истории. При одном историческом обращении — 1,079 [0,932; 1,333]; данных недостаточно для устойчивого различия относительно пересчёта. В первичном режиме работа на чтениях заняла соответственно 69,78, 47,56 и 47,35 мс. Основная разница между журналом и индексом версий кандидатов пришлась на запись (57,06 против 90,38 мс) и checkpoint (8,87 против 13,49 мс). Это измерение **не показывает большого преимущества времени отдельного чтения над покрывающим индексом кандидатов**. Заявлять ускорение каждого чтения в 1,337 раза было бы ошибкой.

После checkpoint файл SQLite занимал 164 КиБ у пересчёта, 248 КиБ у версии оценок, 164 КиБ у журнала. Размер округляется по страницам. Все планы содержат 1 072 квитанции, входные интервалы и общий индекс текущей оценки. Каждый показатель — среднее шести чередуемых измерений на одной машине; 95% парный percentile bootstrap по шести повторам характеризует шум конкретной машины. Измеритель суммирует длительности транзакций записи, чтения и финального checkpoint. Отдельное создание пустой схемы, подготовка входа, Python-oracle, модель, генерация эмбеддингов и качество агентного решения не входят в замер. События и изменения адресов архивные, соотношение запросов и выбор номера прошлого состояния заданы экспериментом.

## Проверка воспроизводимости

Отдельная программа восстановила все интервальные веса и все пары победителя из полного префикса для каждого из 1 112 состояний. На трёх схемах SQLite независимо проверены компенсирующие изменения в одной ревизии, повторное включение удалённого ребра, одинаковая квитанция, конфликтующая квитанция, пропуск версии, отрицательный вес, ошибка после записи интервалов, удерживаемый snapshot и коммит между чтением версии и результата. После восстановления реального снимка в уже изменённой базе тест заново применяет суффикс и сравнивает содержимое всех таблиц, затем повторно открывает файл и проверяет каждую версию.

При подготовке обнаружили окно между двумя чтениями клиента, через которое мог пройти конкурентный коммит. В итоговой версии оба чтения объединены в транзакцию, и все 54 замера были выполнены заново. Инженерный прогон до исправления сохранён в [отдельном журнале предварительных измерений](diagnostics/before-read-snapshot.json.gz) и не входит в таблицы.

Команды из каталога исследования:

~~~text
python source.py
python study.py
python verify.py
~~~

Для замера нужен Python с NumPy и SQLite, исследовательские данные R44/R48 и каталог диска D для временных БД. Скрипт использует WAL, synchronous=NORMAL и отключённый автоматический checkpoint. Для проверки готовых результатов достаточно python verify.py; он не измеряет скорость заново.

## Интерактивная проверка q11

Команда python demo/server.py --port 0 поднимает локальную консоль и выводит адрес в stdout. Порт выбирает ОС. Показаны все 32 группы q11 и начальное состояние, выбранная ревизия для исторического запроса регулируется независимо от числа применённых групп. Пересчёт по интервалам и журнал выполняются двумя независимыми соединениями SQLite на одном префиксе фактического потока. Интерфейс показывает вклад конкретного ребра, суммарный счёт источника, последнюю применимую запись журнала и EXPLAIN QUERY PLAN. По умолчанию используется английский язык, переключатель включает русский. Проверка python demo/verify_http.py выполняется средствами стандартной библиотеки и проходит все 33 состояния.
