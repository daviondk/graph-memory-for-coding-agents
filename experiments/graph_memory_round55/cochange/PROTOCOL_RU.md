# Протокол для скользящего графа совместных изменений

Единица сравнения — одна история репозитория. Шесть проектов и конечные SHA заимствованы из подписанного списка R54. Цель — получить для каждого последние 576 коммитов по первым родителям. Первые 64 изменений задают прогрев, остальные до 512 сравниваются хронологически. Для вычисления отличий всегда нужен дополнительный родитель. Если исходная история короче, используем все доступные переходы после первых 64. Включаем коммиты с пустым набором Python-путей. При наличии сети для углубления разрешены отдельные общедоступные деревья Git без содержимого файлов. Возможное перекрытие со 120 версиями из исследования импортов R54 раскрывается в отчёте.

Файл определяется полным относительным путём с суффиксом `.py`. Добавление, редактирование и удаление включаются. Переименование даёт два пути. Допустимы изменения тестов и документации Python. Порядок равных оценок задаётся ID, выданным при первом появлении файла в допустимом коммите, внутри коммита — лексикографически по пути. Для коммита с >64 Python-путями пропускаем все его вклады в граф и предсказания, сохраняя его положение в окне. Так ограничивается стоимость квадратичного расширения и размер референтного графа. Файлы остаются кандидатами после выхода из окна. Задача — рекомендовать пути из прежней истории, включая встречавшиеся ранее удалённые пути.

Каждая неупорядоченная пара совместно изменённых файлов в допустимом коммите создаёт единицу веса. Через W последующих коммитов соответствующий вклад отзывается. На шаге t одновременно добавляем коммит t и вычитаем t−W, сравниваем конечные целочисленные взвешенные степени файлов. W=32 — основное окно, W=16,64 — чувствительность. K=8. Одна холодная загрузка из непустого рейтинга на проект и каждое W после первых 64 коммитов. У всех алгоритмов одни и те же известные ID и баллы. Независимая проверка полной перестройкой оконных степеней на каждом шаге и точного порядка ID и баллов после любой обработки.

Основные сравнения на одной SQLite-таблице баллов и одном индексе. Используем функции поддержания точного префикса Yi et al. и отложенной верхней границы из R54. Учитываем баллы и гарантированную верхнюю границу с парой (балл, ID) по 2 × int32. Допустимо кодировать заполненность префикса классического алгоритма общим флагом и брать его границу из последней строки. Первичны бюджеты 9 пар — классический префикс 9 против 8 позиций и 1 пары границы. Вторичны 13 пар — классический 13 против 12 и границы. Также публикуем сравнения при равном числе позиций 8,9,12,13. Представление с фиксированной разрядностью описывает полезную нагрузку и общий флаг, не память объектов Python. Фиксируем фактические обращения SELECT к упорядоченному индексу и число возвращённых строк, холодные отдельно, выигрыши/проигрыши по проектам. Oracle имеет отдельные данные, метод не видит результата полного поиска. Выводы о времени, вводе-выводе ОС или успехе LLM по этим метрикам не делаем.

До включения следующего допустимого непустого коммита (t) делаем две проверки качества по состоянию t−1. Общая подсказка — top‑8 по степени графа с порядком (степень, −ID) против оконной частоты с тем же порядком и против последнего наблюдения с тем же порядком. Вторая проверка моделирует задачу с одной известной правкой: для |S|≥2 открываем один путь, равновероятно определённый через SHA коммита modulo |S| по отсортированным путям. Это выбор подсказки из эталонного коммита, а не доступ к сюжету или сообщению коммита. Остальные пути остаются скрытыми. Сравниваем с частотой и давностью без якоря (среди прошлых кандидатов, исключая сам якорь). Порядок условного поиска — число общих изменений с известным путём, затем оконная частота целевого пути, затем −ID. Сравниваем Hit@8 и средний Recall@8 по коммитам с соответствующим эталоном, отдельно долю доступных в памяти путей. Учитываем и новые пути. Пустые наборы не определяют полноту, но остаются физическими обновлениями. Итоговые доли даём по запросам и показываем знак на шести проектах. Не тестируем множество зависимых коммитов как независимые наблюдения.

Зафиксированные аналоги: [материализованные top-k, Yi et al.](https://cse.hkust.edu.hk/~yike/topk/icde03.pdf) и [поиск совместных изменений при известном начальном файле, Zimmermann et al.](https://thomas-zimmermann.com/publications/files/zimmermann-icse-2004.pdf). Это повторное использование идей, а не запуск оригинальных систем авторов.
