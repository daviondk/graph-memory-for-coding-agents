# Графовая память между правками. Результаты и границы переноса

Короткое окно по всему проекту теряет сведения о редко меняющихся файлах. На 880 многофайловых правках шести проектов история, ограниченная восемью событиями **известного файла**, дала 48,14% Recall@8. Окно по последним 32 коммитам проекта дало 34,75%, вся накопленная с начала наблюдения история — 48,83%. Это воспроизводимый аргумент в пользу отбора истории по объекту, о котором агент уже получил наблюдение. Последние восемь событий и выборка до восьми событий по хешу показали близкое качество. ## Что можно обоснованно включить в статью

1. **Демонстрируемая операция над памятью.** Посетитель меняет доступность источника или размер кеша и получает точный результат на заданной версии. Для нескольких реальных адресов можно восстановить конкретные коммиты и понять, при каких правилах скорректированная выдача нашла нужный файл. Демо связывает алгоритм обслуживания представлений в БД с действием агента.
2. **Граница выигрыша.** Раздельный учёт числа упорядоченных SQL-запросов, строк, инструкций и служебной памяти показывает, почему прежний выигрыш при фиксированных восьми позициях исчезает для индексного времени при равных байтах. Значения относятся к данной реализации SQLite на одном узле. Метод поддерживает точный ответ, включая порядок при равных оценках. Контроль основан на работе Yi и соавт. [Опубликованный алгоритм](https://cse.hkust.edu.hk/~yike/topk/icde03.pdf).
3. **Следующий проверяемый вопрос.** Доставлять дополнительный файл только тогда, когда у него есть независимый источник поддержки и его чтение не вытеснит более полезный адрес. Нужен заранее отложенный набор эпизодов программирования, где один и тот же решатель получает равное число файлов и токенов, затем выполняется независимый набор тестов. Два попадания при изменении пятого места дают примеры механизма. Такой масштаб эффекта и смена его знака при исходных позициях исключают вывод о превосходстве над современными кодовыми агентами.
