# Как менять порядок чтения графовой памяти при разном бюджете

На ISETrace простое закрепление двух первых узлов оказалось полезно для читателя с бюджетом 512 токенов. Этот порядок почти полностью сохраняет полное покрытие при 2 048 токенах. При 256 токенах те же два узла могут занять слишком много места, и покрытие снижается. Плавная зависимость весов от бюджета проиграла простому выбору между двумя готовыми ранжированиями. Проверка относится к этапу извлечения доказательств из ранее записанных траекторий агента. Качество конечного ответа здесь не измерялось.

## Сравнение

Официальный тест содержит 2 000 вопросов из 1 207 траекторий. Для каждого вопроса обе системы получают одни и те же кандидаты. Dense-FT и обучение структурного prior взяты из предыдущей серии без изменений. Первый балл учитывает плотный ранг и графовые признаки, включая ранг степеней внутри одной роли траектории (global_role). Второй добавляет линейную поправку, которую обучили на 196 train-вопросах сильнее штрафовать дорогие отрицательные узлы впереди самого слабого положительного (cost_worst). Дополнительных обращений к языковой модели в этой серии нет.

Пакетировщик ISETrace последовательно принимает целые узлы, останавливаясь перед первым непомещающимся. Для каждого бюджета Coverage означает долю покрытых эталонных спанов по нативному оценщику. FS — доля вопросов с полным покрытием. MRR использует позицию первого релевантного элемента в полном порядке. У методов с несколькими порядками ниже указано, для какого бюджета выбирался порядок. Первичная MeanCoverage равновесно усредняет Coverage при 256, 512, 1 024, 2 048 и 4 096 токенах. Такое распределение бюджетов задаёт исследовательский протокол. Реальная частота бюджетов другого приложения может изменить предпочтение.

Для выбора правила 352 dev-траектории разделены по хешу на две непересекающиеся половины, с 286 и 294 вопросами. Вторая половина оценивалась при фиксированном выборе. Ранее модели и checkpoint подбирались с использованием dev, поэтому отложенная половина проверяет только выбор нового правила условно на этих моделях. Все интервалы разностей парные, бутстрэп по 1 207 траекториям, 10 000 повторов. При нескольких seed предварительно усредняем их оценки каждого вопроса. Ниже точечные значения в процентах и разности в процентных пунктах. Интервалы отдельных вторичных показателей приведены без поправки на множественные сравнения.

## Первичная проверка на seed 13

Пусть α задает долю коррекции cost_worst. Выбор единого веса на калибровочной части дал α=0,75. Схема независимого выбора между α=0 и α=1 по бюджету дала последовательность 1, 0, 1, 1, 1. Плавное правило выбрало 0, 0, 0,5, 1, 1. Для свободного выбора доступны пять весов отдельно на каждый бюджет. Все решения перенесены с первой половины dev без изменения.

На seed 13 двоичный маршрут нарушал вложенность в 253 из 8 000 переходов между соседними бюджетами. Это означает, что часть уже отданных узлов исчезала при расширении бюджета. Для плавного правила таких переходов 11, для фиксированного переключателя 37, для одного порядка 0. Фактическая задержка и время повторного чтения здесь не измерялись.

## Перенос и контроль механизма

Проверку закрепления начала очереди расширили на seed 13, 17, 29, 37, 41. Пороговый вариант включает в неизменяемую голову первый узел, из-за которого сумма превысила 256 токенов. Это гарантирует совпадение выдачи с global_role для любого меньшего бюджета. Простой контроль сохраняет первые k узлов, затем берёт хвост cost_worst с удалением дубликатов. Из k∈{1,2,3,4,8} на 286 dev-вопросах выбраны два. Обе реализации используют один порядок при всех размерах окна. Для вторичной серии протокол зафиксирован после просмотра первичной.

## Почему при 256 и 512 предпочтения расходятся

На seed 13 при 256 токенах переход от global_role к cost_worst превратил пустой контекст в непустой для 124 вопросов. Для пяти вопросов произошло обратное. Совместный вклад этих случаев в C256 равен +1,085 п.п., из общей разности +1,739 п.п. Для 839 вопросов контекст пуст в обоих порядках и для 1 032 непуст в обоих. При 512 токенах все 2 000 контекстов непусты в обоих вариантах. Читатель cost_worst получает в среднем больше узлов (2,300 против 2,110), а Coverage уменьшается на 0,373 п.п. Эти наблюдения отделяют возможность вообще прочитать узел от того, насколько полезен ранний узел после чтения.

В дополнительной диагностике сохраняли два узла исходного порядка, если такая перестановка не уменьшала число помещающихся при 256 токенах узлов. Иначе использовали целиком cost_worst. Длины и порядки доступны до раскрытия разметки. Правило задано после разбора результатов seed 13. Оно переключило 11,13% пар «вопрос, seed» и вернуло C256 к уровню cost_worst, 25,797% против 25,780%. Разность MeanCoverage составила +0,006 п.п. [−0,102, 0,115], C512 −0,166 п.п. [−0,500, 0,161]. По сравнению с сохранением двух узлов переключение подняло C256 на 1,561 п.п. [1,214, 1,933] ценой 0,919 п.п. C512 [−1,412, −0,452]. Результаты более слабого переключателя только при пустом префиксе и отложенной половины dev опубликованы в guard-results.json. Количество уместившихся узлов объясняет часть потерь при коротком бюджете, но его максимизация не оценивает релевантность.

## Вывод для статьи

Форматы с единым порядком дают возможность расширять ранее прочитанный префикс. Если целевой режим использует 512 и 2 048 токенов, простой двухэлементный префикс восстанавливает качество ранних позиций и практически сохраняет показатель полного покрытия на изученной выборке. Исходный cost_worst остаётся сильным вариантом для 256 токенов. Преимущество нового метода по равновесной интегральной метрике или над опубликованной SOTA не установлено. Поиск более сложной монотонной зависимости α от бюджета слабо мотивирован результатами. Для отдельной проверки остаётся вопрос, позволяет ли измеримая релевантность следующего узла предсказать полезность чтения при одинаковой физической вместимости префикса. Независимый набор траекторий нужен для оценки переносимости этого наблюдения.
