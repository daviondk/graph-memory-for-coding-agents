# Условная сила структурного приоритета на ISETrace

**Вопрос.** Помогает ли изменять вес локального структурного приоритета по наблюдаемым признакам конкретного вопроса и уверенности Dense-FT? Ближайшие локальные работы R20/factor_reader и R21/five_seed суммируют фиксированные коэффициенты ранга и графа. R22/conditional_lookup/adaptive исследует выбор чтения на другом корпусе. Здесь меняется только порядок полного набора provenance units внутри траектории.

**План до расчета результатов.** Seed 13, E5-base-v2 Dense-FT с идентичным выбором эпохи на dev500 и dev580. Используем нативные скалярные dense scores. Для обучения поправок объединяем два небольших опубликованных обучающих поднабора R20 availability и hash64 по уникальным траекториям. Обучающая цель — взвешенная бинарная логистическая потеря перекрытия нативного кандидата с доказательством, равный вес классам внутри вопроса и равный вес вопросам. Эмбеддер видел официальный train при fine-tuning. Сам графовый приоритет оценён по другим обучающим траекториям. Ранговая калибровка R20 ранее видела hash64. Ни один dev-вопрос не входит в обучающие данные.

**Сравнения.** (1) Dense, исходный factor; (2) постоянный множитель графа из 0, 0.25, 0.5, 0.75, 1, 1.25, 1.5, 2, 3; (3) общий немонотонный калибратор, включающий hinge-функции log(rank), величины prior и их взаимодействие; (4) тот же калибратор с взаимодействиями prior и наблюдаемых признаков. Три варианта взаимодействий — неопределённость, текст, оба семейства. Для контроля одинаковый выбор штрафа 0.03 или 0.3 на dev. Базовый логит R20 — offset. Непрерывные признаки центрируются и масштабируются только по train с защитой от экстремальных значений. Скаляры вопроса — число слов, маркер отношения во времени, координации и запроса причин/способа. Неопределённость — разрывы между dense #1 и #2/#5, standard deviation top20, нормализованная энтропия top20 с температурой 0.03. Поля query_type, gold и будущие действия отсутствуют на входе ранжировщика.

**Выбор и оценка.** Сначала оценить все настройки на всех официальных 580 dev-вопросах. В каждом семействе максимизируется Full Support@2048, затем Coverage@2048, затем порядок регистрации. Выбор gated-модели среди шести конфигураций и сильнейшего контрольного метода фиксируется в отдельном файле до расчёта test. Метрики test по 2000 вопросам, 1207 независимым для ресэмплинга траекториям. Нативная политика берёт префикс до первого превышения 2048 токенов. Первичное сравнение — условный минус сильнейший dev-контроль по Full Support. Одновременно публикуются Coverage, Recall@5, MRR, числа разнонаправленных изменений и парные интервалы bootstrap по траекториям (10000). Дополнительные конфигурации оцениваются на dev.

**Ограничение.** Исходный официальный test уже известен проекту по предыдущим экспериментам. Подбор текущего метода изолирован программно, это исследовательская репликация на известном бенчмарке и одном seed. Различия в PU retrieval не измеряют качество конечного ответа агента. GPU не требуется.
