# Как отличить источник прочитанного значения от простого совпадения

Проверили два предположения о графовой памяти действий. Во-первых, сохранит ли граф правильные исторические связи, если отзывать атрибуцию после появления второго производителя того же значения. Во-вторых, достаточно ли сохранять уникальность значения в два момента, чтобы находить его источник при повторном чтении. Первую проверку проводили на зарегистрированных зависимостях программ. Во второй сравнили два момента с правилами, использующими имя переменной и последнюю запись.

## Что служит эталоном

Из пяти открытых коллекций выбрали все 84 файла по заранее заданным шаблонам путей. В 75 записях есть обязательные таблицы, у шести отсутствуют нужные секции, два файла содержат некорректный JSON, один пуст. Из записей извлекли 3 673 действия. В 51 трассе 28 семейств скриптов нашлись подходящие чтения. Для каждого чтения числа, строки или логического значения по идентификатору версии соединили записанные инструментатором рёбра `used` и `wasGeneratedBy`. Получили 1 804 чтения и 1 803 различные пары «производитель — читатель». Предсказатели не получают идентификатор версии или эталонного производителя. Исходники программ в исследовании не исполнялись. [Формат записей](https://github.com/End-to-end-provenance/ExtendedProvJson/blob/master/JSON-format.md), [публичные трассы RDataTracker](https://github.com/End-to-end-provenance/RDataTracker/tree/d4c096cbce24d7e4822e90305ee0917b52b3d172/scriptTests).

Данные неоднородны. 961 чтение происходит из тестовых примеров двух инструментаторов, 834 принадлежат семейству pplant, включая 832 чтения одной трассы, ещё девять — примерам других пакетов. Авторы описывают pplant как прикладной скрипт моделирования кислорода в экосистеме растения. Инструментатор определяет переменные из текста выражения и записывает значения при исполнении. Эталон независим от нашего правила совпадения значений, но метод получения разметки близок к правилу поиска по именам. Уровень измерения — семантика инструментатора языка. Данные представляют программные операции и не дают оценки успешности задач LLM-агента. [Описание набора](https://github.com/End-to-end-provenance/eep-usecases/tree/a6ef670ce838694c51a308edec7cff1ac04016e9), [Making Provenance Work for You, раздел 5](https://journal.r-project.org/articles/RJ-2023-003/).

## Поиск источника при известном прочитанном значении

Алгоритму заранее сообщили факт чтения и точное значение. На момент чтения одно подходящее действие наблюдалось в 659 случаях. Впоследствии для 155 из них появился второй производитель. Отзыв старой связи оставляет 504 из 1 804 верных источников вместо 659. Потеря полноты составляет 8,59 п.п., 95% кластерный ДИ [4,78; 17,60]. Без pplant теряется 137 верных источников, результат падает с 387 до 250 из 970. Позднейшее совпадение объясняет риск дальнейшей атрибуции, хотя связь со старым чтением по-прежнему подтверждается конкретной версией.

В 1 145 случаях уже в момент чтения имелось несколько кандидатов. Самый поздний производитель того же значения правилен в 534/1 145 таких случаях и в 1 193/1 804 по всем чтениям. Случайный кандидат среди совпадающих правилен в 901/1 804, перестановка идентичностей хронологически допустимых производителей оставляет 124/1 804. Возврат всех кандидатов находит все 1 804 источника ценой 7 188 лишних рёбер. При предоставленном прочитанном значении полнота всех кандидатов и точность однозначных связей следуют из отбора. При предоставленном имени и области видимости последняя запись даёт 1 745 верных источников, 59 воздержаний, ноль ложных. Это привилегированный ориентир.

Учитываются все ложные предсказания, включая действия без эталонного чтения. F1 рассчитана по парам действий. Последний столбец усредняет F1 по семействам. ## Два момента времени на наблюдаемых последующих чтениях

Для каждой пары последовательных чтений одного скалярного значения в одной трассе выбирали кандидата заранее — последнего производителя до первого чтения. По двум независимым от данного предсказания идентификаторам версий проверяли, создал ли он значение первого и второго чтений. Ответы могли измениться, поскольку произошло **новое чтение**. Получили 1 348 пар из 20 семейств. Первое и второе утверждения о кандидате расходятся в 298 парах. Любой метод, копирующий одно неизменное логическое значение в оба ответа, может дать полностью правильный ответ максимум в 1 050 из 1 348 случаев, даже если заранее подбирает лучший бит по меткам.

| Два верных ответа одновременно | Все 1 348 | Без pplant, 681 |
|---|---:|---:|
| Уникальность в первом срезе, скопированная в оба ответа | 832 | 234 |
| Уникальность во втором срезе, скопированная в оба ответа | 832 | 234 |
| Уникальность отдельно в каждом срезе | 909 | 302 |
| Последний производитель данного значения, заново в каждом срезе | 812 | 541 |
| Вхождение кандидата в последние записи имён второго выражения, скопированное в оба ответа | 962 | 371 |
| Вхождение кандидата в последние записи имён каждого выражения | 1 013 | 393 |

Два флага уникальности выигрывают у копии одного однотипного флага на 5,71 п.п. [2,95; 13,27], причём ровно 77 пар дают весь прирост. Поиск по имени в каждом срезе превосходит два флага на 7,72 п.п. [2,86; 18,04] и на 13,36 п.п. [5,18; 19,22] без pplant. Копия позднего именного флага — ретроспективный контроль, которому доступен второй текст при ответе на первый вопрос. Раздельный ответ именного правила выигрывает у него на 3,78 п.п. [−0,38; 7,02]. Выбор между моментом чтения и текущим состоянием важен для смысла вопроса. Наблюдаемый прирост не обосновывает превосходство двух флагов уникальности над доступными алгоритмами атрибуции.

## Что переносить в граф агента

Если инструмент предоставляет идентификатор результата вызова или версию артефакта, такую связь можно сохранять как подтверждённый источник. Если доступен только текст и совпало значение, стоит хранить происхождение гипотезы и признаки неоднозначности при чтении. Полезность такого различения для агентных задач остаётся проверить на трассах с инструментально подтверждёнными зависимостями и скрытыми от агента метками. При равном бюджете сравнивать следует с последним производителем по явной ссылке, с последним по имени из текста и с последним по значению. Разбор по именам и статические ссылки уже дают сильные результаты в этой задаче. Его превосходство на LLM-бенчмарке, экономия памяти в байтах и ускорение здесь не измерялись.

Первичная схема зафиксирована в `protocol.json`. Типы действий, пары последовательных чтений и дополнительные именные контроли изучались после получения сводных результатов первичной проверки. ДИ основаны на 5 000 парных bootstrap-перевыборках семейств, seed 2209. Эффективная единица повторения — семейство скриптов, число чтений отражает размер журнала. Подробные диагнозы и ограничения воспроизведения собраны в `REPRODUCE_RU.md`.
