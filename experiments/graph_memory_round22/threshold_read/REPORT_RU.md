# Точный префикс с ранней остановкой

Однокурсорная реализация восстановила выбранные графовым читателем ссылки в том же порядке на всех 2 000 вопросах ISETrace. Для строгого префикса она вычислила **67 091 из 249 089 баллов** (26,93%). На этих небольших историях полная векторизованная сортировка NumPy оказалась быстрее. Медианное процессорное время после получения исходных плотных рангов составило **7,0 мкс** для NumPy и **22,5 мкс** для однокурсорной реализации. Этот результат задаёт конкретное условие для дальнейшей работы с БД. Экономия вычисления и передачи метаданных имеет значение при достаточно дорогом доступе к ним.

## Почему можно остановиться

Пусть q — текущий вопрос, r — семантический ранг, p — статический структурный скор. Для каждого ещё не оценённого узла его сумма не превышает U = max g(r) по непрочитанному суффиксу рангов плюс max p по непосещённым узлам. Максимум суффикса сохраняет корректность при произвольном немонотонном g. Если лучший элемент уже вычисленной очереди имеет сумму строго выше U, он идёт раньше всех ещё не оценённых узлов. Среди уже известных узлов равенства разрешаются исходным Dense-рангом. При равенстве с U чтение продолжается. Последовательное извлечение таких сертифицированных узлов воспроизводит полный отсортированный порядок до границы бюджета. При доборе разрешено завершить поиск, если минимальная стоимость оставшихся узлов превышает остаток. Пример с длинным первым фрагментом даёт пустой префикс, но добор может вернуть последующие короткие фрагменты.

На реальном тесте все 1 207 массивов g оказались монотонны. Однокурсорное чтение делает только последовательные обращения к имеющемуся Dense-рейтингу и совершило суммарно 67 091 индексное обращение к значению prior при строгом префиксе. Двухкурсорный метод прочитал 24 009 позиций последовательного Dense-потока, запросил обратный ранг 24 008 раз и построил отображение всех 249 089 позиций «узел → ранг» для этих вопросов. Последняя работа включена в его таймер. Когда исходная служба поиска предоставляет только последовательный поток, двухкурсорная оценка времени предполагает дополнительный полный проход на формирование обратного индекса.

## Стоимость вспомогательных массивов

Для графов 1 207 траекторий две отсортированные таблицы (приоритет и цена с их идентификаторами) заняли 4 806 912 байт в int64/float64. Материализованные верхние границы g заняли 1 201 728 байт в варианте с отдельным массивом для каждой траектории. Значения g зависят от длины и фиксированной калибровки, поэтому одинаковые длины допускают переиспользование. Медиана подготовки сортированных таблиц составила 11,2 мкс на траекторию, суффиксных максимумов — 2,4 мкс. Изменение prior в активно обновляемой истории требует обслуживания этого индекса. Реальные накладные расходы такой записи зависят от частоты обновлений.

Фикстуры открывают только численные признаки, порядки узлов и ожидаемые списки индексов. Протокол позволяет повторить саму проверку без модели и исходных текстов. Идея сортированного и случайного доступа следует классическому Threshold Algorithm. Здесь проверена его специализация для фактического токенного бюджета и двух правил остановки. ## Практический результат и границы применимости

При переносе всех методов на C++17 и один нативный API SQLite строгий пороговый префикс выполнил 282 364 инструкции виртуальной машины SQLite против 1 010 356 у полного чтения и std::sort. Снижение нативной медианы составило 17,1%, отношение 0,83 [0,80 … 0,85]. Против полного чтения с heapify отношение составило 0,85 [0,82 … 0,86]. Во внешнем таймере с расходами FFI медианы — 18,8 и 22,3 мкс для порога и std::sort. Для добора нативная разница мала, 20,15 против 20,55 мкс, отношение 0,98 [0,96 … 1,00]. Все 20 000 нативных выходов на исходных вопросах и 1 280 синтетических случаев совпали.

Эти измерения относятся к уже полученному полному семантическому рангу и прогретой локальной SQLite с грубой гранулярностью системного таймера. В таймингах page cache зарегистрировала ноль пропусков. Полная задержка ответа агента, холодный диск, сетевой доступ, создание исходных embeddings и обслуживание индекса при изменении истории требуют отдельных замеров. Полностью материализованный порядок всех известных вопросов дал наименьшую медиану префикса 15,8 мкс. Его таблица добавила 4 042 752 байта и 0,287 с построения на зафиксированной выборке.
