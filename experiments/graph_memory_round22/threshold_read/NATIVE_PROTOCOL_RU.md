# Тот же план запроса через нативный API SQLite

Первые реализации на Python показали снижение числа возвращённых строк и близкое время тёплого чтения префикса. Проверяем объяснение, что выигрыш скрывается в обработке каждой строки интерпретатором. Перед новым измерением фиксируем одну реализацию C++17 для пяти вариантов и неизменяемую БД из SQL-протокола.

Сравниваем полное чтение sqlite3_step с std::sort, полное чтение со std::make_heap, ленивый порог с последовательным sqlite3_step, SQL JOIN с ORDER BY и чтение уже материализованного результата. Истории уже имеют статические массивы приоритетов, стоимостей и верхних границ. Исходные плотные ранги во всех режимах находятся на диске D в SQLite. Все варианты используют одну версию sqlite3.dll, подготовленные SQL-выражения, общий процесс и прогретый page cache 64 MiB. Для кучи и полной сортировки реализуем ранний выход при dobore по минимальной возможной цене. Подготовка и хранение индекса начисляются в основном отчёте. Основной контраст — пороговый префикс против std::sort, вторично против полного чтения + heapify. Межъязыковую стоимость отделяем от времени всей нативной операции.

На всех 2 000 вопросах проверяем 5 методов × 2 политики, точное совпадение порядка с замороженным результатом. Измеряем фактические строки sqlite3_step, инструкции виртуальной машины SQLite и внутреннее время метода. Время также измеряем снаружи вызова DLL на том же фиксированном пуле из 256 вопросов (7 повторений, перемешанный порядок условий). Для выводов о времени используем парный bootstrap по 240 траекториям. Нативные измерения — отдельная реализация, выбранная после Python-эксперимента. Дополнительно проверяем непрерывность результата на специально созданных случаях с равенствами и немонотонным рангом.
