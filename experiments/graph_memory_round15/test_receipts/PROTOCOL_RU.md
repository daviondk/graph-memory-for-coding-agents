# Когда можно сохранить ребро «этот запуск pytest прошёл»

Мотивация — два R12-эпизода с командой pytest | tail и кодом 0 при фактических падениях. Эта пара и оба соответствующие проекта (flake8-comprehensions и mpmath) полностью исключаются из внешней панели. До чтения результатов и сборки нашего парсера фиксируем две отдельные проверки.

**Наблюдаемые траектории.** Публичные записи VibeMemBench из замороженного revision 11164976b4f920cdb0d0cd570ca572e49acea1e8. Панель A — использованный в иных задачах R12/R13 научный список из extract.REPOSITORIES за вычетом mpmath. Панель B заранее независима по репозиторию: Delgan/loguru, HypothesisWorks/hypothesis, ipython/traitlets, pallets/click, pypa/setuptools, python-attrs/attrs, scikit-build/scikit-build-core, theacodes/nox. Все доступные задачи выбранных репозиториев, без отбора по статистике pytest. Исключаем задания по уязвимостям/безопасности по тексту описания до чтения команд, команды не исполняем. В первичную выборку входят только однострочные вызовы Bash с единственным распознаваемым запускаемым pytest либо python -m pytest, которые имеют совпадающий tool_call_id и согласованные числовые returncode в structured extra и показанной оболочке. Учитываются прямые команды, конвейеры и составные команды; границы и исключения декларируются. Номер задачи и пары исходного вызова сохраняются. Парсер получает только показанный агенту stdout; полный сырой stdout используется отдельно в проверке.

**Единица утверждения** — успешное выполнение запрошенного набора тестов. Пройденный node или файл не доказывает успешное выполнение всего репозитория. Финальная положительная квитанция требует завершения, хотя бы одного успешно выполненного теста и отсутствия failed/error/strict xpass в видимом итоговом отчёте. Состояния «все пропущены», ноль тестов, обрыв и отсутствие читаемого итогового отчёта учитываются отдельно. Единица естественного наблюдения — команда; для устойчивости есть проценты по панелям и кластерный bootstrap по задачам. Частота ошибок относительно реально завершившихся наблюдений с однозначным полным итогом pytest может быть оценена непосредственно, но не устанавливает исход всех команд без итога.

До сравнения фиксируем правила записи: (1) любое shell rc=0; (2) обычный парсер финального отчёта, который отличает failed/error от passed, без предположения о состоянии оболочки; (3) парсер плюс shell rc=0 для успешного ответа; (4) консервативный сертификат — положительный финальный отчёт плюс нулевой код непосредственно pytest или явно выставленный для пайплайна pipefail, без последующих команд; (5) отдельная контролируемая регистрация PIPESTATUS и независимого JUnit XML. В сравнении подтверждения регистрируем правильно/неправильно выданные pass, ошибочно выданные fail, воздержания, покрытие. Для натуральных данных «ложный pass» в основном результате означает наблюдаемое противоречие с явным финальным итогом, а не догадку о скрытом коде pytest. Обязательно сообщаем число returncode=0 с неизвестным/прерванным итогом. Сравнение парсера на естественных данных с его же собственной меткой не является независимой проверкой; для него отдельно делаем слепой аудит и исполняемый контроль.

**Слепая проверка.** До классификации выбираем хешированно 24 любых команд и ещё 24 непересекающихся команды с конвейером (или все доступные в страте). Проверяющий читает видимую текстовую квитанцию без shell rc и прогнозов и записывает pass/fail/no-evidence/skip-or-empty. Указывается, кто проверял, и ограничения такой проверки. Результаты целевой страты не экстраполируем на полную панель.

**Контролируемый CPU опыт в отдельном временном каталоге.** Фиксированные безвредные мини-наборы с успешным, падающим, смешанным, не собирающимся, пустым, пропущенным, явно выбранным успешным поднабором и принудительно прерванным запуском. Действительно исполняем pytest в Bash в WSL вне Docker. Сравниваем direct, обычный tail, tail с pipefail, читатель только первых строк с и без pipefail. Bash сохраняет отдельно настоящий код pytest (PIPESTATUS), а pytest пишет отдельный JUnit XML в свежий путь. Проверяем количество ожидаемых тестов и исходы по testcase, scope и наличие запуска. За границами обычного сравнения — плацебо: произвольный вывод, похожий на успешный pytest, или строка «успех» после неуспешного запуска. Конкретный инструмент/обёртку и размер подтверждающей записи считаем отдельно. Реальный dataset ни при каких условиях не исполняется. Метки этого компонента и результат решения задач агентом — различные критерии.
