# Можно ли записывать результат теста в графовую память агента по коду оболочки?

В публичной истории VibeMemBench **843 из 3 132 нулевых статусов оболочки противоречат показанному агенту финальному отчёту pytest**. Доля составляет 26,9% (95% процентильный кластерный интервал 24,6–29,2%). Во всех 843 случаях команда содержала конвейер. 745 отчётов явно упоминают упавший тест, остальные 98 содержат ошибки тестовой сессии. Эти наблюдения охватывают 349 задач и 22 репозитория. Частота описывает выбранные команды и интерфейс оболочки. По ней нельзя узнать, счёл ли сам языковой агент тест пройденным.

## Данные и измерение

Источником служат опубликованные истории mini-SWE-agent из VibeMemBench, ревизия `11164976b4f920cdb0d0cd570ca572e49acea1e8`. R12/13 заранее использовали часть этих репозиториев для других вопросов. Два проекта, породивших исходную гипотезу, полностью исключены. Во второй панели заранее выбраны восемь других проектов. Это независимые по репозиториям панели внутри одного и того же источника и семейства инструментов. [Снимок VibeMemBench](https://huggingface.co/datasets/Tongyi-ConvAI/VibeMemBench/tree/11164976b4f920cdb0d0cd570ca572e49acea1e8/history/python)

Протокол и состав панелей зафиксированы до чтения результатов. В 828 найденных трассах заранее применён фильтр тематики, одна трасса исключена. Из 3 375 синтаксически подходящих однострочных запусков 120 исключены из-за отсутствия согласованной пары наблюдений. Для остальных 3 255 сопоставлены команда, ответ по идентификатору вызова, два представления shell-кода и показанный агенту вывод. Они представляют 710 задач и 24 репозитория. Сценарии сложнее разрешённой грамматики отсутствуют в знаменателе. Показанный и исходный stdout дали одинаковые классы во всех 3 255 случаях. Натуральные команды читались как данные.

| Выборка | Команд | shell rc=0 | Из них явный fail/error | Доля среди нулевых | 95% ДИ по задачам |
|---|---:|---:|---:|---:|---:|
| Научные проекты, 16 репозиториев | 2 405 | 2 325 | 657 | 28,3% | 25,5–31,0% |
| Остальные проекты, 8 репозиториев | 850 | 807 | 186 | 23,0% | 19,4–26,8% |
| Все конвейеры | 2 880 | 2 878 | 843 | 29,3% | 26,8–31,7% |
| Прямые вызовы | 374 | 253 | 0 | 0% | — |
| Все формы, включая одну дополнительную составную команду | 3 255 | 3 132 | 843 | 26,9% | 24,6–29,2% |

Механизм воспроизводится, например, в pandas-dev/pandas, задача 55518, вызов `75fedcc4974562b74dda9935`: команда направляет вывод pytest в `tail -30`, оболочка сообщает 0, pytest суммирует один провал и двенадцать успешных тестов. В pallets/click, задача 1830, результат — один провал и семнадцать успешных тестов при тех же 0. В 744 из 843 противоречий присутствовал буквальный вызов `| tail`. Без параметра `pipefail` Bash возвращает статус последней команды конвейера. Статусы отдельных процессов доступны через `PIPESTATUS`. [Руководство Bash](https://www.gnu.org/software/bash/manual/html_node/Pipelines), [переменные Bash](https://www.gnu.org/software/bash/manual/bash.html)

В 427 нулевых ответах не найдено достаточного финального свидетельства. Ещё 181 сообщает пропуск, отсутствие либо снятие тестов с запуска. Такие ответы учтены отдельно. При ограничении нулевыми ответами с явным успехом или ошибкой доля противоречий 843/2 524 = 33,4% (30,6–36,1%). Интервал рассчитан ресемплированием задач с возвращением и всеми их командами, 5 000 повторений, seed 1536. Он условен по выбранным репозиториям. Для прямых вызовов нулевое число наблюдаемых противоречий не даёт содержательного эмпирического bootstrap-интервала.

## Что можно извлечь из существующей траектории

| Политика | Выдано pass | Выдано fail | Воздержаний | Покрытие pass/fail |
|---|---:|---:|---:|---:|
| Только код оболочки | 3 132 | 123 | 0 | 100% |
| Финальная строка pytest | 1 681 | 954 | 620 | 81,0% |
| Финальная строка и нулевой код для pass | 1 681 | 954 | 620 | 81,0% |
| Финальная строка и подтверждённая семантика кода для pass | 251 | 954 | 2 050 | 37,0% |

Распознаватель читает последнюю непустую строку, проверяет грамматику и наличие положительного числа успешных тестов, отличает ошибку коллекции, учитывает явный обрыв. Проверка статуса в строгой политике асимметрична: отрицательный итог подтверждает сам pytest; для положительного требуется прямой статус либо явно настроенный `pipefail`. Среди исторических команд распознаваемой явной настройки `pipefail` не оказалось. Снижение покрытия показывает стоимость консервативного правила при неполной телеметрии. На этих данных сравнивать распознаватель с его собственным выводом как с независимой истиной было бы круговым доводом.

Для ручной проверки до расчёта метрик выбраны 24 случайно-хешированные команды и непересекающаяся дополнительная страта из 24 команд с конвейером. Исследователь видел только фрагмент вывода, без кода и машинного решения. В первой страте зафиксированы 12 pass, 7 fail и 5 без подтверждения. В дополнительной — 14 pass, 7 fail, 2 пропуска/пустых и 1 без подтверждения. Парсер воспроизвёл классы на 48/48 карточках. Только shell-код выдал 6 и 7 противоречащих fail положительных записей соответственно. Это аудит на выходах, которые видел разработчик парсера, с одним проверяющим. Он не заменяет внешнюю разметку и не служит оценкой точности для всех форматов вывода.

## Контролируемый запуск

Сформированы восемь локальных наборов: успех, провал, смесь двух тестов, ошибка коллекции, пустой набор, только пропущенный тест, успешный именованный узел внутри смешанного файла и реальный принудительный обрыв уже начатого теста. Каждый выполнен в пяти режимах: прямой вызов, последние строки с/без `pipefail`, только первая строка с/без `pipefail`. Все 40 ячеек исполнены в свежих рабочих каталогах. Использованы Bash 5.2.37, Python 3.12.16, pytest 8.4.2 и WSL на CPU. Для каждой сохранены исходник, аргументы, видимый вывод, статусы процессов и оригинальный XML. Наличие и имена ожидаемых тестов сопоставлены с `testcase` в XML. [Реализация JUnit в pytest 8.4](https://docs.pytest.org/en/8.4.x/_modules/_pytest/junitxml.html), [коды pytest](https://docs.pytest.org/en/stable/reference/exit-codes.html)

Эталон включает 10 положительных сессий, 15 с тестовой ошибкой/провалом, 10 пустых или полностью пропущенных и 5 принудительно прерванных. Таблица показывает семантику «можно записать хотя бы один успешный тест в заданной области». Графы «ложный pass» и «pass без свидетельства» отвечают на разные вопросы.

| Политика | Истинный pass | Истинный fail | Ложный pass при fail | Pass на пустом/пропущенном | Pass после обрыва | Всего воздержаний |
|---|---:|---:|---:|---:|---:|---:|
| Код оболочки | 10 | 9 | 6 | 7 | 2 | 0 |
| Статус первого процесса (0/1, прочие коды — воздержание) | 10 | 10 | 0 | 5 | 0 | 15 |
| Обычный парсер / парсер плюс код | 6 | 9 | 0 | 0 | 0 | 25 |
| Строгий текстовый сертификат | 4 | 9 | 0 | 0 | 0 | 27 |
| Отдельный JUnit и ожидаемый состав | 10 | 15 | 0 | 0 | 0 | 15 |

При прямом вызове состояние `skip` действительно возвращает код 0. Все пять ошибок коллекции дают код 2. Успешный запуск одного узла из смешанного файла не подтверждает его соседний узел, который падает при запуске всего файла. В обеих плацебо обычный парсер и оболочка принимали напечатанный успех: один процесс имитировал строку без запуска pytest, во втором строка появилась после реально упавшего теста. Структурированная запись не нашла свидетельств в первом случае и правильно сохранила ошибку во втором. Оба плацебо вынесены за пределы основных 40 ячеек.

**Цена свидетельства.** В естественном архиве медиана составила 1 байт для кода, 80 байт для положительной строки и 1 841 байт для показанного вывода. В контролях — 395 байт для полного XML, включая отсутствующие отчёты как ноль. Иллюстративная компактная запись с хешами исходника и XML, областью запуска, версией pytest и составом занимает 275 или 286 байт в двух положительных прямых случаях, плюс отдельно хранимый XML. Эти размеры измерены в данной реализации. В реальном репозитории ключ версии должен покрывать зависимости/рабочее дерево и окружение. Во внешних историях полная привязка к версии и составу тестов отсутствует.

В первом запуске контролей BusyBox не принял синтаксис флага timeout, поэтому пять ячеек не доходили до pytest. Первоначальные артефакты сохранены в `initial-infrastructure/`. Во второй полной серии применён совместимый синтаксис и добавлена проверка файла-маркера из тела начавшегося теста. Записанный код завершения процесса 143, JUnit отсутствует. Таблица относится ко второй серии.

## Для исследования графовой памяти

Наблюдаемая ошибка возникает уже на этапе записи ребра о прохождении теста. В архиве короткая финальная строка выявляет многочисленные противоречия с shell-кодом. При повреждённом выводе нужна независимая квитанция запуска, а при смене версии или набора тестов нужно заново проверять область применимости. Осталось измерить, как меняется действие настоящего решателя при равном бюджете чтения и как часто политики ошибочно разрешают пропустить повторную проверку.

## Воспроизведение

1. Готовые `calls.gz` и `controlled.gz` содержат первичные записи. Запустите `python -B score.py` (NumPy 2.4.4 в исходной обработке) и `python -B diagnostics.py`. Первый скрипт проверяет хеши пререгистрации и входов. `results.json` хранит матрицы ошибок и интервалы. `predictions.gz` — все решения, `visible-conflicts.gz` — все 843 противоречия.
2. Для повторного извлечения из открытого снимка используйте `collect.py` и модуль `graph_memory_round12/negative_external/extract.py`. Внутри официального HF snapshot путь начинается с `history/python/`, локальная копия хранится под `benchmark/history/python/`. Хеш каждого исходного файла записан в `cohort.json`. Проверяемый CLI и два канала ответа версионированы в скрипте.
3. Для переисполнения контролей в Linux/WSL нужны Bash, sed, tail, timeout и Python с pytest 8.4.2. Вызов `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 PYTHONDONTWRITEBYTECODE=1 python3 -B controlled.py` следует делать из копии директории, затем повторить шаг 1. Имена временных каталогов, timestamps XML и время тестов меняются. Контроллер проверяет ожидаемые исходы каждого запуска и наличие маркера прерываемого теста. [Авторская реализация JUnit](https://docs.pytest.org/en/8.4.x/_modules/_pytest/junitxml.html)
