# Сохранять ли адрес до первого чтения файла?

План зафиксирован до оценки новых ранжирований. Известно, что в предшествующем эксперименте по предъявлению шести файлов решателю 6 из 19 целей патча отсутствовали в меню. Включаем все подходящие префиксы, независимо от прежнего результата. Первичные панели — 267 и 73 события R13. Третья панель включает все 111 подходящих промахов в пяти проектах R14, оригинальные 30 событий grounded анализируются отдельно как вложенный срез. Четвёртая панель — все строгие пустые запросы в доступных ранее не входивших в эти три панели репозиториях elastic/curator и apiflask/apiflask, с фильтром security-задач по прежним правилам. Имена отобраны по доступности до извлечения меток. На четвертой панели в любом случае оцениваем следующие чтения. Для PR используем ранее зафиксированные исторические метки, где они доступны, и отдельно сообщаем точное определение и покрытие при наличии нового источника.

**Запись.** Храним строго явные .py-адреса из исходного текста задачи, успешных find/ls/git ls-files/rg --files/grep -l, явных Python traceback (включая ненулевой код), явных адресов в кавычках в уже показанных Python-фрагментах и строк с File/filename/location. По импорту модулей без видимого пути файловый адрес не достраиваем. Для ls с одним буквальным аргументом-каталогом разрешаем присоединение показанного basename к этому каталогу. Отсекаем служебные деревья и адреса вне зафиксированного корня. До следующего промаха держим последние 64 ещё не прочитанных пути на корень, до пяти первых источников разных типов и счётчик уникальных показов. Уже прочитанные пути исключает точное множество, его сериализованный объём оплачиваем отдельно. Один вывод и одна строка являются максимум одним наблюдением одного пути. При выдаче используем состояние перед текущим пустым поиском и известную область запроса. Сохраняем происхождение, индекс события, видимую строку с адресом, признак наблюдавшегося содержимого и размер.

**Чтение.** Исходный view_graph — неизменённый порядок графа R13 по прежнему меню. flat_recent использует последнее упоминание по всему пулу. bm25_all ищет по пути и имеющемуся содержимому, запрос и параметры совпадают с BM25 R13. flat_union = 0,55 × нормированный BM25 + 0,25 × обратная давность по всем путям + 0,20 × обратная позиция в view_graph для уже доступного файла. Обе обратные величины равны 1/(1+0,35 × индекс), ноль для отсутствующей старой позиции. typed_union добавляет 0,25 новому адресу, если он показан минимум двумя разными типами источника в разных событиях. Это наблюдаемая разнородность свидетельств, статистическая независимость из неё не следует. Контроль shuffled_union переставляет положительные надбавки среди новых адресов хешированием в рамках того же меню, random_all выбирает случайный детерминированный порядок. Дополнительно простой alternating_union чередует порядки view_graph и BM25 среди новых адресов, начиная с первого наблюдавшегося файла. Параметры постоянны для панелей и исходов.

**Основной вопрос.** Относительный прирост Hit@6 по целям production PR у typed_union против view_graph и flat_union в повторной панели R13. Отдельно измеряем Hit@1/3/6 и MRR, доступность цели в полном пуле, случаи приобретённых и потерянных попаданий, новые слоты, число различных поддерживающих источников, объём состояния и кластерный интервал 95% (5000 повторов, задача — единица). Изменение доступности не считается попаданием при ограничении k. Дополнительный поведенческий исход — первое успешное подходящее чтение в следующие пять инструментальных шагов по ранее зафиксированному правилу. Пустые и недостижимые меню с известным исходом получают ноль. Правильность исправления не измеряется.

До извлечения будущих наблюдений все входы и списки фиксируются SHA256. Для каждого префикса повторяем извлечение, физически обрезав доступное сообщение сразу после текущего инструмента, сверяем хешы полученных состояний. Команды и тексты из историй рассматриваются как данные, воспроизведение команд не требуется. Исторические репозитории на этапе прогнозирования не открываются.
