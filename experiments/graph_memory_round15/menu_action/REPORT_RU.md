# Какие записи памяти меняют следующее чтение файла

После безрезультатного поиска кода модель получает шесть путей и выбирает один файл для чтения. Мы проверили две разные гипотезы. Даёт ли прибавку к качеству ранжирования свидетельство о том, что один путь независимо от формулировки поиска показали разные типы инструментов? И помогает ли вообще менять меню, сохраняя в том числе адреса, которые агент видел в выдаче, но ещё не открывал?

**В первом сравнении модель получила одинаковые входы во всех 32 задачах.** Во втором меню отличались во всех 32, запрошенный файл изменился в девяти случаях. Когда учитывали ещё не прочитанные пути и пересчитывали ранг, Qwen открыл файл будущего изменения в 18 из 27 задач. В меню, ограниченном старыми адресами и исходным ранжированием, — в 15 из 27. Три выигрыша, ноль потерь и 24 совпадения дают двустороннее точное p = 0,25. Во всех трёх выигрышах модель открыла ранее известный ей адрес. Результат выделяет **состав меню и повторное ранжирование уже известных файлов** как механизм, заслуживающий отдельного испытания. Правильность итогового исправления здесь не измерялась.

## Дизайн и область вывода

Из опубликованных траекторий VibeMemBench отобраны события, в которых наблюдался пустой поиск, имелось шесть разных путей у каждого конкурента и хотя бы два меню отличались составом. На задачу брали первое подходящее событие, до 12 задач на панель по хешу идентификатора. Весь отбор использовал только предшествующую историю. `view_graph` предлагает файлы из прежней памяти адресованных файлов. `flat_union` расширяет пул за счёт ранее показанных имён и ранжирует по BM25, давности и позиции в старом графе. `typed_union` дополнительно повышает ранг нового имени при его наблюдении в разных событиях и типах источников. Отдельные обозначения типов и оценки кандидатов в контексте Qwen отсутствуют. Во всех ветках видны один и тот же issue, литерал и область пустого поиска, а шесть путей отсортированы независимым от политики хешем. Изменение состава может сдвигать абсолютные позиции общих элементов и длину контекста. Между двумя расширенными методами пул и базовое ранжирование совпадают. Между расширенным методом и старым графом меняются как пул, так и ранжирование.

Нативный Qwen3.8-27B UD-Q4_K_M выбрал один `read_file` при temperature 0, top-k 1, seed 13. Значение пути ограничено шестью вариантами JSON-схемой инструмента и дублируется в тексте контекста. Зафиксированы запросы, полные ответы и выборы. Затем каждая из 96 логических веток физически запросила содержимое по публичному базовому коммиту. К будущим просмотрам и PR обратились только после фиксации результатов чтения. Этот дизайн оценивает одно действие при отсутствии дополнительного диалога. Файл открывался исполнителем после решения, его содержимое модели для второго действия не передавалось.

## Результаты

В числителях — задачи. По каждому исходу все сравниваемые варианты имеют один знаменатель. «PR» учитывает только файлы production Python, существовавшие на базе, когда база совпадает с первым родителем merge, а время коммитов согласовано. Фильтр оставил 27 задач из 32, четыре имели другого родителя, ещё одна не содержала изменения существующего production-файла. Поведение исходного агента удалось оценить для 23 задач. Целью служил первый успешный однофайловый просмотр или содержательный поиск в файле того же рабочего корня среди пяти следующих действий.

| Реально открыт файл будущего PR | 15/27 | 18/27 | 18/27 | 3 / 0 |
| Такой файл присутствовал хотя бы в одном слоте меню | 22/27 | 23/27 | 23/27 | 1 / 0 |

По панелям число фактических попаданий в PR у `view_graph → flat_union` составило 6 → 7 из 11 в primary, 4 → 4 из 4 в replication, 3 → 5 из 10 в grounded_all и 2 → 2 из 2 во внешней панели. Во внешней панели по двум задачам elastic/curator модель во всех вариантах открыла файл будущего PR и в обоих случаях выбрала иной файл, чем исторический агент. Научное обобщение внешней панели ограничено одним репозиторием.

Парная разность по PR +11,1 п.п. Описательный процентильный 95% интервал перевыборки 27 задач с возвращением составляет [0,0; +25,9] п.п. Он условен на состав отобранной панели и игнорирует зависимость задач одного проекта. В 27 задачах с меткой представлено 12 проектов, девять задач относятся к cfn-lint. Для следующего исторического чтения разность −4,3 п.п., двустороннее точное p = 1,00. Разные направления двух результатов показывают, что сходство с траекторией исходного агента и локализация будущего изменения оценивают разные свойства.

| Задача | Файл, выбранный расширенным меню | Был в исходном top-6 | Доступность любого правильного файла в исходном меню |

| cfn-lint #3700 | `src/cfnlint/rules/resources/dynamodb/TableSseSpecification.py` | Нет | Нет |

Два выигрыша сохранили правильный путь в обоих меню. В третьем старый известный адрес поднялся в первые шесть. Только в одной из 32 задач расширенная память привела к физическому открытию прежде не просмотренного адреса из накопленной выдачи, `pennylane/optimize/qng.py`; файл не входил в будущее изменение. Следующий контролируемый контраст — зафиксировать одинаковую формулу ранжирования и менять только доступность новых файлов. Ещё один независимый контраст — при неизменном пуле ранее просмотренных адресов менять только их ранжирование. Это позволит отделить полезность записи новых имён от композиции списка.

### Почему нет измеренного эффекта типизации

Из всех 172 префиксов с тремя полными меню в трёх изменилось множество шести между `typed_union` и `flat_union`; это две задачи. В отобранных 32 множества совпали во всех случаях. В одном из них различался порядок, который заранее предусмотренное независимое перемешивание удалило. Совпали SHA всех 32 пар запросов. Полученное нулевое различие является структурным свойством предъявления. Данных для оценки воздействия типизации при реально изменённом меню в запланированной выборке нет. На полном входном пуле число смен состава в меню длины 1, 3, 6 и 10 равно соответственно 0/388, 3/281, 3/172 и 7/116 при трёх полных рангах. ## Стоимость и проверяемость

Все 64 уникальных запроса Qwen дали валидный вызов. Из 96 логических вариантов 32 побайтно совпали с другим вариантом и переиспользовали его ответ. В выставленных сервером счётчиках всего 45 940 входных и 2 196 выходных токенов, кешированных входных токенов ноль. Последовательное время запросов на данной машине — 103,7 с. Для 32 действий исходное меню заняло 22 939 входных и 1 091 выходной токен, любое из расширенных — 23 001 и 1 105. Длина имён по 192 пунктам составила 7 224 против 7 354 байтов UTF-8.

Реальные попытки чтения повторялись и при одинаковых запросах. Для 93 успешных чтений сверены SHA256, длина и Git blob SHA1. Совокупный объём 2 157 846 байтов, из них 795 032 у исходного меню и по 681 407 у расширенных. 39 различных содержимых занимают 850 930 байт до сжатия. Сумма времени всех 96 запросов чтения — 27,4 с с учётом параллельного получения данных, поэтому это сумма длительностей, а не время ожидания пользователя. Один выбранный всеми тремя ветками адрес cfn-lint отсутствовал в реальном Git-дереве, что независимо проверено `git ls-tree`. Чтение по SHA, выбор адреса и воспроизведение будущих просмотров проверены поштучно. Полная цена построения состояния по каждому исходному префиксу и правила амортизации приведены в смежном исследовании. Локализация одного файла на отобранных событиях не даёт сопоставимой оценки сквозного успеха SWE-агента или SOTA.
