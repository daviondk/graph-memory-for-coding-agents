# Сильный контроль стоимости обновления полных списков

В исходной реализации сжатый полный список на добавлении заново выбирает формат и поэтому платит за декодирование всех старых ID. Проверим более сильный контроль. Для полных списков при чтении выбираем более короткое из абсолютных varint, разностей с сохранённым последним ID и битовой карты с базой. На записи абсолютный формат дописывает новый ID, формат разностей обновляет короткий заголовок и дописывает одну разность, карта расширяет битовую строку. Дополнительный последний ID всегда внутри оплачиваемого слота. Дополнительно проверим простой список одних разностей со всегда оплаченным последним ID. Схема XOR конкурирует с тем же обновляемым полным кодированием. Для сканирования тел сравним последовательное декодирование varint с поиском канонической подпоследовательности байтов и обязательной проверкой границы значения. Оба должны принимать одни и те же решения, отдавать одинаковые байты и ровно тот же ответ. Сравним также изменение относительно уже измеренной более компактной полной кодировки.

Для шести новых репозиториев, 721 плотный запрос и после границы все новые записи. Оба лимита — 1 и 4 КиБ. Три блока с перестановкой порядка каждого чтения и обновления при одной и той же истории и горячих страницах SQLite. Отчёт о медиане суммарного времени чтения, обновления кеша и обоих действий, количестве переданных BLOB и SQL вызовов. Это дополнительная проверка на уже просмотренных данных. Проверим пограничные совпадения подпоследовательностей в многобайтовых varint и точность инкрементального добавления. Цель — узнать, зависит ли вывод о времени от заведомо устранимого повторного кодирования.
