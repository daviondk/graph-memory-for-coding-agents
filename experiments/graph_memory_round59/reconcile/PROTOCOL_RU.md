# Восстановление недостающих адресов по состоянию графового кеша

Вместо полного списка связанных событий для пути f можно хранить их число и XOR идентификаторов. При каждом подтверждённом добавлении нового события обновляются только записи его участников. На запросе известна часть адресов — события, составы которых уже есть в общем кеше и в удерживаемом после записи окне B8. Если число недостающих адресов равно нулю, список полностью известен. Если пропал один адрес, XOR двух множеств даёт точный ID. Тогда можно прочитать сразу тело и пропустить чтение инвертированного списка. Контроль второго порядка хранит число, сумму и сумму квадратов и алгебраически восстанавливает до двух недостающих адресов. Для большего числа отсутствующих всегда читаем фактический список SQLite. Это применение классической задачи согласования множеств к общей памяти событий агентного сервиса. [Minsky, Trachtenberg и Zippel](https://ipsit.bu.edu/documents/isit2001_short.pdf)

**Фиксация до измерения.** Основная проверка — после рестарта, 1 024 байта на один LRU-пул для двух типов предметов, удерживаемые после записи события B8 одинаковы и оплачиваются отдельно. Две внешние панели R58 с плотным расписанием, сумма байтов указателей и тел при тождественных top-8. Основной метод хранит более короткое из полного списка и схемы число+XOR (однобайтовая метка). Контроль — полный список с выбором более короткой из абсолютных ID, разностей, bitmap от первого до последнего ID; есть также обычный LRU из неупакованных сверх исходного varint списков и отдельный кеш одних тел. Аналогично сравним чистое число (проверяет только полное покрытие), два момента, ёмкость 4 КиБ, редкое расписание и исходные девять проектов. При равной длине предпочитается полный список. На записи полной или свернутой записи с обновлением можно хранить текущий формат до следующего запроса. Свернутый вариант при отсутствии доказательства считывает настоящий список; если доказательство успешно, набор ID известен и может быть закодирован заново.

Все варианты используют один порядок при вытеснении, один общий источник и стоимость формата R59/lazy. Никакого необъявленного обратного индекса: для установления множества известных ID явно сканируем закодированные тела в ограниченном кеше, пересекаем с членствами B8 и учитываем объём/число сканирований и время. У контрольных вариантов нет необходимости декодировать тела ради проверки. Логи содержат стоимость запроса и исход проверки, плотные и разреженные потоки могут частично пересекаться по запросам. При технической возможности добавим контроль частоты/выбора представления без подмены основного исхода. Никаких заявлений о превосходстве по решению задач или новизне самой операции XOR.
