# Кеш чтения графа после перезапуска

Фиксация до расчёта результатов R59. Состояние до перезапуска не копируем. Проверяем, помогает ли единый ленивый LRU-кеш из списков событий и неизменяемых тел коммитов уменьшить объём SQLite-ответов. Повторный запрос другого участника вправе переиспользовать загруженное по ID тело. Полный список связанных событий действителен и для следующих запросов, если после подтверждённой записи в него дописывать каждое новое событие этого файла. Поддерживаем общий лимит двух типов записей, вытесняем по давности обращения; последовательность записи при чтении — тела в возрастающем порядке ID, затем полный список. Никаких запросов или переносов тел при открытии.

Исходный контракт — точные ранжированные пары файл/балл для восьми кандидатов. На входе девять прежних проектов R58 (6 B, 3 длинных) и 12 внешних из двух архивов (обе частоты запросов B и long). Момент рестарта, якоря, видимый префикс, tie-break, порядок и ограничения длины исходного события неизменны. Чтения делаем только в последующей сессии. На каждом проекте и нагрузке выполняем реальный FULL WAL SQLite replay со всеми методами читающими одну и ту же версию базы. Общие входные события пишутся один раз, физические SELECT выполняются отдельно для каждого метода. Первичная метрика — суммарные списки и тела в байтах на внешней разреженной нагрузке. Основные парные контроли для единого кеша — LRU только из событий и LRU полных счётчиков по файлу, каждый при 4 096 сериализованных байтах над общей оперативной памятью из последних восьми событий каждого участника. Если хотя бы один контроль лучше, сообщаем. Дополнительные условия — 1 024 байта, отдельный LRU только списков и варианты без подогрева записями (кеш комбинированный, только тела, только счётчики). Также сравниваем с голой БД и с общей памятью B8 без дополнительного кеша. По возможности проверяем число запросов на путь и перенос полезных тел между **разными** путями.

Бюджет оперативной памяти измеряем как длину действительно представимой сериализации содержимого LRU: kind, varint(key+1), varint(размер полезных байтов), BLOB; порядок записей кодирует порядок LRU. Тела и списки содержат положительные или нулевые varint-ID. Кеш полных счётчиков содержит varint-пары (кандидат, балл); счёт ведётся по всей видимой истории. Содержимое ссылок и ключи учитываем. Для ответов также измеряем текущий/максимальный логический размер и выборочно размер Python-объектов. Общие B8 и его доказательства покрытия отдельно от дополнительного лимита; некешированные временные результаты текущего запроса доступны всем. Различия в стоимости обработки новых записей фиксируем в количестве обновлений кешированных списков/карт. Сервис может хранить на диске весь журнал и индекс без изменения схемы. Измеряем передаваемые приложению BLOB; размер ОС-кеша, физическое чтение страниц, CPU, эффективность LLM и время работы приложения не являются исходами.

Контроли восстановления с новым процессом — B8-cold, естественный полный и естественный частотный на 1 КиБ из R58, с оплатой записи + загрузки + проверки SHA в первой точке наблюдения. При горизонтах 0/1/4/16/до конца на проект не переносим оплату в будущее и учитываем короткие/нулевые продолжения. Сохраняем результаты для каждого запроса, суммы по исходным и внешним группам, число выигрышей/проигрышей. Независимый битовый эталон проверяет точное ранжирование; совпадение B8-cold сверяем по всем побайтовым счетчикам R58, а сопоставимость полного и выбранного снимков — с измерениями естественной длины. Варианты могут существенно отличаться по размеру общей B8 и неконтролируемой памяти Python; сравнения с полным снимком трактуем отдельно от равного дополнительного бюджета. Параметры и заявленная гипотеза не редактируются по итогам прогонов.
