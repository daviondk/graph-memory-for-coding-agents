# Точное восстановление адресов: байты SQLite, стоимость чтения и поддержки при записи

На 12 внешних Git-историях при общем лимите 1 024 байта схема «число + XOR» уменьшила передачу от SQLite с **123 019 до 115 945 байт (−5,75%)**. Чтения при этом заняли больше времени: **205,74 против 181,18 мс** на 2 063 запроса. При записи XOR обновляется существенно дешевле, поэтому сумма времени чтений и обслуживания кеша уменьшилась с **247,98 до 220,04 мс (−11,3%)**. При 4 096 байтах направление изменения смешанного времени и трафика сменилось: преимущество получил полный сжатый список.

Это сравнение с конкретным сильным по размеру форматом: на каждой модификации существующая реализация целиком переоценивает три способа кодирования полного списка. Выигрыш по времени обслуживания при записи не переносится автоматически на индекс с более дешёвой дописью. ## Что именно измерялось

Пять блоков по 12 проектов, в каждом на одной хронологической нагрузке 2 063 пострестартовых запросов и 2 067 подтверждённых записей. В середине истории закрывали и открывали реальную FULL WAL базу SQLite. После этого считали все BLOB двух таблиц для прогрева, всего 23 715 байт полезных исходных данных в двенадцати префиксах (общие SHA в этот подсчёт не входят). Далее один писатель поддерживал историю и общий B8. По каждой операции порядок исполнения четырёх режимов (размер × представление) выбирался случайно; порядок проектов также менялся в каждом блоке. Все 41 260 проверок ранжирования совпали с эталоном. Покадровые счётчики SQL, исходы восстановления, объём сканирования и занятость кеша сверены с предыдущей реализацией.

В таблице — медиана пяти сумм по проектам одного блока. Суммарное время рассчитано сначала внутри блока, затем взята медиана. Столбец циклов измерен у текущего потока Windows и показан в миллионах. Во время чтения учитывается сканирование тел, арифметика восстановления, SQL и формирование точного ранга. Столбец обслуживания записи включает изменение соответствующего сжатого кеша после успешного коммита. Общие SQLite-записи и общий B8 оценены отдельно.

При 1 КиБ XOR декодировал при поиске известных ID 37 346 уже резидентных объектов объёмом 218 933 байта. Полный список обходился без этого прохода. При 4 КиБ внутреннее сканирование выросло до 189 596 объектов и 971 949 байт. Эти байты относятся к работе с RAM, в таблице отдельно учитывается передача из SQLite. На обоих бюджетах полный список быстрее отвечал на запросы. При 1 КиБ отношение смешанного времени XOR к полному списку во всех пяти блоках лежало в пределах 0,882–0,893, при 4 КиБ — 1,090–1,114. Пять технических повторов характеризуют разброс на этой машине и не дают пяти независимых наборов репозиториев.

Медианное общее время физических записей источника — 925,56 мс, добавления в B8 — 13,14 мс на блок. Если прибавить оба общих этапа внутри каждого блока, получаются соответственно 1 186,55 против 1 157,38 мс при 1 КиБ, то есть около 2,5% экономии учтённых операций. При 4 КиБ — 1 209,40 против 1 239,27 мс. Это защищённое сравнение последовательной локальной реализации с прогретой БД, не end-to-end время работающего агента. Использованы CPython 3.14.4, SQLite 3.50.4 и Windows. Индивидуальные измерения времени, порядок запуска и показания циклов сохранены. ## Условия точности

Пусть A — множество всех идентификаторов событий данного якоря на текущем префиксе, K — множество известных ID, полученных из тел, в которых действительно присутствует якорь. Важна предпосылка K ⊆ A: неизменяемые события, уникальные возрастающие ID, одинаковый префикс для сводки и данных, обновление сводки каждого участника только после принятой записи. Повтор события через нескольких участников устраняется множеством K. При d = |A| − |K| = 0 множества совпадают. При d = 1 отсутствующий ID равен XOR(A) XOR XOR(K) из-за попарного сокращения одинаковых членов.

При d = 2 два пропущенных ID u и v задаются первой и второй степенными суммами: s = u + v, q = u² + v². Тогда (u − v)² = 2q − s². Целочисленный квадратный корень и сумма s однозначно дают два корня без учёта порядка. Проверяются положительность квадрата для различных ID, точность корня, чётность, допустимый диапазон и отсутствие повторов. Если информации недостаточно, читатель обращается к полному списку. Сами тела недостающих событий всё равно нужно загрузить.

Сводка не обнаруживает произвольный повреждённый кеш. Например, при A = {0,3} и ошибочном K = {1} схема XOR вернёт правдоподобное, но неправильное множество {1,2}. Более того, при ошибочном K = {1,2} один счётчик объявит полное покрытие; текущий путь при нулевой разности размера поступает так же и для других сводок. Для перезапуска контракт требует утраты неподтверждённого состояния кеша. Для работающего процесса требуется подавление повторных уведомлений по результату принятия входного события.

## Независимые проверки

- Проверены **15 309** сочетаний сводки и действительного подмножества над 320 входными множествами. Независимо сверены фактическая минимальная длина полного кодирования среди абсолютных ID, разностей и bitmap, обратимость и добавление следующего ID. В тестах есть границы 127/128 и 16 383/16 384, а также ID больше 2⁴⁰.
- В SQLite-интеграции проверены **4 752** ранжирования и **13 813** резидентных записей (тело сверяется с исходным событием, компактная сводка — с независимо вычисленными полными множествами). Четыре раза закрывали и вновь открывали БД, в том числе после коммита до оповещения кеша. Четыре инъекции отката не оставили изменений. Четыре повторные доставки были подавлены, четыре конфликтующих записи отклонены. Проверка охватывает работу после нескольких новых коммитов, вытеснение и разные ограничения кеша.
- В отдельной серии из 12 контролируемых состояний физически вытесняли ноль, одно, два или три тела при сохранённой сводке. XOR с одним отсутствующим телом, а моменты с одним/двумя, восстановили его адреса и обошлись без обращения за полным списком; выборка самих тел выполнялась. При большем дефиците зафиксирован запрос полного списка. Это отдельный тест точных ветвей; в предыдущем синтетическом потоке случайные обращения редко создавали именно такие состояния.
