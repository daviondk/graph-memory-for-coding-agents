# Независимый аудит стоимости ссылок на события

Для 33 сочетаний публичного проекта и нагрузки повторно восстановлены хронология, момент рестарта, отбор событий и ожидаемый Top‑8 по исходным историям. Новый расчёт ранжирует файлы прямым подсчётом совместных изменений, затем применяет установленное правило разрешения равенств. Полученные последовательности 2 940 ответов совпали по SHA‑256 со всеми девятью исходными режимами. В 66 сочетаниях потока и отбора число байтов первого обращения независимо восстановлено из пересечения выбранных событий с реально запрошенными файлами. Два отбора — набор по спросу до 1 КиБ и полный живой набор. [Код](check_refs.py) · [Результаты по потокам и SHA входа](results.json)

## Что доказано

Пусть C — размер копии снимка, R — размер ссылочного снимка, F — суммарный размер тел выбранных событий, действительно потребовавшихся к заданному горизонту. Оба снимка записывают и затем читают по одному разу. При одинаковом наборе событий, одинаковой версии доступного архива, одинаковой логике выдачи и закреплении каждого загруженного тела до окончания сессии получаем

`стоимость копии − стоимость ленивых ссылок = 2(C−R) − F`.

Плата за проверку ревизии, списки событий и прочие тела одинакова и сокращается. Равенство проверено для обеих копий — исходной и кодированной zlib — на наблюдаемых SQLite BLOB. Для немедленного чтения ссылок вместо ленивого разность равна B−F, где B — общий объём всех выбранных тел. Идентичность покомпонентных счётчиков проверена для каждого запроса. Тождество также непосредственно проверено по итоговым байтам для 306 вариантов горизонта и отбора.

**Гарантия против несжатой копии.** Общий заголовок сокращается. Простое допустимое представление ссылок содержит только абсолютные varint ID событий. Исходная копия, помимо тех же ID, содержит каждое тело и поле длины минимум в один байт. Алгоритм выбирает самый короткий адресный формат, поэтому C−R ≥ B+k для k событий. Каждое тело из неизменяемого архива загружается по ссылке максимум один раз, следовательно F≤B. Экономия составляет минимум B+2k при непустом выборе. Эта нижняя граница зависит от формата копии и логической, двусторонней оплаты. Другие форматы, физические страницы SQLite, сеть с иным соотношением цен и вытеснение прочитанных тел требуют отдельного расчёта.

**Граница для сжатой копии.** Точное условие выигрыша — 2(C−R)>F. На полном наблюдённом продолжении оно выполнено для каждого из 33 случаев при обоих отборах. Общая экономия относительно сжатой копии — 28 144 байта при отборе до 1 КиБ и 72 161 при полном живом наборе. Совокупность включает 21 уникальный проект; режимы одной и той же истории зависимы. Для первичной группы из трёх длинных входных историй при отборе до 1 КиБ разница составила 2 836 байт.

Построен воспроизводимый контрпример в настоящей SQLite. Каждое из 128 событий связывает 32 общих файла и один собственный файл, поэтому все события имеют право остаться в полном живом наборе. Один запрос общего файла требует все тела, F=B=4 256. Сжатый снимок занимает 658 байт, ссылки на полный набор — 40 байт. Фактически получены 1 464 байта у сжатой копии, 4 484 у ленивых ссылок и 9 252 у несжатой копии при совпадении ранга. Контрпример показывает, почему полученный выигрыш против сильного контроля является измеренным свойством этих историй. [Пакеты, счётчики и контрпример](results.json)

## Отдельное физическое воспроизведение

На исходных историях Sphinx, Babel и Dask заново созданы SQLite-базы, закрыты, затем открыты из другого соединения. Проверены четыре нагрузки (для Babel две), четыре набора событий (по спросу, полный, каждое третье и пустой) и четыре реализации. Перехват результата `SELECT` непосредственно на границе SQLite независимо измеряет длины возвращённых BLOB и число обращений. Объём записанного снимка измерен `length(v)` после фиксации и закрытия писателя. Проверены **64 прогона и 5 664 ответа**; каждая выдача совпала с эталоном. Эти наблюдения измеряют логическую передачу из SQLite; объём фактических чтений диска и латентность под нагрузкой в аудит не входят. ## Кодек и отказоустойчивость

Проверены 576 пакетов штатного кодировщика и 1 440 независимо собранных пакетов десяти разрешённых форматов. Проверки охватывают пустые, полные, разреженные и случайные подмножества, неполный последний байт bitmap, границы 127/128 и 399/400/401. Бинарный состав и порядок полностью восстанавливаются для копий, множество ID — для адресных пакетов. В 48 дополнительных циклах закрытия и открытия SQLite с корректным, повреждённым или устаревшим снимком проверены 192 ранга. Ошибка контрольной суммы, несовпадение ревизии или длины префикса приводит к отклонению снимка и точному чтению архива. Отдельно проверено устаревание после фактической фиксации нового события в журнале. Такая привязка требует общего, неизменяемого, доступного журнала с теми же ID. Сценарий параллельных писателей, крах операционной системы во время фиксации и восстановление удалённой истории в аудит не включены.

Воспроизведение из этой директории: `python -B check_refs.py --verify` и `python -B sql_meter.py --verify`. Используются стандартная библиотека Python, SQLite, локальные исходные архивы и проверяемая реализация R59.
