# Графовая память при ограниченном кеше

В предыдущей серии сравнивали, какие изменения Git стоит переносить через рестарт кодового агента. В этой серии исследовали следующий шаг. Если полная история уже есть в SQLite, какие связи выгодно оставить в небольшом кеше, насколько дешевле получить тот же ответ и помогает ли структура графа выбрать полезный прошлый опыт?

**Основной результат.** Поставили один и тот же запрос к истории файла в двух режимах. В первом в кеше размещается полный упакованный список связанных событий, во втором допускается компактная сводка, по которой можно точно восстановить одно недостающее событие. При лимите 1 КиБ на шести ранее не использованных репозиториях потребовалось 20 055 против 21 957 байт из SQLite (−8,66%). Каждый из 721 ответов вернул те же восемь файлов в том же порядке с теми же баллами. В отдельной реализации по TCP измерено 33 180 против 36 582 прикладных байт в обоих направлениях (−9,30%) и 670 против 688 обменов. Экономия наблюдалась в трёх проектах, два дали равенство, в одном выиграл полный список. При 4 КиБ выиграл полный список. [Репликация по проектам](holdout/REPORT_RU.md) · [Измерения по TCP](transport/REPORT_RU.md)

## Что объясняет выигрыш

Вершины графа — файлы и события Git. Два файла могут ссылаться на одно и то же событие. При чтении агенту нужно знать, какие другие файлы чаще всего менялись вместе с указанным. Часть подходящих событий уже доступна благодаря недавним запросам о других файлах. Для длинного списка можно сохранить только количество и XOR идентификаторов. Если в кеше ровно на одно подтверждённое событие меньше, побитовое сложение по модулю два раскрывает недостающий ID. При нескольких пропусках точную историю возвращает БД. Механизм не требует предварительного векторного индексирования исходного кода. Само алгебраическое согласование множеств известно. Вклад прототипа — комбинация точной проверки покрытия с общим кешем событий, учитывающим размер записи, и проверка условий экономии. [Метод и исходные сравнения](reconcile/REPORT_RU.md) · [Аудит восстановления](reconcile_perf/REPORT_RU.md)

На шести проектах при 1 КиБ чтение самих списков потребовало на 914 байт больше, зато чтение тел событий — на 2 816 байт меньше. Отключение декодирования при той же цене сводки увеличило затраты с 20 055 до 23 139 байт. При 4 КиБ стало выгоднее удерживать полный список, 5 911 байт против 7 725. На разреженном потоке даже при 1 КиБ обычный полный список потребовал 3 746 байт против 4 048. Три случая, где результат меняется, доступны в интерактивном просмотре. [Варианты чтения и допуска](reconcile/admission-results.json) · [Автономное демо](demo/index.html)

## Что можно утверждать для статьи

Наблюдаемый вклад относится к стоимости точного доступа к графовой памяти. Есть воспроизводимый режим, в котором компактное описание связей экономит трафик даже по сравнению с дополняемым сжатым списком, и объяснение, когда экономия исчезает. Рабочая нагрузка Git построена по реальным хронологиям с модельным расписанием запросов. Качество восстановления графа и качество решения задач агентом — разные конечные точки. Превосходство над опубликованной SOTA на полном бенчмарке агентных задач пока не установлено.

Для следующей проверки имеет смысл заранее зафиксировать правило переключения между сводкой и полным списком по наблюдавшейся цене промаха и доле уже доступных событий. Его следует сравнить на новых историях с обоими постоянными режимами и обычным LRU при одинаковом бюджете, отдельно оценить байты, число RPC и время. Связь с работой LLM требует испытания в едином агентном цикле со штатными тестами решения задач. Для демотрека можно варьировать бюджет кеша и число пропущенных событий и наблюдать точный ответ и его стоимость. [Демонстрационный пакет](release/README.md) · [Рабочая рукопись](manuscript/paper.pdf) · [Требования ICDE Demonstrations](https://icde2027.github.io/cf-demonstrations.html)

Для проверки итоговых чисел, хешей и связанных материалов выполнить `python -B verify_round.py --manifest` в этой папке. Исходные программы, покейсные данные, параметры запусков, отрицательные результаты и проверки приведены по ссылкам в таблице. [Краткий отчёт](../../docs/progress-report-r59.md)
