# Новая проверка единственного отобранного правила на исходном архиве Python
После результатов первой части R6 обнаружен разведочный сигнал модели r4_alignment: 566/2000 вместо 505 на Python HF. Выбор этого варианта по прежнему тесту явно учитывается. До получения исходных Python файлов архива и каких-либо их разметок фиксируем одну последующую гипотезу: та же обученная Java-модель увеличивает Acc@1 относительно R4 на исходном Python test.zip выпуска ICLR. Используем закрытые до этого ветвью исходные retrieval/Python два члена zip. Выбираем максимум 1000 на каждую из CFF easy/hard, CFR easy/hard по sha256 от фиксированной строки с ID, максимум 15 запросов одного проекта на страту, исключая точные имена ВСЕХ проектов Java обучения R4 и предыдущих оценок R6 обоих языков. До скоринга кандидаты и запросы сохраняются отдельно от эталонов, фиксируются хеши. Веса фиксированы в ablation_fit_lock.json. Переобучение и прочая настройка исключены. Использовать именно функцию обрезки архива RepoBench и авторскую BPE-Jaccard. Вторичные сравнения full, прямых совпадений и BM25 издателя, @3, @5 и MRR. Одна первичная проверка paired Top1 по знаковой перестановке кластерных сумм; 95% ДИ 10000 повторных выборок проектов. Если после изъятия ранее известных репозиториев поднабор мал, опубликовать фактическое n, оценку и её неопределённость. Эта более строгая проверка не сравнивает подборку исключительно с опубликованной усреднённой таблицей.
