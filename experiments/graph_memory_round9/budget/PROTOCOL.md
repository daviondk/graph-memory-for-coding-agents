# Равный бюджет памяти о тестовых наблюдениях

В исходной системе один тест связан с несколькими сотнями определений, косвенно наблюдавшихся при общей инициализации тестового сеанса. Каждая собственная запись снова платит за одно и то же множество. Предварительные результаты на Python 3.14 показали, что точное отдельное хранение общей части плюс частные битовые фильтры устранит часть лишних чтений, но общее множество было оплачено отдельно. Здесь вводим строгий **одинаковый максимальный бюджет байтов на весь сеанс**.

Пилот: 10 прежних SymPy с Python 3.14 и те же 10 на совместимом Python 3.11. Это одна выборка, результаты приводятся отдельно. Репликация: 8 других заранее сохранённых задач R7 под Python 3.11. Для распределения памяти доступны только множества старых наблюдений, число тестов и бюджет. Методы не видят будущий diff, исход или тип запроса. Баланс памяти не оптимизируем по известным результатам. Бюджет — 64 либо 256 байтов на тест, умноженные на число адресуемых тестов одного снимка. Метаданные самих фильтров включены. Имена и порядок тестов — общий интерфейс всех методов. Считаем частной инфраструктурой предыдущие результаты и ID версии, одинаковые для сравниваемых методов.

Контроли: один Bloom с 4 хешами на тест, один Bloom с подобранным по формуле числом хешей на тест (1–8). В новом варианте выделяем общий фильтр для пересечения всех множеств и частные фильтры для разностей. Для каждой таблицы известны число ключей и выделенные биты. Хранение длины и числа хешей явно оплачивается. Варианты доли для общего фильтра перебираются по сетке с шагом 5% от остатка, затем остаток распределяется по мощности частных множеств. До выбора известна только расчётная вероятность ложноположительного ответа для независимого отсутствующего ключа. Сравниваем (а) всегда использовать факторизацию, (б) на момент записи выбрать такую схему или плоские адаптивные фильтры по меньшей расчётной ошибке. Риск для запроса к общему и частному фильтрам оценивается как p_common + (1-p_common) p_private. Действительную ошибку на запросах к изменившимся символам измеряем отдельно. Восемь 32-битных хешей BLAKE2b; устойчивость к выбору хеша — фиксированные соли 0..31, основной анализ соль 0.

Первичная конечная точка — дополнительные запуски теста относительно точного графа на **восьми** задачах репликации при 256 байтах на тест, схема выбора против плоского адаптивного фильтра. Вторичные точки — 64 байта, ошибки использования устаревшего результата, число проверок, размер фактического payload, сохранение всех истинных пересечений. Пара — одно и то же наблюдение до применения или отката изменения; bootstrap по issue, направления объединены в кластер, число солей не увеличивает n. Результаты сверх точного графа относятся к потерям компактного представления. Независимую от графа полноту контроля тестовых исходов проверяем отдельно. Проверяем расчёт настоящей сериализацией и повторным чтением, сохраняем бинарные состояния для основной соли. До тестирования не предполагаем, что факторизация выйдет лучше плоского фильтра.
