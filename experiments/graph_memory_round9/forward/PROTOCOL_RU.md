# R9. Сохранился ли Java-метод после наблюдаемого изменения

**Гипотеза до ранжирования.** Если старое определение исчезло и у сохранившегося вызывающего метода пропал прямой вызов старого метода, то память о ребре вызова помогает распознать встраивание Inline Method. При перемещении/переименовании сохраняется идентичность исходного метода. Для различения классов используем текущие и прошлые исходники, а не тип из аннотации. Модели и проектный код не запускаются.

## Источник и отбор

Независимый от Python-панелей Java Benchmark 1 RefactoringMiner, файл src/test/resources/oracle/data.json, ревизия 136ee7da5a3a13e10bea2ca8f4f8342f3fd40c98. Реальное направление parent→commit, только один подтверждённый родитель. После знакомства со схемой и числом разметок по проектам выбраны 11 проектов компиляторов, анализа кода, обработки данных и инфраструктуры: checkstyle/checkstyle, google/guava, google/closure-compiler, apache/drill, graphhopper/graphhopper, antlr/antlr4, gradle/gradle, real-logic/Aeron, processing/processing, puniverse/quasar, neo4j/neo4j. Только подтверждённые TP трёх типов. Исключаем описания, темы коммитов и пути с признаками security-задач. Выбор не использует будущую доступность цели, число совпавших отпечатков или исход классификации.

Для каждого проекта отбираем до четырёх Inline, двух Rename, двух Move. Порядок SHA256 от постоянного префикса r9-forward-java, репозитория, commit, типа и описания. Сначала по одному примеру каждого типа на каждый доступный коммит без повторов, затем второй и т. д. При проблемах загрузки или разбора замены нет. Внешние аннотации используются для выбора исходного запроса и проверки метки на отдельной фазе. До расчёта тестовой метрики сохраняются раздельные queries и labels. Известны старые полные класс, имя и параметры, но не новые адрес, имя, получатель или тип. Коллизии одинакового исходного запроса раскрываются.

## Доступ к данным и алгоритмы

Граница чтения — до восьми изменённых Java-путей на запрос. Порядок по совпадению имени файла с известным старым классом (включая внешние классы), затем числу общих слов исходного package/класса с путём, затем лексикографически. Один и тот же пул доступен всем политикам. Снимки скачиваются с GitHub по двум SHA, хешируется содержимое; дерево не выполняется. Git сообщает соответствие путей и интервалы изменений. Оценщик старый метод и цель сопоставляет с AST по классу, имени, числу параметров и, при неоднозначности, по типам параметров. Неоднозначные старые методы пропускаются до предсказания. Отсутствие цели в текущем пуле — промах адресной оценки. Статус исчезновения ниже означает только отсутствие точного ключа среди просмотренных файлов.

Точный ключ метода включает полный класс (пакет и вложенные типы), имя и типы аргументов. Используем tree-sitter-java и распознаваемые прямые method_invocation по имени и числу аргументов. Это синтаксическая аппроксимация вызова: динамическая диспетчеризация, статические типы receiver и полноценное разрешение имён не выполняются. Отдельно регистрируем, исчез ли этот вызов в новой версии того же вызывающего метода. Кандидаты — все распознанные определения на фронтире, включая конструкторы с блоком.

Базовые варианты бинарного прогноза «исходная функция встроена»: (D) её точный ключ исчез, (G) исчез и выбранный по Git новый кандидат существовал ранее под собственным ключом, (L) то же для лучшего лексического кандидата, (E) исчез и сохранившийся старый вызывающий метод потерял вызов. Первичное сравнение **E против L по balanced accuracy**. Строгий вариант (EL) дополнительно требует согласия выбранного лексического кандидата с вызывающим методом, хранится как абляция. При нескольких кандидатах выбираем лидера при равенстве по Git-близости. Для адресного измерения (Inline→конкретный метод-получатель, Rename/Move→метод-преемник) сравниваются Git, отпечатки + Git при равенстве и E: если ребро найдено, оцениваем только соответствующих бывших вызывающих, иначе даём общий лексический прогноз. Суммируем также точность совместного ответа «роль и адрес». Это разные задачи.

Лексическая память — до восьми редких в старом исходном файле 64-битных хешей пятёрок последовательных лексических токенов тела, без комментариев, сигнатуры и содержащих собственную декларацию начальных токенов. Порядок разрешения ничьих по значениям самих хешей. Git-контроль использует число старых строк диапазона, находящихся вне изменённых hunk, которые проецируются в диапазон нового кандидата, затем совпадение проекции заголовка, старого имени, пути, владельца, близость номера строки. Цена графового варианта — доступ к старым ключам и ребрам в этом же наблюдаемом наборе файлов. Частота вызовов и конечная доля правильных ответов живого агента здесь не измеряются.

## Метрики и неопределённость

Основная величина — (TPR Inline + TNR Rename/Move)/2; также считаем TP/FP/FN/TN, точность адреса, совместную классификацию+адрес, каждую метрику по проектам и типам. Парный 95% интервал по 10 000 выборкам целых коммитов, seed 19021, без выборок с пустым классом. Опубликуем результаты вне зависимости от знака; вторичные контроли исследовательские. Поскольку классы подбираются стратифицированно, precision и accuracy условны на этот состав. Панель одновременно меняет язык, проекты и источник аннотаций относительно R8. Вывод о преимуществе для всех репозиториев, об обнаружении всех рефакторингов или о SOTA по этой условной задаче из сравнения не следует.
