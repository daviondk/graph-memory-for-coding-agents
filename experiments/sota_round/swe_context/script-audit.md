# Независимая проверка кода SWE-ContextBench Lite

16 ноября 2026 г. Проверены исходники cards.py, rank.py, cross_encoder.py, choose.py и score.py, предварительный PROTOCOL.md, дополнение об альтернативных контролях и назначение fetch.py. Это статическая проверка. Оценщик не запускался; содержимое таблицы отношений, строк результатов по задачам, целевых заплат и журналов отдельных ответов не открывалось. Изменения в протокол и вычислительный код не вносились.

**Прямого канала от целевых patch, test_patch или relationship к ранжированию в проверенных скриптах не обнаружено.** cards.py:78 запрашивает из двух таблиц задач только instance_id и problem_statement. ID служит для устранения повторов. В queries.json попадают порядковый номер, группа и обработанный текст задачи. rank.py работает с этим текстом и карточками прошлых публичных диалогов. choose.py показывает модели пять текстовых карточек и целевое описание; непрозрачный идентификатор определяет порядок вариантов, но в текст варианта не попадает. Исходный fetch.py скачивает и хеширует файлы, включая таблицу отношений; это локальная доступность данных. Проверена граница чтения в программе, а не аппаратная изоляция, история доступа операторов или отсутствие обучающей контаминации у предобученных моделей.

**Что получает зачёт.** score.py:41 проверяет хеши основного предсказательного манифеста до чтения отношений. Строки relationship группируются в множества experience_instance_id по related_instance_id. Непрозрачное имя каждого из 300 исходных файлов преобразуется в instance_id его прежней задачи из исторического пользовательского сообщения. Match@1 равен единице, если ID задачи выбранной карточки входит в множество допустимых предыдущих задач. При нескольких траекториях одной задачи все её алиасы получают одинаковую оценку. Поэтому точное название единицы совпадения — **предыдущая задача**, даже если на входе поиск возвращает файл сессии. Несколько допустимых отношений обрабатываются через «хотя бы одно». При наличии отношения и отсутствии соответствующей записи в библиотеке результат равен нулю. Полное отсутствие строки отношения вызывает assert для всей совокупности, включая расширение (score.py:92). Основной знаменатель жёстко проверяется на 99 Lite-вопросов, расширение и его доступная подгруппа выводятся отдельно. Порядок двух проекций исходных задач согласован при использовании одних и тех же неизменённых файлов и одинакового порядка чтения. Повторной независимой сверки текста вопроса по ключу на этапе оценки нет.

**Границы маски и бюджета.** Правило cards.py:19 удаляет HTTP(S)-ссылки, идентификаторы вида owner__repo-N, некоторые ссылки #N и отдельные последовательности hex длиной 32–64. Оно не удаляет произвольные названия репозиториев в естественном тексте, slug вида owner/repo, короткие SHA, все URL-схемы и все форматы номеров задач. В прошлой записи поле симптома извлекается из текста до следующего заголовка из ограниченного перечня; это эвристика по формату, а не структурная гарантия для произвольно вложенного текста. Утверждение «не подаём отдельное поле repo и не используем repo-фильтр» поддержано. Полную анонимизацию исходных данных этот код не устанавливает. В control-addendum.md отдельно зафиксированы нулевое пересечение ID источников с Lite и один случай в расширении; основной rank.py не удаляет совпадение с собой по правилу запроса.

Карточка хранит видимый текст ассистента из последнего подходящего фрагмента, а не проверенное исправление, и до 85 слов из путей и идентификаторов **попыток** Edit/MultiEdit/Write. Подтверждение исполнения не требуется. Код не читает содержимое tool_result и hidden thinking для этих полей. Пустые/короткие поля допускаются. Пределы карты одинаковы, но читатели фактически видят разный объём: BM25 получает всю карту, Contriever — максимум 384 субтокена, MiniLM — 512 субтокенов на пару вопрос–карточка, Qwen — максимум 175/90/40 разделённых пробелами слов трёх полей каждой из пяти карточек. Это сопоставление систем на общей библиотеке с разным доступным текстом; обозначение «одинаковый контекст в токенах» было бы неточным.

**Выбор и статистика.** Код реализует зарегистрированные веса независимых полей и RRF с константой 12 для рангов с единицы. При ничьей, в том числе для строк BM25 со всеми нулями, стабильная сортировка назначает различные места в порядке исходных имён файлов. MiniLM-L12 и Qwen используют ту же первую пятёрку fusion. Двенадцать слоёв проверяются в cross_encoder.py; первоначальный шестислойный результат сохранён отдельно. Qwen получает варианты в детерминированном порядке по хешу, сохраняет первый выбор fusion при неподходящем ответе. Его итоговый артефакт фиксирует один выбор, поэтому Match@3/5/10 относится к тем методам, для которых действительно опубликован список. Исторический результат REM 68/99 задан как опубликованный агрегат. Границы возможного p по его маргинальным суммам не заменяют известные пары результатов. score.py возвращает парные выигрыши/проигрыши, обычный точный McNemar без поправки за несколько сравнений и интервал пересэмплирования репозиториев. Отдельный bootstrap по независимым вопросам отсутствует. Внутрирепозиторийная зависимость учитывается в интервале, а обычный McNemar её не моделирует.

**Манифесты.** choose.py:71 создаёт blind_commit.json после 99 уникальных выборов. Он охватывает основной прогноз, код выбора и переданные ему данные; это локальная контрольная сумма, не внешняя временная метка. При возобновлении choose.py пропускает существующие порядковые номера, не пересчитывая хеш их запроса. Дополнительные recall_keyword и recall_hybrid условно загружаются в score.py:71 и проверяются на порядок и допустимые ID. Основной score.py не сверяет их собственные хеши и дату фиксации с отдельными receipts, поэтому заморозку внешних сравнений обосновывают их собственные манифесты. По этим внешним файлам и завершённости всего прогона статический аудит не выставляет эмпирический вердикт.
