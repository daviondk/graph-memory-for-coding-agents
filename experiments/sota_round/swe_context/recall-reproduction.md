# Слепые контрольные выдачи Recall

## Возобновление гибридного запуска

Перезапуск Windows прервал первый процесс с индексом в оперативной памяти. В нём было зарегистрировано частичное обращение к эмбеддеру, итоговой выдачи на 99 задач он не записал. В повторе каждый полный ответ Ollama сохранялся на D по SHA-256 неизменённого тела запроса. При повторе прерванного расчёта файл можно предъявить той же версии Recall и той же модели. При первой сборке каталога каждый батч был вычислен заново. Поле `checkpoint` в итоговом реестре различает вычисленные и прочитанные ответы. Время и счётчик токенов в receipt относятся к завершённому повтору, ранняя прерванная работа учитывается отдельно в recall_recovery.json.

Сторонние веса запущены сервером Ollama на 127.0.0.1:18842. Сервер и дочерний процесс llama-server ограничены двумя логическими процессорами, рабочая копия содержит только CPU-библиотеки. Для воспроизведения в Alpine WSL с монтированным диском D и уже подготовленным окружением задайте переменные и вызовите штатный метод.

```sh
d=/mnt/d/CodexResearch/x20-swe-context
export LD_LIBRARY_PATH="$d/apk-recall/usr/lib"
export PYTHONPATH="$d/apk-recall/usr/lib/python3.12/site-packages"
export OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1
ulimit -v 1200000
/usr/bin/python3 /mnt/d/CodexResearch/x20-bench-workspace/work/sota_round/swe_context/recall_hybrid.py --data "$d" --upstream "$d/recall-upstream"
```

Поисковая реализация Ali Rangwala зафиксирована на [теге 0.5.0, коммит 585d0e21](https://github.com/alirng/recall/tree/585d0e21553d20e353588b9278e067d641a8283a). Публикация чисел 53,5% и 58,6% относится к отдельно указанной там проверке версии 0.4.1. Исходный драйвер `evals_swecb.py` одинаков в двух версиях, файлы реализации поиска и эмбеддингов между версиями менялись. Исходная выдача 0.4.1 по каждому вопросу не опубликована. Локальный прогон версии 0.5.0 позволяет парное сравнение; его метрики рассчитывает независимый скорер после фиксации результатов. [Опубликованные агрегаты и идентификатор версии](https://github.com/alirng/recall/blob/585d0e21553d20e353588b9278e067d641a8283a/docs/benchmarks/results.json) · [сравнение версий](https://github.com/alirng/recall/compare/cdc05db827b351aa8c9100fd6436ebee25d50d67...585d0e21553d20e353588b9278e067d641a8283a).

## Доступные сведения и фиксация

1. Словарный запуск проецирует из официального GitHub-набора только `instance_id`, `repo` и `problem_statement`. Штатный `_tasks` получает эти поля, порядок 99 вопросов восстановлен по единственному полю `instance_id` Lite Parquet. Запросом служит полный исходный текст задачи с обрезкой крайних пробелов. Фильтрации по репозиторию нет. Индивидуальные метки связей, целевые исправления и результаты тестов не поступают на вход ранжирования.
2. Штатные методы `_transcript` и `_index` обработали все 300 исходных JSONL в авторском порядке. Из них получились 300 уникальных сессий и **600** сообщений в индексе. В собственном открытом ранжировщике сохранены все разрешённые им слова, явные идентификаторы и ссылки. Эксперимент сравнивает готовые системы представления и поиска. Метод с маскированными карточками получает меньше текста и удаляет явные ID. Также в Recall собственный ридер сам исключает из транскрипта события, которые не считает сообщениями.
3. Область поиска — 300 траекторий. Авторский вызов `store.search` получает `limit=16`, затем код удаляет собственный ID запроса, если он встретился, и оставляет 15. Публикуются первые 10 прежних cессий в порядке оценки, заменённые на исходные восьмизначные имена JSONL без расширения. Каждая строка содержит только ординал и ранжированные ключи. Локальный адаптер не вызывает этап автора, который читает таблицу связей и пропускает строки без доступной положительной метки. Внешний скорер фиксирует знаменатель 99.
4. Перед снятием слепоты у словарной выдачи записан SHA-256 в `recall_keyword_pin.json`. Для гибридной выдачи аналогичен `recall_hybrid_pin.json`. Источник и код поиска берутся без изменений. SHA-256 исходного ZIP из GitHub Codeload — `bb9d2ead4a91d4d1ed719744522b2ddb9bcf5e2023b51fe20dcfac7cf4ae9eb4`. Архив и модель помещаются на D отдельно от репликационного пакета.

## Запуск словарного контроля

Исходное дерево скачивается по полному коммиту из [GitHub](https://github.com/alirng/recall/archive/585d0e21553d20e353588b9278e067d641a8283a.zip). Разместить содержащуюся в нём папку `src` в `$stage/recall-upstream`. Необходимая структура данных и её проверка хешей приведены в `fetch.py` и `source.json`. Изолированный Windows Python 3.13.5 запускается с подходящими версиями PyArrow и импортируемых зависимостей.

```powershell
$stage = 'D:/CodexResearch/x20-swe-context'
$env:UV_CACHE_DIR = "$stage/uv-cache"
uv venv "$stage/recall-venv" --python 3.13.5
uv pip install --python "$stage/recall-venv/Scripts/python.exe" 'pyarrow==22.0.0' 'jsonschema==4.25.1' 'pyyaml==6.0.3'
& "$stage/recall-venv/Scripts/python.exe" -X utf8 recall_original.py --data $stage --upstream "$stage/recall-upstream"
```

## Запуск гибридного контроля

Тот же поисковик добавляет выдачу по близости отдельных сообщений. Стандартная `nomic-embed-text` из реестра Ollama содержит 137 млн параметров в формате F16 GGUF. Вес модели — 274 290 656 байт, SHA-256 `970aa74c0a90ef7482477cf803618e776e173c007bf957f635f1015bfcfef0e6`. Использован официальный переносимый Ollama 0.40.5 от 14 октября, последний стабильный релиз до начала 16 октября — даты авторской контрольной проверки. Точную сборку Ollama, использованную Ali Rangwala, автор не фиксирует. Файл модели сверяется с digest реестра, бинарный ZIP — с SHA-256 релиза. Для запуска извлекаются только CPU-компоненты. [Реестр весов](https://registry.ollama.ai/v2/library/nomic-embed-text/manifests/latest) · [модель](https://ollama.com/library/nomic-embed-text) · [релиз Ollama](https://github.com/ollama/ollama/releases/tag/v0.40.5).

Расчёт использует оригинальные `Embedder`, `index_messages`, `query_vector`, `store.search`, исходную нормализацию, FP16-хранение в SQLite и сканирование in-memory индекса. Для каждого сообщения и вопроса действует штатный лимит 2 000 символов с соответствующим префиксом `search_document: ` или `search_query: `. Вектор содержит 768 координат. Обычный размер пакета при инжесте равен 32. Векторы запросов вычисляются по одному. При отсутствии вектора обёртка останавливает расчёт. Единственный служебный HTTP-посредник передаёт неизменённый запрос по loopback из Linux-процесса в Windows Ollama; код ранжирования выполняется на Alpine Linux без замен библиотек.

На Windows используется локальный порт 18842, максимальное число моделей и число параллельных запросов равны одному. Процессы сервера и раннера получают маску двух логических процессоров и приоритет ниже обычного. Диагностика `recall_cpu_backend.json` сохраняет `size_vram` из реального `/api/ps`. В журнале Ollama указывается выбранная CPU-библиотека. Память используется только на длительность расчёта.

```powershell
python -X utf8 stage_recall_ollama.py "$stage/ollama-cpu"
& "$stage/recall-venv/Scripts/python.exe" -c "import json,sys,pathlib,pyarrow.parquet as pq; d=pathlib.Path(sys.argv[1]); ids=pq.read_table(d/'SWEContextBench_Related_Lite.parquet',columns=['instance_id']).column(0).to_pylist(); (d/'recall-safe-queries'/'ordinals.json').write_text(json.dumps(ids))" $stage
powershell -NoProfile -ExecutionPolicy Bypass -File ./run_recall_cpu.ps1 -Stage $stage -Distribution CodexX20MSR
```

В этом запуске WSL-дистрибутив использует Alpine 3.22.8 с Python 3.12.16. Зависимости Linux размещены в отдельном дереве `apk-recall` на D. Создать его можно внутри WSL, используя ключи и репозитории соответствующей версии Alpine.

```sh
p=/mnt/d/CodexResearch/x20-swe-context/apk-recall
mkdir -p "$p/etc/apk"
cp -r /etc/apk/keys "$p/etc/apk/"
cp /etc/apk/repositories "$p/etc/apk/repositories"
apk --root "$p" --initdb --no-cache --no-scripts add py3-numpy py3-jsonschema py3-yaml
```
