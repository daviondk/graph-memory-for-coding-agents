# Qwen3.8-27B single-GPU coding service

The Qwen team announced Qwen3.8-27B on 14 August 2026. The open-weight Apache-2.0 model is a 27B-class model with its own weights and tool template. The hosted Qwen3.8-Max used in the VibeMemBench frozen-prior study is a different model. Our checkpoint source is [Qwen's pinned release](https://huggingface.co/Qwen/Qwen3.8-27B/tree/37561816e66b5b9153b1b64c10968c18c1e6f4a0); the release date and official qwen3_coder parser direction are in the [Qwen repository](https://github.com/QwenLM/Qwen3.8/blob/2ea10dc725823bf7c3e21ce8557cbe15245132ae/README.md). The original weights and architecture are served through a third-party low-bit quantization and native llama.cpp chat-template parser.

The exact file `Qwen3.8-27B-UD-Q4_K_M.gguf` is 16,564,259,744 bytes. Its LFS SHA-256 is `1bce504dfecd84153666928a41d8a66706f0158d3a317bc5196b72819d7dc529`. The pinned Windows x64 CUDA 12.4 build is b12441 from llama.cpp commit `164ab018f9b7368ff8122094994c4b74e468aa0e`. Both binary archives have the release-supplied SHA-256 digests recorded in `runtime_receipt.json`. [Pinned quantization](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF/tree/4af51b3542f775b0a8e4b310bfb3f17e01c306c9) · [Native binary release](https://github.com/ggml-org/llama.cpp/releases/tag/b12441) · [Native function calling](https://github.com/ggml-org/llama.cpp/blob/164ab018f9b7368ff8122094994c4b74e468aa0e/docs/function-calling.md)

The model actually loaded on the workstation's RTX 3090 (24,576 MiB, driver 610.88). The server reported one 49,152-token slot and native support for both tool definitions and parallel tool calls. Five pre-cohort calls through the 27B service used 1,564 prompt and 162 generated tokens. The paired mini-SWE-agent messages generated `printf FIRST` and then `printf SECOND` after a properly linked tool result. The seed probe got native function arguments encoded as JSON strings, replayed the same request and seed, and verified a distinct per-replicate seed. No reasoning text was returned in those five calls. Short-smoke decode throughput ranged from 38.19 to 40.93 tokens/s. Device usage peaked at about 18.7k MiB during initial observations, including the desktop. Full-cohort resource receipts are separate. The binary's startup log reports ignoring extra block-64 tensors. The architecture has 64 ordinary layers; no speculative or MTP decoding was enabled.

We serve the embedded Jinja template with native OpenAI-format `tools`, `assistant.tool_calls` and matching `role: tool` messages. The localhost proxy forwards request/response contents without writing or parsing shell actions. It assigns per-step experimental sampling seeds and sets the native sampling options. The endpoint alias is `openai/qwen38-27b-ud-q4km` in the authors' LiteLLM client, routes are `http://127.0.0.1:18839/replicate/0/v1` and `/replicate/1/v1`. The native server binds only to loopback on port 18840. Automatic tool choice, nonthinking mode, temperature .5, top-p .95, top-k 20, min-p 0, repeat penalty 1, up to 1,024 output tokens. The experimental seed is the first 15 hexadecimal digits of SHA-256 over `20261116|<replicate>|<count of prior assistant messages>` interpreted as an integer modulo 2^31−1. A supplied explicit seed takes precedence. Tools remain structural; format failures are visible in the wire logs. Semantic replay can be tested independently of random transport IDs.

## Reproduction

Stage scripts in one writable D-drive directory, change into it, and run `python stage_model.py`, then `python stage_runtime.py`. The model downloader supports resumption and verifies every HTTP Content-Range and the final official LFS hash. The Windows script `start_server.ps1` uses verified artifacts, Nvidia CUDA and the embedded chat template. Source, copied service metadata and smoke records describe the actual run. The Windows default is one 49,152-token slot, Q8_0 K/V, batch 512 and microbatch 256; only lightweight source/hashes belong in the archive. Use the corresponding pinned mini-SWE-agent environment and the sibling `vibe_solver/pinned_smoke.py` to test ability to emit FIRST then SECOND across a tool observation; `smoke_seed.py` checks same-seed semantic replay and distinct seed routing. All control-flow tests use fixed harmless synthetic commands. Model speed and correctness on coding tasks are separately measured outcomes.
