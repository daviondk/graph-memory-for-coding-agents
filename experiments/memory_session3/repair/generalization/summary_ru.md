# Сохраняется ли эффект памяти на новых тестах исправления кода

На 464 новых входах для 29 программ QuixBugs все эталонные исправления прошли все проверки. У каждого из 29 оригинальных программных дефектов нашёлся хотя бы один вход, на котором он проявился. По числу задач, решённых полностью, прошлое наблюдение об ошибке плюс контрольный успешный случай дали **24 из 29**. Такой же результат получен при сохранении двух последних наблюдений, а агент с пустой памятью решил **25 из 29**.

## Что проверяли

Использованы прежние 116 назначений условий памяти одним и тем же 29 программам. Между условиями встречались побайтно идентичные ответы модели. Осталось 50 уникальных кандидатных модулей в пределах задач, произведённых ранее Qwen3.8-27B. Все ответы и исходный набор проверены по SHA-256. Новых вызовов LLM, повторных попыток генерации и отбора лучших решений не было. Зафиксированы 464 новых входа, по 16 для каждой из 29 задач, со своими проверяющими функциями. Эти входы не повторяют публичные JSON-тесты соответствующей задачи и распарсенные литеральные примеры в документации. Для Ханоя учитывались параметры по умолчанию. Это новое тестовое покрытие тех же известных задач. [QuixBugs, использованная ревизия](https://github.com/jkoppel/QuixBugs/tree/4257f44b0ff1181dedaedee6a447e133219fcebf)

Выбор входов и ожидаемые свойства записаны до открытия сравнений новых кандидатов. Сортировка сверялась с Python sorted, факторизация — с простотой и произведением множителей, счёт сдачи — с независимой динамической программой, НОД — с math.gcd. Оптимальную длину возрастающей и общей подпоследовательности искали перебором на маленьких входах. При поиске не первого вхождения допускался любой верный индекс. Для Ханоя проверялись легальность каждого перемещения, достижение цели и минимальное число ходов. Для подмножеств и сочетаний проверялась полнота с точным учётом кратности, при нескольких оптимальных общих подпоследовательностях принималась любая действительная. Для переноса строк оцениваются длина, сохранение текста и перенос целых слов в случаях, когда каждое слово помещается. В этих постановках допустимый вывод может отличаться от примера в репозитории.

С учётом оригиналов и эталонов выполнены 107 уникальных модулей × 16 свежих интерпретаторов = **1 712 фактических проверок**. Каждый запуск кандидата выполнялся в отдельном интерпретаторе Python внутри закреплённого по дайджесту образа. Файловая система доступна только для чтения, сеть отключена, монтирований с компьютера нет, права непривилегированные. Лимит 0,9 с на процесс, 144 MiB адресного пространства для дочернего интерпретатора. Кандидату передавали его код и аргументы примера, проверка ответа выполнялась отдельно. Для всех оценённых сгенерированных вариантов число таймаутов равно нулю. Шесть ошибок в подсчёте по назначениям были исключениями исполнения, прочие неудачи дали несовпадающий ответ.

## Результаты

| Условие при исходной генерации | Все 16 новых входов верны, задач из 29 | Верных ответов из 464 | Успех по публичному holdout и новым условиям, задач |
|---|---:|---:|---:|
| Исходная программа | 0 | 105 | 0 |
| Эталонное исправление | 29 | 464 | — |
| Пустая память | 25 | 440 | 25 |
| До двух последних наблюдений | 24 | 427 | 24 |
| Короткое свидетельство об ошибке + успешный контроль | 24 | 422 | 24 |
| Все доступные наблюдения префикса | 25 | 432 | 25 |

Сравнение свидетельства с двумя последними наблюдениями даёт 2 выигрыша (find_in_sorted, max_sublist_sum), 2 проигрыша (lis, longest_common_subsequence) и 25 ничьих. Парная разность 0 процентных пунктов, 95%-й описательный bootstrap-интервал с пересэмплированием программ от −13,79 до +13,79 п.п., точный двухсторонний знаковый тест p=1. Относительно пустой и полной памяти у свидетельства по одному выигрышу и два проигрыша. Эти сравнения используют общие ответы и один набор программ. Отдельные тестовые входы внутри математической задачи зависимы.

Новые тесты обнаружили ошибку в max_sublist_sum у пустой памяти и у последних наблюдений. Обе версии проходили исходный публичный holdout. На [-5, -5, -4, -7] обе вернули −4. Контракт допускает пустой подсписок, его сумма 0. Также проверка новых входов обнаружила исходный дефект is_valid_parenthesization, который не проявлялся на прежнем публичном holdout. Во всех 29 программах эталон прошёл, поэтому предусмотренное протоколом исключение при несостоятельном оракуле не понадобилось.

Эксперимент позволяет отказаться от заявления о воспроизводимом улучшении при сохранении одного короткого свидетельства вместо двух последних событий на этих задачах. Для исследования памяти особенно показательны различные проигрыши условий на разных программах. Корпус мал, генераторы ручные и покрывают выбранные части допустимых входов. Новые входы той же задачи не проверяют перенос на другие репозитории, модели, длительные интерактивные сеансы или задачи, неизвестные модели из предобучения.

## Как перепроверить

Автономная проверка только по содержимому этого каталога запускается командой `python offline_verify.py`. Она пересчитывает результаты по сырым наблюдениям и проверяет отсутствие официальных входов по сохранённому перечню хешей. Полная проверка ниже дополнительно сверяет черновые результаты с исходными файлами в рабочем пространстве.

В этом каталоге команда `python audit.py --check` без Docker и модели повторно оценивает каждое записанное фактическое значение, проверяет хеши исходных генераций и совпадения с опубликованными входами. Требуются соседний каталог исходного опыта repair и локальная копия закреплённой ревизии D:/CodexResearch/x20-session3-quixbugs. Это путь, используемый в текущей установке. Для переноса можно указать свой путь в generate.UP в отдельной копии, что изменит хеш кода.

- PROTOCOL.md, generate.py, oracle.py и lock.json — постановка, условия и зафиксированные хеши.
- cases.json и generation.json — входы с номерами генерации и перечень исключённых публичных примеров.
- receipts/ и assignments.json — неизменяемый идентификатор модуля, фактические значения, исключения, длительность каждой проверки.
- results.json, per_program.csv, failed_cases.json — итоги и разбор по задачам и условиям.
- execute.py воспроизводит контейнерную проверку после подтверждения зафиксированных хешей и состояния Docker. Возобновляет работу с первого отсутствующего журнала. Для физического повтора использовать отдельную копию каталога без receipts, сохраняя lock.json. Оценку записанных значений повторить проще через audit.py --check.
