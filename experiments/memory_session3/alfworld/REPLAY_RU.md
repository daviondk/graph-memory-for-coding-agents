# Воспроизведение окружения

В корне раунда находятся точные архивы train/valid исходных игр, таблиц траекторий и применённых классов ALFWorld (upstream). В основном коде среда загружает подлинные game.tw-pddl через textworld.start. Имена задаёт официальный AlfredDemangler в детерминированной конфигурации. Содержимое PDDL и внутренние факты не передаются функции выбора действия. Отдельный сборщик использует metadata для воспроизводимого выбора эпизодов и анализа групп; это поле отсутствует в передаваемых стратегии данных.

Исходные условия и сравнения записаны в PROTOCOL.md, AMENDMENT-before-eval.md, PLANNER_PROTOCOL.md, TRANSFER_PROTOCOL.md и text_only/PROTOCOL.md. Для независимого воспроизведения в чистом каталоге подготовить исходный код, игры и Python-окружение по ../README_RU.md, настроить точки монтирования движка, сохранить реальные входные архивы под ожидаемыми именами. Порядок запуска на новой копии:

1. Windows host: roster.py генерирует идентификаторы разрешённых задач и официальный фильтр solvable + six task types; исправность обёртки проверяется probe.py на train. На Linux в исследовательском контейнере roll.py train собирает 39 честных траекторий и файл learned.json, затем roll.py eval исполняет шесть базовых вариантов. 
2. public_init.py снимает только первое пользовательское наблюдение. В отдельной фазе на GPU plan.py принимает initial.json и learned.json, фиксирует входной хеш, генерирует q_prior / q_shown / q_placebo и подписывает планы. Дубликаты запроса целиком кешируются. Никаких действий в процессе этого шага не симулируется.
3. На Linux planner_roll.py исполняет четыре замороженных варианта планирования. score.py пересчитывает нативный won и элементы стоимости, выставляя 50 шагов каждой неудаче независимо от последней команды. 
4. transfer.py prepare берёт состав valid_seen и те же train-трассы, генерирует новые хеши. transfer.py eval исполняет новые варианты в обоих разбиениях; transfer_score.py сравнивает сохранённые исходы. 
5. В text_only действует отдельный контроллер с текстовым вводом. Формат и команды описаны в его протоколе. checks.py --final перепроверяет основной агент по ранее сохранённым действиям и наблюдениям; checks.py --native повторяет тренировочные эпизоды в исходном движке.

Первая попытка включить планировщик одновременно с CPU-подготовкой была остановлена контролем свободной памяти Windows. Предыдущие 110 ответов в QuixBugs к этому моменту были сохранены. Первая попытка планирования не записала ни одного успешного ответа; в отдельной фазе выполнены все 90 вызовов, проверены исходные payload и native response ID. Работа GPU и загрузка симулятора затем шли последовательно. Журнал инфраструктурного сбоя сохранён в planner.log, успешный перезапуск — planner_retry.log и stages.jsonl, телеметрия — ../runtime.
