# Selecting the next verification procedure from an episode's own action history

Registered before extracting or scoring verification actions from the already projected 1,441 public trajectories. This is a separate exploratory retrospective replay from the file-content experiment. Question: once a coding agent is about to run a test, can a small private history tell it *which test target(s)* it will use again? No current test name, command, tool result, issue labels, textual solution, or future action contributes to the choice. The fact it is about to verify is supplied as a conditional trigger; this does not test when to choose testing. No cross-episode write or model calls. No repository indexing or training.

Use strictly parseable pytest/unittest/Django runtests commands (including a leading explicit cd /testbed) and project ordered set of explicitly specified test selectors. Clean shell suffix piping to a display command may count for question target; only a direct single invocation can label its return code as a test verdict. Exclude bare whole-suite tests, shell expansions, implicit -k filters without an explicit file, multi-invocation ambiguities, and non-Python custom probes for the primary target. Include a literal -k expression in the procedure identity if present. A procedure is runner plus normalized explicit target(s) and optional -k filter, ignoring quiet/verbosity etc. Branching and cwd must be statically recognizable. Model is asked to predict from up to 8 most recent distinct saved recipes, with recorded access refresh on observed verification. An oracle over that bank gives the maximum achievable top-1. New targets count as misses, no target-specific filtering by future availability. Denominators include first-ever eligible invocation.

Pre-specified four policies: last-used; most frequently used (thinned to the same 8 resident records; tie last); last then prefer most recent known failing record (use only direct rc=1, other statuses unknown); context matching. For context matching index each past recipe by up to six latest distinct recognized file reads/explicitly patched paths since preceding verification. At lookup compare current file set with the context at the last use of each resident recipe: score two for each same complete path and one for each distinct matching basename stem after disallowing generic __init__, conftest, models, test, tests, main, utils. Rank by this sum then recency. Additional strong baseline: if context has no exact-path or stem match, use last-used (same as context primary) and give separate conditional analysis on the cases where it *changes* the last-used decision. Do not tune after scoring. For simultaneous tool calls treat group as one instant, exclude composite query groups where there are two distinct verification invocations, no within-batch transfer. Report all calls, number of model-task sessions, unique tasks covered, top-1 per method, pair wins/losses, cold-starts, exact random expectation, and PR-cluster bootstrap difference. Outcome is subsequent human-observed agent choice, not test usefulness or correctness of repair. Split by generating model with correlated issues grouped for pooled intervals. Record actual predicted recipe hashes and truth after sealing predictions.
