# Сколько ответов нужно для точного сравнения двух правил чтения

Когда два правила дают вопросу один и тот же токенизированный запрос на одном снимке читателя, вклад этого вопроса в парную разность EM и F1 известен до генерации: он равен нулю. В новом операторе SQLite можно изменить политику и узнать, для каких вопросов нужны оба ответа. Для порога бонуса единственная возможная смена задаётся отрывом между лучшим заголовком и лучшим упомянутым заголовком. Индекс по отрыву перечисляет нужную полуоткрытую область порогов. Контрольный линейный перебор сравнивает обе полные адресации и приходит к тому же набору входов. [Предварительный протокол](PROTOCOL_RU.md) · [Реализация](replay.py)

| Сравнение фиксированного бонуса с dense | Вопросов | Разных входов на оба варианта при обычной мемоизации | Вызовов для точной парной разности из пустого кеша | Дополнительно при уже известной базе | Разность Answer F1, п.п. |
|---|---:|---:|---:|---:|---:|
| 2Wiki, первый отложенный набор | 640 | 672 | 64 | 32 | +0,64 |
| 2Wiki, подтверждающий набор | 1 280 | 1 335 | 110 | 55 | +1,08 |
| HotpotQA, независимый перенос | 640 | 685 | 90 | 45 | +1,69 |
| HotpotQA, подтверждающий набор | 1 280 | 1 367 | 174 | 87 | +1,35 |

На 1 280 вопросах два способа вычислили одну и ту же поштучную разность с одинаковым знаменателем. Из 1 255 нулевых разностей F1 **1 225** следуют из идентичности входа; ещё 30 установлены сравнением реально сохранённых ответов. Этот план требует 23 744 входных и 1 242 выходных токенов вместо 301 406 и 16 736 соответственно для полного объединения входов. Чтобы сообщить абсолютный F1 каждой политики при холодном старте, нужны также результаты исходной политики. При полной тёплой базе оба корректных варианта требуют 55 новых вызовов. Это подсчёт запросов и записанных токенов при детерминированном снимке, а не замер ускорения GPU. Для всех возможных порогов на этой панели достаточно пар по всем 300 отличающимся адресам (600 отдельных входов). На двух свежих панелях HotpotQA отдельно проверили перенос того же способа подсчёта после фиксации первоначального протокола двух панелей. [Стоимость всех контрастов](results.json) · [Парные записи 2Wiki](gate_confirmation-witnesses.json.gz) · [Парные записи HotpotQA](transfer-witnesses.json.gz)

**Почему ключ включает всю последовательность токенов.** На 640 общих вопросах двух архивных конфигураций оба адреса документов совпали во всех случаях. В 26 случаях различались полные входы, в 11 различался сгенерированный текст, в пяти изменился F1. Упрощённое кеширование по паре адресов скрыло бы эти изменения. Проверка различает модель, движок, настройки вывода, клиент и токены. Независимая случайная генерация требует отдельного контракта. [Протокол контроля](CONTROL_RU.md) · [Все 640 сравнений](control.json.gz)

**Как проверить.** Из этого каталога `python -B verify.py` реконструирует четыре панели по исходным данным и проверяет векторы разностей по обоим направлениям для всех точек смены и соседних чисел. Всего проверено 5 038 080 поштучных назначений между dense и порогами. `python -B replay.py --panel transfer --start registered --end always` выводит стоимость прямого сравнения на HotpotQA. [Результаты независимого контроля](verification.json)

## Какие последствия можно установить после исправления одного ребра

Для фиксированной линейной модели с положительной надбавкой за видимое упоминание понижение оценки может сменить лидерство только при изменении самого лидера. Достаточно сравнить его новый балл с прежним вторым кандидатом в том же полном порядке. При добавлении ребра достаточно сравнить изменённого кандидата с прежним лидером. При изменении признаков других строк или новой версии первого отрывка такой сертификат нужно пересчитать. В интерактивном сценарии удаляется только признак связи для ранжирования, текст сохраняется. [Протокол и область применимости](EDGE_PROTOCOL_RU.md)

На первых трёх панелях независимый полный SQL дал **совпадение выбора во всех 22 982** случаях удаления или добавления одного ребра. После отдельной проверки ещё на 1 280 HotpotQA полное совпадение сохранилось на **34 417 из 34 417** вмешательств по четырём панелям. Из 2 472 удалений наблюдавшихся связей выбор поменялся в 771 случае. Для 491 такого изменения известен ответ на точно том же входе и при том же бюджете, для 280 он отсутствует. В этих случаях демо показывает новый заголовок и явно сообщает об отсутствии наблюдаемого ответа. Из имеющихся 491 ответа нельзя оценить средний эффект по всем 771 сменам. Перебор вставок — искусственное вмешательство, оно проверяет корректность обновления. [Проверка оператора](edge_audit.py) · [Все счётчики](edge-results.json) · [Все смены](edge-switches.json.gz)

**Воспроизведение интерфейса.** `python -B server.py --port 8789` открывает локальную службу. Главная страница сравнивает две пороговые политики, путь `/rank` исполняет обученную модель в SQLite. Если доступны оригинальные корпуса и их проверенные проекции, `projection.py` и `rank_projection.py` заново собирают базы в новый выходной файл. Автономное демо поставляет обе готовые базы. [Комплект для запуска](../submission/candidate.zip)


Файл [verify_views.py](verify_views.py) отдельно сверяет все 7 680 решений двух обученных моделей в поставляемой SQLite, хеш промпта и F1 выбранного ответа, в том числе на четвёртой панели. В сценарии со снятым ребром он также проверяет реальный исход без сохранённого ответа.
