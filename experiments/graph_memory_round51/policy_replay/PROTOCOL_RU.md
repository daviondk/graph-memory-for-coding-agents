# Протокол точной оценки разности двух политик чтения

Вопрос исследования — сколько вызовов одного и того же зафиксированного читателя нужно, чтобы в точности вычислить разницу двух политик графовой памяти по всем вопросам? Возможность не вызывать читателя заранее определяем исключительно по адресам полных входов, до чтения ответов. Эта серия переиспользует два опубликованных ранее локальных прогона 2Wiki: 640 вопросов adaptive_address и 1280 вопросов gate_confirmation. Их итоговые эффекты уже известны. Это ретроспективная проверка стоимости и правильности физического плана. Ранжирование и качество не переобучаем.

**Контракт.** Одна неизменная версия декодера, детерминированная семантика одного сохранённого ответа на пару «снимок, SHA256 массива входных токенов». Ответы и оценки привязаны к вопросу. Одинаковые заголовки или адреса документов сами по себе не разрешают перенос ответа. Для эпизода с двумя идентичными вызовами разность результата равна нулю при любой функции оценки. Для остальных требуется результат каждого различающегося вызова, если он отсутствует в кеше. Все доверительные интервалы продолжают учитывать полную выборку и прежнюю единицу кластеризации, включая структурные нули. Независимая стохастическая генерация запускает два разных вызова даже с одним промптом и из этого контракта исключена.

**Оценивание.** Основная сравниваемая пара — замороженный порог против плотного поиска на панели 1280. Вторичные проверки — то же на 640, безусловный переход против плотного поиска, порог против безусловного перехода, а также все пороги с точностью до класса эквивалентных назначений. Один читатель и прежняя политика выравнивания токен-бюджета во всех условиях. Основная системная метрика — число уникальных полных вызовов при пустом кеше на одну точную парную разность против обычной мемоизации запроса во всём объединении двух политик. В качестве сильного контроля применяем прямой программный перебор с предварительным сравнением отпечатков. Для исходной абсолютной метрики отдельно указываем затраты, если исходные ответы уже получены. Из журналов считаем расходы входных и сгенерированных токенов уникальных вызовов. Это точный контрфактический подсчёт работы при данном контракте, часы исполнения отдельно заново не замеряются.

**Физический план.** Из замороженной выдачи материализуем реестр точек, при которых меняется выбранный второй источник. Область политики — неотрицательный порог от 0 до 2 включительно. При равенстве порогу выигрывает лучший упомянутый заголовок. Индекс по величине отрыва позволяет запросить ровно строки между двумя порогами, затем сравнить полные ключи обращений. Отдельно проверяем стартовое ранжирование по плотной близости и специальный режим обязательного перехода по упоминанию. По каждому различному отрыву сравниваем полную адресацию и вектор разностей с контрольным расчётом. Дополнительные тесты на точной границе с соседними представимыми числами, на совпадении входа у разных адресов и на изменении снимка читателя. Если указатели адресов различны, входы совпадают — работа может сократиться ещё.

**Воспроизводимость.** Сохраняем запросы, версию SQLite/Python, идентификаторы снимков, строку на вопрос, цены каждого реально достижимого промпта, агрегированные результаты и отдельную проверку по исходным данным R50. Основное требование к точности — одинаковая поштучная разность при сравнении с полным парным пересчётом. Любое расхождение блокирует вывод о сокращении работы. За числитель выигрыша в качестве принимаем только ранее зафиксированные сравнения. Ограничение по итогам этого исследования не используется для выбора нового порога.
