# Перенос и распределение затрат между уровнями сложности
После просмотра общей эффективности и разреза Easy/Hard на Java ставим новый проверочный опыт. Данные для обучения и параметры запрещено менять. Для основной независимой проверки применяем те же веса модели размера пула к сохранённым R4 выдачам исходного графа Python на четырёх панелях по 500 задач RepoBench-R HF. Прошлые результаты поиска на этих примерах исследователям известны. Переносим между языками ранее не проверенную политику глубины. Перед любыми метками исключаем репозитории из исходной Java обучающей выборки 24k и внешней Java панели 36k по полному имени организации/проекта. Набор, исходный граф и часто используемый бенчмарк едины с предыдущими работами.

Два новых контрольных правила без обучения — равномерная вероятность 1/n для каждого кандидата и гармонический приоритет 1/[r H(n)], где H(n) — гармоническая сумма первых n чисел. Для равных вероятностей берём меньшую глубину, затем неизменный ID позиции в очереди. Локальный лимит — до восьми объявлений и хотя бы одно. Общая квота на блок из 32 вопросов фиксирована, основное k=3. Проводим две политики формирования очереди: перемешанная по SHA и отдельная на каждое точное число кандидатов. Во втором варианте простая зависимость от размера списка и ранга даёт одинаковые приоритеты всем запросам с одинаковой глубиной; сравнение изолирует эффект перераспределения между разными размерами пулов. Дополнительно на Java в таких же очередях проверяем гибкую и адаптивную модели прежней серии с уже замороженными весами. Оцениваем coverage, затраты токенов на Python из уже опубликованных счётчиков CodeGen (один разделитель между сниппетами), реальные выигрыши/потери, уровень по группам. На Java число обращений совпадает, но чтение пересекается с основным R5 и повторение относится к разведочному анализу. Сырые метки теста открываем лишь после сохранения всех глубин.
