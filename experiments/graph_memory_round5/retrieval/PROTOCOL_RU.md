# Предварительный протокол. Две проверки условного чтения графовой памяти
18 ноября 2026. Из прошлой серии известны агрегаты графа на полном архиве RepoBench и сравнение с энкодером на 320 задачах другого издания. До формулировки правила индивидуальные метки новой панели для выбора параметров не использовались. Выборки переиспользуют общедоступные данные, их нельзя называть неизвестным миру или всей лаборатории тестом.

**Первая проверка.** Сочетаем три ранее запечатанных списка одного запроса: граф между объявлениями, равнообученный локальный поиск по тексту и истории обращения (owner) и авторский Jaccard. Если локальное свидетельство и словесное совпадение поддерживают одного кандидата, а связи подняли другого, информативно учитывать величину и направление перестановки. В модели кандидата совместимость рангов используется как признак; например повышение графом само по себе и повышение, поддержанное словесным совпадением, получают разные веса. Основной исход — первое место полного адаптивного правила против обычного обученного смешивания тех же трёх рейтингов (логлинейная калибровка обратных рангов, согласий на первом месте и нормированных позиций; взаимодействий нет). Сильный дополнительный контроль — гибкий аддитивный калибратор ранга каждого источника с отдельными порогами top-1/2/3/5/10 и интервалами относительного ранга. Для выделения специфичности связей повторяем модель без графового ранжировщика. Публикуем также три отдельных системы, необученное RRF k=60, и перестановку дополнительных колонок внутри задач с сохранением базовых рангов. Переобучение: исходные ранги на 24 000 примерах HF из 731 проекта, после обучения тест на 36 000 строк авторского архива из 349 других проектов, по 3 строки. Выбор гиперпараметров по тесту запрещён. Пример имеет единичный суммарный вес при формировании условной модели. Все ранжировщики читают те же три строки и только предоставленные бенчмарком объявления, без признака страты first/repeat, названия или индекса эталона. На этапе обучения отложенные метки недоступны, решения и код хешируются до оценки.

**Вторая проверка.** Обучаем другую модель на уже оценённых 320 размеченных HF-запросах (по четыре страты) и тестируем на выбранных до новых вычислений 224 запросах другого исходного архива (56 в каждой страте, не больше четырёх примеров от одного проекта в страте; выбор по SHA). Отвечает на другой вопрос: помогает ли похожесть клиентского фрагмента по настоящему UniXcoder определить, какой используемый им тип читать. Вычислим сходства исходных полных кандидатов с запросом, оценки замороженных графа и owner, лексику. Добавим для каждого кандидата максимум и среднее входящих сообщений от семантически близких соседей, в том числе с поправками на вес неоднозначного имени и на совпадение непосредственно предшествующего кода; отдельно исходящие связи. Основной контраст — нейронные сообщения поверх так же обученной прямой смеси графа, owner и энкодера против прямой смеси без сообщений. Контроли — дополнительный калибратор с переставленными сообщениями, RRF, исходный граф, UniXcoder и вторичный графовый контроль без энкодера для оценки пользы запуска сети. Один и тот же FP32 CPU UniXcoder, max_length=512, официальный публичный wrapper, без изменения весов. У обоих методов два одинаковых префикса 3 и 10 строк с splitlines, основная проверка использует три. Не передаём модели последующую строку или страту. Обучаем отдельно для каждого окна, регуляризацию задаём заранее.

Единица оценки — конкретное обращение к внешнему объявлению, интервалы по независимой повторной выборке репозиториев 10 000 раз (на большой панели потоковые блоки); 95% интервал парной разницы, wins/losses, @1/@3/@5/MRR, общий и макро по проектам. Два основных теста, по одному на каждую проверку, поправка Holm на проектный знаковый рандомизационный тест. Широкий интервал не устанавливает эквивалентность. Для второй проверки веса обучены лишь на 320 действиях, для первой на 24 000; сравнение этих результатов между собой не изолирует память. Проекты обучения исходного графа не пересекаются с обеими внешними панелями по аудиту предыдущей серии. У первой проверки использованы готовые ранги, цена дообучения не включает создание базовых ранжировщиков. Оценивается retrieval; итоговое выполнение задач агентом — другой исход.
