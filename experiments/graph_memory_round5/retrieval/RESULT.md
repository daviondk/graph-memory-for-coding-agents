# Чтение графовой памяти при ограниченном бюджете
18 ноября 2026. Вопрос в этих опытах — какое объявление показать кодовому агенту и сколько таких объявлений ему дать. Репозитории, код, запросы и эталоны взяты из Java и Python RepoBench-R. Порядок кандидатов определяет замороженный граф R4. Экспериментальные способы меняют объединение источников, передачу сигнала соседям или глубину чтения. Правильность имеет проверяемый эталон: указанное авторами внешнее объявление. Дальнейшее использование выданного контекста генератором здесь не измерялось. Код, каждая выдача, число прочитанных объявлений, позиции эталона, веса и статистика сохранены рядом с этим отчётом.

## При одинаковом количестве объявлений можно повысить покрытие; играет роль длина очереди

В 36 000 Java-задачах фиксированный top-3 исходного графа решил retrieval для 15 963 обращений. При бюджете ровно 108 000 объявлений лучший из перечисленных по общей доле верных ответов простой распределитель покрыл 17 504. Каждый пакет до 32 вопросов получает квоту, равную трём объявлениям на каждый запрос. Семантический порядок внутри вопроса остаётся прежним. Планировщик гарантирует первый элемент, затем распределяет оставшиеся места по ожидаемой предельной вероятности включить эталон. На каждого приходится от одного до восьми объявлений. Зная только число кандидатов n и позицию r, условная логлинейная модель оценивает p(r|n) на 24 000 Java-примерах HF; её веса заморожены. Проекция оценок на невозрастающую последовательность даёт монотонные предельные выигрыши. При одинаковой цене одного элемента и принятой модели вероятности жадный выбор наибольшего доступного выигрыша максимизирует *модельное* ожидаемое число покрытых запросов: предшествующие объявлению позиции имеют не меньший вес, и допустимый оптимум можно получить последовательной заменой меньшего веса бо́льшим. Утверждение касается оценки модели, а не неизвестных истинных вероятностей. Разные длины объявлений делают оптимизацию числа токенов отдельной задачей.

| Выдача на среднем бюджете 3 | Java, число из 36 000 | Java, % | Python, число из 1 997 | Python, % |
|---|---:|---:|---:|---:|
| Каждый раз top-3 | 15 963 | 44,34 | 1 044 | 52,28 |
| Без обучения, равное 1/n | 17 291 | 48,03 | 1 064 | 53,28 |
| Без обучения, 1/[r H(n)] | 16 839 | 46,78 | 1 071 | 53,63 |
| Обученная зависимость от n и r | 17 504 | 48,62 | 1 110 | 55,58 |
| Условная смесь трёх рангов | 17 447 | 48,46 | — | — |

Планировщик размера против top-3 на Java дал +4,28 п.п. (парный 95% ДИ по проектам +2,18…+6,67), 3 798 выигрышей и 2 257 потерь. Это разведочная постановка после открытия агрегатов фиксированной глубины на тех же примерах. При чтении всех возвращённых фрагментов поток UTF‑8 уменьшился с 1 217 679 160 до 1 085 443 544 байт; многократная выдача оплачивается многократно. Условная смесь прочитала 1 020 437 569 байт и уступила простому планировщику 57 попаданий. Простая эмпирическая частота эталонной позиции при том же размере списка дала 17 358. Подробные результаты при 2, 3 и 5 местах, распределение глубин и интервалы по пакетам и проектам сохранены в budget_results.json.

Перенос на Python использует тот же графовый ранжировщик R4 и те же Java-веса планировщика. Выбрали существующую замороженную панель из четырёх страт (изначально по 500). По полному имени проекта убрали три запроса amplab/smash, пересекавшиеся с Java-панелями. Осталось 348 проектов. В смешанной очереди +3,30 п.п. к top-3 (95% ДИ +0,87…+5,83), 190 выигрышей и 124 потери. Последовательности содержали 6 070 862 кодовых токена в фиксированной тройке против 5 548 811 с планировщиком; учитывали CodeGen-токенизацию и один разделитель между фрагментами. Сравнение с равномерным 1/n дало +2,30 п.п. (+0,48…+4,05). Политика впервые проверялась на этом языке. Предыдущая серия использовала эти же Python-задачи для оценки рангов графа. Оценка переносимости ограничена семейством RepoBench.

**Кому достался бюджет.** На Java Easy поднялся с 55,71% до 76,25% при среднем чтении 4,45 вместо трёх; Hard опустился с 32,97% до 20,99% при 1,55. Результат зависит от цели, заданной как суммарное покрытие: перенаправление ресурса выгодно в среднем и ухудшает поведение на трудных обращениях. Если половины Easy и Hard получают каждую собственную квоту ровно три, простой планировщик сохраняет преимущество на Java (16 421 против 15 963, +1,27 п.п., ДИ +0,53…+2,17), на Python остаётся 1 056 против 1 044 (+0,60 п.п., ДИ −0,87…+2,17). При очередях отдельно для каждого *точного* n модели размера и необученные функции по построению возвращают фиксированную тройку. Сложная смесь на Java при этом дала 15 898 против 15 963, −0,18 п.п. (−0,51…+0,16). Структурной смеси не удалось заметно улучшить выбор глубины среди одинаковых пулов. Исключить фиксированный размер пула из абляций в будущей статье было бы существенной ошибкой.

## Когда следующее обращение ещё неизвестно

В каждом репозитории начинаем с нулевого баланса. Поступление запроса пополняет его на три места. Для текущего n правило со списком p(r|n) вычисляет желаемую глубину по порогу, зафиксированному исключительно на Java HF. Читает хотя бы одно объявление, не может взять больше доступного кредита. Первая версия допускает баланс до 12. Суммарный расход на любом префиксе ≤3t, что проверено независимо для каждой группы и перестановки. Порядок событий в датасете не является рабочей хронологией; результаты усреднили по десяти заранее заданным SHA-перестановкам одних событий. Доверительные интервалы построены по проектам, каждая задача вносит единичный вес после усреднения десяти зависимых прохождений.

| Задачи | Политика | Покрытие | Средняя глубина | Разница к top-3, п.п. и 95% ДИ |
|---|---|---:|---:|---|
| Java | Постоянный резерв до 12 | 46,65% | 2,975 | +2,31 (+1,87…+2,66) |
| Java | Резерв до 2% квоты | 46,47% | 2,988 | +2,13 (+1,72…+2,45) |
| Python | Постоянный резерв до 12 | 49,69% | 2,628 | −2,58 (−3,86…−1,38) |
| Python | Резерв до 2% квоты | 52,26% | 2,987 | −0,02 (−0,17…+0,12) |

У первой политики покрытие на Python менялось между 49,37% и 50,03% в зависимости от порядка, на Java между 46,58% и 46,71%. На Python она расходовала 5,09 млн токенов. При том же среднем расходе случайное независимое от задачи распределение между top-2 и top-3 дало бы на 1,98 п.п. меньше покрытия; относительно реального постоянного top-3 система уступила. При одинаковом алгоритме банка необученная гармоническая функция показала 51,09% на Python, равномерная 47,51%, их фактические расходы также разнятся. На Java эффект обученной модели к равномерной +0,25 п.п. с интервалом, включающим ноль.

После раскрытия этих результатов поставили отдельную проверку сохранения бюджета. После t обращений в конкретном репозитории резерв ограничен min(12, floor(3t/50)). Тогда в любой момент потрачено как минимум 98% выданных мест. При t≤16 банк равен нулю. На Python 321 из 348 проектов содержит максимум 16 обращений; для 1 683 из 1 997 запросов политика по построению возвращает тройку. Восстановление покрытия Python к первой версии составило +2,56 п.п. (ДИ +1,44…+3,79). Java уступил первой версии −0,18 п.п. (−0,30…−0,08). Уточнение резерва мотивировано уже увиденным отрицательным результатом, новая независимая проверка необходима. Открытым остаётся распознавание полезной глубины в долгой истории одного проекта при сходном числе кандидатов.

## Какие фрагменты должны стоять первыми

Первая заранее зафиксированная проверка — изменение доверия к источникам с учётом согласия их выдач. Данный этап отвечает на другой вопрос, чем распределение мест. На 24 000 Java HF запросах изучали вероятность правильности каждого объявления, условную на весь набор конкурентов. Граф R4 и его контроль owner обучены на прежней отдельной Java-панели. Owner имеет доступ к истории обращения внутри данного кода, без ориентированных рёбер между разными объявлениями. Использовали их ранги и ранг Jaccard. Прямой линейный контроль использует обратные позиции, нормированные позиции и индикатор первого места для каждого источника. Гибкий аддитивный контроль включает 13 признаков ранга каждого источника. Адаптивное правило добавляет межисточниковые взаимодействия; placebo привязывает дополнительные колонки к неверным кандидатам циклическим сдвигом. Страты, ID правильного кандидата и название проекта исключены из признаков.

| Правило | @1 | @3 | @5 | MRR |
|---|---:|---:|---:|---:|
| Граф R4 | 6 663 | 15 963 | 23 045 | 0,37717 |
| Owner R4 | 6 152 | 15 167 | 22 437 | 0,36267 |
| Jaccard | 4 367 | 12 341 | 19 870 | 0,30676 |
| Необученный RRF k=60 | 6 021 | 15 280 | 22 694 | 0,36250 |
| Линейная смесь | 6 559 | 15 853 | 23 015 | 0,37453 |
| Гибкая аддитивная | 6 588 | 15 777 | 23 002 | 0,37489 |
| Адаптивная смесь | 6 606 | 15 756 | 23 076 | 0,37537 |
| Перемешанные взаимодействия | 6 584 | 15 713 | 23 012 | 0,37468 |
| Адаптивная без графового списка | 6 136 | 15 118 | 22 492 | 0,36213 |

На внешнем Java-архиве 36 000 запросов в 349 проектах, без совпадающих с 731 Java-проектами калибровки полных имён. Для заявленного основного исхода получено +47 попаданий к линейной модели, +0,131 п.п. (95% ДИ −0,015…+0,275), 345 выигрышей и 298 потерь. Двусторонний кластерный sign-flip p=0,102, с поправкой Holm по двум заранее заданным исходам p=0,203. К гибкому аддитивному контролю прирост +0,050 п.п. (−0,083…+0,185). К графу −0,158 п.п. (−0,329…+0,030). Удаление графового источника стоило 470 ответов, разница +1,306 п.п. (+0,901…+1,718). Наибольшее число попаданий @5 у адаптивной смеси, но +31 к графу совместимо со случайностью (−0,211…+0,339 п.п.). Данные поддерживают включение графового ранга и оставляют открытой замену самого ранжировщика.

## Приносит ли пользу семантика соседнего объявления

На 320 размеченных задачах HF обучили два оценщика отдельно для запросов в три и десять строк. Исходный граф и признаки его структуры одинаковы в контрольной прямой смеси и в экспериментальном расширении. Обе видят BM25, оценки owner, графа и действительного microsoft/unixcoder-base, а также его прямой cosine score и ранги. Расширение дополнительно передаёт сходство связанных узлов по входящим/исходящим рёбрам, учитывает неоднозначность названия типа, положение соседей и текст возле ссылки. Контроль сдвигает эти сообщения внутри запроса. Закрытая внешняя панель на этом этапе — 224 запроса по 56 в четырёх стратах, 81 проект; индивидуальные решения/веса запечатаны до оценки. Она является подмножеством общего Java-архива; веса для обеих нейронных постановок зафиксировали до открытия первичных внешних оценок R5. Сравнения двух панелей не являются независимыми репликациями. Все 640 воспроизведённых списков замороженного графа совпали с R4. На CPU в FP32 обработано 3 085 различных непустых токенизированных последовательностей за 671,6 с на пяти потоках. Независимая одиночная проверка девяти почти равных случаев ни разу не изменила порядок.

| Метод | @1/3/5, три строки | MRR | @1/3/5, десять строк | MRR |
|---|---:|---:|---:|---:|
| Только настоящий UniXcoder | 46 / 102 / 132 | 0,38435 | 30 / 84 / 139 | 0,33370 |
| Только граф | 42 / 103 / 142 | 0,37678 | 44 / 104 / 143 | 0,38941 |
| Смесь без энкодера | 31 / 98 / 138 | 0,35078 | 47 / 89 / 144 | 0,38245 |
| Прямая смесь | 43 / 101 / 144 | 0,38432 | 39 / 86 / 141 | 0,36253 |
| Сообщения соседей | 42 / 100 / 146 | 0,38016 | 35 / 91 / 138 | 0,35110 |
| Перемешанные сообщения | 38 / 103 / 145 | 0,37504 | 45 / 90 / 141 | 0,37891 |

На трёх строках сообщения − прямая смесь дали −0,45 п.п. (95% ДИ −3,27…+2,13), 6 выигрышей, 7 потерь, raw и Holm p=1. На десяти строках получили −1,79 п.п. (−5,08…+1,00). Вторично, прямая смесь с энкодером относительно той же смеси без энкодера дала на трёх строках +5,36 п.п. (+1,71…+9,48), на десяти −3,57 п.п. (−6,93…0,00). Небольшая выборка и различия окон не позволяют считать энкодер универсальным методом улучшения. Речь о retrieval, Qwen, Codex и другие решатели в этих измерениях не запускались.

## Проверяемость и отношение к литературе

Три базовых Java-списка внешней панели независимо совпали с результатами R4 по всем четырём метрикам, что проверяет привязку правильных кандидатов. При разработке первого рангового скрипта программа первоначально читала поле ширины окна как метку; контроль структуры R4 показал ошибку до расчёта тестовых исходов, отладочные предсказания отброшены. Финальная версия берёт эталоны напрямую из исходных обучающих Parquet и для каждой из 24 000 строк проверяет эквивалентность вычисленной reciprocal rank сохранённому независимому результату R4. У первоначального оптимизатора исчерпался лимит итераций; предел повышен до открытия теста. Правило обрезки краевой пустой строки в повторной сборке нейронных признаков исправлено с проверкой 640/640. Записи исправлений и хеши сохранены. Общие агрегаты базовых систем на Java-архиве уже существовали; перенос относится к новым решениям с зафиксированными весами и общедоступным заданиям. В R4 отдельное воспроизведение Jaccard на исходном архиве не совпало с пятью табличными числами ICLR на сотые доли процента. Международный рекорд или превосходство над всеми методами памяти из этой проверки не следуют.

Постановка и метрики выдачи соответствуют retrieval-компоненте RepoBench. Нейронный контроль использует публичный UniXcoder, базовое смешивание списков воспроизводит классический Reciprocal Rank Fusion. Важный контроль обученной калибровки мотивирован работой о роли сочетания нормированных оценок и рангов в гибридном поиске. Применение этих идей к собственно чтению в процессе длинной сессии требует временных трасс, сопоставимого вычислительного бюджета и измерения решённых задач. [Liu et al., RepoBench, ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/d191ba4c8923ed8fd8935b7c98658b5f-Abstract-Conference.html) · [Guo et al., UniXcoder, 2022](https://arxiv.org/abs/2203.03850) · [Cormack et al., SIGIR 2009](https://doi.org/10.1145/1571941.1572114) · [Bruch et al., An Analysis of Fusion Functions for Hybrid Retrieval](https://arxiv.org/abs/2210.11934)

Наблюдение о выгодной переменной глубине допускает эксперимент с прямой причинной проверкой на сведениях из хронологии реального агента. Фиксировать длину списка, удерживать такие же токены на каждой задаче и явно измерять цену ухудшения трудных задач важно уже на стадии протокола. Для короткой истории простая тройка остаётся сильным контролем.
