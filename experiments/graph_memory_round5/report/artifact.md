# Какие наблюдения сохранять кодовому агенту
> Самый воспроизводимый результат серии — при записи вывода терминала сохранять, какому файлу и каким строкам принадлежит увиденный текст. Этот приём сработал на двух непересекающихся наборах задач.
Когда агент готовит изменение, ему часто приходится снова открыть код, который он недавно читал. Мы воспроизвели публичные журналы Kimi по шагам и ограничили сохранённое состояние 4 КиБ. У прежней памяти был адрес сведений из редактора. Новый вариант умеет также извлекать адреса из понятных команд чтения и их результатов. К будущим действиям он обращается только на этапе оценки.
@ 5 3 3 3
| Панель | Блоков в тесте | Только редактор | Добавлена адресная запись терминала |
| Основная, 112 задач | 253 | 112 (44,27%) | 173 (68,38%) |
| Новые 98 задач | 206 | 73 (35,44%) | 121 (58,74%) |
Измеряется возможность вернуть **весь точный текст** старого блока по тому файлу и диапазону, который агент вскоре исправит. На второй панели выигрыш составил 23,30 процентного пункта, 95% интервал по задачам от 17,45 до 29,70. На тех же данных простое вытеснение по давности с правильно записанными адресами восстанавливает 119 блоков против 121 у графовой памяти.
Когда Qwen сама называла следующую позицию с допуском в пять строк, редактор дал 17 попаданий из 96, терминальные выдержки — 28, те же выдержки с адресами — 31. Разность последних двух вариантов пока неопределённа.
Ещё один результат касается бюджета чтения. При одинаковом суммарном числе выданных фрагментов покрытие эталонных объявлений выросло на Java и Python, но на трудных задачах общей очереди оно ухудшилось. В отчёте раздельно приведены результаты по поиску, выбору действия и генерации, а также их сопоставимость с опубликованными системами.

# Что именно измеряет память
> Когда агент обращается к памяти, он выбирает источник, решает, сколько из него прочитать, и применяет увиденное в коде. Для каждой операции у нас свой проверяемый исход.
@ 3 5 5
| Операция | Что получает система | Что измеряем |
| Записать действие | Завершившиеся вызовы инструментов в журнале Kimi | Сохранился ли целиком исходный текст блока, который агент позднее заменил |
| Выбрать адрес | Локальный префикс и доступные объявления Java или Python | Позиция эталонного объявления. Top-1, покрытие при ограниченном бюджете, MRR |
| Прочитать и применить | Одинаковый генератор и разные представления тех же объявлений | Точное совпадение строки, сходство текста и F1 имён. Для CrossCodeEval применяем функции авторов |
Эксперименты с кодом выполнялись на локальной RTX 3090, Qwen3.8-27B в формате UD-Q4_K_M, с отключённым thinking и жадным декодированием. Для поисковых сравнений веса графа и UniXcoder зафиксированы, подсчёт шёл на CPU. Всего выполнено 2 004 физических вызова генератора, 1 337 872 входных токена и 31 687 выходных. Одинаковый запрос внутри панели декодировали один раз. Хеши связывают исходную задачу, текст запроса и необработанный ответ.
Парные сравнения выполнялись на одних заданиях. Где один проект давал несколько строк, интервалы поиска пересчитывались по проектам. В опыте записи единицей повторной выборки служила задача. Оценки следующей строки на RepoBench-R образуют отдельный эксперимент. Полный тест Java CrossCodeEval рассматриваем отдельно.
~ [Структура заданий RepoBench](https://proceedings.iclr.cc/paper_files/paper/2024/hash/d191ba4c8923ed8fd8935b7c98658b5f-Abstract-Conference.html) · [CrossCodeEval, данные и оценка](https://github.com/amazon-science/cceval) · [Веса генератора](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF)

# Что теряла память после чтения кода в терминале

> Если записывать прочитанную строку вместе с путём и её номером, память в 4 КиБ сохраняет весь код следующей правки в 173 случаях из 253. Прежний сбор только через редактор давал 112.

На каждом четвёртом действии Kimi K2 Instruct запечатывали состояние, затем искали первую правку в следующих четырёх действиях. В оценку входили подтверждённые замены с однозначно восстановимым прежним текстом. Распознаватель связывал с адресами только простые чтения файлов, подтверждённые в двух полях исходной трассы. В 277 действиях он записал 10 603 строки, включая повторные чтения.

@ 6.6 3.3 3.3
| Что и как сохранялось | Полных блоков | Доля |
| Редактор, графовое вытеснение | 112 / 253 | 44,27% |
| Редактор и терминал, верный адрес | 173 / 253 | 68,38% |
| То же, адрес сдвинут на строку | 107 / 253 | 42,29% |
| Верный адрес, обычное вытеснение LRU | 172 / 253 | 67,98% |

Прибавка составила 24,11 п.п. (95% ДИ по задачам +18,15…+31,36), выигрыш наблюдался во всех восьми репозиториях. С тем же входом разница между графовым вытеснением и LRU равна одному случаю. Без ограничения памяти непосредственно перед правкой сохранялись 118 блоков из 253. Из остальных 135 уже 89 целиком встречались в терминальных ответах. Это ретроспективная оценка доступной информации. При принятии решений будущая правка была скрыта. Измерена доступность текста по адресу; влияние на решённые задачи SWE-bench ещё предстоит установить.
В независимой проверке соседних строк подтвердился 481 из 487 новых адресов. Все шесть расхождений возникли в одном файле Django после команды терминала с вставкой трёх строк. Внешние изменения файла остаются ограничением.

# Адресная запись помогла на новых задачах

> При общем лимите памяти 4 КиБ агент мог восстановить весь исходный блок для 121 из 206 будущих правок. Раньше это удавалось в 73 случаях. Прирост составил 23,30 процентного пункта.

Взяли 98 новых задач SWE-bench Verified из пяти проектов. Ни одна задача ранее не оценивалась на двух панелях Kimi. Повторили тот же алгоритм без настройки. В ходе работы он сохраняет строку из уже показанного терминального вывода, путь к файлу и номер строки. Если редактор меняет файл, память обновляет адреса.

Её разница с более сложным правилом составила всего две правки. На этой выборке основную пользу принесло сохранение самого наблюдения по правильному адресу. # Почему номер строки помогает и когда он устаревает
> Полезное наблюдение содержит три разные вещи: текст, место, где его прочитали, и момент чтения. Они перестают быть взаимозаменяемыми после изменения файла.
Если агент выполнил простое чтение непрерывного диапазона с первой строкой a, то строка вывода с нулевым смещением j относится к строке a + j. Это правило применимо, если известны файл и рабочий каталог и вывод не обрезан. Для нумерованного вывода поиска позицию берём из результата. При подтверждённой замене u старых строк на v новых строки ниже правки меняют адрес на v − u. Такие переходы можно обновлять по мере наблюдений, используя память только уже открывавшихся файлов.
Практическая проверка дала 481 совпадение из 487 дополнительных адресов на первой панели и 370 из 370 на второй. Эти знаменатели включают только строки, которые удалось позднее независимо проверить рядом с подтверждённой правкой. Все шесть ранних расхождений пришлись на один файл Django. Между чтением и проверкой в журнале есть команда редактирования этого файла. Две строки сместились точно на три позиции, что согласуется с заменой одной строки четырьмя.
У записей терминала не всегда раздельно доступны код завершения и поток ошибок. Произвольная программа может изменить файл вне редактора. Для такого случая проверяемое развитие метода — помечать адрес устаревшим, после чего подтвердить его дешёвым повторным чтением. Цену такого чтения нужно учитывать при сравнении.

# Сможет ли модель сама выбрать место правки
> На 96 задачах из восьми проектов Qwen получила описание ошибки и журнал до среза. Модели требовалось самой назвать файл и строку следующей реальной правки Kimi. Будущий адрес в запросе отсутствовал.
Из ранее пригодных срезов взяли по одному на задачу. В течение следующих четырёх действий в журнале должна была произойти подтверждённая правка. Показали три формы одной истории. В двух ветвях с терминалом команды, текст наблюдений и их порядок были одинаковы. В последней к фрагментам добавлялся вычисленный адрес. Набор строк подбирался совместно при потолке в 900 токенов. В 65 случаях адрес изменил фактический промпт.
@ 5 3 3 3
| Что видит решатель | Верный файл | Файл и строка ±5 | Точная позиция |
| Последний адрес, простое правило | 68 | 8 | 2 |
| Qwen, только редактор | 80 | 17 | 10 |
| Qwen, редактор и вывод терминала | 80 | 28 | 13 |
| Qwen, те же строки с адресами | 81 | 31 | 13 |
В основном сравнении добавление адресов дало семь выигрышей и четыре потери по допуску ±5. Разность +3,13 п.п., 95% интервал по задачам от −3,13 до +10,42, p = 0,55. Сам показ вывода терминала дал 13 выигрышей и две потери относительно редактора. При повторной выборке задач этот контраст заметен, точный тест по восьми проектам даёт p = 0,0625. Сходство с действием прежнего агента измеряет локализацию. Тесты конечного патча в этой постановке не запускались.

# Откуда берётся выигрыш при общем бюджете
> Если на каждую задачу приходится одно правильное объявление, полезность следующего места в выдаче можно выразить через вероятность того, что ответ находится именно на этой позиции.
Пусть pᵢⱼ — условная вероятность встретить верное объявление на позиции j у задачи i. При чтении первых kᵢ объявлений ожидаемое число покрытых запросов равно сумме всех pᵢⱼ по j от 1 до kᵢ и по всем задачам. Выбор kᵢ ограничен общим бюджетом слотов. Независимость ответов разных задач для формулы не нужна. Требуется, чтобы вероятности относились к тому порядку, в котором действительно выдаётся память.
Если предельные вероятности убывают с глубиной, после обязательного первого слота достаточно каждый раз добавлять доступное место с наибольшей вероятностью. Доказательство — обмен местами. Последний слот меньшей ценности в любом другом допустимом решении можно заменить доступным слотом большей ценности, сохранив бюджеты и префикс каждого списка. Повторение таких обменов приводит к жадному решению. В реализации соседние нарушающие порядок оценки усредняются.
Эта модель объясняет, почему правило может перераспределять чтение к коротким спискам. Оптимальность относится к оценённому покрытию и одинаковой цене слота. Токены различаются по цене, а полезность второго примера для генератора может зависеть от первого. Поэтому в серии измеряем фактические токены и отдельно проверяем конечную строку Qwen.
RepoDistill уже обучает распределению бюджета сжатия внутри контекста одной задачи. ACToR исследует момент дополнительного поиска при генерации критического токена. Здесь проверяется более узкий вопрос о распределении числа чтений по потоку задач и о цене такого решения для трудных случаев. [RepoDistill, Findings ACL 2026](https://aclanthology.org/2026.findings-acl.217/) · [ACToR, препринт](https://arxiv.org/abs/2609.01601)

# Что меняется, когда запросы приходят по одному

> При переносе на Python последовательное правило сберегало слишком много мест. Ограничение резерва вернуло покрытие почти к исходному уровню.

Каждый новый запрос добавляет три места в отдельный баланс своего репозитория. Читатель видит текущий список и остаток; он может взять больше трёх после предыдущей экономии. Порог полезности обучен на Java. Проверили десять порядков поступления запросов. В таблице показаны среднее покрытие и число выданных объявлений.

@ 6.4 3.1 3.1
| Правило | Java, % / мест | Python, % / мест |
| Всегда три объявления | 44,34 / 3,00 | 52,28 / 3,00 |
| Можно накопить до 12 мест | 46,65 / 2,98 | 49,69 / 2,63 |
| Резерв до 2% выданной квоты | 46,47 / 2,99 | 52,26 / 2,99 |

Первое правило накопления повысило покрытие Java на 2,31 п.п. (95% ДИ по проектам +1,87…+2,66), на Python потеряло 2,58 п.п. (−3,86…−1,38). После этого ввели ограничение: к любой точке истории использовано минимум 98% квоты. На Python разница с фиксированной тройкой сократилась до −0,02 п.п. (−0,17…+0,12). Там 321 из 348 проектов содержат не более 16 запросов, для которых второе правило гарантированно выдаёт три объявления. Порядки синтетические; для вывода о поведении работающего агента нужны реальные хронологические трассы. Ограничение резерва выбрано после первой проверки.

Точки показывают изменение доли запросов, в которых агент получил эталонное объявление. Отсчёт ведётся от постоянной выдачи первых трёх объявлений того же графа. Отрезки — парные 95% интервалы повторной выборки проектов. В двух верхних строках число выданных объявлений совпадает в каждом пакете. Прямой вызов с явным типом получателя или создание объекта найдено в 21 из 79 случаев A и в 11 из 64 случаев B. Простое упоминание в типе или объявлении встречалось в 32 и 31 случаях соответственно. # Где проходит граница научного вклада
> Привязка опыта к объектам репозитория уже исследуется. Наш результат сужает вопрос до того, какие сведения из фактически выполненного действия можно записать, а затем проверить независимо от модели.
SWE-agent показывает путь и номера строк в специализированном редакторе. MemTrace сохраняет неизменяемые записи хода работы, связывает их с файлами, символами и тестами и проверяет актуальность перед восстановлением. Авторы оценивают конечное решение задач на DeepSWE, SWE-EVO и SWE-Milestone. В SDK OpenHands полную длинную выдачу терминала можно сохранить отдельно, а в контекст передать сокращение. Это три подходящих ориентира для сравнения взаимодействия агента с наблюдениями. [SWE-agent](https://arxiv.org/abs/2405.15793) · [MemTrace, препринт](https://arxiv.org/abs/2610.04838) · [Код MemTrace](https://github.com/theseus-labs-rsi/MemTrace) · [Инструмент терминала OpenHands](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-tools/openhands/tools/terminal/definition.py)
В нашей постановке терминал и редактор читают один и тот же меняющийся файл. Даже без заранее построенного индекса некоторые результаты терминала можно обратимо связать с местом чтения. Известный допустимый номер строки позволяет восстановить блок; намеренно сдвинутый адрес и простой кеш с теми же входами проверяют конкурирующие объяснения.
Показатели действующих агентов из публикаций нельзя перенести в таблицу восстановления блоков. Для заявления о преимуществе всей системы нужны один решатель, одни открытые задачи с исполняемыми тестами, одинаковые права на чтение файлов, одинаковый бюджет и воспроизведение сильной памяти в том же harness.

# Что развивать для статьи
> Первое направление — запись наблюдений терминала с проверяемым источником и сроком действия адреса. Для него уже есть повторение эффекта на новых задачах. Второе — выбор глубины чтения при ограниченном бюджете.
**Запись и повторное чтение.** На свежем наборе задач следует передать одному и тому же решателю три варианта памяти: полный журнал с обычным поиском, компактный LRU с привязкой к файлу и версии и граф со строго теми же наблюдениями. Ветви должны иметь одинаковый бюджет токенов и одинаковое право повторно открыть файл. Основной исход — доля принятых патчей по скрытым тестам. Дополнительно измерять число повторных чтений, их стоимость, возврат устаревшего кода и частоту отказа от сомнительного адреса. При наблюдаемой записи в файл полезно испытать точное обновление координат и более простой сброс изменившегося диапазона.
**Распределение бюджета.** Повторить опыт на естественном порядке действий вместо перестановок запросов, выравнять токены и установить нижнюю границу качества на трудных задачах. Сравнение с фиксированной глубиной и правилом по одной длине списка покажет, даёт ли что-либо текущее состояние работы агента.
Для планирования парного теста конечных решений при 20% расхождений и интересующем сдвиге 5 п.п. нормальное приближение даёт около 628 независимых задач при мощности 80% и двустороннем уровне 0,05. Это иллюстрация размера выборки. Для реального запуска нужны оценка расхождений по пилоту и поправка на повторные задачи одного репозитория. Размер выборки для качества исправлений следует рассчитывать отдельно от размера выборки для поиска и восстановления блоков.
