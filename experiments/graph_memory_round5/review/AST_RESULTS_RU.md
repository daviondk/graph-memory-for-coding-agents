# Что в действительности означает найденное ребро

18 ноября 2026, архивная выборка Java для серии 5. Мы разобрали исходные фрагменты Tree-sitter и проверили выбранное вхождение имени по его синтаксической роли. В A — по одному заданию из 128 репозиториев, в том числе 79 со ссылкой-кандидатом. В B — 64 других репозитория с различающимися входами для edge и local. Программа использует только поля входного кода. Поиск фрагмента, номера строки и соответствующие хеши сохранены отдельно. [Грамматика Java](https://github.com/tree-sitter/tree-sitter-java)

| Тип создаваемого объекта | 3 | 2 |

Для A лишь 21 из 79 фрагментов (26,6%) явно демонстрируют создание выбранного типа или вызов метода у получателя с точным именем. Для B — 11 из 64 (17,2%). На полном знаменателе A это 21 из 128 задач, 16,4%. У всех 143 фрагментов дерево получено без синтаксических ошибок. Оригинальное написание восстановлено из целевого объявления, поскольку поиск привёл ключ графа к нижнему регистру.

Классификатор проверяет синтаксис. Имя переменной в другом регистре может указывать на объект нужного типа. Имя получателя с тем же написанием может, напротив, относиться к другому символу. Для разрешения таких случаев нужны таблица символов, импорты и типы выражений. Сигнатура, аннотация типа и обращение к полю также могут быть полезны генератору. Ни одна из этих долей сама по себе не измеряет вероятность правильного ответа.

## Стоимость одной дополнительной проверки

На местном CPU после разогрева проверили 143 пары «определение — место использования» по пять раз в перемешанном порядке, без повторного использования уже построенного дерева. Медиана по примерам составила 1,00 мс в A и 0,55 мс в B. 95-й процентиль — 7,07 и 3,21 мс. Измерялось восстановление имени в объявлении и разбор одного известного места использования при нахождении обоих текстов в памяти. Это лишь добавка после поиска ссылки. Измерение всей системы, индексации, декодирования, затрат на запись и задержки запроса целиком потребовало бы отдельного теста. Сырые параметры и вычисления находятся в ast_cost.py и ast_cost.json.

## Сколько подходящих строк осталось в уже доступной памяти

Проверили все остальные объявления при том же первом узле графа. В A графу были доступны 1 388 других кандидатов суммарно по задачам. Прямое использование выбранного типа есть в 32 из 128 задач, лексический выбор строки показал его в 21. Во всех 11 дополнительных задачах такое использование нашлось в том же фрагменте, из которого уже бралась подсказка. В B просмотрено 627 кандидатов. Подходящая строка есть в 21 из 64 задач, исходно выбрана в 11. В пяти из десяти дополнительно открытых задач она также находится в уже выбранном фрагменте, в пяти потребуется другое видимое объявление.

Ограничение источников первыми четырьмя узлами графового ранжирования понизило доступность до 22/128 и 12/64. Поиск подтверждает конкретную причину потери сведений при упаковке. После этого измерения подготовлена панель G, где новые строки получили реальные ответы модели. На A изменения относительно исходного ребра дали один выигрыш и одну потерю, на B число точных строк осталось тем же. Результаты представлены в AUDIT_RESULTS_RU.md и reader/G_results.json. Все адреса и номера строк получены программой witness_supply.py и сохранены в witness_supply.json.
