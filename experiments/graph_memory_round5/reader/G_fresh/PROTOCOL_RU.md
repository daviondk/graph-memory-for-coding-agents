# Выбор синтаксически подтверждённого места использования

Панель G — дополнительный эксперимент после диагностики роли исходных 143 упоминаний и измерения доступности альтернативных строк. Выбор ветви фиксируется по входному коду. На момент записи протокола A и B ещё не имели замков ответов; C уже запечатана, целевые строки A/B/C не открывались рецензентом. Гипотеза сформулирована после просмотра распределения синтаксических ролей. Проверка проводится на ранее выбранных 128 примерах A и 64 обогащённых примерах B. Состав ограничивает переносимость.

Для фиксированного первого узла восстановить правильное написание имени объявленного типа. Сильное свидетельство — совпадающий с ним идентификатор в позиции непосредственного получателя вызова метода или тип в создании объекта. Для статического синтаксического анализа используем Tree-sitter. Динамическое связывание и полный Java type checker не применяются. Источники возможных строк — прежний набор видимых кандидатов, исключая сам первый узел. Если прежняя строка edge уже сильная, её запрос переиспользуется дословно. Если возможна сильная строка из того же источника, оставляем источник; иначе берём источник с минимальным графовым рангом среди подходящих. Внутри него среди сильных строк выбираем по исходному лексическому сходству предыдущих трёх строк и самой строки с текущим префиксом, при равенстве берём раннюю. Если ни одной сильной строки нет, подаём исходную ветвь local без изменений.

Когда выбрано сильное использование, объявление получает до 145 токенов, само использование и две следующие строки до 100, с тем же разделителем и суммарным потолком 256 токенов, как в edge. Для local используется его обычный потолок в 256. Фактические длины измеряем отдельно. Системный промпт, seed задачи, параметры декодирования и модель унаследованы от A/B. Запросы, совпадающие с ранее запланированными, получают тот же физический ответ после проверки сериализованного тела запроса. Новые запросы исполняются тем же infer.py на том же сервере.

Показать EM, ES, F1 идентификаторов и реальные длины промптов. Основное исследовательское сравнение с local в A и B привести отдельно. Вторичные — парные сравнения с edge, отдельно среди изменившихся запросов, среди всех и, описательно, среди 21 задачи с найденным дополнительным местом использования. При близких или нулевых разностях оценить информативность интервалов. Суммарное число запросов отделять от логических сравнений.
