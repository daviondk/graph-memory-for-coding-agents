# От выбора объявления к выбору свидетельства для генерации
Замораживаем метод, исходные и контрольные условия до вызовов генератора и до чтения next_line. Дата и SHA фиксируются при подготовке. Задача — следующая непустая строка Java из оригинального архива RepoBench-R (ICLR), где четвёртая серия уже оценивала поиск. Эти репозитории не встречались в обучении графа и в предыдущих прогонах генератора Java. Ранги каждого объявления берутся из готового запечатанного до оценки файла archive.pred.jsonl.gz. На них не доучиваемся. Контексты из официального набора уже предоставлены, наблюдение кандидата — допущение нашей модели памяти. Не измеряем обнаружение файлов по всему репозиторию.
Панель A — до 128 задач (32 на каждую комбинацию first/random × easy/hard) по хешу, по одному на репозиторий. Панель B — до 64 задач (по 16 на страту) из остальных проектов, условие включения — наличие видимого использования выбранного типа в другом кандидате и отличающегося фактического стимула. Для получения воспроизводимого компактного пула оставляем заранее три строки данных на проект и страту по хешу. Страты циклически получают доступ к проектам. Отбор использует только видимые входы; доля успехов B относится к событиям с таким ребром. Безопасность содержимого проверяется до генерации по пути, видимому коду и входным кандидатам; Java-программы не исполняются.
Те же локальные Qwen3.8-27B UD-Q4_K_M и токенизатор, температура 0, 80 токенов вывода, без thinking. Модели доступны до 30 локальных строк (1024 токена) и до 256 токенов внешних наблюдений. Код программы сохранён в evidence.py. head — начало top-1, local — заголовок и наиболее сходное окно внутри того же объявления. edge — часть бюджета top-1 получает видимое место применения его типа из другого кандидата, взятое по сходству предшествовавших строк с текущим кодом. При отсутствии ссылки возвращается точное local. Для four_head/portfolio берём одни и те же четыре объявления графа: в первой политике отдаём начала, во второй — заголовок и подходящие строки внутри каждого. empty — без внешних сведений. B получает head/local/edge. Одинаковые промпты в одной панели считаются один раз, позиция между методами перемешана по хешу, seed один на задачу. Сохраняем входы, реальные ответы GPU, фактическое потребление токенов и причины завершения.
Основной контраст — edge против local на A по доле точного воспроизведения авторской строки после снятия пробелов по краям. Заранее выбранная проверка механизма — тот же контраст на B. В каждой панели сопряжённый двусторонний точный тест Мак-Немара, 95% парный bootstrap по репозиториям; для двух основных проверок показываем поправку Холма. Прочие сравнения и метрики вторичные: среднее сходство строк (нормированный Indel, 0–100), F1 идентификаторов, длина и точное совпадение авторской строки с видимым контекстом. Бюджет одинаков как потолок, реальную стоимость приводим отдельно. Нулевая оценка при малом числе расхождений не доказывает эквивалентность. На уровне статей сравнимы принципы и метрики; это пользовательская задача генерации на строках RepoBench-R, отдельная от официального RepoBench-P.
