# Адресная запись наблюдений из терминала
По опубликованным действиям Kimi K2 Instruct мы проверили, теряется ли информация в момент поступления в память, ещё до ранжирования и вытеснения. При общем лимите 4096 байт добавление адреса к наблюдению из терминала повысило полное восстановление кода следующей правки с 112/253 до 173/253. Та же поправка увеличила результат простой памяти LRU со 111 до 172. Такой результат делает систему приёма наблюдений приоритетным объектом следующих исследований. Сам вклад графового вытеснения на равноинформированном входе составил лишь одно дополнительное полное восстановление.

## Данные, задача и отсечка

Взяли ровно 112 траекторий предыдущей панели из публичной подачи 20250804_codesweep_sweagent_kimi_k2_instruct. Проверили 112 SHA-256 исходных .traj, обработали 344 752 765 байт. Ни одна команда из истории не исполнялась. Использовали наблюдения до фиксированной отсечки после каждого четвёртого действия. Затем разметка находила попытку изменения файла в установленном в R5 окне до четырёх шагов. В оценку включали подтверждённую замену, когда новый текст можно однозначно локализовать в пронумерованном результате редактора и обратить замену, восстановив точное содержание строк на старом адресе. В итоге 3386 действий, 778 контрольных точек, 253 оценимых изменения в 104 задачах из 8 репозиториев. При вычислении целевого признака все строки блока должны полностью совпасть, включая отступы и пробелы. Удельная доля совпавших строк усредняется сначала внутри изменения. Перед выбором нового метода были известны агрегаты предыдущей серии; результаты этой панели разведочные.

Раньше только редакторские наблюдения имели структурированный адрес. В дополнение из 1456 остальных действий 1435 удалось сопоставить с непосредственным tool-ответом в истории модели. В четырёх случаях сопоставление действий не удалось, ещё для 17 не выполнены условия однозначной связи вызова и ответа. Допускались только совпавшие строки двух полей (trajectory.observation и tool.content). Далее статический разборщик проверял простые чтения без конвейера или перенаправления с однозначным путём или номером. Для команды с явным диапазоном проверяется корректность и полнота подтверждённого вывода в пределах указанного диапазона, отбрасываются известные метки обрезки. Номерные результаты поиска имеют отдельные правила. Один бит сообщает, соответствует ли текущая директория корню репозитория; неизвестная директория запрещает вывод относительного пути. Приняты 10 603 вывода строк в 277 событиях, из них 10 113 по диапазону или порядку строк в обычном чтении и 490 по номерному результату поиска. Это количество записей, включая повторения. За пределами поддержанных команд адрес из текста не выводили.

Поток редактора, кодек, общий словарь и политика переноса незатронутых строк одинаковы для основного контроля и экспериментального метода. При чтении новой строки добавляем ребро от пути и координаты к наблюдённому тексту с номером шага. При наблюдаемом успешном изменении существующее правило использует подтверждённый результат для передвижения сохранившихся строк. Для нового чтения в ограниченном хранилище обновляются дата последнего просмотра пути, точка просмотра и счётчик наблюдений тем же способом, что и при обычном запросе редактора. Никакой индекс исходного репозитория не строится. В момент чтения политика использует текущий результат вызова и своё прежнее состояние. Следующая правка, её адрес, аргументы и ответ доступны только процедуре оценки запечатанных состояний.

## Разбор прежних промахов

| Где обнаруживается точный текст | В момент исходного среза, 138 промахов | Непосредственно перед правкой, 135 промахов |
|---|---:|---:|
| Когда-либо полностью встречался по исходным адресам редактора | 0 | 0 |
| Ранее целиком напечатан редактором в том же файле | 1 | 1 |
| Ранее целиком напечатан редактором в другом файле | 0 | 0 |
| Непрерывный блок обнаружен в выводе другого инструмента | 67 | 89 |
| Все строки встречались по отдельности | 2 | 3 |
| Хотя бы одной точной строки нет в доступных наблюдениях | 68 | 42 |

Категории взаимоисключающие, соответствие проверяется в порядке сверху вниз. При свободном поиске по всей истории до события учитывались и строки без адреса, с явно отделяемым префиксом позиции и повторявшийся текст; текст самой будущей правки разрешён для ретроспективного сравнения. Этот оракул характеризует наличие данных и завышает возможности при реальном поиске. Во всех 135 блоках есть хотя бы одна нетривиальная строка (не менее восьми букв или цифр). Отсутствие строки в доступных двух полях публичной истории допускает неполноту вывода и неподдержанное форматирование. Добавление литералов старых аргументов редактора не сделало полностью покрытым ни один дополнительный остаточный блок по критерию отдельных строк. Перепривязка старых редакторских значений при отсутствии текущего адреса не изменила результат.

## Проверка причинного использования адресов

| Правило | Весь блок на исходном срезе | Доля точных строк | Весь блок прямо перед правкой |
|---|---:|---:|---:|
| Редактор без вытеснения | 115/253 | 46,71% | 118/253 |
| Редактор и адресованные наблюдения без вытеснения | 178/253 | 71,89% | 198/253 |
| Смещение каждой добавленной строки на +1 | 110/253 | 44,55% | 111/253 |
| Историческое значение редактора для пропущенного адреса | 115/253 | 46,71% | 118/253 |

На исходном срезе добавились 63 точных блока без потерь, +24,90 п.п., парный 95% ДИ по задачам +18,79…+32,24. В последний момент перед правкой восстановились 80 из 135 прежних промахов, +31,62 п.п. к исходному восстановлению, ДИ +25,00…+39,49. Это другое окно наблюдения; часть вызовов чтения происходит уже после первоначального среза. Оракул полного терминального блока (89) не следует выдавать за результат программы (80 дополнительных полных попаданий во всей группе 135).

При проверке дополнительного адреса строго последующим editor view доступных наблюдений не оказалось. До открытия целевых исходов добавили отдельную проверку неизменённых соседних строк, показанных в подтверждении правки. Обратный сдвиг координаты для стоящей после правки строки известен по величине изменения; изменённый интервал исключён. Отдельные значения, которых у первого метода не было или которые отличались от его текста, оказались верны в 481 из 487 проверок. В контрольном сдвиге верны 6 из 450. Проверяемые значения и знаменатели различны по построению, эти проценты нельзя приравнивать к общей точности адреса на всей трассе. Наличие шести ошибок показывает, что синтаксическое распознавание и поддержание адреса не безошибочны.

## При равном лимите памяти

Внешний размер каждого состояния ≤4096 байт при каждом шаге. Один байт хранит флаг текущей директории; JSON/Zstandard-15, текст, время, номера, пути и остальная запоминаемая история делят 4095 байт. Для всех вариантов одинаковы текущий вход, статическое условие задачи, фиксированный словарь сжатия и общие параметры соответствующего правила. Временная память чтения текущего ответа и код программы не относятся к этому лимиту. Полученный в ходе воспроизведения полный файл трассы не доступен через интерфейс политики, алгоритм получает ровно текущее событие с уже проверенной связью tool-вызова и результата. Состояние между шагами заново восстанавливается из ограниченного блоба. У основной ветви без терминала все 253 индивидуальные метки совпали с предыдущими 4096 байтами без нового флага.

| Вытеснение | Вход | Точных блоков | Доля точных строк |
|---|---|---:|---:|
| Прежний cal_neighbor | Редактор | 112/253 | 45,52% |
| Прежний cal_neighbor | Редактор и корректные адреса | 173/253 | 69,91% |
| Прежний cal_neighbor | Редактор и адреса +1 | 107/253 | 43,37% |
| LRU с известными адресами | Редактор | 111/253 | 45,13% |
| LRU с известными адресами | Редактор и корректные адреса | 172/253 | 69,52% |

Первичный для анализа ёмкости контраст дал +24,11 п.п. (95% ДИ по задачам +18,15…+31,36), 61 выигрыш и 0 потерь, улучшение затронуло 49 задач. При повторном отборе целых репозиториев ДИ +16,10…+33,83. Во всех восьми проектах суммарная разница положительна, точный двусторонний тест знаков с переворотом на уровне проекта даёт p=0,0078125. Для LRU тот же метод приёма добавил 61 правильный блок (ДИ +18,15…+31,20 п.п.). Разница cal_neighbor относительно LRU при одинаковом адресованном входе +0,40 п.п. (−0,87…+1,80); 3 выигрыша, 2 потери. Данные поддерживают причинный эффект более полного структурированного входа в этом воспроизведении. Они не дают основания приписывать все 61 попадание новизне графового алгоритма. Результирующая мера касается возможности вернуть конкретное наблюдение при известном пути и позиции. Изменения числа повторных чтений и успешно решённых задач потребуют запуска действующего агента.

## Ограничения адреса и проверка шести расхождений

Все шесть ошибок среди 487 проверявшихся добавленных адресов приходятся на одну замену в Django, задача django__django-16560, редакторский шаг 59, файл django/db/models/constraints.py. На шаге 56 зафиксирована команда sed -i в этом же файле с заменой одной строки четырьмя. Такие операции адаптер не переносит в карту текущих адресов. При последующей печати содержимое настоящих строк 95 и 98 совпало с сохранёнными значениями строк 92 и 95, что соответствует сдвигу на три места. Это объяснение согласуется с тремя добавляемыми переводами строк. Полного снимка всего файла между этими шагами и проверенного exit status для команды нет; единственную причину каждого из шести несовпадений по отдельности установить невозможно. Ранее в том же файле встречались и другие sed -i. Файлы disagreements.json и trace_reason.json фиксируют шаги, координаты и хеши, inspect_disagreements.py и trace_reason.py восстанавливают этот диагноз без исполнения команд из логов.

Проверка равенства текста в trajectory.observation и связанном tool.content означает, что агенту действительно показывали строку через эти поля. В текущей проекции нет раздельных потоков stdout/stderr или надёжного типизированного exit code. Программа фильтрует известные маркеры обрезки и неоднозначное форматирование. Она не проверяет успешность bash-команды как отдельное условие. Короткое диагностическое сообщение, повторённое обоими полями, при распознанной форме cat/sed/head теоретически может получить неверный адрес. Для редакторских замен, напротив, сохраняется прежняя явная проверка подтверждения замены.

При инициализации проект предполагает, что shell находится в /testbed. Память несёт один байт с тем, известно ли совпадение с корнем. Распознанные cd/pushd/popd делают путь неопределённым; одиночный cd /testbed восстанавливает флаг. При неопределённости относительные имена исключаются. Это консервативное приближение: составной cd /testbed && ... может отключить дальнейшие относительные чтения. Алиасы, симлинки, вложенные оболочки, произвольные перемещения и скрытые изменения рабочей директории подробно не моделируются. При подтверждённой редакторской замене версии обновляются. Произвольные sed -i, перенаправления, Python-сценарии, git-команды и изменения файлов сторонними процессами не вызывают общей инвалидации или переноса строк. Поэтому сохранённые адреса могут устаревать. Условия надёжности при работе живого агента требуют проверки, например посредством предоставленного инструментом адреса и версии файла, подтверждения успешного чтения и сброса затронутого пути при внешней записи.


## Воспроизведение

Используется Python 3.14 с библиотеками NumPy, Brotli и встроенным compression.zstd, вместе с запечатанными исходниками серий R3–R5 в прежней структуре каталогов. Все вычисления выполнялись на CPU. Веса Kimi не запускались повторно. Все нужные для результатов предыдущие журналы, receipts и ссылки находятся в соседней папке writer; исходные публичные raw .traj повторно скачаны только в оперативную память и сопоставлены по SHA-256. Для повторного вычисления из опубликованных промежуточных данных достаточно начать с policy.py. Для независимой проверки уже сохранённых ограниченных состояний достаточно bounded.py score и checks.py.

```powershell
py -3.14 acquire.py
py -3.14 policy.py
py -3.14 score.py
py -3.14 bounded.py predict
py -3.14 bounded.py score
py -3.14 checks.py
py -3.14 inspect_disagreements.py
py -3.14 trace_reason.py
```

PROTOCOL.md, IMPLEMENTATION.md, VALIDATION_AMENDMENT.md, BOUNDED_PROTOCOL.md и LRU_AMENDMENT.md фиксируют порядок постановок. source_receipt.json связывает исходные трассы с SHA и числом проверенных наблюдений. decisions.jsonl.gz хранит изменения карт адресов по каждому событию, observed.jsonl.gz — независимые списки точных хешей строк для оракулов, items.jsonl.gz и bounded_items.jsonl.gz — каждый исход и координату. В bounded_steps_*.gz записаны SHA и размеры 3386 состояний каждой из пяти ветвей; bounded_cuts_*.gz содержит по 778 полных контрольных состояний. Независимый аудит checks.py сверил каждый сохранённый блоб с соответствующим пошаговым хешем и пересчитал интервалы по репозиториям. Оба технических сбоя до открытия ограниченных исходов сохранены в bounded_setup.log и bounded_metadata_setup.log: Windows-процессу явно задан путь к локальному модулю и для новой операции чтения зарегистрированы поля метаданных существующего ранжировщика. Первичные исправления не изменяли адресов распознавателя.

Проверка дополняет работу по интерфейсам инструментов для программных агентов. Для заявления о новизне разумно отделять регистрацию терминального чтения как довольно обычную инженерную идею от воспроизводимой постановки, показывающей объём теряемого сигнала, точность адреса и эффект на новых трассах.
