# Дополнительная проверка после основного опыта

В основном результате однозаписный кэш последней выдачи экономит запросы при последовательной обработке каждой трассы. Наблюдалась также грубая дискретность процессного таймера Windows. Отдельно проверяем два объяснения, оставляя исходный первичный результат без изменений. Зафиксирована единственная выдача на обновление, три одинаковых прогона, семь заранее перечисленных реализаций (scan, scan_memo, exact, exact_memo, deferred, deferred_memo, eager).

На тех же 31 279 обновлениях сохраняем порядок событий каждой трассы. Сравниваем обработку трасс по очереди и чередование всех трасс по номеру очередного шага. Первый сценарий благоприятен однозаписному кешу. Второй должен почти исключить повтор последнего ключа, сохранив те же входные изменения и эталоны. Холодный старт начинается с отдельно созданной пустой базы в каждом проходе. Измеряем аппаратные циклы текущего Windows-потока QueryThreadCycleTime и настенное время транзакции вместе с построением выдачи. Проверка результата проводится за таймером. Стоимость остатка служебного вызова измерителя входит одинаково во все плечи. Основная диагностическая пара scan/scan_memo для каждого порядка. Добавляем отношения scan/deferred, scan_memo/deferred_memo, eager/deferred, exact/deferred и exact_memo/scan_memo. Тем же парным бутстрэпом по траекториям с 10 000 выборок показываем условные интервалы. Три повтора используют перестановку порядка плеч в каждой группе по заранее заданному seed. Аппаратные циклы не переводятся в наносекунды.
