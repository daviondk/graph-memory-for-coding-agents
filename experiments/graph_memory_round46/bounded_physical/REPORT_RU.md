# Сокращение числа запросов к графу и фактическая цена SQLite

**Переход с 490 точных SUM к 343 не ускорил основную операцию.** На 31 279 границах из 1 207 траекторий ISETrace при одной выдаче всех признаков на группу отложенная проверка K=3 заняла 584 мс за проход, ранняя — 570 мс. Отношение раннего времени к отложенному составило **0,975 [0,922; 1,006]**. По отдельным повторам — 0,987, 1,015 и 0,929. Оба файла занимали 332 КиБ, включая базовую таблицу весов пар и обратный индекс. Результат по 30-процентному сокращению справочных запросов воспроизведён на уровне каждой траектории. Все плечи хранили одинаковую авторитетную таблицу пар. В колонке обращений учитываются дополнительные SUM/EXISTS для восстановления локальных состояний. Обычные чтения и запись основных таблиц включены во время. У односканового плана основной файл содержал 27 страниц таблицы пар, 24 страницы обратного индекса и одну страницу схемы. У отложенного добавилась ещё 31 страница состояния. В эксперименте с отключённым автоматическим checkpoint файл WAL перед усечением составил 84 736 072 и 127 823 032 байта соответственно. WAL, SHM, полезное заполнение страниц, свободное место, закрытие, повторное открытие и затраты CPU по каждому повтору сохранены в [физическом журнале](results.json). Размеры WAL зависят от политики checkpoint.

**Цена счётчиков при обязательном графе.** Без кэша отношение полного времени однопроходного плана к отложенному равно 0,689 [0,651; 0,712] при одной выдаче и 0,807 [0,800; 0,814] при четырёх. При одинаковом однозаписном кэше для обеих политик получено 0,667 [0,637; 0,685] и 0,689 [0,683; 0,695]. Отдельное приложение хранителя могло бы обойтись одной таблицей точных счётчиков, если взвешенные пары вообще не нужны. В этой работе их сохранение задано общим контрактом. На ноутбуке, большем и более плотном графе или при точечном чтении отдельной вершины соотношения могут измениться. [Исходные схемы SQLite](../../graph_memory_round44/sql_flow/REPORT_RU.md)

## Независимые проверки двух объяснений

**Локальность запросов.** При чтении всех флагов сразу после каждой группы и завершении одной трассы до открытия следующей однозаписный кэш дал 18 558 попаданий. При обходе тех же историй по номеру шага и чередовании активных трасс осталось 37. Последовательность событий внутри каждой траектории сохранена. Отношение времени scan/scan с кэшем изменилось с **1,172 [1,160; 1,184]** до **0,979 [0,974; 0,983]**. Тем самым направление эффекта кэша поменялось. В то же время прямой проход по парам потребовал 0,726 [0,722; 0,731] аппаратных циклов отложенных счётчиков при последовательном порядке и 0,716 [0,709; 0,723] при чередовании. Для первичной пары ранний/отложенный отношение циклов было 1,016 [1,011; 1,020] и 0,998 [0,990; 1,005]. Эта дополнительная проверка использует отдельный зарегистрированный эксперимент и таймер Windows QueryThreadCycleTime; необработанные значения циклов сохраняются по траекториям. [План](INTERLEAVE_PROTOCOL_RU.md) · [Результаты](cycle-results.json)

**Устранение избыточных битов.** В первичном K=3 два выведенных флага хранятся рядом с двумя состояниями, чтобы максимально удешевить SQL-выдачу. Отдельно записали только код 7a+b из диапазона 0…48. Для выдачи можно вычислить флаги в SQL или обратиться к общей таблице из 49 значений в Python. Физический файл обеих версий сократился с 332 до **324 КиБ**. Полезная нагрузка строк вспомогательной таблицы упала с 77 470 до 71 961 байта. Прежнее отложенное время к варианту с таблицей из 49 значений составило 1,049 [1,022; 1,098], к варианту с SQL-вычислением 1,034 [1,007; 1,083]. Отношение scan/плотный SQL составило 0,733 [0,703; 0,788], scan/плотная таблица — 0,744 [0,713; 0,799]. Здесь есть небольшой физический выигрыш от прямого кодирования; односкановый план на этом разреженном графе сохраняет преимущество одновременно по объёму и настенному времени. ## Границы и воспроизведение

В основном эксперименте фактически проверены **4 691 850** полных выдач, затем ещё 72 420 конечных состояний после повторного открытия баз. Все совпали с независимой проекцией. Три технических повтора агрегированы внутри 1 207 связанных траекторий; интервалы получены 10 000 совместными перевыборками целых траекторий. Они характеризуют разброс этой нагрузки и режимов исполнения на одном хосте. Для режима с четырьмя чтениями каждое чтение действительно строит отдельный клиентский словарь. Расход RAM для кэша учитывается отдельно, максимум составил 56 записей в единственном сохраняемом словаре. Измерение не охватывает извлечение связей из сырой траектории, конкурентных клиентов, произвольные запросы к графу и работу LLM. Траектории OS-агента в ISETrace синтетические, вызовы инструментов в них исполнены.

Для проверки переносимого результата нужны Python с NumPy; команда `python -B verify.py` проверяет входы, полные конечные таблицы, покластерные обращения и статистику. Для полного повторения измерений на Windows используется SQLite со встроенной виртуальной таблицей dbstat: `python -B reproduce.py <новый-каталог-на-диске>`. При первом техническом запуске системный Python после стадии выполнения не смог получить статистику страниц, потому что в его SQLite отсутствовал dbstat. Публикуемые измерения заново выполнены в окружении SQLite 3.50.4 с предварительной проверкой dbstat.
