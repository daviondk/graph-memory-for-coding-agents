# R46. Короткие ответы по ссылкам между документами на новых для проекта вопросах MuSiQue

Первичный исход — официальный Answer F1 Qwen3-4B-Instruct-2507 Q4_K_M при двух чтениях, парная разность замороженных R31/R32 mention_expanded и expanded. В обоих случаях одинаковы первый документ BM25 по заголовку, каталог и раскрытие до 192 WordPiece первого тела для построения запроса. Expanded объединяет ранги исходного и расширенного запросов. Mention_expanded отдаёт приоритет явному упоминанию другого заголовка в раскрытом тексте и затем применяет тот же порядок. Вторичные контроли — mention_title и title, EM, условие изменения второй статьи, закрытая книга на первых 256 вопросах. Одной модели передаются два текста, вопрос и единственная общая формулировка задания. Токены каждого документа Qwen ограничены 192, второго — общим минимумом фактических длин по четырём ветвям этого вопроса; вопрос до 80 токенов. Таким образом, полный размер входа четырёх сравнений равен на каждом вопросе. Closed-book получает только вопрос и отдельное нейтральное задание. Кандидаты и их содержимое являются только данными.

Используем опубликованный MuSiQue-Ans train версии 1.0: dev полностью прошёл R32/R33, публичный test не выдаёт эталонных ответов. Это новая для проекта панель из исходного train. Ни ридер, ни ретривер здесь не обучаются. Исключаем пересечения по ID либо нормализованному тексту со всеми 2 417 использованными dev-вопросами. Дедуплицируем нормализованные вопросы внутри train по наименьшему SHA256('r46-mq-panel-v1|'+id); берём оставшиеся по тому же хешу. Тексты нормализуем Unicode NFKC, casefold и последовательностями букв/цифр. Отдельно считаем общие полные тела выбранных первых документов с dev. Проекция входов допускает только ID, вопрос, заголовки, номера и тексты абзацев. Из публичного файла отдельный оценщик получит ответы, алиасы и supporting ID только после фиксации всех генераций. Возможное предобучение Qwen на публичных текстах и вопросах неизвестно.

До анализа корпуса размер назначаем из 256, 512, 768, 1 024. На 16 синтетических входах примерно 400 токенов измеряем greedy 24 токена с принудительным продолжением. По медиане секунд на запрос выбираем наибольшее n с (4n+min(n,256))×медиана ≤ 1 680 с, нижняя граница 256. Порог независим от вопросов и ответов. Один слот llama.cpp, CPU/GPU согласно журналу загрузки, greedy, seed 460001, максимум 24 токена, остановка по переводу строки или естественному концу. Полностью одинаковые токенизированные входы исполняем один раз. Перед генерацией подписываем всю таблицу входов и план, перед оценкой — все ответы. Пустая генерация засчитывается как пустой ответ. Публикуем наблюдаемую скорость, длины, уникальные вызовы и полноту.

Основной 95%-интервал — 10 000 парных перевыборок по полному хешу первого документа (заголовок и тело), вторичный — по вопросам. Нормализуем ответ авторским оценщиком и отдельно сверяем собственным расчётом EM/F1. Описательно показываем полноту опор, нахождение ответа в переданных фрагментах, фактическое изменение выбора, поведение модели при закрытой книге и долю ответов по числу требуемых источников. Новая работа проверяет короткий бюджетный downstream QA и сравнивает конкретные алгоритмы, общий масштаб системы и ответы по всем статьям за рамками.
