# Индекс выдачи при пересмотре веса одного источника

Для интерактивного пересмотра доверия к источнику построили SQLite-представление. По паре «запрос–источник» оно хранит точки, в которых меняется оптимальный пакет свидетельств. Пользователь выбирает поправку; один поиск предшествующего ключа возвращает полный упорядоченный список ID. В численном примере домен от −0,25 до +0,25 в Q32 содержит **2 147 483 649** возможных значений на источник.

**Почему можно сжать диапазон.** У фиксированного пакета полезность — аффинная функция поправки. Если один пакет предпочтительнее любого соперника на двух концах отрезка, то он сохраняет это свойство на всех внутренних точках. Один общий порядок полных пакетов разрешает ничьи. Для различных концевых пакетов наклоны возрастают; пересечение их прямых позволяет делить отрезок. Соседние целые значения проверяются отдельно, в том числе когда предпочтительный при ничьей пакет существует ровно в одной точке. Варианты с одинаковым наклоном не могут последовательно сменять друг друга при неизменном правиле равенства. Поэтому число различных победителей на один источник ограничено числом допустимых количеств его выбранных необязательных фрагментов. Аффинная постановка параметрического рюкзака известна; здесь реализовано точное обслуживание полных пакетов памяти в фиксированном ранговом префиксе. [Алгоритм](view.py) · [Исходные условия](PROTOCOL_RU.md) · [Параметрическая оптимизация](https://www.sciencedirect.com/science/article/abs/pii/S0020019016301843)

На **40 проекциях, 2 528 источниках** индекс содержит **5 426 отрезков**, самое большое число на источник — четыре. Полные ответы часто совпадают, поэтому физически хранятся 2 763 различные последовательности ID. Для построения понадобилось 12 592 прямых решения, около **1,31 с** на этом компьютере и **740 КиБ** для базы. Во всех **91 748 проверках** на случайных весах и концах интервалов выдача совпала с прямым нативным решателем. Интервал, содержащий исходный нулевой вес, для всех 2 528 источников совпал с независимым расчётом через динамическое программирование по числу выбранных фрагментов. При новых весах исходный решатель занимал в **33,81 раза** больше времени, чем SQLite-поиск, 95% парный кластерный интервал **[29,04; 38,05]**. При повторении восьми весов простой прогретый кэш точных ответов был **в 5,32 раза быстрее SQLite** [4,94; 5,70]. Все планы возвращали байты полного упорядоченного набора. Для первого сценария совокупная оценка окупаемости начального построения относительно сильного нативного контроля — **18 444 запроса**, или в среднем **7,30 обращения на пару «запрос–источник»** при таком распределении нагрузки. Оценка зависит от оборудования, реализации и повторяемости запросов. Инициализация признаков, оценка текстов и сетевые задержки здесь отсутствуют. [Протокол усиленного контроля](TIMING_CONTROL_RU.md) · [Результаты усиленного контроля](control-results.json)

В первичном эксперименте полный расчёт с упаковкой ID в Python занял 83,00 мкс на выдачу. SQLite-сертификат только для исходного пакета с пересчётом для изменившихся результатов занял 38,21 мкс, SQLite-индекс всех пакетов — 2,36 мкс. Проведено по 80 896 измеренных чтений для каждого метода в каждом заявленном режиме. Во втором опыте на новых весах у кэша точных значений не было попаданий, для повторов после прогрева попадания составили 100%. [Первичный замер](results.json) · [Пооперационное сравнение](control-times.json.gz)

Измерения относятся к управляемым изменениям одного источника в одном снимке. Вне диапазона, при одновременных изменениях нескольких источников либо изменении ранга, цен или базы полезностей потребуются другие условия обслуживания. События пересмотра имитировались на реальных проекциях, влияние на ответы пользователя здесь не оценивалось. Для автономной сверки выполнить `python -B verify.py`. Полное воспроизведение требует вход R39, результаты соседнего source_sensitivity и C++17; последовательно запустить `view.py`, `analyze.py`, `timing_control.py`, `control_analysis.py`.
