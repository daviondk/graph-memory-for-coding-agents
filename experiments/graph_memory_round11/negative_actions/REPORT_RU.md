# Что происходит с неуспешными поисками реальных кодовых агентов

Проанализированы **6 132 действия в 163 публичных траекториях** SWE-agent из пяти репозиториев. В семи случаях редактор явно сообщил об отсутствии точного пути. Все семь путей оставались недоступны в опубликованном исправлении. Дополнительно обнаружены 29 уникальных поисков по имени или тексту, для которых журнал зафиксировал пустую выдачу, а независимый повтор подтвердил отсутствие на исходной версии Git. Три из этих поисков стали успешными после изменения кода. Сохранение запроса вместе с областью поиска и проверка добавленных строк выявили все три изменения. Сигнал «агент в ближайших действиях снова упомянул искомую строку» преимущества над случайным выбором при таком же размере памяти не дал.

## Данные, протокол и воспроизведение исхода

В выборку целиком вошли доступные ранее зафиксированные панели из SymPy, Sphinx, matplotlib, scikit-learn и Astropy. У 65 траекторий Kimi-transfer было 2 407 действий, у 76 Kimi-writer — 2 504, у 22 Claude — 1 221. Задачи между панелями различны. Ранее эти журналы использовались для исследований чтения кода. Для текущего исследования заранее определены допустимые команды, правила отбора задач и бюджеты памяти. Шаги сопоставлены через идентификатор вызова и исходную траекторию. Контрольные суммы всех 163 оригиналов совпали с зафиксированными SHA256. На 49 шагах однозначно сопоставить вход и ответ не удалось. [Протокол](PROTOCOL_RU.md) · [Популяция и прямые ссылки на первоисточники](roster.json) · [Проверка загрузок](receipts.json) · [Разбор покрытия по причинам](coverage.json).

Разделение по качеству наблюдения оказалось существенным. Штатный grep возвращает 1 при отсутствии совпадений и 2 при ошибке. В этих журналах ответ оболочки о завершении без вывода часто не включал числовой код. Поэтому 7 явных диагностик редактора образуют строгий слой. Дополнительный слой охватывает 34 события без вывода (33 текстовых поиска и один поиск имени файла), из них 32 уникальных внутри задачи. Три запроса обращались к локально сгенерированному HTML, который отсутствовал в обоих деревьях Git. Остались 29 подтверждённых запросов по 17 задачам всех пяти репозиториев. Длинные конвейеры, неподдерживаемые регулярные выражения, нестандартизованные ошибки и нераспознанные действия исключались. Частота семи событий является нижней оценкой покрытия принятой грамматики. [Уточнение о кодах возврата](ANNOTATION_RU.md) · [Исходные входы и ответы для всех 41 событий](action_notes.json) · [GNU grep, коды возврата](https://www.gnu.org/software/grep/manual/html_node/Exit-Status.html).

До получения новых исходов записаны неизменяемые ключи и предсказания. Для 22 задач получены официальный base_commit SWE-bench и фактический merge SHA публичного PR. Один и тот же запрос проверялся на обоих Git-деревьях. Результат 78 обращений дополнительно сверялся по содержимому объектов Git независимым способом. У 12 из 22 задач исходный SHA являлся непосредственным родителем merge. На подвыборке с прямым родством в дополнительном слое из 14 запросов изменились 2, точный ключ дал 2 повтора, наблюдение области — 8. Отдельная проверка каждого из трёх обнаруженных изменений показала, что искомой строки также ещё не было в первом родителе merge. [Снимки и PR](git_pairs.json) · [Зафиксированные предсказания](pre_oracle.lock.json) · [Пооперационные исходы и независимая сверка](checked_rows.json) · [Анализ чувствительности](sensitivity.json).

## Что хранить и когда перечитывать

Единица сравнения — один прежний отрицательный запрос, который гипотетически нужно повторить после обновления. Для содержимого ключ включает литерал, область, флаги и способ поиска. Политика по области учитывает изменённые пути. Политика по ключу проверяет появление нужного пути либо совпадение в добавленных строках изменившегося файла. При отсутствии записи в памяти всегда выполняется полный поиск. Таблица показывает число таких повторных обращений и число пропущенных изменений значения.

| Политика | 7 строгих путей, повторов / пропусков | 29 подтверждённых пустых запросов, повторов / пропусков |
|---|---:|---:|
| Использовать прежний результат при каждом обращении | 0 / 0 | 0 / 3 |
| Выполнять запрос заново | 7 / 0 | 29 / 0 |
| Учитывать изменение области поиска | 4 / 0 | 14 / 0 |
| Хранить все точные ключи и проверять изменения в diff | **0 / 0** | **3 / 0** |
| Хранить ключ, если агент упомянул его в следующих трёх действиях | 6 / 0 | 21 / 0 |
| Детерминированный случайный отбор при равной исходной квоте | 6 / 0 | 19 / 0 |

На дополнительном слое полные дескрипторы 29 подтверждённых запросов заняли 4 421 байт в компактном JSON. На принятие решений по точным ключам обработано 27 193 байта диффов с учётом повторного обращения к одинаковому диффу. Объём содержимого файлов в трёх повторно запрошенных областях составил 71 284 байта. Для полного пересмотра это 7 839 965 байт, где один файл мог входить в несколько запросов. Это объём объектов в областях поиска. Реальный grep может завершаться раньше. Измерений wall-clock, токенов и нагрузки в продолженной LLM-сессии здесь нет. Диспетчер, история инструмента, индексы Git и построение diff не входят в размер записи. [Измерения и все контрольные варианты](summary.json).

В дополнительном слое отбор по трём действиям сохранил 11 из 32 исходных ключей. После проверки доступности исходного дерева остались 10 из 29 ключей и 1 572 байта хранения. Исходный случайный контроль также сохранял 11 из 32, все его ключи удовлетворили проверке доступности. Для сравнения при строго одинаковой конечной квоте посчитано полное распределение случайного выбора десяти ключей с сохранением размеров трёх панелей. Ожидается 20,21 повтора, наблюдалось 21 по сигналу агента. Из трёх будущих изменений сигнал раннего упоминания выделил два. В одном случае агент, использующий только этот сигнал, должен был бы выполнить полный поиск из-за отсутствия записи. В анализируемых траекториях 19 из 29 подтверждённых ключей встречались во входах агента после окна в три действия. Точного повтора идентичных аргументов на этом более позднем участке не было. Симуляция отвечает на вопрос об актуальности записи. Частоту реальных запросов после обновления она не оценивает. [Распределение сравнения при равной квоте](sensitivity.json).

## Как агент действительно восстанавливался после ошибочного пути

В отдельной разведочной проверке рассмотрен первый успешный просмотр отслеживаемого файла в шести следующих действиях после каждой из семи строгих диагностик. В каждом случае проверены заголовок ответа инструмента, нумерованное содержимое и соответствие первым показанным строкам файла в исходном Git SHA. Во всех семи случаях агент открыл подходящий по структуре другой путь. В шести из них агент предварительно просмотрел каталог. Пять эпизодов из семи повторяют одну и ту же ошибку с `sphinx/ext/autodoc.py`. Остальные касаются `sphinx/locale.py` и `simplify/fu.py`. Это три разных ошибочных адреса в двух репозиториях. [Протокол разведочной проверки](RECOVERY_PROTOCOL_RU.md) · [Фактические следующие действия](recovery.json).

| Как предсказывался следующий успешно открытый файл | Выдано кандидатов | Совпало из семи |
|---|---:|---:|
| Повторить исходный путь | 7 | 0 |
| Проверить обычное представление Python-пакета X/__init__.py вместо X.py | 6 | 6 |
| Добавить недостающий префикс, если старое дерево содержит единственный путь с таким суффиксом | 1 | 1 |
| Переиспользовать исправленный путь из другой задачи того же проекта, смерженной раньше и имевшей меньший номер PR | 4 | 4 |
| Сначала проверить Python-пакет, затем уникальный суффикс | 7 | 7 |

Переиспользование перехода удалось только для одного повторяющегося адреса Sphinx. Проверка представления Python-пакета требует одной проверки известного пути. Поиск уникального суффикса в нашей реализации использовал полное старое Git-дерево. Этот дешёвый контроль объясняет все семь переходов на небольшой выборке. Пока нет свидетельства, что запоминание исправленного адреса лучше простого правила навигации. Остаётся открытым вопрос, помогают ли сохранённые исправления при произвольных переименованиях, нескольких правдоподобных кандидатах или дорогом разрешении имени.

## Границы результата и следующий опыт

Для отсутствующего текстового совпадения появление новой строки в обновлённой области часто можно обнаружить непосредственно из diff. Эффект на трёх запросах согласуется с определением инкрементального поиска. Он даёт проверяемую контрольную политику с измеримой ценой, а приоритет идеи учёта изменённых строк уже установлен в инструментах Git. Качество исправления кода, скорость решения issue или улучшение результата агента на общем бенчмарке здесь не измерялись. Три изменившихся случая относятся к дополнительному слою с восстановленным объективным результатом. Все строгие случаи принадлежат Kimi. Нельзя переносить оценку на произвольные шелл-команды, пользовательские артефакты вне Git или на распределение запросов другого агента. [Описание поиска по диффу в Git](https://git-scm.com/docs/git-diff).

Следующий различающий эксперимент — записывать в стенде агента точный exit-код, cwd, флаги, источник отслеживаемых и локально созданных файлов, а затем до обновления случайно выдавать агенту либо точную запись, либо только область. Чтобы измерить выигрыш в реальной работе, нужны задачи, где естественно возникает повторный запрос, и одинаковые бюджеты действий. Исходы для сравнения — повторные обращения, суммарная стоимость поиска и доля решённых задач с независимыми тестами.

## Воспроизводимость

Использованы локальные read-only данные прошлых панелей, анонимно доступные исходники траекторий, публичные GitHub PR, Git 2.49.0.windows.1 и Python 3.14.4. Для полного повтора скопируйте сценарии и Markdown-протоколы в новый соседний каталог под graph_memory_round11 и выполняйте команды там. Это сохраняет ссылки на входы из прошлых панелей и исходные хеши готового опыта. Выгруженные траектории проецируются в локальные сжатые файлы с входами и ответами инструментов. Каждый полный оригинал можно восстановить по URL и SHA. Для автономной проверки существующего набора достаточно `summary.py`; утилиты Git используют локальные объекты. Повтор загрузки исходников и нового поиска метаданных требует интернета.

```text
python -B harvest.py
python -B classify.py
python -B git_pairs.py
python -B replay.py predict
python -B hydrate.py
python -B replay.py score
python -B recovery.py
python -B summary.py
python -B sensitivity.py
```
