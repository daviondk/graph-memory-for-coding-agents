# Нейронное ранжирование пар HotpotQA после отзыва источников

Проверяем, сколько записей нужно сохранить, чтобы вернуть ту же пару документов, что и при полном поиске с фиксированными весами. Условия поиска и удаление источника определены на уровне ранжирования документов. Метрика качества пары относительно поддерживающих фактов размечена отдельно.

## Данные и заранее выбранный объём

Берём HotpotQA validation distractor, ослеплённые поля question, titles, sentences в исходном порядке из R31/support_pairs. Замораживаем вопросы, содержащие ровно десять документов, в порядке SHA256 от UTF-8 строки «r31-native-beam-v1/» и id. Первые четыре образуют группу для оценки стоимости и репликации, следующие четыре — отдельную фиксированную группу. Разрешена остановка после готового вопроса по 90 минутам CPU-работы (настенное время) либо свободной RAM менее 3 GiB. Незавершённые задания обозначаются отдельно. На первом вопросе физически запускаем исходный поиск также после удаления первого документа исходной первой ступени. Качество модели, кэша и доступ к меткам не служат критерием продолжения. Итоги показываем по обеим группам и вместе. Измеряем время каждого полного графа, число оценённых пассажей/пар и максимальную рабочую память процесса. CPU float32, максимум 2 потока, ниже обычного приоритета. Норматив для N=8 — восемь независимых единиц; 56 сценариев каждого вопроса зависимы. Корпус поиска содержит 7405 вопросов.

## Источник баллов и два разных поиска

Используем код Beam Retrieval Zhang et al., официальный репозиторий commit 902980bfb5bd47a963569ab9c3621fd5ae81204a, авторский HotpotQA beam=2 checkpoint из GitHub issue #1. В официальной выпущенной таблице находится единственная пара на вопрос. Для нашей задачи нужны все 45 несортированных комбинаций. Используем исходный forward, обученные совместные logits второго шага, beam=10, FP32 inference. Сохраняем сырые баллы обеих голов и ориентацию пары, установленную очередностью документов первого шага. Детерминированно упорядочиваем точные равенства одинаковых scores по исходным индексам и регистрируем коллизии. Архитектура, удаление конечного «?» в запросе, склейка title с предложениями, маска SEP и обрезка до 512 — авторские. Отдельно сверяем исходный beam=2 в полном пуле с официальной top1-таблицей, чей точный checkpoint в JSON не записан.

1. Фиксированный полный порядок всех пар. После каждого исключения не более двух документов сравниваем полный скан, первые шесть, первые K при K=размеру точной семьи, пары четырёх лучших документов из hop1, algebraic representative family и дерево реализуемых победителей. Основная метрика — доля состояний, возвращающих точную пару при ровно двух удалениях, с числом записей и результатами по каждому вопросу. Все 0/1/2 удаления перебираются. Повторяем семейства/контроли R31/support_pairs.
2. Исходный beam=2 расширяет лишь два возможных первых документа (17 пар). После удаления сравниваем фильтрацию исходных 17 против нового выбора двух первых доступных документов и повторного расширения поиска. Для каждого состояния отдельно сравниваем новое нативное beam=2 с фильтрацией полного исходного порядка и с полной совместной выдачей. Первый шаг оценивает каждый документ независимо. Относительный порядок оставшихся документов сохраняется, поэтому можно восстановить повторный поиск из 45 попарных баллов при сохранённом порядке первого шага. Проверяем на первом вопросе прямым авторским forward после удаления. Случаи расхождения и точность компактных представлений приводим раздельно.

Первая цель измеряет воспроизведение решения полного ранжирования. Вторая устанавливает цену изменения доступной области поиска. Ссылки на поддержку ответа присоединяем только после подписи прогнозов. Для модельного качества указываем точное совпадение двух supporting titles по варианту и число вопросов. В ресурсы кэша не включаем расходы на первичное вычисление баллов; они показаны отдельно. Эта панель не воспроизводит общую метрику модели на всех 7405.
