# Какие первичные строки действительно доходят до следующего кодового агента

Проверяем естественную передачу Handoff Debt для 37 benign-задач научных Python-репозиториев, совпавших с публичным SWE-bench Verified по текущему R27 allowlist. Из таблицы runs до исходов были известны 1 032 основных, 2 052 robustness и 112 повторных takeover runs, по четырём представлениям. По одному примеру схемы установлены официальные поля FileEditorObservation/command=view и исходная нумерация cat -n. Перед вычислением результатов зафиксированы следующие правила. Не используем финальные исходы проверок или patch/gold, содержимое закрытых чатов, скрытые рассуждения или команды для исполнения. Данные — публичные сохранённые траектории. Основная выборка — main_takeovers. Robustness и repeat описываются отдельно, их issue могут повторять основную.

1. Соединяем готовый handoff по run_id с первым настоящим входным сообщением пользователя у successor. Проверяем тождество текстов по SHA-256. Переданным считаем то, что есть в фактически доставленном вводе, а дополнительной передачей от первого работника — лишь содержимое размеченной секции PREVIOUS AGENT … BEGINS/ENDS; общий issue и ввод состояния доступны всем. Проверяем согласованность четырёх видов и считаем отдельные пропуски. Не считаем неоднократные запуски отдельными исходными задачами.
2. Из predecessor берём только фактически возвращённый tool observation FileEditorObservation, command=view, успешный, production Python, номер и полный текст строки в формате «cat -n». Берём исключительно step ≤ checkpoint.step, как в коде авторов, и только /testbed/ или /workspace/... путь, корректно связанный с отпечатком файла. Каждая строка NFC не нормализуется, сохраняются все байты её текста без EOL/выводимой слева нумерации. Информативная строка содержит 24–320 UTF-8 байт и минимум три различные буквенные/идентификаторные последовательности, не пустая и не служебная лицензия или номер. Выводы shell и редактирования в основную метрику не входят.
3. Сильный причинный контроль задачи выбора — будущее чтение одной и той же repo_only траектории. Для каждой matched-группы initial_run_id, checkpoint_id, successor, subset, attempt имеется одна и та же будущая цель для всех offline-политик. Цель — первый успешный direct view production .py у фактического repo_only successor; две опоры — первая и последняя информативные различные строки этой выдачи. Если у самого первого валидного view менее двух строк, фиксируется исключение, последующий удобный view не подставляется. Если данных чтения нет, метрика не определена и знаменатель публикуется. Отдельно считаем естественное повторное чтение в каждом из четырёх реально выполненных вариантов с его собственным первым view. Разница между этими естественными когортами не является эффектом подачи заметки.
4. Первичная метрика — точная доступность **обеих** прошлых опор в переданной записи. По каждой цели считаем также одну/долю строк, исходно были ли обе реально прочитаны predecessor по тому же пути, номеру и SHA, были ли обе буквально переданы. Для нативного ввода строгое доказательство — в нужной части handoff наблюдается заголовок чтения точно того же пути и соответствующая пронумерованная строка. Это требование чувствительно к формату, поэтому вторично отдельно проверяем совпадения полного исходного текста с любым местом дополнения и пары текстов независимо от адреса. Подходящий пересказ без буквальной цитаты не признаётся ошибкой решения задачи. Заголовки и исходные адреса из будущего чтения недоступны политикам. Проверяются различия между чтением объекта, отправленным текстом и повторным открытием у получателя.
5. К измерению нативных промптов добавляем контролируемый единый лимит 512 BERT WordPiece. Журнал сырых исходных чтений сериализуем детерминированно в адресные записи «[path:line] исходная строка». Один и тот же токенизатор и формат для всех политик, строки выбраны пока следующая помещается, нецелая строка пропускается. Контроли — последние по времени источники, лексический BM25 по issue на line+path, приоритет строк, увиденных в нескольких отдельных событиях. Основной кандидат — RRF 1/(60+rank) трёх порядков (лексика, недавность, повторные наблюдения). Сильный контроль — RRF первых двух без повторов. Фиксируем стабильную развязку равенств по строковому адресу и SHA. Никаких обучаемых параметров и подбора по будущим чтениям. В native естественный токен-бюджет отличен. Короткие представления не объявляются эквивалентными всем исходным ресурсам агента. Если новый метод хуже базового, соответствующий результат публикуется.
6. Единица веса — issue, внутри все eligible matched repo_only цели имеют равный вес. 10 000 парных bootstrap целыми issue, seed 31031. При очень малом числе исходных задач положительный эффект останется исследовательским. Публикуем расходы пересылки реальных WordPiece (и байты), знаменатели, полную достижимость из предшествующего чтения, число исходно различных сообщений и прозрачные ограничения на источник: это передача двум действительным последовательно работающим агентам, но выбранные координаты не означают противоречивые факты или необходимость для успешного исправления.
