# Что сохранять при первом вопросе, если следующий может измениться

В 793 траекториях ISETrace встретилось ровно два разных тестовых вопроса. Взяли реально показанную память первого из них и предъявили второй. На SQuAD так же выбрали первый вопрос по каждой из 48 статей и предъявили по 11 других вопросов, всего 528. Первенство определялось хешем до оценки. Это реальная смена формулировки на одном источнике, но синтетический порядок вопросов. Поиск проводился только по блокам, которые агент уже получил для первой формулировки. Вся область записи составила 22 133 окна ISETrace и 1 034 окна SQuAD.

Полный поиск по новому вопросу требует частот его слов в окнах. В который момент их стоит сохранить? Сравнили полный инвертированный индекс и выборочное хранение. Последнее оставляет при записи частоты слов первого вопроса, глобальные частоты документов, максимум остальных частот в каждом окне и 256-битный Bloom-фильтр. Для нового вопроса оно перечитывает исходную запись только там, где верхняя оценка ещё допускает победу. Каждая реально возвращённая строка и её размер фиксируются при `SELECT` в SQLite.

**Точность.** Все шесть точных альтернатив, включая обычный перебор допустимых окон, воспроизвели тот же номер лучшего окна, что независимый исходный BM25, на всех 1 321 запросах. Когда сохранили только частоты старых слов и вовсе отказались от догрузки новых, правильный адрес выбрали на 475/793 и 89/528; правильное окно — в 418 и 76 случаях. При настоящем однократном обращении к источнику полный BM25 довёл число полностью покрытых наборов с 414 до 435 на ISETrace, приближённая проекция — до 430. На SQuAD результаты составили 177 → 217 и 177 → 193. Для SQuAD засчитывалось полное покрытие любого официального диапазона ответа, для ISETrace требовалось покрыть все доказательства. [Адреса и результаты следующего чтения](next-results.json)

**Почему отсечение точно.** Для длины окна и фиксированной IDF вклад слова в BM25 монотонно возрастает с его частотой. Известный счётчик даёт точный вклад. Если битовая сигнатура исключает слово, вклад равен нулю. В остальных случаях вместо неизвестной частоты можно подставить максимальную частоту несохранённого слова этого окна и получить верхнюю границу. Окно физически перечитывается только пока его граница может превзойти уже подтверждённого кандидата. При равенстве сохраняется исходный приоритет окна. В отличие от приближённого отказа от новых слов это сохраняет точный ответ для произвольной следующей формулировки и данной функции ранжирования. Идеи верхних оценок релевантности и блочных сигнатур известны в информационном поиске; здесь проверяется их практическая цена при записи эпизода агента. [Работа по двухуровневой оценке запросов](https://research.google/pubs/efficient-query-evaluation-using-a-two-level-retrieval-process/) · [Signature files](https://www.vldb.org/conf/1985/P165.PDF)

**Какие затраты действительно уменьшились.** По сравнению с тем же Bloom без границы среднее сокращение чтения исходных байтов — 1 070 для ISETrace (скорректированный интервал [960; 1 179]) и 5 532 для SQuAD ([5 170; 5 869]). Это логические байты строк, выданных движком. При расчёте стоимости «одна запись состояния плюс все последующие физические возвраты исходных строк» в среднем на вопрос получилось 3 319 и 2 666 байтов. Полный индекс потребовал 2 185 и 393 байта соответственно: у статьи SQuAD стоимость одной записи индекса амортизируется на 11 вопросов. Исходный журнал общий для способов, его хранение не исчезает. Показатель, ориентированный только на экономию перечитывания относительно полного сканирования, переоценил бы преимущества проекции. [Размеры, попадания и кластерные интервалы](results.json)

Для уже раскрытых объектов медианное время выбора у проекции с Bloom составило 74,9 и 185,2 мкс, у полностью материализованного индекса — 25,0 и 32,4 мкс. Задержки локальные, на CPU, при прогретом кеше страниц. В отдельном контроле оплачена и физическая загрузка сжатых метаданных. **Контроль с индексом по словам.** В SQLite сохранили отдельную строку для каждой пары «состояние памяти, слово». При смене вопроса БД возвращает общие координаты и списки только для слов нового запроса. Этот контроль выбрал те же окна во всех 1 321 случаях. В общей перемешанной серии его медиана составила **128 и 135 мкс** против **288 и 481 мкс** у проекции с Bloom. Суммарный ответ SQL, включая и метаданные, и исходный текст, составил **341 и 366 байтов** против **3 319 и 6 268 байтов**. Новая таблица заняла 5 050 368 байтов на диске для 841 состояния и 245 750 строк терминов. Указанный размер включает структуру SQLite. Число байтов, возвращённых запросом, измерено на границе SQL и клиента. Кеш страниц ОС был прогрет. Основная практическая граница проходит по числу уже прочитанных окон и количеству последующих запросов. На проверенной нагрузке обычный адресуемый инвертированный индекс по увиденным окнам дал более выгодный режим обслуживания.
