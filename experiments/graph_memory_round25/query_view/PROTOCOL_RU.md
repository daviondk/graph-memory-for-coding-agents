# Какую поисковую информацию записать при первом вопросе

Накапливаем только отрывки, которые агент фактически получил при первом вопросе. При смене вопроса нужно найти лучший видимый 128-токенный фрагмент по BM25 и разрешить одно расширение от конца соответствующего отрывка. Гипотеза: для точного выбора одного адреса достаточно дешёвой верхней границы балла, журнал исходных текстов приходится перечитывать лишь там, где действительно может измениться лучший кандидат.

Две популяции: все истории ISETrace с двумя или более различными авторскими вопросами среди 2 000 тестовых и все статьи 576-вопросного среза SQuAD R25/directional_open. Для каждой истории/статьи первой считаем формулировку с минимальным SHA-256 с фиксированным префиксом query-view-v1/. Остальные вопросы рассматриваются отдельно на том же изначальном состоянии записи. Порядок синтетический, формулировки реальные. При записи используются только видимые тексты, первый вопрос и длины полей. История и документ известны по постановке. Идентификаторы следующих вопросов и эталоны в выдачу не попадают. Эталон прежнего результата search — полное сканирование текстов именно первого состояния по каждому новому вопросу. Смена вопроса может требовать другого корпуса или иных документов; наш эксперимент изолирует чтение уже имеющейся памяти.

Одинаковое правило BM25, те же токены и порядок при равенстве, те же расширяемые фрагменты. Для каждого сохранённого окна на этапе записи сохраняем его координаты, длину в словах, частоты слов первого вопроса и максимальную частоту любого другого слова. Для каждого слова журнала можно хранить число видимых окон с этим словом. Это компактный общий словарь DF для точной IDF нового вопроса. Сравниваем варианты:
- Полный поиск физически запрашивает все строки окон в SQLite и вычисляет все TF и DF. Сильный контроль с готовым DF сканирует только допустимые окна.
- Индекс со всеми частотами получает правильный результат без повторного чтения строк. Размер всего материализованного индекса учитываем.
- Проекция только на слова первого вопроса не догружает частоты новых слов. Проверяем, как часто её выбор ошибается.
- Точное отложенное чтение использует известные TF и локальный предел неизвестной частоты. Вклад каждого слова монотонно возрастает с частотой, поэтому сумму верхних границ можно использовать для отсечения кандидатов. Порядок при равенстве должен точно совпадать с эталонным. Проверяем варианты без фильтра, с одним 256-битным Bloom-фильтром на окно и с фильтром без отсечения по баллу. Фильтр использует четыре производных позиции хеша. Он может ошибочно допустить страницу к перечитыванию; правильность выбора остаётся проверяемой.
- Дополнительный контроль — готовые DF и отложенное чтение с фильтром и отсечением, но без сохранённых частот первого вопроса (верхняя граница максимальной частоты тогда учитывает все слова). Отделяет вклад записи под текущую задачу от обычного индекса блоков.

Первичная стоимость — байты исходного текста, реально возвращённые из SQLite для неизвестных TF, на каждый следующий вопрос. Сравнения фильтр+граница против фильтра без границы и против границы без фильтра на каждом корпусе. Парные интервалы группируем по истории или статье. Равенство индекса лучшего окна и его адреса с полным перебором требуется для каждого запроса; выбор ближайшего окна лишь в среднем недостаточен. Дополнительно — сколько преимуществ остаётся после оплаты записи индекса, фактические размеры сериализованных метаданных, число обращений и расхождение приближённой проекции. Отчёт явно указывает стоимость общего журнала и различает логические байты результата SQL и дисковый трафик. Метрики точности оценивают конкретный оператор выбора адреса.

Блочные сигнатуры, Bloom-фильтры и верхние оценки баллов давно известны в поиске и аналитических БД. Предмет проверки — их сочетание с записью сведений о виденных фрагментах, текущем вопросе и смене запроса агента при ограниченном размере памяти.
