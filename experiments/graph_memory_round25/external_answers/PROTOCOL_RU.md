# Внешняя проверка конечного ответа на QASPER

До подготовки входов и запуска Qwen фиксируем 24 документа. Берём первые 24 из официального test v0.3 по SHA256("r25-qasper-v1/doc/"+paper_id), ровно один вопрос из каждого по SHA256("r25-qasper-v1/question/"+question_id). Все выбранные вопросы остаются в знаменателе. Тип, ответ, свидетельства и результат чтения не используются для отбора. В ранее сохранённых рабочих Markdown и Python на D поиск QASPER не дал совпадений. Это перенос с ISETrace и MultiDoc2Dial на иную предметную область. Данные публичны и могут входить в предобучение Qwen.

Абстракт, отдельные разделы с разделителями абзацев и подписи иллюстраций доступны как адресуемые поля исходной статьи. Заголовок статьи доступен всем методам. По запросу стандартный BM25 с k1=1.2, b=0.75 ранжирует непересекающиеся окна по 128 WP внутри всей статьи. Три первых непустых окна дают общую исходную память с координатами символов. Метод из R24 ранжирует только уже доставленные окна, узнаёт длину поля и выбирает верхнее окно, у которого есть продолжение. Старое чтение начинает в начале этого окна (same_window), новое в правом конце содержащей его видимой объединённой области (right_edge). Максимум одного чтения 256 WP со служебной координатой, части входов сверх общего лимита обрезаются справа. Выбором управляет открытый код, без оценки эталонов и скрытой части поля. Начальный поиск по статье является затратой и доступен одинаково всем условиям.

Четыре независимых входа на вопрос. Чистая база показывает только память. В трёх других условиях после неё допускается дополнительный текст. Контроль replay повторяет начало сериализованной памяти, old читает по старому адресу, edge по новому. Выбираем максимальную общую достижимую длину всей пользовательской части в нативных токенах Qwen среди символьных префиксов с ограничением 256 WP в дополнительном тексте. Для replay используем настоящие прежние записи, повтор не добавляет новых координат. Если совпадает только пустой фрагмент, все три используют исходную базу. Нативную длину фактического chat prompt проверяем по usage, отдельно сообщаем WP и токены генерации. Чистая база проверяет влияние самого повтора и экономию токенов при полном отказе от обращения.

Reader Qwen3-4B-Instruct-2507 Q4_K_M, llama.cpp, два потока CPU, один запрос за раз, температура 0, seed 13, максимум 64 выходных токена, отдельные сообщения без истории и инструментов. Инструкция требует только краткого английского ответа, Yes/No или Unanswerable при недостаточных данных. Хешированный порядок запросов, одинаковые байт-в-байт запросы разрешено выполнять один раз. Ошибка после 3 попыток считается нулём. Исходный контекст и буквальные ответы хранятся на D в частном кэше; до оценки фиксируем хеши ответов.

Основной контраст edge минус old по официальному Answer F1, максимум по аннотациям, на всех 24. Вторичный контраст edge минус replay. Дополнительно нормализованное exact match, доли выбора Unanswerable, 95% парный percentile bootstrap по 24 документам (20 000, seed 25046), исходы win/loss/tie. Отдельно официальный F1 по типу лучшей аннотации, плюс фиксированные до предсказания группы unanimous extractive/abstractive/boolean/none/mixed. Для покрытия вычисляем по каждому непустому набору текстовых gold paragraphs долю доступных символов (по объединению координат; для повторяющихся абзацев берём лучшее вхождение), её максимум по допустимым аннотациям и индикатор полного покрытия всего набора. Абзацы без адреса считаются отсутствующими. Стандартный evidence F1 по выбранным ID касающихся абзацев приводится как сопутствующая retrieval-метрика. Отдельно считаем потолок покрытия при всей статье в памяти. Это потолок доставки свидетельств, вывод по ответу зависит и от читателя.

Это малый пилот с фиксированным бюджетом и одной локальной моделью. Прямое сравнение со статьями на полном QASPER требует 1451+ вопросов полного split по данным релиза и их условий доступа; точный размер будет извлечён автоматически. Итоги пилота не сравниваются с лидербордом.
